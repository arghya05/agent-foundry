# agent_foundry/distributed.py — Q&A

Redis-backed implementations of the framework's `*Like` Protocols (`RunBudgetLike`, `RateLimiterLike`, `ToolCacheLike`, `SLATrackerLike`, `CostLedgerLike`, plus an idempotency store, a `StateStore`, and a distributed lease) — the "any cloud, at scale" story that makes budgets, rate limits, caches, SLAs, and idempotency actually correct across N replicas behind a load balancer, not just correct within one process.

## Q1: The module docstring says an in-process budget/rate-limiter is "correct and fast for one process" but wrong across N replicas. Give the concrete failure mode this module exists to close.

If `AgentConfig.budget` is an in-process `RunBudget` and the same agent is deployed behind a load balancer across, say, 3 replicas, each replica holds its own independent counters for a given `thread_id`. A caller enforcing "$0.50 max spend per thread" would actually get up to $1.50 of real spend across the fleet if requests for that thread happen to be routed to different replicas over the session's lifetime — each replica's own `RunBudget.spend()` only ever sees the fraction of that thread's spend that happened to land on it, so none of them individually ever crosses $0.50, and the *combined* real-world spend silently exceeds the configured ceiling by up to 3x. The same reasoning applies identically to rate limiting (a "10 req/s" cap becomes an effective 30 req/s cap across 3 replicas each independently enforcing 10) — this is exactly the numeric example the module's own reasoning implies, even though it isn't spelled out as a worked example in the source comments themselves.

## Q2: Walk through `_TOKEN_BUCKET_LUA` in detail. Why must the read-compute-write sequence be a single atomic Lua script rather than separate Python-side `GET`/compute/`SET` calls?

The script reads `tokens`/`last` timestamp via `GET`, refills `tokens = math.min(burst, tokens + (now - last) * rate)`, and either denies (returns `0`, still persisting the refilled-but-insufficient state) or consumes one token and returns `1` — all inside one `EVAL` call, which Redis executes atomically with no other client's commands interleaving. If this were instead done as separate Python round-trips — `GET tokens`, compute in Python, `SET tokens` — two replicas racing on the *same* rate-limit key could both execute their `GET` before either executes its `SET`: both would read, say, `tokens=1`, both would compute "yes, I have a token, proceed," and both would then independently write `tokens=0`. The result is two requests allowed through on a single remaining token — precisely the double-spend race this class exists to prevent. Redis's single-threaded command execution model guarantees a Lua script's body runs to completion without another client's command interleaving partway through, which is exactly the atomicity a plain multi-round-trip GET/compute/SET sequence cannot offer.

## Q3: Why does `RedisRunBudget.spend()` use `HINCRBYFLOAT` rather than `HGET` + Python arithmetic + `HSET`?

`HINCRBYFLOAT` is a single atomic Redis operation that increments a hash field and returns the *new* total in one round trip, with no window for another replica's concurrent increment to be lost. If `spend()` instead did `current = self._r.hget(...)`, computed `current + amount` in Python, then `self._r.hset(...)` with the new value, two replicas spending against the same thread concurrently could both read the same starting value, both compute their own "current + my amount," and whichever `HSET` executes last would overwrite the other's update — a classic lost-update race that would silently undercount total spend and let a thread's real cumulative cost exceed its configured budget without ever being detected, since neither replica's local computation ever saw the other's contribution. `HINCRBYFLOAT` sidesteps this by making the increment itself, not just the read or the write, atomic — every `spend()` call gets back the true, fleet-wide post-increment total, which is exactly the value compared against `self.policy.max_cost_usd_per_thread` immediately afterward.

## Q4: Even with atomic `HINCRBYFLOAT`, can a distributed budget still be "overspent" in practice? Walk through why.

Yes — the atomicity of the increment guarantees the *recorded total* is always accurate, but it doesn't make budget enforcement preventive. Looking at how `orchestration.py` actually calls this: `make_think_node` calls `budget.spend(resp.cost_usd, thread_id=session_id)` *after* `config.llm.complete(...)` has already run and the real dollar cost has already been incurred — the LLM call itself was never gated on remaining budget, only the *bookkeeping and enforcement* happen after the fact. This means it's entirely possible for two nearly-simultaneous requests against the same thread, on two different replicas, to each independently pass their own pre-call checks (if any exist upstream), both execute their real, billed LLM calls, and only when both `spend()` calls land do you discover that the combined total exceeds the budget — at which point `BudgetExceeded` is raised, but the money has already been spent. This isn't specific to the distributed case (the in-process `RunBudget` has the identical "detect after the cost is incurred" structure), but multiple replicas make the race window during which two calls can both slip through *before* either one sees the over-limit signal more visible, since a single process's own sequential calls don't have this concurrent-slip-through risk to begin with.

## Q5: `RedisToolCache` requires tool results to be JSON-serializable — a real constraint the in-process cache doesn't have. What's the concrete failure mode, and why is this constraint worth documenting explicitly?

The in-process `ToolCache` (implied elsewhere in the framework) can hold a raw Python object reference — a custom class instance, a `numpy` array, arbitrary bytes — with no serialization step at all, since it's just a dict living in the same process that will read it back. `RedisToolCache.set()` calls `json.dumps(result)` before writing to Redis; if `result` is anything `json` can't natively serialize (a dataclass instance without `default=`, `bytes`, a `set`, `NaN`/`Infinity` in some strict modes, a custom object), this raises `TypeError` at cache-write time — a real, loud failure that would only surface the first time a particular tool's result happens to be non-JSON-safe, potentially long after that tool was already working fine against the in-process cache in development. The module's own comment flags this directly: "document this on any tool you expect to be cached across a fleet" — it's an explicit, acknowledged behavioral difference between the in-process and distributed implementations of the exact same `ToolCacheLike` Protocol, not a bug, but a real contract change a builder must be aware of before swapping one for the other.

## Q6: Walk through `RedisLease.acquire()`/`release()` in detail. Why does `release()` need a Lua check-and-delete instead of a plain `DEL`, and what specific bug would a plain `DEL` introduce?

`acquire(key, ttl_s)` generates a fresh `uuid.uuid4().hex` token and does `SET key token NX EX ttl_s` — the `NX` flag means this only succeeds if the key doesn't already exist, so it atomically both checks "is this lease free" and "claim it" in one operation, returning the token on success or `None` if someone else already holds it. The bug a plain `DEL` in `release()` would introduce: suppose replica A acquires the lease with token T1, then a slow operation causes A's lease to *expire* (its TTL runs out) while A is still working — replica B then successfully acquires the same key with a new token T2, believing it now safely holds exclusive access. If A, unaware its lease already expired, later calls `release(key, T1)` and that were implemented as a plain `self._r.delete(key)`, it would delete B's *active* lease (T2) — a third replica could then acquire the same key while B still believes, incorrectly, that it holds exclusive access, and now two replicas (B and the new claimant) are both driving the same protected operation concurrently. `_LEASE_RELEASE_LUA`'s check-and-delete (`if GET(key) == token then DEL(key) end`) prevents exactly this: A's stale token T1 no longer matches what's currently stored (T2), so A's release becomes a safe no-op instead of stealing B's still-valid lease.

## Q7: `RedisLease` has no renew/heartbeat method. What happens to a task whose real runtime exceeds the lease's configured `ttl_s`?

Once a lease's TTL expires, Redis's own `EX` expiry silently removes the key — there is no notification back to the holder that this happened, and no built-in mechanism in this class to extend a lease's TTL from within a long-running operation. If a task legitimately takes longer than the `ttl_s` it was acquired with, the scenario in Q6 plays out exactly: another replica can acquire the same key and start working on the same protected resource while the original holder is still mid-task, believing itself exclusive. This is a real, honest limitation — a caller must either choose a `ttl_s` generously larger than any plausible task duration (risking a long stall if the original holder crashes without releasing) or implement their own periodic re-acquire/heartbeat loop entirely outside this class, since `RedisLease` provides `acquire()` and `release()` only, with no `renew()`/`extend()` method to bridge the gap safely.

## Q8: Why is `import redis as redis_lib` done lazily inside each class's `__init__` rather than once at module top level?

The module docstring states this directly: "Requires `pip install redis` (lazily imported per class, not a base dependency of agent_foundry — nothing else in this package needs it)." This is the identical "optional dependency, imported only where actually needed" discipline `orchestration.py` applies to LangGraph and `channels.py` applies to FastAPI — importing `agent_foundry.distributed` (or even just referencing one of its class names for a type hint elsewhere) must never fail for a user who hasn't installed `redis`, and only actually *instantiating* one of these classes (`RedisRunBudget(...)`, `RedisLease(...)`, etc.) should require it to be installed, at which point a clear `ModuleNotFoundError` surfaces at the exact point of real need rather than at unrelated import time.

## Q9: The comment in `RedisCostLedger.by_tenant()` defends against `k` being `bytes` even though `decode_responses=True` was passed to the Redis client constructor. Is that a real runtime possibility, or is the code defending against something that can't actually happen?

Per the comment itself, this is an honest note about a type-stub inaccuracy, not an observed runtime bug: `decode_responses=True` is a genuine runtime setting on the Redis client that guarantees keys and values come back as real Python `str` objects, not `bytes` — but redis-py's own type stubs still type `hgetall`'s return as `dict[bytes | str, bytes | str]` regardless of that flag, because the stub's generic signature doesn't (and structurally can't easily) reflect a runtime constructor argument. The defensive `(k.decode() if isinstance(k, bytes) else k)` is therefore purely to satisfy a type checker's static view of the world, not a defense against an actual code path that can produce bytes given `decode_responses=True` is set. It's a small but genuine example of code correctly distinguishing "what the type checker thinks could happen" from "what actually happens at runtime," and choosing to write defensively for the former without pretending it reflects a real bug.

## Q10: Compare `RedisSLATracker`'s rolling-window approach (`LPUSH` + `LTRIM`) to a more sophisticated time-decayed metric. What's lost with a hard count-based cap?

`record()` pushes a new `{"ok": ..., "latency_ms": ...}` JSON blob and immediately trims the list to the most recent `window` entries (default 1000) via `LTRIM key 0 window-1`. Every entry within that window is weighted identically regardless of age — the 999th-oldest surviving entry counts exactly as much toward `success_rate()`/`p95_latency_ms()` as the entry from a second ago. This means the metric can look artificially stable during a slow trickle of traffic (a fixed count of 1000 events might span hours) or, conversely, artificially reactive during a traffic spike (the same 1000-entry window might span seconds), since the window is bounded by *event count*, not *wall-clock time*. There's also a hard cliff at exactly `window` entries: the 1001st push evicts the oldest entry entirely and instantly, rather than gradually decaying its influence — a time-decayed exponential moving average, or a genuine time-windowed structure (bucketed by minute, say), would avoid both the count-versus-time mismatch and the sudden-eviction discontinuity, at the cost of more complexity than a simple capped list.

## Q11: Walk through `error_budget_remaining()`'s special-casing of `allowed == 0`. What does it mean for `target_success_rate` to be exactly `1.0`, and why the ternary rather than letting the division happen naturally?

`allowed = 1 - self.target_success_rate` — if `target_success_rate` is exactly `1.0` (a "zero tolerance for any failure" SLA), `allowed` is exactly `0.0`, and the natural formula `1 - (actual / allowed)` would divide by zero. The method special-cases this: `if allowed == 0: return 1.0 if actual == 0 else 0.0` — meaning a zero-failure-tolerance target reports a full (`1.0`) error budget remaining only if the observed failure rate is *also* exactly zero (perfect track record against a perfect target), and reports the budget as *fully exhausted* (`0.0`) the instant even one failure has been observed, since any failure at all violates a zero-tolerance target completely. This is a sensible, explicit definition of an otherwise mathematically undefined edge case (`0/0`), chosen to match the intuitive meaning of a zero-tolerance SLA rather than raising `ZeroDivisionError` or returning some arbitrary sentinel like `NaN` that a caller might mishandle silently.

## Q12: Why does `RedisStateStore` require state to already be JSON-safe rather than using `pickle`, which could serialize arbitrary Python objects?

The class docstring states the state shape explicitly: "a plain dict (messages/thread_id/critique_retries/critique_last_score/`_pending`) — already JSON-safe, so this needs no custom serialization beyond `json.dumps`/`loads`." Choosing JSON over `pickle` here is a deliberate security and portability tradeoff: `pickle.loads` on untrusted or even just externally-modifiable data is a well-known arbitrary-code-execution risk, since a pickle stream can encode instructions to construct and call arbitrary objects during deserialization — a real concern for state sitting in a shared Redis instance that other processes, tools, or even a compromised replica might be able to write to. JSON has no such capability; it can only ever produce plain data structures (dicts, lists, strings, numbers, booleans, `null`), which is both safer to deserialize from a potentially-shared store and more portable (readable/debuggable by any tool that speaks JSON, not just Python with the exact same pickle protocol version). The cost is real too, though unstated as a limitation in the source: any future state shape that isn't naturally JSON-safe (say, a Python `datetime` object, or a custom class instance) would need explicit conversion before being handed to `RedisStateStore.save()` — this store has no `default=` serializer hook to bridge that gap automatically.

## Q13: What happens if two replicas both call `RedisStateStore.save()` for the same `run_id` concurrently, without first coordinating via `RedisLease`?

`save()` does a plain `self._r.set(key, json.dumps(state))` — a straightforward last-write-wins operation with no optimistic concurrency control (no version field, no compare-and-swap, no `WATCH`/`MULTI` transaction). If two replicas both compute a state update for the same `run_id` concurrently and both call `save()`, whichever call reaches Redis last simply overwrites the other's write entirely — there's no detection of the conflict, no merge, and no error raised to either caller; both believe their save succeeded. This is exactly the scenario `RedisLease` exists to prevent — acquiring the lease for a given run before driving it forward (and only one replica succeeding) is the intended discipline — but `RedisStateStore` itself does nothing to *enforce* that callers actually do this. The two classes are designed to be composed together by a caller's own orchestration logic; `RedisStateStore` alone provides no protection against concurrent overwrites if a caller bypasses the lease.

## Q14: Walk through the full path of a retried destructive tool call across a fleet, from `orchestration.py`'s `_default_idempotency_key` through `RedisIdempotencyStore`. Where's the remaining race?

`orchestration.py`'s `_default_idempotency_key(session_id, tool_call_id)` derives `f"{session_id}:{tool_call_id}"` automatically for every native tool call (real provider tool-calling always carries a `tool_call_id`), so a retried/replayed `act()` step protects a destructive call by default, without a caller needing to pass `idempotency_key=` explicitly. That key flows into `ToolRegistry.invoke(..., idempotency_key=...)`, which — when an `idempotency_store` is configured, e.g. `RedisIdempotencyStore` — checks `get(key)` first; if a cached `ToolResult` already exists for that key, the tool doesn't re-execute at all, and the cached result is returned. Across a fleet, this means a retry that lands on a *different* replica than the one that originally handled the call can still recognize "this was already done," because the store is shared via Redis, not per-process. The remaining race: `get()`/`set()` are two separate operations with no "in-progress" marker in between — if replica A is still *executing* a destructive call (hasn't yet reached its `set()` call) when a retry lands on replica B, B's `get()` returns `None` (nothing cached yet, since A hasn't finished), and B will proceed to execute the same destructive call concurrently with A. `RedisIdempotencyStore` only caches *completed* results; it has no equivalent of `RedisLease`'s claim-before-work semantics, so true concurrent-in-flight duplication is not actually prevented by this class alone — it would need to be composed with `RedisLease`, keyed on the same idempotency key, to close that gap.

## Q15: Why do `RedisToolCache` and `RedisIdempotencyStore` both set a TTL (`ex=...`) rather than storing entries forever?

Both are caches of transient value, not permanent records — `RedisToolCache`'s docstring frames it as serving "a repeated identical tool call ... from cache," which is only useful while the underlying data it reflects is still fresh (a tool result for "what's the weather" cached forever would eventually be silently wrong), and `RedisIdempotencyStore`'s job is specifically to protect against a *retry* landing shortly after an original call, not to remember every tool call a system has ever made indefinitely. Without a TTL, both stores would grow without bound — every distinct tool-call/args combination ever made, or every distinct idempotency key ever generated, would accumulate in Redis forever, consuming memory for entries that will realistically never be looked up again once their retry/cache-freshness window has passed. The TTL (`ttl_s`, defaulting to `60.0` for the cache and `3600.0` for idempotency, reflecting how much longer a retry is plausible versus how long a cached tool result stays "fresh") bounds memory growth at the cost of eventually forgetting entries that are, by design, meant to become irrelevant.

## Q16: What's the most consequential limitation of this module you'd fix given more time?

The idempotency race from Q14 — the gap between "no in-flight marker" and "completed-result cache only" — is the most consequential, because it's precisely the scenario this class exists to prevent (a replayed *destructive* tool call executing twice) that still slips through under real concurrent-retry timing, not merely a theoretical edge case. The fix would be straightforward given `RedisLease` already exists in the same module: `ToolRegistry.invoke()` (or a wrapper) would attempt to acquire a lease keyed on the same idempotency key *before* checking the idempotency cache, execute the tool only if the lease is acquired, write the result to `RedisIdempotencyStore`, then release the lease — a concurrent retry landing during that window would fail to acquire the lease and could either wait briefly and re-check the idempotency cache, or fail fast with a clear "in progress, retry shortly" signal, instead of silently re-executing a destructive operation. This composition isn't implemented anywhere in the current module — `RedisLease` and `RedisIdempotencyStore` exist side by side but aren't wired together, leaving that composition as an exercise for a caller who has to notice the gap themselves.
