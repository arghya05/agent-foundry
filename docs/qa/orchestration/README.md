# agent_foundry/orchestration.py — Q&A

Composable LangGraph primitives (`make_think_node`, `make_act_node`, `make_router`, `make_critique_node`) parameterized by one `AgentConfig`, plus a set of `build_*_graph` functions (single-agent, supervisor, swarm, fan-out, blackboard, debate, DAG) that wire those primitives into different multi-agent topologies without any topology being privileged over another.

## Q1: `AgentState` declares `request_identity`, `request_budget`, `request_deadline`, etc. as explicit `TypedDict` fields instead of a generic `extra: dict`. Why does that matter, and what actually broke when it wasn't done this way?

LangGraph derives its recognized state channels from the `TypedDict`'s own field set at graph-compile time. If a key isn't declared there, an `invoke()` input dict containing that key is silently dropped before it ever reaches a node — no error, no warning, just absence. The module's own comment on `request_identity` (around line 130) says this was found live: an early version let per-request identity flow through `state.get(...)` the way `native_engine.py`'s plain-dict state handles it, and it worked fine there because a plain dict has no declared-channel concept — but the LangGraph engine quietly ignored the same field. This is a sharp, non-obvious LangGraph gotcha: unlike a normal Python dict, a `StateGraph`'s state schema is closed by declaration, not by usage. The fix generalizes to every one of the `request_*` fields (`request_trace_id`, `request_budget`, `request_deadline`, `request_cancellation_token`, `request_tool_policy`, `request_model_policy`, `request_memory_scope`) — they all had to be added to the `TypedDict`, not just read defensively via `.get()`, for a per-request `ExecutionContext` override to actually reach either engine identically.

## Q2: Why is `critique_retries` a plain `int` field on `AgentState` instead of `Annotated[int, operator.add]`, given that `messages` uses the additive reducer pattern?

Because `critique_retries` is a plain overwrite field, the value written by one node replaces whatever was there, rather than accumulating with it. This is deliberate: the checkpointed `AgentState` persists across an entire multi-turn session, not just one turn. If it accumulated via `operator.add`, turn 1's retry count would leak into turn 2's retry budget — a session that used 2 retries answering the first question would start its second, unrelated question already "2 retries deep" against `CritiqueConfig.max_retries`, silently shrinking its retry budget over the session's lifetime. `make_think_node` explicitly resets both `critique_retries` and `critique_last_score` to zero/`None` whenever it detects a genuinely fresh user turn (`is_fresh_turn`), and `make_critique_node`'s retry branch sets the new total directly in Python (`retries_done + 1`) rather than relying on a reducer to add it — both of those only compose correctly because the channel is overwrite, not additive.

## Q3: Walk through exactly how `make_think_node` tells "a fresh user turn" apart from "critique looped back with a retry prompt" — both end in a `role="user"` message.

`is_fresh_turn` checks `last_message["role"] == "user" and not last_message.get("_critique_retry")`. `make_critique_node`'s retry branch tags its synthetic retry-prompt message with `"_critique_retry": True` specifically so this check can distinguish the two cases — a naive check of `role == "user"` alone can't, since both a genuine new question and a critique retry loop-back produce a `role="user"` message. This also can't be inferred from `critique_retries` being zero, because a *prior* turn that used retries would leave a stale nonzero value sitting in the checkpoint, and the next genuinely-fresh turn would incorrectly read as "already mid-retry." The marker field is the only reliable signal.

## Q4: Why is the reset of `critique_retries`/`critique_last_score` gated on `config.critique is not None`, and what would break in a multi-agent graph if it weren't?

If every `think()` node unconditionally wrote those two keys on every fresh turn, that's harmless for a single-agent graph, but `build_fanout_graph` (via `Send`) and, less obviously, any graph where multiple `think()` calls could occur in the same LangGraph superstep, would have several different `AgentConfig`-bound `think()` closures writing to the *same shared* `AgentState` channel concurrently. Since `critique_retries` is a plain (non-`Annotated`) channel, LangGraph enforces "can receive only one value per step" — a second concurrent write in the same step raises an error. The module's comment says this was "found live running the existing fanout test suite," not a theoretical concern. Gating the reset on `config.critique is not None` means only agents that actually use critique write that channel at all, which is also exactly why `build_fanout_graph` goes further and raises `ValueError` at build time if `config.critique` is set (see Q6).

## Q5: Why does `build_fanout_graph` explicitly forbid `AgentConfig.critique` with a `ValueError` at graph-build time, rather than letting it fail wherever it actually breaks at runtime?

`build_fanout_graph` dispatches via `Send`, and LangGraph's Pregel engine runs every `Send` target concurrently within the same superstep. Every fanned-out worker shares the *same* graph state, and `critique_retries` is a plain, overwrite-only channel — two or more concurrent workers writing to it in the same step would hit LangGraph's "can receive only one value per step" error, deep inside a `graph.invoke()` call, with a confusing stack trace far from the actual misconfiguration. Raising `ValueError` in `build_fanout_graph` itself, before the graph is even compiled, turns a latent runtime race into an immediate, actionable build-time error: "use `build_agent_graph` directly per item instead." This is a good example of failing fast at the API boundary instead of at the first unlucky concurrent collision.

## Q6: `_dispatch_tool_calls` uses `ThreadPoolExecutor`, not `asyncio.gather`, even though tools can be `async def`. Why, and how does that interact with `Agent.arun()`/`.astream()`?

The reason is structural: LangGraph's synchronous `.invoke()` raises `TypeError: No synchronous function provided` if a node function is `async def`. `make_act_node`'s `act()` closure must stay a plain `def` so `Agent.run()` (sync) keeps working, which means `act()` itself can never be `async def` and therefore can never `await asyncio.gather(...)` to dispatch calls concurrently. Threads are the only concurrency primitive available to a synchronous function that still needs to run several blocking (or, via `_invoke_tool_call`'s internal `asyncio.run()` bridge, async) calls in parallel. This doesn't sacrifice real async behavior at the top: `Agent.arun()`/`.astream()` get genuine asyncio-native non-blocking behavior at the *caller's* boundary, because LangGraph runs this whole synchronous node off-thread automatically when invoked via `.ainvoke()` — so an `await agent.arun(...)` caller's event loop is never blocked, even though the tool dispatch underneath is thread-based, not coroutine-based.

## Q7: Why does `flush_cleared()`'s post-dispatch bookkeeping (breaker.record, audit.record, memory writes) happen sequentially after `future.result()`, rather than inside the worker threads themselves?

`CircuitBreaker`'s per-tool counters are a read-modify-write operation, not safe to mutate concurrently from multiple threads — two threads racing on the same tool's failure counter could lose an increment. By contrast, the plain list-index writes (`results[i] = ...`) and `.append()` calls done inside worker threads elsewhere in the dispatch path are safe under the GIL because they're single atomic bytecode-level operations, not read-modify-write sequences. So `_dispatch_tool_calls` deliberately keeps the actual tool invocation (`_invoke_tool_call`) as the only thing that runs concurrently on worker threads, and defers every stateful side effect — breaker updates, audit logging, eval-harness recording, working-memory tool-sequence tracking — to the calling thread, executed strictly sequentially once every future has resolved. This trades a small amount of latency (bookkeeping can't overlap with dispatch) for correctness that doesn't depend on reasoning about which mutations are individually thread-safe.

## Q8: Walk through what happens when `act()` processes a batch of tool calls where one in the middle requires human approval — what exact ordering guarantee does `flush_cleared()` give?

`act()` iterates `calls` in order, appending each cleared (non-approval-needing) call into a `cleared` list without yet invoking it. The moment it hits a call whose PDP decision requires approval (`"approval" in gr.reason`), it calls `flush_cleared()` *before* calling `interrupt()` — this actually dispatches (concurrently, if there's more than one) everything accumulated in `cleared` so far, then clears the list. Only after that does it call `interrupt()`, pausing the graph. This preserves the same ordering guarantee the old strictly-sequential loop gave: everything positioned before the approval-needing call in the model's tool-call list has genuinely *run* (not merely been gated) by the time a human reviewer sees the approval prompt. Without this, a reviewer could approve or deny a call while earlier, already-cleared calls from the same turn were still sitting un-dispatched — a correctness-vs-perceived-state mismatch. After approval, the approved call itself falls through to the `cleared` list like any other and is picked up by the trailing `flush_cleared()` call after the loop.

## Q9: Compare `build_supervisor_graph`'s `Command(goto=...)` routing to `build_swarm_graph`'s `HANDOFF <name>` text convention. Why two different mechanisms for what's conceptually the same "route to another agent" operation?

`build_supervisor_graph` is *centralized*: one dedicated `supervisor` node runs a router LLM call every turn and unconditionally decides, via `_resolve_supervisor_route`, which specialist handles it — implemented with LangGraph's `Command(goto=f"{name}_think")`, the same primitive `langgraph-supervisor` itself uses, because there's a real graph node whose entire job is to emit that command. `build_swarm_graph` is *decentralized* — there is no supervisor node at all; any specialist can, from inside its own `think()` reply, hand off directly to a named peer by emitting the text convention `HANDOFF <agent_name>`, parsed by `make_swarm_router`. This can't reuse `Command(goto=...)` the same way because it isn't a dedicated routing node deciding on every turn — it's each specialist's own router (`make_swarm_router` falls back to `make_router(config)` when there's no `HANDOFF`) inspecting its own just-produced message. The two topologies represent a genuine architectural choice: pay for one extra LLM call per turn to get a single point of control and auditability (supervisor), or let specialists decide handoffs inline with no extra call but no central oversight (swarm).

## Q10: Trace `_resolve_supervisor_route` end to end when the supervisor's router LLM returns an unrecognized agent name. What happens, and why does the module fail closed instead of picking an arbitrary agent?

`ask()` sends a system prompt instructing the model to reply with exactly `ROUTE <agent_name>` and parses the reply by stripping that prefix. If the returned name isn't in `agents`, `_resolve_supervisor_route` retries *once* with a corrective prompt appended ("Your previous reply {name!r} was not one of the available agents. Reply again, exactly."), giving the model a genuine chance to self-correct rather than failing on the first miss. If the second attempt is still unrecognized, the function checks `fallback_agent`: if one is configured and valid, it routes there; otherwise it raises `SupervisorRoutingError`. The module's own docstring on `SupervisorRoutingError` explains why this fails closed rather than defaulting to, say, `next(iter(agents))`: once specialists carry different tool/permission scopes, silently landing an unrecognized routing decision on an arbitrary agent is a real security hole — the comment cites a concrete scenario where nothing would have stopped a misrouted triage turn from reaching "a finance agent with wire-transfer tools." Failing loud (or routing to an explicitly-opted-into `fallback_agent`) is the only safe default.

## Q11: `CritiqueConfig` has two separate thresholds — `kpi.threshold` and `escalate_threshold` — with genuinely different behaviors rather than one "block below X" gate. Why is that distinction load-bearing?

Below `kpi.threshold` alone, the answer is *not* withheld — it's still sent to the user, just with its score recorded so a caller (the docstring cites `healthcare/backend/app.py`) can surface it as a UI "low confidence" badge. Below the stricter, opt-in `escalate_threshold` (`None` by default, meaning "never escalate"), the turn pauses via `interrupt()` for a human reviewer — the same HITL mechanism `make_act_node` already uses for tool approval. The design principle stated directly in the docstring is that withholding a genuinely useful, imperfectly-grounded answer is worse than showing it clearly labeled as uncertain — most "not perfectly grounded" answers should land in the first bucket, and only the rare, genuinely ambiguous or hallucinated case should ever interrupt a human's time. Collapsing these into a single threshold would force every deployment into an all-or-nothing choice: either flood reviewers with anything below a modest confidence bar, or silently let a truly bad answer through unflagged because the bar was set loose enough to avoid over-escalating. Two thresholds let a builder tune "how uncertain is worth a badge" independently from "how uncertain is worth blocking on a human," and `escalate_threshold=None` cleanly expresses "flag everything, escalate nothing" as a first-class default.

## Q12: What is `CLARIFY_PREFIX` for, and why does `make_critique_node` never run the KPI against a reply that starts with it?

`CLARIFY_PREFIX = "CLARIFY:"` is a convention (shared via `CritiqueConfig.retry_prompt` and a builder's own system prompt) that lets the model itself decide it can't answer confidently and ask the user a genuine clarifying question instead of guessing. `make_critique_node` checks `draft.strip().startswith(CLARIFY_PREFIX)` before ever calling `config.critique.kpi.evaluate(...)`, because a clarifying question is not a factual claim — scoring it for "grounding in retrieved evidence" is a category error; there's no evidence to ground a question against, and doing so would either always fail (misleadingly flagging a legitimate clarification as low-confidence) or require special-casing the KPI itself. Instead, the turn finalizes immediately with the prefix stripped as the final reply, recorded via `eval_harness.record(..., "clarification_requested", ...)` and `_finalize_turn(..., outcome="needs_clarification")`. This path works whether or not `max_retries` is configured, and composes with the retry mechanism: `CritiqueConfig.retry_prompt` explicitly instructs the model to use this convention if, after gathering more evidence, it's still genuinely stuck.

## Q13: Explain the `retries_exhausted_no_progress` logic in `make_critique_node`. Why compare against `prev_score` instead of simply checking "still below threshold after N retries"?

The reasoning, spelled out in the code's own comment, is that exhausting every retry *without making any real progress* is the actual signal that a human is needed — not merely "still below threshold." A retry that genuinely improved the score, even if still imperfect, gets the same flag-and-show treatment a first-pass miss always receives, because the stated product principle ("always answer, flag low confidence; only truly ambiguous escalates") still holds for real, partial progress. `retried_without_improvement` is computed as `retries_done > 0 and prev_score is not None and result.value <= prev_score` — comparing the current score against `critique_last_score` from the previous retry attempt. `retries_exhausted_no_progress` is then true only when the turn failed, retries were actually configured and exhausted, `escalate_threshold` is configured at all, and the score made no improvement across the retry. Escalation only fires when `escalate_threshold` is set — a builder who left it `None` has explicitly said "never pause for a human," and retry exhaustion doesn't silently override that choice, even if the model is stuck.

## Q14: Why does `make_self_verify_node` require `context: Callable[[AgentState, str], dict]` to be the *same* callable as `critique.context`, and why does `build_agent_graph` raise `ValueError` if `self_verify=True` without `critique` set?

`make_self_verify_node`'s docstring is explicit that it reuses "the exact same `context` callable the critique gate will use right after this node runs," so self-verify checks the just-produced draft against the *identical* retrieved evidence critique is about to score against — not a second, possibly-inconsistent retrieval that could disagree with what critique sees. This matters because the value proposition of self-verify is specifically for agents whose `critique.escalate_threshold` is deliberately loose (the docstring's example: a "Doctor persona trusted to judge nuance itself") — giving the model one more chance to catch and fix its own unsupported claim compensates for that loose external gate *before* the answer ever reaches it, rather than duplicating retrieval work that critique will redo anyway. Since self-verify has no independent value without a critique context to reuse, `build_agent_graph` enforces the dependency at construction time (`self_verify and critique is None` → `ValueError`) rather than letting a caller discover the missing wiring only when `make_self_verify_node(config, context=critique.context)` would otherwise raise an `AttributeError` on `None`.

## Q15: Describe the exact, documented gap in `_run_governed_turn` when it's used by `build_blackboard_graph` or `build_debate_graph`, and walk through what actually goes wrong.

`_run_governed_turn` builds a *fresh, ephemeral* `build_agent_graph` instance per call, invokes it once, and unconditionally reads `result["messages"][-1]["content"]`. If that specialist's turn contains a tool call requiring approval, `interrupt()` fires inside that inner ephemeral graph, and `graph.invoke()` returns with `"__interrupt__"` set instead of a normal final message — but the inner graph object is discarded the instant `_run_governed_turn` returns, since nothing keeps it alive across the call boundary. Because the trailing `.content` read is unconditional, the interrupt is silently swallowed: the outer blackboard round or debate continues as if the specialist had answered normally, with a corrupted (empty or partial) message in the transcript, rather than surfacing the pause to a human. The module's own comment says this was *reproduced directly*, not assumed — `build_debate_graph` with a debater whose tool requires confirmation returns a "completed" result with no `"__interrupt__"` key at all, silently consuming the wrong number of scripted LLM calls in a test. This is a real, honestly-documented limitation, not a hypothetical: `build_supervisor_graph`/`build_swarm_graph` avoid it entirely because their specialists are real nodes of the *same* outer graph (so an interrupt propagates normally to the whole compiled graph), while blackboard/debate specialists are invoked through disposable inner graphs.

## Q16: Given the gap in Q15, what would actually need to change to fix it, and why hasn't it been done in this pass?

The comment reasons through this carefully: each blackboard participant or debater needs an *isolated* view of the conversation (every participant is called with the same fixed `messages`/`history` snapshot, never chained through each other's replies), which rules out simply turning each into a sequential node the way `build_supervisor_graph`/`build_swarm_graph` do — that would be a real semantic regression, not just a plumbing change, because a supervisor-style node chain implies each node sees the *previous* node's output. The correct shape, per the comment, is LangGraph's `Send`-based fan-out — the same mechanism `build_fanout_graph` already uses, which naturally gives each dispatched branch its own isolated state. But the interrupt/resume behavior for a paused task *inside* a `Send`-dispatched branch is real, version-specific LangGraph behavior that this pass explicitly says it "didn't verify live" — flagged rather than guessed at, in contrast to the supervisor/swarm topology-hop approval case, which the module states *is* verified working (citing specific tests: `test_supervisor_pauses_for_a_specialists_tool_approval_and_resumes` / `test_swarm_pauses_inside_the_handed_off_specialist_and_resumes`). It's an honest "known, confirmed gap," not a silently-accepted one.

## Q17: How does `_resolve_tool_policy` combine a per-request `Policy` override with an agent's static `config.policy`, and why is every combination rule a "narrow, never widen" operation?

`_resolve_tool_policy` reads `state.get("request_tool_policy")`; if absent, it returns `config.policy` unchanged. If present, it builds a new `Policy` where `allowed_tools` is the *intersection* of both (`base.allowed_tools & override.allowed_tools` — a tool must be allowed by both to be usable), `requires_approval` is the *union* (an override can only ADD an approval requirement, never remove one the base policy already demands), and `max_cost_usd_per_thread`, `max_steps_per_thread`, and `autonomy` each take the *stricter* (lower) of the two. This asymmetry is a deliberate security invariant: a per-request override — which typically comes from something like an inbound HTTP caller's `ExecutionContext.tool_policy` — must never be able to grant an agent more capability than its own static configuration already allows. If overrides could widen the policy, a caller could effectively re-authorize a tool the agent's own designer explicitly excluded, which would make `config.policy` meaningless as a ceiling. The same reasoning underlies `_resolve_model_names`, which narrows (never widens) which models a request may use, and never acts as a second, independent cost ceiling — total spend enforcement stays solely `_resolve_budget`/`RunBudget`'s job, avoiding a redundant, weaker after-the-fact check.

## Q18: What's the practical difference between `_resolve_identity`'s per-request identity and `config.identity`, and why does it matter for a single compiled graph serving many users?

`config.identity` is fixed once at graph-build time — a static, service-level identity baked into the `AgentConfig`. `_resolve_identity` instead prefers `state.get("request_identity")` when present, seeded from an `ExecutionContext` an `Agent.run()`/`.stream()`/`.resume()` caller passed in (per `core/agent.py`'s identity-dict construction), falling back to `config.identity` only when no per-request identity was set. Without this, the docstring notes, every caller of a *shared* Agent/graph instance is authorized as the exact same static identity — an HTTP layer correctly authenticating Alice (`role=support_agent`) and Bob (`role=admin`) as different people has no way to make that distinction reach the PDP's scope/data-classification checks, which would only ever see `config.identity.roles`. This is the same reasoning behind `session_id` being sourced from `state.get("thread_id")` rather than `config.tracer.thread_id` in `make_think_node` — a build-time value is wrong the instant one compiled graph serves more than one session or one caller, which is the normal production shape (see `serve.py`'s shared `graph` object).

## Q19: How does `build_dag_graph` differ philosophically from every other `build_*_graph` function in this module, and when would you actually reach for it?

Every other builder assumes an LLM makes a judgment call at each hop — `make_router` decides tool-vs-critique-vs-done, a supervisor LLM decides which specialist, a swarm specialist decides whether to hand off. `build_dag_graph` is explicitly the non-agentic pattern: a fixed DAG of plain Python functions (`DAGStep.fn: Callable[[dict[str, Any]], Any]`) with declared `depends_on` edges, no LLM reasoning anywhere in the graph itself. It exists for pipelines that need reliability and determinism (the docstring's example: "fetch → validate → transform → notify") rather than judgment at every hop — a category of workflow where injecting an LLM decision would add latency, cost, and non-determinism with no benefit. Independent steps (no shared dependency) run in parallel automatically via LangGraph's own edge-based concurrency, the same underlying Pregel-superstep mechanism `build_fanout_graph`'s `Send` uses for concurrent dispatch, just triggered by static graph topology instead of a dynamic per-item fan-out. `make_step`'s closure also enforces `depends_on` at runtime (`RuntimeError` if a dependency "hasn't run yet"), a defensive check that's mostly redundant given LangGraph's own edges guarantee ordering, but cheap insurance against a malformed manually-constructed `DAGStep` list.

## Q20: What's a genuine limitation of this module you would fix given more time, and why hasn't it already been fixed?

The clearest, already-self-documented one is the `_run_governed_turn` interrupt-swallowing gap covered in Q15/Q16: `build_blackboard_graph` and `build_debate_graph` participants run through disposable, ephemeral inner graphs, so a tool call requiring approval mid-turn inside a blackboard round or a debate is silently lost rather than surfaced — a real correctness gap for anyone using human-in-the-loop tool approval inside those two topologies specifically (supervisor and swarm don't have this problem, because their specialists are real nodes of the outer graph). It hasn't been fixed because the correct fix (`Send`-based fan-out so each participant gets an isolated view without becoming a chained sequential node) depends on LangGraph's interrupt/resume behavior *inside* a `Send`-dispatched branch, which is genuinely version-specific behavior the author explicitly declined to guess at rather than ship an unverified fix. A second, smaller gap worth naming: `Planner`-style per-request overrides narrow policy/model choice, but there's no equivalent per-request override surface for *topology* — you can't currently ask a supervisor-routed turn to temporarily restrict which specialists are reachable for one particular caller the way you can restrict tools or models.
