# agent_foundry/agent_spec.py — Q&A

A pure declarative-composition layer: `AgentSpec` is a dataclass that mirrors `core.agent.Agent.__init__`'s kwargs one-for-one, and `build_agent()` translates a spec (loaded from JSON/YAML) into a real `Agent(...)` call without introducing any second construction path or independent validation semantics.

## Q1: Why does this module avoid Pydantic for `AgentSpec`, and what does that cost you?

`AgentSpec` (line ~137) is a plain `@dataclass`, not a `BaseModel`. The stated project-wide reason is to keep the core dependency-free — no Pydantic in the import graph at all, which matters for a "Python-native core" that wants to stay light and auditable without a schema-validation library shaping its type system. The gain: zero extra dependency, plain dataclasses that are trivially inspectable (`fields(cls)` at line 168), easy to `replace()` (used in `_tool_from_entry`), and no metaclass magic — what you read is what runs.

The cost is real and visible in the code you have to hand-write instead of getting for free: `from_dict` (line 166) only checks for *unknown* top-level field names (`set(data) - known`); it does zero type coercion or nested validation. If you pass `policy: {"max_cost_usd_per_thread": "not-a-number"}`, nothing here catches it — the dataclass field will just hold a string until `Policy(**d)` (line 127, called from `_policy_from_dict`) raises whatever dataclass-level failure surfaces (probably nothing at construction — Python dataclasses don't type-check field values — and only breaks later when the budget arithmetic runs). Compare this to Pydantic, where `policy: PolicySchema` would validate types, coerce compatible ones, and raise a structured `ValidationError` with a field path — that machinery doesn't exist here. Nested dict fields (`policy`, `identity`, `memory`, `critique`, `eval`, `serve`) are typed as `dict[str, Any] | None` in the dataclass and are only unpacked/validated at the point they're consumed (`_policy_from_dict`, `_identity_from_dict`), not at `from_dict` time — so a malformed `identity:` block in a YAML file won't fail until `build_agent()` actually tries to construct an `Identity`, which could be much later than the parse, and error messages are whatever the underlying dataclass constructor raises (a bare `TypeError: __init__() got an unexpected keyword argument`), not a friendly field-level message.

## Q2: Walk through exactly what happens when `AgentSpec.from_yaml("agent.yaml")` is called on a file with a typo'd top-level key.

`from_yaml` (line 178) does `import yaml` lazily inside the method — if PyYAML isn't installed it raises `ImportError` with an actionable message pointing at `pip install agent-foundry[spec]` (the try/except at 180-183), rather than a raw `ModuleNotFoundError` bubbling from deep inside. Assuming PyYAML is present, `yaml.safe_load(Path(path).read_text())` parses the file into a plain dict, then delegates to `from_dict` (line 174). `from_dict` computes `known = {f.name for f in fields(cls)}` and `unknown = set(data) - known`; if the file has, say, `polciy:` instead of `policy:`, that typo lands in `unknown`, and `from_dict` raises `ValueError(f"AgentSpec: unknown field(s) {sorted(unknown)} — known fields are {sorted(known)}")`. This is actually a nice piece of hand-rolled validation — it gives you both the bad key and the full valid set, which is arguably more actionable than Pydantic's default "extra fields not permitted" error for a single field. But note what it does NOT do: it doesn't catch a *missing* required field at this layer either — `cls(**data)` (line 172) will raise a standard `TypeError: __init__() missing 1 required positional argument: 'instructions'` if `instructions` is absent, which is correct behavior but a less structured error than a schema validator would give.

## Q3: `resolve_tool()` documents itself as a real attack surface (lines 34-52). Why is that acceptable here, and when would it not be?

`resolve_tool(ref)` takes a string like `"pkg.module:function_name"`, splits on `:`, `importlib.import_module`s the module, and `getattr`s the function — meaning a spec's `tools:` list can name any importable module in the process's environment and execute its module-level code (imports run side effects) plus later call whatever function it names. The docstring is explicit that this is "the same trust boundary `foundry run <script>` already has" — i.e. the framework already assumes whoever can hand you a spec/script can execute arbitrary Python, so this isn't a *new* privilege escalation, just an existing one restated. That's acceptable in a context where specs are authored by the same trust tier as the deploying operator (e.g. checked into the same repo, reviewed in the same PR). It stops being acceptable the moment specs become untrusted input — e.g. accepting an `agent.yaml` uploaded by an end user or a third party through a multi-tenant SaaS surface — because then `tools: ["os:system"]` (or any importable module with a dangerous callable) becomes a straightforward RCE vector with no sandboxing anywhere in this file. The module doesn't allowlist modules, doesn't restrict to a package prefix, and doesn't sandbox the import — it's a known, documented, but unmitigated gap if the trust model ever shifts.

## Q4: What's the difference between a bare-string `tools:` entry and the dict form, and why keep both instead of just requiring the richer shape everywhere?

A bare string like `"mypackage.tools:search"` resolves straight to the callable via `resolve_tool` and is handed to `Agent(tools=[...])` unchanged (`_tool_from_entry`, line 65-66) — `core.agent`'s own `_coerce_tools` already knows how to turn a plain callable into a `ToolSpec` by inferring its JSON-schema-ish `parameters` from type hints and docstring. The dict form (`{"implementation": "...", "name": ..., "description": ..., "destructive": ..., ...}`) is for when a spec author needs to declare metadata a bare callable reference structurally cannot carry — most importantly `destructive: true`, which routes a tool through the action guardrail / human-in-the-loop path (per `ToolSpec.destructive` in contracts.py). The comment at lines 62-64 explicitly frames this as "the gap examples/commerce_agent/agent.yaml's own comment documents" — i.e. this was added because a real example needed to mark a tool destructive declaratively and couldn't. Keeping both forms rather than forcing the richer one everywhere is a deliberate ergonomics choice: most tools need no extra metadata, so forcing every `tools:` entry into a 5-key dict would be needless verbosity for the common case. The cost is `_tool_from_entry` (line 54) has to branch on `isinstance(entry, str)`, and any future field added to the dict form needs a `replace(spec, **entry)` (line 80) to actually accept it — since `replace()` will raise if `entry` contains a key `ToolSpec` doesn't have, a spec author typo in a dict-form tool key surfaces as a `TypeError` from `dataclasses.replace`, not a friendly spec-level error.

## Q5: In `_tool_from_entry`, why are `scopes` and `permissions` special-cased to convert to `frozenset` before `replace()` is called?

Lines 77-79 loop over `("scopes", "permissions")` and convert each to `frozenset(entry[frozenset_field])` if it isn't already one. This exists because YAML/JSON have no native frozenset type — a spec author can only write a list (`scopes: ["read", "write"]`), but `ToolSpec.scopes` and `ToolSpec.permissions` (contracts.py lines 67, 87) are typed as `frozenset[str]` fields, presumably because they're used in set-membership checks and need to be hashable (e.g. as part of a cache key, or compared against `Policy.allowed_tools`/`requires_approval`, which are also frozensets). If this conversion were skipped, `replace(spec, scopes=["read","write"])` would silently put a `list` into a field the rest of the codebase expects to be a `frozenset`, and the failure would only surface later — wherever downstream code calls `.issubset()`, hashes the object, or otherwise assumes set semantics — as a much harder-to-diagnose `AttributeError` or `TypeError` far from the actual root cause. The same normalization pattern appears independently in `_frozenset_fields` (line 114) for `Policy`'s `allowed_tools`/`requires_approval`, and inline in `_identity_from_dict` for `Identity.roles` (a tuple, not frozenset) — three near-duplicate hand-rolled coercions that a Pydantic model with typed fields and validators would have unified into one mechanism.

## Q6: What happens if `spec.critique` names an `evaluator` that isn't `"groundedness"` — walk through `_named_evaluator_kpi`.

`_named_evaluator_kpi(name, llm, *, threshold)` (line 83) has exactly one special-cased branch: `if name == "groundedness"`, it builds `composite_grounding_kpi` wired to a grounding-specific judge (`make_grounding_judge(llm)`) that scores an answer against `ctx["references"]`. For literally any other string — `"correctness"`, `"tone"`, `"plan-adherence"`, or even a typo like `"groundedeness"` — it falls through to the generic branch: `llm_judge_kpi(name, judge=make_llm_judge(llm, name), threshold=threshold)`. Critically, there is no validation that `name` is a recognized criterion at all: a typo doesn't raise an error, it silently becomes a *valid but different* KPI — `make_llm_judge` (llm_gateway.py line 391) just interpolates whatever string you give it into a prompt template ("Rate the following on {criterion}..."), so `"groundedeness"` would produce a real, running critique gate that asks an LLM to rate text on the literal criterion "groundedeness," always returning some score, never erroring. This is a genuine footgun: a spec author who fat-fingers the evaluator name gets no error, just a critique gate that quietly measures the wrong (or nonsensical) thing, likely passing every time because a lenient LLM judge is asked to score an invented rubric.

## Q7: Why is the critique's `llm` object explicitly forced to be the *same* `LLMGateway` as the agent's own completions (lines 202-210), rather than letting each default independently?

If `spec.critique` is set and no `llm` was already resolved from `spec.provider`, `build_agent` explicitly constructs `LLMGateway(provider=AnthropicProvider())` right there (line 210) rather than letting `Agent()`'s own constructor lazily default its own gateway when `critique_config` is passed in without an `llm`. The comment (204-208) explains why: if the critique judge and the agent's main completions used two independently-defaulted gateways, they'd have separate caches, separate rate limiters, and — most importantly — separate cost ledgers. A `RunBudget` tied to one `LLMGateway`'s cost tracking would be blind to spend happening through the other, which defeats the entire point of `Policy.max_cost_usd_per_thread`. This is a subtle but important piece of design reasoning: eagerly resolving the gateway here isn't laziness-avoidance for its own sake, it's preserving a single source of truth for cost/rate-limit state across both the agent's reasoning loop and its self-critique loop.

## Q8: What is `_default_critique_context` actually grounding the critique judge against, and what's a scenario where that's the wrong reference set?

`_default_critique_context(state, draft)` (line 101) builds `references = [m["content"] for m in state.get("messages", []) if m.get("role") == "tool"]` — i.e., it grounds the draft answer against every tool-result message produced so far in the turn, plus `{"output_text": draft, "references": references}`. This is a reasonable default for tool-using agents (e.g. RAG-style agents where tool calls fetch the evidence a final answer should be grounded in) and the docstring explicitly says it promotes the one existing hand-written precedent (`examples/autonomous_workflow/agent.py`'s `_critique_context`) into the framework so specs don't need Python to get it. But it's a hard-coded default with no override exposed anywhere in `AgentSpec.critique`'s dict shape (only `evaluator`, `threshold`, `escalate_threshold`, `max_retries` are read at line 212-215) — a spec-defined agent that answers purely from its own reasoning with zero tool calls in a given turn will always ground its critique against an empty `references` list, meaning `composite_grounding_kpi`'s judge sees "(no reference passages provided)" (per the prompt fallback in `make_grounding_judge`) and presumably scores low or trivially. There's no way for a spec to say "ground against conversation history" or "ground against a static knowledge base" instead — that's a real extensibility gap: the context-building function isn't spec-expressible at all, it's a single Python closure baked into this module.

## Q9: How does `build_agent()` decide which `LLMGateway` an agent actually uses — trace the precedence when both `llm=` and `spec.provider` are given?

Precedence, from the code: (1) if the caller passes `llm=` explicitly to `build_agent`, it "wins outright and `spec.provider` is ignored" (per the docstring at lines 193-196) — the `if llm is None and spec.provider is not None:` guard at line 197 never even evaluates the provider branch once `llm` is non-None. (2) If `llm` is `None` and `spec.provider` is set, it must be a key in `PROVIDERS` (`"anthropic"` or `"openai"`) or `build_agent` raises `ValueError(f"AgentSpec.provider {spec.provider!r} must be one of {sorted(PROVIDERS)}")` (line 199) — and then `llm = LLMGateway(provider=PROVIDERS[spec.provider]())` is constructed with the *default* `LLMGateway` routing table (the `routes={"default": [...], "cheap": [...], "hard": [...]}` default from llm_gateway.py), meaning a spec can pick a provider but cannot express a custom routing table, cache, or rate limiter — those remain Python-only, reachable only through the `llm=` escape hatch. (3) If neither is given and `spec.critique` isn't set either, `llm` stays `None` all the way to `Agent(..., llm=None)`, and whatever `Agent.__init__`'s own default construction does (presumably its own `AnthropicProvider()`-backed gateway) takes over — this module doesn't control that path at all. This three-way precedence is exactly what the docstring calls "the one escape hatch to real Python objects a JSON/YAML spec can't itself express."

## Q10: `AgentSpec.eval` and `AgentSpec.serve` fields exist on the dataclass but are explicitly commented as "read by callers... not by `build_agent`" (lines 163-164). Why include them in the spec schema at all if this module ignores them?

Because `AgentSpec` is meant to be the single declarative source of truth for everything about deploying that agent — not just how to construct it, but how to evaluate it (`eval: {"dataset": ..., "thresholds": ...}`) and how to serve it (`serve: {"host": ..., "port": ...}`). Other tooling (the docstring says "e.g. `foundry eval`") reads those fields off the same `AgentSpec` object `build_agent` also consumes, so one YAML file drives construction, evaluation, and serving without three separate config schemas drifting out of sync. The tradeoff is that `AgentSpec` is not a tightly-scoped "arguments to `Agent.__init__`" type anymore — it's a superset that mixes concerns, and `from_dict`'s unknown-field check (line 169-171) has to know about `eval`/`serve` even though `build_agent` itself never looks at them, which is a bit of a leaky abstraction: this module both defines and partially ignores its own schema.

## Q11: Why is `model` on `AgentSpec` misleadingly named, per the class docstring (lines 139-141)?

The docstring flags this directly: `model: str = "default"` is *not* a literal model identifier like `"claude-sonnet-5"`. It's passed straight through as `Agent`'s own `model=` kwarg, which `orchestration.AgentConfig` actually stores as `task` — i.e., it's `LLMGateway`'s *routing key* (`"default"`, `"cheap"`, `"hard"` in the gateway's default `routes` dict), not a model name at all. This is a real naming trap for anyone reading a YAML spec cold: writing `model: claude-opus-5` in a spec would not select that model directly — it would only work if that exact string happened to also be a registered routing key in the `LLMGateway`'s `routes` dict, which by default it is not (the defaults are `"default"/"cheap"/"hard"`). The `PROVIDERS` registry comment in llm_gateway.py (lines 273-277) makes the reasoning explicit: overloading `model=` to mean two incompatible things (a routing task vs. a literal model id) was judged a worse bug than the naming confusion, so the field keeps its name and the confusion is documented rather than "fixed" by a breaking rename.

## Q12: What's a concrete limitation of this module you'd flag in an interview, and how would you fix it given more time?

The most defensible answer: `from_dict`'s validation is shallow and single-level. It catches unknown *top-level* keys but does nothing for nested dict fields (`policy`, `identity`, `memory`, `critique`) until those dicts are consumed much later by `_policy_from_dict`/`_identity_from_dict`/`build_agent` — meaning a malformed spec can pass `AgentSpec.from_yaml()` cleanly and only fail deep inside `build_agent()`, or in the worst case (a badly-typed but not-obviously-wrong value, like a string where a float is expected) not fail loudly at all until arithmetic breaks at runtime. Given more time, the fix wouldn't necessarily be "add Pydantic" (that reopens the dependency debate this project has deliberately settled) — it would be extending the existing hand-rolled pattern into a real one: a `validate()` method that walks every nested dict field against its target dataclass's `fields()` (mirroring what `from_dict` already does at the top level) and raises one aggregated, field-path-qualified error before `build_agent` ever runs, so a spec author gets all their mistakes back in one pass instead of playing whack-a-mole one `TypeError` at a time.

## Q13: How does this module's approach compare to Pydantic + instructor for the same "declarative spec" problem, and why did the project pick this instead?

Pydantic/instructor would give you: automatic type coercion (string `"0.5"` → `float` for `max_cost_usd_per_thread`), structured `ValidationError`s with per-field paths, JSON-schema generation for free (useful if you wanted an LLM to *generate* a valid `AgentSpec`, which `instructor` specializes in), and nested-model validation recursively for free. What this module does instead: plain dataclasses (`AgentSpec`, and downstream `Policy`/`Identity` in contracts.py) with hand-written `_dict_to_x` converter functions that do the minimum coercion actually needed (frozenset/tuple/enum conversions, because those are the only types YAML/JSON can't natively express) and a hand-rolled unknown-field check. The tradeoff is explicit in the project's own architecture memory: no Pydantic in the core, which keeps the import graph and mental model minimal, at the cost of every one of these conversions and validations being hand-maintained and only as complete as someone remembered to write. If a new dataclass field is added to `Policy` with a non-YAML-native type (say, a `datetime`), someone has to remember to add a converter in `_policy_from_dict` — Pydantic would handle that automatically via a validator or type coercion. This is the classic "own your dependencies vs. own your bugs" tradeoff, made in favor of the former.

## Q14: What happens, concretely, if you call `build_agent(spec)` where `spec.memory = {"enabled": true}` — what kind of memory does the resulting agent get, and what are the limits per the module docstring?

`MemoryStore() if spec.memory and spec.memory.get("enabled") else None` (line 223) — note it only checks truthiness of `.get("enabled")`, so `{"enabled": false}` and `{}` both correctly produce `None`, but also any other key like `{"type": "persistent"}` without `enabled: true` silently produces no memory at all with no warning that the key was ignored. When it *is* enabled, you get a fresh in-process `MemoryStore()` with zero arguments — no backing store selection, no persistence, nothing seeded. The module's own top-of-file docstring (lines 11-16) is upfront that this is deliberately shallow: "working/episodic/semantic/procedural/knowledge_graph all start empty," and that seeding real documents into semantic memory or a knowledge graph is explicitly *not* something the declarative shape tries to cover — that's a Python-level task, pointed at `examples/support_agent.py`. So `memory: {"enabled": true}` in a spec is really just "give this agent a scratchpad for the duration of one process," not "connect this agent to persistent long-term memory" — a spec alone cannot produce a production RAG-backed agent memory; you drop into Python for that.

## Q15: If two different fields in a spec disagree about budget — e.g. `policy.max_cost_usd_per_thread` set high but the actual LLM calls are cheap — how does this module surface that, if at all?

It doesn't do any cross-field reasoning at all — `_policy_from_dict` (line 122) just constructs `Policy(**d)` with whatever numbers were given, and the docstring at the top of the file (lines 6-9) explicitly explains why there's no separate "budget" concept to reconcile: `policy.max_cost_usd_per_thread`/`max_steps_per_thread` in the spec ARE the budget, because `Agent.__init__`'s own `budget=` kwarg just defaults to `RunBudget(policy)` — so there's no independent budget shape here that could disagree with policy in the first place; they're definitionally the same numbers. This is a deliberate non-duplication decision (don't expose two knobs that control the same underlying value), but it does mean this module performs no sanity-checking of the policy numbers themselves — e.g. `max_cost_usd_per_thread: -5` or `max_steps_per_thread: 0` pass straight through with no validation, and whatever happens next depends entirely on how `RunBudget` (in core/agent.py, not this file) interprets a non-positive ceiling.

## Q16: Why does `_tool_from_entry` call `_toolspec_from_callable` even for a structured dict entry, rather than requiring the spec to supply `parameters` explicitly?

Because most of the time a tool's JSON-schema `parameters` can be correctly inferred from the underlying Python function's type hints and docstring — `core.agent`'s existing inference machinery (`_toolspec_from_callable`, imported from `.core.agent` at line 28) already does this for the plain-callable case, and the comment at lines 71-75 is explicit that a structured spec entry should get "the identical inferred schema unless it overrides `parameters:` itself below." So `_tool_from_entry` always calls `_toolspec_from_callable(fn, name=name, description=description)` first to get a fully-formed baseline `ToolSpec` (line 76), and only then applies `replace(spec, **entry)` (line 80) with whatever remaining dict keys the spec author actually supplied (`destructive`, `timeout_s`, `scopes`, etc., or an explicit `parameters` override). This means a spec author only has to write the fields they want to *override*, not restate the entire schema — but it also means if `_toolspec_from_callable`'s inference gets something wrong (e.g. a type hint it can't map cleanly to JSON schema), the spec's only recourse is to explicitly override `parameters:` by hand, since there's no way to say "infer, but patch this one nested property."

## Q17: What's the actual mechanism by which a `critique:` block in a spec becomes retry behavior at runtime, and what does `max_retries` there actually bound?

`CritiqueConfig` (imported from `.orchestration`) is constructed at lines 211-216 with `kpi=_named_evaluator_kpi(...)`, `context=_default_critique_context`, `escalate_threshold=spec.critique.get("escalate_threshold")` (defaults to `None` if absent — presumably meaning "never escalate"), and `max_retries=spec.critique.get("max_retries", 0)` (defaults to zero retries, i.e. score once and accept regardless, unless a spec explicitly opts into retrying). This module itself does none of the actual retry looping — it only assembles the `CritiqueConfig` object and hands it to `Agent(critique=critique_config, ...)` at line 228; the looping/escalation logic lives entirely in `orchestration.py`, which this file doesn't touch. That's a clean separation of concerns (spec assembly vs. runtime behavior), but it also means you cannot fully understand what a spec's `critique:` block *does* by reading only this file — you have to cross-reference `orchestration.CritiqueConfig`'s consumer to know what `max_retries`/`escalate_threshold` actually trigger.

## Q18: Is `AgentSpec` safe to construct concurrently / reuse across threads — any thread-safety concerns in this module?

`AgentSpec` itself is an ordinary mutable dataclass (not frozen, unlike `Identity` in contracts.py), so nothing stops two threads from mutating the same `AgentSpec` instance's `tools` list concurrently, and `build_agent()` reads `spec.tools`/`spec.policy`/etc. without any locking — but in practice specs are meant to be loaded once (`from_json`/`from_yaml`/`from_dict`) and then treated as an immutable blueprint, so this is a "convention, not enforcement" safety story, same as most of this codebase's dataclasses. The more interesting concurrency question is actually about `build_agent`'s shared `LLMGateway`: if the same `llm` instance is deliberately shared between an agent's main completions and its critique judge (per Q7), and that `Agent` is then used to serve concurrent requests, the `LLMGateway`'s own internal state (its `PromptCache`'s plain `dict`, its `rate_limiter`) needs to be thread-safe — but that's `llm_gateway.py`'s concern, not this module's; `agent_spec.py` just wires the same instance in twice and inherits whatever thread-safety (or lack thereof) `LLMGateway` provides.

## Q19: How would you extend this module to support a new `runtime` (say, `"temporal"`) beyond the two implied by the `runtime: str = "native"` default — what would actually need to change here?

Almost nothing in `agent_spec.py` itself needs to change to support a new runtime value, which is a genuine strength of the design: `runtime` is passed straight through as a string (`Agent(..., runtime=spec.runtime, ...)`, line 227) with zero validation or branching in this module — there's no `if spec.runtime not in {"native", "langgraph", "temporal"}: raise` guard anywhere, unlike `spec.provider`, which IS validated against `PROVIDERS` (line 198). That's actually an inconsistency worth calling out: `provider` gets a friendly `ValueError` for a bad value, but `runtime` doesn't — an invalid runtime string will pass straight through this module and fail wherever `Agent.__init__`/`core/agent.py` actually dispatches on runtime, with whatever error message that layer happens to produce. Fixing that would mean adding a small `RUNTIMES` set (mirroring `PROVIDERS`) purely for early, friendly validation — the actual runtime dispatch logic lives entirely in `core/agent.py`, not here.

## Q20: What test strategy would you use to gain confidence in `build_agent()` without needing a live LLM?

Since `build_agent()`'s job is pure composition — turning an `AgentSpec` into `Agent(...)` kwargs — the highest-value tests never need a live API call: (1) construct an `AgentSpec` with every field populated and assert the resulting `Agent`'s internal config/policy/identity match field-for-field, catching any future drift between `AgentSpec`'s fields and `Agent.__init__`'s kwargs; (2) pass a scripted/fake `Provider` (something implementing `contracts.Provider`'s `complete()` protocol) as `llm=` to exercise `build_agent`'s critique-sharing logic (Q7) deterministically — assert the same `LLMGateway` object identity is used for both the agent and the critique judge; (3) feed `from_dict` deliberately malformed specs (extra top-level key, missing required field, wrong-typed nested `policy` dict) and assert the exact exception types/messages, since those hand-rolled error paths (Q2, Q6) are exactly the kind of thing that silently regresses if untested; (4) a spec with `tools: [{"implementation": "tests.fixtures:fn", "scopes": ["a","b"]}]` to verify the frozenset coercion (Q5) actually produces a `frozenset`, not a list, on the resulting `ToolSpec`. None of this requires network access or a real Anthropic/OpenAI key, which is exactly the point of keeping construction logic this declarative.
