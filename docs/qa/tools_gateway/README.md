# agent_foundry/tools_gateway.py — Q&A

Layer 04, the Tools Gateway: `ToolRegistry` lets any Python callable be registered as a tool for any agent and enforces RBAC/policy-scope, caching, idempotency, rate-limiting, and argument/output schema validation at call time, via `invoke()` (sync) and `ainvoke()` (async), regardless of what the underlying tool actually does.

## Q1: `ToolRegistry.invoke()`'s own docstring admits it does NOT do the "richer PDP checks" and calls this "a real gap, not a hypothetical one." Explain exactly what's missing and why it was left this way.

Lines 240-254: `invoke()` checks `policy.allowed_tools` (a name-based allowlist) plus caching/idempotency/rate-limiting/arg-validation, but explicitly does *not* check `ToolSpec.scopes`, `data_classification`, `requires_confirmation`, `egress` (the host-allowlist checks `http_tool()` populates via `egress_hosts`), or an external OPA/Cedar `PolicyEngine` — those live one layer up in `policy_engine.PolicyDecisionPoint`, invoked by `orchestration.make_act_node` and `native_engine._act` *before* they ever reach `ToolRegistry.invoke()`. The honest admission is that nothing in `ToolRegistry` itself prevents a caller from calling `.invoke()` directly, bypassing the PDP entirely, and getting only the coarser name-based check. The docstring explains why this wasn't fixed: properly closing the gap would mean folding invocation into a separate enforcement wrapper (a registry/executor split), which is "a larger, separately-scoped redesign" since "every existing direct caller of `.invoke()`, tests included, would need to move" — i.e., it's a real architectural debt, consciously deferred rather than accidentally missed, and documented rather than hidden. This is a good example of the kind of honest self-critique the project maintains rather than presenting the registry as more secure than it actually is on its own.

## Q2: Trace what happens, in order, when `invoke()` is called with `idempotency_key` set and a cache also configured. Which check wins if both would apply?

`_pre_invoke()` (lines 201-222) runs, in this exact order: (1) `policy.allowed_tools` check — raises `PermissionDenied` immediately if not allowed (line 206-207); (2) if `idempotency_key is not None` and an `idempotency_store` is configured, look up that key — if found, return the *cached idempotency result* immediately (lines 208-211), short-circuiting everything else, including the general-purpose cache; (3) only if there was no idempotency hit, check `self.cache` for a `(tenant, name, args)`-keyed result (lines 212-215); (4) then rate-limiting (line 216-217); (5) then arg validation (lines 218-221). So idempotency wins over the general cache when both are configured and both would apply — this makes sense semantically: an idempotency key represents "this exact operation was already performed, return its exact prior outcome" (used for retried side-effecting calls like `issue_refund`), which is a stronger, more specific guarantee than the general result cache's "this call with these args recently returned this," and idempotency lookups don't even need to match on `args` (only on the caller-supplied key), so they're checked independently and first.

## Q3: `ToolCache.set()`'s comment explains why the cache key uses `json.dumps(args, ...)` instead of `tuple(sorted(args.items()))`. What was the actual bug this fixed, and is the fix fully sound?

Lines 129-133: the comment states the prior approach — `tuple(sorted(args.items()))` — "crash[es] on being used as a dict key" when a tool takes a list- or dict-valued argument, because Python dicts (and lists) aren't hashable, so `sorted(args.items())` would produce tuples containing unhashable values, and using that as a dict key (inside `self._store`) would raise `TypeError: unhashable type`. Switching to `json.dumps(args, sort_keys=True, default=str)` sidesteps this because the *string* JSON representation is always hashable, regardless of what nested structures `args` contains. It's largely sound, but not perfectly: `default=str` means any value JSON can't natively serialize (e.g. a custom object, a `datetime`, `bytes`) falls back to `str(value)` — which is fine for cache-key *uniqueness* purposes generally, but two distinct non-JSON-native objects that happen to stringify identically (e.g. two different objects whose `__str__` collides, or a `datetime` object versus a string that looks like that datetime) would collide into the same cache key and incorrectly serve one call's cached result for what should be a distinct call. This is a narrow edge case, but a real one given the general-purpose `default=str` fallback.

## Q4: Why does `ToolCache`/`_finish()` explicitly skip caching for `destructive` tools, using two different flags (`ToolSpec.destructive` and `ToolSpec.cacheable`) rather than one?

`_finish()` line 233: `if self.cache is not None and spec.cacheable and not spec.destructive:` — caching requires *both* `cacheable=True` (the default) *and* `destructive=False`. The two flags serve different purposes and the comment at lines 121-124 spells out why both exist: `destructive=True` marks a side-effecting operation (e.g. a refund) where caching would be actively dangerous — returning a stale cached result for what looks like a repeat call could mask whether the side effect actually happened, or worse, let a caller believe a second refund was issued when the "result" was just a replayed cache hit from the first. `cacheable=False` is for a *non-destructive* tool that still shouldn't be cached for other reasons — the example given is "get current time," where caching would return a stale, wrong answer even though there's no safety risk in re-executing it. Collapsing these into one flag would either force builders to mark "get current time" as if it were dangerous (misleading, and would presumably also block other destructive-specific behavior wherever `destructive` is checked elsewhere, e.g. HITL/guardrail gating referenced in `contracts.ToolSpec`'s own comment: "True => goes through the action guardrail / HITL"), or force `destructive` tools to be cacheable by default unless separately opted out, which is the wrong default for anything with side effects.

## Q5: Walk through `invoke()`'s retry loop (lines 265-274). What's actually retried, and what is a critical thing this retry loop does NOT protect against?

`invoke()` calls `spec.fn(**args)` inside a `while True` loop; on any `Exception`, if `attempt >= spec.max_retries` it gives up and returns `ToolResult(ok=False, error=str(e), ...)`, otherwise it increments `attempt` and loops back to retry the same call with the same `args` (lines 266-274). Since `max_retries` defaults to `0` (per `contracts.ToolSpec`), most tools registered without explicitly setting it get *no* retries at all — a single failure is final. Critically, this retry loop provides **no backoff** (no sleep between attempts — a failing tool that's rate-limited or overloaded gets hammered immediately again on the next loop iteration) and, more importantly, **no idempotency safety net of its own**: if a tool has side effects and isn't wrapped with an `idempotency_key`, retrying it here after a *partial* failure (e.g. the side effect actually completed server-side, but the response was lost due to a network blip, raising an exception client-side) would re-execute the side effect a second time. The framework's actual defense against this is `IdempotencyStore` — but that's an opt-in mechanism the *caller* of `invoke()` must supply an `idempotency_key` for; `spec.max_retries` and `IdempotencyStore` are two independent knobs that only compose safely if a builder remembers to set both together for any retryable, side-effecting tool. Nothing in `invoke()` warns or enforces that `max_retries > 0` and `destructive=True` without an `idempotency_key` is a dangerous combination.

## Q6: `invoke()` raises `TypeError` for an async tool function rather than calling it. Why not just have `invoke()` detect and await async functions itself, the way `ainvoke()` does?

Line 256-258's docstring explains the reasoning: "calling an async tool through here would otherwise silently return the unawaited coroutine object as `output`" — i.e., `spec.fn(**args)` on an `async def` function doesn't execute the function's body; it just constructs and returns a coroutine object without running it. If `invoke()` didn't check for this and just let that coroutine flow through, `_finish()` would treat the *coroutine object itself* as the tool's output — passing it through output-schema validation (`_validate_against_schema`, comparing a coroutine object against a JSON schema, which would almost certainly fail in a confusing way or silently "pass" a schema with no type constraints), caching it (a cached coroutine object is useless and can only be awaited once), and returning it to the caller as `ToolResult.output`, which anything downstream expecting a plain value (e.g. text to feed back to an LLM) would mishandle. Rather than silently awaiting it (which `invoke()`, being a synchronous method, can't safely do without its own event loop — the same nested-loop hazard discussed for `autogen_bridge.py`), the design makes the mismatch a loud, immediate `TypeError` at the call site, forcing the caller to use `ainvoke()` instead — a fail-fast choice over a silently-wrong one.

## Q7: `_pre_invoke()` is shared between `invoke()` and `ainvoke()`. What exactly is the sync/async split point, and does `_pre_invoke()` itself do any async work?

`_pre_invoke()` (lines 201-222) is fully synchronous — every check inside it (`policy.allowed_tools` lookup, `idempotency_store.get()`, `cache.get()`, `rate_limiter.allow()`, `_validate_args()`) is plain synchronous code with no `await` anywhere, which is why it can be shared unchanged between the sync `invoke()` and the async `ainvoke()`. The only place sync/async actually diverges is in the two callers' handling of `spec.fn` itself: `invoke()` (lines 263-264) raises `TypeError` if `spec.fn` is a coroutine function (Q6), while `ainvoke()` (line 290) does `await spec.fn(**args) if inspect.iscoroutinefunction(spec.fn) else spec.fn(**args)` — the one method that actually handles both sync and async tool functions correctly. This split is clean specifically because none of the pre-checks (policy, cache, idempotency, rate limit, validation) need to be async themselves — they're all in-memory or synchronous-store operations in every concrete implementation shown in this file (`ToolCache`, `InMemoryIdempotencyStore`).

## Q8: `_finish()` raises a plain `ValueError` when a tool's output fails its declared `output_schema`. How does that propagate, and is a schema-violating output treated the same as any other tool exception?

Lines 224-232: if `spec.output_schema is not None` and `_validate_against_schema()` finds the actual `output` doesn't match it, `_finish()` raises `ValueError(f"tool {spec.name!r} returned output that doesn't match its declared output_schema: {invalid_output}")`. The comment explicitly states the intent: "a schema-violating output is treated like any other execution failure (retried up to `spec.max_retries`, same as an exception)." This works because `_finish()` is called from *inside* the `try` block in both `invoke()`'s and `ainvoke()`'s retry loops (line 270, line 291) — so a `ValueError` raised here is caught by the same `except Exception as e:` that catches a raw exception from `spec.fn()` itself, and follows the identical retry-then-give-up path. This is a deliberate unification: from the retry loop's perspective, "the tool threw" and "the tool returned garbage that violates its contract" are the same category of failure, both retried the same number of times before surfacing as `ToolResult(ok=False, ...)`. One subtlety: because `_finish()` runs the validation *before* setting the cache (line 233 comes after the raise), a schema-violating output is never cached — only genuinely valid output reaches `self.cache.set()`.

## Q9: `_validate_against_schema()` prefers `jsonschema` if installed, falling back to `_validate_basic()`. What exactly does the fallback validator miss, and what's the practical risk of running without `jsonschema` installed?

`_validate_basic()` (lines 49-73) only checks: for an object schema, that `value` is a dict, that all `required` keys are present, and that each property's Python type roughly matches its declared JSON Schema `type` (via the `_SCHEMA_TYPES` mapping, line 44-46) — the docstring itself is explicit that this is "not a full JSON Schema implementation (no `$ref`/`oneOf`/`pattern`/etc.)." This means, without `jsonschema` installed, a tool's schema declaring a `pattern` (regex constraint), an `enum`, a numeric `minimum`/`maximum`, nested object validation beyond one level, or `oneOf`/`anyOf`/`allOf` composition would have all of those constraints silently ignored — a call or output that violates them would pass `_validate_basic()` even though it violates the schema shown to the model. The practical risk: an agent's tool-calling behavior could look correctly validated in an environment with `jsonschema` installed and then behave more permissively (accepting malformed args that violate `pattern`/`enum` constraints) in an environment without it — a genuinely different validation posture depending on an *optional* dependency being present, which is easy to overlook when reasoning about what's actually enforced in production.

## Q10: What's the actual difference between `tool_json_schema()`'s two branches (lines 36-40), and what happens if a tool's `parameters` dict has a key literally named `"type"` that isn't meant as a JSON-Schema-object marker?

`tool_json_schema()` checks `params.get("type") == "object"` (line 36): if true, it assumes `params` is *already* a full JSON Schema object and passes it through unchanged (`schema = params`); otherwise it treats `params` as the "loose docs-only" shorthand (`{"order_id": "string"}`) and builds a proper schema from it (lines 39-40), defaulting any value not in `_JSON_TYPES` to `"string"`. This is a reasonable heuristic for the two shapes the docstring says it accepts, but it does mean a loose-shorthand tool whose docs happen to declare a parameter literally named `type` — e.g. `parameters={"type": "string", "order_id": "string"}`, meaning "there are two params, one called `type`" — would be misinterpreted: `params.get("type") == "object"` would be `False` here (since the value is `"string"` not `"object"`) so it would actually fall through correctly to the loose-shorthand branch in *this specific example*, but if a tool author ever set `parameters={"type": "object"}` intending "one parameter named `type` whose type is `object`" rather than "this is already a JSON Schema," the ambiguity would misfire — the function would treat the whole dict as an already-formed (but degenerate, propertyless) JSON Schema instead of a one-parameter shorthand. This is a real ambiguity baked into overloading a single dict shape to mean two different things, disambiguated only by a magic key/value pair.

## Q11: Why does `ToolCacheLike`'s docstring insist a cache "is only useful across a fleet if every replica shares it," and connect this to `RunBudgetLike`? What's the actual multi-tenant bug this design closes?

Lines 103-111: the comment explains `ToolCache`'s in-process `dict` means "N replicas each independently re-execute the same call at least once" — an in-memory cache doesn't help correctness across a horizontally-scaled fleet (each process instance has its own cold cache), only within one process. The more important detail is the `tenant` parameter: `ToolCacheLike.get()/set()` both accept `tenant: str | None = None`, and `ToolRegistry.invoke()`/`_finish()` *always* pass `identity.tenant_id` (line 213, line 234) rather than leaving it to whatever default a cache implementation chooses. The comment states this "clos[es] the gap where two tenants sharing one registry/cache could otherwise read each other's cached tool results" — i.e., without a mandatory tenant dimension in the cache key, a multi-tenant deployment sharing one `ToolRegistry`/`ToolCache` (e.g. a SaaS deployment serving multiple customer orgs from the same process) could have Tenant A's cached tool result (which might contain Tenant-A-specific data, e.g. "get account balance") served back to Tenant B simply because the tool name and args happened to match — a real cross-tenant data leak the mandatory-tenant-key design specifically prevents, as long as every `ToolCacheLike` implementation actually honors the `tenant` parameter in its key construction (which `ToolCache._key()`, line 129-133, does).

## Q12: `list_for()` filters tools by `name in policy.allowed_tools`. What's a case where this simple membership check is insufficient, and where does the module itself say the richer logic actually lives?

`list_for()` (line 193-194) and `native_tools()` (line 196-199) both gate purely on tool *name* membership in `policy.allowed_tools` — there's no consideration of `ToolSpec.scopes`, `data_classification`, or any other per-tool policy dimension at this layer. This means a policy that wants to say "this identity can call `query_data`, but only against public-classification tables" has no way to express that distinction through `list_for()`/`native_tools()` alone — either the tool name is in the allowlist (fully permitted) or it isn't (fully hidden). Per Q1, the module is explicit that this richer, attribute-based policy evaluation is `policy_engine.PolicyDecisionPoint`'s job, not `ToolRegistry`'s — `ToolRegistry` intentionally stays a coarse, name-based allowlist mechanism, with the PDP responsible for finer-grained scope/classification/confirmation checks *before* a call ever reaches `ToolRegistry.invoke()` through the normal `Agent`/`build_agent_graph` path. `list_for()`/`native_tools()` inherit this same coarseness — a model given `native_tools(policy)` output sees every allowed-by-name tool's full schema, without any indication that finer PDP-level restrictions might still apply at call time.

## Q13: `InMemoryIdempotencyStore` only caches successful (`ok=True`) results, per its own docstring. Walk through what happens if the *same* idempotency key is used for two calls with genuinely different `args`.

Lines 152-158: "Only successful (ok=True) results are cached — a failed attempt should be retryable, not permanently stuck." But note `IdempotencyStore.get(key)`/`set(key, result)` are keyed *purely* by the caller-supplied string key — not by `(key, args)` the way `ToolCache` is keyed by `(tenant, name, args)`. This means if a caller reuses the same `idempotency_key` (e.g. `"refund-order-A100"`) for two calls with different `args` (a bug in the calling code, or a deliberate-but-wrong reuse), `_pre_invoke()`'s idempotency check (lines 208-211) would return the *first* call's cached result for the *second* call's request, silently ignoring whatever different `args` the second call actually supplied — the comment's framing ("the caller decides what makes two calls 'the same operation'") puts the entire correctness burden on whoever chooses the idempotency key, with no validation anywhere in this module that the key and the args are actually consistent across reuses. This is a real, if narrow, correctness trap: idempotency keys are a powerful safety mechanism against retried duplicate side effects, but they're equally capable of silently masking a genuine second, different operation if the key-generation logic upstream has a bug (e.g. deriving the key from only part of the relevant state).

## Q14: What's a limitation of this module you'd fix given more time?

The registry/PDP split documented in Q1 is the most consequential — `ToolRegistry.invoke()`/`ainvoke()` being directly callable and bypassing all the richer scope/classification/confirmation/egress checks is a real gap the module's own docstring calls out as unresolved due to migration cost, not because it's considered acceptable. Close behind: the retry loop's lack of backoff and its unenforced interaction with idempotency (Q5) — nothing here warns or prevents configuring `max_retries > 0` on a `destructive` tool without a corresponding `idempotency_key`, which is exactly the combination retries are supposed to be dangerous without. A third: the `jsonschema`-optional validation gap (Q9), where the actual strictness of argument/output validation silently depends on whether an optional dependency happens to be installed in a given environment — at minimum, this could be surfaced as an explicit warning/log line rather than a silent capability downgrade.
