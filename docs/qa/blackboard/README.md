# agent_foundry/blackboard.py — Q&A

A tiny, dependency-free `Blackboard` dataclass (six typed sections: facts, hypotheses, evidence, tasks, contradictions, open questions) that multiple agents read and post to via a `POST <section>: <text>` text convention, instead of exchanging messages directly.

## Q1: Why is `Blackboard` a plain dataclass with six separate `list[str]` fields, instead of a single `dict[str, list[str]]` keyed by section name?

Six explicit fields give every section a real, IDE-discoverable, type-checked attribute (`self.facts`, `self.hypotheses`, ...) rather than string-keyed dictionary access that a typo could silently misroute to a brand-new key. The tradeoff is extensibility: adding a seventh section (say, "risk") requires touching the dataclass definition, the `_SECTIONS` mapping, and `render()`'s tuple of labels/lists — three coordinated edits instead of one dictionary insert. The module accepts that cost deliberately in exchange for a shape a static type checker and an IDE can actually reason about, and because the six sections here aren't meant to be arbitrary or user-defined — they're a fixed, opinionated vocabulary for structured multi-agent reasoning (a fact is not a hypothesis; a contradiction is a distinct category from an open question), which a closed dataclass encodes more honestly than an open-ended dict would.

## Q2: What is `_SECTIONS` actually for, and why not have `post()` use `getattr(self, section)` directly against the user-facing section name?

`_SECTIONS` maps the *singular*, human-friendly names agents actually write in a `POST` command (`"fact"`, `"hypothesis"`, `"evidence"`, `"task"`, `"contradiction"`, `"question"`) to the dataclass's *plural* attribute names (`"facts"`, `"hypotheses"`, ..., `"open_questions"`). These don't line up 1:1 by simple pluralization rules — `"question"` maps to `"open_questions"`, not `"questions"` — so a direct `getattr(self, section)` would fail for that case and would also happily accept any string that *happens* to match an attribute name, including ones that were never meant to be writable via this convention. Routing through the `_SECTIONS` dict makes the vocabulary of valid `POST` targets an explicit, closed set independent of the dataclass's actual field names, and returns `False` (not an exception) for anything outside it — `post()` fails soft, which matters because its caller (`orchestration.build_blackboard_graph`'s `collaborate()`) treats a `False` return as "this agent's reply wasn't a valid contribution" and just records that as a `0.0` eval score rather than crashing the round.

## Q3: Trace `parse_post` in detail. What happens if an agent replies `"POST FACT:   the sky is blue  "` — mixed case, extra whitespace, a leading section-name space?

`parse_post` first checks `content.startswith("POST ")` (case-sensitive, single space) — this must match exactly, so a reply like `"post fact: ..."` or `"POST: fact ..."` (no space before the colon-delimited section) would fail this check outright and return `None`. Given a matching prefix, it strips `"POST "` and does `content[len("POST "):].partition(":")`, giving `section="FACT"` (with any trailing spaces from the partition) and `text="   the sky is blue  "`. `section.strip().lower()` normalizes `"FACT"` to `"fact"`, which *is* a valid key in `_SECTIONS`, so the case-insensitivity is intentional and handled. `text.strip()` trims the surrounding whitespace before it's returned. So `"POST FACT:   the sky is blue  "` parses successfully to `("fact", "the sky is blue")` — the function is deliberately forgiving of case and whitespace around the section name and text, but strict about the literal `"POST "` prefix and the colon separator existing at all.

## Q4: What happens if an agent's reply doesn't match the `POST` convention at all — no prefix, a malformed section name, or just a normal conversational answer?

`parse_post` returns `None` in every one of those cases: wrong prefix, or a section name (after normalization) that isn't a key in `_SECTIONS`. Its caller, `orchestration.build_blackboard_graph`'s `collaborate()`, does `parsed = parse_post(text); if parsed: blackboard.post(*parsed); ...; else: config.eval_harness.record("component", name, "posted", 0.0)`. So a non-conforming reply is not an error — it's silently treated as "this agent didn't contribute this round," recorded with a `0.0` score and no blackboard mutation, and the round moves on to the next agent. There's no retry, no corrective re-prompt (unlike, for comparison, `orchestration.py`'s `_resolve_supervisor_route`, which retries once on an unrecognized routing reply before failing closed) — a model that ignores the instruction simply contributes nothing that round, which is a soft-failure design choice appropriate for "one voice in a multi-round brainstorm" but would be too permissive for something safety-critical.

## Q5: Is `Blackboard.post()` thread-safe? Could two agents post to it concurrently, and does the current codebase ever actually do that?

`post()` itself does a single `getattr(self, attr).append(text)`, and Python's `list.append` is atomic under the GIL for a single call, so two threads calling `post()` on *different* sections, or even the same section, won't corrupt the underlying list or lose an append. But `Blackboard` has no coordination beyond that GIL-level atomicity — no lock, no versioning, no way to tell which round or which agent a given entry came from. In practice, `orchestration.build_blackboard_graph`'s `collaborate()` node deliberately never exercises this concurrently: it loops over `agents.items()` and calls each agent's turn (`_run_governed_turn`) strictly *sequentially* within a round, exactly because — per that function's own docstring — "a shared, mutable Blackboard isn't given concurrent writers within a round." If someone wired `Blackboard` into a `Send`-based fan-out (the same primitive `build_fanout_graph` uses) to run agents concurrently instead, the individual `.append()` calls would still be safe, but the *rendered order* of contributions would become non-deterministic between runs, and there would be no way to attribute a race between two agents both reacting to the exact same prior-render snapshot — a subtler correctness issue than raw thread-safety.

## Q6: `Blackboard` has no cap, eviction policy, or size limit on any of its six lists. What actually happens over many rounds, and how does that interact with `render()`?

Every successful `post()` call permanently appends to one of the six lists — there is no trimming, deduplication, or summarization anywhere in this module. Over `rounds` (the `build_blackboard_graph` parameter, default 2, but arbitrarily large in principle) multiplied by however many agents participate, `render()` — which is called fresh every round to build the next prompt — produces a linearly growing string: `"\n".join(f"{label}:\n" + "\n".join(f"- {x}" for x in items) ...)` over the full, ever-growing contents of every section. Unlike `orchestration.ContextEngine`, which the orchestration module documents as running a full "retrieve → rank → filter → compress → budget" pipeline before injecting retrieved content into a prompt, `Blackboard.render()` has no compression or budgeting step at all — it is a raw, unbounded dump. In a long-running or many-round collaboration, this means the prompt token cost of just *rendering the board* grows without bound, eventually crowding out or exceeding an LLM's context window; this is a real, honest limitation of the module as written, not an oversight the module tries to hide — there's no truncation logic to point to because none exists.

## Q7: Does `Blackboard` survive a process restart, and what happens to in-flight multi-round collaboration state if the process crashes mid-collaboration?

No — `Blackboard` is a plain in-memory dataclass with no persistence layer of its own, and, notably, it is *not* part of the LangGraph-checkpointed state in `build_blackboard_graph`. `BlackboardState` (the `TypedDict` that graph actually checkpoints) only carries `messages`, `thread_id`, and `round` — the `blackboard` object itself is a Python closure variable captured by `build_blackboard_graph`'s `collaborate()` function, passed in by the caller, and never serialized into the checkpointer at all. This means that even with a durable checkpointer configured (e.g. a `SqliteSaver`), resuming a blackboard-graph thread after a process restart would restore the *round counter* correctly but hand `collaborate()` whatever `Blackboard` instance the caller happens to construct on resume — an empty one, unless the caller has separately persisted and reconstructed its facts/hypotheses/evidence/etc. themselves. This is a genuine gap worth calling out explicitly: the graph's own durability story (LangGraph checkpointing, discussed at length in `orchestration.py`'s module docstring) simply does not extend to the shared reasoning artifact the whole topology exists to build.

## Q8: Why does `contradiction` get its own first-class section instead of being derived programmatically by comparing facts and hypotheses for conflicts?

Nothing in this module does any semantic comparison at all — `Blackboard` has zero logic beyond appending strings and rendering them back out; it has no understanding of what a "fact" or a "contradiction" *means* semantically, only that they're different labeled buckets. Detecting an actual logical contradiction between two facts would require real reasoning (an LLM call, or at minimum some structured claim representation with negation), which this module deliberately doesn't attempt — that's exactly the kind of judgment left to the agents themselves. `contradiction` exists as a section precisely so an agent that *notices* one (because it's the one doing the actual reasoning) has a designated place to record it, distinct from a plain fact, so it's visible to every other agent in the next round's rendered board. The module is infrastructure for agents to communicate structured observations to each other; it is not an inference engine that derives those observations on its own.

## Q9: Nothing in `Blackboard` enforces that content posted to `"fact"` is actually true, or that `"hypothesis"` versus `"fact"` is used correctly. What's the trust model here?

There is none, by design — `post()` performs zero validation of content, only of the section *label*. Any agent can post a fabricated or hallucinated claim to `"fact"` with exactly the same mechanism and exactly the same trust as a well-grounded one; the blackboard has no way to distinguish them, and neither does `render()`, which presents every section's contents with equal typographic weight. This mirrors a real, honestly-scoped limitation: the module's docstring frames it purely as "a shared reasoning workspace," not a verified-knowledge store — verification, if wanted, has to be layered on top (for instance, by routing blackboard-derived answers through `orchestration.py`'s `CritiqueConfig`/KPI grounding gate before they're ever shown to a user, since `Blackboard` itself has no equivalent of a KPI check). A team adopting this pattern for anything higher-stakes than exploratory multi-agent brainstorming would need to add that verification layer explicitly rather than assume the blackboard itself provides any truthfulness guarantee.

## Q10: How does this shared-blackboard pattern compare architecturally to something like AutoGen's group-chat transcript, or a flat shared message log?

A flat transcript (every agent sees every other agent's full chat history) preserves conversational nuance and order but gives a reader — human or LLM — no structure to skim; distinguishing "this is an established fact" from "this is speculation" from "this is an unresolved question" requires re-reading the whole thing and inferring intent from prose. `Blackboard`'s six-section model forces that categorization to happen at write time (an agent must decide which bucket its contribution belongs in via the `POST <section>:` convention) rather than leaving it to be inferred at read time. The cost is exactly the rigidity named in Q1 and Q4: a contribution that doesn't fit neatly into one of six buckets, or that a model phrases wrong, is silently dropped rather than preserved verbatim the way a raw transcript would preserve it. This is a genuine tradeoff, not a strictly better design — a flat transcript-based pattern is strictly more expressive and lossless, at the cost of being far harder for either a human reviewer or model to skim for "what do we currently believe."

## Q11: Why is `parse_post` a standalone module-level function instead of a method on `Blackboard`?

`parse_post` only needs a string — it has no dependency on any live `Blackboard` instance's state, and its output, a `(section, text)` tuple, is deliberately decoupled from the act of writing it (`blackboard.post(*parsed)`). Keeping it standalone lets a caller parse a candidate `POST` line without needing a `Blackboard` object at all — useful for, say, validating or testing the parsing convention in isolation, or for a caller that wants to inspect what an agent *tried* to post before deciding whether to actually apply it (which is exactly what `orchestration.build_blackboard_graph`'s `collaborate()` does: it parses first, then conditionally calls `.post()` only if parsing succeeded, and separately records an eval-harness score either way). Making it a `Blackboard` method would have coupled the pure parsing logic to a specific instance for no functional benefit, and would have made "parse without applying" an awkward operation.

## Q12: The module docstring emphasizes "No LangGraph dependency here on purpose." Why does that matter, and what would be lost if `Blackboard` imported LangGraph types directly?

`Blackboard` and `parse_post` are pure Python with zero external imports beyond the standard library's `dataclasses` module — genuinely usable standalone, outside any graph at all (embedded in a CLI tool, a notebook, a test, or a completely different orchestration framework). The actual LangGraph wiring lives entirely in `orchestration.build_blackboard_graph`, which imports `Blackboard`/`parse_post` from this module rather than the reverse. This mirrors the same "optional dependency, imported lazily where actually needed" discipline `orchestration.py`'s own module docstring describes for LangGraph itself (`runtime="native"` never imports LangGraph at all, reusing pure-Python helpers from `orchestration.py` the same way `build_blackboard_graph` reuses this module). If `blackboard.py` imported LangGraph types, every consumer of the shared-workspace pattern — including a hypothetical native-runtime blackboard implementation — would be forced to install and depend on LangGraph just to use six lists and a text-parsing convention, which would be a disproportionate dependency cost for what the data structure actually needs.

## Q13: Walk through exactly what a caller would need to change to add a new section, e.g. `"risk"`, to the blackboard.

Three coordinated edits, none of which is optional: (1) add a new dataclass field, e.g. `risks: list[str] = field(default_factory=list)`, to `Blackboard`; (2) add `"risk": "risks"` to the `_SECTIONS` dict so `post("risk", ...)` and `parse_post`'s validity check (`section in _SECTIONS`) recognize the new label; (3) add `"Risks"` to `render()`'s `labels` tuple and `self.risks` to its `lists` tuple, in matching position, since `render()` zips those two tuples together positionally rather than iterating `_SECTIONS`. Missing step 3 would mean the new section could be posted to successfully but would never appear in the text any agent actually sees, silently defeating the point of adding it — a subtle trap for anyone extending this module without noticing that `render()`'s label/list pairing is manual and separate from `_SECTIONS`, rather than derived from it.

## Q14: What is the actual difference in intent between the `"fact"` and `"hypothesis"` sections, and is there anything in the code that would stop an agent from misusing one for the other?

Nothing in the code distinguishes them beyond being two different list attributes — the distinction is entirely conventional, communicated only through the system prompt `collaborate()` builds each round ("Contribute with exactly: `POST <fact|hypothesis|evidence|task|contradiction|question>: <text>`") and whatever a builder's own agent-specific system prompt says about when to use which. There is no schema validation, no confidence score attached to a hypothesis versus a fact, and no mechanism to "promote" a hypothesis to a fact once evidence accumulates — that transition, if a use case wants it, has to happen by an agent explicitly posting the same claim again under `"fact"` in a later round, leaving the original hypothesis entry sitting unchanged and unlinked to its "promotion." This is consistent with the rest of the module's philosophy — plain, untyped, agent-trusted text buckets — but it does mean the fact/hypothesis boundary is a social convention enforced only by prompt engineering, not by the data structure.

## Q15: What's the single most consequential limitation you'd point to if asked to critique this module in a design review?

The combination of Q6 (unbounded growth, no compression) and Q7 (not part of checkpointed state) together mean `Blackboard` doesn't actually scale to the kind of long-running, restart-resilient multi-agent collaboration its own module docstring implies it's for. A brainstorming session capped at 2-3 rounds with a handful of agents works fine — the board stays small and the process almost never dies mid-collaboration in a demo or test. But there's no path from this implementation to a production long-running collaborative task without a caller building both a persistence layer (to survive restarts) and a summarization/compression step (to keep `render()`'s output within an LLM's context budget) entirely on top, since neither exists inside `blackboard.py` itself. Given more time, the fix would be adding an optional `max_items_per_section` (or age-based eviction) plus wiring the `Blackboard` object itself into `BlackboardState` so a checkpointer actually captures it — turning the "shared workspace" from something that lives only as long as one Python process into something that genuinely persists the way the rest of the framework's durability story promises.

## Q16: How would you actually implement the "swap `render()` for something LLM-summarized" fix, and why hasn't the module done that already?

You'd add a compression hook analogous to what `orchestration.ContextEngine` already does for retrieved memory — something like an optional `summarizer: Callable[[list[str]], str] | None` per section, invoked by `render()` once a section exceeds some length, collapsing older entries into a running summary while keeping the most recent ones verbatim. The module hasn't done this because it states its own scope narrowly: it's meant to be usable standalone with zero dependencies and minimal logic — a summarizer would need an LLM call (or at least a callable a caller supplies), which starts to blur the line between "dumb shared data structure" and "another orchestration layer," at which point it arguably belongs in `orchestration.py` (which already imports `Blackboard`) rather than in `blackboard.py` itself. The current design keeps the two concerns cleanly separated: `blackboard.py` is the passive data structure, `orchestration.py`'s `build_blackboard_graph` is where any future compression logic would actually be layered in without polluting the dependency-free base module.
