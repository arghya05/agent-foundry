# agent_foundry/security.py — Q&A

Tool supply-chain fingerprinting (`ToolManifestRegistry`), per-tool network egress allowlisting (`EgressPolicy`), pluggable short-lived credential issuance (`CredentialVault`/`VaultCredentialProvider`), and an append-only audit trail (`AuditLog`/`JSONLAuditLog`/`EncryptedJSONLAuditLog`) — the "what is the system itself allowed to run, and who did what" rail, distinct from `guardrails.py`'s content screening.

## Q1: `manifest_hash` (line 21) hashes `f"{spec.name}:{spec.description}:{inspect.signature(spec.fn)}:{body}"` where `body` is `inspect.getsource(spec.fn)`. What specific supply-chain drift does this catch that hashing the signature alone would miss, and what drift does hashing the *function's own source* still miss?

The docstring is explicit about the first half: hashing only `name:description:signature` would leave the fingerprint completely unchanged if only the function's *body* changed — `def refund(order_id: str) -> bool:` has an identical signature whether it silently issues a refund of the requested amount or silently issues 10x the requested amount, so a signature-only hash would let that swap through undetected. Including `inspect.getsource(spec.fn)` closes that. What it still misses: `inspect.getsource` returns only the *textual source of this one function definition* — it does not follow calls into helper functions, module-level constants the function reads, or mutable closures it captures. If `refund()`'s body calls `_process_refund(order_id)` and an attacker (or a careless deploy) changes `_process_refund`'s implementation elsewhere in the codebase, `refund`'s own source text is byte-for-byte unchanged, so `manifest_hash` returns the identical fingerprint even though the tool's actual runtime behavior completely changed. This is a real, exploitable blind spot for anything beyond a single-function, self-contained tool — which is a common shape for tools registered via decorators wrapping thin adapters around a "real" implementation living elsewhere.

## Q2: What happens when `manifest_hash` is called on a tool whose `fn` is a lambda passed via `exec`/`eval`, or a dynamically built closure? Does drift detection silently degrade there?

`inspect.getsource` raises `OSError` or `TypeError` when source isn't retrievable — a dynamically constructed closure, a builtin, or a lambda assembled at runtime via `exec`/`eval` has no backing `.py` file line range `inspect` can locate. `manifest_hash`'s `try/except (OSError, TypeError): body = ""` (lines 31-34) catches exactly that and falls back to `body = ""`, so the fingerprint degrades to just `name:description:signature`  — precisely the weaker, signature-only fingerprint Q1 says is insufficient. The comment at line 27-30 is upfront about this being a deliberate, honest fallback rather than a silent success: "Falls back to signature-only when the source genuinely isn't retrievable... not something to hide from a caller by pretending drift-detection covers it when it doesn't." But in practice, `ToolManifestRegistry.verify()` returns a plain `bool` — it has no way to tell its caller "this tool's fingerprint is degraded to signature-only coverage," so a caller cannot distinguish "verified with full source coverage" from "verified, but only against a signature because I never captured the body." That distinction matters operationally: a dynamically generated tool (increasingly common with LLM-authored or template-generated tool wrappers) gets systematically weaker supply-chain protection with zero visible signal that it's weaker.

## Q3: `ToolManifestRegistry.pin()` (line 47) and `verify()` (line 52) operate on an in-memory `dict[str, str]`. Walk through the trust boundary this protects, and the one it explicitly does NOT protect, in a realistic deployment.

`pin()` records a tool's fingerprint *at whatever moment the caller invokes it* — typically at tool registration time — and `verify()` later recomputes the fingerprint and compares. This protects against *post-registration drift*: if a tool's underlying function is monkey-patched, hot-reloaded, or replaced after pinning (e.g., a compromised dependency updates a shared helper at runtime, or a malicious actor with code-execution-after-startup swaps a tool's implementation), `verify()` catches the mismatch. It does NOT protect against a malicious or already-compromised registration: if the attacker controls the code path that calls `pin()` in the first place — e.g., they've already gotten a backdoored `refund()` into the codebase before the process starts — `pin()` happily fingerprints the backdoored version and `verify()` will report it as "unchanged" forever after, because there was never a legitimate baseline to compare against. There's also no persistence: `_pins` (line 45) is a plain in-memory dict with no default serialization, so every process restart starts with an empty registry and nothing is verified until each tool is re-pinned — this is fine if pinning happens deterministically at every startup (baking the pin into the same registration code that creates the `ToolSpec`), but it means the "registry" carries no memory across deployments; there's no persisted, append-only record an auditor could later use to prove "this exact fingerprint was approved on this date by this person," the way a real supply-chain system (Sigstore/cosign, npm's provenance attestations) would.

## Q4: `EgressPolicy.check(tool, host)` (line 62) is `return allowed is None or host in allowed`. What does "not registering a tool in `allowed_hosts`" actually mean for that tool's network access, and is that a fail-open or fail-closed default? Is that the right default for this threat model?

It's fail-open: `self.allowed_hosts.get(tool)` returns `None` for any tool that was never explicitly given an entry in the `allowed_hosts` dict, and `None is None` short-circuits the `or` to `True` — meaning a tool with NO egress configuration at all is granted access to *any* host, unconditionally. The docstring calls this out plainly ("`None` means unrestricted"), so it's a documented behavior, not a hidden bug — but it's still the riskier of the two possible defaults for an egress allowlist specifically meant to contain what a compromised or malicious tool can reach (OWASP LLM06/LLM08-adjacent: a tool with SSRF-style capability, or one whose args an attacker partially controls, can exfiltrate data to an attacker-controlled host unless it's been *explicitly* locked down). A fail-closed default (`allowed is not None and host in allowed`, with unconfigured tools blocked entirely until an operator opts them in) would force every new tool integration to make an explicit, auditable egress decision instead of silently inheriting unrestricted network access by omission. As shipped, an operator who forgets to add a new HTTP-calling tool to `EgressPolicy.allowed_hosts` doesn't get an error or a warning — the tool just works, reaching wherever its arguments point it, and the absence of a restriction is indistinguishable from a deliberate "this tool needs unrestricted egress" decision.

## Q5: `PolicyDecisionPoint.decide` in `policy_engine.py` only calls `self.egress.check(tool_name, host)` when `self.egress is not None`, and `AgentConfig.__post_init__` builds the default `PolicyDecisionPoint` with `egress=None`. Trace what this means for egress enforcement in a default Agent Foundry deployment.

`orchestration.py`'s `AgentConfig.__post_init__` builds the default PDP as `PolicyDecisionPoint(guardrails=self.guardrails)` — no `policy_engine`, no `egress` — unless a caller explicitly constructs and passes a `PolicyDecisionPoint(..., egress=EgressPolicy(...))` into `AgentConfig.pdp`. Since `PolicyDecisionPoint.decide`'s egress-checking `for host in hosts: if not self.egress.check(...)` block is nested inside `if self.egress is not None:`, a default deployment performs **zero egress checking whatsoever** — every tool with declared `egress_hosts` on its `ToolSpec` reaches every host it wants, unconditionally, regardless of what `EgressPolicy` would have said, because `EgressPolicy` was never wired in at all. This is a strictly stronger version of Q4's fail-open problem: it's not just "an unconfigured tool defaults to unrestricted," it's "the entire egress-allowlisting subsystem defaults to not running at all" unless an integrator specifically opts a running agent into it. Combined with `EgressPolicy`'s own fail-open default for unlisted tools, the honest summary is: egress allowlisting in this codebase is an opt-in capability an operator must deliberately assemble and wire in twice (build an `EgressPolicy`, then pass it into the `PolicyDecisionPoint`) — it is not a default protection any agent gets "for free."

## Q6: `CredentialVault.rotate(name, value)` (line 124) writes `value` into `self._overrides[name]` and records a timestamp. What does this method NOT do that its name might lead someone to assume it does?

`rotate()` does not talk to any external system, does not generate a new credential value, and does not invalidate the old one at its source (an IAM provider, a database, an API key issuer) — it simply overwrites this in-process dict entry with whatever `value` the caller already obtained and stamps `time.time()` against it. The actual work of "rotating a secret" — calling out to AWS IAM/Vault/whatever system owns the credential to generate a fresh value and revoke the old one — is entirely the caller's responsibility; `CredentialVault.rotate` is bookkeeping, not rotation. This matters because `age_s(name)` (line 128) is the only thing in this class that gives an operator a rotation-freshness signal, and it's trivially gameable: calling `rotate(name, get(name))` (re-supplying the identical, stale value) resets `age_s` back to zero with no actual security improvement, because nothing here validates that `value` is actually a *new* credential distinct from the old one. Contrast this with `VaultCredentialProvider.rotate` (line 98), which is the real thing — it POSTs a new value to a live HashiCorp Vault KV v2 endpoint — versus `CredentialVault`, whose docstring itself is honest that it's "a reference implementation" meant to be swapped out ("swap get()/rotate() for AWS Secrets Manager, HashiCorp Vault, or GCP Secret Manager and nothing calling it needs to change").

## Q7: `VaultCredentialProvider.get`/`rotate` (lines 89, 98) build requests with `urllib.request.Request(..., headers={"X-Vault-Token": self.token})` and call `urllib.request.urlopen`. What are the concrete failure modes if `base_url` is `http://` instead of `https://`, or if the Vault server is temporarily unreachable?

If `base_url` starts with `http://`, `self.token` — a live, unscoped-by-this-code Vault token capable of reading/writing whatever `mount`/paths it has policy access to — is sent as a plaintext HTTP header over the network with zero enforcement anywhere in this class that the scheme be `https`; nothing in `VaultCredentialProvider` validates or rejects an `http://` `base_url`, so a misconfiguration silently downgrades to sending the master credential-store token in cleartext. If the Vault server is unreachable or returns a non-2xx status, `urlopen` raises (`urllib.error.URLError`/`HTTPError`) and neither `get` nor `rotate` catches it — the exception propagates straight to the caller uncaught, with no retry, no circuit-breaking, and no distinguishing "Vault is down" from "the secret doesn't exist" from "the token is invalid/expired" beyond whatever `HTTPError.code` the caller inspects itself. There's also no token-lease renewal logic here at all — if `self.token`'s TTL expires mid-run, every subsequent `get()`/`rotate()` call starts failing with an auth error, and this class has no mechanism to detect that proactively or renew the lease; it's a thin, honest wrapper (the docstring calls it "verified against a live local `vault server -dev` instance, not mocked"), not a hardened production Vault client.

## Q8: Why does `AuditSink` exist as a `Protocol` with a single `.record()` method (line 133) instead of the audit system requiring a specific concrete logger class?

The docstring states the design intent directly: "orchestration.py only ever calls this one method... the entire contract a compliance system needs to satisfy: ship it to Splunk, a SIEM, a warehouse table, wherever." Minimizing the Protocol to exactly the one method callers actually invoke (`record(*, identity, action, **detail)`) means any team can drop in their own sink — a Splunk HEC forwarder, a Kafka producer, a database writer — by implementing just that one method, without needing to also implement a `tail()`/`history()`/query interface they may not want, and without inheriting from any base class in this module. Note that `AuditLog`, `JSONLAuditLog`, and `EncryptedJSONLAuditLog` all additionally implement `tail(n)` for read-back convenience, but `tail` is NOT part of the `AuditSink` Protocol — a minimal custom sink (e.g., one that only forwards to an external SIEM and relies on that SIEM for querying) is under no obligation to support reading its own history back out, which is the correct scoping: writing and reading an audit trail are genuinely separable concerns, and forcing every sink to support both would make simple forwarding sinks unnecessarily heavy.

## Q9: `AuditLog.entries` is a plain in-memory `list[dict]` appended to by `record()` (line 147). What happens to the audit trail on process restart, and is `AuditLog` an appropriate choice for anything compliance-relevant?

Everything in `AuditLog.entries` lives only in process memory — a crash, restart, redeploy, or container recycle loses the entire audit history with no recovery path, since nothing here persists to disk or any external store. That makes `AuditLog` fundamentally unsuitable for compliance, incident response, or any scenario where "prove what happened" needs to survive past the current process's lifetime — it's explicitly positioned as the in-memory/testing counterpart to the durable options: the codebase's own comments (line 184, referencing `healthcare/backend/agent.py`'s `_default_audit`) confirm `JSONLAuditLog` is "production's default," not `AuditLog`. Concurrency-wise, `list.append` is safe under CPython's GIL for the simple dict-literal append this does, so concurrent `record()` calls from multiple threads within one process won't corrupt the list structurally — but there's no lock protecting the read-modify sequence across `record()` and `tail()` together, so `tail()` reading `self.entries[-n:]` while another thread is mid-`append` is fine at the Python level (list operations are individually atomic) but offers no stronger consistency guarantee (e.g., no snapshot isolation) than that.

## Q10: `JSONLAuditLog.tail(n)` (line 180) does `with open(self.path) as f: lines = f.readlines()` then `reversed(lines[-n:])`. What's the scalability problem here, and what's the tamper/corruption story compared to a real audit system?

`readlines()` loads the *entire* audit file into memory just to return the last `n` entries — for a long-running deployment with a large, ever-growing JSONL audit log, this means every single `tail()` call (e.g., an ops dashboard polling recent activity) does an O(file size) read and O(file size) memory allocation instead of an O(n) tail-read (seeking from the end, or maintaining a rotating/indexed log). This is fine for a demo or a short-lived audit file and degrades quietly as the file grows — there's no log rotation, size cap, or archival logic anywhere in `JSONLAuditLog`. On the corruption/tamper side: `record()` (line 173) only ever appends plain JSON text with no integrity mechanism (no hash chaining, no HMAC, no append-only filesystem enforcement) — an attacker or operator with write access to `self.path` can edit, delete, or reorder past lines with zero detectability from this code; `tail()` has no way to notice a line was altered versus genuinely written that way. A real audit system (e.g., a hash-chained log, or write-once storage like S3 Object Lock / an immutable ledger) would make such tampering either impossible or cryptographically evident; `JSONLAuditLog` provides durability across process restarts (a real improvement over `AuditLog`) but not tamper-evidence.

## Q11: `EncryptedJSONLAuditLog.tail()` (line 232) wraps its `json.loads(self._fernet.decrypt(line))` call in `try/except Exception: continue`, silently skipping any line that fails to decrypt. The docstring frames this as matching `JSONLAuditLog`'s own "fail-soft" posture toward malformed JSON. Is that framing fully honest about what's being traded away here, for an *audit log specifically*?

Only partially. For `JSONLAuditLog`, a line that fails `json.loads` is most plausibly explained by an interrupted write (e.g., a crash mid-append) — genuinely benign corruption, and skipping it so a dashboard doesn't 500 over one bad line is a reasonable availability tradeoff. For `EncryptedJSONLAuditLog`, a line that fails Fernet decryption has a second, security-relevant explanation: `cryptography.fernet.Fernet.decrypt` verifies an HMAC before returning plaintext, so a line failing to decrypt isn't just "malformed" — it can also mean *someone tampered with this ciphertext* (Fernet's whole point is that any bit-flip in the token fails authentication rather than silently decrypting to garbage). Silently `continue`-ing past that means a deliberate tampering attempt on the audit trail is indistinguishable, from `tail()`'s perspective, from an innocent partial write — and it produces NO signal to an operator that something was tampered with. For a component whose entire purpose is being a trustworthy record of "what happened," silently swallowing evidence of tampering (rather than, say, logging a warning with the line's position, or exposing a count of skipped/failed lines) undermines the tamper-evidence property an encrypted audit log is implicitly expected to provide. This is a real, specific gap worth calling out plainly rather than accepting the docstring's "same fail-soft posture as the plain log" framing at face value — the two failure classes aren't equivalent for this particular component.

## Q12: `EncryptedJSONLAuditLog.generate_key()` (line 219) and the class docstring say the Fernet key "must be kept OUTSIDE this repo/disk... losing the key makes every past entry unrecoverable; that's the correct tradeoff." Do you agree that's the correct tradeoff, and what operational discipline does it actually require that this code doesn't enforce?

Losing the key permanently destroying the audit history is indeed the correct cryptographic tradeoff for at-rest encryption generally — a system that could recover encrypted data *without* the key would mean the encryption wasn't providing real confidentiality in the first place. But "correct tradeoff" only holds if key management discipline outside this code is actually solid: the class itself does nothing to enforce that the key isn't, say, hardcoded next to the `EncryptedJSONLAuditLog(path=..., key=...)` call site, checked into source control, or stored unencrypted on the same disk as `path` (which would defeat the entire point — an attacker who can read `path` to get the ciphertext can typically also read whatever config/env file holds the key sitting right next to it). The docstring correctly points at `security.py`'s own `CredentialVault`/`VaultCredentialProvider` as where the key *should* live, but nothing in `EncryptedJSONLAuditLog`'s constructor validates that `key` came from a real secrets manager rather than a literal string in a config file — the class accepts any 32-byte url-safe base64 `bytes` value with equal trust regardless of provenance, so the security property is entirely a matter of operational discipline this module can describe but not verify or enforce.

## Q13: `EgressPolicy.check(tool, host)` (line 62) trusts whatever `host` string the caller supplies — it never resolves DNS, never inspects an actual outbound socket connection, and never sees the tool's real runtime arguments. If a generic `http_tool`-style tool takes an arbitrary URL as one of its own call arguments, does `EgressPolicy` actually prevent that tool from reaching an attacker-chosen host?

Not by itself, and this is a real, specific gap worth being precise about. `EgressPolicy.check` is a pure string-membership test against whatever `host` value it's handed — it has no visibility into the tool's actual execution, no socket-level interception, and no DNS resolution step, so it cannot detect a mismatch between the `host` it's asked about and the host the tool code will actually connect to at runtime. `policy_engine.py`'s own comment on `PolicyDecisionPoint.decide` (around line 88-91) confirms exactly this design: `hosts` passed into the egress check "comes from `ToolSpec.egress_hosts` (the tool's OWN declared destinations, known at registration time)... not derived from `args`, which vary per call and have no generically reliable 'this is the host' field." That means the entire enforcement is against a *static, self-declared* allowlist fixed at registration time, not a live check of what the tool is about to do this call. For a narrowly scoped tool (e.g., one hardcoded to only ever call `api.stripe.com`), the declared `egress_hosts` and the actual runtime host are the same thing, so the check is meaningful. But for a genuinely generic tool whose `args` include a caller-or-model-supplied URL (the kind of tool an agent would use to "fetch this URL" from user-provided input), the declared `egress_hosts` at registration is disconnected from what host the code underneath will actually dial — `EgressPolicy` has no mechanism to catch that at call time, so a model convinced (via injected content or a bad plan) to pass a malicious URL into such a tool sails past this control entirely unless the tool's own implementation independently re-validates its resolved destination against the same allowlist. This is exactly the kind of "unvalidated input reaching a sensitive sink" gap a sharp reviewer should flag: the allowlist protects against a category of tool (fixed-destination), not the category (dynamic-destination) where egress control matters most.

## Q14: `EgressPolicy.allowed_hosts` values are `frozenset[str]` of exact host strings (line 60). What real-world hostnames would this incorrectly allow or deny compared to what an operator probably intended?

Exact string membership means no wildcard or subdomain matching: an operator who lists `"api.example.com"` in a tool's allowlist has NOT implicitly allowed `"cdn.api.example.com"` or `"example.com"` — each subdomain needs its own explicit entry, which is arguably the safer default (least privilege) but easy to get wrong operationally (a service that load-balances across `api-1.example.com`/`api-2.example.com` needs both listed, or every request to the non-listed one fails closed). Conversely, there's no normalization: `"API.Example.com"` (different case) or a trailing-dot FQDN (`"api.example.com."`) would NOT match an entry of `"api.example.com"` since `check()` does a raw `host in allowed` set-membership test with no `.lower()`/normalization step anywhere in this file — a caller supplying a host string in a different case than what was registered gets an unexpected denial, which fails closed (safe) but could be confusing to debug. There's also no port or scheme awareness (`"api.example.com:8443"` is a different string than `"api.example.com"`), and — tying back to Q13 — even a perfectly normalized, exact-match allowlist is only as good as the caller's guarantee that the `host` string passed into `check()` is the actual resolved destination, which this module has no way to verify.

## Q15: `SecretsProvider` is a `Protocol` with `get()`/`rotate()` (line 67), mirrored by `AuditSink`'s single-method Protocol. Why keep `CredentialVault` (env-backed) and `VaultCredentialProvider` (real Vault-backed) as two separate concrete classes instead of one class with a `backend` flag?

Two separate classes satisfying the same narrow Protocol is a cleaner factoring than one class branching on a `backend` parameter: each implementation owns exactly the state and error-handling relevant to *its* backend (`CredentialVault` tracks `_overrides`/`_rotated_at` dicts and reads `os.environ`; `VaultCredentialProvider` tracks `base_url`/`token`/`mount`/`timeout_s` and does real HTTP I/O against Vault's KV v2 API), so neither carries dead fields or unreachable branches for the other's concerns. It also means `CredentialVault`'s `age_s()` convenience method (line 128, not part of the `SecretsProvider` Protocol at all) can exist as extra, opt-in surface on the reference implementation without forcing every other `SecretsProvider` implementer (including a hypothetical `AWSSecretsManagerProvider`) to support it. The cost is exactly what Q7 already surfaces for `VaultCredentialProvider`: since neither class shares an implementation, there's no shared base class enforcing consistent behavior (e.g., consistent exception types across backends) — `CredentialVault.get` raises `KeyError` for a missing credential (line 121) while `VaultCredentialProvider.get` would surface whatever `urllib`/JSON-parsing exception occurs on a missing or malformed Vault response (`HTTPError`, `KeyError` on `body["data"]["data"]["value"]` if Vault's response shape doesn't match, etc.) — a caller written against the `SecretsProvider` Protocol that only catches `KeyError` for "credential missing" would NOT reliably catch a missing-secret case against the Vault-backed implementation.
