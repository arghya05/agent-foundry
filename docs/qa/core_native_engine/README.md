# agent_foundry/core/native_engine.py — Q&A

Implements the entire single-agent think/act/critique loop as plain, LangGraph-free Python (`NativeEngine`), plus `_NativeGraph`, a thin adapter that duck-types LangGraph's own compiled-graph `.invoke`/`.stream`/`.get_state`/`.update_state` interface closely enough that nothing downstream needs to know which engine it's talking to.

## Q1: Walk through exactly what happens, step by step, when `NativeEngine.run(config, "book a flight", thread_id="t1")` is called for a brand-new thread, and the model's first response includes a tool call that requires human approval.

`run()` (line ~146) acquires `self._lock_for("t1")` — a fresh per-thread lock created on demand via `_lock_for`'s `_threads_lock`-guarded `setdefault`. It then calls `_state_for("t1")`, which, since `"t1"` isn't in `self._threads` yet and no `state_store` is configured, creates a fresh state dict (`messages: []`, `critique_retries: 0`, `critique_last_score: None`, `_pending: None`) and caches it. The user message is appended to `state["messages"]`, and `_drive(config, state, "t1")` runs the loop: `_drive_stream` calls `_think`, which builds the system prompt (possibly augmented by memory/context-engine retrieval), calls `config.llm.complete(messages, task=..., tools=native_tools)`, and appends an assistant message with `tool_calls` since the response includes one. Because `has_tool_calls` is true, `_act` is called. Inside `_act`, the PDP's `config.pdp.decide(...)` for this call returns a decision where `not gr.allowed and "approval" in gr.reason` — `needs_approval` is `True`. Since this is a fresh call (`resume is None`, so `already_decided` is `False`), `flush_cleared()` runs any tool calls ordered *before* this one for real, then `state["_pending"]` is set to a dict describing the pending approval, and `_act` returns `self._raw(state, interrupt=pending)` — a dict with `messages`, `thread_id`, and `__interrupt__: [_Interrupt(pending)]`. `_drive_stream` yields that and returns immediately (line ~243–244), so `_drive`'s `for last in self._drive_stream(...): pass` loop ends there, and `run()` returns that raw dict up through `_NativeGraph.invoke()` to `result_from_graph_output`.

## Q2: `_state_for` explicitly does `state_store.load()` *outside* `self._threads_lock`, re-checking the cache after reacquiring the lock. What race would holding the lock during the load create, and is the re-check actually necessary?

`self._threads_lock` guards the **entire** `self._threads` dict, not any single `thread_id`'s entry — so holding it while calling `state_store.load(thread_id)` (a potentially slow network round-trip to Redis or Postgres, per the class docstring) would block every *other* `thread_id`'s concurrent `_state_for`/`_persist` call for the full duration of that one thread's load, even though they have nothing to do with each other. The fix (lines ~112–129) releases the lock before the load, then reacquires it briefly to do the actual insert. The comment is explicit that the re-check ("if thread_id in self._threads: return") is "defensive, not a fix for a reachable race" — its stated reasoning is that every real caller into `_state_for` already holds *its own* per-thread `_lock_for(thread_id)` for the whole duration of the call (see `run()`'s `with self._lock_for(thread_id):` wrapping the entire turn), so two concurrent `_state_for(thread_id)` calls for the *same* thread_id genuinely can't happen through any public entry point today. This claim is honest but worth pressure-testing: `_PausableTurns` in `native_orchestration.py` constructs fresh `NativeEngine()` instances and reaches directly into their private `_threads`/`_lock_for` internals — as long as every caller continues that same discipline, the race stays theoretical, but it's an invariant maintained by convention across files, not enforced by this class's own public API.

## Q3: Trace the exact chain of locks that guarantees "different thread_ids never block each other." What would break that guarantee if `self._thread_locks` were a single shared `threading.Lock()` instead of a dict of per-thread locks?

`_lock_for(thread_id)` (line ~104) acquires `self._threads_lock` only long enough to do `self._thread_locks.setdefault(thread_id, threading.Lock())` — a fast, in-memory dict operation — then releases it and returns the per-thread `threading.Lock()` object. The caller (`run`, `resume`, `stream_run`) then does `with self._lock_for(thread_id):` around the **entire** turn, holding only that one thread's lock for however long the turn takes (potentially several LLM calls and tool executions). Two different `thread_id`s get two different `Lock()` objects from the dict, so a slow turn on `"t1"` never blocks a concurrent turn on `"t2"` — they hold entirely separate lock objects. If `self._thread_locks` were replaced by one global `Lock()` shared across all threads, every conversation in the process would serialize behind whichever turn happened to acquire it first — a single slow tool call on one user's conversation would stall every other unrelated user's turn for the same duration, turning what's meant to be per-conversation isolation into full single-agent-instance-wide serialization.

## Q4: Explain the "re-run the whole node on resume" HITL semantics in `_act`. If two tool calls in one assistant turn both require approval, walk through what happens across two separate `.resume()` calls, and why this is safe only because of `ToolRegistry`'s idempotency store.

Suppose `_act` iterates two tool calls, `A` (needs approval) and `B` (needs approval), in order. On the first pass, `A` is reached first; since `resume is None`, `flush_cleared()` runs (nothing was cleared yet, since `A` is the first call), `state["_pending"]` is set for `A`, and `_act` returns an interrupt — `B` is never even evaluated in this pass. When the caller calls `.resume(approved=True)` for `A`, `_resume_locked` calls `_act(config, state, thread_id, resume=("A", call_id_A, True))`. This re-enters `_act` from the top, re-iterating **both** calls again: for `A`, `already_decided` is now `True` (its `tool_name`/`tool_call_id` match `resume`), so it falls through to `cleared` and gets dispatched for real, this time landing in `results`. For `B`, `resume` doesn't match, so `already_decided` is `False` again, `flush_cleared()` runs — which now actually executes `A`'s dispatch call a **second time** (the pass discarded `A`'s first, pre-pause `flush_cleared()` invocation's results without committing them to `state["messages"]`, per the comment at lines ~423–434) — and `B` pauses with its own interrupt. Only `ToolRegistry`'s `idempotency_store`, keyed by `_default_idempotency_key(session_id, tool_call_id)`, prevents `A`'s tool from actually running twice: the *dispatch call* happens twice, but the underlying tool implementation, if idempotency-aware, returns the cached first result instead of re-executing its side effect. Without that idempotency layer, a non-idempotent tool (e.g., "charge $50") would be charged twice — this module's docstring calls this "a known, pre-existing property of this codebase's HITL model, not something new here," meaning the risk exists in the LangGraph engine's own `interrupt()`-based resume too, not just here.

## Q5: `_drive_stream`'s docstring claims its yield pattern was "confirmed empirically" to match LangGraph's own `stream_mode="values"` chunk count — "4 chunks for a think->act->think turn." What's the actual risk of building a from-scratch engine's streaming contract around an empirically observed behavior of a third-party library rather than its documented API?

LangGraph's public documentation for `stream_mode="values"` says it yields "the full state after each step," but doesn't commit to a precise, versioned guarantee about exactly which internal transitions count as a "step" for a compiled `StateGraph` built by `build_agent_graph` — the comment states this was verified "empirically (not just by reading LangGraph's docs)," meaning someone actually ran a real graph and counted chunks (per `tests/test_orchestration.py`'s or `test_workflow_engine_protocol.py`'s referenced usage). The risk is that this is an implicit contract with an external dependency's *observed* behavior rather than its documented one — a LangGraph version upgrade that changes internal step granularity (e.g., splitting a node's execution into two supersteps for some new feature) could silently desynchronize the two engines' streaming cadence without either engine's own code changing, and there's no test guarding against LangGraph's behavior drifting out from under this assumption other than whatever comparison test already exists. This is an honest, documented risk rather than a hidden one, but it's real: matching an unversioned empirical observation is inherently more fragile than matching a documented contract.

## Q6: `_resume_locked`'s critique-escalation branch asserts `config.critique is not None`. Under what circumstance could that assertion actually fail, given a `StateStore` is in play?

The comment states this path is "only ever reached when a critique gate paused this turn, which can't happen without config.critique set" — true for a single, continuously-running process where the same `AgentConfig` instance that paused the turn is also the one resuming it. But with `state_store` configured (line ~98), state is meant to survive **across** `NativeEngine` instances — e.g., after a process restart, a new `NativeEngine(state_store=same_store)` loads a previously-persisted `state["_pending"]` with `kind="critique"` via `_state_for`'s load-on-miss path. If that *new* process's `AgentConfig` was constructed differently — say, critique was removed from the agent's configuration between the pause and the restart — then `resume()` would be called against a state whose `_pending["kind"] == "critique"` but whose *current* `config.critique` is `None`, and `assert config.critique is not None` (line ~208) would raise `AssertionError` rather than a clean, descriptive error. This is a real, if narrow, gap: the assumption "the config that resumes a turn matches the config that paused it" is guaranteed only within one process's lifetime, not across a restart backed by durable `state_store` persistence — exactly the scenario the `state_store` feature exists to support.

## Q7: Compare `_NativeGraph.update_state`'s plain `state.update(values)` to LangGraph's own `update_state()` behavior on a reducer-typed `messages` channel (`Annotated[list, operator.add]`), as documented in `core/run.py`'s module docstring. Why is a plain assign correct here but would be wrong for LangGraph?

`core/run.py`'s docstring documents an empirically-verified LangGraph behavior: calling `update_state()` against a channel declared with an `operator.add` reducer **appends** the new value onto the existing one rather than replacing it — seeding an already-invoked LangGraph thread with a "replacement" message list actually concatenates it onto history. `_NativeGraph.update_state` (native_engine.py, lines ~585–595) has no such reducer machinery at all: `NativeEngine`'s per-thread state is a bare Python dict with no `Annotated`/reducer typing, so `state.update(values)` is a literal field-by-field overwrite — assigning `state["messages"] = [...]` genuinely *replaces* the list. This is why `core/run.py`'s `Run.fork()` deliberately builds its seeding logic around "seed a brand-new, empty thread" (append-onto-empty is equivalent to set, safe on both engines) rather than "truncate an existing thread's history in place" — even though a truncating assign would be safe specifically on the native engine, building the shared primitive around the LangGraph-safe approach keeps the two engines interchangeable for anything built on top of `update_state`, matching `WorkflowEngine`'s whole point.

## Q8: The module's own docstring self-admits a scope limitation: it doesn't reproduce LangGraph's support for "a queue of resume values across several sequential interrupts in one turn." What would need to change to support that?

Currently, `state["_pending"]` (used throughout `_act`/`_critique`/`_resume_locked`) holds exactly one pending interrupt at a time — a single dict describing either a tool approval or a critique escalation — and `.resume()` accepts exactly one `approved`/`decision` pair per call, consumed immediately by `_resume_locked`. To support LangGraph's model (queueing several resume values so a caller can pre-answer multiple upcoming interrupts before they even occur), `state` would need a `_pending_queue: list[dict]` rather than a single `_pending: dict | None`, `resume()`'s signature would need to accept a sequence of decisions rather than one, and `_act`'s loop (which currently re-evaluates every tool call from scratch on each resume, per Q4) would need to check the queue for a *matching* pre-supplied decision for each call rather than only ever comparing against the single most-recently-supplied `resume` tuple. This is nontrivial because the current "re-run everything, match by tool_name+tool_call_id" design (lines ~421) would need to become "pop the next matching entry off a queue," which changes the idempotency-key-reliant safety argument in Q4 as well, since now multiple approved-but-not-yet-committed tool calls could be in flight across one resume cycle.

## Q9: Why does this module reuse `orchestration.py`'s private, underscore-prefixed helpers (`_finalize_turn`, `_get_all_tool_calls`, `_tool_param_names`, `_dispatch_tool_calls`, `_resolve_identity`, `_default_idempotency_key`, `_tool_timeout`, `CLARIFY_PREFIX`) instead of re-implementing them? What's the coupling risk?

The module docstring is explicit: these are "pure, framework-agnostic functions already," and duplicating them would create "two copies to keep in sync" — specifically calling out `_get_all_tool_calls`'s own documented history of fixing "the multi-tool-call bug," where a fresh reimplementation could easily reintroduce that exact bug by not knowing it was ever a problem. The coupling risk is that these are *private* (underscore-prefixed) symbols of another module, meaning `orchestration.py`'s maintainers have no formal contract obligating them to keep those signatures stable — a refactor of `orchestration.py` that renames or changes the behavior of `_dispatch_tool_calls` (say, changing its return-value shape) would break `native_engine.py` silently unless both modules are updated together, since Python enforces no interface boundary between "private to this module" and "imported by a sibling module in the same package." This is a deliberate, acknowledged trade-off (correctness-via-shared-code now, versus a formal public API for these helpers that doesn't yet exist) rather than an accident.

## Q10: What happens to a paused (interrupted) turn on process restart, with and without `state_store` configured?

Without `state_store` (the default, `None`), all state — including a pending `_pending` dict describing an in-flight approval or critique escalation — lives only in `self._threads`, an in-process Python dict. A process restart loses it entirely: a subsequent `.resume()` call against the same `thread_id` on a new process would create a *fresh* `NativeEngine` with an empty `self._threads`, `_state_for` would build a brand-new state with `_pending: None`, and `_resume_locked` would immediately raise `RuntimeError(f"thread {thread_id!r} has nothing pending to resume")` (line ~195) — the pending approval is simply gone, with no error at the time it was lost, only when someone tries to resume it later. With `state_store` configured, `_raw()` (line ~260) persists via `self._persist(state["thread_id"])` at exactly the granularity every mutating step completes — including the moment `_pending` is set, since `_act`/`_critique`'s pause branches call `self._raw(state, interrupt=pending)`, which itself calls `_persist` internally. A new process's `_state_for` on cache-miss then does `state_store.load(thread_id)`, recovering the exact `_pending` dict, and `.resume()` proceeds normally — assuming (per Q6) the resuming process's `AgentConfig` is compatible with what paused it.

## Q11: Why does `flush_cleared()` actually *execute* tool calls that were ordered before a later approval-needing call, rather than simply discarding the whole batch and re-running everything cleanly from the top on resume?

The comment explains this preserves ordering semantics: "everything ordered before an approval-needing call has genuinely run" before the pause signal is returned — matching what a user reviewing the pending approval would expect (any prior, non-gated actions in that turn already happened, only the flagged one is waiting). The cost is exactly the double-dispatch behavior traced in Q4: those already-executed calls get dispatched *again* when the turn resumes and `_act` re-runs from scratch, relying on `ToolRegistry`'s idempotency cache to avoid duplicate side effects. An alternative design — never executing anything until the entire turn's approvals are resolved — would avoid double-dispatch entirely but would change the user-facing behavior: reviewers approving a batch of gated actions would have no visibility into whether the earlier, non-gated actions in that same turn had already run, and if the LLM's tool-calling behavior depends on earlier tool results within the same turn (it doesn't here, since all calls in one assistant message are dispatched from the same fixed `calls` list), the two orderings could diverge. The chosen design optimizes for "the turn behaves as if unpaused, except at exactly the gated point" at the cost of tool-dispatch idempotency being load-bearing rather than optional.

## Q12: Trace what happens in `_think` if `with_timeout(call, seconds=config.step_timeout_s)` raises a timeout exception partway through an LLM call. What state is left in `state["messages"]`, and is it consistent for the next turn?

By the time `_think` calls `with_timeout(call, seconds=...)` (line ~331), `state["messages"]` already has the user's message appended (done earlier, either in `run()` before `_drive` is called, or via a critique retry appending a synthetic user message). If `with_timeout` raises, execution never reaches `config.budget.spend(...)`, `span["attributes"].update(...)`, or the `state["messages"].append(...)` calls for the assistant's reply — the exception propagates straight up through `_drive_stream` → `_drive` → `run()`, out past the `with self._lock_for(thread_id):` context manager (releasing the lock cleanly), and out of `NativeEngine.run()` itself to whatever called it. The result: `state["messages"]` is left with the user's message appended but **no** corresponding assistant reply — the turn is half-committed. If the caller retries by calling `.run()` again with a new message, `state["messages"]` would end up with two consecutive `role: "user"` messages (the timed-out one, followed by the new one), since nothing rolls back the first user append on failure. Whether that's a problem depends on the downstream LLM's tolerance for consecutive user turns in its message format — this is an unhandled, undocumented edge case: there's no compensating rollback of the just-appended user message on a mid-`_think` exception anywhere in this file.

## Q13: Compare LangGraph's `interrupt()`-based pause mechanism to how this module implements "pause the graph." What's fundamentally different in the two suspension models?

LangGraph's `interrupt()` is an actual control-flow primitive: calling it inside a node function raises a special exception that LangGraph's runtime catches to unwind execution back to its own scheduler, persisting the *entire* graph's execution state (which node was running, what its local variables/inputs were) via the checkpointer, so a later `.invoke(Command(resume=...))` call can resume execution *exactly where it left off*, including local state inside the interrupted node function itself. `NativeEngine` has no equivalent unwind-and-resume-mid-function mechanism at all — `_act` (and `_critique`) simply `return`s a sentinel dict (`self._raw(state, interrupt=pending)`) from a normal Python function call, and the **entire calling chain re-executes from `_act`'s top on resume**, using `state["_pending"]` and the `resume=` tuple purely as data to short-circuit the decision that paused it last time (see Q4's trace). This is a fundamentally simpler, "replay-with-a-flag" design rather than true continuation-passing/coroutine suspension — it's why the tool-call re-dispatch behavior in Q4/Q11 exists at all: there's no way to resume *mid-function* without re-entering the function from its start, so idempotency at the tool-dispatch layer has to compensate for what a real suspend/resume primitive wouldn't need.

## Q14: What would need to change in `NativeEngine` to add genuine Temporal-backed durability, beyond the optional `state_store` it already supports?

The `state_store` mechanism already gives per-thread state durability at "one snapshot per completed step" granularity (via `_raw()`), which is closer to Temporal's *event-sourcing* model than to LangGraph's checkpointer, but it's missing the actual durable-execution guarantee Temporal provides: automatic replay of in-flight work after a crash mid-step (e.g., if the process dies *during* `config.llm.complete(...)` inside `_think`, nothing here resumes that exact in-flight LLM call — the next process would simply re-run `_think` from the last persisted state, calling the LLM again from scratch, which is a correctness difference from Temporal's activity-retry model where each individual side-effecting call is itself checkpointed and not blindly repeated). Genuinely Temporal-backed durability would mean rewriting `_think`/`_act`/`_critique` as Temporal activities called from a Temporal workflow function, letting Temporal's own SDK handle the checkpoint-before-each-activity and automatic-replay-on-crash semantics — a much larger structural change than plugging in a different `StateStore` implementation, since Temporal's programming model (deterministic workflow code, side effects isolated into activities) doesn't map cleanly onto this class's current "one big Python function doing everything inline" structure.

## Q15: What is a genuine limitation of `NativeEngine` you'd fix given more time, beyond what's already self-documented in the module's own docstring?

The `_think` timeout/consistency gap from Q12 — a mid-LLM-call timeout leaving a dangling, unanswered user message in `state["messages"]` with no rollback — is a real, silent correctness gap that isn't called out anywhere in the module's own docstring (which focuses on the multi-agent-topology and multi-interrupt scope limits instead). A fix would wrap the message-append and the LLM call together such that either both succeed or neither leaves a trace — e.g., appending the user message only after a successful `_think` call returns, or explicitly catching the timeout and appending a synthetic "the assistant did not respond in time" assistant message so the conversation never ends up with two consecutive unanswered user turns.
