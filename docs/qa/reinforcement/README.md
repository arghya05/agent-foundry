# agent_foundry/reinforcement.py — Q&A

Two offline, batch-cadence feedback loops that close eval signal back into the agent (PLAN.md section 5): `PromptOptimizer` curates few-shot exemplars from the best-scoring recent trajectories and flags the worst for prompt review; `PreferenceStore` accumulates HITL approve/deny decisions as chosen/rejected pairs and exports them as JSONL for DPO/RLAIF or distillation. Neither runs inside a live request.

## Q1: This module is named `reinforcement.py`, but is anything here actually reinforcement learning in the technical sense (a reward signal driving policy gradient updates, value functions, exploration/exploitation)? Be precise about what this code does and doesn't do.

No — nothing in this file trains a model, computes a gradient, or updates any policy parameters. `PromptOptimizer.observe()` (lines 26-35) computes a plain arithmetic mean of `EvalRecord.score` values for a given `unit`, and buckets the resulting trajectory into either `exemplars` (if `avg >= good_threshold`) or `flagged` (if `avg <= bad_threshold`) — that's a simple two-bin classification of trajectories by average score, not a reward function feeding any learning algorithm. `few_shot_block()` (lines 37-40) just serializes the top-k highest-scoring trajectories as JSON, concatenated into a string meant to be spliced into a system prompt — that's in-context learning via prompt engineering (few-shot examples), a fundamentally different mechanism from RL's parameter updates. `PreferenceStore` (lines 43-56) doesn't train anything either — it just accumulates `{context, chosen, rejected, source}` dicts and writes them to a JSONL file via `export_jsonl()`; the actual DPO/RLAIF training step (which *would* be genuine preference-based reinforcement learning, e.g. Direct Preference Optimization's loss function operating on chosen/rejected pairs) is explicitly named in the docstring as something this exports *for* — happening entirely outside this module, presumably as a separate offline training job this codebase doesn't implement. The honest characterization: this is a **feedback curation and export pipeline** — the data-plumbing and heuristic-selection layer that a real RL/preference-learning pipeline would consume — not RL itself. The module name and PLAN.md's "reinforcement loop" framing describe the broader *system* this plugs into, not what this specific file computes.

## Q2: Walk through exactly what happens when `PromptOptimizer.observe(unit="think", trajectory=[...], eval_harness=harness)` is called, for a `unit` that has three matching `EvalRecord`s with scores `[1.0, 1.0, 0.9]`.

`observe()` (line 26) first filters: `scores = [r.score for r in eval_harness.records if r.unit == unit]` — a linear scan over *every* record in the harness, matching purely on the `unit` field string, with no filtering by `session_id`, `level`, or `metric` at all. For the example, this returns `[1.0, 1.0, 0.9]` (assuming exactly three records across the harness happen to have `unit="think"` — critically, this could span *multiple different sessions*, not just the one trajectory being observed right now, since nothing in this filter scopes it to a single session). `avg = sum(scores)/len(scores)` → `0.9\overline{6}`. It builds `entry = {"unit": unit, "trajectory": trajectory, "score": avg}` and, since `0.9\overline{6} >= good_threshold` (default `0.8`), appends it to `self.exemplars`. Note this average blends scores from however many past calls happened to share this exact `unit` string across the harness's entire lifetime — the *trajectory* passed in for this specific call gets tagged with a score computed from a broader, cross-session population of same-named records, not a score computed from that trajectory's own execution alone.

## Q3: That reveals something worth probing further — `observe()` filters `eval_harness.records` by `r.unit == unit` with no session scoping. What's the actual bug/limitation risk here if `PromptOptimizer.observe()` is called once per session for a recurring `unit` name like `"think"`?

Since `"think"`, `"act"`, or any other recurring node name is the exact `unit` string `orchestration.py`'s `make_think_node`/`make_act_node` record against (per `eval.py`'s own instrumentation conventions), and `EvalHarness.records` accumulates *every* record from *every* session for the harness's whole lifetime, calling `observe(unit="think", ...)` after each new session doesn't score "how did the `think` step do in *this* trajectory" — it scores "how has `think` performed on average across every session ever recorded in this harness, including sessions that have nothing to do with the trajectory currently being curated." This means: (1) the `avg` used to decide exemplar/flagged status drifts and gets diluted as more history accumulates in the harness — a single genuinely excellent trajectory observed early, when the harness has few records, could tip `avg` above `good_threshold` even though its *own* individual quality was middling, simply because the pool of same-`unit` scores it's being averaged against happened to be small and favorable at that point; (2) the *same* trajectory, if `observe()` were called on it twice (accidentally, or due to retry logic), would get scored against a slightly different (larger) pool of harness records the second time, producing a different `avg` for literally the same trajectory data — a non-idempotency footgun. The comparable, correctly-scoped tool in this codebase is `eval.trajectory_report(harness, session_id)`, which *does* filter records to one session via `detail.get("session_id")` — `PromptOptimizer.observe()` doesn't reuse that machinery and instead does its own coarser, unscoped filter by `unit` alone, which is a real design inconsistency between the two modules.

## Q4: Why does `few_shot_block()` sort by score and take only the top `k` (default 3), rather than including every exemplar ever collected?

Splicing every historically-collected high-scoring trajectory into a system prompt would grow the prompt unboundedly as `self.exemplars` accumulates over the life of a long-running `PromptOptimizer` — every additional exemplar costs real prompt tokens (and thus real $ and latency) on every subsequent LLM call that uses this few-shot block, with rapidly diminishing returns past a small number of well-chosen examples (a well-established few-shot prompting finding: quality and diversity of a handful of examples usually beats raw quantity). `few_shot_block(k=3)` (line 37-40) does `sorted(self.exemplars, key=lambda e: e["score"], reverse=True)[:k]` — always taking the *current* top-k by score, recomputed fresh on every call rather than maintaining a running top-k incrementally, which is correct but means this is an O(n log n) sort over the full `exemplars` list every single time `few_shot_block()` is called; for a `PromptOptimizer` that's been running a long time with many exemplars, this becomes a real (if probably minor in practice) inefficiency compared to maintaining a bounded max-heap of size `k` as exemplars are added.

## Q5: `PromptOptimizer.exemplars` and `.flagged` are unbounded lists (`field(default_factory=list)`) with no eviction, size cap, or expiry anywhere in this module. What's the practical consequence of running this in a long-lived production process?

Every call to `observe()` that crosses either threshold appends to one of these two lists permanently — there's no cap, no LRU eviction, no time-based expiry, and no persistence/reload boundary visible in this file. For `exemplars`, the practical cost is bounded in one sense (`few_shot_block()` only ever reads the top `k`, so a large `exemplars` list doesn't directly bloat the prompt), but it does mean the list itself grows without bound in memory for the lifetime of the process, and the per-call sort cost in Q4 grows with it. For `flagged`, there's no `few_shot_block()`-equivalent consumer function at all in this file — `flagged` is just accumulated and presumably meant to be inspected manually or exported by calling code ("flags the worst ones for prompt review," per the module docstring) but this module provides no export/summary method for it (unlike `PreferenceStore.export_jsonl()`, which *does* give `pairs` a durable export path) — so `flagged` trajectories only exist as long as the process does, with no built-in mechanism to persist them for the "prompt review" the docstring promises actually happens on. A real production deployment of `PromptOptimizer` would need external code to periodically snapshot/export both lists and likely truncate/reset them, none of which exists here.

## Q6: `PreferenceStore.record()` takes a `source` parameter defaulting to `"hitl"`. What's the significance of tracking provenance this way, and what happens to `export_jsonl()`'s output if a caller mixes HITL-sourced pairs with some other `source` value in the same store?

Tracking `source` per pair (line 49) matters because a downstream DPO/RLAIF training pipeline consuming the exported JSONL likely wants to weight or filter training pairs differently depending on where the preference signal came from — a human's explicit approve/deny decision (`"hitl"`, the default) is a much higher-trust signal than, say, an LLM-judge-derived preference or a heuristic-derived one, if this store were ever fed by something other than HITL decisions despite its docstring's HITL-specific framing ("Chosen-vs-rejected pairs, sourced from HITL approve/deny decisions," line 45). `export_jsonl()` (lines 52-55), however, does nothing with `source` beyond faithfully serializing it into each line's JSON — it doesn't filter, group, or annotate the output file by source in any structural way (no separate files per source, no summary of the source-mix). So if a caller mixes `"hitl"` and some other `source` value into the same `PreferenceStore`, the exported JSONL is a flat, undifferentiated stream of pairs where a downstream training script has to itself parse each line's `"source"` field and decide what to do with the mix — this module provides the field but no policy around using it, which is consistent with its generally minimal, mechanism-not-policy design throughout.

## Q7: What happens if `PreferenceStore.export_jsonl()` is called with a `path` that's already open for writing elsewhere, or if the export is interrupted mid-write (process killed partway through)?

`export_jsonl()` opens the file in `"w"` mode (line 53) — truncating whatever was there before, unconditionally, every call — and writes one JSON line per pair in a plain `for` loop with no atomicity guarantees: no temp-file-then-rename pattern, no fsync, and no `try`/`finally` to handle a partial write cleanly. If the process is killed mid-loop, the resulting file contains a truncated prefix of the full pair list (however many lines got flushed to the OS before the kill), silently indistinguishable from "this is genuinely a smaller dataset" unless the caller happens to know the expected pair count in advance and checks it. If another process has the same path open for writing concurrently (a genuinely unusual but possible misconfiguration), the two processes' writes would interleave unpredictably at the OS level, producing a corrupted file with intermixed/partial JSON lines from both writers — nothing here defends against that. For a training data export specifically, where a partially-corrupted or unexpectedly-truncated file could either crash a downstream training job's JSONL parser (on a malformed final line) or silently train on fewer, differently-distributed examples than intended, this is a real production gap — a more robust implementation would write to a temp path and atomically rename on completion, exactly the pattern many data-export tools use to avoid partial-file corruption.

## Q8: What's the actual reliability/rigor story if the "eval signal" feeding `PromptOptimizer.observe()` is noisy or delayed — e.g. a KPI's LLM-judge score (from `kpi.py`'s `llm_judge_kpi`) that's itself uncalibrated, or a trajectory that gets scored well after the fact?

`observe()` has zero defense against noisy input — it takes whatever `EvalRecord.score` values happen to exist for a given `unit` and averages them with equal weight, with no outlier rejection, no confidence weighting, and no distinction between a deterministic KPI's score (reliable, reproducible) and an LLM-judge KPI's score (subject to whatever miscalibration `kpi.py`'s own `judge_calibration_kpi` exists to detect, per that module's Q&A). If the judge feeding these scores is systematically biased — say, it over-rates verbose answers — `PromptOptimizer` would happily curate exemplars that reinforce exactly that bias into future few-shot prompts, compounding the judge's miscalibration into the agent's own behavior over successive rounds of this feedback loop (a feedback-loop amplification risk inherent to any self-reinforcing curation system fed by an imperfect signal, and one this module has no mechanism to detect or dampen). On delay: nothing in `observe()` requires the trajectory and its eval records to be temporally close — `eval_harness.records` simply accumulates over the harness's lifetime, so a `unit`'s average could be computed from records spanning a long time window during which the underlying agent/prompt may have already changed, meaning `observe()` could be scoring a trajectory against a stale population of historical scores that no longer reflects current behavior. Both of these are genuine, unaddressed methodological gaps — this module is a mechanism for aggregating and thresholding scores, not a robust statistical or bias-aware aggregation system.

## Q9: How does the two-tier design here (`PromptOptimizer` = cheap, same-day batch job; `PreferenceStore` = slower, scheduled export) compare to how a production RLHF/DPO pipeline (e.g. what a team using OpenAI's fine-tuning API or an open-source TRL/DPO pipeline) would actually structure this?

The module docstring's own framing (lines 3-9) maps cleanly onto two real, distinct stages of a production preference-learning pipeline: `PromptOptimizer` is analogous to fast, cheap **prompt-engineering iteration** — the kind of thing you'd do same-day, in response to recent eval signal, entirely within the prompt itself (no model weights touched) — while `PreferenceStore`'s JSONL export is analogous to the **data-collection stage** that feeds an actual weight-updating training job (DPO/RLAIF/distillation), which in a real TRL-based pipeline would consume exactly this chosen/rejected pair format (TRL's `DPOTrainer`, for instance, expects `prompt`/`chosen`/`rejected` fields — structurally very close to what `PreferenceStore.pairs` already stores) as its training dataset. What this module does *not* implement, and what a real production pipeline needs on top: the actual training loop (loss computation, gradient updates, LR scheduling — none of which is remotely in scope for an in-process Python dataclass exporting JSONL), any data quality filtering before export (deduplication, contradiction detection between pairs, minimum-pair-count gating before a training run is even worth kicking off), and any evaluation of the *trained* model afterward to confirm the DPO/RLAIF round actually improved behavior rather than degrading it (a full loop would want to re-run the eval harness against the newly fine-tuned model and compare against the pre-training baseline — exactly the kind of regression check `eval_dataset.py`'s baseline/`compare_to()` machinery could support, though nothing here wires the two together automatically).

## Q10: Contrast this module's approach with LangSmith's or Weights & Biases' concept of "dataset curation from production traffic" for fine-tuning — is `PromptOptimizer`'s exemplar/flagged split methodologically comparable?

LangSmith's dataset-curation workflow typically lets you tag production runs (via a UI or API), filter by score/feedback, and export a curated dataset for few-shot prompting or fine-tuning — conceptually similar to what `PromptOptimizer` does, but with a materially richer selection mechanism: filtering by arbitrary metadata, manual human review/tagging on top of automated scores, and versioned dataset snapshots you can diff over time. `PromptOptimizer`'s selection logic is deliberately much simpler: exactly two fixed thresholds (`good_threshold=0.8`, `bad_threshold=0.3`) applied to a single averaged score per `unit`, with everything in between (`0.3 < avg < 0.8`) silently excluded from both `exemplars` and `flagged` — a real, if reasonable, methodological simplification: there's no notion of "borderline" trajectories worth a closer look, they simply fall into neither bucket and are never surfaced anywhere. There's also no deduplication or diversity-aware selection in `few_shot_block()` — `sorted(...)[:k]` could easily return `k` nearly-identical high-scoring trajectories (e.g. three instances of the same easy query all scoring 1.0) rather than a diverse, representative sample, whereas good few-shot curation typically wants to actively maximize diversity among the chosen examples, not just raw score. This is consistent with the module's overall philosophy of being a lightweight, easily-understood mechanism rather than a fully-featured curation platform — appropriate for a smaller-scale or earlier-stage deployment, but a real gap versus a purpose-built curation tool if the exemplar pool ever grows large or repetitive.

## Q11: What happens if `good_threshold` and `bad_threshold` are misconfigured such that `bad_threshold > good_threshold` (e.g. someone accidentally swaps them)?

Nothing in `PromptOptimizer`'s `@dataclass` definition validates the relationship between the two thresholds — they're independent fields with independent defaults (`0.8` and `0.3`), and `observe()`'s `if avg >= self.good_threshold: ... elif avg <= self.bad_threshold: ...` (lines 32-35) is just two independent comparisons, not a single range check. If someone swapped them (`good_threshold=0.3, bad_threshold=0.8`), then for a trajectory with `avg=0.9`: the first branch `0.9 >= 0.3` is `True`, so it's still added to `exemplars` — the `elif` never even gets checked, since the `if` already matched. For `avg=0.1`: `0.1 >= 0.3` is `False`, falls to `elif 0.1 <= 0.8` which is `True`, so it lands in `flagged`. Actually walking through the full range with swapped values: everything `>= 0.3` goes to `exemplars` (including genuinely mediocre `0.3-0.79` trajectories that shouldn't be treated as exemplary), and only things `< 0.3` reach the `elif`, all of which then satisfy `<= 0.8` and land in `flagged` — so the practical effect of swapping the thresholds is that the "exemplar" bar becomes far too permissive (anything decent-or-better gets treated as a few-shot-worthy example) while the "flagged" bucket still correctly catches only genuinely poor trajectories, just via a different (accidentally still-functional) comparison path. It's not a crash, but it is a silent quality-bar degradation for `few_shot_block()`'s output that no validation in this module would catch — a `__post_init__` assertion (`good_threshold > bad_threshold`) would be a cheap, worthwhile safeguard that's currently absent.

## Q12: `PreferenceStore.record()` has no deduplication — what happens if the same trajectory gets reviewed twice by HITL (e.g. a reviewer accidentally re-approves/re-denies the same turn) and recorded twice?

`record()` (line 49) unconditionally appends `{"context": context, "chosen": chosen, "rejected": rejected, "source": source}` to `self.pairs` — there's no equality check against existing entries, no idempotency key, and no dedup pass anywhere in `export_jsonl()` either. A duplicate HITL review (the same context/chosen/rejected triple recorded twice, whether from a genuine double-click in a review UI, a retried API call, or a batch job re-processing the same feedback event) simply produces two identical lines in the exported JSONL. For a downstream DPO/RLAIF training job, this isn't a crash, but it does silently *overweight* that particular pair relative to every other pair in the dataset — a training objective that treats each JSONL line as one training example effectively counts the duplicated pair twice, which skews the resulting preference model's calibration toward whatever idiosyncrasy that specific (possibly accidentally-duplicated) example represents. Since `PreferenceStore` has no `session_id`/idempotency key anywhere in its schema, there's also no principled way to *retroactively* detect and remove duplicates once they're in `self.pairs` — dedup would require comparing full `context`/`chosen`/`rejected` payloads for exact equality, which works for byte-identical duplicates but wouldn't catch near-duplicates (the same underlying decision recorded with slightly different context formatting).

## Q13: If two threads call `PromptOptimizer.observe()` concurrently on the same instance, is there a race condition beyond the simple GIL-atomicity of individual list appends?

`observe()` itself does a read (`scores = [r.score for r in eval_harness.records if r.unit == unit]`, a full list comprehension scan) followed by a conditional append to either `self.exemplars` or `self.flagged`. The append itself is GIL-atomic (same reasoning as `Tracer.spans`/`ExperimentTracker._records` elsewhere in this codebase), so no corruption of `exemplars`/`flagged` can occur from concurrent appends. But the *read* — scanning `eval_harness.records` — is not protected by anything, and if a third thread is concurrently calling `eval_harness.record(...)` (appending a new `EvalRecord`) while `observe()`'s list comprehension is iterating, CPython's list iteration over a list being appended to concurrently is memory-safe (no crash) but the exact snapshot `scores` ends up with is timing-dependent — the comprehension might or might not include a record that was appended mid-iteration, depending on precisely when the append happened relative to where the comprehension's internal cursor is. This doesn't corrupt anything, but it does mean `observe()`'s computed `avg` is not a fully deterministic function of "the state of `eval_harness` at the moment `observe()` was called" under concurrent writers — a subtle non-reproducibility that compounds with the unscoped-filtering issue from Q2/Q3 (an already-fuzzy average becomes fuzzier still under concurrent instrumentation).

## Q14: `PromptOptimizer` and `PreferenceStore` both store full trajectory/context payloads directly in their own lists (`exemplars`, `flagged`, `pairs`) rather than storing a `session_id` and re-deriving the trajectory from `EvalHarness`/some other source of truth on demand. What's the tradeoff, and does this create a data-drift risk analogous to the one `eval.py`'s `TrajectoryReport` docstring explicitly warns about for cost/latency?

`eval.py`'s `TrajectoryReport` docstring is explicit that cost/latency are deliberately *excluded* and left to `CostLedger`/`sla_tracker` specifically to avoid "a second, driftable copy of the same numbers" (per that module's Q&A). `reinforcement.py` takes the opposite approach for trajectory data: `observe()` takes a `trajectory: list[dict]` parameter directly and stores a full copy of it in `entry["trajectory"]` inside `self.exemplars`/`self.flagged`, and `PreferenceStore.record()` similarly stores full `context`/`chosen`/`rejected` payloads rather than a `session_id` pointer back into some canonical trajectory store. This is a deliberate and reasonable tradeoff given this module's actual purpose: `few_shot_block()` needs the *literal trajectory content* to splice into a prompt (a `session_id` alone would require a lookup against `EvalHarness`/wherever raw trajectories live, at prompt-construction time, adding a dependency and a failure mode `few_shot_block()` currently doesn't have), and `export_jsonl()` needs the actual `chosen`/`rejected` text to hand to a DPO trainer — a pointer-based design would just push the "go fetch the real data" problem onto whatever consumes the export, likely well after the original session's data might have been garbage-collected or aged out of whatever store held it. The real cost of this choice is that `PromptOptimizer`/`PreferenceStore` become their own persistent copies of trajectory data, entirely decoupled from `EvalHarness` after the fact — if the original trajectory in `EvalHarness` were later corrected, redacted, or found to be based on a data quality issue, there's no mechanism here to propagate that correction into an already-stored `exemplars`/`pairs` entry; the copy has already drifted from whatever the "current" source of truth might later become.

## Q15: What's a limitation of `reinforcement.py` you'd fix given more time?

The most consequential fix is `PromptOptimizer.observe()`'s unscoped record filtering (Q2/Q3) — matching purely on `unit` across the *entire* harness's history, rather than scoping to the specific session/trajectory being observed, means the average score driving exemplar/flagged classification is contaminated by however much unrelated history happens to share that unit name, and produces non-idempotent results if the same trajectory is observed more than once as the harness accumulates more records. I'd have `observe()` take (or default to deriving) a `session_id` and reuse `eval.trajectory_report()`'s already-correct session-scoping logic, rather than reimplementing a coarser, unit-only filter from scratch. A close second: the complete lack of atomic-write safety in `PreferenceStore.export_jsonl()` (Q7) — a truncating `"w"`-mode write with no temp-file-and-rename pattern is a real risk for a training-data export path, where a partial or corrupted file could silently degrade or crash a downstream DPO training run; I'd switch to writing to a temp file and renaming into place on success, and add a minimal sanity check (e.g. asserting the written line count matches `len(self.pairs)`) before considering the export complete.
