# agent_foundry/sandbox.py — Q&A

`run_sandboxed()` executes model-generated Python with a restricted `__builtins__` namespace and a `with_timeout` wall-clock limit (from `runtime.py`), exposed to an agent as the `code_execution_tool()` `ToolSpec` — the module's own docstring is upfront that this is process-level isolation only, "not a deliberately hostile actor" boundary.

## Q1: `_SAFE_BUILTINS` (line 21-25) excludes `__import__`, `open`, `exec`, and `eval` from the namespace handed to `exec(code, scope)`. Does that actually stop a determined adversarial payload from escaping the sandbox? Show a concrete escape.

No — this was verified directly against the exact `_SAFE_BUILTINS` dict this file builds. Restricting `__builtins__` blocks anything that requires calling a *named builtin function* (`import os` fails because the `import` statement calls `__import__`, which isn't in `_SAFE_BUILTINS`; `open(...)`/`exec(...)`/`eval(...)` fail the same way). It does **not** block ordinary attribute access on any object already reachable in the restricted scope, because attribute traversal is a core language operation mediated by the object model, not by `__builtins__`. Running exactly this code against the module's own `_SAFE_BUILTINS`:

```python
result = [c.__name__ for c in ().__class__.__base__.__subclasses__()][:5]
```

succeeds and returns real subclass names (`['type', 'async_generator', 'bytearray_iterator', 'bytearray', 'bytes_iterator']`) — this is the classic Python sandbox-escape technique: `()` is a tuple literal available with zero builtins, `.__class__` gets its type, `.__base__` walks to `object`, and `.__subclasses__()` enumerates *every class currently loaded in the process*, including ones with file, subprocess, or `os`-adjacent capability (e.g., anything importing `subprocess.Popen`, `os._wrap_close`, or similar, depending on what else the host process has imported). From there, an attacker walks the returned class list, finds a subclass whose `__init__`/methods give file or process access, and instantiates/calls it directly — none of that requires `__import__`, `open`, `exec`, or `eval`. The sandbox's own docstring (lines 7-11) is honest about exactly this: "this is process-level isolation only... It stops accidental misuse (an infinite loop, a stray `import os`), not a deliberately hostile actor." This confirms it in code, not just in the docstring's disclaimer.

## Q2: `run_sandboxed` calls `with_timeout(_exec, seconds=timeout_s)`, and `with_timeout` (in `runtime.py`) is `with concurrent.futures.ThreadPoolExecutor(max_workers=1) as ex: return ex.submit(fn).result(timeout=seconds)`. Walk through exactly what happens when `code` is `while True: pass` and `timeout_s=1.0`. Does the caller actually get a `TimeoutError` back after ~1 second?

This was verified by direct execution, not just read: it does **not**. `ex.submit(fn).result(timeout=seconds)` does raise `concurrent.futures.TimeoutError` after ~1 second — but that raise happens *inside* the `with` block, so before the exception can propagate to `run_sandboxed`'s caller, Python must first run the context manager's `__exit__`. `ThreadPoolExecutor.__exit__` (inherited from `concurrent.futures.Executor`) unconditionally calls `self.shutdown(wait=True)` regardless of whether an exception is propagating — and `shutdown(wait=True)` blocks the calling thread until every submitted task, including the one currently stuck in an infinite loop on the sole worker thread, actually finishes. Since `while True: pass` never finishes, `shutdown(wait=True)` never returns, and the `TimeoutError` never reaches the caller — the calling thread hangs forever. A minimal reproduction (`ThreadPoolExecutor(max_workers=1)` submitting a `while True: time.sleep(0.01)` function with a 1-second timeout, wrapped in a shell `timeout 8` guard) confirms the process is still hung and gets killed by the external timeout rather than ever printing the expected `TimeoutError` message. **This means `run_sandboxed`'s `timeout_s` parameter does not actually bound execution time for genuinely infinite loops** — it works only for code that eventually returns on its own (even very slowly), because in that case the worker thread finishes and `shutdown(wait=True)` unblocks normally. This is a serious, non-obvious latent bug in the interaction between `sandbox.py` and `runtime.py`'s `with_timeout`, not something either module's docstring calls out.

## Q3: Given Q2, is `code_execution_tool()`'s advertised safety property — "runs a short Python snippet... with a timeout" — actually true for an adversarial or accidentally-buggy `code` argument?

Only partially, and in a way that's worse than "no timeout at all" in one specific sense: for code that raises, returns normally, or runs long but finite, the timeout behaves exactly as documented. For code containing a genuine infinite loop with no I/O that could be interrupted, the timeout doesn't just fail to fire — the *calling thread itself* hangs indefinitely inside `shutdown(wait=True)`, so the failure mode isn't "the tool call errors after 5 seconds," it's "the tool call, and whatever thread invoked `run_python`, never returns at all." In a synchronous request path (e.g., an HTTP handler serving `code_execution_tool()`'s `run_python` directly), this converts a single malicious/buggy tool call into a permanently stuck request/worker — a resource-exhaustion vector an operator relying on the documented "5-second timeout, safe to expose" behavior would not expect. Repeated calls each leak one more permanently-blocked OS thread (each call constructs its own fresh `ThreadPoolExecutor` via `with`, so it isn't literally one shared thread pool starving after one bad call — but each individual call that hits this bug leaks that specific request/handler thread forever), which is a real availability concern for any deployment exposing this tool to less-than-fully-trusted callers.

## Q4: `run_sandboxed`'s inner `_exec()` function builds `scope: dict[str, Any] = {"__builtins__": _SAFE_BUILTINS}` and returns `str(scope.get("result", ""))`. What happens if the submitted code never assigns to `result` at all, or assigns something huge/unserializable to it?

If `code` never sets `scope["result"]`, `.get("result", "")` quietly returns the empty string — there's no error, no signal to the caller that the code "did nothing" or didn't follow the calling convention documented in `code_execution_tool`'s own `description` field ("Assign the answer to a variable named `result`"). A model that writes syntactically valid but logically incomplete code (e.g., it computes an answer into a differently-named variable) gets back `""` with no diagnostic, which could easily be misread by the agent as "the correct answer is the empty string" rather than "the code was wrong." On the size/type side: `str(scope.get("result", ""))` will happily call `str()` on whatever object `result` was bound to — if that's a multi-gigabyte data structure, `str()` itself could be slow or memory-heavy, and there's no size cap anywhere in `run_sandboxed` on the returned string; a pathological `result` (e.g., a deeply nested or huge list) could make the `str()` conversion itself take a very long time or consume large amounts of memory, and unlike the *execution* of `code`, that `str()` call happens outside the part of `_exec` that respects `timeout_s` conceptually but is still executed on the worker thread within the same `with_timeout` call — so it's covered by the timeout race from Q2, not immune to it, but also not something a caller can control independently of the code's own execution time.

## Q5: Compare `run_sandboxed`'s isolation model to how Temporal actually isolates workflow code, or how a real "code execution" product (e.g., a Jupyter-kernel-in-a-container, or OpenAI's Code Interpreter) does it. What's categorically different, not just "less robust"?

Temporal's workflow sandboxing (and products like Code Interpreter) isolate at the OS/process/VM boundary — a separate container, microVM (Firecracker/gVisor-style), or at minimum a separate OS process with its own memory space, seccomp/cgroup limits, and no shared Python interpreter state with the host. `run_sandboxed` isolates at the *language namespace* level only: `code` executes via `exec()` in the **same process, same interpreter, same memory space** as the rest of the Agent Foundry runtime, merely with a restricted `__builtins__` dict handed to that one `exec()` call. This is a categorical difference, not a matter of degree: a namespace restriction can only ever control what *names* are directly reachable at the start of execution — it cannot prevent access to any Python object graph reachable via attribute traversal (Q1), cannot prevent CPU/memory exhaustion within the same process (a memory bomb inside `code` competes for the same process's RAM as everything else running), cannot prevent the executing thread from outliving its logical timeout (Q2), and offers zero protection if the underlying object graph happens to include anything with filesystem, network, or subprocess capability already imported elsewhere in the process. A container/VM boundary enforces isolation at a layer the guest code cannot see past regardless of what Python-level tricks it tries; a namespace restriction is enforced entirely *within* the same trust domain the code is executing in, which is why the module's own docstring recommends "Swap `run_sandboxed()` for gVisor/Firecracker/a Docker-per-call before trusting genuinely untrusted input in production" rather than claiming this is sufficient as-is.

## Q6: `_SAFE_NAMES` (line 22-24) includes `str`, `dict`, `list`, `tuple`, `type`-adjacent constructors like `int`/`float`/`bool` — none of which are individually dangerous — but doesn't include `type` itself, `getattr`, `setattr`, or `vars`. Does omitting those actually prevent introspection-based escapes, given Q1's finding?

No, and this is worth being precise about why: `getattr`/`setattr`/`vars`/`type` being absent from `_SAFE_BUILTINS` only removes the *builtin-function* forms of introspection — but Python's attribute-access syntax (`obj.attr`) is a language feature, not a call to the `getattr` builtin, so `().__class__.__base__.__subclasses__()` (Q1) needs none of those omitted names to work; it's pure dot-notation the interpreter resolves without consulting `__builtins__` at all. Even `type` being absent doesn't matter for this particular escape, since `.__class__` reaches the same information `type(x)` would. This is exactly why "an allowlist of safe builtin *functions*" is a categorically weaker security boundary than people often assume: Python's object model exposes an enormous amount of introspective power through syntax alone (attribute access, subscripting, the `__mro__`/`__subclasses__`/`__globals__` chains), none of which is gated by what's present in a `__builtins__` dict. A namespace restriction like this one is better understood as "removes the most obvious and commonly-typed escape hatches" (accidental `import os`, a stray `open('/etc/passwd')`) than as "prevents introspection" in any general sense.

## Q7: `code_execution_tool()`'s `ToolSpec` (line 47-52) doesn't set `destructive=True`. Per `contracts.py`'s `ToolSpec.destructive` field and `guardrails.py`'s `GuardrailEngine.check_action`, what does that mean for how this tool is gated under different `AutonomyLevel`s, and is `destructive=False` the right default given Q1's escape?

Because `code_execution_tool()` constructs its `ToolSpec` without passing `destructive=True`, it defaults to `destructive=False` (per `contracts.py`'s `ToolSpec` dataclass). Tracing through `GuardrailEngine.check_action` (`guardrails.py`, line 108-118): at `AutonomyLevel.L2_DRAFT`, the check `if autonomy == AutonomyLevel.L2_DRAFT and destructive` only blocks *destructive* actions — since this tool is marked non-destructive, an agent at L2 (nominally "may prepare a non-destructive action; destructive ones still blocked") is free to actually *execute* arbitrary sandboxed Python, not merely draft it, which is a meaningfully higher-trust operation than the L2 tier's stated intent suggests. Given Q1's finding that the sandbox can be escaped to enumerate and potentially invoke arbitrary in-process classes, marking this tool non-destructive is questionable: "run arbitrary code, in-process, with a demonstrated escape path" is arguably a more consequential capability than many single-purpose tools that *are* marked `destructive=True` (e.g., a scoped `delete_file` tool). Nothing in `sandbox.py` or `contracts.py` enforces any particular `destructive`/`requires_confirmation` setting for a code-execution tool — that classification is entirely up to whoever calls `code_execution_tool()`, and the reference implementation here ships with the more permissive default.

## Q8: If a malicious/compromised MCP server or tool somehow got its output fed back into `run_python`'s `code` argument (e.g., an agent plan that pipes untrusted tool output into "run this code to process it"), walk through the realistic worst case.

Say an upstream tool call (a web fetch, a document read) returns content that itself contains a crafted Python snippet, and the agent's plan — misled by a prompt-injection payload embedded in that content (exactly the OWASP LLM01 indirect-injection scenario `guardrails.py`'s `looks_like_injection`/`screen_tool_output` exist to catch, but which isn't guaranteed to be applied to every string that ends up in a tool's arguments) — passes that snippet as the `code` argument to `run_python`. `run_sandboxed` then executes it with `_SAFE_BUILTINS` and a `timeout_s` that (per Q2) doesn't reliably bound execution for a hostile payload designed to hang forever, and (per Q1) doesn't prevent the payload from walking the live object graph to find and invoke something with real capability — file access, subprocess spawning, or network I/O, depending on what's already imported in the host process. The realistic worst case is therefore not "sandbox contains it" but "sandbox slows down an unsophisticated attacker while doing little against one who knows the standard Python sandbox-escape techniques," combined with a potential thread-exhaustion DoS if the payload also hangs (Q2/Q3). This is precisely the scenario the module's own docstring flags by name: "Swap `run_sandboxed()` for gVisor/Firecracker/a Docker-per-call before trusting genuinely untrusted input in production" — the honest reading of this code is that it should never be the last line of defense between an LLM-controlled `code` string and the host process.

## Q9: What testing strategy would actually validate this sandbox's security claims, versus what's plausible to test given the module as written?

Functional correctness (does `run_sandboxed("result = 2 + 2")` return `"4"`, does a `NameError` for an unassigned `result` degrade to `""`, does `import os` raise because `__import__` is absent from `_SAFE_BUILTINS`) is straightforward to unit test and almost certainly already covered given the rest of this codebase's stated testing discipline. Security-relevant testing is harder and would need to be adversarial by design: a real test suite should include the exact subclass-traversal escape from Q1 as a *known-failing* (or explicitly-skipped-with-a-comment) test that documents the limitation rather than silently leaving it undiscovered, plus a timeout test that specifically exercises `while True: pass` with a short `timeout_s` and asserts the call actually returns within a bounded wall-clock window — which, per Q2's verified finding, it currently would NOT pass if written honestly, because the call hangs. The absence of such a test is itself notable: a test suite that only exercises well-behaved code (valid syntax, terminates, doesn't probe the object graph) would report 100% green while missing the two most security-relevant behaviors of this module entirely. This is a case where the honest engineering move is either to fix `with_timeout`'s `shutdown(wait=False)` behavior (accepting that the orphaned thread keeps running in the background rather than blocking the caller) or to explicitly document — the way the top-of-file docstring already partially does — that `timeout_s` is a best-effort hint for well-behaved code, not a hard ceiling.

## Q10: `run_sandboxed`'s docstring (line 29-30) says it executes code "with only the names in `_SAFE_BUILTINS` available (no import, no open, no exec/eval, no dunder access)." Is "no dunder access" an accurate claim given Q1?

No — this is the one claim in the module's own docstring that Q1's verified escape directly contradicts. Restricting `__builtins__` prevents calling dunder-named *builtin functions* that aren't in the allowlist (there are none of those relevant here — `__import__` is the main one, and it's excluded), but it does nothing to prevent *reading* dunder *attributes* on ordinary objects already reachable in the code (`().__class__`, `.__base__`, `.__subclasses__()`, `.__globals__` on a function object, etc.) — all of which are dunder attribute accesses, not builtin function calls, and none of which are gated by what's present or absent from `_SAFE_BUILTINS`. This is worth stating plainly rather than accepting the docstring's phrasing at face value: the claim "no dunder access" is true only in the narrow sense of "no *named builtin* whose name happens to start with dunders is present," which is a different and much weaker property than "code cannot read or use any dunder attribute," and the verified escape in Q1 demonstrates the gap concretely.

## Q11: `_exec()`'s `scope: dict[str, Any] = {"__builtins__": _SAFE_BUILTINS}` (line 33) assigns the module-level `_SAFE_BUILTINS` dict *by reference*, not a copy, into every single call's fresh `scope`. `_SAFE_BUILTINS` itself (line 25) is a plain mutable `dict`. What happens if one call to `run_sandboxed` executes `__builtins__["len"] = lambda x: 9999` — does that affect only that call, or every future call in the process?

Every future call, for the rest of the process's lifetime — and this was verified directly, not inferred. `__builtins__` inside `exec(code, scope)` is bound to the exact same dict object as the module-level `_SAFE_BUILTINS` (Python doesn't copy it; `scope["__builtins__"] = _SAFE_BUILTINS` is a reference assignment), and dictionary item assignment (`d[key] = value`) is ordinary `__setitem__` — it requires no builtin function at all, so nothing in `_SAFE_BUILTINS`'s restricted namespace prevents it. Running `_exec('__builtins__["len"] = lambda x: 9999\nresult=1')` once, then running a completely separate, later, "innocent" call `_exec('result = len([1,2,3])')`, returns `9999` instead of `3` — the second call's `len` is now permanently the attacker's function, because both calls shared the literal same `_SAFE_BUILTINS` dict object (confirmed via `id()` staying constant across calls). This is arguably the single most serious concrete finding in this module: it isn't just a sandbox escape *within* one call (Q1) or a timeout that doesn't fire (Q2) — it's a **persistent, process-wide corruption of the sandbox's own trust base** that silently poisons every subsequent invocation, across every caller, every tenant, and every session sharing that process, until the process restarts. In a multi-tenant deployment (this codebase's own `Identity.tenant_id` concept in `contracts.py` implies exactly that shape), one malicious or even accidentally-buggy `code` string from Tenant A permanently and silently corrupts the sandbox behavior seen by Tenant B's completely unrelated, later `run_python` calls. The trivial fix — `scope = {"__builtins__": dict(_SAFE_BUILTINS)}`, a shallow copy per call — is a one-line change nowhere present in the shipped code.

## Q12: Does the corruption in Q11 require the object-graph escape from Q1 to pull off, or is it independently exploitable with *only* the explicitly-allowed safe names?

It's independently exploitable and doesn't need Q1's subclass-traversal trick at all — the reproduction in Q11 uses nothing but a dict-item assignment on the `__builtins__` name, which is legal syntax available in every Python `exec` call regardless of what's in scope, and doesn't call a single function from `_SAFE_BUILTINS` or reach outside it via attribute traversal. That makes it a strictly *lower-bar* attack than Q1's escape: an attacker doesn't need to know the classic `().__class__.__base__.__subclasses__()` technique, doesn't need any introspection knowledge of CPython internals, and doesn't even need malicious intent — a buggy but well-meaning agent-generated script that happens to (for whatever reason) write to a variable literally named `__builtins__` in its own top-level scope would trigger this by accident. Because `exec(code, scope)` uses `scope` as both the globals and (implicitly) locals for top-level code, any assignment to a name matching a dict key already present in `scope` — including `__builtins__` itself — overwrites that entry in the exact same dict object every future call reuses.

## Q13: Given both Q11's shared-dict corruption and Q1's object-graph escape, how would you rank these two findings by severity for someone deciding whether to ship `code_execution_tool()` behind an internal-only flag versus exposing it to less-trusted callers?

Q11 (shared-`_SAFE_BUILTINS` corruption) is arguably the more severe finding for a multi-tenant or multi-session deployment specifically, because its blast radius extends *beyond* the call that triggered it — a single compromised or buggy invocation silently degrades the security and correctness guarantees of every other caller sharing the process, with no isolation between them and no detection mechanism (nothing in `run_sandboxed` validates that `_SAFE_BUILTINS` still matches its expected contents before or after a call). Q1 (object-graph escape) is scoped to the single call that exploits it — serious, and a genuine sandbox-boundary failure, but it doesn't persistently poison unrelated future calls the way Q11's dict mutation does. In practice both findings independently disqualify `run_sandboxed`/`code_execution_tool()` from being exposed to genuinely untrusted or cross-tenant input without the process-isolation upgrade the module's own docstring recommends (gVisor/Firecracker/Docker-per-call) — but if forced to prioritize a quick mitigation, defending against Q11 first (a one-line per-call copy of `_SAFE_BUILTINS`) removes the cross-call persistence property that turns any single successful compromise into a standing, silent backdoor for the rest of the process's life, which is a categorically worse failure mode than a single-call escape.

## Q14: How would you extend `code_execution_tool()` to be genuinely safer without switching to a full container/VM sandbox, using only what's already in this codebase (e.g., `runtime.py`'s other primitives, `security.py`'s `EgressPolicy`, `policy_engine.py`'s `PolicyDecisionPoint`)?

A few concrete, incremental improvements are possible without a rewrite: (1) fix `with_timeout` to use `shutdown(wait=False)` (or `cancel_futures=True` on Python 3.9+, though that only cancels *unstarted* futures, not one already running) so a hung worker thread doesn't block the caller — accepting that the orphaned thread keeps consuming CPU in the background is a real cost but strictly better than the caller hanging forever; (2) run `code` in a genuinely separate OS process (`multiprocessing`, not `threading`) so it can actually be `.terminate()`d on timeout and so a crash or an infinite loop doesn't share memory or GIL time with the rest of the agent process; (3) mark `code_execution_tool()`'s `ToolSpec` with `destructive=True` and/or `requires_confirmation=True` so it's gated by `PolicyDecisionPoint.decide`'s existing confirmation/autonomy checks rather than defaulting to the more permissive non-destructive path (Q7); (4) apply a resource limit via `resource.setrlimit` (on POSIX) inside the worker to bound CPU time and memory even if the timeout mechanism itself is imperfect. None of these reach container-grade isolation — the module's own honesty check is correct that a determined adversary with process-level code execution in the same interpreter is a fundamentally hard problem to solve with namespace restrictions alone — but they would close the two concretely verified gaps (Q1's object-graph escape, Q2's non-terminating timeout) that this reference implementation currently leaves open.

## Q15: `code_execution_tool()`'s `ToolSpec.parameters` is `{"code": "string"}` — a bare JSON-schema type declaration with no length limit, no pattern restriction, and no pre-execution static scan for known-dangerous substrings (`__subclasses__`, `__globals__`, `__builtins__`, `__import__`). Would adding a static pre-check for these substrings meaningfully improve safety, or is it a false sense of security given everything else in this file?

A substring blocklist on `code` before executing it (reject if `"__subclasses__"` or `"__builtins__"` appears in the text, for instance) would raise the bar against the *specific* escape techniques demonstrated in Q1 and Q11 without requiring any change to the execution model — and as defense-in-depth alongside the namespace restriction, catching the most common/well-known escape idioms by name is cheap and not unreasonable as one additional layer. But it should not be mistaken for a real fix, for exactly the reason `guardrails.py`'s literal-substring injection detection is honestly flagged as weak (see that module's own Q&A): a blocklist is trivially defeated by trivial obfuscation the interpreter itself will happily normalize — string concatenation (`"__sub" + "classes__"`), `getattr`-free but syntactically-equivalent spellings, unicode look-alikes in identifiers, or simply reaching the same subclass-graph through a different, non-blocklisted attribute chain (there are many paths to `object.__subclasses__` and beyond, not just the one literal spelling a blocklist happens to check for). Because Python's object model offers this introspective power through general-purpose syntax rather than through a small, enumerable set of named entry points, no substring or even AST-level blocklist can be exhaustive — the fundamental gap (namespace restriction doesn't cover attribute-graph traversal, Q1/Q6) remains, and a blocklist mainly raises the bar for unsophisticated or accidental triggers while doing comparatively little against a deliberate, informed attacker who knows to route around whatever specific strings are being checked for.
