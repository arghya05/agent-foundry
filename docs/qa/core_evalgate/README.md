# agent_foundry/core/evalgate.py — Q&A

This module runs a named dataset of `EvalCase`s against a real `Agent` (never mocked) and produces a `Scorecard` — task success, tool accuracy, full trajectory correctness (sequence/args/forbidden tools/call ceiling/approval), groundedness (via `KPI`), latency, and cost — with a pass/fail regression gate (`Scorecard.passes()`) that `agent_foundry/cli.py`'s `foundry eval` command calls.

## Q1: `Scorecard.passes()` *skips* a threshold when the underlying metric has no data (`if actual is None: continue`) rather than failing it. What's the risk?

`passes(thresholds)` (lines 247-274) builds a `metrics` dict of every named property, then for each threshold key the caller supplied, does `actual = metrics[key]; if actual is None: continue` — silently not evaluating that threshold at all. The only metric that can actually be `None` is `groundedness_avg` (line 231-233: `None` when no case in the run used a `kpi`). This is meant to make thresholds "opt-in per capability tested" — a dataset with no KPI-scored cases shouldn't fail a `groundedness_avg_min` gate that had nothing to measure. But the risk is real: if a CI pipeline configures `thresholds={"groundedness_avg_min": 0.8}` expecting it to gate every run, and a *typo* in a case's KPI wiring (e.g., `case.kpi` accidentally left `None`, or `kpi_context` raising and getting swallowed elsewhere) means zero cases ever actually attach a `kpi_result`, `groundedness_avg` silently returns `None` and the threshold is silently skipped — the gate reports "passing" while never having actually checked groundedness at all, with no warning printed anywhere that the threshold was skipped rather than satisfied.

## Q2: Walk through `_percentile`'s interpolation math, and compare it to `runtime.py`'s `SLATracker.p95_latency_ms`. Do they actually produce different numbers for the same data?

`_percentile(values, pct)` (lines 65-73) does `k = (len(s) - 1) * pct`, `lo, hi = floor(k), ceil(k)`, and if `lo != hi`, linearly interpolates: `s[lo] + (s[hi] - s[lo]) * (k - lo)`. `runtime.py`'s `SLATracker.p95_latency_ms()` instead does `idx = min(len(vals) - 1, int(len(vals) * 0.95)); return vals[idx]` — a truncated nearest-index lookup with no interpolation. These are genuinely different algorithms for the same conceptual metric, and they diverge concretely: for `[10, 20, 30, 40]` at p95, `_percentile` computes `k = 3 * 0.95 = 2.85`, `lo=2, hi=3`, → `30 + (40-30)*0.85 = 38.5`; `SLATracker` computes `idx = min(3, int(3.8)) = 3` → `40`. Same four latency samples, two different "p95" answers (38.5 vs. 40) depending on which subsystem computed it — an unflagged inconsistency between eval-gate reporting and fleet SLA reporting for what should be the same statistic.

## Q3: `attribute_failure()` checks failure causes in a fixed order — error, task_success, tool_accuracy, trajectory, kpi — and returns only the first. What if a case fails on both `task_success` and its `kpi` simultaneously?

Only `"task_success"` is returned — `attribute_failure` (lines 180-201) is an `if/elif`-free chain of independent `if` statements that each `return` immediately, so the *first* true condition in that fixed order wins and every later one is never even checked. The docstring explicitly ties this ordering to `run_eval`'s own boolean formula for `ok` (line 319: `task_success and tool_accuracy and not trajectory_errors and (kpi_result is None or kpi_result.passed)`) — "Checked in the same order `run_eval` itself computes `ok`." This consistency is currently correct (the two orderings do match, term for term), but it's maintained entirely by convention: nothing enforces that `attribute_failure`'s if-chain order stays in sync with `run_eval`'s boolean expression order if either is edited independently in the future — a refactor of one without the corresponding update to the other would silently misattribute failures, with no test asserting the two orderings are the same by construction.

## Q4: Trace what `trajectory_accuracy_rate` reports for a case that raises an exception mid-run but *does* declare trajectory expectations. Is there a real inconsistency here?

Yes — a genuine, concrete bug-shaped inconsistency. In `run_eval`'s `except Exception as e:` branch (lines 325-330), the constructed `CaseResult` sets `ok=False`, `task_success=False`, `tool_accuracy=False`, `kpi_result=None`, `error=str(e)` — but it never touches `trajectory_errors`, which therefore keeps its dataclass default: `field(default_factory=list)` → an **empty list**. Now look at `Scorecard.trajectory_accuracy_rate` (lines 219-228): `checked = [c for c in self.cases if _has_trajectory_expectations(c.case)]` (filtering on the *case definition*, independent of whether it errored) then `sum(1 for c in checked if not c.trajectory_errors) / len(checked)`. For an exception case with trajectory expectations declared, `c.trajectory_errors == []`, so `not c.trajectory_errors` is `True` — **this failed case is counted as a trajectory-accuracy pass**, even though the whole case crashed before ever meaningfully exercising (or failing to exercise) its expected trajectory. This means `trajectory_accuracy_rate` can read artificially high on a dataset where many cases are crashing outright — the aggregate metric looks better than reality specifically for the failure mode (an exception) that should arguably be the *most* concerning one to a trajectory-focused eval gate.

## Q5: `cost_usd` for a case comes from `agent.config.budget.cost_usd_for(context.resolved_thread_id())`. What does this depend on, and what happens if `agent.config.budget` doesn't behave as expected?

`run_eval` (line 311) calls `agent.config.budget.cost_usd_for(context.resolved_thread_id())` directly on `agent.config.budget` — meaning this line assumes `agent.config.budget` is a real, populated `RunBudgetLike` object (a real `RunBudget` from `runtime.py`, or any object satisfying that Protocol) that has already been tracking spend for exactly this run's `thread_id` by the time `agent.run()` returns. There's no `None`-check or `hasattr` guard here: if `agent.config.budget` were `None` (a theoretical misconfiguration — `AgentConfig.budget` presumably always defaults to a real `RunBudget()` in practice, but nothing in this file enforces that), the line would raise `AttributeError: 'NoneType' object has no attribute 'cost_usd_for'` — inside the `try` block, so it would actually be *caught* by `run_eval`'s own `except Exception` and reported as a per-case `"error"` via `attribute_failure`, rather than crashing the whole eval run. This is a case where the module's blanket exception handling around the entire per-case body incidentally makes an unguarded assumption safe in practice, even though the assumption itself is never explicitly validated.

## Q6: Why does each `EvalCase` get a fresh, randomly-generated `thread_id` (`f"eval-{uuid.uuid4().hex[:8]}"`) unless the case supplies its own `context`?

`run_eval` (line 306): `context = case.context or ExecutionContext(thread_id=f"eval-{uuid.uuid4().hex[:8]}")`. If every case in a dataset instead shared one `thread_id`, two real problems would follow directly from how `RunBudget` and conversation state work: first, `RunBudget.spend()`/`.step()` (`runtime.py`) accumulate *per `thread_id`*, so sharing one `thread_id` across cases would mean case #50's cost/step budget check is affected by every prior case's spend in the same run — a dataset of 50 independent test cases could start failing purely from cumulative budget exhaustion, with the *later* cases artificially penalized regardless of their own individual correctness. Second, and just as serious, conversation *history* — `messages` — is keyed by `thread_id` in `NativeEngine`/LangGraph checkpointing; sharing a `thread_id` would mean case #2's `agent.run()` call sees case #1's prior messages still in context, turning what's supposed to be N independent single-turn evaluations into one long, cross-contaminated conversation, corrupting every downstream measurement (task_success substring matching against a reply influenced by prior unrelated cases, tool-call detection picking up tool calls from earlier cases' turns, etc.).

## Q7: `_check_trajectory`'s `expected_args` check only verifies the *listed* keys match — what does that under-catch?

For a tool named in `case.expected_args`, the check is `mismatched = {k: (v, actual_args.get(k)) for k, v in expected_args.items() if actual_args.get(k) != v}` (line 123) — this only iterates over the keys present in the *expected* dict, checking that each one matches the actual call's value for that key. It never inspects whether `actual_args` contains *additional* keys the expectation didn't mention at all. Concretely: if `case.expected_args = {"transfer_funds": {"amount": 100}}` and the agent actually calls `transfer_funds(amount=100, recipient="attacker@evil.com")`, this check passes cleanly — `amount` matches, and the unexpected `recipient` argument is invisible to this check entirely, since it only ever asks "do the keys I listed match," never "were there other, unlisted keys I should have flagged." For a trajectory check whose entire purpose is catching agents doing something subtly wrong, this is a meaningful gap: an eval case author has to enumerate *every* argument they care about, including ones they'd want to affirmatively assert are *absent* or unexpected, and there's no `forbidden_args` or "exact match, no extras" mode available today.

## Q8: `must_request_approval` is checked against `result.awaiting_approval` from a single `agent.run()` call. Does `run_eval` ever call `agent.resume()` to test what happens *after* approval is granted?

No — `run_eval` (lines 303-331) calls `agent.run(case.input, context=context)` exactly once per case, and never calls `.resume(...)` anywhere in this module. This means `must_request_approval=True` can verify "did the agent correctly pause and ask for approval," but the eval harness has **no mechanism at all** to then simulate approving that request and scoring what the agent does next (does it correctly proceed with the approved tool call? does it correctly abort on rejection? does the final answer after resume make sense?). Any genuinely multi-turn HITL trajectory — request approval → grant it → continue — is entirely outside what `evalgate.py` can measure today; the module can only ever assert the *first* interrupt boundary was reached correctly, never anything about the agent's behavior beyond it. This is a real, honest gap in eval coverage for exactly the kind of approval-gated tool call this framework's `AutonomyLevel`/`requires_approval` policy machinery is built around.

## Q9: `Scorecard.compare_to(baseline)` returns raw deltas with the docstring noting "positive is better for X, negative is better for Y." Is that sign ambiguity resolved programmatically anywhere?

No — `compare_to()` (lines 276-285) computes `deltas[attr] = getattr(self, attr) - getattr(baseline, attr)` uniformly across `task_success_rate`, `tool_accuracy_rate`, `trajectory_accuracy_rate`, `p95_latency_ms`, `avg_cost_usd`, `error_rate` (plus `groundedness_avg` when both scorecards have it), with zero normalization of sign or any accompanying "improved: bool" verdict. A caller consuming this dict — say, a CI script deciding whether to flag a regression — has to hardcode, entirely on its own, which direction is "bad" per metric (a positive `p95_latency_ms` delta or `error_rate` delta is a regression; a positive `task_success_rate` delta is an improvement) — `compare_to()` itself provides no such classification. This is a real usability gap compared to `passes()`, which *does* give a clean, self-contained `(bool, list[str])` verdict — `compare_to()` gives raw numbers a caller must independently know how to interpret correctly for each metric, with no help from the API.

## Q10: Why does `ScorecardLike` exist as a `Protocol` rather than `compare_to` simply being typed to take another `Scorecard`?

The docstring for `ScorecardLike` (lines 30-52) names the exact motivating use case: `eval_dataset.BaselineScorecard` — "a saved run's metrics reloaded from disk, with no `.cases` to reconstruct a full `Scorecard` from." A genuine `Scorecard` is built from a live list of `CaseResult` objects (`cases: list[CaseResult]`), each of which embeds the full `EvalCase`, the `RunResult`, per-case latency/cost, etc. — far more data than you'd want to serialize and reload just to compare a *baseline's aggregate numbers* against a fresh run. `ScorecardLike` narrows the contract down to exactly the seven read-only properties `compare_to()` actually touches (`task_success_rate`, `tool_accuracy_rate`, `trajectory_accuracy_rate`, `groundedness_avg`, `p95_latency_ms`, `avg_cost_usd`, `error_rate`) — so a lightweight `BaselineScorecard` that merely stores those seven numbers (loaded from a saved JSON/file) and exposes them as properties satisfies `ScorecardLike` structurally, with no inheritance from `Scorecard` and no need to fake up a `cases` list it doesn't have, purely because Python's structural typing accepts any object with matching attributes/properties.

## Q11: `tool_accuracy_rate` and `trajectory_accuracy_rate` both default to `1.0` (not `0.0`, not `None`) when zero cases in the dataset declare that expectation. Why, and what's the risk?

`tool_accuracy_rate` (lines 214-217): `checked = [c for c in self.cases if c.case.expected_tool is not None]; return ... if checked else 1.0`. `trajectory_accuracy_rate` (lines 219-228) follows the identical pattern, and its own docstring says so explicitly: "1.0 (not skipped) when no case declared one, matching `tool_accuracy_rate`'s own convention." The reasoning is "vacuous truth" — if nothing was asked, nothing was violated, so the rate is reported as perfect rather than undefined. The risk mirrors Q1 exactly but for a *rate*, not a threshold: a dataset where every `EvalCase` only sets `expected_substring` and never `expected_tool` or any trajectory field would report `tool_accuracy_rate: 100%` and `trajectory_accuracy_rate: 100%` in `Scorecard.render()` — numbers that look like meaningful, high-confidence signals of correct tool usage, when in reality zero cases ever tested tool usage at all. A reviewer skimming a scorecard showing "100% tool accuracy, 100% trajectory accuracy" could easily mistake vacuous coverage for verified coverage, since the render output gives no visual distinction between "we checked, and it was perfect" and "we never checked."

## Q12: Walk through `_check_trajectory` for a case with `expected_tool_sequence=["search", "checkout"]` where the agent actually calls `["search", "cart_add", "checkout"]`.

`names_in_order = [name for name, _args in calls]` would be `["search", "cart_add", "checkout"]`. The check (line 115): `if case.expected_tool_sequence is not None and names_in_order != list(case.expected_tool_sequence):` — this is a strict **list equality** check, not a subsequence check, so `["search", "cart_add", "checkout"] != ["search", "checkout"]` is `True`, and the case records the violation `f"expected tool sequence ['search', 'checkout'], got ['search', 'cart_add', 'checkout']"`. This fails the trajectory check even though the agent's actual behavior may have been entirely reasonable — it called `search`, then a legitimate intermediate step (`cart_add`), then `checkout`, in the right relative order, just with one extra (arguably correct) tool call the expectation didn't anticipate. There is no way today to express "these tools must appear in this relative order, but other calls in between are fine" — `expected_tool_sequence` only supports exact, complete-sequence matching, which makes it brittle for any agent behavior that's correct but not maximally minimal in its tool usage.

## Q13: Why does `_get_all_tool_calls` get imported from `orchestration.py` rather than reimplemented here, and what's the tradeoff?

The module docstring states this directly: "`orchestration._get_all_tool_calls` for real tool-call detection (same reused-not-reimplemented reasoning as `native_engine.py`)." The benefit is a single source of truth: however tool calls are actually represented inside a message dict (whatever shape `orchestration.py`'s own message-building code produces) is decided in exactly one place, and `evalgate.py`'s `_called_tool_names`/`_tool_calls_in_order` (lines 76-93) both build directly on top of it rather than re-deriving that parsing logic independently — if `orchestration.py` ever changed how tool calls are embedded in a message, `evalgate.py` would automatically stay correct with zero changes needed. The tradeoff is tight coupling: `evalgate.py` has no independent verification of message shape and would break (loudly, via whatever exception `_get_all_tool_calls` raises on an unexpected shape) if that function's contract ever changed incompatibly — there's no adapter or version-check layer between the two modules, just a direct import and call.

## Q14: `Scorecard.render()` conditionally omits the "Trajectory accuracy" line (only shown `if any(_has_trajectory_expectations(c.case) for c in self.cases)`) but *unconditionally* shows "Task success," while "Error rate" is shown only `if self.error_rate` (i.e., only when nonzero). Is this inconsistent?

Yes, in a way worth noticing: `render()` (lines 287-300) treats "no data for this metric" (trajectory accuracy, groundedness) and "zero value for this metric" (error rate) with two *different* display conventions, both under the umbrella of "don't clutter the output." Trajectory accuracy is hidden when *no case declared an expectation* (a genuine "not applicable" case) — reasonable, since showing a vacuous 100% (Q11) unlabeled would be actively misleading. But error rate is hidden specifically `if self.error_rate:` (truthy, i.e., nonzero) — meaning a run with a *literal, computed* 0% error rate (every case ran without an exception) shows no "Error rate" line at all, which is different from "we never tracked errors" — error tracking is *always* active (every case either errors or doesn't; there's no "not applicable" state the way trajectory checks have). Hiding a genuinely-computed 0% behind the same "omit if not interesting" convention used for genuinely-inapplicable metrics could read to a report viewer as "errors weren't measured" rather than "errors were measured, and there were none" — a minor but real ambiguity in what an absent line means.

## Q15: The module docstring insists "nothing here is a mock scorer... every metric is measured from a real `Agent.run()` call." What does that cost in testing, and how would you test the pure-math parts in isolation?

Every `run_eval()` call genuinely invokes a real `Agent`, which in turn genuinely calls out to whatever LLM provider/tools that agent is configured with — meaning any test exercising `run_eval()` end-to-end is inherently slow, potentially non-deterministic (LLM outputs vary), and costs real API spend unless the `Agent` under test is deliberately wired to a stub/fake `Provider` for testing purposes (a reasonable and common pattern, but one that has to be set up explicitly by the test, not something `evalgate.py` provides). The module's own pure-math logic, though, is fully separable from that cost: `_percentile`, `_check_trajectory`, `_has_trajectory_expectations`, `attribute_failure`, and every `Scorecard` property (`task_success_rate`, `tool_accuracy_rate`, `passes()`, `compare_to()`, `render()`) operate purely on already-constructed `CaseResult`/`EvalCase`/`RunResult` data — they can be tested directly by hand-constructing `CaseResult` objects (no `Agent`, no LLM call, no `run_eval()` involved at all) and asserting the computed rates/thresholds/render strings, exactly the kind of test that would have caught the Q4 (`trajectory_accuracy_rate` on exception cases) and Q9 (`str(bool)`-style, sign-ambiguity) issues immediately, cheaply, and deterministically.

## Q16: Given more time, what's the single most valuable fix to this module?

The `trajectory_accuracy_rate`/exception-case inconsistency from Q4 is the most concrete, currently-real correctness bug: a dataset with crashing cases can report a *better*-looking trajectory-accuracy number than a dataset with the same cases succeeding but occasionally missing a trajectory expectation, purely because `run_eval`'s exception branch leaves `trajectory_errors` at its empty-list default rather than explicitly marking trajectory as "not evaluated due to error." The fix is small and precise: in `run_eval`'s `except Exception` branch, either set `trajectory_errors=["run raised an exception before trajectory could be evaluated"]` (so exception cases with declared trajectory expectations are correctly counted as trajectory failures) or exclude exception cases from `trajectory_accuracy_rate`'s `checked` list entirely (treating them as "not applicable" rather than "vacuously passing") — either is a one-line change that would make this widely-used regression gate materially more trustworthy on the exact failure mode (agent crashes) it should be most sensitive to.
