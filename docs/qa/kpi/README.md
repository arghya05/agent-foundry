# agent_foundry/kpi.py — Q&A

The general pluggable-metric mechanism (`KPI`/`KPIBoard`) that guardrails, eval, and planning compose with from the outside rather than inheriting from — plus a large reference catalogue of concrete KPI factory functions (efficiency, conciseness, groundedness, cost, hallucination rate, LLM-judge, schema validity, fact-checking, composite grounding, retrieval F1, citation correctness, judge calibration, pairwise comparison) that a builder can register on a `KPIBoard` and combine into one weighted objective score.

## Q1: The module docstring says "nothing here imports from the rest of `agent_foundry`; guardrails.py, eval.py and orchestration.py compose with it from the outside, by choice, not by inheritance." Why does that specific dependency direction matter architecturally?

If `kpi.py` imported from `guardrails.py`/`eval.py`/`orchestration.py`, you'd get an import cycle risk the moment any of those modules also needed something from `kpi.py` (which they do — `guardrails.py` and `eval.py`/`orchestration.py` are exactly the consumers named). Keeping `kpi.py` at the bottom of the dependency graph (importing only `re`, dataclasses, and stdlib `typing`, plus `jsonschema` lazily inside `schema_valid_kpi`) means it can be tested, reasoned about, and reused in complete isolation — a `KPI` is just a name, a `Callable[[dict], float]`, a direction, and a threshold; it has no idea an "agent," a "guardrail," or an "orchestration graph" even exist. This is also what makes `KPI` usable in contexts this codebase's authors probably didn't originally anticipate — anywhere a caller can produce a `dict[str, Any]` context and wants a pass/fail plus a weighted score, not just inside this specific agent framework. "Composes with it from the outside" concretely means: `guardrails.py`/`eval.py`/`orchestration.py` import `KPI`/`KPIBoard` and *call* them, but `kpi.py` never imports anything that would create a cycle back — a one-directional dependency edge, by deliberate choice.

## Q2: Walk through exactly what `KPI.evaluate(context)` does for a `direction="target"` KPI like `conciseness_kpi()`, given `ctx={"output_text": "a" * 350}`.

`conciseness_kpi(target_chars=400, tolerance=200)` (lines 121-124) constructs a `KPI` whose `score` function is `lambda ctx: float(len(ctx.get("output_text", "")))` — note the KPI's own `score` callable ignores `target_chars`/`tolerance` entirely; those two only get threaded into the `KPI` object's `target=target_chars, threshold=tolerance` fields, not into the scoring function itself. Calling `.evaluate(ctx)` on the constructed `KPI` (in the base `KPI.evaluate`, lines 70-79) first computes `value = self.score(context)` → `350.0` (the raw character count, not yet compared to anything). Since `self.direction == "target"` and both `self.target` (`400`) and `self.threshold` (`200`) are set, it computes `passed = abs(value - self.target) <= self.threshold` → `abs(350 - 400) = 50 <= 200` → `True`. It returns `KPIResult(name="conciseness", value=350.0, passed=True)`. The key subtlety: `KPIResult.value` is the *raw* character count (350.0), not a normalized 0-1 score — this matters a lot for `KPIBoard.weighted_score()` (Q5 below), since a raw value like `350.0` blended arithmetically with other KPIs' 0-1-scaled values would dominate any weighted average nonsensically.

## Q3: That answer surfaces something real: `conciseness_kpi`'s `value` is a raw character count (e.g. `350.0`), while most other KPIs in the catalogue (`efficiency_kpi`, `groundedness_kpi`, `task_success_kpi`) return values already normalized to `[0, 1]`. What actually breaks if `conciseness_kpi` and `efficiency_kpi` are both registered on the same `KPIBoard` and someone calls `weighted_score()`?

`KPIBoard.weighted_score()` (lines 101-105) computes `sum(r.value * self.kpis[r.name].weight for r in results) / total_weight` — a straight weighted average of every registered KPI's raw `.value`. If `conciseness_kpi` reports `350.0` and `efficiency_kpi` reports something in `[0, 1]` (say `0.6`), both with `weight=1.0`, the composite score is `(350.0*1.0 + 0.6*1.0) / 2.0 ≈ 175.3` — a number with no coherent meaning, dominated entirely by the unnormalized character count regardless of how the efficiency KPI actually scored. This is a genuine, unaddressed design gap in the catalogue: `direction="target"` KPIs like `conciseness_kpi` compute `passed` correctly (comparing raw value to target±tolerance, per Q2) but were never designed to also participate meaningfully in a *weighted composite score* alongside `[0,1]`-scaled KPIs — `KPIBoard.weighted_score()` has no normalization step and no awareness that different KPIs report values on wildly different scales. A builder combining KPIs for a single objective needs to be aware of this and either avoid mixing raw-scale and normalized-scale KPIs on the same board's `weighted_score()`, or write their own conciseness-style KPI that normalizes its own `score()` output to `[0,1]` (e.g. `1.0 - abs(len(text) - target) / tolerance`, clamped) if it needs to participate in a composite average correctly.

## Q4: Why does `_tokenize()` use a regex (`[a-z0-9]+`) instead of `.split()`, and what specific real-world failure did this fix (per the docstring)?

`.split()` treats `"500mg"` (something an agent's reply might say verbatim) and `"500 mg"` (how the same fact might appear in a retrieved source document, with a space) as entirely non-matching tokens — plain whitespace splitting has no concept of separating a number from an attached unit, and it also treats `"daily."` (trailing punctuation from a sentence) as a different token from `"daily"` in another context, purely due to punctuation, not any real semantic difference. The docstring (lines 20-29) states this was "found live" — wiring `reference_check_kpi`'s exact word-overlap math into a real blocking guardrail gate (a healthcare/backend critique step) and testing it against a genuine ChromaDB-retrieved passage, not hand-written test fixtures — surfaced false negatives on genuinely correct, well-grounded answers, specifically because the naive tokenization couldn't see that "500mg" and "500 mg" were the same fact. `_WORD_RE = re.compile(r"[a-z0-9]+")` (line 16) fixes this by extracting maximal runs of lowercase letters/digits after lowercasing the whole text, so `"500mg"` tokenizes to `{"500", "mg"}` and `"500 mg"` also tokenizes to `{"500", "mg"}` — now genuinely comparable — and `"daily."` tokenizes to `{"daily"}`, identical to `"daily"` elsewhere. This is a small function with an unusually well-documented, real production incident behind its specific design, which is worth knowing precisely because it demonstrates the KPI catalogue wasn't purely designed on paper — this edge case was caught against live data.

## Q5: `word_overlap(text, passages)` computes `len(text_words & ref_words) / max(len(text_words), 1)` — fraction of the *output's own words* found in the passages. Why that direction, rather than the fraction of *passage* words the output covers (which would be closer to a recall metric)?

The metric is deliberately precision-shaped, not recall-shaped: it asks "of everything the model actually said, how much of it can be traced back to the source material" — which is exactly the question a groundedness/hallucination check needs to answer (an ungrounded, hallucinated claim is a *word the model said that isn't supported*, not a source fact the model failed to mention). A recall-shaped version (`len(overlap) / len(ref_words)`) would instead measure "how much of the source did the answer cover," which is a completeness question, not a groundedness one — and is in fact a *different*, already-existing KPI in this same file: `completeness_kpi()` (lines 133-155) explicitly measures whether required elements are covered, using a totally separate mechanism (`required` checklist matching or an LLM judge). Conflating the two would produce a metric that penalizes both hallucination (bad — should count against grounding) and simply being concise (not necessarily bad — an answer needn't restate every word of a long passage to be well-grounded), which is exactly the kind of confound `word_overlap`'s specific directionality avoids.

## Q6: Walk through what `composite_grounding_kpi`'s `score()` function actually does for an output with no numeric claims at all, and explain why `fact`'s weight is *excluded* rather than blended in at a default value in that case.

For an output like `"The medication should be taken with food."` (no digits, no matched unit patterns), `_NUMERIC_CLAIM_RE.search(text)` (the regex from line 268-271, matching digit+unit patterns like `mg`/`ml`/`%`/`hours` etc.) returns `None`, so the `if _NUMERIC_CLAIM_RE.search(text): parts.append((_fact.score(ctx), weight_fact))` branch (line 356-357) never executes — `_fact`'s score is never even computed, and its weight never enters `parts` at all. `parts` then contains only `(_reference.score(ctx), weight_reference)` (always included) and, if a judge was given, `(judge(...), weight_judge)`. The final `score()` normalizes by `total = sum(w for _, w in parts) or 1.0` — so with only reference (and optionally judge) contributing, the composite becomes a weighted average over *just those*, correctly re-normalized, rather than blending in `fact_check_kpi`'s own `1.0` "nothing to get wrong" auto-pass at its full nominal weight. The docstring (lines 332-347) explains exactly why this distinction matters with a real anecdote: naively blending `fact`'s auto-pass `1.0` in at 40% weight would have pulled a composite score for "completely unrelated text sharing no words with the uploaded prescription whatsoever" up from `reference`'s correct near-`0.0` to roughly `0.5` — high enough to sail past a real escalation gate's `escalate_threshold`, exactly defeating the purpose `reference_check_kpi` exists to serve (catching wholesale-hallucinated, unrelated answers). *Excluding* fact's weight (not scoring it as 0, and not blending its 1.0 in) when there's nothing for it to check keeps the composite's actual sensitivity to hallucination exactly where `reference` alone already correctly had it.

## Q7: How is `fact_check_kpi`'s numeric-claim verification meaningfully stricter than `reference_check_kpi`'s bag-of-words overlap, and what specific failure mode does that difference exist to catch?

`reference_check_kpi` (lines 256-265) uses `word_overlap`, which tokenizes both the output and the reference passages into sets and computes fractional set intersection — this is fundamentally a bag-of-words comparison with no notion of *which specific token appears near which other token*, so it treats `"take 500mg twice daily"` and a source saying `"take 50mg twice daily"` as sharing almost every token (`{"take", "twice", "daily"}`, missing only the differing number/unit pairing since `"500mg"`/`"50mg"` tokenize differently), producing a *high* overlap score despite the number being wrong by 10x — a potentially dangerous dosage hallucination that a fuzzy bag-of-words metric structurally cannot catch, because nearly all of the surrounding sentence still matches. `fact_check_kpi` (lines 278-299) fixes exactly this: it extracts every explicit numeric claim from the output via `_NUMERIC_CLAIM_RE` (dosages, frequencies, durations — units like `mg`/`ml`/`%`/`bpm`/`hours`/`tablets`) and checks each one appears **verbatim** (whitespace-insensitive, via `_normalize_claim`) somewhere in the reference text — `"500mg"` verbatim-checked against a source containing only `"50mg"` fails outright, `supported/len(claims)` scoring it as unsupported, exactly the case `word_overlap`'s token-set math would score as well-grounded. The docstring names this precisely: "a wrong number... is exactly the error class `word_overlap`'s bag-of-words math can't catch."

## Q8: `completeness_kpi` requires *exactly one* of `judge` or `required`, enforced by `if (judge is None) == (required is None): raise ValueError(...)`. Walk through why both being `None` and both being provided are treated as equally invalid, and what happens with `judge=None, required=None`.

The XOR-style check (line 141) is `True` (raising) in exactly two cases: both `None` (`None is None) == (None is None)` → `True == True` → `True`) — the caller gave no way to score completeness at all, which should fail loudly rather than silently produce a KPI whose `score()` function would crash the first time it's called with `judge=None, required=None`'s branch logic (`if judge is not None: ...` falls through, then `assert required is not None` — the assertion the comment explicitly notes is "checked above" — would fire, but only lazily, at scoring time, on whatever thread happens to run the first eval case, rather than immediately at KPI-construction time where the mistake was actually made). And both given non-`None` — an ambiguous config where the caller specified two different, potentially conflicting scoring methods with no rule for which one wins. By raising `ValueError` eagerly, at `completeness_kpi()` call time (i.e. when a builder is *wiring up* their KPIBoard, likely during startup/config), the mistake surfaces immediately with a clear message rather than only when the first eval case actually runs — a good example of fail-fast validation applied specifically because the alternative (a lazy `AssertionError` deep inside a `score()` closure, potentially during a live eval run) would be a much worse debugging experience.

## Q9: `schema_valid_kpi` and `db_match_kpi` are both described as fully "deterministic" methods, contrasted implicitly with `llm_judge_kpi`. What's the actual reliability/cost tradeoff between deterministic and LLM-judge KPIs, and is "deterministic" a synonym for "more correct" here?

Deterministic KPIs (`schema_valid_kpi`, `db_match_kpi`, `reference_check_kpi`, `fact_check_kpi`) are cheap (no LLM call, no latency, no added cost, no non-determinism from sampling), reproducible (the exact same input always produces the exact same score, useful for CI regression gating where flaky scores would be intolerable), and precisely scoped to whatever narrow question they're built to answer — `schema_valid_kpi` (lines 222-238) only knows whether `ctx["output_text"]` parses as JSON and validates against a given JSON Schema; it has zero opinion on whether the *content* is actually correct, sensible, or well-written, only that its *shape* conforms. `db_match_kpi` (lines 241-253) is even narrower: exact equality between a claimed value and an actual database value, with zero tolerance for near-misses or paraphrasing. "Deterministic" is not a synonym for "more correct" in any general sense — it's a synonym for "correct at exactly the narrow, mechanically-checkable thing it measures, and nothing else." `llm_judge_kpi` (lines 200-219) trades that narrowness and cost-freeness for the ability to judge genuinely semantic properties (tone, faithfulness to nuance, whether an answer is "good" in ways no schema or exact-match check could capture) — at the cost of a real LLM call (latency, $, and LLM sampling non-determinism unless the judge itself is made deterministic via temperature=0 or similar, which is the judge implementation's responsibility, not this module's). `composite_grounding_kpi`'s entire design (Q6) exists because the two approaches genuinely catch different failure classes and neither alone is sufficient — the deterministic checks are free/fast but catch only mechanically-detectable errors, while the judge catches semantic errors ("right numbers, wrong drug entirely," per its own docstring) that no deterministic regex or bag-of-words check ever could.

## Q10: `pairwise_comparison_kpi` reads `ctx["output_a"]`/`ctx["output_b"]` instead of the usual `ctx["output_text"]` convention every other KPI in this file follows. Why does it break that convention, and what would happen if it didn't?

Every other KPI in the catalogue scores exactly one candidate output against a threshold or target — `ctx["output_text"]` is a sufficient, unambiguous input for that. `pairwise_comparison_kpi` (lines 450-467) is fundamentally different: it exists specifically to compare *two* candidates against each other (two prompt variants, a release candidate vs. a previous saved output, two different models) — there is no single "the output" to put in `ctx["output_text"]`, because the entire point is there are two competing outputs and the KPI needs both simultaneously to make a relative judgment (`judge(output_a, output_b)` returning who wins). If it tried to force this into the `output_text` convention, you'd need either two separate `KPI.evaluate()` calls (one per candidate) that somehow communicate with each other to produce a *relative* judgment — architecturally awkward, since `KPI.score` is a pure `dict -> float` function with no notion of "the other candidate" — or some hacky serialization of both outputs into a single string field, which the docstring's convention explicitly avoids by just using two dedicated context keys instead. The default `threshold=0.5` reflects the chosen semantics too: `output_a` is "the side being judged, by convention" (a release candidate against a baseline `output_b`), so `passed` at the default threshold answers "did the candidate at least tie the baseline," a natural bar for "is it safe to ship this candidate" — a stricter threshold would instead require the candidate to outright win, not just hold its own.

## Q11: `judge_calibration_kpi` measures something different from every other KPI in the file — walk through exactly what it's actually evaluating and why that's a distinct concern from correctness.

Every other judge-based KPI (`llm_judge_kpi`, `completeness_kpi`'s judge path, `composite_grounding_kpi`'s judge component) uses an LLM judge to evaluate the *agent's output*. `judge_calibration_kpi` (lines 433-447) instead evaluates the *judge itself* — `score(ctx) = 1.0 - abs(judge(ctx.get("output_text", "")) - labeled(ctx))`, where `labeled(ctx)` returns a known-correct human-assigned score for that eval case. The resulting value measures how closely the judge's automated score tracks a trusted human label, not whether the underlying output was good — a judge that consistently scores everything `0.9` regardless of actual quality could still happen to get a high `judge_calibration_kpi` score on a dataset where most human labels also cluster near `0.9`, while being a genuinely bad judge for distinguishing quality on cases where labels vary. This is a meta-evaluation concern: before trusting `llm_judge_kpi` (or any judge-based KPI) as a substitute for human review at scale, you'd run `judge_calibration_kpi` against a labeled validation set to establish that the judge is actually trustworthy — exactly the kind of "who evaluates the evaluator" step that's easy to skip and dangerous to skip, since an uncalibrated judge silently propagates its own biases into every downstream KPI that relies on it (`llm_judge_kpi`, `completeness_kpi`, `composite_grounding_kpi`'s judge weight) with no signal that anything is wrong.

## Q12: `retrieval_recall_precision_kpi` returns the harmonic mean (F1) of precision and recall, with explicit special-casing: `1.0` when both retrieved and relevant sets are empty, `0.0` when exactly one is empty. Why is the "both empty" case scored as a perfect pass rather than, say, undefined/skipped?

"Nothing was relevant, and nothing was retrieved" (line 396-397) is a case where the retrieval system did exactly the right thing — there was nothing to find, and it correctly found nothing — so scoring it `1.0` ("vacuously correct," per the docstring at line 390) rewards the system for not hallucinating irrelevant results when none exist, rather than penalizing it or treating the case as unscoreable. This mirrors standard information-retrieval convention (precision/recall are conventionally defined as 1 for the trivial all-empty case in many IR evaluation frameworks) and avoids a `0/0` division that would otherwise need special-casing anyway — the alternative, silently excluding these cases from the metric's denominator entirely, would mean a dataset with many "no relevant docs exist" cases (a common and important scenario — testing that a RAG system doesn't fabricate sources for queries with no good answer) contributes zero signal about that important behavior. The `0.0` case (line 398, exactly one side empty) is the genuinely bad outcome — either relevant docs existed and nothing was retrieved (pure recall failure) or things were retrieved when nothing was relevant (pure precision failure, likely a hallucinated-source scenario) — and correctly scores as a hard failure rather than getting averaged into something misleadingly moderate.

## Q13: `citation_correctness_kpi` and `fact_check_kpi`/`reference_check_kpi` all deal with "is the output trustworthy," but they check genuinely different things. What specific failure mode does `citation_correctness_kpi` catch that grounding checks miss entirely?

The docstring is explicit (lines 411-416): an answer can be "fully grounded in its retrieved passages" — every claim it makes is well-supported by real source content, passing both `reference_check_kpi` and `fact_check_kpi` cleanly — while still citing `"[3]"` when only two sources were actually retrieved (a nonexistent citation), or citing a *real* source's content but attributing it to the *wrong* id. Grounding checks (`word_overlap`, verbatim numeric matching) only ever look at whether the output's *prose* is supported by *some* passage somewhere in the reference set — they have no concept of citation markers at all, and would score a perfectly-grounded-but-mis-cited answer as fully grounded, missing the citation error entirely. `citation_correctness_kpi` (lines 408-430) is the only KPI in the catalogue that specifically extracts citation markers from the output text (via a caller-supplied `citations(text)` extractor) and checks each one against the actual set of `sources(ctx)` ids that were genuinely available for that case — a completely orthogonal failure mode (attribution correctness) from content grounding (factual correctness), and one that matters a great deal for any system that presents citations to end users as a trust signal, since a wrong citation actively misleads a user checking the source, even when the underlying claim itself was true and well-supported.

## Q14: `KPIBoard.weighted_score()` divides by `total_weight = sum(...) or 1.0`. What edge case does the `or 1.0` guard against, and is `1.0` the right fallback?

If `self.kpis` is empty (no KPIs registered) or every registered KPI has `weight=0.0` (a KPI a builder wants included for reporting/`failing()` purposes but explicitly excluded from the composite score), `total_weight` would compute to `0` — dividing by that would raise `ZeroDivisionError`. The `or 1.0` fallback avoids the crash, but note: with zero KPIs, `results` is also empty, so the numerator `sum(r.value * ... for r in results)` is also `0`, and `0 / 1.0 = 0.0` — a defensible "no KPIs, no score" result. With all-zero-weight KPIs, the numerator is `sum(r.value * 0.0 for r in results) = 0.0` regardless of the actual scores, so the fallback again yields `0.0` — also defensible (weight-zero KPIs contribute nothing, and there's nothing else to normalize against). So `1.0` as the fallback divisor is really just "avoid dividing by zero when the numerator is also guaranteed zero" — the specific fallback value doesn't actually matter for correctness here since it's only ever reached when the numerator is already `0`, but it's a slightly fragile pattern (relying on the numerator-is-also-zero invariant rather than explicitly special-casing "no contributing KPIs" and returning `0.0` directly) that would need re-auditing if `weighted_score()`'s numerator formula ever changed.

## Q15: `KPIBoard.failing(context)` calls `self.evaluate_all(context)`, which itself calls `kpi.evaluate(context)` for every registered KPI. If one KPI's `score` function raises an exception (say, `reference_check_kpi`'s `references(ctx)` callable does a network call to fetch documents and it times out), what happens to `failing()` and every other KPI on the board?

There's no `try`/`except` anywhere in `KPIBoard.evaluate_all()` (lines 95-96, a bare list comprehension calling `kpi.evaluate(context)` for each) or in the base `KPI.evaluate()` itself — an exception from any single KPI's `score` callable propagates immediately out of the list comprehension, aborting the entire `evaluate_all()` call before any subsequent KPI in the dict gets evaluated at all. This means one flaky or slow KPI (a network-dependent `references()` callable timing out, an LLM judge call failing) takes down the *entire board's* evaluation for that context — `failing()`, `weighted_score()`, and any caller of `evaluate_all()` all inherit this fragility, since none of them defensively wrap individual KPI evaluations. For a `KPIBoard` used as a live blocking gate (per the composite-grounding docstring's own example of wiring this into "a real blocking escalation gate"), this is a real production risk: a single external dependency failure in one KPI's scoring function can block an entire turn's critique step from completing at all, rather than degrading gracefully (e.g. treating that one KPI as failed/unavailable and continuing with the rest). Nothing in `kpi.py` addresses this — it would need to be handled by whatever caller wraps `KPIBoard.evaluate_all()`.

## Q16: How is this KPI framework methodologically different from a standard ML evaluation library's metric suite (say, scikit-learn's `metrics` module or HuggingFace `evaluate`)?

Standard ML metric libraries are almost entirely deterministic, single-purpose functions operating on complete, already-collected prediction/label arrays after the fact (accuracy, F1, BLEU, ROUGE) — they don't have a notion of "pass/fail against a target," "weight in a composite objective," or being invoked live, per-turn, as a gating mechanism inside a running system. `kpi.py`'s `KPI`/`KPIBoard` design is built for exactly that latter use case: `KPI.evaluate()` takes a single case's context dict and returns pass/fail plus a value *live*, meant to be called inline during or right after a single agent turn (as `composite_grounding_kpi`'s "wired into a live blocking escalation gate" anecdote demonstrates), not batch-computed over a large offline dataset after the fact. The `direction`/`threshold`/`target` machinery and `weight`-based composite scoring exist specifically to support decision-making (should this turn be blocked, escalated, or allowed) rather than pure measurement/reporting — a genuinely different design goal from a metrics library whose job stops at "here's the number." That said, the actual math behind several KPIs here (word-overlap F1-style scoring, precision/recall F1) is standard and would be recognizable to anyone who's used scikit-learn's metrics — the novelty is in the composable, live-gating framework around those metrics, not in inventing new statistical measures.

## Q17: What's the actual statistical/methodological rigor behind this catalogue as a whole — is it production-grade evaluation, or a reasonable approximation?

It's a well-engineered, honestly-scoped approximation, not a rigorous statistical evaluation framework, and the module is fairly self-aware about this even without saying so explicitly. The strengths: several KPIs (`fact_check_kpi`, `word_overlap`/`_tokenize`) were demonstrably hardened against real production failure modes (Q4's documented live incident), the composite-weighting logic (`composite_grounding_kpi`) shows genuine methodological care about *how* to combine signals without one masking another (Q6), and the catalogue covers a wide, sensible range of failure modes (grounding, citation correctness, retrieval quality, judge calibration) that a naive "just use an LLM judge for everything" approach would miss. The weaknesses: there's no confidence interval or variance reporting anywhere (every KPI returns a single point value), `KPIBoard.weighted_score()` naively averages raw values with no normalization guard (Q3), individual KPI evaluation has no fault isolation (Q15), and none of the thresholds baked into the factory functions (`threshold=0.3` for `reference_check_kpi`, `max_rate=0.05` for `hallucination_rate_kpi`, etc.) are derived from any statistical calibration process visible in this file — they're reasonable-sounding defaults a builder is expected to tune for their own domain, not empirically validated cutoffs. This is exactly the right level of engineering for a flexible, extensible framework a team customizes per use case, but it would be a mistake to treat any of these default thresholds as validated out of the box for a new domain without recalibrating against real labeled data — which `judge_calibration_kpi` (Q11) is itself an implicit acknowledgment of, since calibrating a judge against human labels is a manual step this framework enables but doesn't automate.

## Q18: What's a limitation of `kpi.py` you'd fix given more time?

The clearest fix is `KPIBoard.evaluate_all()`'s lack of fault isolation (Q15) — a single KPI's exception (a network timeout inside a `references()` callable, an LLM judge call failing) currently aborts evaluation of every other KPI on the board, which is a serious reliability problem for any KPI board used as a live gating mechanism. I'd wrap each `kpi.evaluate(context)` call in `evaluate_all()` with error handling that produces a distinguishable "errored" `KPIResult` (rather than either crashing the whole board or silently treating an error as a pass/fail) and lets the caller decide how to handle a partially-evaluated board. A close second: the raw-value-vs-normalized-value inconsistency across the catalogue (Q2/Q3) — `conciseness_kpi` reports a raw character count while most others report `[0,1]`-normalized values, and `KPIBoard.weighted_score()` has no defense against silently averaging incompatible scales. I'd either normalize every catalogue KPI's `score()` output to `[0,1]` consistently, or add a runtime check/warning in `weighted_score()` when a registered KPI's observed value falls well outside `[0,1]`, so a builder combining KPIs gets an early signal rather than a silently nonsensical composite number.
