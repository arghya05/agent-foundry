# agent_foundry/serve.py — Q&A

`serve.py` wraps any compiled graph (LangGraph-based or the framework's own native engine) as a minimal, containerizable FastAPI app via `build_http_app` — four routes (`/`, `/chat`, `/resume`, `/health`), an `AuthResolver` protocol for pluggable authentication, per-user thread-id namespacing, a browser-based reference chat UI, and human-in-the-loop tool-approval support through `/resume`.

## Q1: Walk through exactly what happens when a POST hits `/chat` on an app built with `build_http_app(graph, auth=my_resolver)`, from request to response.

`chat(req: ChatRequest, request: Request)` (serve.py:298) first calls `_resolve_caller(request)`, which calls `auth.resolve(request.headers)`; if that raises `AuthenticationError`, `_resolve_caller` converts it to `HTTPException(status_code=401, ...)` (serve.py:271-277) — this is the one and only place a raw `AuthenticationError` gets turned into an HTTP response, so any `AuthResolver` implementation only needs to raise the domain exception, never touch FastAPI/Starlette types. Next, `_namespaced_thread_id(req.thread_id, identity)` (serve.py:279) rewrites the client-chosen `thread_id` into `f"{identity.tenant_id}:{identity.id}:{req.thread_id}"` — critically keyed by identity, not just tenant (see Q3). Then `invoke_graph_chat_turn(graph, message=req.message, thread_id=thread_id, identity=identity)` builds a state dict (`{"messages": [...], "thread_id": thread_id}`), seeds `state["request_identity"]` if `identity is not None`, and calls `graph.invoke(state, {"configurable": {"thread_id": thread_id}})` inside a `try/except BudgetExceeded` (serve.py:193-196) that converts a budget overrun into `HTTPException(429, ...)`. Finally `chat_response_from_result(result)` checks `result.get("__interrupt__")`: if present, returns `ChatResponse(status="awaiting_approval", pending=interrupts[0].value)`; otherwise `ChatResponse(status="ok", reply=result["messages"][-1]["content"])`.

## Q2: What specifically breaks if `build_http_app` is called with neither `auth` nor `allow_unauthenticated_demo=True`, and why is that the default failure mode instead of silently falling back to unauthenticated?

`build_http_app` raises `ValueError` immediately at function-call time (serve.py:259-264), before any routes are even registered — so a deployment misconfiguration is caught at startup, not silently at the first request. The docstring is explicit about the rationale: "a governed serving surface should not default to trusting a client-supplied identity" — this mirrors the runtime's own posture that a model-supplied `session_id`/`user_id` is never trusted (overridden by `make_act_node`), applied one layer further out to the HTTP client itself. Making the escape hatch a loudly-named boolean (`allow_unauthenticated_demo`, not just an implicit default) means a team can't end up unauthenticated in production by simply forgetting to pass `auth=...` — they'd get an immediate crash at app-build time instead of a working-but-insecure server that nobody notices is open.

## Q3: Why does `_namespaced_thread_id` combine `tenant_id` AND `identity.id`, not just `tenant_id`, into the thread-id namespace? Walk through the exact collision this prevents.

If namespacing used `tenant_id` alone (`f"{identity.tenant_id}:{req.thread_id}"`), then two different users belonging to the same tenant who both happen to pick the same client-side `thread_id` string — the docstring's own example is "Alice and Bob both picking 'support'" — would collide on the exact same LangGraph checkpointer thread, meaning Bob's chat turn could read and continue Alice's conversation history, a serious cross-user data leak within a single tenant. Including `identity.id` in the namespace (`f"{identity.tenant_id}:{identity.id}:{req.thread_id}"`, serve.py:286) makes isolation per-USER, not merely per-tenant, closing that gap. This is a case where the "obvious" simpler implementation (tenant-only namespacing) is a real security bug, and the code's own docstring calls this out explicitly rather than leaving it to be discovered later.

## Q4: `invoke_graph_chat_turn`'s docstring describes a bug that was "found live": `BudgetExceeded` propagating out of `graph.invoke()` as a raw 500 that browsers reported as an opaque "Failed to fetch." Explain the full failure chain and why this fix specifically requires funneling both `/chat` and `/resume` through this one function.

Before this fix, nothing anywhere in the codebase caught `runtime.BudgetExceeded` (a `RunBudget`/`LatencyBudget` ceiling — cost, step count, or cumulative session wall-clock time), so it propagated straight out of `graph.invoke()` as an unhandled exception, which FastAPI/Starlette turns into a bare 500. The docstring notes a genuine Starlette quirk: an unhandled exception's response doesn't reliably carry `CORSMiddleware`'s headers, so a browser making a cross-origin request sees a response missing the required CORS headers and reports it as a generic, information-free "Failed to fetch" — the actual 500 and its detail message never even reach the browser's JS error handler. The discovery happened testing a real multi-turn conversation against `healthcare/backend/agent.py`'s `LatencyBudget`. The fix — catching `BudgetExceeded` and re-raising as `HTTPException(429, ...)` — has to live in `invoke_graph_chat_turn` specifically (not duplicated in every route) because `/resume` needs the identical handling (a resumed turn can also exceed budget), and any external caller with `serve_chat_route=False` who registers their own custom `/chat` (e.g. `healthcare/backend/app.py`'s role-aware chat) is explicitly told, via this function's own docstring, to invoke through `invoke_graph_chat_turn` rather than calling `graph.invoke()` directly, so the 429 conversion isn't something every custom route has to remember to reimplement.

## Q5: What happens if `/resume` is called against a thread that never actually paused for approval — i.e., there's no pending `__interrupt__`?

Nothing in `resume()` (serve.py:305) checks whether the target thread is actually in a paused/interrupted state before constructing and sending a `Command(resume=payload)` (or the native-engine `_ResumePayload` fallback). It unconditionally calls `graph.invoke(command, {"configurable": {"thread_id": thread_id}})`. What happens next depends entirely on the underlying graph/checkpointer's own semantics for resuming a non-interrupted thread — this module doesn't defensively guard against that case at all, so the failure mode (a no-op, an exception, or resuming from the last real checkpoint incorrectly) is whatever LangGraph's or the native engine's own `invoke` does with an unexpected `Command`, not something `serve.py` controls or documents. This is a real gap: a client bug or a double-submitted "Approve" click could send a second `/resume` for an already-resolved approval with unclear results.

## Q6: Explain the `_ResumePayload` dataclass and the `hasattr(graph, "ainvoke")` branch in `/resume`. Why does this module duplicate a shim that also exists in `core.agent` and `ui.console`, rather than importing it?

`_ResumePayload` (serve.py:17-26) is a "langgraph-free stand-in for langgraph.types.Command(resume=...)" used when `graph` is a `native_engine._NativeGraph` rather than a real compiled LangGraph graph. The `/resume` route checks `hasattr(graph, "ainvoke")` as a duck-typed way to detect "this is a real LangGraph compiled graph" (LangGraph graphs expose `ainvoke`; the native engine apparently doesn't) — if true, it does a real `from langgraph.types import Command; command = Command(resume=payload)`; otherwise it builds the local `_ResumePayload`. The docstring is explicit that this is "duplicated rather than imported" specifically so `serve.py` "only ever takes a bare compiled `graph`, no dependency on `core.agent`" — importing `_ResumePayload` from `core.agent` would create a coupling where `serve.py` (a generic HTTP-serving module meant to work with ANY compiled graph, per its own top docstring about zero cloud-specific imports) would transitively pull in `core.agent`'s import graph, including a hard `langgraph` dependency, even for deployments using only the native engine that deliberately never installed `langgraph`. Three near-identical copies of the same four-line dataclass is a real, acknowledged duplication cost traded for that decoupling.

## Q7: Why are `ChatRequest`, `ResumeRequest`, and `ChatResponse` defined at module level rather than nested inside `build_http_app` where they're used?

The docstring explains this precisely: with `from __future__ import annotations` active (serve.py:9), FastAPI resolves a route handler's Pydantic model type annotations by looking them up as strings in the module's global namespace at request-handling time — a Pydantic model defined INSIDE a function (i.e., in that function's local namespace, not the module globals) can't be resolved that way, and FastAPI would silently misinterpret the parameter as a query parameter instead of a JSON request body. This is a genuinely subtle, easy-to-get-wrong FastAPI/`__future__ annotations` interaction, and the fact that the docstring calls it out explicitly suggests it was discovered the hard way (a request that "worked" but expected query params instead of a POST body) rather than known in advance — exactly the kind of gotcha a comparable "just Flask/FastAPI conventions" project could quietly hit without ever explaining why the models live where they do.

## Q8: What's the `BaseModel = object` fallback for, and what does `ChatRequest(BaseModel)` become if `pydantic` isn't installed?

Serve.py imports `pydantic.BaseModel` inside a `try/except ImportError` guarded by `TYPE_CHECKING` (lines 28-39) — under real runtime with `pydantic` missing, `BaseModel` is rebound to the builtin `object`. This means `class ChatRequest(BaseModel): thread_id: str; message: str` becomes a plain class inheriting from `object`, with no field validation, no `.dict()`/`.model_dump()`, and critically the class-level type annotations become inert (Python doesn't enforce annotation-declared attributes on plain classes) — so `ChatRequest` would just be an empty class with unenforced hints. Since FastAPI itself requires Pydantic to function as a request/response model at all, this fallback doesn't actually make `build_http_app` work without `pydantic`/`fastapi` — the real import of `FastAPI`, `HTTPException`, `Request` happens inside `build_http_app` itself and would raise `ImportError` there. The module-level fallback exists purely so `serve.py` is IMPORTABLE (e.g., by `cli.py`'s `cmd_serve`, which does `from .serve import build_http_app` only when actually needed) even in an environment without FastAPI/Pydantic installed — the module docstring's own "Requires `pip install fastapi uvicorn`" line confirms this is intentional: import-time tolerance, call-time hard requirement.

## Q9: How does `serve_chat_route=False`/`serve_resume_route=False`/`serve_demo_ui=False` support a multi-graph deployment like the docstring's referenced `healthcare/backend/app.py`? What would go wrong without these flags?

`build_http_app` always registers `/health` unconditionally, but gates `/`, `/chat`, `/resume` behind these three booleans (serve.py:292-322). The docstring explains the underlying constraint: FastAPI matches routes in REGISTRATION ORDER, so a route registered by `build_http_app` can't later be overridden by registering another handler at the same path — there's no "last registration wins" semantics to rely on. A deployment with more than one graph (one graph per user role, per the healthcare example) can't have `build_http_app`'s single fixed `/chat` handler (bound to one `graph` closure variable) serve requests that need to route to a DIFFERENT graph depending on the caller's role — so that caller sets `serve_chat_route=False` and registers its own `/chat`, reusing `chat_response_from_result()` (a module-level, not app-instance-bound, function — see Q10) for the shared interrupt-handling logic. Without these flags, the only way to avoid the route collision would be to not call `build_http_app` at all and reimplement `/health`/`/` from scratch too, duplicating code this module already provides correctly.

## Q10: Why is `chat_response_from_result` a free module-level function rather than a private closure inside `build_http_app`?

Because a caller that disables `serve_chat_route`/registers its own `/chat` handler (Q9) still needs the exact same interrupt-vs-normal-reply response-shaping logic — checking `result.get("__interrupt__")` and building the right `ChatResponse` — and shouldn't have to reimplement or copy-paste it. Making it a public, importable, stateless function (it takes a plain `dict` and returns a `ChatResponse`, no closure over `graph` or `auth`) means `healthcare/backend/app.py`'s custom role-aware chat route can do `from agent_foundry.serve import chat_response_from_result` and get identical, tested interrupt-handling behavior for free — this is the same "extend without reimplementing" design principle evident throughout the framework (e.g. `cli.py`'s composition-only subcommands).

## Q11: How does this differ from typical LangServe or bare-FastAPI-convention serving, and why did the author choose this narrower approach?

LangServe auto-generates OpenAPI schemas, `/invoke`/`/stream`/`/batch` endpoints, and a playground UI directly from a Runnable's inferred input/output types — a generic "serve any chain" tool. `build_http_app` instead hand-defines a fixed, narrow, opinionated four-route surface purpose-built for ONE interaction pattern: a stateful multi-turn chat with human-in-the-loop tool approval via LangGraph's interrupt/resume mechanism, plus a governed-auth layer LangServe doesn't provide out of the box. There's no streaming endpoint, no batch endpoint, no auto-generated OpenAPI schema beyond what FastAPI derives from the three Pydantic models. The tradeoff mirrors the framework's broader philosophy (see `cli.py`, `scaffold.py`): a small, understandable, auditable surface that does exactly what the approval-gated chat use case needs, at the cost of not being a general-purpose "serve any Runnable" tool — extending it for streaming or batch requires bypassing `build_http_app` and writing custom routes, exactly the escape hatch `serve_chat_route=False` etc. provide.

## Q12: The reference `AuthResolver` implementation, `ApiKeyAuthResolver`, checks `Authorization: Bearer <key>` OR a bare `X-API-Key` header, case-insensitively. What happens on a request with BOTH headers set to different (possibly conflicting) values?

Looking at `resolve()` (serve.py:74-83): it checks `auth_header.lower().startswith("bearer ")` first — if the `Authorization` header is present and Bearer-prefixed, `X-API-Key` is never even read, regardless of what it contains. Only if `Authorization` is absent or not Bearer-shaped does it fall back to `X-API-Key`. So `Authorization: Bearer keyA` + `X-API-Key: keyB` silently resolves using `keyA` only — `keyB` is completely ignored, with no validation that the two headers agree, no error, no logging. This is a reasonable and common precedence rule (Bearer wins), but it's implicit and undocumented in this dataclass's own docstring, which only says it's a "Zero-dependency reference AuthResolver" — a caller relying on both headers being mutually consistent would get no signal that one was silently discarded.

## Q13: What happens if `ApiKeyAuthResolver.identities` doesn't contain the resolved key — walk the exact exception path back to the HTTP response.

`resolve()`'s final line is `identity = self.identities.get(key); if identity is None: raise AuthenticationError("invalid or missing API key")` (serve.py:80-83) — note `key` could also be the empty string if neither header was present at all (`headers.get(...)` defaults to `""`), and an empty string simply won't be a key in the `identities` dict either, so "no credentials supplied" and "wrong credentials supplied" produce the exact same generic error message, which is a deliberate (if unstated) security practice — not leaking which failure mode occurred avoids helping an attacker enumerate valid vs. invalid keys via response differences, though this isn't called out as intentional anywhere in the docstring so it may simply be incidental. That `AuthenticationError` then propagates up through `resolve()` to whichever route called it, is caught in `_resolve_caller` (serve.py:271-277), and becomes `HTTPException(status_code=401, detail="invalid or missing API key")` — a proper structured 401, not a raw 500.

## Q14: The demo UI (`_PAGE`) is a single large string embedded directly in `serve.py`. What's the tradeoff of inlining an entire HTML/CSS/JS page as a Python string constant versus a separate static file served via `StaticFiles`?

Inlining `_PAGE` (serve.py:102-148) as a single triple-quoted string means `build_http_app` has zero filesystem dependency for the demo UI — no need to locate, package, or ship a separate `static/` directory alongside the installed `agent_foundry` package, which matters for a library meant to be `pip install`ed and whose `serve()` function should work regardless of the caller's working directory or how the package was installed (wheel vs. editable install can have very different static-file-path behavior). The cost is exactly what you'd expect: no syntax highlighting, no linting, and any HTML/CSS/JS edit requires editing a Python string literal with escaped quotes and manual JS embedded inline (note the page's own `fetch`/`async` JS logic for polling `/chat` and `/resume` and rendering approve/deny buttons, serve.py:118-147) — a genuinely awkward authoring experience for anything beyond this minimal reference page, which is presumably why the docstring frames `serve_demo_ui=False` as the expected path for "a deployment with its own separate, real frontend."

## Q15: The docstring for `serve_demo_ui` mentions a real incident: "a real user landed on it by navigating to the API's base URL instead of the actual frontend's port, and reasonably mistook it for a broken/old version of the real app." What does this reveal about a limitation of `serve_demo_ui=True` as a default?

Defaulting `serve_demo_ui=True` means every deployment of `build_http_app` — even ones that already have a real, separate, branded frontend elsewhere — gets a working, unbranded, session-less HTML page mounted at the API's own root path by default unless the caller remembers to pass `serve_demo_ui=False`. The incident described shows the real-world cost of that default: an unbranded page at a production API's root looks enough like "the app" that a confused user reasonably concluded the real app was broken, when in fact they'd simply hit the wrong URL/port. The default is defensible for the framework's own quickstart/demo scenario (batteries-included, "point a browser at it and it works" with zero setup), but it's a sharp edge for anyone deploying `build_http_app` behind a real product without immediately reading this specific docstring paragraph — a more defensive default might require the caller to explicitly opt IN to the demo UI rather than opt out of it, given how easy the incident shows it is to forget.

## Q16: What's a limitation of `serve.py` you'd fix given more time?

The two most concrete gaps found in this file: `/resume` never verifies the target thread actually has a pending interrupt before invoking `Command(resume=...)` (Q5) — a defensive check against double-resume or resuming a never-paused thread would close a real correctness gap. Second, the near-identical `_ResumePayload` dataclass triplicated across `serve.py`, `core.agent`, and `ui.console` (Q6) is an acknowledged, deliberate tradeoff for decoupling, but if `Command`'s or `_NativeGraph`'s resume-payload shape ever changes, all three copies need to be updated in lockstep with no shared test enforcing that — a small shared "resume payload protocol" module (importable without pulling in `langgraph` OR `core.agent`) could preserve the decoupling while removing the duplication risk.
