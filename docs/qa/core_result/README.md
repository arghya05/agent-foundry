# agent_foundry/core/result.py — Q&A

This module defines `RunResult`, the plain, engine-agnostic shape `Agent.run()`/`.resume()` return, plus `result_from_graph_output()`, the single function both `LangGraphWorkflowEngine` and `NativeWorkflowEngine` (`core/engines.py`) call to turn a raw graph-invocation dict into that shape — so callers like `serve.py`/`ui/console.py` never touch LangGraph's own result shape directly.

## Q1: What exactly does `RunResult` decouple callers from, and why does that matter?

Per the module docstring: "so a caller never has to know LangGraph's own result shape (`result["messages"][-1]["content"]`, `result.get("__interrupt__")`) the way `serve.py` and `ui/console.py` currently do." Without this abstraction, every consumer of an agent's output would need to independently know that LangGraph returns a dict with a `"messages"` list whose last element's `"content"` key holds the reply text, and that a truthy `"__interrupt__"` key signals a paused-for-approval state — internal implementation details of one specific runtime backend leaking into every caller. `RunResult` (lines 11-17) instead exposes five plain, named fields — `content: str`, `messages: list[dict]`, `awaiting_approval: bool`, `thread_id: str`, `raw: dict[str, Any]` — so `serve.py` can write `result.content` and `result.awaiting_approval` without knowing or caring whether the underlying engine was LangGraph or Native.

## Q2: Walk through `result_from_graph_output` when `raw["messages"]` is an empty list. What real scenario produces that, and is an empty string an ambiguous signal?

`content = messages[-1]["content"] if messages else ""` (line 22) — if `messages` is empty, `content` defaults to the empty string rather than raising an `IndexError`. This is a defensive default, but it's genuinely ambiguous to a caller: an empty string could mean "the agent produced a message and it happened to be empty content" or "no messages exist at all yet" (e.g., a call that failed before any turn was ever appended, or a resume path returning a raw dict with no fresh `"messages"` key populated). `RunResult` gives the caller no way to distinguish these two cases from `content` alone — they'd have to separately check `len(result.messages) == 0` themselves, since `content == ""` alone is consistent with either.

## Q3: `messages[-1]["content"]` assumes the last message is the thing the caller wants to display. What if the last message is actually a tool call or tool result rather than final assistant text?

Nothing in `result_from_graph_output` checks the `role` or shape of `messages[-1]` — it blindly takes `["content"]` off whatever the last dict happens to be. This function trusts an invariant it does not itself enforce: that whatever produced `raw` (`build_agent_graph` for LangGraph, `_NativeGraph` for Native) always finishes a `run()`/`resume()` call with a final assistant message as the last entry in `messages`, never leaves a dangling tool-call or tool-result message at the tail. If that invariant were ever violated — say, a future code path in the orchestration graph returned control with a tool-result message as the last entry (e.g., an interrupted run that hasn't yet produced a follow-up assistant turn) — `result.content` would silently show tool-call/tool-result data (or whatever shape that message's `"content"` key holds) as if it were the agent's reply, with no validation or error to catch the mismatch.

## Q4: `awaiting_approval: bool = bool(raw.get("__interrupt__"))` collapses LangGraph's interrupt payload down to a single boolean. What does that lose, and where would a caller who needs the actual interrupt details go?

LangGraph's `__interrupt__` key, when present, typically holds a list/tuple of `Interrupt` objects carrying the actual payload of *why* execution paused (e.g., what tool call needs approval, what value is being requested) — `bool(...)` on that discards all of it down to "yes, something is pending" or "no, nothing is." A caller that needs to know *what* is being approved — to render an approval UI, say — cannot get that from `RunResult.awaiting_approval` alone; they have to reach into `RunResult.raw["__interrupt__"]` directly, which is exactly the LangGraph-shape-leaking `raw` dict the whole abstraction was meant to hide. This is a deliberate, pragmatic tradeoff (`awaiting_approval` covers the common "should I show an approve/reject button" case cheaply) but it means the abstraction is incomplete for any caller needing interrupt *content*, not just interrupt *presence*.

## Q5: `raw: dict[str, Any] = field(default_factory=dict)` is kept on `RunResult` as an escape hatch. Doesn't that defeat the purpose of hiding the engine's raw shape?

Partially, yes — and this is worth being honest about rather than glossing over. The whole point of `RunResult` is that `serve.py`/`ui/console.py` shouldn't need to know LangGraph's dict shape, but `raw` is still right there on the object, fully populated with exactly that shape (line 28: `raw=raw`), one attribute access away. Any caller who needs something `RunResult`'s five named fields don't expose (full interrupt payloads per Q4, custom state keys a particular graph might stash, anything engine-specific) can — and, in practice, likely will — reach into `.raw` and start depending on the underlying shape again, silently reintroducing the exact coupling the abstraction exists to prevent. The honest framing: `RunResult` covers the *common* cases cleanly and gives an unenforced escape hatch for everything else, rather than being an airtight boundary.

## Q6: `result_from_graph_output` is called identically by both `LangGraphWorkflowEngine` and `NativeWorkflowEngine` (`core/engines.py`'s `_invoke`). What invariant must `NativeEngine`'s raw output satisfy for this shared function to work correctly across both runtimes?

`core/engines.py._invoke()` does `raw = compiled.invoke(...)` then `return result_from_graph_output(raw, thread_id=thread_id)` — the exact same call for both a real LangGraph compiled graph and a `_NativeGraph` instance (`core/native_engine.py`). For this to produce sensible `RunResult`s in both cases, `_NativeGraph.invoke()`'s return value must be shaped like a dict with (at minimum) a `"messages"` key holding a list of `{"role":..., "content":...}`-shaped dicts, and optionally a `"__interrupt__"` key with the same truthy/falsy interrupt-signaling convention LangGraph uses. This is the actual seam that keeps `runtime="native"` and `runtime="langgraph"` interchangeable from `Agent`'s perspective (per `core/engines.py`'s own docstring: "both `.build()` outputs... speak the same `.invoke(state_or_command, run_config)`... calling convention") — `result.py` doesn't itself enforce this contract on `_NativeGraph`; it simply assumes it, and a bug in `_NativeGraph` that ever returned a differently-shaped dict would surface as a `KeyError`/`TypeError` inside `result_from_graph_output`, not inside `_NativeGraph` itself.

## Q7: Why is `RunResult` a plain `@dataclass` and not a Pydantic model, given other constraints on this codebase?

Agent Foundry's architecture is explicitly Python-native with no Pydantic dependency in the core layer — `RunResult` doesn't need validation or coercion (its fields are already well-typed values produced by trusted, in-process code, not untrusted external input needing parsing/sanitization at a boundary), so a dataclass is sufficient and keeps the module dependency-free. This matches the pattern across the rest of `core/*.py` (`ModelCapabilities`, `EvalCase`, `CaseResult`, `Scorecard` in `evalgate.py`; `RunBudget`, `LatencyBudget` in `runtime.py` — all plain dataclasses) — Pydantic's validation/serialization machinery would be pure overhead here since nothing needs runtime type-checking or JSON (de)serialization at this boundary; if `RunResult` ever needed to cross a process boundary (e.g., serialized over HTTP in `serve.py`), that's a job for an explicit serialization step at the actual boundary, not a reason to make the in-process type itself heavier.

## Q8: Does `result_from_graph_output` protect a caller from accidentally mutating the engine's own internal state through the returned `RunResult`?

No — and this is a genuine, concrete inconsistency worth flagging. `messages = raw.get("messages", [])` (line 21) takes the list *by reference*, not a copy; `RunResult(... messages=messages, ... raw=raw)` stores that same list object (and the same `raw` dict object) directly on the result. Contrast this with `core/state_store.py`'s `MemoryStateStore.load()`/`.save()`, which *deliberately* `copy.deepcopy()` state specifically because it nests a list of message dicts, precisely to prevent "a caller mutating what `load()` returned... [from reaching] back into this store's own storage." `result_from_graph_output` makes no such guarantee: if `raw["messages"]` is the same list object `NativeEngine._threads[thread_id]["messages"]` currently points at (which, for the Native engine, it plausibly is, since `_NativeGraph.invoke()` builds its raw output from that in-process state), then a caller appending to or mutating `result.messages` could corrupt the engine's own live conversation state for that thread — a real risk the module doesn't document or guard against, unlike the deep-copy discipline `state_store.py` explicitly calls out for the same underlying data shape.

## Q9: `RunResult.content` is typed `str`, but Anthropic's (and other providers') APIs can return multi-block content (a list of content blocks, e.g., text + tool_use). What happens if `messages[-1]["content"]` isn't actually a string?

Nothing in `result_from_graph_output` validates the type of `messages[-1]["content"]` before assigning it to `RunResult.content` — a plain dataclass performs no runtime type checking of its own, so if a particular message's `"content"` value happens to be a list of content blocks rather than a plain string (a real shape Anthropic's Messages API can return for structured/multi-modal responses), `RunResult.content` would silently hold a `list`, not a `str`, contradicting its declared type. Any downstream code doing `result.content.lower()` (exactly what `core/evalgate.py`'s `run_eval` does: `case.expected_substring.lower() in result.content.lower()`) would raise `AttributeError: 'list' object has no attribute 'lower'` at that call site, not here — the type mismatch is silent at the point it's introduced and only surfaces as a crash wherever a caller first assumes `content` is really a string.

## Q10: Why keep `RunResult` this minimal instead of a rich structured result carrying a full step-by-step trace, per-tool-call cost, etc. — how does this compare to CrewAI/AutoGen's richer result objects?

Cost and step accounting already live elsewhere in the system — `AgentConfig.budget` (a `RunBudgetLike`, `runtime.py`) tracks per-thread cost/step totals independently, and `core/evalgate.py`'s `run_eval` pulls cost via `agent.config.budget.cost_usd_for(...)` rather than expecting `RunResult` to carry it. `RunResult` stays a thin projection of "what to show the user" — final text, the message transcript, whether approval is pending, the thread id, and an escape hatch — rather than a report object trying to be everything at once. This is a deliberate separation of concerns: a per-call result object answers "what happened in this specific call," while budget/cost/eval-scoring are cross-cutting concerns tracked by their own dedicated primitives (`RunBudget`, `Scorecard`) that outlive any single `RunResult`. It's a narrower design than, say, a framework that bundles a full execution trace into every returned result object — the tradeoff is that a caller wanting a full trace has to go get it from `result.raw["messages"]` (the whole transcript is there) or from a tracer/audit sink, not from a single rich field.

## Q11: If you wanted to add a `tool_calls` convenience field to `RunResult` (e.g., a pre-extracted list of tool names called during the run), would that be a backward-compatible change?

Yes — because `RunResult` is a dataclass and every existing field beyond the required `content` already has a default (`messages`, `awaiting_approval`, `thread_id`, `raw` all default via `field(default_factory=...)` or a literal default), a new field added with its own default (e.g., `tool_calls: list[str] = field(default_factory=list)`) would not break any existing positional or keyword construction of `RunResult` — this is the same additive-field discipline used elsewhere in the codebase (`contracts.ToolSpec`'s own comment: "Everything below is additive (all defaulted) — existing positional/keyword construction... is unaffected"). The actual work would be in `result_from_graph_output` itself — it would need to derive `tool_calls` from `raw["messages"]`, likely by reusing `orchestration._get_all_tool_calls` (the same helper `core/evalgate.py` already reuses for this exact purpose) rather than reimplementing tool-call extraction a third time.

## Q12: `result_from_graph_output(raw: dict[str, Any], *, thread_id: str)` makes `thread_id` keyword-only via the bare `*`. Why enforce that specifically here?

Both `raw` (a dict) and `thread_id` (a string) are unrelated in type, so a positional mix-up wouldn't even be a type error most of the time — but forcing `thread_id` to be passed by keyword makes every call site self-documenting (`result_from_graph_output(raw, thread_id=thread_id)`, exactly how both `LangGraphWorkflowEngine._invoke` and `NativeWorkflowEngine._invoke` in `core/engines.py` call it) rather than relying on positional-argument order to communicate what `thread_id` means. Given this function is called from at least two independent engine implementations, keeping the call signature unambiguous at every call site is cheap insurance against a future third engine implementation accidentally swapping argument order.

## Q13: `RunResult.thread_id` is set from the *caller's* `context.resolved_thread_id()`, not derived from anything inside `raw` itself. What happens if the raw graph output somehow reflects a different thread than the one the caller thinks it's talking to?

`result_from_graph_output(raw, *, thread_id)` simply echoes back whatever `thread_id` value its caller passed in (line 27: `thread_id=thread_id`) — it never cross-checks that value against anything inside `raw` (LangGraph's checkpointer config, e.g., embeds a `thread_id` under `configurable`, but this function doesn't look there). If some code path ever produced a `raw` dict whose actual underlying state belonged to a *different* thread than the one the caller believes it invoked (a coding bug elsewhere, e.g., in checkpointer configuration or in `_NativeGraph`'s thread-state lookup), `RunResult.thread_id` would faithfully report the caller's *intended* thread id even while `RunResult.messages`/`content` silently came from the wrong thread's state — this function provides no consistency check to catch that class of bug; it's an honest, undocumented limitation.

## Q14: Is there any error handling inside `result_from_graph_output` for malformed input — what if `raw` isn't a dict, or `raw["messages"]` holds something other than a list of dicts?

None at all. `raw.get("messages", [])` assumes `raw` supports `.get` (i.e., is dict-like); `messages[-1]["content"]` assumes `messages` is indexable and its last element supports `["content"]`; `raw.get("__interrupt__")` again assumes dict-like `raw`. Any deviation — `raw` being `None`, `messages` containing a non-dict entry, etc. — raises whatever built-in exception that operation naturally produces (`AttributeError`, `TypeError`, `KeyError`), uncaught, right here. Whether that's "acceptable" depends entirely on the caller: `core/evalgate.py`'s `run_eval` wraps its own call to `agent.run(...)` (which internally calls `result_from_graph_output`) in a blanket `try: ... except Exception as e:` that records `error=str(e)` on the `CaseResult` — so in the eval-gate path, a malformed `raw` would surface as a generic per-case error, correctly attributed by `attribute_failure()` as `"error"` (checked first, before task_success/tool_accuracy/trajectory/kpi). Outside that wrapped path (e.g., a bare `serve.py` request handler calling `agent.run()` directly with no try/except), the same exception would propagate uncaught all the way up unless that caller adds its own handling.

## Q15: Given how small this file is (~30 lines), why does it warrant being a separate module rather than living inline inside `core/agent.py` or `core/engines.py`?

Single-responsibility and independent testability: `result_from_graph_output` has a pure, narrow contract — dict in, `RunResult` out — that can be unit tested with hand-built dicts (`result_from_graph_output({"messages": [{"role": "assistant", "content": "hi"}]}, thread_id="t1")`) with zero dependency on a real `Agent`, LangGraph, or `NativeEngine` at all. Keeping it in its own module means `RunResult`'s shape and `result_from_graph_output`'s extraction logic can be reasoned about, tested, and changed in complete isolation from either engine implementation, and both `core/engines.py`'s `LangGraphWorkflowEngine`/`NativeWorkflowEngine` can import the same shared function (`from .result import RunResult, result_from_graph_output`) without either engine module needing to depend on the other or duplicate the extraction logic — exactly the "reused, not reimplemented" discipline visible elsewhere in the codebase (e.g., `core/evalgate.py` reusing `orchestration._get_all_tool_calls`).
