# agent_foundry/experiments.py — Q&A

A/B testing infrastructure: `Experiment` does deterministic, stable-hash variant assignment per identity, and `ExperimentTracker` aggregates per-variant metric values (count/mean) into a `summary()` — designed to compose with `kpi.py` (score each run with a KPI, feed the score into `.record()`) rather than invent its own scoring mechanism.

## Q1: Walk through exactly what `Experiment.assign(identity)` computes, step by step, for a concrete example — `variants={"control": 0.5, "treatment": 0.5}` and some `identity.id`.

`assign()` (lines 20-32) first computes `total = sum(self.variants.values())` — here `1.0` — establishing that weights need not already sum to 1; they're normalized internally against whatever their actual total is. It then builds a deterministic digest: `hashlib.sha256(f"{self.name}:{identity.id}".encode()).hexdigest()` converted to a big integer via `int(..., 16)`. Note the hash key is `"{experiment.name}:{identity.id}"`, not identity alone — this is what lets the *same* identity get a *different* (but still stable) variant assignment in a different experiment, since the experiment name is baked into the hash input. That integer is reduced with `% 10_000` and divided by `10_000`, producing a float in `[0, 1)`, then scaled by `total` to land the "bucket" in `[0, total)`. The function then walks `self.variants.items()` accumulating `cumulative`, and returns the first variant whose cumulative weight exceeds `bucket` — standard weighted-bucket assignment. For the 50/50 example, `bucket` lands somewhere in `[0, 1.0)`; if it's `< 0.5` it returns `"control"` (assuming `"control"` is iterated first), otherwise `"treatment"`. Because `sha256` and `identity.id` are both fixed for a given identity/experiment pair, `assign()` returns the exact same variant every single call — no randomness, no state, no memoization needed.

## Q2: Why hash-bucket on `identity.id` instead of using `random.choice()` or `random.random()` weighted by variant?

The docstring is explicit: "the same identity always gets the same variant for this experiment... an identity's experience never flaps between calls" (lines 22-23). A naive `random.random()`-based assignment would give a *different* variant every time `assign()` is called for the same user — meaning a single user could see the control prompt on one turn and the treatment prompt on the next, which corrupts both the user experience (inconsistent behavior mid-conversation) and the experiment's statistical validity (per-user metrics would be a blend of both variants' effects rather than a clean single-variant signal, destroying the entire point of A/B testing — you can no longer attribute an outcome to "the variant this user was in" if they were actually in both). Hash-based bucketing solves this without needing any persisted assignment table: `assign()` is a pure function of `(experiment.name, identity.id)` and the current `variants` dict, so consistency is achieved by determinism rather than by looking up and caching a prior decision somewhere — no database, no session state, nothing to go stale or get lost.

## Q3: What happens to existing users' variant assignments if you change `Experiment.variants`' weights mid-experiment — say from `{"control": 0.5, "treatment": 0.5}` to `{"control": 0.3, "treatment": 0.7}`?

Because `bucket` is computed as `(digest % 10_000) / 10_000 * total` and then compared against `variants`' *cumulative* weights in iteration order, changing the weights changes where the cumulative boundaries fall for every identity, even though each identity's underlying `digest`/`bucket` value is unchanged. Concretely: a user whose `bucket` happened to be `0.4` was in `"control"` under the 50/50 split (since `0.4 < 0.5`) but would flip to `"treatment"` under the 30/70 split (since `0.4 > 0.3`, and cumulative after control is now `0.3`). This is a real, unannounced consequence of changing weights mid-flight: some fraction of already-assigned users silently get reassigned to a different variant the next time `assign()` is called, with zero record of the fact that they switched or what they experienced before the change. For a rigorous A/B test, this is a serious methodological problem — most real experimentation platforms (e.g. a proper feature-flagging/experimentation system) use variant boundaries designed so that changing weights only affects users who haven't yet been bucketed, or they lock in assignments at first-sight and persist them explicitly, precisely to avoid this "an ongoing experiment silently reshuffles some fraction of its participants" failure mode. `experiments.py` has no such protection — bucket boundaries are recomputed fresh from `variants` on every single `assign()` call with no persisted assignment history.

## Q4: What is `ExperimentTracker.summary()` actually reporting, and what's missing from it if you wanted to determine whether a difference between variants is statistically significant?

`summary()` (lines 42-48) returns, per variant, only `{"count": float(len(values)), "mean": sum(values) / len(values)}` — the raw sample size and the arithmetic mean of whatever values were `.record()`-ed for that `(experiment, variant)` pair. There is no variance, no standard deviation, no confidence interval, and no significance test (a t-test, a z-test for proportions, a Bayesian posterior, anything) anywhere in this module. Given just two means and two counts, you cannot tell whether "treatment mean 0.62 vs. control mean 0.58" is a real effect or noise from small samples — the module gives you the raw ingredients for a statistical test but performs none of the actual test itself. This is honestly scoped: `experiments.py` is explicitly a "deterministic variant assignment plus per-variant metric aggregation" mechanism, not a statistics engine — a real production A/B testing decision would need to layer a proper significance test (accounting for sample size, variance, and ideally sequential-testing corrections if peeking at results before the experiment is "done") on top of the numbers `summary()` provides, none of which exists here.

## Q5: `ExperimentTracker._records` is keyed by `tuple[str, str]` (experiment, variant), with a leading underscore suggesting it's meant to be treated as private/internal. What happens if two different experiments happen to use the exact same variant name — say both have a `"treatment"` variant — does `record()`/`summary()` conflate them?

No — because the dict key is the *tuple* `(experiment, variant)`, not just `variant` alone, `_records[("prompt_v2", "treatment")]` and `_records[("topology_v3", "treatment")]` are entirely distinct keys even though both share the string `"treatment"`. `record(experiment, variant, value)` (line 39-40) does `self._records.setdefault((experiment, variant), []).append(value)`, so values only ever accumulate within the exact same experiment+variant pair. `summary(experiment)` (lines 42-48) then filters with `if exp != experiment: continue`, iterating every key in `_records` and only including matches — so cross-experiment variant-name collisions are a complete non-issue by construction. The leading underscore on `_records` is really just a convention signaling "use `.record()`/`.summary()`, don't poke this dict directly" (there's no actual name-mangling enforcement since this isn't a double-underscore, and nothing prevents external code from reading/mutating `_records` directly if it really wanted to) — Python's `@dataclass` doesn't give you real private fields, only a naming convention.

## Q6: The module docstring says `experiments.py` "composes with `kpi.py`... no new scoring mechanism needed." Concretely, what would that composition look like in code, and what's the actual coupling between the two modules (import-wise)?

Concretely: you'd construct a `KPI` from `kpi.py` (say `task_success_kpi()` or a custom one), call `kpi.evaluate(context)` to get a `KPIResult` for one run, and then call `experiment_tracker.record(experiment.name, variant, kpi_result.value)` — using the KPI's numeric `.value` as the metric fed into `ExperimentTracker`. `Experiment.assign(identity)` would be called first, before the run, to decide which variant (which prompt, which topology, whatever) that identity's turn should actually use; then after the run completes, the resulting KPI score gets recorded against that same variant. Import-wise, however, `experiments.py` has **zero** actual import of `kpi.py` — it only imports `hashlib`, dataclasses, and `.contracts.Identity`. The "composition" described in the docstring is a runtime/design-level composition (a caller wires the two together), not a code-level dependency — `experiments.py` doesn't know `KPI`/`KPIResult` exist, and `ExperimentTracker.record()`'s `value: float` parameter is generic enough to accept a KPI score, a raw latency number, a binary success flag, or anything else a caller wants to track per variant. This mirrors the deliberate compositional philosophy stated in `kpi.py`'s own docstring — "nothing here imports from the rest of `agent_foundry`... composes with it from the outside, by choice, not by inheritance" — the two modules are designed to be combined by callers, not coupled to each other.

## Q7: What happens if `Experiment.variants` is an empty dict, `{}`?

`assign()` computes `total = sum(self.variants.values())` → `0` (sum of nothing), then `bucket = (digest % 10_000) / 10_000 * total` → `bucket = <something> * 0` → `0.0` regardless of the digest. The `for variant, weight in self.variants.items()` loop then doesn't execute at all (no items to iterate), so `cumulative` never accumulates and the loop's `return variant` line is never reached — execution falls through to `return next(iter(self.variants))`. But `iter({})` is an empty iterator, so `next()` on it raises `StopIteration` immediately (with no default given) — meaning `assign()` on an experiment with zero variants raises `StopIteration` rather than returning a sensible error or `None`. This is a real, unguarded edge case: nothing in `Experiment.__init__` or `assign()` validates that `variants` is non-empty, so an experiment configured with no variants (a configuration bug) fails at first `assign()` call with a somewhat cryptic error rather than failing fast at construction time with a clear message like "an Experiment needs at least one variant."

## Q8: What happens if `Experiment.variants` has weights that sum to a *negative* number, or contains a negative weight (e.g. `{"control": 1.0, "treatment": -0.5}`) — is this validated anywhere?

Nothing validates weight signs anywhere in `Experiment` or `assign()`. With `total = 0.5` (1.0 + -0.5), `bucket` is computed as some value in `[0, 0.5)`. Walking the loop: `cumulative` after `"control"` is `1.0`, which is already `> bucket` for any non-negative bucket value, so `"control"` is returned unconditionally — `"treatment"`'s negative weight can never actually be reached by the cumulative-sum walk (since `cumulative` only decreases if you get to the negative-weight variant, and by the time you'd reach it, `bucket < cumulative` was already true at the prior step for any positive `bucket`). Effectively, a negative weight silently means "this variant will basically never be assigned" rather than raising a validation error — which is a confusing failure mode for someone debugging why 100% of traffic is landing in `"control"` despite configuring what looks like a majority-`treatment` split. This is a config-validation gap: sane experimentation configs should have all-positive weights, and there's no assertion here enforcing that.

## Q9: `ExperimentTracker.summary(experiment)` returns a `dict[str, dict[str, float]]` — what happens if a caller calls `summary()` for an experiment name that was never `.record()`-ed at all?

`summary()` iterates all of `self._records.items()` and filters by `exp != experiment` — if no key in `_records` has a matching `exp`, the loop body's `if` never assigns to `out`, and the function returns an empty dict `{}`. This is graceful (no exception), but silent in the same way several other modules in this codebase are — an empty summary for "an experiment I forgot to record any data for" looks identical to "an experiment I recorded data for, but happened to filter to nothing" (which can't actually happen here since any recorded value creates an entry, but the general pattern of "empty dict means either 'nothing happened' or 'you asked about the wrong thing'" recurs across this module and others, e.g. `trajectory_report()` in `eval.py` has an analogous ambiguity for an unknown session id).

## Q10: How does this A/B testing approach compare to how a real experimentation platform (Optimizely, LaunchDarkly, or Statsig) would handle the same problem?

Real experimentation platforms typically add several layers this module doesn't attempt: persisted assignment (once a user is bucketed, that assignment is recorded and never recomputed, even if the experiment config later changes — solving exactly the Q3 reassignment problem, which `experiments.py`'s pure-recompute-every-time approach does not solve), mutually-exclusive experiment layers (so a user isn't simultaneously in conflicting experiments that confound each other's results), sequential testing / peeking corrections (so a team looking at results mid-experiment doesn't inflate false-positive rates), and real statistical significance testing built into the reporting UI. `experiments.py` intentionally implements only the most foundational piece — deterministic, consistent hash-based bucketing (which these platforms also use internally, so the core mechanism is legitimate and matches industry practice) plus bare aggregate stats — and leaves everything else (persistence, significance testing, layer management) as a gap a caller building on top of this module would need to fill themselves, exactly as `kpi.py`'s honest-limitations framing does for its own domain.

## Q11: Given `Experiment.assign()`'s hash-bucketing is a pure function with no persisted state, how would you actually implement the "persist assignment at first sight, never reassign" fix identified in Q3, using only what this module currently provides?

You'd need to add an assignment-persistence layer above `Experiment` — nothing in the current `Experiment`/`ExperimentTracker` pair does this. A minimal fix consistent with the module's existing style: a small `AssignmentStore` (a dict, or a real DB-backed store for production) keyed by `(experiment.name, identity.id)` that's checked *before* calling `assign()` — if an assignment already exists for that key, return it; otherwise call `assign()` once, persist the result, and return it. This converts `Experiment.assign()`'s inherent recompute-every-time behavior into "compute once, remember forever," decoupling a user's original assignment from any future changes to `variants`' weights. It's a natural extension precisely because `assign()`'s pure-function determinism means the *first* computed value is always a valid, reproducible choice to persist — you're not fighting the existing design, just adding a cache-with-write-once semantics in front of it, matching the same "protocol-first, add durable persistence separately" pattern used by `CostLedgerLike`/`EvalHarness`/`Evaluator` elsewhere in this codebase.

## Q12: What's the actual thread-safety story for `ExperimentTracker` if two threads call `record()` concurrently for the same `(experiment, variant)` key?

`record()` does `self._records.setdefault((experiment, variant), []).append(value)` — two operations, but each individually GIL-atomic in CPython (`dict.setdefault` and `list.append` are each single bytecode-level operations from the interpreter's perspective, in the sense that neither can be interrupted mid-way to produce a torn/corrupted dict or list — same reasoning as `Tracer.spans` and `EvalHarness.records` elsewhere in this codebase). The only genuine race is on `setdefault` itself when the key doesn't yet exist and two threads race to create it simultaneously — CPython's GIL still serializes the two `setdefault` calls (only one truly "wins" and creates the list, the other's `setdefault` sees the already-created list from the first), so no duplicate lists or key collisions can occur; you just can't predict which thread's `[]` "wins" the initial creation, which doesn't matter since both threads' subsequent `.append(value)` still land in the single resulting list. So this is safe under CPython's GIL by the same accidental-safety argument used throughout this codebase's simple in-memory dataclasses — but, as with `observability.Tracer`, there's no explicit lock anywhere, and this reasoning is CPython-specific (it would not automatically hold under a free-threaded/no-GIL Python build, which is an increasingly real possibility as of Python 3.13+'s experimental free-threading mode).

## Q13: `Experiment.assign()` hashes on `identity.id` alone — `Identity` (from `contracts.py`) also carries `tenant_id` and `roles`. What happens if two different tenants happen to use the same `id` string (e.g. both use `"user-1"` as a locally-scoped identifier)?

`assign()`'s hash input is `f"{self.name}:{identity.id}".encode()` (line 25) — `tenant_id` never enters the computation at all. If two different tenants both have a user with `id="user-1"`, they hash to the exact same digest for a given experiment name, and therefore land in the exact same variant bucket, deterministically, every time — the experiment can't actually distinguish between them despite them being different real-world users belonging to different tenants. For a single-tenant deployment this is harmless (ids are presumably unique within that tenant's namespace), but for a genuinely multi-tenant system where `id` values aren't guaranteed globally unique across tenants (a very plausible scenario if ids are locally assigned, e.g. sequential per-tenant user numbers), this is a real bucketing collision: two unrelated users, from two unrelated tenants, are forced into correlated variant assignments for every experiment, purely by coincidence of sharing an `id` string. The fix would be trivial — hash on `f"{self.name}:{identity.tenant_id}:{identity.id}"` instead — but as written, `assign()` silently assumes `identity.id` is already globally unique across the whole deployment, an assumption `Identity`'s own shape (carrying a separate `tenant_id` field specifically because ids apparently aren't assumed globally unique elsewhere in this codebase) doesn't actually guarantee.

## Q14: The bucketing math is `(digest % 10_000) / 10_000 * total` — what's the practical precision/granularity limit this imposes on variant weights, and could you express, say, a 0.03% vs. 99.97% split accurately?

`digest % 10_000` can only ever take one of 10,000 discrete integer values (`0` through `9999`), so the resulting `bucket` value before scaling by `total` is restricted to exactly 10,000 possible positions in `[0, 1)` — a granularity of `0.01%` per step. A `0.03%` vs. `99.97%` split is representable in principle (the boundary would fall at bucket position `3` out of `10000`), but whether any specific `identity.id` actually lands in that razor-thin `0.03%` slice depends entirely on whether its digest happens to hash into exactly those first 3 out of 10,000 buckets — with a small population of identities, you could easily see zero or a wildly disproportionate fraction actually landing in a slice that thin, purely from sampling variance at that granularity (this is a general property of hash-bucketing-based assignment, not unique to this implementation, but the fixed `% 10_000` modulus does hard-cap the achievable precision at two decimal places of percentage — a split like `0.001%` genuinely cannot be expressed by this bucketing scheme at all, since anything finer than `1/10000` collapses onto the same integer bucket boundary). For the realistic experimentation use case (variants like 50/50, 90/10, 95/5), `10_000` buckets is more than enough resolution; it would only become a real limitation for extremely small "canary" slices of traffic.

## Q15: What's a limitation of `experiments.py` you'd fix given more time?

The most consequential limitation is the lack of persisted assignment (Q3/Q11) — because `assign()` recomputes the bucket fresh from `variants`' *current* weights on every call, an experiment whose weights are adjusted mid-flight silently reassigns some fraction of already-bucketed users with zero record of the change, which is a real threat to the validity of any experiment run this way for more than a brief, fixed-configuration window. Given more time, I'd add the write-once `AssignmentStore` layer from Q11 as a first-class part of this module (not left as a caller's exercise), plus basic input validation on `Experiment.variants` (reject empty or negative-weight configs at construction time, per Q7/Q8, rather than failing cryptically at first `assign()` call). A second, smaller gap: `ExperimentTracker.summary()` reporting only count/mean with no variance or significance testing (Q4) means this module can tell you *that* two variants differ, but never *whether that difference is real* — a genuinely useful next step would be adding an optional significance-test helper (even a simple two-proportion z-test for binary KPI outcomes) rather than requiring every caller to reimplement that themselves.
