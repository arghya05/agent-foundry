# agent_foundry/cli.py — Q&A

`cli.py` is a thin `argparse`-based command-line front end (`foundry`) that composes existing `agent_foundry` modules — `scaffold.create_agent`, `agent_spec.build_agent`, `core.evalgate.run_eval`, and `serve.build_http_app` — into six subcommands (`init`, `run`, `eval`, `serve`, `inspect`, `trace`) without introducing any new engine logic of its own.

## Q1: The module docstring says "No new engine: every subcommand is composition over something that already exists." Why is that architectural constraint valuable, and what would violating it look like in practice?

The constraint means `cli.py` is not allowed to contain business logic — it can only parse arguments, import the relevant module, and call a function that already exists and is presumably already tested. This keeps the CLI and the library in permanent lockstep: if `scaffold.create_agent`'s signature changes, `cmd_init` breaks loudly and immediately (an `ImportError` or `TypeError`), rather than silently drifting from a duplicated code path. Violating it would look like `cmd_eval` re-implementing scoring logic inline instead of calling `core.evalgate.run_eval`, or `cmd_serve` hand-rolling a FastAPI app instead of calling `serve.build_http_app` — at that point you have two implementations of "how to score an agent" or "how to serve a graph" that can silently diverge, and a user who only exercises the CLI path would never catch a regression that unit tests against the library functions would catch. The tradeoff is that the CLI is deliberately un-clever: it can't do anything the library can't already do standalone, which is exactly the point for a portfolio piece that wants to demonstrate the library, not the wrapper.

## Q2: Walk through exactly what happens when a user runs `foundry init sales_agent --tools lookup_lead,send_email`.

`main()` builds the `argparse` parser, dispatches to `args.func`, which is `cmd_init` (registered at line 160 via `p_init.set_defaults(func=cmd_init)`). `cmd_init` (line 28) splits `--tools` on commas and strips whitespace/empties (`[t.strip() for t in args.tools.split(",") if t.strip()]`), imports `create_agent` lazily from `.scaffold` (not at module top — see Q3), and calls `create_agent("sales_agent", directory=".", tools=["lookup_lead", "send_email"])`. That function writes `prompts/sales_agent.md` and `agents/sales_agent.py` to disk and returns a dict of the two paths. `cmd_init` then prints both paths and a "next steps" hint pointing at `foundry run <path>`. Note `cmd_init` never passes `--topology` through to `create_agent` even though `create_agent` accepts a `topology` kwarg — the CLI's `init` subparser has no `--topology` flag at all, so every CLI-scaffolded agent silently gets the default `"single"` topology. That's a real, minor inconsistency between `cli.py`'s `p_init` and `scaffold.py`'s own `_main()`, which does expose `--topology`.

## Q3: Every subcommand function does its real imports (`from .scaffold import create_agent`, `import uvicorn`, etc.) inside the function body rather than at module top. Why, and what does it cost?

This is deliberate lazy-loading to keep `foundry` fast and dependency-light for any single invocation. `agent_foundry` has many optional extras (`fastapi`, `uvicorn`, `chromadb`, `cedarpy`, `opentelemetry`, `a2a-sdk`, `autogen_agentchat` — see the `_EXTRAS` tuple at line 116) and a user running `foundry init` should not need `uvicorn` or `fastapi` installed at all; if imports were hoisted to module top, `import cli` (and therefore every subcommand, including ones that don't need those packages) would raise `ImportError` for anyone who hasn't `pip install`ed the extras used only by `serve` or `eval`. The cost is that errors surface later than they could (you find out `uvicorn` is missing only when you actually run `foundry serve`, not at `foundry --help` time), and it makes the module a little harder to statically analyze/type-check since imports are scattered across function bodies rather than centralized. `cmd_inspect` (line 129) exists specifically to give users a way to check which extras are present without triggering these deferred `ImportError`s — it wraps each probe in its own `try/except ImportError`.

## Q4: `cmd_run` supports two mutually-exclusive execution paths: a bare script, or `--spec` + `--message`. What happens if a user passes both `--spec` and a positional `script`, or neither?

Looking at `cmd_run` (line 38): it checks `args.spec is not None` first. If `--spec` is given, it builds an agent from the spec and ignores `args.script` entirely — a user who passes both a `script` positional and `--spec` will have the script silently ignored, with no warning that it was never used. That's a real usability gap: `argparse` doesn't declare these as `add_mutually_exclusive_group()`, so nothing stops the user from passing both, and there is no code path that rejects the combination or even mentions it. If neither is given, `args.spec is None` and `if not args.script` is true, so it raises `SystemExit("foundry run needs either a script or --spec")`, which `argparse`'s own `nargs="?"` on `script` (line 163) makes possible — `script` is optional at the parser level specifically to allow the `--spec`-only invocation. Also worth noting: `--spec` requires `--message` (line 40-41, `if not args.message: raise SystemExit(...)`), but that's an imperative runtime check, not something `argparse` itself enforces (e.g. via `required=True` conditional on another flag), so the failure mode is a `SystemExit` with a decent message rather than an `argparse` usage error — slightly less discoverable via `--help`.

## Q5: `cmd_run`'s bare-script path does `subprocess.call([sys.executable, args.script])` instead of importing and executing the script in-process like `cmd_eval` does via `_load_module`. Why the inconsistency, and what does each choice cost?

The bare-script path runs a scaffolded `agents/<name>.py` file whose `if __name__ == "__main__": main()` block starts an interactive `chat_loop` (see `scaffold.py`'s `_AGENT_TEMPLATE`) — that's meant to take over the terminal exactly as if the user typed `python agents/sales_agent.py`, complete with its own `sys.path` manipulation, its own `ANTHROPIC_API_KEY` check, and a blocking `input()` loop. Running it as a subprocess isolates its `sys.path` hacks, global state, and any `sys.exit()` calls from `foundry`'s own process — a crash or `SystemExit` inside the script becomes a clean subprocess exit code (`raise SystemExit(subprocess.call(...))` at line 51 forwards it), not a corrupted CLI process. `cmd_eval`'s `_load_module` (line 19), by contrast, needs to reach into the executed module's namespace afterward (`getattr(module, args.agent_attr, None)`) to grab the `Agent` object and actually call `run_eval` on it in-process — a subprocess can't hand back a live Python object across the process boundary, so `importlib` module-loading is the only option there. The cost of the subprocess approach is that `cmd_run --spec` (the declarative path) and the bare-script path have completely different execution semantics and error surfaces, which is a little surprising for two branches of the same subcommand.

## Q6: What happens if `foundry eval` is pointed at a script whose top-level attribute name doesn't match `--agent-attr`'s default of `"agent"`?

`cmd_eval` (line 54) does `agent = getattr(module, args.agent_attr, None)` and then `if agent is None: raise SystemExit(f"{args.script!r} has no top-level `{args.agent_attr}` — pass --agent-attr to name it")`. This is a deliberately defensive check with a self-documenting error message — rather than letting a raw `AttributeError` propagate (which `getattr` without a default would do), it uses `getattr(..., None)` plus an explicit `None` check so the failure mode names exactly which flag fixes it. One subtlety: if the script legitimately defines `agent = None` on purpose (unlikely, but possible during a refactor), this code treats that identically to "attribute missing" and gives a misleading error message — a `hasattr()` check would distinguish "missing" from "present but None," but the current code doesn't need to make that distinction for its actual use case.

## Q7: Explain the two different "versioned vs. flat" dataset code paths inside `cmd_eval`, and why `--baseline`/`--save-baseline` are only compatible with one of them.

`cmd_eval` loads `raw = json.loads(...)` and branches on `EvalDataset.looks_versioned(raw)`. A versioned dataset is a JSON object shaped `{"name": ..., "version": ..., "cases": [...]}"`, wrapped into an `EvalDataset` object so `dataset_name`/`dataset.version` exist as identity for a baseline lookup. A flat dataset is just a bare JSON list of case dicts, parsed straight into `[EvalCase(**case) for case in raw]` with no name/version identity beyond the file's own stem (`Path(args.dataset).stem`, line 71). `--baseline` and `--save-baseline` need a `(name, version)` key to look up or store a `Scorecard` against (`EvalDataset.load_baseline(args.baseline, dataset.name, dataset.version)`), so both branches explicitly guard `if dataset is None: raise SystemExit(...)` — a flat list has no stable identity across runs (today's stem-derived name could collide with an unrelated file, or the same logical dataset could be renamed and silently "lose" its baseline history), so the CLI refuses rather than silently keying baselines off a filename that isn't guaranteed stable.

## Q8: How would you compare this CLI's design to a `click`/`typer`-based CLI, and why did the author choose raw `argparse` instead?

`click`/`typer` give you declarative option parsing via decorators, automatic `--help` generation with richer formatting, and built-in support for things like mutually-exclusive option groups, but they're an extra runtime dependency for a framework whose entire pitch (per `serve.py`'s and `cli.py`'s own docstrings) is minimal external dependencies and "nothing here that isn't composition over something that already exists." `argparse` is stdlib, so `foundry` works with zero extra installs, consistent with how `_EXTRAS` frames everything else (`fastapi`, `uvicorn`, etc.) as opt-in. The cost is exactly what Q4 and Q9 highlight: `argparse` doesn't give you `--spec`/`script` mutual exclusivity or conditional-required flags for free, so the module has to hand-roll those checks as imperative `if` statements with `SystemExit`, which is more verbose and easier to get subtly wrong (as the untested `--spec` + `script` combination shows) than `click`'s `mutually_exclusive_group` or `typer`'s type-driven validation.

## Q9: `cmd_serve` inspects the loaded script for either a top-level `app` or a top-level `graph` attribute. Walk through both branches and explain why this dual-attribute convention exists instead of requiring one canonical name.

`cmd_serve` (line 102) does `app = getattr(module, "app", None)`; if that's `None`, it falls back to `graph = getattr(module, "graph", None)` and, if that's also `None`, raises `SystemExit`. If a `graph` is found, `cmd_serve` builds an `app` on the fly via `serve.build_http_app(graph, allow_unauthenticated_demo=args.allow_unauthenticated_demo)`. This dual convention accommodates two different user postures: someone who wants full control over auth, extra routes, or middleware builds their own FastAPI `app` (potentially by calling `build_http_app` themselves with a real `AuthResolver` and additional custom routes) and exports it as `app`; someone who just wants "point foundry at my compiled graph and get a demo server" exports the bare `graph` and lets the CLI wire the batteries-included, `allow_unauthenticated_demo`-gated app for them. Requiring one canonical name would force every user down the same path — either always hand-rolling a FastAPI app (bad for the quick/demo case) or always taking the CLI's opinionated defaults (bad for anyone doing real multi-tenant auth, per `serve.py`'s own extensive docstring on `AuthResolver`).

## Q10: What is `--allow-unauthenticated-demo` for, and what security posture does it override? Trace it through to `serve.py`.

The flag is passed straight through to `serve.build_http_app(graph, allow_unauthenticated_demo=args.allow_unauthenticated_demo)` only in the `graph`-fallback branch of `cmd_serve` — if the script already exports its own `app`, the flag is silently ignored (the comment on `p_serve`'s help text says this explicitly: "the script's `app` (if it built one with its own auth already wired in) is used as-is regardless"). Inside `build_http_app`, if neither an `auth` resolver nor `allow_unauthenticated_demo=True` is provided, the function raises `ValueError` rather than defaulting to an open, unauthenticated server — this is a deliberate secure-by-default posture ("a governed serving surface should not default to trusting a client-supplied identity"). The CLI's `p_serve` help text calls the flag name "deliberately loud so it can't be set by accident," which matters because `cmd_serve` has no way to construct or point at a real `AuthResolver` from the command line at all — CLI-driven serving is inherently demo/local-dev-only unless the script itself builds and exports a fully-authenticated `app`.

## Q11: `cmd_trace` reads a JSONL file, splits non-blank lines, takes the last `n`, and re-serializes each with `json.dumps(json.loads(line))`. Why round-trip through `json.loads`/`json.dumps` instead of just printing the raw line?

Re-parsing and re-serializing normalizes formatting (consistent key ordering isn't guaranteed, but whitespace/quoting is) and — more importantly — validates that each of the last `n` lines is actually well-formed JSON before printing it; a raw `print(line)` would happily echo a corrupted or partially-written line (e.g. a process killed mid-`write()` on the last log line) without any signal that something's wrong. The tradeoff is that a single malformed line among the last `n` will raise an uncaught `json.JSONDecodeError` and kill the whole `trace` command with a traceback rather than printing what's readable and warning about the rest — there's no per-line `try/except` here, so `foundry trace` is not resilient to a truncated tail write, which is a realistic failure mode for a log file being actively appended to by a running process.

## Q12: What's a limitation of `cli.py` you'd fix given more time?

The most concrete one is the missing `argparse` mutual-exclusion/validation between `cmd_run`'s `--spec` and positional `script` args (Q4) — right now the failure mode for "user passed both" is silent, not an error, which is exactly backwards from a CLI's job of catching user mistakes early. A close second is that `cmd_init`'s subparser doesn't expose `--topology` even though `scaffold.create_agent` accepts it and `scaffold.py`'s own standalone `_main()` does expose it — meaning `python -m agent_foundry.scaffold` and `foundry init` are not actually equivalent entry points despite `cli.py`'s docstring implying `cmd_init` is a full wrapper over `scaffold.create_agent`. Both are small, but for a CLI whose entire value proposition is being a faithful, unsurprising composition layer over the library, any place where the two entry points diverge undermines that promise.

## Q13: Why does `cmd_eval`'s `--thresholds` argument take a raw JSON string on the command line instead of, say, a path to a thresholds file or individual `--min-success-rate`-style flags?

A raw JSON string (`json.loads(args.thresholds)` at line 94, passed to `scorecard.passes(...)`) keeps the CLI's surface area proportional to `Scorecard.passes()`'s own signature — whatever keys that method accepts (e.g. `task_success_rate_min`) are automatically available on the CLI with zero code changes if `Scorecard.passes()` grows new threshold keys, because `cli.py` never enumerates them. The cost is CLI ergonomics: a user has to know `Scorecard.passes()`'s keyword names and hand-write JSON on a command line (quoting is finicky in shells, as the help text's own escaped example `'{"task_success_rate_min": 0.9}'` shows), rather than getting `--help`-documented, tab-completable individual flags. This is the same "composition over reimplementation" tradeoff as Q1 — the CLI author chose not to duplicate `Scorecard`'s threshold vocabulary into `argparse` flags.

## Q14: How does `foundry inspect` determine which optional extras are installed, and what's a subtle correctness issue with that approach?

`cmd_inspect` (line 129) iterates the `_EXTRAS` tuple of `(label, module_name)` pairs and does `importlib.import_module(module_name)` inside a `try/except ImportError`, printing `[x]`/`[ ] ... not installed` accordingly. The subtlety: `import_module` actually executes the module's top-level code, not just checks for its presence on disk — for most well-behaved packages this is harmless and fast, but it means `foundry inspect` has the side effect of actually importing (and thus running any import-time side effects of) every optional dependency it checks, every time it's run. For a package with heavyweight or side-effecting imports (initializing a client, reading environment variables, spawning a thread), this check is more expensive and less "pure" than, say, `importlib.util.find_spec(module_name) is not None`, which would check installability without executing the module.

## Q15: If `agent_foundry`'s package `__version__` doesn't exist or the package is only partially installed, what happens when a user runs `foundry inspect`?

`cmd_inspect` does `from . import __version__` at the top of the function body (line 129-130) — if `agent_foundry/__init__.py` doesn't define `__version__`, this raises an `ImportError` that is NOT caught (the `try/except ImportError` in this function only wraps the per-extra `importlib.import_module` calls in the loop below, not this import). So a broken or unusual install would surface as an uncaught traceback for `foundry inspect` specifically, which is somewhat ironic for the one subcommand whose entire purpose is diagnosing the health of an install — a more defensive version might catch that too and print "version: unknown" rather than crashing.

## Q16: Compare `foundry serve`'s composition model to LangServe's. What's fundamentally different about the deployment surface it produces?

LangServe auto-generates a full OpenAPI-documented REST API (with `/invoke`, `/stream`, `/batch`, playground UI, and schema introspection) directly from a Runnable's input/output types, using Pydantic models it infers. `foundry serve` / `serve.build_http_app` instead exposes a fixed, hand-written four-route surface (`/`, `/chat`, `/resume`, `/health`) regardless of what the underlying graph's state schema looks like — there's no automatic OpenAPI generation from the graph's `AgentState`, no streaming endpoint, and no batch endpoint. This is a much smaller, more opinionated surface purpose-built for the framework's own chat + human-in-the-loop-approval interaction pattern (see `serve.py`'s `ChatRequest`/`ResumeRequest`/`ChatResponse` models), rather than a generic "serve any Runnable" tool. The tradeoff: `foundry serve` gives you a working, authenticated (if configured), approve/deny-capable chat server in one function call with no schema work, but it's not a general-purpose serving framework — anything beyond chat-turn + approval (streaming tokens, batch scoring, custom endpoints) requires bypassing `build_http_app` and writing your own FastAPI app, which `cmd_serve`'s `app`-attribute fallback (Q9) explicitly supports.

## Q17: If a user runs `foundry run some_script.py` and that script raises an unhandled exception before printing anything, what does the CLI's exit behavior look like, and is that intentional?

Since `cmd_run`'s bare-script branch uses `subprocess.call([sys.executable, args.script])` and wraps the return code in `raise SystemExit(...)` (line 51), an unhandled exception inside the script prints its own traceback to stderr (because the subprocess's own Python interpreter handles it, unbuffered, same as running the script directly) and exits with Python's standard `1` exit code for an uncaught exception; `foundry` then re-raises that as `SystemExit(1)`. This is effectively identical to what the user would see running `python some_script.py` directly — which is the intended behavior given the design rationale in Q5 (subprocess isolation specifically to make `foundry run` transparent/pass-through for scaffolded scripts). The one difference a user might notice is that `foundry`'s own process wraps the exit code, so `$?` after `foundry run` reflects the subprocess's code correctly, but any signal-based termination (e.g. Ctrl-C mid-script) is reported by `subprocess.call`'s return semantics (negative for signals on POSIX) fed straight into `SystemExit`, which Python will coerce oddly if the value isn't a small int or string — a minor, unlikely-but-real edge case.
