# agent_foundry/core/agent.py — Q&A

The framework's public entry point: `Agent` wraps one `AgentConfig` behind a runtime-agnostic surface (`run`/`stream`/`resume`/`as_tool`/`serve`), `_CompiledWorkflow` is the shared invoke/stream/resume adapter over either a compiled LangGraph graph or `native_engine._NativeGraph`, and `Workflow` holds the multi-agent topology factories (supervisor/swarm/blackboard/debate/fanout/dag) that take several `AgentConfig`s instead of fitting Agent's single-config constructor.

## Q1: `Agent.__init__` runs five separate validation checks before building anything. Walk through them in order, and explain what happens if you call `Agent("x", "y", workflow="supervisor")`.

In order (lines ~397–410): (1) `workflow != "react"` raises immediately, telling the caller to use `Workflow.supervisor/.swarm/...` instead — `Agent("x", "y", workflow="supervisor")` fails here with a `ValueError` before touching `runtime`, `llm`, or `provider` at all, because `Agent` only ever constructs the single-`AgentConfig` react topology; multi-agent topologies are static methods on `Workflow`, not a constructor argument. (2) `runtime not in RUNTIMES` — checked against the live `RUNTIMES` dict from `core/engines.py`, not a hardcoded tuple, so a third registered backend is automatically valid here with zero changes to this file. (3) `runtime == "native" and checkpointer is not None` — native keeps its own in-memory per-thread dict and has no concept of an external checkpointer. (4) `llm is not None and provider is not None` — mutually exclusive, because `llm=` is a fully-built `LLMGateway` and `provider=` is a hint to construct a *new* one; passing both is ambiguous about which wins, so it's rejected rather than silently preferring one. (5) `provider is not None and provider not in PROVIDERS` — fails fast with the actual set of valid vendor names rather than deferring to a `KeyError` inside `PROVIDERS[provider]()`. The ordering matters: the workflow check goes first because it's a completely different construction path, then runtime validity, then the runtime/checkpointer interaction, then the LLM-selection checks last, since they're independent of the earlier decisions.

## Q2: `Agent._runner_for` lazily builds and caches a `_CompiledWorkflow` per runtime name. Trace what happens when you construct `Agent(..., runtime="native")` and then call `.run(msg, runtime="langgraph")` — is this actually safe, and what state do the two calls share?

At construction (line ~438), only `self._runners = {"native": _CompiledWorkflow(native_graph)}` exists. Calling `.run(msg, runtime="langgraph")` goes through `_runner_for("langgraph")` (line ~447), which isn't in `self._runners` yet, so it looks `"langgraph"` up in `RUNTIMES`, builds a **brand new** LangGraph graph via `RUNTIMES["langgraph"].build(self.config, checkpointer=self._checkpointer if name != "native" else None)`, caches it, and returns it. This is safe in the sense that it won't crash, but the two runtimes do **not** share conversation state: `native`'s `NativeEngine` keeps state in an in-process dict keyed by `thread_id`, while `langgraph`'s graph keeps state in its own checkpointer (default in-memory `MemorySaver`-equivalent). Even though both calls might resolve to the *same* `thread_id` via `ExecutionContext.resolved_thread_id()`, the two engines have entirely separate storage, so switching `runtime=` mid-conversation silently starts a second, disconnected thread of history under the same `thread_id` — a real footgun if a caller assumes `runtime=` is just a performance knob with no state implications.

## Q3: `_CompiledWorkflow.astream()` implements a manual worker-thread + `asyncio.Queue` bridge instead of `asyncio.to_thread(lambda: list(self.stream(...)))`. Why, concretely?

The simpler `asyncio.to_thread` approach would run the **entire** synchronous generator to exhaustion inside the thread pool before returning anything — the caller's `async for chunk in agent.astream(...)` wouldn't see the first chunk until the whole turn (potentially several LLM calls and tool executions) had already finished, defeating the purpose of streaming. The actual implementation (lines ~252–273) starts a daemon `threading.Thread` running `worker()`, which iterates `self.stream(message, context=context)` (the native engine's real per-step generator) and pushes each chunk onto an `asyncio.Queue` via `loop.call_soon_threadsafe`, with a sentinel object `_DONE` marking completion and an `error` list used to re-raise any exception on the event-loop side rather than swallowing it. The `await queue.get()` loop then yields each item as soon as it's queued, giving genuinely incremental delivery. The cost is complexity and one un-joined daemon thread per `astream()` call; if the caller's `async for` loop is abandoned early (e.g., via `break` or a cancelled task) before `_DONE` arrives, the worker thread keeps running to completion in the background — nothing joins or cancels it, since Python has no clean way to preempt a synchronous generator from outside. This is an unacknowledged resource-leak edge case: the thread eventually exits on its own (the turn finishes), but it isn't cleaned up eagerly.

## Q4: Why does `_request_identity_dict` return `None` instead of a dict with empty/None fields when the caller's `ExecutionContext` has no `user_id`/`tenant_id`/`permissions`?

Because `state["request_identity"]` is only set in `_initial_state` when the returned value `is not None` (line ~187), and the reasoning is spelled out directly in the comment: "omitting the key on a continuing thread must not reset an earlier turn's resolved identity to 'none'." If this function always returned `{"id": "unknown", "tenant_id": "", "roles": ()}` for an unset context, then every subsequent turn on the same thread that didn't explicitly repeat identity information would overwrite whatever identity a prior turn resolved (via `orchestration._resolve_identity`) with an empty one — silently de-authenticating a long-running conversation. Returning `None` and skipping the key entirely lets the downstream `_resolve_identity` fall back to whatever was already in state from an earlier turn. This is the same pattern `ExecutionContext.to_request_state()` uses for every other override field (budget, deadline, tool_policy, etc.) — "only includes fields the caller actually set."

## Q5: `_coerce_memory` raises `TypeError` for anything that isn't `None` or doesn't satisfy the `Memory` protocol, rather than silently constructing a fresh `MemoryStore()`. Why is failing loudly the right call here specifically?

The comment on lines ~109–112 states it directly: a caller who passes the wrong type for `memory=` — say, a plain dict, or an object that looks *almost* like a `MemoryStore` but is missing methods — needs to know immediately, by name, what they actually passed. Silently substituting a brand-new empty `MemoryStore()` would produce an agent that runs without error but has "amnesia" from turn one, with no exception or log line pointing at the actual mistake; the user would spend far longer debugging "why does my agent not remember anything" than they would fixing a `TypeError: memory= must be a MemoryStore (or satisfy the Memory protocol), got <type>` raised at construction time. This is a deliberate contrast with `_coerce_tools`, where `None` and unrecognized-but-callable inputs are actively coerced (via `_toolspec_from_callable`) rather than rejected — tools have an unambiguous default conversion path (a bare function becomes a `ToolSpec`), whereas an unrecognized `memory=` object has no safe default other than "this is probably a mistake."

## Q6: `_toolspec_from_callable`'s type-name mapping only covers `str`, `int`, `float`, `bool`. What happens if a tool function's parameter is annotated `list[str]`, `dict`, or left unannotated, and is that a real limitation?

`type_names.get(p.annotation, "string")` (line ~87) falls back to `"string"` for anything not in that four-entry dict — an unannotated parameter (`inspect.Parameter.empty` as the annotation), a `list[str]`, an `Optional[int]`, or a custom class all get silently typed as `"string"` in the generated `ToolSpec.parameters` schema. This is a genuine limitation for the "type hints + docstring become schema" convenience path (mirrored from `quickstart.py`): a tool author who annotates a parameter `count: int` gets a correct `"integer"` schema, but one who annotates `items: list[str]` gets a schema that tells the LLM to pass a string, likely producing malformed tool-call arguments the tool then has to defensively parse. The workaround already available in the same function — passing an explicit `ToolSpec` with a real `parameters` dict — bypasses this entirely; this shorthand path is meant for simple scalar-argument tools only, and that constraint isn't enforced or even warned about anywhere.

## Q7: The `_ResumePayload` dataclass here is a near-verbatim duplicate of the one in `core/engines.py`. Why isn't it defined once and imported?

`core/agent.py` and `core/engines.py` are explicitly separate, parallel implementations of the same "compiled workflow" idea — `core/agent.py`'s `_CompiledWorkflow` is a higher-level convenience wrapper that itself calls into whichever engine `RUNTIMES[runtime].build()` produced, while `core/engines.py`'s `LangGraphWorkflowEngine`/`NativeWorkflowEngine` are the lower-level `WorkflowEngine` protocol implementations `_CompiledWorkflow` could in principle be built without. Both need the identical trick — a lightweight object exposing exactly a `.resume` attribute so `native_engine._NativeGraph.invoke()`'s `getattr(state_or_command, "resume", None)` duck-typing check succeeds without ever importing `langgraph.types.Command` — but sharing one canonical `_ResumePayload` class would create an import dependency between two modules whose whole point (per the module docstrings) is to have zero import-time coupling in either direction. The real cost of the duplication is that if the resume payload's shape ever needs to grow a new field or change its semantics, both copies must be updated in lockstep, and nothing in the codebase enforces that they stay identical beyond code review discipline.

## Q8: Compare `Workflow.supervisor`'s `fallback_agent=None` default to how a naive supervisor implementation might handle an unrecognized routing decision. Why "fail closed"?

The docstring at lines ~556–561 is explicit: an LLM-driven router occasionally returns a specialist name that doesn't match any key in `agents` (typos, hallucinated names, ambiguous prompts). The unsafe naive approach — silently falling back to `list(agents)[0]` — is exactly the *previous* behavior the comment calls out as "unsafe once specialists carry different tool/permission scopes": if specialist A has broad filesystem access and specialist B is sandboxed read-only, silently routing a misrouted request to whichever agent happens to be first in dict-iteration order could hand overly broad tool access to a request the router never actually intended for that agent. `fallback_agent=None` (the default) means `orchestration._resolve_supervisor_route` retries the routing decision once, then raises `SupervisorRoutingError` if it still can't resolve — failing the request outright rather than guessing. A caller who explicitly wants degraded-but-available behavior can opt in by naming a specific, deliberately-chosen `fallback_agent`.

## Q9: `Workflow`'s topology factories validate `runtime` via `_validate_workflow_runtime`, which hardcodes `if runtime not in ("native", "langgraph")`, while `Agent.__init__` validates against the live `RUNTIMES` dict. Is this an inconsistency, and what breaks if you add a third runtime?

Yes — this is a genuine asymmetry. `Agent.__init__` and `Agent._runner_for` both check membership in `RUNTIMES` (core/engines.py's registry), so registering a third engine there — say `RUNTIMES["temporal"] = TemporalWorkflowEngine()` — makes `Agent(..., runtime="temporal")` work with **zero** changes to `core/agent.py`, exactly as the module docstring promises ("adding a third backend... means implementing WorkflowEngine and adding one RUNTIMES entry, not touching core/agent.py"). But `_validate_workflow_runtime` (line ~535) is a literal tuple check, completely independent of `RUNTIMES`, so `Workflow.supervisor(..., runtime="temporal")` would raise `ValueError: runtime must be 'native' or 'langgraph'` even after registering the new engine — because none of the `Workflow.*` factories dispatch through `RUNTIMES` at all; they hand-branch on `if runtime == "native": ... else: ...` and call `_NativeSupervisorGraph`/`build_supervisor_graph` directly. Extending multi-agent topologies to a third backend therefore requires editing `core/agent.py` (both the validator and every `Workflow.*` method's if/else), which directly contradicts the "extension point" claim the module docstring makes for `RUNTIMES` — that claim is true for single-agent `Agent`, but not for `Workflow`.

## Q10: `_FanoutWorkflow` and `_DagWorkflow` don't inherit from or reuse `_CompiledWorkflow`. Why does the framework need two additional wrapper classes instead of forcing everything through one shape?

`_CompiledWorkflow`'s entire public surface (`run(message, ...)`, `_initial_state`, `resume`, `batch`, `as_tool`) is built around a specific state shape: `{"messages": [...], "thread_id": ...}`, because that's what `build_agent_graph` and every conversational multi-agent topology (supervisor/swarm/blackboard/debate) actually operate on. `build_fanout_graph`'s state is `{"items": [...], "messages": [...], "thread_id": ...}` — it dispatches N items concurrently rather than looping one conversation — so `_FanoutWorkflow.run(items: list[str])` (line ~341) takes a list, not a single message, and returns `[m["content"] for m in raw.get("messages", [])]` rather than a `RunResult`. `build_dag_graph`'s state is just `{"results": {...}}` with no messages/thread_id/content notion at all, so `_DagWorkflow.run(inputs)` (line ~360) returns the raw `results` dict directly. Forcing these into `_CompiledWorkflow`'s `run(message)` signature would mean either lying about what the call actually does (pretending a list of items is "a message") or padding the API with parameters that are meaningless for these two topologies — the two dedicated thin wrapper classes are honest about what each topology's `invoke()` actually consumes and returns, at the cost of `Agent`/`Workflow`'s public surface not being perfectly uniform across all six topologies.

## Q11: Trace exactly what happens if `_CompiledWorkflow.stream()` is called against a LangGraph-compiled graph vs. a `native_engine._NativeGraph`, focusing on `stream_mode="values"`.

Both paths call `self._graph.stream(state, {"configurable": {"thread_id": thread_id}}, stream_mode="values")` identically (line ~229) — there's no branching in `_CompiledWorkflow.stream()` itself, which is the whole point per the module's design. On a real LangGraph graph, `"values"` mode (LangGraph's non-default option; its own default is `"updates"`, which yields per-node partial dicts like `{"think": {...}}`) yields the **full accumulated state** after every graph step. On `_NativeGraph.stream()` (native_engine.py, line ~553), `stream_mode` is accepted only via `**kwargs` and silently ignored — the method unconditionally yields `NativeEngine.stream_run`'s output, which was deliberately built (per native_engine.py's own docstring) to match that exact "full state after every think/act/critique step" granularity empirically observed from LangGraph. The comment on lines ~218–225 calls this out directly: the two engines "actually agree on a chunk shape now, not just by accident" — meaning someone had to verify LangGraph's real streaming behavior first (documented as confirmed via `tests/test_workflow_engine_protocol.py`) and then hand-build the native engine to match it, rather than the two independently happening to line up.

## Q12: How would you unit-test `Agent`'s runtime dispatch without spinning up a real LLM provider or a real LangGraph installation?

Because `Agent.__init__` resolves the actual engine purely through `RUNTIMES[runtime].build(self.config, checkpointer=checkpointer)` (line ~438) and `RUNTIMES` is a plain importable dict in `core/engines.py`, a test can monkey-patch or substitute an entry in `RUNTIMES` with a fake object implementing the four-method `WorkflowEngine` protocol (`build`/`run`/`stream`/`resume`) that returns canned dicts, entirely bypassing both LangGraph and any real LLM call — `Agent` itself never imports LangGraph or an LLM provider directly, it only touches `self.config.llm` (an `LLMGateway`, itself swappable with a fake provider via `llm=`) and the `RUNTIMES` registry. This is precisely the value of the seam the module docstring calls out: testing `Agent`'s validation logic, runtime-caching behavior (`_runner_for`), and public-method dispatch is decoupled from testing either concrete engine's actual execution semantics, which get their own dedicated test suites elsewhere.

## Q13: Compare this design to how CrewAI wires up a `Crew`/`Process` or AutoGen wires a `GroupChatManager`. What's the key structural difference in how Agent Foundry composes multi-agent topologies?

CrewAI's `Crew` and AutoGen's `GroupChat`/`GroupChatManager` are themselves the orchestration primitive — you construct a `Crew(agents=[...], process=Process.hierarchical)` or a `GroupChat(agents=[...])`, and the library's own internal scheduler decides turn order, typically hardwired to one control-flow strategy per class. Here, `Workflow.supervisor/.swarm/.blackboard/.debate/.fanout/.dag` are separate static factory methods, each producing a `_CompiledWorkflow` (or `_FanoutWorkflow`/`_DagWorkflow`) that wraps an underlying compiled graph — and critically, each topology has **two independent implementations** of its control flow (a LangGraph `StateGraph` version in `orchestration.py`, and a from-scratch Python version in `core/native_orchestration.py`), selected via `runtime=`. The `Agent` objects passed into `Workflow.supervisor(agents={...})` only ever contribute their `.config` (an `AgentConfig`) — the topology never holds a reference to another `Agent` instance's compiled graph, engine, or event bus. This means the "same" specialist agent can be reused unmodified across multiple topologies (or standalone) since only its configuration, not its runtime state, is shared — a cleaner separation than CrewAI's typical model where an `Agent` instance is more tightly bound to the `Crew` it's a member of.

## Q14: `Agent.batch`, `.schedule`, `.as_tool`, and `.serve` all delegate to `self._runner` — the construction-time default runtime — with no `runtime=` override parameter, unlike `.run`/`.arun`/`.stream`/`.astream`/`.resume`/`.aresume`. Is this an oversight?

It's a real asymmetry, though arguably a defensible one rather than a pure oversight. `run_batch` (in `batch.py`, invoked via `_CompiledWorkflow.batch`) and `IntervalScheduler.schedule` (via `_CompiledWorkflow.schedule`) both operate against one fixed compiled graph reference captured at `_CompiledWorkflow.__init__` time; supporting a per-call `runtime=` override for these would mean re-resolving which cached `_CompiledWorkflow` in `self._runners` to batch/schedule against on every call, which the single-call methods (`run`, `resume`, etc.) already do via `_runner_for(runtime)` but batch/schedule never adopted. Similarly, `as_tool` binds a specific compiled graph into a `ToolSpec` via `orchestration.agent_as_tool(graph=self._graph, ...)` at call time — exposing a runtime-overridable version would mean the resulting tool's behavior could vary per invocation based on which runtime the caller happened to specify when they called `.as_tool()`, which is a strange contract for a tool that's supposed to have one fixed identity once handed to another agent. The net effect: if you construct `Agent(..., runtime="native")` and want a `langgraph`-backed batch run, you must call `agent.run(msg, runtime="langgraph")` in a loop yourself, or construct a second `Agent` with `runtime="langgraph"` — `.batch()` offers no shortcut.

## Q15: `_default_policy` builds a `Policy(allowed_tools=frozenset(tool_names))` from whatever tools were registered, and this becomes `resolved_policy` used to construct both `GuardrailEngine` and `RunBudget` when the caller didn't pass their own `policy=`. What's the security implication of this default?

The default policy is exactly as permissive as "every tool the caller registered is allowed" — there's no default *denial* of any registered tool, no default cost cap beyond whatever `RunBudget(resolved_policy)` derives, and no default distinction between safe and destructive tools at the policy level (that distinction is enforced per-call later, via each `ToolSpec.destructive` flag feeding into the PDP's `decide()` call inside `_act`, not via `Policy` itself). This means the out-of-the-box `Agent(name, instructions, tools=[dangerous_tool])` with no explicit `policy=` will let the agent call `dangerous_tool` freely — the framework trusts that a caller who registers a tool intends for the agent to be allowed to use it, and pushes finer-grained gating (approval requirements, destructive-action confirmation, cost thresholds) onto the PDP/guardrail layer rather than onto this default `Policy` construction. A security-conscious caller who wants tools registered-but-not-default-allowed must construct and pass an explicit, narrower `Policy` themselves.

## Q16: What is a concrete limitation of this module you would fix given more time?

The `Workflow`/`Agent` runtime-validation asymmetry from Q9 is the clearest one: `Workflow.*`'s hardcoded `("native", "langgraph")` tuple check in `_validate_workflow_runtime` should instead validate against a registry analogous to `RUNTIMES` but scoped to topology builders — something like `TOPOLOGY_RUNTIMES: dict[str, TopologyEngine]` mapping runtime names to objects exposing `build_supervisor`/`build_swarm`/etc., mirroring how `core/engines.py`'s `RUNTIMES` already decouples `Agent` from hardcoding two engines. As written, adding a genuinely new backend for multi-agent topologies requires touching six near-identical if/else blocks inside `core/agent.py`'s `Workflow` class, which is exactly the kind of "if/else special case" the module docstring's stated design philosophy (for `Agent` itself) explicitly tries to avoid.

## Q17: `_CompiledWorkflow.arun()` picks between a genuinely async path (`self._graph.ainvoke(...)`) and `asyncio.to_thread(self.run, ...)` based on `hasattr(self._graph, "ainvoke")`. What if someone constructs a custom object that happens to define an `ainvoke` method but isn't actually a real LangGraph graph — say, in a test double for the native engine?

Because the discriminator is pure duck-typing (`hasattr`, not `isinstance` against any real LangGraph type), any object with a callable `ainvoke` attribute takes the "LangGraph-native async" branch and is awaited directly with `await self._graph.ainvoke(state, {"configurable": {"thread_id": thread_id}})`. If a test double defines `ainvoke` but doesn't actually implement the compiled-graph state/config contract correctly, `arun()` would happily call it and propagate whatever it returns (or raises) straight through `result_from_graph_output`. This is a deliberate simplicity trade-off consistent with the rest of the codebase's philosophy (`_NativeGraph` itself duck-types `.resume` on incoming payloads rather than checking a real `Command` type) — it makes swapping in fakes for testing trivially easy, at the cost of zero runtime protection against a malformed fake that defines the wrong attribute name coincidentally.

## Q18: `Agent.on(topic, ...)` both wires the agent's graph to an event bus via `events.wire_event_driven` AND separately subscribes the decorated function as a plain handler. Why do both, rather than just one or the other?

`wire_event_driven(graph=self.graph, bus=self.event_bus, topic=topic, thread_id_fn=thread_id_fn)` (line ~526) makes the *agent itself* react to the published event by turning the event dict into a triggered turn's user message — this is the "agent listens to a topic and responds" behavior. The `decorator` returned by `.on()` additionally calls `self.event_bus.subscribe(topic, handler)` for whatever plain function the caller decorates — this is a *second*, independent side effect the caller wants to run on every publish (e.g., logging, a metrics counter, forwarding to another system) that has nothing to do with triggering the agent's own graph. The docstring is explicit that "both run on every publish, decorator or not" — meaning `wire_event_driven` fires unconditionally as soon as `.on(topic)` is called (even before any function is decorated), and the decorated handler is purely additive. A caller who only wants the agent-reaction behavior without a custom side handler can call `agent.on("topic")` and simply discard the returned decorator, since Python allows calling a decorator factory without ever applying it to a function.
