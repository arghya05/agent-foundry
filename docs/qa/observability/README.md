# agent_foundry/observability.py — Q&A

Tracing (`Tracer`/`OTelTracer`), latency/error-rate metrics and threshold alerting (`Metrics`, `check_alerts`), and per-finished-task cost attribution (`CostLedger`) — the three pieces `orchestration.py` composes with via the swappable `TracerLike`/`CostLedgerLike` protocols to know what an agent run cost, how fast it was, and when something's wrong.

## Q1: `CostLedger` keeps `completed` and `incomplete` as two separate lists instead of one list with a status field. Why does that distinction matter, and what would break if you collapsed it?

The module docstring is explicit about the reasoning: real LLM spend already happened before a turn fails — a `BudgetExceeded`, an unhandled exception, or a timeout doesn't refund the two expensive tool-calling rounds that already billed. `close_task()` (called from `orchestration.py`'s `_finalize_turn` once a turn genuinely reaches `END`) and `close_incomplete()` (called by whatever catches a mid-flight failure) record into different lists precisely so "cost per completed task" — the number a billing dashboard wants — never gets a fantasy nudge either up or down from failed runs. If you collapsed them into one list with a status field, `cost_per_task()` (line ~197, `total_cost_usd() / len(completed)`) would either need to filter that field internally at every call site (easy to forget) or would silently under-report unit cost by diluting the "clean completion" denominator with runs that scored zero value. The two-bucket design also means `total_incomplete_cost_usd()` and `cost_per_incomplete_task()` exist as their own first-class queries — a real deployment can ask "how much am I burning on runs that never finish" as its own health signal, which a single merged list would bury inside an aggregate.

## Q2: Walk through exactly what happens, mechanically, when `Tracer.span("orchestration.act", tool=tool_name)` is used as a context manager in `_invoke_tool_call`.

`Tracer.span()` (observability.py line 33) is a `@contextlib.contextmanager` generator. On entry it builds a `record` dict with a fresh `span_id` (`uuid.uuid4().hex[:12]`), the tracer's `thread_id` as `trace_id`, the span `name`, and an `attributes` dict seeded from the kwargs (`{"tool": tool_name}` here). It captures `start = time.time()`, then `yield`s the record — the caller's `with` block runs, and in `orchestration.py`'s `_invoke_tool_call` that block calls `config.tools.invoke(...)` (via `with_timeout` if a timeout is set) and then mutates the yielded object with `span["attributes"].update(ok=result.ok, latency_ms=result.latency_ms)`. Because `record` is the *same dict object* handed to `spans.append()` in the generator's `finally` block, that mutation is visible after the `with` exits. The `finally` always runs — even if `call()` raises — computing `duration_ms` from the elapsed wall time, appending the record to `self.spans`, and immediately `print`ing it as one line of JSON (`json.dumps(record, default=str)`). So every span is both retained in memory (queryable via `Metrics`) and streamed to stdout as a structured log line — a cheap, dependency-free way to get both "query the run after the fact" and "tail live logs" from a single write.

## Q3: `_invoke_tool_call`'s docstring claims the span-inside-the-function placement is safe for concurrent tool dispatch "under the GIL." What exactly is the concurrency argument, and where would it break?

`_dispatch_tool_calls` in `orchestration.py` can run several `_invoke_tool_call` invocations concurrently on separate worker threads (a thread pool) when a turn has more than one cleared tool call. Every one of those threads calls `config.tracer.span(...)` on the *same* `Tracer` instance, and each span's `finally` does `self.spans.append(record)`. The safety claim rests on `list.append` being a single bytecode-level operation that CPython's GIL makes atomic — so concurrent appends from N threads can't corrupt the list or lose an entry, even with zero explicit locking in `Tracer`. That's real, but it's also the *only* thing that's thread-safe by accident rather than by design: nothing else in `Tracer` synchronizes multi-threaded access. `print()` itself is not guaranteed atomic across two full `json.dumps()` outputs the way a single `list.append` is — under enough concurrent throughput, interleaved `print` calls from different threads can (rarely, depending on buffering) interleave their bytes into a corrupted log line, even though the in-memory `self.spans` list stays consistent. And the safety argument evaporates entirely under `OTelTracer`, whose `span()` delegates to `self._tracer.start_as_current_span`, real OTel machinery with its own (separate) thread-safety guarantees — the GIL-append argument is specific to the plain in-memory `Tracer`, not a property of the `TracerLike` protocol in general.

## Q4: `Metrics.percentile()` computes p95 as `vals[min(len(vals)-1, int(len(vals) * p))]`. Is this a statistically correct percentile, and what happens at small sample sizes?

It's the nearest-rank method on a sorted list, not linear interpolation — for `p=0.95` and `len(vals)=20`, `int(20*0.95)=19`, which is the last index (`len-1`), i.e. the max. That's a legitimate (if coarse) percentile definition, but it means p95 on small samples is dominated by whichever single slow call happened to land there — with only 5 spans, `int(5*0.95)=4`, again the max, so "p95 latency" is literally just "the slowest call recorded," not a real tail statistic. This is honest as a lightweight dev-time metric but would be misleading as a production SLO gate without a much larger sample; `check_alerts` firing on `metrics.percentile(0.95) > 5000` for a thread with only 3-4 spans is really just an "was any single call slow" check wearing a percentile's clothing.

## Q5: `check_alerts` is described as "threshold-based alerting — swap for anomaly detection once you have volume." What's actually wrong with hardcoded thresholds (5000ms p95, 20% tool error rate, 80% of budget) as a long-term alerting strategy?

Fixed thresholds don't adapt to a workload's own baseline: an agent that's structurally slower (say, it always makes three sequential LLM calls) will permanently trip the 5000ms alert even when operating exactly as designed, while an agent that's usually fast but has one genuinely anomalous 4900ms spike sails under the same threshold and never alerts. The 20% tool error rate threshold has the same problem in the other direction — a tool that's *supposed* to fail on invalid input at, say, 15% (search-not-found is a normal outcome, not a bug) would never trigger this, while a tool with a real 100% failure rate over just 2-3 calls (small-sample noise) might. None of the three thresholds account for the number of underlying data points, workload type, or seasonal/traffic-shape baselines the way a real anomaly-detection system (e.g. rolling z-scores, EWMA, or a learned baseline per agent+environment) would. This is explicitly acknowledged in the docstring as a placeholder, appropriate for a first deployment or a demo, not a production SRE posture at scale.

## Q6: `OTelTracer`'s docstring calls out an "honest limit": `Metrics`, `check_alerts`, and `render_dashboard` don't work with it. Why not, and what does a caller actually need to do differently once they switch tracers?

`Metrics` and `render_dashboard` both read `tracer.spans` directly (a `list[dict]` attribute that only the plain `Tracer` class populates). `OTelTracer` doesn't keep that list at all — its `span()` method hands each span to `self._tracer.start_as_current_span(...)`, which under real OpenTelemetry semantics ships the span off to whatever `SpanProcessor`/exporter is configured (a `ConsoleSpanExporter` by default, or your own OTLP-backed processor to Jaeger/Honeycomb/Datadog). Keeping an in-process mirror of every span just to satisfy this module's own dashboard would defeat the entire point of using OTel — you'd be paying double storage and drifting between two representations of the same data. So the tradeoff is explicit and honest: swapping `Tracer` for `OTelTracer` in `AgentConfig.tracer` buys you a real, interoperable trace pipeline but means `Metrics(tracer).percentile(...)`, `check_alerts(...)`, and `render_dashboard(...)` all silently produce empty/zero output (`Metrics.latencies_ms` would iterate an empty or nonexistent `.spans`) rather than raising — a caller has to know to go query the actual collector backend (Jaeger UI, Honeycomb, whatever) instead of calling this module's in-process helpers. `total_cost_usd()` is the one thing `OTelTracer` *does* replicate correctly, by tracking `self._cost` inside `_OTelAttrs.update()` whenever a `cost_usd` attribute is set — but that only works if callers keep using the `span["attributes"].update(cost_usd=...)` idiom rather than setting it some other way.

## Q7: Explain `_OTelAttrs` and why `OTelTracer.span()` doesn't just yield a plain dict the way `Tracer.span()` does.

`orchestration.py`'s only contract with a tracer's yielded span object, per the `TracerLike` docstring, is `span["attributes"].update(**kwargs)` — that's the literal code in `_invoke_tool_call` and `make_think_node`. Plain `Tracer` satisfies this because its yielded `record` really is a dict with an `"attributes"` key holding a plain dict, so `.update()` just merges kwargs into it. Real OTel spans don't work that way — attributes are set one at a time via `otel_span.set_attribute(k, v)`, there's no bulk `.update()`, and there's no dict to hold them in application code (OTel owns that internally). `_OTelAttrs` is a small shim class whose own `.update(**kwargs)` method iterates the kwargs and calls `self._span.set_attribute(k, v)` for each — reproducing the *interface* `span["attributes"].update(...)` needs without reproducing OTel's internals. `OTelTracer.span()` then yields `{"attributes": _OTelAttrs(otel_span, self)}`, a one-key dict whose value is this adapter object — so `span["attributes"].update(cost_usd=..., model=...)` works identically to the plain-`Tracer` case from the caller's point of view, even though under the hood one line becomes N `set_attribute` calls plus (for `cost_usd` specifically) an accumulation into `self._tracer._cost`. This is the Adapter pattern in miniature, and it's also *why* `OTelTracer`'s yielded dict has no `trace_id`/`span_id`/`name` keys the way `Tracer`'s does — nothing in the actual calling code ever reads those from the span object (they're set as OTel attributes directly, via `otel_span.set_attribute("trace_id", ...)` and the span's own `name`), so the shim only needs to cover what's actually used.

## Q8: How would `Tracer`/`OTelTracer` compare to how a purpose-built system like Honeycomb, Datadog APM, or LangSmith solves the same tracing problem?

Structurally, `Tracer` (in-memory JSON spans, printed to stdout) is closer to "structured logging with span shape" than to a real distributed tracing system — it has no context propagation across process/service boundaries, no sampling strategy, no trace visualization, and its cost/latency queries (`Metrics`) are ad hoc Python over a Python list rather than a queryable time-series backend. `OTelTracer` closes most of that gap by delegating to the real `opentelemetry-sdk` — once wired to an OTLP exporter, it gets you actual distributed context propagation, standard span semantics, and a real backend's query/visualization layer (Jaeger, Honeycomb, Datadog, whatever you point `processor` at) for free. LangSmith specifically is a purpose-built LLM observability product: automatic prompt/completion capture, run trees for agent graphs, built-in eval dataset integration, and a hosted UI — none of which this module tries to replicate; `agent_foundry`'s tracer is intentionally minimal and generic (any span with `name`+`attributes`), leaving LLM-specific visualization to whatever backend you export to. The honest read is that `Tracer` is a zero-dependency, always-works reference implementation good for local dev/tests/demos, and `OTelTracer` is the "graduate to something real" path — but neither is a competitor to a hosted LLM-observability product on features; they're a shim that plugs into one.

## Q9: What happens if `render_dashboard` is called with a `budget` object that has `policy.max_cost_usd_per_thread = 0` (unlimited/unset budget)?

`render_dashboard` (line 213) formats `f"cost: ${budget.cost_usd:.4f} / ${budget.policy.max_cost_usd_per_thread} budget"` unconditionally — it doesn't guard against a zero or `None` budget, so it would print something like `$0.0032 / $0 budget`, which is misleading (reads as "already over budget by definition") rather than "no budget configured." Contrast this with `check_alerts`, which explicitly guards with `if max_cost_usd and budget_cost_usd > 0.8 * max_cost_usd` — the truthy check on `max_cost_usd` means a zero/falsy budget short-circuits and never fires the "within 80% of budget" alert. `render_dashboard` has no equivalent guard; it's a display function that assumes a sane budget was configured, whereas `check_alerts` was written defensively because a false alert is actively harmful (pages someone) while a slightly confusing dashboard line is merely cosmetic. This is a small but real inconsistency between the two functions' defensiveness.

## Q10: `CostLedger.by_tenant()` only aggregates over `self.completed`. Is that a bug or a deliberate choice, and what's the practical consequence?

It's consistent with the module's overall design choice to keep "completed" as the canonical basis for per-unit cost math (`cost_per_task()` does the same), but it does mean a tenant whose runs are disproportionately *failing* to complete (timeouts, budget blowouts) would show an artificially low `by_tenant()` total relative to what they're actually being billed for by the LLM provider — their incomplete-run spend simply isn't visible in this view. There's no `by_tenant()` equivalent over `incomplete`, so a caller building a real billing report has to remember to separately sum `incomplete` entries by `tenant_id` themselves if they want the true total; the API as given nudges you toward under-counting a struggling tenant's actual spend unless you know to look at both lists.

## Q11: The `CostLedgerLike` protocol docstring says a fleet-wide cost total "can't come from N replicas each holding their own independent `CostLedger`." Walk through why, and what a real production implementation would need.

`CostLedger` as written is a plain in-memory `dataclass` — `completed`/`incomplete` are Python lists that live in one process's heap. If you run N replicas of the agent service behind a load balancer, each replica gets its own `CostLedger` instance with only the tasks *that replica* happened to handle. Calling `.total_cost_usd()` or `.by_tenant()` on any single replica's ledger gives you that replica's slice of the fleet, not the fleet total — and there's no mechanism here to merge them (no shared state, no periodic flush, no aggregation endpoint). The `CostLedgerLike` protocol exists precisely so a real deployment can swap in something backed by shared storage (a Postgres table, a metrics backend like Prometheus counters, a Kafka topic feeding a rollup job) that implements the same seven methods (`close_task`, `close_incomplete`, `total_cost_usd`, `cost_per_task`, `total_incomplete_cost_usd`, `cost_per_incomplete_task`, `by_tenant`) but persists writes centrally — at that point `close_task()` becomes an INSERT or an atomic counter increment rather than a list append, and the read methods become aggregate queries instead of a `sum()` over an in-process list. The protocol is the seam; the actual distributed implementation is left as an exercise, honestly, since it's an infra choice (which DB, which consistency model) rather than something this module can prescribe.

## Q12: What's the actual failure mode if two threads call `close_task()` on the same `CostLedger` at the "same" wall-clock instant — is there a race, and does it matter?

`close_task()` does one `self.completed.append({...})` — a single dict construction followed by one list append. Dict construction happens entirely on the calling thread's own stack before the append, so there's no partial/torn write visible to another thread; and `list.append` is GIL-atomic in CPython, same argument as the `Tracer.spans` case. So no corruption risk. What *can* happen under concurrent completion is two entries getting essentially identical `ts` values (both `time.time()` at construction, not append time) — if a caller relies on `ts` ordering to reconstruct "which task finished first" for two genuinely concurrent completions, `time.time()`'s resolution (platform-dependent, often ~1ms or coarser) could make them appear simultaneous or even slightly out of true order relative to when `append` actually ran. That's a cosmetic ordering concern, not a data-integrity bug — `total_cost_usd()`/`cost_per_task()`/`by_tenant()` are all order-independent sums, so they're correct regardless.

## Q13: `Metrics.tool_error_rate()` filters `self.tracer.spans` for `s["name"] == "orchestration.act"`. What happens to this metric if `native_engine.py`'s tool-call spans use a different span name?

Grepping the codebase, `orchestration.py`'s `_invoke_tool_call` names its span `"orchestration.act"`, but `native_engine.py` has its own `"native.think"` span (and, by the same pattern, presumably its own act-equivalent span name for the native engine's tool dispatch). `tool_error_rate()` hardcodes the string `"orchestration.act"` — so if an agent is run under the native engine path rather than the LangGraph-based `orchestration.py` path, and its tool-call spans are named differently, `Metrics.tool_error_rate()` would silently return `0.0` (the `if not acts: return 0.0` early-exit) rather than erroring, because it simply finds no matching spans. That's a quiet blind spot: a caller monitoring tool error rate on a native-engine-driven thread via this `Metrics` class would see "0% error rate" when the real number could be anything, purely because of a span-name mismatch between the two execution paths. This is the kind of coupling-by-string-literal that's easy to miss in tests (which likely only exercise one engine) and would need either a shared constant for the span name or a name-pattern match (e.g. `.endswith(".act")`) to be robust across both engines.

## Q14: If you had to add a new tracer backend — say, shipping spans to Datadog APM directly — what exactly would you need to implement, and what could you get wrong?

You'd implement the `TracerLike` protocol: a `.span(name, **attrs)` context manager and a `.total_cost_usd()` method — that's the entire contract `orchestration.py` needs (per the protocol's own docstring, verified against real call sites in Q2/Q3 above). The two failure modes to avoid: first, whatever object your `span()` yields must support `span["attributes"].update(**kwargs)` — if you yield a raw Datadog span object without an `_OTelAttrs`-style adapter, the `.update()` call in `_invoke_tool_call`/`make_think_node` will raise `AttributeError` or `TypeError` immediately, since Datadog's span API doesn't have a bulk-update method either. Second, `total_cost_usd()` needs some way to actually accumulate `cost_usd` — Datadog's span API won't do that bookkeeping for you the way OTel attributes plus `_OTelAttrs._tracer._cost` do here; you'd need your own running total, exactly mirroring the pattern `_OTelAttrs.update()` uses (checking `if k == "cost_usd": self._tracer._cost += v`). Skipping that means `total_cost_usd()` silently returns `0.0` forever, which — because there's no assertion or warning anywhere in this module for an unimplemented cost accumulator — would be a very easy bug to ship undetected until someone notices the cost dashboard always reads zero.

## Q15: What's a limitation of this module you'd fix given more time?

The clearest one is `Metrics`/`check_alerts`/`render_dashboard` being tightly coupled to plain `Tracer`'s in-memory `.spans` list rather than to the `TracerLike` protocol — anyone using `OTelTracer` (the module's own recommended "real" tracer) loses all three, per Q6. A cleaner design would define an `AggregatableTracer` sub-protocol (or make `Metrics` accept any iterable of span-like records) so the same percentile/error-rate/dashboard logic could work against a small in-memory ring buffer that `OTelTracer` optionally also maintains alongside exporting to OTel — giving you both real interoperability *and* the in-process dashboard, instead of forcing a strict either/or. A second, smaller fix: `Metrics.percentile`'s nearest-rank calculation (Q4) should either document its small-sample unreliability more prominently or switch to linear interpolation, since "p95" as computed here is trivially just "the max" for any sample under ~20 spans, which is exactly the regime a single agent thread's tracer will usually be in.
