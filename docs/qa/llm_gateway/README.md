# agent_foundry/llm_gateway.py — Q&A

The unified LLM abstraction: `LLMGateway` routes a logical task ("default"/"cheap"/"hard") to a ranked list of models and fails over across them, sitting on top of vendor-specific `Provider` implementations (`AnthropicProvider`, `OpenAIProvider`) that each normalize requests/responses, meter cost via `PricingRegistry`, and translate between this codebase's provider-agnostic message shape and each vendor's native wire format.

## Q1: Walk through exactly what happens, step by step, when `LLMGateway.complete(messages, task="default")` is called and the first model in the route is rate-limited.

`complete()` (line 357) iterates `models or self.routes.get(task, self.routes["default"])` — for `task="default"` with no override, that's `["claude-sonnet-5"]` by default (line 349), so if that's the only model in the route and it's rate-limited, there's nowhere to fail over *to* within this route; but assume a route with multiple models (e.g. `"cheap"`: `["claude-haiku-4-5-20251001", "claude-sonnet-5"]`, line 350). For the first model, it first checks `self.cache` (if set) via `self.cache.get(model, messages)` — a cache miss returns `None`, so no early return. Then, if `self.rate_limiter` is set, it calls `self.rate_limiter.allow(model)`; if that returns falsy, `last_err = RateLimitExceeded(...)` is recorded and the loop does `continue` — critically, it does NOT call `self.provider.complete()` for that model at all, so no vendor request happens, no cost is incurred, and no exception propagates yet. The loop then moves to the next model in the route (e.g. `claude-sonnet-5`), repeats the cache check, the rate-limiter check, and (assuming it passes) calls `self.provider.complete(messages, model=model, **kw)`. If that succeeds, the cache is populated (`self.cache.set(...)`) and the `LLMResponse` is returned immediately — the earlier rate-limit "failure" is silently absorbed; the caller never sees it. Only if **every** model in the route is rate-limited or raises does the function fall through the loop and raise `RuntimeError(f"all models for task={task!r} failed") from last_err` (line 379) — and note `last_err` here is whichever failure happened *last* in iteration order, not necessarily the most informative one; if the first model failed with a specific, diagnosable error and the last model failed with a generic timeout, the raised `RuntimeError`'s `__cause__` only shows the last one.

## Q2: What happens if a provider's completion call raises an exception that ISN'T a rate limit — say the Anthropic SDK raises an authentication error or a 500? Does `complete()` distinguish between "retryable" and "fatal" failures?

No — line 373's `except Exception as e:` is a blanket catch with no discrimination by exception type. The comment right there says "provider outage / rate limit -> try next model in the route," but the code doesn't actually check *what kind* of exception it is before deciding to fail over; a genuine, non-retryable `AuthenticationError` (bad API key) is treated identically to a transient `RateLimitError` or a `ConnectionError` — both just get recorded as `last_err` and the loop tries the next model. This has a real, non-obvious consequence: if your API key is simply invalid, `LLMGateway.complete()` will burn through every model in the route (each failing for the same root-cause reason: bad auth) before finally raising `RuntimeError("all models for task=... failed")` — which is slower to fail than it should be, and the resulting error message doesn't clearly say "your API key is invalid," it says "all models failed," with the real cause buried in `.__cause__`. A more defensive implementation would inspect exception type/status code and re-raise immediately on clearly-fatal errors (auth, malformed request) while only failing over on clearly-transient ones (rate limit, 5xx, timeout) — this module doesn't do that distinction anywhere.

## Q3: How does the module-level `_turns()` in `AnthropicProvider` differ from `OpenAIProvider`'s, and why does each provider need to reconstruct the conversation on every single call rather than storing state?

Both `_turns()` methods (AnthropicProvider lines 109-137, OpenAIProvider lines 201-226) convert this codebase's provider-agnostic message list (plain dicts with `role`/`content`/optionally `tool_calls`/`tool_call_id`/`ok`) into each vendor's own wire format, and both do it fresh on every call because neither vendor's API is stateful across calls — every request must carry the *entire* conversation history, so there's no "session" to persist, only messages to re-serialize each time. The formats genuinely differ in structurally important ways: Anthropic represents an assistant's tool call as a `tool_use` content block *inside* the assistant's own message content array, and the corresponding result as a `tool_result` block inside the *next user* message's content array (`_turns` lines 121-130) — Anthropic has no separate `"tool"` role at the wire level, tool results are user-role content blocks. OpenAI, by contrast, has a genuine `"tool"` role (`{"role": "tool", "tool_call_id": ..., "content": ...}`, line 220) and represents the assistant's tool call via a top-level `tool_calls` list on the assistant message rather than embedding it in a content-block array. This means the exact same input message list produces meaningfully different, non-interchangeable wire payloads — which is precisely why `LLMGateway` treats `Provider` as an opaque protocol (`contracts.Provider`) rather than trying to share serialization logic between vendors; the abstraction boundary is deliberately placed one level above "what does the wire format look like."

## Q4: Why does `AnthropicProvider.complete()` special-case `system=None` by omitting the key entirely rather than passing `system=None` (lines 142-149)?

The comment is explicit and cites a real, observed failure: Anthropic's API rejects an explicit `system: null` in the request body outright, with the actual error message `"system: Input should be a valid array"` — not a hypothetical concern, the comment says "a real 400 hit on any call with no system message," naming two concrete call sites that trigger it (`document_store.py`'s image transcription and `guardrails.py`'s LLM-judge check), both of which build message lists with no `{"role": "system", ...}` entry at all. So `_turns()` returns `system = None` in that case (from the `next((...), None)` generator lookup at line 116, which finds no match), and `complete()` guards with `if system is not None: create_kw["system"] = system` (line 142) — meaning the key is left out of `create_kw` entirely rather than being present with a `None` value. This is a small but important lesson in "the wire protocol validates the *presence* of a key differently than its *value*," and it's the kind of bug that's easy to reintroduce later if someone "simplifies" this to `create_kw["system"] = system` unconditionally — which is presumably exactly what happened before this comment was written. The identical guard is repeated in `stream()` (line 175) for the same reason, since `stream()` doesn't share code with `complete()` here — it independently rebuilds `_turns()` and independently needs the same `system is not None` check, which is minor duplication worth flagging.

## Q5: Trace a native tool-calling round trip through `AnthropicProvider`: an agent turn calls a tool, the tool runs, and the result is fed back. What message shapes does `_turns()` expect at each step, and what breaks if `tool_call_id` is missing on the tool-result message?

Turn 1: the assistant's message from a prior `complete()` call had `tool_calls=[{"id": "toolu_123", "name": "search", "args": {...}}]` set (from `LLMResponse.tool_calls`, contracts.py line 136, populated by the `ToolCall(id=block.id, name=block.name, args=block.input)` list comprehension at llm_gateway.py lines 157-160). When that assistant message is fed back into a *new* `complete()` call as part of `messages`, `_turns()` checks `m["role"] == "assistant" and m.get("tool_calls")` (line 121) and rebuilds it as `{"role": "assistant", "content": [{"type":"text",...}?, {"type": "tool_use", "id": "toolu_123", "name": "search", "input": {...}}]}`. The next message in the list must be `{"role": "tool", "tool_call_id": "toolu_123", "content": <result>, "ok": True/False}` — `_turns()` checks `m["role"] == "tool" and m.get("tool_call_id")` (line 127) and rebuilds it as a user-role message with a `tool_result` content block referencing `tool_use_id: "toolu_123"`. If `tool_call_id` is missing (falsy/absent) on that tool-role message, the `elif` at line 127 fails its second condition, and the message falls through to the final `else` branch (line 133-136): it's treated as "a tool-result message from the text-convention fallback path" and rendered as a plain user message `f"[tool result] {m['content']}"` with no `tool_use_id` correlation at all. The practical consequence: Anthropic's API requires every `tool_use` block to be followed by a matching `tool_result` referencing its exact id — if the correlation is dropped this way, the API will reject the request (a `tool_use` block with no matching `tool_result`), or at minimum the model loses the structured linkage between its own tool call and the result, degrading to unstructured text it has to parse itself.

## Q6: What is the "text-convention fallback path" mentioned in both `_turns()` implementations, and why does it exist at all if native tool-calling is the primary path?

The comment at lines 134-136 (Anthropic) and lines 224-225 (OpenAI) both reference "a tool-result message from the text-convention fallback path, with no native tool_call_id to correlate against" — implying this codebase supports (elsewhere, likely in `orchestration.py` or an older/simpler execution mode) a non-native way of representing tool results, where a tool's output is just appended as a message without the structured `tool_call_id` linkage that native provider tool-calling requires. Both providers defensively handle this case identically: fall back to rendering it as `f"[tool result] {m['content']}"` — a plain, unstructured user turn — rather than crashing on a `KeyError` when `tool_call_id` is absent. This tells you the message-list contract this file consumes is intentionally more permissive than "always native tool-calling everywhere" — likely to support simpler agents/tests that don't bother wiring up real tool-call IDs, or an execution path predating native tool-calling being fully wired through. It's a reasonable defensive fallback, but it does mean a caller who *thinks* they're using native tool-calling but forgot to set `tool_call_id` on a tool-result message won't get an error — they'll silently get worse (unstructured, uncorrelated) tool-result framing with no warning that they fell into the fallback path.

## Q7: How does `PricingRegistry` decide the cost of a call to a model that isn't in its `rates` dict, and why does the module docstring frame this as a "dangerous" prior behavior it's fixing?

`PricingRegistry.calculate(model, input_tokens, output_tokens)` (line 71) looks up `self.rates.get(model)`; if `None` (unlisted model), behavior branches on `unknown_model_policy` (default `"estimate"`, line 68): `"block"` raises `UnknownPricingError` with a message telling you exactly how to fix it (register the rate, or loosen the policy); `"estimate"` meters at `self.estimate_rate`, which defaults to `(15.00, 75.00)` per 1M tokens (line 69) — the docstring is explicit this is "a deliberately conservative top-tier rate, not an average," i.e. it *overestimates* cost for an unknown model rather than guessing low; `"allow"` (anything else) falls back to `(0.0, 0.0)` — free. The class docstring (lines 48-65) explains the "dangerous" framing directly: the *previous* design apparently had `_PRICING.get(model, (0.0, 0.0))` inline in each `Provider.complete()`, meaning any model not in the hardcoded `_PRICING` dict silently cost $0 to track — so real spend would keep happening (you're still being billed by the vendor) while `RunBudget`'s cost ceiling saw none of it, defeating the entire purpose of `Policy.max_cost_usd_per_thread`. `"estimate"` as the new default converts a silent blind spot into a loud, conservative overestimate — spend is still tracked (just imprecisely), so a budget ceiling still means something, at the cost of possibly throttling a genuinely cheap unlisted model as if it were expensive.

## Q8: Why is `_OPENAI_PRICING` (line 186) left as an empty dict, and what actually happens when `OpenAIProvider.complete()` is called with a real OpenAI model today?

`_OPENAI_PRICING: dict[str, tuple[float, float]] = {}` — genuinely empty, unlike `_PRICING` for Anthropic (lines 34-38), which has three real entries. The comment (lines 181-185) explicitly tells the operator to "fill in your account's model ids and per-1M-token rates via `pricing=PricingRegistry(rates={...})`" — this is a documented, deliberate gap, not an oversight, but it does mean `OpenAIProvider()` constructed with its default `pricing = pricing or PricingRegistry(rates=_OPENAI_PRICING)` (line 199) will, for *every* OpenAI model, hit `PricingRegistry.calculate`'s "unlisted model" branch — and since the registry's own default `unknown_model_policy` is `"estimate"` (line 68), every OpenAI call by default gets metered at the conservative `$15/$75 per 1M tokens` estimate rate regardless of which actual OpenAI model you're using, until an operator explicitly supplies real OpenAI pricing. That's arguably the correct conservative default (spend is tracked, just imprecisely, per Q7's reasoning) but it's worth knowing cold that out-of-the-box OpenAI cost tracking in this module is an estimate, not a real number, for every single call unless configured.

## Q9: `LLMGateway.stream()` only ever uses `self.routes.get(task, self.routes["default"])[0]` — the *first* model in the route (line 385). Why does streaming not get the same failover behavior as `complete()`?

`stream()` (line 381) picks exactly one model — the first candidate in the resolved route — checks `hasattr(self.provider, "stream")`, raising `NotImplementedError` if absent (line 386-387), and then delegates via `yield from self.provider.stream(messages, model=model, **kw)`. There is no loop over the route's remaining models, no rate-limiter check, no cache lookup at all for streaming. This is a structural limitation, not an oversight the code hides: streaming is fundamentally different from a single request/response — once you've started yielding tokens to a caller, you can't transparently "fail over" to a different model mid-stream without either discarding partial output or somehow stitching two different models' outputs together, neither of which is sound. So `stream()` deliberately doesn't attempt the `complete()`-style resilience; if the single chosen model's stream fails or is rate-limited, that failure propagates directly to the caller with no fallback. This means production code relying on streaming has strictly weaker resilience guarantees than code using `complete()`, which is worth flagging explicitly as a known gap: there's no "restart the stream against model #2 in the route" logic anywhere in this file.

## Q10: Walk through exactly what happens if a streaming connection to Anthropic drops mid-token — what does the caller of `LLMGateway.stream()` actually observe?

`AnthropicProvider.stream()` (lines 170-178) uses `with self._client.messages.stream(**stream_kw) as stream: yield from stream.text_stream` — it's a thin pass-through to the Anthropic SDK's own streaming context manager and `text_stream` iterator; this module adds no reconnection, buffering, or partial-output handling of its own. If the underlying HTTP/SSE connection drops mid-stream, the SDK's `stream.text_stream` generator will raise whatever exception the Anthropic SDK raises for a broken stream (typically some form of connection/timeout error from its HTTP client) — that exception propagates straight up through `yield from` in `AnthropicProvider.stream()`, through `yield from self.provider.stream(...)` in `LLMGateway.stream()` (line 388), directly to whoever is iterating the generator returned by `LLMGateway.stream()`. Two consequences worth calling out: (1) the caller sees a raw SDK-level exception, not a normalized `agent_foundry` error type — there's no `try/except` anywhere in the streaming path in this file; and (2) whatever partial text was already yielded before the drop is NOT recoverable or resumable — there's no buffering of partial output, no `PromptCache` interaction for streaming at all (the cache is only wired into `complete()`, never `stream()`), so a caller who wants "resume where it left off, plus fail over to model #2" has to build that entirely themselves on top of this primitive. This is a real, honest limitation: streaming here is a raw pass-through with none of the resilience `complete()` has.

## Q11: How does `PromptCache._key()` handle multimodal message content (e.g. an `image_content()` block), and why does it need special handling at all (lines 304-309)?

Cache keys must be hashable (they become dict keys in `self._store`, line 302), but a message's `content` field can be either a plain string or a list of content blocks (e.g. `[image_content(path), {"type": "text", "text": "..."}]`, per the `image_content()` helper at lines 22-31) — and a `list` (or the `dict`s inside it) is unhashable in Python, so using raw `content` directly in a tuple-based cache key would raise `TypeError: unhashable type: 'list'`. `_key()`'s inner `content_key()` helper (lines 307-308) checks `isinstance(content, str)` and passes strings through unchanged, but for anything else (a list of multimodal blocks) it does `json.dumps(content, sort_keys=True)` — serializing it to a canonical, hashable string. This is necessary but has a subtlety: `image_content()` embeds the *base64-encoded image bytes themselves* inside the content block's `source.data` field (line 30) — so `json.dumps` on a multimodal message includes the full base64 image payload in the cache key computation. For a large image, that means every cache lookup/insert does a nontrivial JSON serialization of a potentially multi-megabyte base64 string just to compute a dict key, which is a real (if probably rarely hit) performance cost baked into the caching path.

## Q12: `PromptCache.get()` checks `time.time() - ts > self.ttl_s` to decide staleness (line 316) — what happens to an expired entry? Is it evicted, or does it just sit there?

Looking closely: `get()` (lines 311-318) checks the timestamp and returns `None` if expired, but it never deletes `self._store[key]` in that branch — the stale entry is left in the dict forever (or until a future `set()` call overwrites that exact same key with a fresh entry). This means `PromptCache` has no actual memory-bound eviction policy at all: it's an unbounded, ever-growing `dict` for the lifetime of the process, and "TTL" here only governs whether a *read* treats an entry as valid, not whether the entry's memory is ever reclaimed. For a long-running server process fielding many distinct message sequences, this is a genuine memory leak in the sense that the cache dict will monotonically grow with every unique `(model, messages)` combination ever seen, expired or not — there's no LRU eviction, no max-size cap, and no background sweep. The class docstring (lines 296-299) explicitly frames this as "swap the dict for Redis/Memcached behind the same get()/set() interface for a cache shared across processes," which would also incidentally fix the unbounded-growth problem (Redis TTLs actually evict), but the in-memory reference implementation as written does not.

## Q13: Is `PromptCache` (or `LLMGateway` generally) safe under concurrent access from multiple threads?

Nothing here uses a lock. `PromptCache._store` is a plain `dict` mutated directly by `get()`/`set()` (`self._store[self._key(...)] = (...)`, line 321) with no `threading.Lock` around read-modify-write sequences. In CPython, individual dict `__setitem__`/`__getitem__` operations are atomic at the bytecode level due to the GIL, so you won't get a *corrupted* dict from concurrent access, but there's no protection against the classic cache race: two threads simultaneously missing the cache for the same `(model, messages)` key, both calling the provider, and both calling `.set()` — the second call simply overwrites the first's entry with no harm done functionally, just a wasted duplicate API call (and duplicate cost — `LLMGateway.complete()` doesn't coordinate to avoid this, e.g. via a per-key lock or in-flight-request de-duplication). `ModelRegistry._scores` (line 329) has the identical property: `record_score`'s `self._scores.setdefault(model, []).append(score)` is safe from corruption under the GIL but not free from lost-update races in the sense that two concurrent `avg_score` calls interleaved with `record_score` could observe slightly different snapshots — not incorrect, just not linearizable. None of this is a crash risk in practice, but it is a real limitation if `LLMGateway` is shared across many concurrent request-handling threads/coroutines expecting exactly-once provider calls per unique cache key.

## Q14: `ModelRegistry.ranked()` sorts models by `avg_score` — what happens to a model that has never had a score recorded, and could this create a routing feedback loop?

`avg_score(model)` (line 334) returns `0.0` if `self._scores.get(model, [])` is empty (line 336) — so an unscored model is treated as the *worst possible* score, not as "unknown/neutral." `ranked(models)` (line 338-340) then sorts descending by that score, meaning a brand-new model with zero recorded evals gets sorted to the bottom of the ranking, below even a poorly-performing but previously-scored model. Fed "straight into `LLMGateway.routes[task]`" per the docstring (line 339), this creates a genuine cold-start problem: a new/candidate model can never get promoted up the routing order via `ranked()` alone, because it will never accumulate the scores needed to rank higher until something *else* (outside this class) deliberately routes traffic to it despite its 0.0 average — i.e., `ModelRegistry` as written has no explicit exploration mechanism (no epsilon-greedy, no Thompson sampling, nothing) to give an unscored model a chance to prove itself; whoever builds the routing table has to manually inject new candidates ahead of pure `ranked()` output, or this becomes a pure exploitation-only system that entrenches whatever was already ranked well.

## Q15: Why does `MultiProvider` exist as a separate class from `LLMGateway`'s own routing — aren't they solving the same problem (pick a model)?

They solve genuinely different layers of the same problem. `LLMGateway.routes` picks *which model name* to try, in priority order, for a logical task — but it still needs exactly one `Provider` object to actually execute the call (`self.provider.complete(messages, model=model, **kw)`, line 372) — `LLMGateway` is constructed with a *single* `provider:` field (line 347). If your routing table mixes models across vendors (e.g. `"hard": ["claude-opus-5", "gpt-4o"]`), a single `AnthropicProvider` instance can't serve the `gpt-4o` call — it would try to hit the Anthropic API with a model name it doesn't recognize. `MultiProvider` (lines 281-292) exists to bridge exactly this gap: it implements the same `complete()` signature as any other `Provider` but internally dispatches by model name to whichever vendor-specific `Provider` in `self.by_model` actually owns that model (`raise KeyError(...)` if none registered, line 291), and you'd pass a `MultiProvider` instance as `LLMGateway`'s single `provider=` — making the one-provider-per-gateway constraint transparent even when the routing table spans vendors. The docstring calls this "the seam that makes 'every model, one contract' real" — `LLMGateway` never needs vendor-awareness at all, because `MultiProvider` absorbs it.

## Q16: How is this module's design different from LiteLLM or OpenRouter, which solve "one API surface over many LLM providers" as their entire product — why build this in-house instead of depending on one of those?

LiteLLM and OpenRouter both give you an OpenAI-compatible single endpoint/SDK call that internally routes to dozens of providers, generally with pricing tables, retries, and fallback baked in and maintained by a third party (frequently updated as vendors change pricing/models). This module reimplements a narrower slice of that idea in-house: two providers (`AnthropicProvider`, `OpenAIProvider`), an explicit `PROVIDERS` registry (line 278) resolved by name, and a hand-maintained `_PRICING`/`_OPENAI_PRICING` table this project itself has to keep current. The tradeoff is control and dependency-surface versus coverage and maintenance-freeness: depending on LiteLLM means you inherit a large dependency, its own opinions about message normalization, and are exposed to its release cadence and any bugs in its abstraction layer, whereas this hand-rolled version keeps you in full control of exactly how tool-calling round-trips are reconstructed (Q3-Q6), exactly how cost is computed and what "unknown model" means (Q7-Q8), and keeps the entire LLM-facing surface auditable in ~430 lines with zero opaque third-party routing logic — directly consistent with the project's broader "Python-native core, minimal dependencies" philosophy (the same reasoning that keeps Pydantic out of `agent_spec.py`). The real cost: every new provider, every pricing update, every vendor-specific quirk (like the Anthropic `system: null` 400 error in Q4) has to be discovered and hand-fixed here rather than inherited from an actively-maintained third-party project with much broader vendor coverage.

## Q17: What's the actual mechanism for injecting a custom `AnthropicProvider` for tests (avoiding real API calls), and what's genuinely hard to fake given the current design?

`AnthropicProvider.__init__` (line 87) unconditionally does `import anthropic` and constructs a real `anthropic.Anthropic()` client (with or without the workspace-id header) — there's no dependency-injection point for the underlying SDK client itself; you cannot pass in a fake `anthropic.Anthropic`-shaped object through the constructor. The intended seam for testing is one level up: `contracts.Provider` is a `Protocol` with just `complete(self, messages, *, model, tools=None, **kw) -> LLMResponse`, so tests are expected to write an entirely separate fake class implementing that protocol (not subclassing `AnthropicProvider`) and pass it as `LLMGateway(provider=FakeProvider())`. This works fine for testing `LLMGateway`'s own routing/caching/rate-limiting/failover logic in complete isolation from any vendor SDK — which is clearly the design intent — but it means `AnthropicProvider._turns()`'s wire-format-correctness logic (Q3-Q6) can only be genuinely tested either by mocking `anthropic.Anthropic` at the import level (patching `self._client.messages.create`) or by hitting the real API; there's no lighter-weight seam purpose-built for testing `_turns()`'s translation logic in isolation from constructing a real `anthropic.Anthropic()` object (which itself may fail in a CI environment with no API key set at import/construction time, since the SDK's client constructor may validate credentials eagerly).

## Q18: Trace what `AnthropicProvider.complete()` does with a malformed or unexpected response — e.g. `resp.content` contains a block type this code doesn't recognize (not `"text"` or `"tool_use"`).

Lines 161-168 build the returned `LLMResponse` from two separate list comprehensions over `resp.content`: `text="".join(block.text for block in resp.content if block.type == "text")` and `tool_calls=[ToolCall(...) for block in resp.content if block.type == "tool_use"]`. Both comprehensions use an `if block.type == "..."` filter, which means any block type this code doesn't explicitly check for (e.g. a hypothetical future `"thinking"` or `"redacted_thinking"` block type, or any new content-block type Anthropic ships) is silently dropped — neither included in `text` nor in `tool_calls`, with no error, no warning, and no trace that content was discarded. This is a real forward-compatibility risk: if Anthropic adds a new block type to its API and this code isn't updated, a response that legitimately contains meaningful content in that new block type will appear to the rest of the framework as if that content simply wasn't there (e.g. `text` silently shorter than what the model actually said) — a silent data-loss bug rather than a loud failure, which is a strictly worse failure mode than crashing, because it can go unnoticed for a long time.

## Q19: What are `make_llm_judge` and `make_grounding_judge` actually for, and what happens if the judge model returns non-numeric text?

Both (lines 391-431) build a `judge` callable around an `LLMGateway`, used by `kpi.py`'s `llm_judge_kpi`/`composite_grounding_kpi` (and wired into `agent_spec.py`'s `_named_evaluator_kpi`, per the agent_spec Q&A) to turn a subjective quality question into a 0..1 numeric score by asking an LLM to "Rate ... from 0 (worst) to 10 (best). Reply with ONLY the number." and parsing `resp.text.strip()` as a `float`. Both wrap that parse in `try: ... except ValueError: return 0.0` (lines 399-401, 426-428) — so if the judge model ignores the "ONLY the number" instruction and replies with, say, `"I'd rate this a 7 out of 10 because..."`, `float("I'd rate this a 7 out of 10 because...")` raises `ValueError`, which is caught, and the judge silently returns `0.0` — the *lowest possible* score, not a "judge failed to respond usefully" signal. This is a meaningful and somewhat dangerous default: a well-performing agent whose critique judge happens to hit a verbose, non-conforming response from the (typically cheap, per `task="cheap"` default) judge model gets scored as if it had produced the worst possible output, which could trigger `CritiqueConfig`'s retry/escalate logic (in `orchestration.py`) for entirely the wrong reason — a parsing failure masquerading as a quality failure, with zero distinction between the two anywhere in this code.

## Q20: If you had to pick the single biggest limitation of `llm_gateway.py` to fix given more time, what would it be, and why?

The most consequential one is the blanket `except Exception` in `LLMGateway.complete()`'s failover loop (Q2) combined with the complete absence of any retry/backoff *within* a single model before moving on — a transient network blip on the very first model in a route is treated identically to that model being permanently broken, and the loop immediately abandons it for the next model rather than, say, retrying once with a short backoff (a genuinely transient error might succeed on retry, saving you from falling through to a costlier or lower-quality fallback model unnecessarily). A close second: none of `complete()`'s exception handling distinguishes retryable from fatal errors (also Q2), so a bad API key or malformed request burns through the entire route before failing, with the real cause buried in a chained exception. Fixing this well would mean classifying provider exceptions (rate limit / timeout / 5xx as retryable-with-backoff; auth / 4xx-malformed-request as fatal-fail-fast) and adding a small bounded retry-with-backoff before advancing to the next model in the route — a meaningfully more production-grade resilience story than "one attempt per model, then give up on that model entirely," without changing the module's overall shape or adding new dependencies.
