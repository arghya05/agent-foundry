# agent_foundry/autogen_bridge.py — Q&A

Wraps a Microsoft AutoGen `ConversableAgent`/`AssistantAgent` as an ordinary Agent Foundry `ToolSpec` via `autogen_as_tool()`, so an AutoGen agent becomes callable — and subject to RBAC, guardrails, the circuit breaker, and the audit log — exactly like any local function or MCP tool inside a `ToolRegistry`.

## Q1: The whole module is one 33-line function. What's actually being bridged, and why is it this simple?

`autogen_as_tool()` (line 23) takes a `name`, `description`, and an already-constructed AutoGen `agent`, and returns a `ToolSpec` whose `fn` is the nested `call(query: str) -> str` (lines 27-30). The entire bridging work is: run `agent.run(task=query)` to completion, take `result.messages[-1]` (AutoGen's own list of conversation messages, the last one being the agent's final turn), and return its `.content` (falling back to `str(final)` via `getattr(final, "content", str(final))` if the message object has no `.content` attribute). It's this simple because the framework doesn't try to preserve any of AutoGen's richer internal state (its multi-agent group chat, its own tool-calling turns, its own message history) — it treats the entire AutoGen agent as a black box that takes one string in and returns one string out, matching exactly the shape every other tool in a `ToolRegistry` has (`fn(**kwargs) -> Any`, per `tools_gateway.ToolRegistry`). Anything more elaborate (e.g. surfacing AutoGen's intermediate reasoning, or letting a caller resume a specific AutoGen conversation across multiple calls) is explicitly out of scope for this minimal adapter.

## Q2: `call()` uses `asyncio.run(agent.run(task=query))`. What happens if this tool is invoked from code that already has an event loop running — e.g. via `ToolRegistry.ainvoke()`?

`asyncio.run()` creates a brand-new event loop, and it raises `RuntimeError: asyncio.run() cannot be called from a running event loop` if one is already active in the calling thread. `tools_gateway.ToolRegistry.ainvoke()` (the async entry point used by `orchestration.make_act_node`/`native_engine._act` for concurrent same-turn tool dispatch) explicitly branches on `inspect.iscoroutinefunction(spec.fn)` — since `call()` here is a plain `def`, not `async def`, `ainvoke()` calls it synchronously in-line (`spec.fn(**args)`), on whatever thread the surrounding async code is executing on. If that thread already has an asyncio loop running (which it does, since `ainvoke()` itself is a coroutine being awaited inside one), the nested `asyncio.run()` call inside `call()` blows up immediately with that `RuntimeError`. This is a real, structural landmine: this bridge is safe to call via the *synchronous* `ToolRegistry.invoke()` path (no loop running on that thread) but will crash if a caller ever routes it through the async `ainvoke()` path from inside a live event loop — which is exactly the path the framework's own concurrent tool-dispatch code uses. `mcp_tools.py`'s `MCPToolSource` solves the equivalent problem correctly by running a persistent background-thread event loop and marshaling calls onto it with `asyncio.run_coroutine_threadsafe`; this module does not adopt that pattern.

## Q3: Why does the reverse direction (AutoGen calling an Agent Foundry tool) need "no adapter at all," per the docstring?

The docstring (lines 9-11) states that `AssistantAgent`'s own `tools` parameter accepts plain Python callables directly, so a function already written and registered against Agent Foundry's `ToolRegistry` can be handed straight to AutoGen's agent constructor unchanged. This is possible because Agent Foundry tools are, at bottom, ordinary Python functions (`ToolSpec.fn`) — the framework's added value (RBAC, schema validation, caching, retries) lives in the `ToolRegistry`/`ToolSpec` wrapper around the function, not baked into the function's calling convention. AutoGen doesn't need to understand any of that wrapper; it just needs `fn(**kwargs)`-shaped Python callables, which is exactly what `ToolSpec.fn` already is. The asymmetry is real, though: going *into* AutoGen this way means none of Agent Foundry's governance (policy checks, audit logging, circuit breaker) applies when AutoGen invokes the raw function directly — only calls that go through `ToolRegistry.invoke()/ainvoke()` get governed. So "no adapter needed" is also a governance gap if a builder assumes AutoGen-invoked calls are still policy-checked; they aren't, unless the underlying function re-implements those checks itself.

## Q4: What happens if the wrapped AutoGen `agent.run()` call raises an exception mid-conversation — walk through the code path.

`call()` itself has no try/except — an exception raised inside `agent.run()` (e.g. AutoGen's own LLM call failing, a malformed tool call inside AutoGen's internal loop, a network error) propagates straight up out of `call()` as whatever exception AutoGen raises. Since this `ToolSpec` is invoked through `ToolRegistry.invoke()`/`ainvoke()`, and those methods wrap `spec.fn(**args)` in a `try/except Exception` (`tools_gateway.py` lines 268-274 / 289-295), the exception is caught there, not here — the tool call fails gracefully at the registry level, retried up to `spec.max_retries` (which defaults to `0`, since `autogen_as_tool()` doesn't set it), and ultimately surfaces as `ToolResult(ok=False, error=str(e))` rather than crashing the whole agent turn. So the failure handling is real, but it's entirely borrowed from `ToolRegistry` — this module contributes nothing of its own (no retry, no partial-result recovery, no distinguishing "AutoGen agent errored" from "AutoGen agent gave a bad answer") beyond letting the exception bubble.

## Q5: What's lost in translation when an AutoGen agent's multi-turn, potentially multi-agent conversation gets flattened into a single string return value?

Everything except the final message's content. AutoGen's `AssistantAgent.run()` can involve multiple internal turns — the agent calling its own tools, reasoning across several LLM calls, potentially participating in a group chat with other AutoGen agents — and `result.messages` captures that whole trajectory. `call()` discards all of it except `result.messages[-1].content` (line 29). This means: no visibility into *how* the AutoGen agent arrived at its answer (useful for debugging or for the audit log, which — per the module's own framing — should ideally see what actually happened inside a governed tool call); no ability for the calling Agent Foundry graph to intervene mid-conversation (e.g. if AutoGen's agent gets stuck in a loop, the whole `agent.run()` call just blocks until AutoGen's own internal completion condition fires, with no external interrupt point); and no distinction between "the AutoGen agent successfully completed its task" and "the AutoGen agent gave up / hit its own internal turn limit and returned something" — `call()` treats both as an equally valid string result.

## Q6: Why fall back to `str(final)` when `final` has no `.content` attribute (line 30), instead of raising?

`getattr(final, "content", str(final))` is a defensive shim against AutoGen returning a message object shape this bridge doesn't fully understand (AutoGen has evolved its message types across versions — e.g. plain text messages vs. structured/multimodal message types). Falling back to `str(final)` guarantees `call()` always returns *something* stringy rather than crashing on an `AttributeError`, keeping the contract with `ToolSpec` (which expects `fn` to return a value, not to throw on a shape mismatch) intact. The tradeoff is that `str(final)` on an unexpected object type could produce a genuinely useless string for the calling agent — e.g. `<autogen.SomeMessageType object at 0x...>` — that gets treated as a valid, cacheable tool result rather than an error, since nothing here inspects whether the fallback string is actually meaningful. A more defensive version might treat a missing `.content` as worth logging or even raising past the fallback, since it likely means a version mismatch between this bridge and the installed AutoGen package.

## Q7: The `ToolSpec` this function returns declares `parameters={"query": "string"}`. What does that imply for how a model actually invokes the wrapped AutoGen agent, and is that description sufficient?

`tools_gateway.tool_json_schema()` converts `{"query": "string"}` into a JSON Schema `{"type": "object", "properties": {"query": {"type": "string"}}, "required": ["query"]}` before it's exposed to an LLM via `ToolRegistry.native_tools()`. This means the calling model sees a single opaque string parameter named `query` with no further shape — it has no idea what kind of task the underlying AutoGen agent actually handles (is it a coding agent? a research agent? a multi-step planner?) beyond whatever the caller wrote in the `description` argument to `autogen_as_tool()`. Since `description` is entirely caller-supplied free text, the quality of the model's usage of this tool is completely dependent on how well that description characterizes what the wrapped AutoGen agent can do — there's no structural way to encode, say, "this agent needs both a task and a target file path" without cramming both into one free-text `query` string, which the wrapped `call()` function would then have no way to parse back apart (it just forwards `query` wholesale as `task=query` to `agent.run()`).

## Q8: What's a limitation of this module you'd fix given more time?

The `asyncio.run()`-inside-a-possibly-running-loop problem (Q2) is the most consequential — it means this bridge is quietly incompatible with the framework's own async/concurrent tool-dispatch path (`ToolRegistry.ainvoke()`), and would need either an `async def call()` variant registered instead (so `ainvoke()` correctly awaits it via `inspect.iscoroutinefunction`), or the same persistent-background-loop pattern `mcp_tools.MCPToolSource` already uses elsewhere in this codebase, to be safe under concurrent async dispatch. A second, smaller fix: surfacing more of `result.messages` (e.g. as structured metadata alongside the final string, or logged for audit purposes) rather than discarding the AutoGen agent's internal trajectory entirely, since right now a failure or a strange intermediate step inside the wrapped agent is completely invisible to anything downstream.

## Q9: How would you test this bridge without actually installing and running a live AutoGen agent, and does the module's own comment suggest that's how it was actually verified?

Nothing in this file or its docstring claims live verification against a running AutoGen install (contrast with `a2a_bridge.py` and `mcp_tools.py`, which explicitly state they were round-tripped against real live servers/processes). The function's correctness rests entirely on the documented shape of AutoGen's `run()`/message API (`result.messages[-1].content`) being accurate — which is exactly the kind of assumption that silently breaks across AutoGen version bumps. A reasonable test strategy without a live AutoGen dependency: construct a minimal fake object exposing just `.run(task=...)` returning an object with `.messages[-1].content`, verify `autogen_as_tool()` produces a correctly-shaped `ToolSpec` and that `call()` extracts the right string; separately, a smaller number of tests gated behind an actual `autogen-agentchat` install (skipped otherwise, the same pattern used elsewhere in this codebase for optional dependencies) to catch real API drift.

## Q10: Compare this bridge's design to `crewai_bridge.py`'s `crewai_as_tool()`. What's structurally identical, and what's the one meaningful difference?

Structurally identical: both are single functions returning a `ToolSpec` with `parameters={"query": "string"}`, both wrap a third-party multi-step agent/crew object as a single blocking call-and-extract-final-text operation, and both explicitly note in their docstrings that RBAC/guardrails/circuit-breaker/audit-log apply transparently once wrapped as a `ToolSpec` — this is a deliberate, repeated pattern across the interop layer (the same "agents as tools" idea `orchestration.agent_as_tool` uses for LangGraph graphs, applied to a third-party engine). The one meaningful difference: `autogen_as_tool()`'s `call()` is synchronous Python wrapping an *async* AutoGen API (`asyncio.run(agent.run(...))`), which introduces the nested-event-loop hazard from Q2; `crewai_as_tool()`'s `call()` wraps CrewAI's synchronous `crew.kickoff()` directly, with no event loop involved at all, so it has no equivalent hazard. This is a direct consequence of AutoGen's underlying API being async-native while CrewAI's is not — the two bridges look almost identical on the surface but carry different concurrency risk because of that.

## Q11: What's the security posture of exposing an arbitrary AutoGen agent as a tool this way — what could an AutoGen agent's own internal tool use do that this bridge doesn't account for?

`autogen_as_tool()` has zero visibility into or control over what the wrapped AutoGen `agent` does internally — if that agent has its own tools configured (AutoGen's `tools` parameter, per the docstring's reverse-direction note), those tools execute entirely outside Agent Foundry's `Policy`/RBAC/audit-log boundary, because they're invoked by AutoGen's own internal loop, not by `ToolRegistry.invoke()`. So while the *outer* call — the whole AutoGen agent, treated as one tool — is properly governed (policy-checked, rate-limited, cached, audited) by virtue of being wrapped in a `ToolSpec`, anything the AutoGen agent does *inside* its own `run()` call is invisible to and ungoverned by Agent Foundry entirely. A builder who assumes "wrapping it in a ToolSpec means it's governed" would be wrong about the AutoGen agent's own internal actions — only the boundary crossing (input query in, final text out) is actually mediated.

## Q12: Given the query is a single free-text string with no structural validation, what happens if `query` contains something adversarial, e.g. a prompt injection targeting the wrapped AutoGen agent?

Nothing here sanitizes or validates `query` before passing it straight to `agent.run(task=query)` — it's forwarded verbatim. Since `query` typically originates from an upstream LLM's tool-call arguments (the calling Agent Foundry agent decided to invoke this tool with some string), a prompt-injection payload embedded earlier in the conversation (e.g. from a tool result, a document, or a user message) could flow straight through this string parameter into the AutoGen agent's own context, exactly as it would flow into a local function tool's arguments. This bridge doesn't uniquely worsen that risk relative to any other string-taking tool, but it also does nothing to mitigate it — no input-length capping, no scanning for known injection patterns, no separation between "trusted instruction" and "untrusted data" within the single `query` string. That's consistent with the framework's general tool-input validation being schema/type-shape only (`tools_gateway._validate_args`), not content-aware.
