# agent_foundry/prompts.py — Q&A

Loads and renders agent prompts from plain text/markdown files (or a `VersionStore`) using Python's own `str.format`, with an optional locale-fallback convention — deliberately not a templating engine, so a non-engineer can edit an agent's instructions and diff them like any other text file.

## Q1: Why `str.format` instead of Jinja2 (or LangChain's `PromptTemplate`) for variable substitution — what do you give up?

`load_prompt` (line 16-18) is literally `Path(path).read_text()` then `text.format(**variables) if variables else text`. That's the entire templating engine. You give up everything Jinja2 has that `str.format` doesn't: no `{% if %}`/`{% for %}` control flow, no filters (`{{ name | upper }}`), no template inheritance/includes, no autoescaping, no whitespace control. What you get in exchange is zero templating dependency and a format so simple that a non-engineer editing a `.md` file can understand `{customer_name}` without knowing anything about a templating DSL — the module docstring (lines 1-5) frames this whole file's purpose around exactly that: prompts as plain text a non-engineer can edit, reviewed as a diff, reused/A-B'd without touching orchestration code. The real cost shows up the moment a prompt needs conditional content ("if the user is a returning customer, add this paragraph") — there's no mechanism for that here at all; you'd have to build the conditional string in Python before calling `.format()`, which partially defeats the "prompts are plain text a non-engineer edits" goal, since now some of the prompt's logic lives back in Python.

## Q2: Walk through exactly what happens when `load_prompt` is called with a template that references a variable the caller didn't supply.

`text.format(**variables)` only runs `.format()` at all `if variables` is truthy (line 18) — so if you call `load_prompt(path)` with zero kwargs, the raw text is returned completely unrendered, even if it contains literal `{curly braces}` (this is actually a meaningful, if implicit, design point: a prompt with no variables requested is passed through untouched, so accidental braces in a no-variable prompt — e.g. a JSON example embedded in the instructions — won't crash). But the moment you pass even one variable, `.format(**variables)` runs against the *entire* text, and any `{other_placeholder}` in that text that isn't in `variables` raises `KeyError: 'other_placeholder'` — an unhandled Python `KeyError`, not a friendly "missing prompt variable" error. This is a real rough edge: neither `load_prompt` nor `PromptLibrary.get`/`VersionedPromptLibrary.get` catch or wrap this exception anywhere in the file, so a caller sees a raw `KeyError` with just the missing key name, no indication of which prompt file, which template, or which of possibly many placeholders was the actual problem — and if you meant to include a literal `{` in the same text you ARE substituting into (say, a JSON schema example alongside `{customer_name}`), `.format()` will try to interpret `{"key": "value"}` as a format field and raise `KeyError: '"key"'` unless you'd escaped it as `{{"key": "value"}}`.

## Q3: Why is `name` a positional-only parameter on `PromptLibrary.get` and `VersionedPromptLibrary.get` (the `/` at line 31 and line 55)?

Both `get(self, name: str, /, *, locale: str | None = None, **variables: str)` use `/` to force `name` positional-only. The comment (lines 32-33) explains directly: a prompt template variable literally called `{name}` is "a very plausible one" (e.g. "insert the customer's `name` into this prompt"), and if `name` were an ordinary keyword parameter, calling `.get("healthcare_assistant", name="Dr. Smith")` would be ambiguous/impossible — Python would try to bind `name="Dr. Smith"` to the `name: str` parameter that selects *which prompt file to load*, not forward it into `**variables`. Making it positional-only sidesteps the collision entirely: `name` can only ever be supplied positionally as the prompt's own name, and `**variables` is free to accept a keyword literally called `name` without any conflict. This is a small but sharp API-design detail — the kind of thing that only shows up once you've been bitten by exactly this collision in production.

## Q4: What is the locale-fallback mechanism doing, precisely, and what happens if you request a locale that has no dedicated file?

Both `PromptLibrary.get` (lines 38-42) and `VersionedPromptLibrary.get` (lines 60-66) implement the same convention independently: if `locale` is given, first look for a locale-suffixed variant (`f"{name}.{locale}.md"` for the flat-file version, or `f"{name}.{locale}"` as a published name for the versioned one); if that exists (file: `.exists()` check; versioned: catch `FileNotFoundError` from `self.store.get(...)`), use it; otherwise silently fall back to the base `name`. This is "additive" per the comment at line 36 — you don't need to author a locale variant for every prompt, only the ones that actually need localization, and requesting an unlocalized prompt's non-existent locale variant degrades gracefully to the English/default version rather than raising. The tradeoff: this fallback is *silent* — there's no logging, no return value indicating "you asked for hi-IN but got the base file," so a caller who assumes a translation exists (because they didn't get an error) can ship the wrong-language prompt to a user with zero signal anything went wrong. For something as user-facing as locale correctness, that silence is a real limitation.

## Q5: `PromptLibrary` and `VersionedPromptLibrary` implement the exact same `.get(name, *, locale=None, **variables) -> str` signature but are entirely separate classes with duplicated locale-fallback logic. Why not have one inherit from the other, or share a common base?

There's no shared base class or protocol formalizing the shared interface here — it's a duck-typed convention, not an enforced one. The docstring on `VersionedPromptLibrary` (lines 47-51) explicitly justifies this as intentional: "Drop-in anywhere only `.get()` is used (orchestration.py never imports PromptLibrary directly — it just receives a `system_prompt` string)" — i.e., because the consumer only ever calls `.get()` and uses its return value, the two classes never need a common ancestor for polymorphism to work; Python's structural typing (or just "the consumer doesn't care what class it is") is sufficient. The cost is exactly what you'd expect: the locale-fallback branch (try locale-suffixed name, catch not-found, fall back to base) is written twice, with two different failure signals to handle (`Path.exists()` vs. catching `FileNotFoundError` from the store) — if that fallback logic ever needs a fix (e.g. adding locale-fallback chains like `hi-IN` -> `hi` -> base), it has to be fixed in two places, and nothing enforces they stay in sync. A `Protocol` in `contracts.py` (following the pattern `Provider`/`VersionStore` already use elsewhere in this codebase) would at least document the shared contract even without inheritance.

## Q6: What's the actual mechanism `VersionedPromptLibrary` uses to publish a new version and roll back — and what does "instantly" mean given the underlying `VersionStore`?

`VersionedPromptLibrary.publish` (line 69-70) and `.rollback` (line 72-73) are thin pass-throughs to `self.store.publish(...)`/`self.store.rollback(...)` — this class adds no logic of its own beyond the locale-aware `.get()`. The `store` is typed as `"VersionStore"` under `TYPE_CHECKING` (line 13), a `Protocol` (per `versioning.py`) with `publish`/`get`/`rollback`/`history`. Looking at the reference implementation, `FileVersionStore` (versioning.py lines 23-70): `publish()` writes an immutable `{version}.txt` file (version = `str(time.time_ns())`, so versions are just nanosecond timestamps, not semantic version numbers) plus a `{version}.label` file, then overwrites a single `current` pointer file with that version string. `rollback(name, version=...)` just rewrites `current` back to an older version string, after checking the target `.txt` file exists (raising `ValueError` if not). "Instant" rollback, then, really means "instant" only in the sense that it's an O(1) pointer flip on disk — no data is recomputed or migrated — but it's also not atomic across a distributed/multi-process deployment: two processes racing to read `current` while a rollback is in-flight could plausibly see a torn read if the underlying filesystem doesn't guarantee atomic single-file writes (this project doesn't do anything special like write-to-temp-then-rename here, per the `write_text` call at versioning.py line 41).

## Q7: What is `VersionedPromptLibrary.history()` for, and what's a limitation of only exposing `version`, `label`, and `current`?

`history(name)` (line 75-76) passes through to `self.store.history(name)`, which for `FileVersionStore` (versioning.py lines 59-70) returns a list of `{"version": v, "label": ..., "current": v == current}` dicts for every published version, sorted by filename stem (i.e., lexicographic string sort of nanosecond-timestamp strings — which happens to also be chronological order for same-length numeric strings, but is fragile if version identifiers were ever not uniform-length). This is useful for an operator-facing "prompt version history" UI/audit trail, and the `label` field (set at publish time via `publish(name, content, *, label="")`) is the only human-readable annotation available — there's no timestamp field surfaced separately from the version string itself, no author/committer field, and no diff between versions. If you wanted to show "who changed this prompt and why" in an audit UI, you'd have to encode that entirely inside `label` yourself (e.g. `label="alice: tightened refund policy wording"`) — there's no structured metadata field for it.

## Q8: How does this module's approach compare to LangChain's `PromptTemplate` (or similar structured-prompt objects), and why would this project pick plain-file loading instead?

LangChain's `PromptTemplate` is a first-class object with declared `input_variables`, partial-variable binding, template-format selection (f-string vs. Jinja2), composability via `+`, and integration with output parsers and chains. This module has none of that structure — `load_prompt` doesn't even know what variables a given template file requires until `.format()` either succeeds or raises `KeyError` at render time; there's no `input_variables` introspection, no validation step, no way to compose two prompt files into one without string concatenation done by hand. The tradeoff is squarely about dependency surface and content ownership: `PromptLibrary` treats prompts as *files*, not Python objects, so the entire "prompt engineering" workflow (write, diff, review, roll back) happens in whatever tool already handles text files and git — no LangChain import needed anywhere in the core. The real loss versus `PromptTemplate` is exactly the introspection: you can't ask a `PromptLibrary`-loaded prompt "what variables do you need" without either reading the file yourself or waiting for a runtime `KeyError`, whereas `PromptTemplate.input_variables` gives you that statically.

## Q9: If `PromptLibrary.get("healthcare_assistant", locale="hi-IN", patient_name="Anita")` is called and `healthcare_assistant.hi-IN.md` exists but doesn't reference `{patient_name}` at all, what happens? What if it references a `{patient_name}` typo'd as `{patinet_name}` in the localized file?

First case: nothing breaks — `.format(patient_name="Anita")` on text that never uses `{patient_name}` simply ignores the unused keyword argument; Python's `str.format` does not require every supplied kwarg to be consumed. Second case (a typo in the localized template): the localized file's `{patinet_name}` placeholder is *not* satisfied by the `patient_name="Anita"` kwarg (different key), so `.format()` raises `KeyError: 'patinet_name'` — and this failure mode is specific to the *localized* file; if only the base `healthcare_assistant.md` had this typo you'd get the same error, but the point is locale variants are just as vulnerable to template/variable-name drift as the base file, and nothing in `PromptLibrary` cross-checks that a localized template's placeholder set matches the base template's — two translators could independently typo different variables in different locale files and no test here would catch it unless you explicitly render every locale variant with every real variable set in CI.

## Q10: Why does `PromptLibrary` take a `directory: Path` and build filenames by string interpolation (`self.directory / f"{name}.md"`, line 42) rather than validating `name` at all — what's the security/robustness concern, if any?

There is no validation of `name` here — if `name` contains path-traversal characters like `"../../etc/passwd"` (without a `.md` extension, so `f"{name}.md"` would need to end up matching a real file, but `"../../etc/passwd\x00.md"`-style tricks aside, more realistically `"../secrets"` as a name would resolve to `self.directory / "../secrets.md"`), `Path.__truediv__` will happily construct a path that escapes `self.directory`, and `Path.read_text()` will read whatever is there if it exists. Whether this matters depends entirely on where `name` comes from: if it's always a hardcoded string in application code (`library.get("healthcare_assistant", ...)`), there's no exposure. But if `name` were ever derived from user input — e.g. a multi-tenant system that lets a user pick which named prompt to render — this is an unvalidated path-traversal surface with no allowlist, no `Path.resolve()` + prefix-check, nothing. This mirrors the same "not a new attack surface, just worth knowing" caveat that `agent_spec.resolve_tool` documents explicitly for tool refs; `prompts.py` doesn't call this out anywhere, which is itself worth noting as an omission.

## Q11: What happens to `VersionedPromptLibrary.get()` if `self.store.get(name)` (the base, non-localized call at line 66) raises `FileNotFoundError` — is that caught?

No — look carefully at the code: the `try/except FileNotFoundError` block (lines 61-64) wraps *only* the locale-suffixed lookup (`self.store.get(f"{name}.{locale}")`), not the base fallback call at line 66 (`text = self.store.get(name)`). So if `locale` is `None` (the common case) or the locale variant genuinely doesn't exist and falls through to the base lookup, and *that* base name was never published to the store at all, `self.store.get(name)` raises `FileNotFoundError` (per `FileVersionStore.get`, versioning.py line 49) completely unhandled — it propagates straight out of `VersionedPromptLibrary.get()` to the caller. This is actually the *correct* behavior (a genuinely nonexistent prompt name should error loudly, not silently fall back to something), but it's worth being precise about: the try/except here exists purely to make the *locale* lookup optional, not to make the *entire prompt lookup* forgiving — a common point of confusion when reading this code quickly.

## Q12: Is there a `format_map`/`defaultdict` trick that would make missing-variable `KeyError`s softer, and why doesn't this module use one?

Python's `str.format_map()` combined with a `defaultdict`-like object (that returns, say, `"{missing_key}"` unchanged or an empty string for unknown keys) is a well-known pattern for "best-effort" template rendering that never raises on a missing variable. This module doesn't do that anywhere — both `load_prompt` and both `.get()` methods use the strict `.format(**variables)`, which is arguably the *right* call for prompts specifically: a silently-blank or literally-unsubstituted `{missing_key}` left in a system prompt sent to an LLM is a much worse failure mode than a loud Python exception at prompt-load time, because the LLM would see garbled instructions and produce a plausible-looking but subtly wrong response with no error surfaced anywhere — exactly the kind of silent failure that's hardest to debug in an agent pipeline. So the "limitation" here (no graceful degradation) is really a deliberate, defensible tradeoff: fail fast and loud in Python, rather than fail silently and confusingly at the LLM.

## Q13: How would you add caching to `PromptLibrary` (so repeated `.get()` calls for the same prompt don't re-read the file from disk every time), and what would you need to be careful about?

Nothing in `PromptLibrary.get()` caches file reads — every call does a fresh `Path(...).read_text()` (line 17, via `load_prompt`), so a hot path calling `.get()` per-request re-reads the same `.md` file from disk every time. Given how small prompt files typically are, this is unlikely to be a real bottleneck, but if you wanted to fix it, the natural approach is an `functools.lru_cache`-style cache keyed on `(directory, name, locale)` for the *raw template text* (before `.format()` is applied — you must NOT cache the rendered/formatted output, since that's per-call-variable-specific and caching it would leak one request's `{patient_name}` into another's response). The thing to be careful about: this module explicitly bills itself on "a diff on a prompt file is reviewable" and prompts changing via direct file edits or `git pull` — an in-process cache with no invalidation would keep serving a stale prompt after the underlying file changes until the process restarts, which is a meaningfully different (and worse) operational property than the current always-read-fresh behavior. Any caching addition would need either a short TTL or a file-mtime check to avoid silently serving stale instructions — precisely the kind of correctness-vs-performance tradeoff `VersionedPromptLibrary`'s explicit versioning already handles a different way (published/rolled-back versions, not implicit file staleness).

## Q14: What's a concrete limitation of this module you'd fix given more time?

The `KeyError`-on-missing-variable behavior (Q2) is technically defensible (Q12) but the *error message quality* is genuinely bad: a bare `KeyError: 'customer_name'` gives you the missing key but not which prompt file or template was being rendered, which is exactly the information you need to fix it fast in production. A cheap, high-value fix: wrap the `.format(**variables)` call in `load_prompt` in a try/except that re-raises as something like `KeyError(f"prompt {path!r} references undefined variable {e.args[0]!r} — passed variables were {sorted(variables)}")` — same exception type (so nothing downstream that catches `KeyError` breaks), but with actionable context. This is a small, surgical, backward-compatible change that would meaningfully improve debuggability without touching the deliberately-simple `str.format` templating model at all.

## Q15: Suppose two different prompt files need to share a common preamble (e.g. a safety/tone boilerplate every agent's system prompt should start with). How would you do that with this module as written, and what's missing to do it cleanly?

There is no include/composition mechanism in `load_prompt`/`PromptLibrary`/`VersionedPromptLibrary` — no `{% include %}` (that's Jinja2), no multi-file concatenation helper. The only way to share a preamble today is either (a) literally copy-paste the boilerplate text into every prompt `.md` file (violates DRY, and a later edit to the boilerplate requires updating every file individually — exactly the maintenance burden this module's own docstring says it's trying to avoid by making prompts editable/diffable in the first place), or (b) do the composition in Python: call `library.get("preamble")` and `library.get("healthcare_assistant")` separately and concatenate the strings yourself before passing the result on as a `system_prompt`. Option (b) works today with zero new code, but it means "prompt composition" logic leaks back into application code rather than staying declarative — there's no `PromptLibrary.compose(["preamble", "healthcare_assistant"], **vars)` helper. That would be a natural, low-risk addition: a method that loads and concatenates named prompts in order, still using the exact same underlying `.get()`/`load_prompt()` primitives, adding composability without adopting a full templating engine.

## Q16: Are `PromptLibrary` and `VersionedPromptLibrary` safe to share across threads/requests concurrently?

`PromptLibrary` has no mutable per-instance state beyond `self.directory` (set once in `__post_init__`, line 28-29) — every `.get()` call is a fresh, independent file read with no shared mutable buffers, so it's trivially thread-safe for concurrent reads. `VersionedPromptLibrary` is similarly stateless at this layer (`self.store` is the only field), but its actual thread-safety depends entirely on the underlying `VersionStore` implementation, which this file doesn't control. Looking at `FileVersionStore` (versioning.py): `publish()` does two separate file writes (`{version}.txt`, `{version}.label`) followed by a third (`current`) with no locking between them — a concurrent `get()` reading `current` in between could plausibly read a version number whose corresponding `.txt`/`.label` files haven't finished writing yet on a slow/networked filesystem (unlikely on local disk given OS-level write ordering guarantees for a single small file, but genuinely possible if `directory` pointed at a network mount). More realistically, two concurrent `publish()` calls for the *same* `name` racing to write `current` last-write-wins with no lock — which is fine for the common "single operator publishes" workflow this is clearly designed for, but would be a real concern for a multi-writer production setup, and nothing in `prompts.py` or `versioning.py` documents or defends against that race.
