# agent_foundry/core/run.py — Q&A

Adds `Run`, a formal per-thread lifecycle (`STARTED`/`RUNNING`/`WAITING_HUMAN`/`WAITING_EVENT`/`SUSPENDED`/`COMPLETED`/`FAILED`/`CANCELLED`) with `.pause()`/`.unpause()`/`.cancel()`/`.retry()`/`.fork()`/`.replay()`/`.wait_for_event()` layered on top of the existing `Agent.run()`/`.resume()`, which remain unchanged and still return a plain `RunResult`.

## Q1: The module docstring says LangGraph's `update_state()` on a reducer-typed `messages` channel was "verified empirically" to append rather than replace. Walk through exactly what that means and why it makes truncating history in place for `retry()` unsafe.

`AgentState`'s `messages` field is declared `Annotated[list, operator.add]` on the LangGraph engine — a reducer-typed channel, meaning every value passed to that channel via `update_state()` gets *combined* with whatever's already there using `operator.add` (list concatenation), not assigned outright. The docstring states this was confirmed live: "seeding an already-invoked thread with a shorter 'replacement' list just concatenates it onto the existing history." So a naive `retry()` implementation that tried to truncate an existing thread's history back to before the failed turn by calling `graph.update_state({"messages": shorter_list}, ...)` would not actually shorten anything — LangGraph would append `shorter_list` onto the *existing*, still-full history, producing a longer, corrupted transcript rather than a clean rollback. This is precisely why `retry()` is built on `fork()` instead (line ~140): `fork()` always seeds a **brand-new**, empty thread, where appending onto nothing is exactly equivalent to setting — the one truncation-avoiding operation verified safe on the reducer-typed channel.

## Q2: `fork()` calls `self.agent.graph.update_state(...)` directly. `Agent.graph` is a property returning `self._runner.graph` — the graph for `Agent`'s single, construction-time-default runtime. Trace whether `Run` ever supports per-call `runtime=` overrides the way `Agent.run`/`.arun`/`.stream`/`.resume` do, and what that means for `fork()`/`retry()`.

It doesn't. `Run.run()` (line ~89) calls `self.agent.run(message, context=self.context)` with no `runtime=` argument at all, and `Run.resume()` (line ~100) does the same for `self.agent.resume(...)`. Since `Agent.run`/`.resume` both accept an optional `runtime: str | None = None` parameter that, when omitted, falls back to `self.runtime` (the construction-time default), every `Run` is permanently bound to whichever runtime its `Agent` was constructed with — there is no way to construct a `Run` (via `Agent.start()`) against a non-default runtime, and no way to override it per-call the way `Agent.run(msg, runtime=...)` allows. This makes `fork()`'s direct use of `self.agent.graph` (always the default-runtime graph) internally consistent — since a `Run` can never have executed against any other runtime's graph in the first place, there's no scenario where `fork()` seeds "the wrong engine's graph." But it does mean `Run` is a strictly narrower entry point than `Agent` itself: a caller who wants both the formal lifecycle `Run` provides *and* a non-default runtime must either construct `Agent(..., runtime=<the one they want>)` up front, or forgo `Run` and manage lifecycle manually via bare `Agent.run`/`.resume` calls with an explicit `runtime=` each time.

## Q3: `fork()` constructs `new_run.result = RunResult(content=source[-1].get("content", ""), ...)` without ever invoking the engine. What happens if `source`'s last message has `role: "user"` rather than `"assistant"` — e.g., forking from a history captured mid-turn, before any reply exists?

`fork()`'s fallback logic (line ~150) is `source = messages if messages is not None else (self.result.messages if self.result else [])` — if a caller explicitly passes `fork(messages=some_list)` where `some_list`'s last entry happens to be a user message (for instance, forking from `self._pre_turn_messages`, as `retry()` does at line ~140, which is captured *before* the turn that produced a reply), then `source[-1].get("content", "")` (line ~158) grabs that user message's own content — not an actual agent reply — and stores it as `new_run.result.content`. A caller who calls `run.fork(messages=pre_turn_snapshot)` and immediately reads `forked_run.result.content` expecting "the agent's last reply" would instead get back the user's own last message verbatim, with `new_run.status` set to `COMPLETED` (line ~157) as if a real turn had actually finished. This is a real, uncaught correctness gap: the code has no check for which role `source[-1]` actually is before treating its content as "the reply."

## Q4: `Run.cancel()` sets `self.status = RunStatus.CANCELLED` and drops `self._event_subscription`, but never touches `self.context.cancellation_token`. What actually happens if you call `.cancel()` on a `Run` whose `.run()` call is currently executing synchronously on a different thread?

Nothing stops the in-flight call. `Run.run()` only checks `self.status` **before** starting (`if self.status == RunStatus.CANCELLED: raise RuntimeError(...)`, line ~81) — there's no check *during* execution, and `Run.cancel()` (lines ~126–129) doesn't set or touch any `CancellationToken` that the executing turn could observe cooperatively (nor would it help if it did, since — per the `core_execution_context` Q&A — `native_engine.py` never actually checks `cancellation_token` at all today). So calling `run.cancel()` from one thread while `run.run(message)` is executing on another thread does not interrupt that call in any way; the in-flight call runs to completion (or to its next HITL pause), and when it finishes, `Run.run()`'s own `self._apply(result)` (line ~89, inside the `try`) unconditionally sets `self.status` to either `WAITING_HUMAN` or `COMPLETED` — **silently overwriting** the `CANCELLED` status that was set moments earlier. This is a genuine, unguarded race: a "successfully cancelled" `Run` can have its cancellation clobbered by an in-flight call that was already running when `.cancel()` was invoked, with no error or warning that this happened.

## Q5: `Run.cancel()`'s comment says "InMemoryEventBus/EventBus has no unsubscribe; drop our own reference so the closure becomes a no-op below." Trace exactly what "below" refers to, and what actually leaks.

"Below" refers to `wait_for_event()`'s inner `handler` function (lines ~178–182): `if self.status != RunStatus.WAITING_EVENT: return` is the guard that makes the closure a no-op once `.cancel()` has flipped `self.status` away from `WAITING_EVENT`. `Run.cancel()` itself can't remove `handler` from the `EventBus`'s subscriber list — `bus.subscribe(topic, handler)` (line ~184) was already called, and neither `EventBus` nor `InMemoryEventBus` (per the comment) exposes any unsubscribe method — so the closure, and everything it captures by reference (`self` — the entire `Run` object, including its `agent`, `context`, and any `result`), remains registered on the bus's subscriber list indefinitely, for the lifetime of the `EventBus` instance itself. `Run.cancel()`'s only recourse is dropping `self._event_subscription` (its own local reference to the `(bus, topic)` pair) so that *if* the event bus is ever garbage-collected or the topic re-created, this particular `Run` doesn't hold a reference back to it — but the reverse reference (the bus holding the `Run` alive via the subscribed closure) is never broken. For a long-running process where `wait_for_event()` is called frequently and topics persist for the process's lifetime, this leaks one dead `Run` object (and everything it transitively references) per abandoned/cancelled `wait_for_event()` call — a real, acknowledged-in-comment but structurally unfixed memory-growth pattern.

## Q6: Why is `COMPLETED` deliberately excluded from `_TERMINAL = (RunStatus.FAILED, RunStatus.CANCELLED)`? What would break if `pause()`/`.run()` refused a `COMPLETED` run the same way they refuse `FAILED`/`CANCELLED` ones?

The comment on line ~53 states it directly: "COMPLETED is 'this turn is done', not 'dead' — `.run()` stays callable." A multi-turn conversation naturally cycles through `COMPLETED` after every successful turn — `Run.run()` sets `self.status` to `COMPLETED` (via `_apply`, line ~75) whenever a turn finishes without an approval pause, and the caller is expected to call `.run()` again for the *next* turn of the same conversation. If `COMPLETED` were added to `_TERMINAL`, then `pause()` (line ~115, `if self.status in _TERMINAL: raise ...`) would refuse to pause a `Run` sitting between turns, and — more damagingly — nothing currently stops `.run()` itself from being called on a `COMPLETED` `Run` (unlike the explicit `CANCELLED`/`SUSPENDED` checks at the top of `Run.run()`), so if `COMPLETED` were treated as terminal by convention elsewhere, every ordinary multi-turn conversation would need a special exception carved out just to keep working — `FAILED`/`CANCELLED` are the only states that genuinely represent "this Run can never do anything useful again," which is the actual semantic `_TERMINAL` is meant to capture.

## Q7: `pause()`/`unpause()`'s docstring explicitly says this is "not a mid-flight interrupt of an actively executing turn." Why can't it be, structurally — what would have to change in either engine for `pause()` to interrupt an in-flight `.run()` call?

Both engines run one turn **synchronously to completion or to a HITL pause** — there is no yield point inside a single turn's execution where an external `pause()` call (setting a flag on the `Run` object from a different thread) could be observed by the currently-executing `_think`/`_act`/`_critique` loop, because — as established in Q4 and the `core_execution_context` Q&A — neither engine actually polls any external signal during execution today (the `CancellationToken` mechanism that *could* provide such a checkpoint isn't wired into `native_engine.py`, and even where it exists conceptually, it's cooperative/checked-not-preemptive, meaning an in-flight LLM call or tool execution still runs to completion regardless). For `pause()` to genuinely interrupt a mid-flight turn, the engines themselves would need real checkpoint-and-suspend machinery mid-node — either LangGraph's own `interrupt()`-based mechanism repurposed for external pause signals rather than only HITL approval, or `native_engine.py`'s `_drive_stream` loop checking a pause flag between `_think`/`_act`/`_critique` steps (which it currently doesn't) — and even then, an LLM call or tool call already dispatched would still need to run to completion, since neither engine cancels in-flight network calls.

## Q8: Trace `wait_for_event()`'s handler guard `if self.status != RunStatus.WAITING_EVENT: return`. Is this actually race-free, given `Run` has no lock protecting `self.status`?

No — it's a classic check-then-act race with no synchronization. `wait_for_event()` sets `self.status = RunStatus.WAITING_EVENT` (line ~175) and subscribes `handler` to the bus; `handler` (lines ~178–182), when eventually invoked (potentially on a different thread — `EventBus.publish` implementations aren't guaranteed to call subscribers synchronously on the publisher's own thread), checks `self.status != RunStatus.WAITING_EVENT` and returns early if so — intended to guard against a stale/late event firing after the `Run` moved on (was cancelled, or already triggered by an earlier event). But nothing prevents this sequence: `handler` checks `self.status == WAITING_EVENT` (passes), then — before `handler` proceeds to call `self.run(to_message(event))` — a concurrent `.cancel()` call on another thread sets `self.status = CANCELLED`; `handler` then still calls `self.run(...)`, which raises immediately inside `Run.run()`'s own `if self.status == RunStatus.CANCELLED: raise RuntimeError(...)` guard (line ~81) — so at least the *outcome* here is a raised exception rather than silently running on a cancelled `Run`, but that exception propagates out of `handler`, which is itself running inside the event bus's `publish()` call, potentially crashing or corrupting that call's execution for entirely unrelated subscribers on the same bus, depending on how `EventBus.publish` handles handler exceptions — a genuine, if narrow, concurrency hazard with no lock anywhere in this class to close it.

## Q9: `WAITING_TOOL` is defined in the `RunStatus` enum but the module docstring admits it's "reserved but never produced by any code path today." Why ship a dead enum member in a public API rather than adding it only when actually implemented?

The docstring's own justification is structural: "tool execution is synchronous in both engines, so there's no 'waiting on tool completion' state distinct from RUNNING" — meaning today, a tool call executing inside `_act` (native) or the equivalent LangGraph node happens entirely within the same synchronous call that already reports `RUNNING`, so there's genuinely nothing today for `WAITING_TOOL` to distinguish. Reserving the enum member now, ahead of an actual implementation, avoids a breaking change later (adding a new `RunStatus` member is backward-compatible for anyone doing an equality check like `status == RunStatus.RUNNING`, but anyone who wrote an *exhaustive* `if/elif` chain or `match` statement over every current `RunStatus` value, assuming the set was closed, would need to revisit it whichever way the member was introduced) — the trade-off is that a reader of the public `RunStatus` enum today sees eight members, one of which can never actually occur, and has to consult the module docstring (not the enum itself) to learn that fact; nothing about `WAITING_TOOL`'s definition signals "this is aspirational" versus "this is a real, reachable state" the way, say, a code comment directly on the enum member would.

## Q10: How does `Run`'s lifecycle model compare to Temporal's actual workflow execution states, or to how LangGraph itself represents interrupt/resume? What does `Run` add on top of bare `Agent.run()`/`.resume()`, and what does it still not give you?

Temporal's workflow execution states (Running, Completed, Failed, Terminated, Canceled, ContinuedAsNew, TimedOut) are backed by Temporal's own durable event-history log — every state transition is itself a durably-persisted event, survivable across worker crashes and process restarts, with the workflow's execution genuinely resumable from exactly where it left off. `Run`'s states are a plain in-memory Python object's attribute (`self.status`) with **no persistence of its own** — a process restart loses every `Run` object and its lifecycle history entirely, regardless of whether the underlying `Agent`/engine happens to have durable state (via a LangGraph checkpointer or `NativeEngine`'s optional `StateStore`). What `Run` adds over bare `Agent.run()`/`.resume()` is a structured, named-state way to reason about a conversation's position (was it waiting on a human, an event, is it paused, did it fail) without the caller having to separately track "did the last `RunResult` have `awaiting_approval` set" themselves, plus the `fork`/`retry`/`wait_for_event` conveniences built on top. What it still doesn't give you: durability of the `Run` object itself across restarts, true mid-turn interruption (Q7), or protection against the `cancel()`-during-in-flight-call race (Q4) — it's explicitly a lifecycle *view* layered over the existing engines, not a new execution substrate.

## Q11: `replay()`'s docstring says it's "for audit/debugging, not a deterministic from-a-past-checkpoint re-execution." Why not — what would a real replay require that isn't available here?

`replay()` (line ~166) simply returns `list(self.result.messages) if self.result else []` — the flat list of messages accumulated in the *most recent* `RunResult`, i.e., the current final state of the conversation, not a step-by-step recording of how it got there. A genuine "replay from checkpoint N" feature would require the underlying engine to retain **per-step** history — every intermediate state after each `_think`/`_act`/`_critique` transition, not just the final accumulated state — so that execution could be deterministically re-run forward from any earlier point. The module docstring is explicit that "this codebase's MemorySaver-equivalent checkpointers don't retain per-step history for either engine": LangGraph's default in-memory checkpointer and `NativeEngine`'s own `self._threads` dict both only ever hold the *current* state for a `thread_id`, overwriting it as the conversation progresses, not an append-only log of every historical state snapshot. Building true replay would mean changing both engines' persistence model from "current snapshot" to "full event history," a materially larger change than anything `core/run.py` itself could add unilaterally.

## Q12: What happens if you call `.resume()` on a `Run` whose status is `COMPLETED`, not `WAITING_HUMAN`? Cite the exact guard.

`Run.resume()` (line ~95) begins with `if self.status != RunStatus.WAITING_HUMAN: raise RuntimeError(f"run {self.run_id!r} has nothing to resume (status={self.status.value})")` — calling `.resume()` on a `COMPLETED` `Run` (or any status other than `WAITING_HUMAN`) raises immediately, before ever touching `self.agent.resume(...)`, with an error message naming the actual current status so the caller can see exactly why the call was rejected rather than getting a more opaque failure from deeper inside the engine (which would likely fail differently, e.g., `native_engine.py`'s `_resume_locked` raising `RuntimeError(f"thread {thread_id!r} has nothing pending to resume")` if it were reached with no `_pending` state at all) — `Run.resume()`'s own guard fails faster and with a clearer message than letting the call fall through to the engine layer.

## Q13: `retry()` captures `self._pre_turn_messages` inside `Run.run()` itself — `self._pre_turn_messages = list(self.result.messages) if self.result is not None else []` — **before** the new turn executes (line ~85). Why must this snapshot happen before, not after, the turn that might subsequently fail?

If the snapshot were taken *after* the turn (or, worse, only computed lazily inside `retry()` itself, by which point the turn has already failed), there would be no reliable way to recover "the message history exactly as it stood immediately before the failing turn began" — a turn that raises an exception partway through (e.g., inside `native_engine.py`'s `_think`, per the `core_native_engine` Q&A's timeout-consistency finding) may have already partially mutated `state["messages"]` (appending the user's message before failing to produce a reply), so reading `self.result.messages` *after* a failure would either reflect stale data from the *previous* successful turn (since `self.result` is only updated by `_apply()` on a **successful** return, never inside the `except` block) or, if the engine's mutation leaked through some other path, a corrupted mid-turn snapshot. By capturing `self._pre_turn_messages` from `self.result` (the last known-good, fully-applied result) at the very start of `run()`, `retry()`'s later `self.fork(messages=self._pre_turn_messages)` is guaranteed to seed a fresh thread from a clean, complete prior state — regardless of how badly the just-attempted turn failed or how far it got before raising.

## Q14: `Run.__init__` takes `agent: Agent` directly rather than a bare `WorkflowEngine` or `_CompiledWorkflow`. What does this coupling cost, and could `Run` work against something lighter?

`Run` calls `self.agent.run(...)`, `self.agent.resume(...)`, and `self.agent.graph` (for `fork()`'s `update_state()` call) — all public `Agent` methods/properties, not raw `WorkflowEngine` protocol methods (`build`/`run`/`stream`/`resume`, which take a `compiled` object as an explicit first argument rather than being bound to one internally). Because `Agent` already resolves "which compiled graph, using which runtime" internally via `_runner`/`_runner_for`, `Run` gets that resolution for free by depending on the full `Agent` object rather than needing to separately track a `WorkflowEngine` instance *and* a compiled graph *and* an `AgentConfig` itself. The cost is that `Run` can only ever wrap a full `Agent` — it can't be constructed around a bare `_CompiledWorkflow` (e.g., one of `Workflow.supervisor(...)`'s multi-agent topology outputs) or a raw `WorkflowEngine`+compiled-graph pair directly, meaning the formal lifecycle/`fork`/`retry`/`wait_for_event` conveniences `Run` provides are currently only available for single-agent `Agent.start(...)` calls, not for any `Workflow.*` topology — a caller running a supervisor/swarm/etc. topology has no `Run`-equivalent lifecycle wrapper available to them at all.

## Q15: Why does `fork()` generate its new thread ID as `f"{self.context.resolved_thread_id()}-fork-{uuid.uuid4().hex[:8]}"` — an 8-hex-character suffix — rather than a full UUID? Is there a meaningful collision risk?

An 8-hex-character suffix (32 bits of entropy) gives roughly a 50% collision probability only after around 77,000 forks *of the exact same parent thread* (via the birthday-paradox approximation √(2^32) ≈ 65,536, adjusted for the 50% threshold), which is a vanishingly unlikely volume for any single conversation thread to be forked that many times in practice — the intent is clearly a short, human-readable-ish thread ID suffix rather than a strictly collision-proof identifier, prioritizing readability (`"t1-fork-a3f9c21b"` is more legible in logs/debugging than a full 32-character UUID appended) over cryptographic collision resistance. Given `fork()` is explicitly documented as a debugging/exploration/retry tool rather than a high-volume production primitive, this is a reasonable trade-off — but it is a real, if extremely unlikely, latent bug: two concurrent `fork()` calls against the same parent thread that happened to produce colliding 8-hex suffixes would silently create the same `thread_id` for two logically distinct forks, with the second `update_state()` call overwriting the first fork's seeded history before either one had actually run.

## Q16: What is a concrete limitation of this module you'd fix given more time?

The `cancel()`-during-in-flight-call race from Q4 is the most consequential: `Run.cancel()` provides no actual interruption mechanism and can have its effect silently clobbered by an in-flight call's own `_apply()` overwriting `CANCELLED` back to `COMPLETED`/`WAITING_HUMAN` once that call finishes — a caller who calls `.cancel()` and later checks `run.status` could see a status that contradicts what they explicitly asked for, with no error or warning anywhere in the process. A more robust design would have `Run.run()`/`.resume()` check `self.status == RunStatus.CANCELLED` again immediately before calling `self._apply(result)` (not just at the very start) and refuse to apply a result to an already-cancelled `Run`, discarding the just-computed result instead of silently accepting it — closing the specific race traced in Q4 without requiring the deeper (and much larger) work of making cancellation genuinely preemptive inside either engine.
