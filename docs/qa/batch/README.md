# agent_foundry/batch.py — Q&A

`run_batch` runs a compiled graph *N separate times* over N independent items — offline scoring, a nightly re-classification job, bulk outreach — each with its own thread and checkpointer state, no shared turn; `IntervalScheduler` is the zero-dependency default for "run this every N seconds" on a background daemon thread.

## Q1: How does `run_batch` differ semantically from `orchestration.build_fanout_graph`? Both parallelize work — what's the actual boundary between them?

The module docstring draws this distinction explicitly: `build_fanout_graph` parallelizes sub-tasks *within one live turn of one graph* — LangGraph's `Send` mechanism dispatches multiple `think()` invocations that all share the *same* compiled graph, the same `thread_id`, and, notably, the same `AgentState`/`FanoutState` checkpointed together as one unit (which is exactly why `build_fanout_graph` forbids `AgentConfig.critique` — see `orchestration.py`'s own Q&A on that race). `run_batch` instead runs a compiled graph *N separate times*, each against its own distinct thread id and its own independent checkpointer state (`thread_id_fn` derives a fresh id per item), with genuinely no shared turn or shared state between items at all — two items processed by the same `run_batch` call never see each other's conversation history, never share a `critique_retries` channel, and would never race on any shared graph-state field, because there isn't one. Fan-out is "one specialist applied to N inputs *within* a live conversation turn"; batch is "one graph run N completely independent times," which is why it composes safely with a graph that *does* use `AgentConfig.critique`, where `build_fanout_graph` explicitly cannot.

## Q2: Walk through `run_batch`'s default `thread_id_fn`. What would go wrong if two items in the same batch shared a `thread_id`?

The default is `thread_id_fn or (lambda item: f"batch-{uuid.uuid4().hex}")` — a fresh, random UUID-suffixed id generated independently for every item, guaranteeing no two items in a batch collide by default. If a caller supplied a custom `thread_id_fn` that happened to map two different items to the same `thread_id` (e.g., deriving it from a field that isn't actually unique across the batch), both items' `graph.invoke()` calls would checkpoint against the *same* conversation thread — item B's turn would be appended onto item A's message history (since the checkpointer accumulates state per thread id), meaning item B's LLM call would see item A's unrelated conversation as prior context, producing a nonsensical or leaked-context reply, and any budget/cost tracking keyed by that shared thread id (`RunBudget.spend(thread_id=...)`) would incorrectly combine both items' spend into one ceiling. This is precisely the failure mode the random-UUID default exists to prevent by construction.

## Q3: Why does `run_batch` use `ThreadPoolExecutor` + `executor.map` rather than `asyncio.gather`, given the same synchronous-`graph.invoke()` constraint discussed for `orchestration.py`'s tool dispatch?

The reasoning is identical to `_dispatch_tool_calls` in `orchestration.py`: `graph.invoke()` is a synchronous, blocking call — LangGraph's compiled graph doesn't expose a coroutine-native way to run many independent invocations concurrently from plain synchronous code, and `run_batch` itself is a plain `def`, not `async def`. `ThreadPoolExecutor` gives genuine OS-level concurrency for these blocking calls (each `run_one(item)` runs on its own worker thread, and I/O-bound work like an LLM API call releases the GIL while waiting on the network, so real overlap happens even under CPython's Global Interpreter Lock) without requiring the caller of `run_batch` itself to be async. `executor.map(run_one, items)` is a clean, ordered way to dispatch every item to the pool and collect results back in the *original* item order (`executor.map` preserves input order in its output, unlike `_dispatch_tool_calls`'s explicit "completion order, not `cleared` order" behavior) — a meaningful difference worth noting, since `run_batch`'s `BatchReport.results` therefore lines up positionally with the original `items` list.

## Q4: Trace exactly what happens if `graph.invoke()` raises inside `run_one` for one item in a batch of, say, 100. Does one item's failure crash the whole batch, or corrupt other items' results?

`run_one` wraps the `graph.invoke(...)` call in a `try/except Exception as e:` — any exception raised during that item's graph run (an `LLMGateway` error, a `BudgetExceeded` from `runtime.py`, a `RunCancelled`, a guardrail-triggered failure, anything) is caught and converted into `BatchItemResult(item_id=thread_id, ok=False, error=str(e), latency_ms=...)` rather than propagating further. Since each item runs on its own worker thread with its own independent `try/except`, one item's exception has no way to affect any other item's execution or result — `executor.map` will still return a `BatchItemResult` for every item, successful or not, and `BatchReport.results` ends up with a mix of `ok=True` and `ok=False` entries rather than the whole batch aborting because one item failed. This is a genuinely useful isolation property for exactly the offline/bulk use cases this module targets — you want a full report of what succeeded and what didn't, not a batch that dies on the first failure.

## Q5: `orchestration.py`'s `_dispatch_tool_calls` special-cases `len(cleared) <= 1` to skip thread-pool overhead for the common single-call case. `run_batch` doesn't do anything analogous — why not?

`_dispatch_tool_calls` optimizes for the very common case of a single tool call per turn, where spinning up a `ThreadPoolExecutor` for exactly one task is pure overhead relative to the (often fast, sub-second) cost of the tool call itself. `run_batch`'s items, by contrast, are each a full graph turn — potentially involving one or more LLM calls, several tool invocations, guardrail checks, and critique gating — which is orders of magnitude more expensive per item than a single tool call. The fixed cost of creating a `ThreadPoolExecutor` (a handful of milliseconds) is negligible relative to even one item's graph run, so there's no meaningful performance argument for special-casing a batch of size 1 the way there is for special-casing a single tool call inside one turn — the overhead this optimization would save is trivial compared to what it saves in `_dispatch_tool_calls`'s much higher-frequency, much cheaper-per-call context.

## Q6: What happens if `run_batch` is called with `items=[]`? Walk through `BatchReport.success_rate`'s guard.

`executor.map(run_one, [])` produces an empty iterator, so `results = list(executor.map(...))` is `[]`, and `BatchReport(results=[])` is constructed with an empty list. `success_rate` is a property computing `sum(1 for r in self.results if r.ok) / len(self.results) if self.results else 0.0` — the `if self.results else 0.0` guard specifically prevents `ZeroDivisionError` on an empty results list, returning `0.0` rather than crashing. This is a defensible but slightly ambiguous default: `0.0` reads as "the batch failed," when the more precise meaning is "there was nothing to succeed or fail at all" — a caller checking `report.success_rate == 0.0` to detect a failing batch would get a false positive for the genuinely different case of an empty batch, since both produce the identical `0.0` value with no way to distinguish them from `success_rate` alone (a caller would need to separately check `len(report.results) == 0`).

## Q7: Walk through `IntervalScheduler.schedule()`/`tick()`/`_arm()`. Is the resulting interval truly periodic, or does it drift?

`schedule(fn, every_seconds)` generates a `handle`, defines `tick()` (which checks `_cancelled`, calls `fn()`, then re-arms itself via `self._arm(handle, tick, every_seconds)` if still not cancelled), and calls `_arm()` once immediately to start the chain. `_arm()` creates a `threading.Timer(every_seconds, tick)`, a daemon thread that fires `tick` once after `every_seconds` elapses. Critically, each `_arm()` call for the *next* tick happens only *after* the current `fn()` call has already returned — meaning the true interval between two consecutive executions of `fn()` is `every_seconds` plus however long the previous `fn()` call itself took to run, not a fixed wall-clock cadence measured from a stable origin point. If `fn()` takes, say, 2 seconds and `every_seconds=10`, the real period between invocations drifts to 12 seconds, not 10 — under sustained load where `fn()`'s runtime grows, this compounds indefinitely rather than self-correcting, which is a real, honest limitation compared to a scheduler that measures intervals from a fixed origin (like a proper fixed-rate `cron`-equivalent) rather than chaining relative to the previous call's completion.

## Q8: What happens if `fn()` itself raises an exception inside `tick()`? Trace exactly what the caller of `schedule()` observes.

There is no `try/except` around the `fn()` call inside `tick()` at all. An exception raised inside `fn()` propagates up through `tick()`, which is running as the target of a `threading.Timer`'s internal thread — `threading.Timer` (via `Thread.run()`'s own internal exception handling) doesn't crash the whole process or the calling thread; it prints an unhandled-exception traceback to `stderr` via the thread's default excepthook and that worker thread simply terminates. Critically, because `self._arm(handle, tick, every_seconds)` for the *next* tick is only ever reached in the code path *after* `fn()` returns successfully, an exception in `fn()` means that re-arm call is never reached — the entire recurring schedule silently stops firing forever, with nothing more visible to the caller of `schedule()` than a stderr traceback that's easy to miss in a production log stream, and no exception, callback, or status flag surfaces back through `IntervalScheduler` itself to signal "this job died." This is a real, honest limitation: a single transient failure in `fn()` permanently kills the recurring job rather than being retried or even cleanly reported.

## Q9: Walk through a race between `cancel()` and an in-flight `tick()`. Is cancellation preemptive or cooperative, and what's the practical consequence?

`cancel(handle)` adds `handle` to `self._cancelled` and calls `timer.cancel()` on the currently-armed `threading.Timer`. If `tick()` is already *executing* `fn()` at the moment `cancel()` is called (the timer has already fired and its callback is mid-run), `timer.cancel()` is a no-op — `threading.Timer.cancel()` can only prevent a *not-yet-fired* timer from firing, it cannot interrupt an already-running callback. So the currently in-flight `fn()` call runs to completion regardless of when `cancel()` was requested; only the *next* scheduled re-arm is actually prevented, because `tick()` checks `if handle not in self._cancelled` before calling `self._arm(...)` again. This is a cooperative, not preemptive, cancellation model — the exact same posture `orchestration.py`'s own `_check_cancellation`/`CancellationToken` documentation describes for run cancellation elsewhere in the framework ("cooperative, checked only at loop-safe points, not preemptive"). The practical consequence: a caller calling `cancel()` should expect "at most one more `fn()` execution may still happen," not an immediate guaranteed stop.

## Q10: Why does the module docstring explicitly state `IntervalScheduler` "is not a cron-expression engine," and what does it recommend instead?

`IntervalScheduler.schedule(fn, every_seconds)` only supports a fixed numeric interval — "run this every N seconds" — with no concept of calendar-aware scheduling (e.g., "every weekday at 9am," "on the first of the month"). The module docstring is explicit that this is deliberate, not an oversight: "It is not a cron-expression engine — swap in `croniter` behind the same `Scheduler` protocol if a team needs real cron syntax; unbuilt here on purpose rather than faked with a heuristic parser." This is a notably honest design stance — rather than shipping a half-correct, ad-hoc parser for a subset of cron syntax (which would inevitably surprise someone relying on a cron feature it doesn't actually support correctly), the module keeps its own implementation deliberately minimal and points to the `Scheduler` Protocol (declaring only `schedule()`/`cancel()`) as the swap point for a team that needs the real thing, mirroring the same "Protocol as the extension point, don't half-build the sophisticated version" philosophy seen in `planning.py`'s `DecisionMaker`/`BanditSelector` split and `escalation.py`'s `Escalator` Protocol.

## Q11: Is `run_batch` itself safe to run concurrently from two different replicas over overlapping item sets, without any additional coordination?

No — `run_batch` has no built-in deduplication, locking, or coordination mechanism of its own. If two replicas each independently call `run_batch` with overlapping (or identical) item lists — say, a scheduled nightly job accidentally triggered twice, or triggered from two different processes — each replica's `thread_id_fn` (default: a fresh random UUID per call) would generate *entirely different* thread ids for what might be logically the "same" item, meaning there's no natural collision to detect even if you wanted one; both replicas would simply run the full graph turn for that item independently and produce two separate results, silently duplicating work (and cost) with no error or warning from either side. Making `run_batch` fleet-safe would require composing it with `distributed.py`'s `RedisLease`, acquired per item (or per whole batch run) before calling `run_one`, so a second replica attempting to process an already-claimed item would fail to acquire the lease and could skip or defer it — this composition isn't implemented anywhere in `batch.py` itself; the module's own scope stops at parallelizing *within* one process's `run_batch` call.

## Q12: Why does `run_batch` expose `thread_id_fn` as a customization point at all, rather than always using a random UUID?

The default random-UUID-per-item behavior guarantees isolation (per Q2) but also means every `run_batch` call starts every item completely fresh — there's no way to re-run the *same* batch job later and have it resume from where a partially-completed prior run left off, since a new random UUID maps to a brand-new, empty checkpointer thread every time. A caller supplying a `thread_id_fn` that derives a *stable* id from the item itself (e.g., `lambda item: f"batch-job-42-item-{item['id']}"`) enables exactly that: if a batch job was interrupted partway through (the process crashed, or was killed after processing half the items), re-running `run_batch` with the same items and the same deterministic `thread_id_fn`, against a durable (non-default) checkpointer, would let already-completed items' graphs recognize they're continuing an existing thread rather than starting fresh — a realistic and valuable use case for large batch jobs that this parameter exists specifically to support, even though `run_batch` itself does nothing to detect or skip already-completed items automatically; that logic would still need to live in the caller's own item-selection step before calling `run_batch` again.

## Q13: `BatchItemResult` records `latency_ms` per item, but is it aggregated anywhere in `BatchReport`?

No — `BatchReport` exposes exactly one derived property, `success_rate`; there is no `p50_latency_ms`, `p95_latency_ms`, `mean_latency_ms`, or any other aggregation of the per-item `latency_ms` values anywhere in this module, despite every single `BatchItemResult` faithfully recording its own `(time.time() - start) * 1000` on both the success and failure paths inside `run_one`. This is a small, genuine gap: the data needed for latency analysis is captured at the right granularity, but a caller wanting to know "what was the p95 latency across this batch" has to compute it themselves by iterating `report.results` and pulling out `.latency_ms` from each — `RedisSLATracker` in `distributed.py`, for comparison, *does* implement exactly this kind of aggregation (`p95_latency_ms()`) over its own recorded outcomes, making the asymmetry between the two modules' otherwise-similar "record outcome, latency" pattern notable.

## Q14: What happens if a batch item's graph turn pauses via `interrupt()` (a tool-approval or critique-escalation HITL gate) instead of completing normally? Trace `run_one`'s behavior precisely.

`run_one` calls `graph.invoke(...)` once and unconditionally reads `result["messages"][-1]["content"]` on success. If that item's turn hits an `interrupt()` — e.g. a tool call requiring approval, or a critique gate's `escalate_threshold` being crossed — LangGraph's `invoke()` returns with a `"__interrupt__"` key set in the result rather than raising an exception, and the `messages` list reflects whatever was appended *before* the pause (potentially a tool-call message, not a final assistant reply). Because `run_one` doesn't check for `"__interrupt__"` at all, it proceeds straight to `result["messages"][-1]["content"]`, which will either raise `KeyError`/`IndexError` if `messages` doesn't have the expected shape (caught by the surrounding `try/except Exception`, producing a generic `ok=False` result that doesn't actually explain "this item is paused awaiting approval") or, more insidiously, silently succeed with `ok=True` and an `output` value that is actually a mid-turn tool result or partial content, not the genuine final answer — reported as a successful batch item when the underlying graph run is actually stuck waiting for a human decision that will never come, since nothing in `run_batch` ever calls a `resume`-equivalent. This mirrors, almost exactly, the same documented blind spot `orchestration.py`'s own `_run_governed_turn` has for blackboard/debate participants — both places in this codebase share the identical "unconditionally read the last message, don't check for a pending interrupt" pattern, and both inherit the same silent-corruption risk from it.

## Q15: Is there any retry logic in `run_batch` for a transient failure — a rate limit, a network blip, a momentary LLM provider outage?

No — each item gets exactly one attempt via `run_one`'s single `graph.invoke()` call; a transient failure (say, an `LLMGateway` timeout or a provider rate-limit error) is caught by the `try/except Exception` and reported as `BatchItemResult(ok=False, error=str(e))`, with no automatic retry, backoff, or re-queueing built into `run_batch` itself. A caller wanting retry behavior for a large batch job has to implement it entirely themselves — typically by filtering `report.results` for `ok=False` entries, re-deriving the corresponding items, and calling `run_batch` again on just that failed subset, possibly with a backoff delay between passes. This is a defensible minimalism for a "run N independent graph turns and report what happened" primitive, but it does mean `run_batch` alone is not a robust, production-grade batch-processing system out of the box — it's the parallel-dispatch-and-collect core that a more complete retry/backoff/dead-letter-queue layer would need to be built around.

## Q16: What's the single most consequential limitation you'd fix in `batch.py` given more time?

The interrupt-blindness from Q14 is the most consequential, because it can produce a *silently wrong* result — an `ok=True` `BatchItemResult` whose `output` isn't actually the final answer, for a graph that's genuinely paused waiting on a human decision — which is a worse failure mode than an honest `ok=False`, since nothing downstream would know to distrust that result without independently re-checking every item's underlying graph state. The fix is small and mirrors what would also fix `orchestration.py`'s equivalent gap: check `"__interrupt__" in result` before reading `result["messages"][-1]["content"]`, and surface a distinct `BatchItemResult` state (not just `ok=True`/`ok=False`, but something like `ok=False, error="awaiting_approval"` or a dedicated third status) so a caller can tell "this item genuinely failed" apart from "this item is correctly paused and needs a human to resume it" — collapsing both into the current two-valued `ok` field loses information a real batch-processing operator would need to act correctly on the results.
