# agent_foundry/benchmark.py — Q&A

A minimal harness for running a suite of `BenchmarkCase`s against any compiled graph and getting back pass/fail plus latency numbers per case (`run_benchmark` → `BenchmarkReport`) — explicitly scoped as the mechanism a team would use to validate against a published benchmark (GAIA, WebArena, SWE-bench) or an internal regression suite, not as a claimed score against any specific one, since running a real published benchmark needs live API access, the actual dataset, and runtime/cost this environment doesn't have.

## Q1: The module docstring is unusually explicit that this "does not ship a claimed score against any specific published benchmark." Why does that distinction matter, and what would be dishonest about claiming a GAIA/WebArena/SWE-bench score without it?

Published agent benchmarks like GAIA, WebArena, and SWE-bench each have their own carefully curated task sets, scoring rubrics, and often non-trivial infrastructure (sandboxed environments, live web access, specific model/tool configurations) — claiming "our agent scores X% on GAIA" implies you actually ran the real GAIA dataset under GAIA's real evaluation protocol. `run_benchmark()` (lines 55-69) is a generic harness: it takes whatever `BenchmarkCase`s you hand it (an `input` string and a `check: Callable[[str], bool]` that decides pass/fail on the agent's final reply) and reports pass rate and latency — it has no GAIA/WebArena/SWE-bench dataset baked in, no knowledge of those benchmarks' specific scoring rubrics, and no live external evaluation harness or sandboxed tool environment wired up. Presenting a number produced by this harness as "our GAIA score" without actually running the real dataset would be a fabricated credential — exactly the kind of marketing fluff a portfolio piece built on "deep, defensible technical mastery" needs to avoid. The docstring's honesty here is itself the interesting engineering decision: it tells you precisely what's real (the mechanism, "proven against a real graph with real cases below" — presumably a test suite exercising this module) versus what would require infrastructure this environment doesn't have (a genuine benchmark run).

## Q2: Walk through exactly what `run_benchmark(graph, cases)` does for one `BenchmarkCase`, including both the success and exception paths.

For each `case` at index `i` (line 57), it resolves a `thread_id`: `case.thread_id or f"bench-{i}-{case.name}"` — so an explicit `thread_id` on the case wins, otherwise one is deterministically derived from the case's position and name, giving every case its own isolated conversation thread by default (important so cases don't accidentally share state via whatever `StateStore`/checkpointer backs the graph). It builds `config = {"configurable": {"thread_id": thread_id}}` and records `start = time.time()`. In the success path, `graph.invoke({"messages": [{"role": "user", "content": case.input}], "thread_id": thread_id}, config)` runs the graph to completion, `reply = result["messages"][-1]["content"]` extracts the final assistant message's content, and `report.results.append(CaseResult(name=case.name, passed=case.check(reply), reply=reply, latency_s=time.time()-start))` records the outcome — `case.check(reply)` is the case's own arbitrary pass/fail predicate over the raw reply text, so pass/fail logic is entirely caller-defined, not baked into the harness. In the exception path (`except Exception as e`), a `CaseResult` is still appended, but with `passed=False`, `reply=""`, the elapsed `latency_s` up to the point of failure, and `error=str(e)` — critically, the loop does not stop or re-raise: `run_benchmark` always processes every case in the suite regardless of earlier failures, and a single crashing case degrades to one failed result rather than aborting the whole benchmark run.

## Q3: Why does `run_benchmark` catch `Exception` broadly (`except Exception as e`) rather than a narrower set of expected error types?

A benchmark suite's entire purpose is to characterize how an agent behaves across a range of inputs, including inputs that might trigger genuinely unexpected failures — a broad `except Exception` ensures that *any* single case's failure (a tool crash, a budget-exceeded exception, a timeout, a malformed response causing an `IndexError` on `result["messages"][-1]`, literally anything) gets captured as one failed `CaseResult` with the actual exception message recorded in `.error`, rather than crashing the entire `run_benchmark()` call and losing every other case's results along with it. This is the right tradeoff specifically *because* benchmarking is meant to be resilient to the very failures it's trying to measure — a benchmark harness that itself crashes on the first agent failure would be nearly useless for exactly the runs where the agent is struggling most (which is often when you most want a report). The real cost of this breadth: `except Exception` also silently swallows genuine programming bugs in the benchmark harness's own code (a typo in `case.check`, a bug in how `case.input` is constructed) that arguably *should* propagate loudly rather than being recorded as if the agent itself failed — there's no distinction in the resulting `CaseResult.error` string between "the agent under test failed" and "the harness itself has a bug," which could mislead someone debugging a suite of failing cases into investigating the wrong system.

## Q4: What happens if `case.check` itself raises an exception (as opposed to the agent's `graph.invoke()` call raising)?

Because the `try`/`except` block in `run_benchmark` (lines 61-68) wraps the entire body — `graph.invoke(...)`, extracting `reply`, and calling `case.check(reply)` — a `case.check` that raises (say, it does `reply.split(",")[2]` and the reply has fewer than 3 comma-separated parts) is caught by the exact same `except Exception as e` handler as an agent-side failure. The resulting `CaseResult` looks identical in shape to a genuine agent crash: `passed=False`, `reply=""` (note: the *actual* reply the agent produced is discarded here, even though it was successfully retrieved before `case.check` raised — `reply=""` in the except branch is a fresh empty string, not the `reply` variable computed moments earlier in the try block, since exception handling in this structure doesn't preserve partial results from the try block), and `error=str(e)` containing whatever exception `case.check` raised. This is a real diagnostic gap: someone reading a `BenchmarkReport.summary()` output can't tell from the report alone whether a given failure was "the agent gave a bad answer" or "the benchmark author's own `check` function has a bug" — both look exactly like a crashed case with a Python traceback message, and the actual (possibly perfectly reasonable) agent reply that would have revealed which is the case is thrown away rather than preserved in the `CaseResult`.

## Q5: `BenchmarkReport.pass_rate` and `avg_latency_s` both guard against an empty `results` list by returning `0.0`. Is `0.0` the right value for `pass_rate` on an empty benchmark, and what would a caller misinterpret from it?

`pass_rate` (lines 37-39) and `avg_latency_s` (lines 41-43) both use the `... if self.results else 0.0` pattern — avoiding a `ZeroDivisionError` on `sum(...) / len(self.results)` when no cases have been run yet or a suite was constructed with zero cases. The problem: `0.0` for `pass_rate` is indistinguishable from "every single case in a real suite failed," which is a meaningfully different (and much more alarming) situation than "no cases were ever run." A caller building a CI gate on `report.pass_rate >= some_threshold` would treat an accidentally-empty case list (e.g. a bug in whatever code assembles `cases` before calling `run_benchmark`, producing an empty list) identically to a total, catastrophic regression — both read as `pass_rate=0.0` — when the right behavior for an empty suite is arguably to skip the gate entirely, or fail loudly with a distinct "no cases were run" signal, rather than silently reporting the worst possible score. Nothing in `BenchmarkReport` distinguishes these two cases; a caller would need to separately check `len(report.results) == 0` before trusting `pass_rate` at all.

## Q6: Walk through `BenchmarkReport.summary()`'s output format and explain what information it captures that raw `pass_rate`/`avg_latency_s` alone don't.

`summary()` (lines 45-52) builds one line per case: `f"{r.name}: {'PASS' if r.passed else 'FAIL'} ({r.latency_s:.2f}s)"`, appending `f" — {r.error}"` only when `r.error` is truthy (i.e., only for cases that hit the exception path — a case that ran successfully but simply failed its `check()` predicate has `error=None` and gets no trailing message, correctly distinguishing "the agent ran fine but gave a wrong answer" from "the agent/harness crashed," at least for cases that didn't hit the ambiguity described in Q4). It then appends a final summary line: `f"\n{passed}/{len(self.results)} passed ({self.pass_rate:.0%}), avg latency {self.avg_latency_s:.2f}s"`. This per-case breakdown is the whole point of `summary()` versus the two bare properties: `pass_rate`/`avg_latency_s` alone tell you the aggregate outcome but nothing about *which specific cases* failed or *why* (their individual error messages) — for actually debugging a benchmark regression (did case #7's tool-selection logic break, or was it purely a latency spike on case #3), you need the itemized per-case view `summary()` provides, not just the two aggregate numbers.

## Q7: `BenchmarkCase.check: Callable[[str], bool]` receives only the agent's final reply text. What kinds of regressions can this harness *not* detect, given that constraint?

Because `check` only ever sees `result["messages"][-1]["content"]` — the final assistant message's text — this harness has no visibility into *how* the agent arrived at that answer: which tools it called, in what order, whether it needed more or fewer steps than expected, how much it cost, whether a guardrail intervened along the way, or whether it recovered from an intermediate tool failure. Two runs that produce byte-identical final replies but take wildly different paths to get there (one calls three tools efficiently, another retries the same tool five times before eventually succeeding) are indistinguishable to this benchmark's pass/fail check — `check(reply)` literally cannot see the trajectory, only the destination. This is a meaningful contrast with `eval.py`'s `TrajectoryReport`/`trajectory_report()`, which is built specifically to capture tool sequence, recovered failures, and guardrail blocks by reading `EvalRecord`s — `benchmark.py` and `eval.py` are complementary for exactly this reason: `run_benchmark` answers "did the agent get the right final answer, and how fast/reliably across a suite," while `trajectory_report` answers "what actually happened along the way for one session." A regression that changes *how* an agent solves a task without changing *what* it ultimately outputs (say, a prompt change that makes it call an extra, unnecessary tool) would show up as a perfectly passing `BenchmarkReport` while being a genuine efficiency/cost regression invisible to this module — you'd need `Metrics`/`CostLedger` (from `observability.py`) or `TrajectoryReport` layered on top to catch it.

## Q8: Compare `run_benchmark`'s cost/latency accounting (or lack thereof) to `core.evalgate.run_eval`'s `Scorecard`, which tracks `avg_cost_usd` and `p95_latency_ms` alongside pass/fail. Why doesn't `benchmark.py` track cost at all?

`CaseResult` (lines 25-30) has exactly four substantive fields beyond `name`: `passed`, `reply`, `latency_s`, and `error` — no cost field anywhere, and `run_benchmark` never reads `agent.config.budget` or any cost-tracking mechanism the way `core.evalgate.run_eval` does (`cost_usd = agent.config.budget.cost_usd_for(context.resolved_thread_id())`, per that module). This is a real gap given the two modules solve adjacent problems — `benchmark.py` operates directly on a compiled `graph` (calling `graph.invoke(...)` with a raw state dict), not on an `Agent` object with a `.config.budget` attribute the way `run_eval` does; `run_benchmark`'s generic `graph: Any` parameter deliberately doesn't assume anything about the object beyond it having an `.invoke()` method matching the `{"messages": [...], "thread_id": ...}` state-dict convention used across this codebase's native/LangGraph topologies — so it has no guaranteed access point to pull cost data from, unlike `run_eval`, which is coupled specifically to the richer `Agent`/`AgentConfig` object. This is a real, honest architectural tradeoff: `benchmark.py` trades cost visibility for generality (it works against *any* compiled graph, single-agent or multi-agent topology, with zero assumptions about `AgentConfig`), while `run_eval` trades that generality for richer per-case metrics by committing to the `Agent` abstraction specifically.

## Q9: `run_benchmark` derives a default `thread_id` from `f"bench-{i}-{case.name}"`. What happens if two `BenchmarkCase`s in the same suite have the same `name` and neither sets an explicit `thread_id`?

Because the index `i` (the position in the `cases` list, from `enumerate(cases)`) is always part of the default thread id, `f"bench-{i}-{case.name}"` is guaranteed unique across a single `run_benchmark()` call even if two cases share the exact same `name` — case index 2 and case index 5 both named `"login_flow"` would get `"bench-2-login_flow"` and `"bench-5-login_flow"` respectively, never colliding. The `name` component alone is purely cosmetic/for-readability in the id; the `i` prefix is what actually guarantees isolation, which is a good defensive design choice — a naive `f"bench-{case.name}"` (name alone) would have silently collided two duplicate-named cases onto the *same* underlying conversation thread, letting one case's execution state (in whatever `StateStore` backs the graph) leak into and contaminate the other's — cross-case state bleed being one of the worst possible bugs for a benchmark harness whose entire premise is that each case is independently, reproducibly scored.

## Q10: If `run_benchmark` is called twice in a row against the same `graph` with the same `cases` list (no explicit `thread_id`s), do the two runs interfere with each other via shared state?

This depends entirely on what `thread_id` resolution and persistence the `graph`'s underlying `StateStore`/checkpointer actually does, which `benchmark.py` itself has no control over — but the default `thread_id` formula (`f"bench-{i}-{case.name}"`) is a *pure function* of the case's index and name, so a second `run_benchmark()` call over the identical `cases` list in the identical order produces the exact same set of thread ids as the first call. If the graph's checkpointer persists state keyed by `thread_id` beyond a single `invoke()` call (which is the whole point of a `StateStore` in a durable/resumable orchestration system, per this codebase's architecture), the *second* run's `graph.invoke(...)` calls could pick up wherever the *first* run's conversation history left off for each matching thread id, rather than starting fresh — silently turning what looks like "the same benchmark run twice" into "one long continued conversation per case, split across two `run_benchmark()` invocations." Nothing in `run_benchmark` resets or clears prior state for a thread id before invoking — a caller wanting truly independent, repeatable benchmark runs needs to either pass explicit, run-scoped `thread_id`s (e.g. incorporating a run timestamp or UUID) via `BenchmarkCase.thread_id`, or ensure the `StateStore` backing the graph is reset/fresh between runs, since the harness itself provides no isolation guarantee across separate calls to `run_benchmark`.

## Q11: How would `run_benchmark` need to change to support benchmarking a *native multi-agent topology* (supervisor, swarm, etc. from `core/native_orchestration.py`) rather than a single-agent graph — does it already work as-is?

Looking at `run_benchmark`'s actual call — `graph.invoke({"messages": [{"role": "user", "content": case.input}], "thread_id": thread_id}, config)` followed by `result["messages"][-1]["content"]` — this matches the state-dict shape every native topology's `.invoke()` (per the Phase 4 `_drive_stream`-based topologies in `core/native_orchestration.py`) returns for `messages`-based topologies (supervisor, swarm, blackboard, debate). It would *not* work unmodified against `FanoutGraph`/`DagGraph`, whose `.invoke()` returns `{"results": ...}`/`{"items": ...}` rather than a `"messages"` list (per that module's own `_drive_stream` implementations) — calling `result["messages"][-1]["content"]` against a fanout/dag result would raise `KeyError: 'messages'`, an uncaught-by-design mismatch since `run_benchmark`'s `except Exception` would actually catch this and report it as a generic case failure with a `KeyError` message, silently mischaracterizing "this benchmark harness doesn't support this topology's result shape" as "the agent under test failed this case." So `run_benchmark` *does* already work, unmodified, against messages-based topologies (single-agent, supervisor, swarm, blackboard, debate) simply because they share the same output convention — but it's an implicit, undocumented compatibility (nothing in `benchmark.py` asserts or checks the result shape), and it silently mis-attributes a genuine harness/topology-mismatch as an agent failure for fanout/dag topologies rather than raising a clear "unsupported result shape" error.

## Q12: What's the actual statistical rigor of `BenchmarkReport.pass_rate` as a suite-level metric — is a flat pass rate over N cases with no confidence interval a defensible production regression signal?

Exactly as with `eval_dataset.py`'s `compare_to()` deltas and `experiments.py`'s `ExperimentTracker.summary()`, `pass_rate` is a raw fraction with zero statistical framing — no confidence interval, no significance test against a previous run's pass rate, and no accounting for how many cases actually contributed (a 3-case suite's `pass_rate` swinging from `100%` to `67%` because one flaky case failed reads identically, format-wise, to a 300-case suite's genuine 33-point regression). For a small, hand-curated regression suite meant to catch obvious breakage during development, this is a perfectly reasonable, cheap signal — exactly the "is something obviously broken" question a fast dev-loop benchmark should answer. It is not rigorous enough, on its own, to serve as a statistically defensible release gate for a large or noisy benchmark without a human (or an additional statistical layer, like the significance-testing gap already identified in `experiments.py`) interpreting whether an observed pass-rate delta between two runs is a real regression or noise — this module makes no claim otherwise, and its docstring's explicit "does not ship a claimed score against any published benchmark" framing (Q1) is really the same honesty applied one level up: don't over-trust a small, custom-curated pass rate as if it were a rigorously validated external benchmark score.

## Q13: Does `run_benchmark` enforce any per-case timeout? Walk through what happens if `graph.invoke()` hangs indefinitely on one case.

There is no timeout anywhere in `run_benchmark` — `graph.invoke(...)` (line 62-64) is called directly, with no `with_timeout`-style wrapper (unlike `orchestration.py`'s `make_think_node`, which explicitly wraps its LLM call with `with_timeout(call, seconds=config.step_timeout_s)` when a step timeout is configured). If a single case's `graph.invoke()` call hangs — a tool waiting on an external service that never responds, a deadlock in the underlying graph's execution, an infinite loop in some node's logic — `run_benchmark`'s `for i, case in enumerate(cases)` loop simply blocks forever on that one call, and every subsequent case in the suite never runs at all. This is a meaningful gap for a benchmark harness specifically: the entire value of a regression suite is running unattended, often in CI, and a single hung case turning an otherwise-healthy suite into an indefinitely-blocked process (rather than one failed `CaseResult` with a clear timeout error) is a real operational risk — CI systems typically have their own outer timeout that would eventually kill the whole job, but the resulting failure signal ("the CI job timed out") is far less useful than "case #7 hung for 30s and was marked failed with a timeout error, the other 49 cases ran fine."

## Q14: `eval_dataset.py` has explicit baseline persistence (`save_baseline`/`load_baseline`) so a `Scorecard` can be regression-checked against a prior run via `compare_to()`. `BenchmarkReport` has no equivalent. How would you add baseline-comparison to `benchmark.py`, and what would need to change?

`BenchmarkReport` currently has no save/load mechanism at all — `results: list[CaseResult]` lives only in memory for the life of the `run_benchmark()` call, and there's no `to_dict()`/`from_dict()` or JSON persistence anywhere in this file, unlike `eval_dataset.py`'s `BaselineScorecard`, which was specifically designed as a cheaply-serializable duck-typed snapshot of `Scorecard`'s scalar properties (per that module's Q1). A comparable extension here would add a `BenchmarkBaseline` dataclass holding just `pass_rate` and `avg_latency_s` (and per-case pass/fail, if you want case-level regression detection — "case X passed last time, fails now" being a much more actionable signal than a suite-level pass-rate delta alone) plus `save_baseline(report, path)`/`load_baseline(path)` functions mirroring `eval_dataset.py`'s pattern exactly. The one piece that wouldn't translate directly: `CaseResult.reply` holds the full agent response text, which — unlike `Scorecard.cases`' `RunResult` objects — actually *is* cheaply JSON-serializable (plain strings), so a `BenchmarkBaseline` could reasonably persist full per-case results rather than needing `eval_dataset.py`'s more aggressive "only the seven scalar summary properties" reduction; the size/serialization pressure that motivated `BaselineScorecard`'s narrow scope doesn't apply nearly as strongly here.

## Q15: What's a limitation of `benchmark.py` you'd fix given more time?

The most consequential fix is preserving the actual failure-attribution ambiguity from Q3/Q4 — right now, an agent genuinely misbehaving, a `case.check` predicate with its own bug, and a benchmark-harness/topology result-shape mismatch (Q11's fanout/dag `KeyError` case) all collapse into the exact same `CaseResult(passed=False, error=str(e))` shape, making it impossible to tell from the report alone which of the three actually happened. I'd add a distinguishing mechanism — at minimum, catching `case.check`'s exceptions separately from `graph.invoke()`'s (nesting the try/except so a `check`-raised exception gets tagged differently, and critically preserving the actual `reply` the agent produced even when `check` itself blows up, rather than discarding it as the current flat `except` does) — so a benchmark author debugging a failing suite can immediately tell "the agent's answer was fine, my check function has a bug" from "the agent genuinely failed this case." A close second: no cost tracking (Q8) — given this codebase already has a first-class `CostLedger`/budget mechanism in `observability.py`, and `core.evalgate.run_eval` already demonstrates the pattern of pulling `cost_usd` per case, extending `CaseResult` with an optional cost field (populated whenever the underlying graph exposes a budget/cost-ledger, gracefully omitted otherwise) would make `benchmark.py` a genuinely complete regression signal — pass/fail, latency, *and* cost — rather than leaving cost as a blind spot relative to the eval harness it's conceptually adjacent to.
