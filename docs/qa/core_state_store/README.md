# agent_foundry/core/state_store.py — Q&A

This module provides two `StateStore` implementations satisfying the `core.protocols.StateStore` Protocol: `MemoryStateStore` (an in-process, deep-copying, lock-protected reference implementation) and `PostgresStateStore` (a real cross-restart backend using `psycopg2`, recently hardened against SQL injection and a lock-scope concurrency bug in the caller that uses it, `NativeEngine`).

## Q1: `core.protocols.StateStore` specifies exactly three methods — `load`, `save`, `delete` — with no separate `checkpoint()`. Why?

The `StateStore` Protocol's own docstring (`core/protocols.py`, lines 80-83) states this explicitly: "no separate `checkpoint()` alongside `save()`: for a plain per-thread state dict there's no distinct 'durable snapshot' operation that isn't just 'save now,' so a fourth method would be a name with no different behavior behind it." This is a deliberate minimalism: `StateStore` is a key-value contract for one `run_id`'s current state, not a versioned event log or a snapshot/diff system — every `save()` call *is* the durable-write operation, so a `checkpoint()` alias would just be a second name for the same thing, adding API surface without adding capability.

## Q2: Why is `StateStore` deliberately synchronous rather than async, given `Agent` exposes `.arun`/`.astream`/`.aresume`?

Per `core/protocols.py`'s docstring (lines 85-91): this matches every other Protocol in that module (`Tool`/`Memory`/`WorkflowEngine`) — the codebase's async surface is "a non-blocking layer wrapped around sync primitives (`asyncio.to_thread` for native, LangGraph's own off-thread scheduling for langgraph), not an async-native rewrite of the core loop." Making `StateStore` async-only would be "the one place that decision got silently reversed" — i.e., it would break the architectural consistency that every core primitive is sync-first, with async support layered on top generically (via `asyncio.to_thread`) rather than duplicated per-primitive. The practical implication: `PostgresStateStore.load()`/`.save()`/`.delete()` make blocking `psycopg2` calls, and when invoked from an async code path, the *caller* is responsible for offloading that blocking call to a thread (`asyncio.to_thread`), not this module.

## Q3: Why do `MemoryStateStore.save()` and `.load()` both `copy.deepcopy()` the state rather than a shallow copy or no copy at all?

Because the state dict nests a *list of message dicts* (`state["messages"]`, per `NativeEngine`'s own state shape), not just flat scalar values — a shallow copy would copy the top-level dict but leave the inner `messages` list (and each message dict inside it) shared by reference. Concretely, without `deepcopy`: a caller calls `load(run_id)`, gets back a dict whose `"messages"` list is the *same list object* stored internally; the caller appends a message to it (e.g., while building a modified state to eventually `save()`) — that mutation would already be visible to any other caller calling `load(run_id)` again *before* `save()` is ever called, silently leaking uncommitted, in-progress mutations into what's supposed to be an isolated read. `deepcopy()` on both `load()` (line 47) and `save()` (line 51) closes this in both directions: a caller mutating what `load()` returned can never reach back into the store's internal state, and mutating the object the caller *passed into* `save()` afterward can't retroactively change what was stored either. The docstring makes the parity explicit: this is "the same guarantee a real Redis/Postgres backend gets for free from serializing on the way in and out" — deep-copying is `MemoryStateStore`'s stand-in for the isolation that real serialization (JSON/pickle over the wire) provides automatically for network-backed stores.

## Q4: Is `MemoryStateStore`'s `threading.Lock` actually necessary, or is it redundant given CPython's GIL already makes individual dict operations atomic?

Each of `load()`, `save()`, `delete()` performs a single logical operation under the lock — a dict `get`, a dict `set` (preceded by a `deepcopy` call, which itself doesn't touch `self._states`), and a dict `pop`. Under CPython's GIL, each of those individual dict operations would already be atomic on its own even without a lock. So in the *current* implementation, the lock's marginal correctness value over pure GIL atomicity is genuinely small for today's three methods. Where the lock earns its keep is (a) documentation and intent — an explicit `threading.Lock()` signals unambiguously "this class is meant to be called from multiple threads concurrently," which a bare unguarded dict does not, and (b) forward-compatibility and non-CPython correctness — if a future version added any multi-step read-modify-write operation (e.g., a `compare_and_swap`, or the `deepcopy` inside `save()` growing to synthesize the new state from the old one), the lock would already be there to make that safe, and on interpreters without a GIL (PyPy's STM experiments, or CPython 3.13's free-threaded build), individual dict operations are not guaranteed atomic in the same way, so the explicit lock is the only thing making this class correct under those runtimes at all.

## Q5: Describe the SQL injection vulnerability that existed in `PostgresStateStore` before commit `cad0eed`, precisely.

Before the fix, `PostgresStateStore.__init__` stored the caller-supplied `table` argument as a plain string (`self._table = table`) and every SQL statement built its query via an f-string directly interpolating that value: `cur.execute(f"CREATE TABLE IF NOT EXISTS {self._table} (run_id TEXT PRIMARY KEY, state JSONB NOT NULL)")`, and likewise for `SELECT`, `INSERT ... ON CONFLICT`, and `DELETE`. Because `table=` is a constructor parameter — caller-supplied, and in a real deployment plausibly sourced from configuration, an environment variable, or (in a worse scenario) something derived from tenant/user input — any value containing SQL syntax (e.g., `"agent_state; DROP TABLE users; --"`) would be spliced verbatim into the executed statement. Crucially, the existing `%s`-parameterized placeholders for `run_id`/`state` in the same queries did **not** protect against this: parameterization (`cur.execute(query, (run_id,))`) only ever protects *values* substituted into a query, never *identifiers* like table names — psycopg2 (like virtually every DB-API driver) has no `%s`-for-identifiers mechanism, because parameterizing an identifier the same way as a value would just produce a quoted string literal (`'agent_state'`) where a bare identifier is syntactically required, producing invalid SQL rather than a safely-escaped one. So the vulnerability specifically lived in the one place `%s` parameterization structurally cannot reach: the table name.

## Q6: How does the fix (`psycopg2.sql.Identifier`/`sql.SQL`) actually close this, and is it applied consistently?

The fix, applied in `__init__` (lines 70-78): `self._table_ident = sql.Identifier(table)` — wrapping the caller-supplied name in psycopg2's `Identifier` type, which knows how to render any string as a properly double-quoted, internally-escaped SQL identifier (so even a table name containing a double-quote or reserved word is rendered safely, not just one containing an obvious `;` injection attempt) — then every query is built with `sql.SQL("... {} ...").format(self._table_ident)`, which composes the identifier into the query template via psycopg2's own SQL-composition API rather than Python string formatting. This produces a `Composed` object that psycopg2's `cursor.execute()` understands natively and renders correctly at execution time, with the identifier escaped exactly the way Postgres itself requires — categorically different from f-string splicing, which has no awareness of SQL syntax at all. The comment left in the code (`"never f-string a table name into raw SQL — table= is caller-supplied"`, line 74) is a durable warning against reintroducing the same mistake. Checking the diff: the fix was applied to **all four** SQL statements that reference the table — `CREATE TABLE IF NOT EXISTS` (`__init__`), `SELECT` (`load`), `INSERT ... ON CONFLICT` (`save`), and `DELETE` (`delete`) — each now imports `sql` locally and uses `sql.SQL(...).format(self._table_ident)` (or, for `CREATE`, formats directly against the identifier), so the fix isn't a partial patch of only the most obviously exploitable statement.

## Q7: Separately from the SQL injection fix, the same commit fixed a lock-scope bug in `NativeEngine._state_for`. What exactly was wrong?

`NativeEngine._state_for(thread_id)` is the cache-first lookup that backs a `StateStore`-wired `NativeEngine`: check the in-process `self._threads` dict first, and on a miss, fall back to `self._state_store.load(thread_id)`. Before the fix, the *entire* cache-miss path — including the call to `self._state_store.load(thread_id)`, real network I/O for a Redis- or Postgres-backed store — ran **inside** `with self._threads_lock:`. `_threads_lock` is a single lock guarding the *whole* `self._threads` dict, not a per-`thread_id` lock — so while thread-A's slow `load()` call was in flight (say, a 5-second query against a loaded Postgres instance), any *other* thread-B calling `_state_for` or `_persist` for a completely unrelated `thread_id` had to wait for that entire 5 seconds before it could even check whether its own thread's state was already cached in memory — a total, unrelated-thread stall caused purely by one slow I/O call, defeating the entire purpose of per-thread concurrency in a multi-session `NativeEngine`.

## Q8: Why didn't the fix switch to a per-`thread_id` lock instead of just narrowing what the global lock covers?

The commit's own reasoning (preserved as a code comment in `native_engine.py`) is that a finer-grained lock isn't needed here because "every actual caller already holds ITS OWN per-thread_id lock (`_lock_for`) for the duration of this call, so two concurrent `_state_for(thread_id)` calls for the SAME thread_id can't happen in practice." In other words, `NativeEngine` already has a *separate*, existing per-thread-id locking mechanism (`_lock_for(thread_id)`, acquired by `run()`/`stream()`/`resume()` before they ever call `_state_for`/`_persist`) that serializes same-thread access at a higher layer — `_threads_lock` only ever needed to protect the *shared dict itself* (creation of new entries, dict-level reads/writes), not cross-thread mutual exclusion for a given `thread_id`'s data. So the fix is: release `_threads_lock` before the slow I/O, do the `load()` unguarded, then re-acquire `_threads_lock` only briefly to commit the loaded result into `self._threads[thread_id]` — narrowing the *scope* of the existing coarse lock to exclude I/O, rather than introducing an entirely new finer-grained locking scheme that would duplicate what `_lock_for` already guarantees.

## Q9: The fixed code re-checks `if thread_id in self._threads: return self._threads[thread_id]` a second time, after re-acquiring the lock post-load. The commit calls this recheck "defensive, not a fix for a reachable race." Explain why the race is believed unreachable, and why the recheck exists anyway.

The reasoning again rests on the higher-level invariant from Q8: because every real caller already holds `_lock_for(thread_id)` for the full duration of a `_state_for(thread_id)` call, two concurrent `_state_for` calls for the *same* `thread_id` should never actually happen — so the specific race the recheck would catch (thread-A starts a cache-miss load for `thread_id="x"`, thread-B *also* misses the cache for the same `"x"` and starts its own load concurrently, then whichever finishes last overwrites the other's committed result) is not supposed to be reachable given how `NativeEngine` is used today. The recheck is included anyway as defense-in-depth: if a *future* caller of `_state_for` ever bypassed `_lock_for` (a new code path added carelessly, or a caller outside `NativeEngine`'s own controlled call sites), the recheck ensures that even in that scenario, the second thread to re-acquire `_threads_lock` after its own `load()` completes will see that another thread already populated `self._threads[thread_id]` in the meantime and will return the already-cached value rather than overwriting it with a possibly-stale (or simply redundant) result of its own `load()` — a cheap, correct safety net for an invariant the code doesn't currently rely on being violated, but also doesn't bet everything on it never being violated.

## Q10: Walk through the durability guarantee difference between `MemoryStateStore` and `PostgresStateStore` if the process crashes mid-run.

`MemoryStateStore` keeps state purely in an in-process dict (`self._states`) — a process crash loses *everything* it holds, with zero recovery possible; its docstring says so directly: "No persistence across a process restart — that's what RedisStateStore/PostgresStateStore are for." `PostgresStateStore`, by contrast, persists into a real Postgres table (`run_id TEXT PRIMARY KEY, state JSONB NOT NULL`) that survives a process crash entirely. The *granularity* of recoverable work depends on how often `_persist()` is called, not on `PostgresStateStore` itself — per `StateStore`'s own docstring: "`_raw()` (the one function every mutating call path already funnels through, at exactly the granularity a think/act/critique step completes) persists on every call." So a `runtime="native"` agent backed by `PostgresStateStore` that crashes mid-run loses at most the *current, in-flight* think/act/critique step — every previously *completed* step was already durably saved to Postgres — and a restart with the same `state_store` wired up and the same `thread_id` would resume exactly from the last completed step via `load()`, not from scratch.

## Q11: What happens if a caller sets `runtime="langgraph"` and also passes `state_store=PostgresStateStore(...)`?

Per `core/protocols.py`'s `StateStore` docstring, final sentence: "`runtime='langgraph'` ignores this field — it gets its own durability from `checkpointer=` instead." This is a real, sharp landmine: passing `state_store=` alongside `runtime="langgraph"` is **silently a no-op** — `state_store.py` itself contains no validation, warning, or error for this combination; a developer who configures `Agent(runtime="langgraph", state_store=PostgresStateStore(...))` expecting Postgres-backed durability would get none, with LangGraph instead relying entirely on whatever `checkpointer=` was (or wasn't) separately configured, and no signal anywhere that their `state_store=` argument was ignored. This is exactly the kind of "two independent durability mechanisms exist for two different runtimes, and the wiring between `runtime=` and which one actually applies is implicit" gotcha that's easy to hit in practice and hard to debug without already knowing this specific docstring caveat.

## Q12: Why does `PostgresStateStore.save()` use an upsert (`INSERT ... ON CONFLICT (run_id) DO UPDATE SET state = EXCLUDED.state`) rather than a plain `INSERT`?

Because `MemoryStateStore.save()` (line 49-51: `self._states[run_id] = copy.deepcopy(state)`) has "overwrite unconditionally" semantics — calling `save()` twice for the same `run_id` just replaces the value, never raises, regardless of whether an entry already existed. For `PostgresStateStore` to be a genuinely interchangeable `StateStore` implementation (the module docstring explicitly notes both are "run against `tests/test_state_store.py`'s own contract tests"), `save()` must match that exact behavior — a plain `INSERT INTO ... VALUES (...)` without `ON CONFLICT` handling would instead raise a unique-constraint violation (`psycopg2.errors.UniqueViolation`) the *second* time `save()` is called for the same `run_id`, since `run_id` is the table's `PRIMARY KEY`. The upsert (`ON CONFLICT (run_id) DO UPDATE SET state = EXCLUDED.state`) makes repeated saves for the same key silently overwrite, exactly matching `MemoryStateStore`'s contract — without it, the shared contract test suite would fail the very first time it exercised "save the same run_id twice," a scenario every real multi-step agent run triggers constantly (one save per think/act/critique step, same `run_id`, over and over).

## Q13: `PostgresStateStore.load()` does `row[0] if isinstance(row[0], dict) else json.loads(row[0])`. Why the conditional — doesn't a `JSONB` column always come back the same way?

Whether `psycopg2` hands back a `JSONB` column value as an already-parsed Python `dict` or as a raw JSON string depends on whether a JSON adapter/typecaster has been registered on the connection (`psycopg2.extras.register_default_jsonb`, or similar) — by default in some psycopg2 configurations/versions, JSONB columns are auto-decoded into native Python objects, while in others (or without the right adapter registered) the driver returns the raw string and the caller must `json.loads()` it themselves. `PostgresStateStore.__init__` here does not explicitly register a JSON adapter, so `load()` defensively handles *both* possible return shapes rather than assuming one — `isinstance(row[0], dict)` short-circuits to using the value directly if the driver already decoded it, and falls back to `json.loads(row[0])` if it's still a raw string. This is a pragmatic hedge against psycopg2 version/configuration variability rather than a guarantee derived from any single documented psycopg2 behavior asserted in this file.

## Q14: Why is `psycopg2` imported lazily inside `PostgresStateStore.__init__` rather than at module level?

Per the module docstring: `psycopg2-binary` is an optional dependency, installed via `pip install agent-foundry[postgres]`, "not a base dependency." Importing it at module level would mean simply importing `agent_foundry.core.state_store` — which also defines `MemoryStateStore`, usable with zero extra dependencies — would fail with `ModuleNotFoundError` for any installation that didn't opt into the `[postgres]` extra, even for code that never touches `PostgresStateStore` at all. Deferring the import into `__init__` (`import psycopg2` and `from psycopg2 import sql`, lines 71-72, and again locally inside each method) means the module imports cleanly everywhere, and the `ModuleNotFoundError` only surfaces at the moment someone actually tries to *instantiate* `PostgresStateStore()` without the optional dependency installed — the failure is deferred to exactly the point where it becomes unavoidable, not the point where it would needlessly block everyone else.

## Q15: `self._conn.autocommit = True` is set in `__init__`. What does that mean for the atomicity of a single `save()` call, and is there any transactional risk?

With `autocommit = True`, every individual SQL statement psycopg2 executes is committed immediately as its own implicit transaction — there is no multi-statement transaction spanning, say, a `save()` call's single `INSERT ... ON CONFLICT` statement, so within that one statement, Postgres's own single-statement atomicity guarantee applies: the upsert either fully commits or fully fails, with no possibility of a "partially written" state row. The risk this setting *does* introduce is only relevant if `PostgresStateStore` ever needed to make multiple related writes atomic together (e.g., writing to two tables, or writing state alongside an audit-log row) — `autocommit=True` would silently make each of those a separate, independently-committed transaction, opening a window where a crash between them leaves the two writes inconsistent. As currently written, every public method (`load`, `save`, `delete`) issues exactly one SQL statement each, so this risk is latent, not actual, in the current implementation — but it's a constraint a future extension to this class would need to remember to address (e.g., by wrapping a genuinely multi-statement operation in an explicit transaction, temporarily overriding `autocommit`).

## Q16: There's no connection pooling, retry-on-disconnect, or reconnect logic in `PostgresStateStore`. Is this production-ready as-is, and what would you add?

Honestly, not fully: `PostgresStateStore` holds a single `psycopg2` connection (`self._conn`) opened once at construction time and never reconnects if that connection drops (a Postgres restart, a network blip, an idle-connection timeout from a proxy like PgBouncer) — every subsequent `load()`/`save()`/`delete()` call would raise a `psycopg2.OperationalError` (or similar) and stay broken for the lifetime of that `PostgresStateStore` instance, with no automatic recovery. Given more time, the concrete additions would be: a real connection pool (`psycopg2.pool.ThreadedConnectionPool`, or moving to SQLAlchemy's engine/pool) so a single instance can serve many concurrent callers without exhausting connections or serializing on one socket; wrapping each database call in `runtime.with_retry` (already available in this same codebase, `agent_foundry/runtime.py`) to transparently recover from a transient disconnect; and a lightweight health check or reconnect-on-failure path so a dropped connection self-heals rather than requiring the whole `PostgresStateStore` object to be recreated.

## Q17: Why does this repo have *two* separate real state-store backends — `PostgresStateStore` here and `RedisStateStore` in `distributed.py` — instead of one file holding every backend?

Per this module's own docstring: "`PostgresStateStore` is the real cross-restart backend with no existing sibling convention in this repo to follow (no psycopg/sqlalchemy usage anywhere else)... see `RedisStateStore` in `distributed.py` (that module's own established home for every other Redis-backed swappable primitive) for the other real backend." The organizing principle is by *technology family*, not by *Protocol implemented*: `distributed.py` is already the established home for every Redis-backed swappable primitive in the codebase (presumably including Redis-backed versions of `RunBudgetLike`/`RateLimiterLike`/etc. from `runtime.py`, per those Protocols' own docstrings about distributed deployments), so a Redis-backed `StateStore` belongs there alongside its siblings for discoverability and shared connection-handling conventions, while Postgres has no existing home in this codebase at all, so `state_store.py` becomes the natural (and only) place for it, sitting alongside `MemoryStateStore` since both are wired identically (`Agent(..., runtime="native", state_store=<either one>)`).

## Q18: Is `PostgresStateStore` itself thread-safe? What happens if two different `thread_id`s' `load()`/`save()` calls race on the same connection concurrently?

Unlike `MemoryStateStore`, `PostgresStateStore` holds **no `threading.Lock`** anywhere, and it shares a single `psycopg2` connection object (`self._conn`) across every call. `psycopg2` connections are not documented as safe for concurrent use by multiple threads issuing statements simultaneously on separate cursors from the same connection without external serialization — while `NativeEngine`'s own per-`thread_id` lock (`_lock_for`) serializes calls *for a given thread_id*, two *different* `thread_id`s can legitimately call `_persist()`/`_state_for()` concurrently (that's the entire point of the lock-scope fix in Q7-Q9 — different thread_ids shouldn't block each other), and both of those concurrent calls would end up issuing SQL through the *same shared connection object* here with no lock protecting it. This is a genuine, unaddressed gap: the very fix that made `NativeEngine`'s cache-miss path correctly allow different `thread_id`s to proceed concurrently (Q7) also means `PostgresStateStore`'s single unshared, unlocked connection is now more likely to actually be hit concurrently by multiple threads than it would have been under the old (accidentally more serializing) lock-scope bug.

## Q19: What does the "shared contract test suite" (`tests/test_state_store.py`, "run against this class too") actually buy, concretely?

Running the *same* test class/functions against both `MemoryStateStore` and `PostgresStateStore` (presumably via parametrization or a shared base test class) verifies genuine behavioral parity between the two implementations of the same Protocol — e.g., a test asserting "calling `save()` twice for the same `run_id` overwrites rather than errors" is exactly the kind of test that would have caught the `save()` semantics mismatch discussed in Q12 (plain `INSERT` vs. upsert) the moment it was written, rather than only in production when a second save for the same thread inevitably happened. This is the same "proof the seam is real" discipline the module docstring explicitly calls out for `MemoryStateStore` itself: "`isinstance(MemoryStateStore(), StateStore)` — proof the same way `core.engines.RUNTIMES` proved `WorkflowEngine` was a real seam" — a shared test suite is the *behavioral* analogue of that structural `isinstance` proof, checked against a live Postgres instance for `PostgresStateStore` specifically (per the fix commit: "Re-verified against a live Postgres instance after the change"), not mocked.

## Q20: Given more time, what's the single most valuable fix to this module?

The most concrete, currently-real gap is Q18: `PostgresStateStore` sharing one unlocked `psycopg2` connection across concurrent calls for different `thread_id`s, in a codebase whose own recent fix (Q7-Q9) specifically increased the likelihood of exactly that kind of cross-thread_id concurrency by removing an accidental serialization point. A connection pool (Q16) would address this directly — each concurrent `load()`/`save()`/`delete()` call checking out its own connection from a pool rather than sharing one mutable connection object — and would also incidentally close the reconnect-on-failure gap from Q16 as a side effect of most pool implementations' health-checking behavior.
