# agent_foundry/planning.py — Q&A

Defines `Objective` (a KPI to optimize for, with a weight) and two `DecisionMaker` implementations — `Planner` (deterministic, KPI-weighted scoring over a `KPIBoard`) and `BanditSelector` (epsilon-greedy multi-armed bandit that learns from observed reward) — plus `StrategySelector`, a rule-based picker for choosing which topology or strategy should handle a given request.

## Q1: Why is `DecisionMaker` a `Protocol` rather than an abstract base class, and what does `BanditSelector` prove about that choice?

`DecisionMaker` declares exactly one method, `choose(self, candidates: dict[str, dict[str, Any]]) -> str`, and nothing in `orchestration.py` or elsewhere in the codebase is typed against `Planner` specifically — every caller only ever needs `.choose()`. A `Protocol` gives structural typing: any object with a matching `choose()` method satisfies the interface without inheriting from anything, which matters because `Planner` and `BanditSelector` are algorithmically unrelated — one scores candidates against a fixed `KPIBoard`, the other learns from an entirely separate stream of observed rewards via `.observe()`, a method that isn't even part of the `Protocol`. If `DecisionMaker` were an ABC, both would still need to inherit from it, but the actual point being demonstrated is that the "same `.choose()` shape, completely different algorithm underneath" swap works with zero coupling between the two classes — the module's own docstring on `BanditSelector` states this directly: it "proves `DecisionMaker` is a real swap point, not just `Planner` renamed." This is exactly the extension point where "a bandit, an ML ranker, a rules engine, or a call out into a different agentic framework's own planner entirely" could be substituted, per `DecisionMaker`'s own docstring.

## Q2: `Planner.score()` and `Planner._ranked_score()` compute genuinely different things from the same objectives. Walk through the divergence and explain why it exists.

`score(context)` evaluates the whole `KPIBoard` against one shared `context` dict via `self.board.evaluate_all(context)`, then computes `sum(results.get(o.kpi_name, 0.0) * o.weight for o in self.objectives) / total_weight` — a plain weighted average of each KPI's *raw* score, with no adjustment for whether that KPI's `direction` is "minimize" or "maximize." `_ranked_score(context)`, used internally by both `choose()` and `rank()`, instead looks up `self.board.kpis.get(o.kpi_name)` for each objective, reads `kpi.direction`, and *inverts* the value (`-value if kpi.direction == "minimize" else value`) before weighting and summing. This divergence is deliberate for the two methods' different jobs: `score()` answers "how good is this single state, in absolute terms" (useful for logging or a threshold check against one candidate), while `choose()`/`rank()` answer "which of several candidates is objectively *best*," where "best" must always mean "highest score" even for KPIs like cost or latency where a *lower* raw value is actually better. Calling `score()` on a cost-heavy context and expecting it to agree with what `choose()` would pick between two candidates would be a mistake — they are not the same computation, and nothing in the API signature warns a caller that `score()` doesn't respect KPI direction the way `choose()`/`rank()` do.

## Q3: `score()` and `_ranked_score()` also handle a missing KPI differently. What's the actual difference, and what failure mode does it create?

`score()` uses `results.get(o.kpi_name, 0.0)` — if an `Objective` references a `kpi_name` that isn't registered on the board (or that `evaluate_all` didn't produce a result for), it's silently treated as a literal `0.0` and still contributes its full configured `weight` to the denominator-normalized average, which can meaningfully *drag down* the overall score for a KPI that was never actually evaluated. `_ranked_score()` instead does `kpi = self.board.kpis.get(o.kpi_name); if kpi is None: continue` — a missing KPI is skipped entirely, contributing nothing to the numerator, though its `weight` is still counted in `total_weight` (computed once, up front, from `self.objectives`, independent of which KPIs actually resolved). Both behaviors are "silent" in the sense that neither raises an error for a typo'd or unregistered `kpi_name` — a caller who misspells an `Objective.kpi_name` gets no exception, just a plausible-looking but quietly wrong score, which is a real, easy-to-hit footgun in a config-driven deployment where `kpi_name` strings are typed by hand.

## Q4: Why does `Planner.choose()` divide by `total_weight` rather than just summing weighted scores directly, and what happens if every objective's weight is `0.0`?

Dividing by `total_weight` normalizes the result into a weighted-average scale (comparable in magnitude regardless of how many objectives are configured or how large their weights are), rather than a weighted-sum whose magnitude would scale with the number of objectives — this matters if `Planner.score()`'s absolute output is ever compared against a fixed threshold, where the meaning of "0.7" shouldn't depend on whether you configured 2 objectives or 20. Both `score()` and `_ranked_score()` guard against a zero-weight-sum with `total_weight = sum(o.weight for o in self.objectives) or 1.0` — if every objective has `weight=0.0` (or `self.objectives` is empty), `sum(...)` evaluates to `0.0`, which is falsy, so `total_weight` falls back to `1.0` rather than raising `ZeroDivisionError`. With an empty `objectives` list specifically, both methods' inner sums are also `0` (nothing to iterate), so the whole computation degrades gracefully to `0.0 / 1.0 = 0.0` rather than crashing — a reasonable, if silent, "no objectives configured" default.

## Q5: Trace `BanditSelector.choose()`'s exploration logic. Why does an unexplored candidate take unconditional priority over the epsilon-greedy random draw?

`choose()` first computes `unexplored = [name for name in candidates if name not in self._rewards]`. If that list is non-empty, *or* a random draw falls under `epsilon`, it returns `random.choice(unexplored or list(candidates))` — meaning any candidate with zero observed rewards is always explored before epsilon-greedy randomness ever kicks in among already-tried options. This ordering is a reasonable "optimistic initialization" instinct: a brand-new option with literally no data should be tried before the algorithm starts trading off exploration versus the current best-known option, since picking a genuinely untested candidate is strictly more informative than a uniformly-random pick among candidates that already have *some* data. Only once every current candidate has at least one observed reward does the function fall through to the pure epsilon-greedy branch: with probability `epsilon`, pick uniformly at random among all candidates (even already-explored ones, to keep exploring); otherwise exploit the best-known option via `max(candidates, key=lambda name: sum(self._rewards[name]) / len(self._rewards[name]))` — the highest observed mean reward.

## Q6: What are `BanditSelector`'s honest limitations compared to a more sophisticated multi-armed-bandit algorithm, and how would you fix them given more time?

Several: `epsilon` is a fixed constant with no decay schedule — a mature bandit typically anneals exploration down over time as confidence in the best arm grows, but here the exploration rate never changes no matter how many observations accumulate, so it keeps randomly exploring a candidate it's already confident is worse, forever, at the same rate as on day one. There's also no confidence-interval reasoning (no UCB-style bonus for under-sampled arms) — a candidate with one lucky high reward and a candidate with a thousand consistent observations at a slightly lower mean are treated identically by the plain arithmetic-mean comparison in the exploit branch, which can lock onto a noisy early winner. Finally, `_rewards` is a plain in-process `dict[str, list[float]]` with no persistence — a process restart resets all learned reward history to empty, so a production multi-replica deployment (the exact fleet-safety problem `distributed.py` solves for budgets, rate limits, and caches) has no `RedisBanditSelector` counterpart; each replica would learn its own independent, restart-fragile reward history rather than sharing one fleet-wide model.

## Q7: Why does `StrategySelector.select()` use first-match-wins rule ordering instead of scoring every rule and picking a "best" match?

`StrategyRule.when` is a bare `Callable[[dict[str, Any]], bool]` — a boolean predicate, not a scored function — so there is no numeric basis on which to compare two matching rules against each other; either a rule's condition holds for the given context or it doesn't. `select()` iterates `self.rules` in the order given and returns the first `StrategyRule` whose `when(context)` returns `True`, falling back to `self.default` if none match. This makes rule *ordering* a load-bearing part of the configuration: a caller must place more specific conditions before more general ones (the module's own example is `lambda ctx: ctx["complexity"] < 0.3`), because a broader rule placed earlier would shadow a narrower one placed after it and it would never be reached. This is a deliberately simple, predictable "if/elif chain as data" design — the tradeoff is that it pushes correctness onto the caller's discipline about rule order, rather than onto the framework computing which of several matching rules is most specific.

## Q8: Why does `planning.py` depend only on `kpi.py`, deliberately never importing anything from `orchestration.py`?

`StrategySelector.select()` returns a plain string name; what that name actually maps to — a compiled graph, a `build_*_graph` builder callable, anything else — is entirely up to the caller. The module docstring is explicit that this is intentional: "this module doesn't know about `orchestration.py`'s graph builders on purpose." This is the same one-directional dependency discipline seen elsewhere in the framework (`blackboard.py` has no LangGraph dependency; `orchestration.py` imports `Blackboard`, not the reverse) — `planning.py` is a decision-making primitive that composes *underneath* orchestration, never on top of it, which keeps it usable to choose between models, tools, prompts, or anything else "with more than one reasonable option" (per the module docstring) without being coupled to LangGraph or any particular multi-agent topology at all. A caller wires the two together explicitly: e.g., `StrategySelector.select(context)` returns a topology name, and the caller's own code decides that `"supervisor"` maps to a call into `orchestration.build_supervisor_graph`.

## Q9: What happens if `Planner.choose()` is called with an empty `candidates` dict?

`max(candidates, key=...)` on an empty dict (or any empty iterable) raises `ValueError: max() arg is an empty sequence` — there's no guard anywhere in `choose()` or `rank()` against this. This is a real, unhandled edge case: a caller that constructs a candidates dict dynamically (e.g., filtering a list of models down to ones currently available) and ends up with nothing left would get an unhelpful, generic `ValueError` from deep inside `max()`'s builtin implementation rather than a clear, `planning`-specific error message naming what went wrong. `BanditSelector.choose()` has the identical exposure — `random.choice(unexplored or list(candidates))` degrades to `random.choice([])` when `candidates` is empty, raising `IndexError: Cannot choose from an empty sequence`. Neither class defends against this input at its boundary.

## Q10: Why does `Planner` also expose `rank()` in addition to `choose()`, when a typical decision point only needs the single best option?

`rank()` returns every candidate ordered best-to-worst (`sorted(candidates, key=lambda name: self._ranked_score(candidates[name]), reverse=True)`), which is useful precisely when a decision shouldn't be made fully automatically — for example, presenting a human reviewer with the top three alternatives rather than silently committing to the single highest-scoring one, or feeding a full ranking into a downstream process (an A/B test bucketing scheme, a fallback chain that tries the second-best option if the first fails at runtime). `choose()` is the degenerate case of `rank()` — indeed, `choose()` could be implemented as `rank(candidates)[0]`, though the actual implementation computes `max(...)` directly rather than sorting the whole list, which is a minor efficiency difference (`O(n)` versus `O(n log n)`) worth noting for a large candidate set, even though `Planner`'s intended use case — choosing between a handful of models or topologies — makes that difference practically irrelevant.

## Q11: Compare `Planner` and `BanditSelector` as strategies for picking, say, which LLM to route a request to. When would you actually choose one over the other?

`Planner` requires you to already have a scoring function for each candidate — real, measured `cost_usd`, `latency_ms`, or a quality KPI value *known ahead of time* for each option in a given context, which it then weighs deterministically according to configured `Objective`s. This is the right tool when the tradeoffs are explicit and quantifiable up front (you already know model A costs more per token and averages lower latency than model B) and you want a transparent, auditable, reproducible decision — the same `context` always produces the same choice. `BanditSelector` instead requires no upfront scoring function at all; it learns purely from `.observe(option, reward)` calls fed back after the fact from real outcomes, making it the right tool when you *don't* know in advance which option will perform best for a given class of request, and you're willing to accept some ongoing exploration cost (occasionally picking the seemingly-worse option) in exchange for continuously improving the decision as more data arrives. In practice, a `Planner` used for something like model routing gives you predictable, explainable choices from day one; a `BanditSelector` used for the same job gives you an initially worse, but eventually self-correcting, choice — the two are complementary strategies, not interchangeable ones, despite satisfying the same `DecisionMaker` shape.

## Q12: `StrategyRule.when` is a bare callable, while `Planner` scores against a `KPIBoard`. Is mixing these two very different "decision" styles within one module a deliberate design choice or an inconsistency?

It's deliberate, and the module's structure makes the distinction clear rather than papering over it: `Planner`/`BanditSelector` both implement the uniform `DecisionMaker.choose()` shape — pick the best *named option* from a set of candidates, either by scoring or by learned reward. `StrategySelector` solves a genuinely different problem — routing a *single* incoming request/context to exactly one named strategy via ordered predicates, not comparing multiple concrete candidates against each other at all. There is no `StrategySelector.choose()`, and it doesn't implement `DecisionMaker` — it has its own `select(context) -> str` method with entirely different semantics (first-match-wins over rules, not best-scoring-among-candidates). The two abstractions coexist in one file because they serve the same higher-level goal stated in the module docstring ("based on the use case, pick the right architecture") through two different mechanisms: `StrategySelector` for coarse, rule-based, human-authored routing decisions ("if complexity < 0.3, use the cheap path"), and `Planner`/`BanditSelector` for finer-grained, quantitative choices between concrete options. Nothing forces a caller to use one or the other exclusively — they could layer `StrategySelector` to pick a topology, then use a `Planner` within that topology to pick a model.

## Q13: Walk through the docstring's own example — choosing between `"gpt-cheap"` and `"gpt-strong"` using `Planner.choose()`. How does the minimize-direction inversion in `_ranked_score` actually make this work?

Given `candidates = {"gpt-cheap": {"cost_usd": 0.001, "latency_ms": 400}, "gpt-strong": {"cost_usd": 0.02, "latency_ms": 1800}}` and objectives weighted over, say, a `cost_kpi` (direction="minimize") and a `latency_kpi` (direction="minimize"), `_ranked_score` looks up each KPI's `direction` from `self.board.kpis` and computes `kpi.score(context)` for each candidate's context — presumably a KPI whose `score()` returns the raw cost or latency value directly (the module comment notes the KPI's own `score()` "returns the raw minimized quantity"). Because `direction == "minimize"`, `_ranked_score` negates that value (`-value`) before summing — so `"gpt-cheap"`'s low cost (`0.001`) becomes a *large positive* contribution (`-0.001`, i.e., barely penalized) relative to `"gpt-strong"`'s (`-0.02`, more heavily penalized), and similarly for latency. Since `choose()` always picks `max(...)` over `_ranked_score`, and minimizing quantities are negated before the max, the candidate with the *lowest* actual cost and latency naturally produces the *highest* `_ranked_score` — the inversion is exactly what lets a single `max()` call correctly favor "lower is better" KPIs alongside any "higher is better" ones in the same objective set, without the caller having to special-case direction anywhere themselves.

## Q14: `Planner` assumes every KPI's score is on a comparable scale when weighted together — is that assumption enforced anywhere, and what happens if it's violated?

Nothing in `Planner`, `Objective`, or `_ranked_score` normalizes different KPIs' scales relative to each other — a cost KPI valued in raw dollars (e.g., `0.001` to `0.02`) and a quality KPI valued on a `0.0`–`1.0` scale would be summed together with only their configured `weight`s to balance them, and no built-in normalization step reconciles the fact that a `weight=1.0` on a dollar-denominated KPI contributes a vastly different *absolute* magnitude than a `weight=1.0` on a 0–1 quality KPI. This is an implicit assumption the module doesn't document or enforce: it silently trusts that whatever KPIs get registered on the `KPIBoard` and referenced in `Objective`s already return comparably-scaled values (or that a caller has hand-tuned `weight`s to compensate). This is a real, honest limitation for anyone assembling objectives from KPIs with wildly different natural scales — a builder would need to normalize KPI outputs themselves (e.g., scale cost into a 0–1 range against some ceiling) before it would behave sensibly.

## Q15: If you were extending `planning.py`, what's the first thing you'd add, and why?

Given the concrete gaps surfaced above, the most impactful additions would be: (1) a guard in `Planner.choose()`/`BanditSelector.choose()` that raises a clear `ValueError` naming the problem when `candidates` is empty, rather than letting Python's builtin `max()`/`random.choice()` fail with an opaque generic error; and (2) either a normalization step in `Planner` (or documentation making the equal-scale assumption from Q14 explicit and enforced, e.g., requiring every registered KPI's `score()` to already be bounded to `[0, 1]`) so combining differently-scaled objectives doesn't silently produce a nonsensical weighted result. Both are small, surgical additions that don't change the module's existing API shape — they close real edge cases already reachable from the code as written, rather than adding new speculative capability like normalization frameworks or scale-detection heuristics that the module's current minimal-dependency philosophy would likely reject as overreach.
