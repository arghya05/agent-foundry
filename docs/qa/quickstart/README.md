# agent_foundry/quickstart.py — Q&A

**2026-09-28 update:** the historical discussion below predates [governed exports](../../GOVERNED_TOOL_ADAPTERS.md). Raw conversions now require explicit opt-in; current enforcement and compatibility limits are documented there.

`quickstart.py` is a thin wrapper (`plug_and_play_agent`) over the real LangGraph v1.0+ prebuilt agent executor (`langchain.agents.create_agent`), plus a bridge (`to_langchain_tool`/`to_langchain_tools`) that turns an already-governed `ToolSpec` into a plain LangChain `StructuredTool`, so a team can start on the simple path and later adopt `orchestration.py`'s governed `AgentConfig` path without rewriting tools.

## Q1: What does `plug_and_play_agent` actually do, line by line, and what does it delegate versus own?

`plug_and_play_agent` (quickstart.py:37) takes a `model` (a string or a `BaseChatModel`), a list of plain callables (`tools`), a required `system_prompt`, and an optional `checkpointer`. It lazily imports `langchain.agents.create_agent` and `langgraph.checkpoint.memory.MemorySaver`, then returns `create_agent(model, tools=tools, system_prompt=system_prompt, checkpointer=checkpointer or MemorySaver())`. It owns nothing about tool-calling, schema inference, message handling, or graph construction — all of that is `langchain.agents.create_agent`'s job. The only value this function itself adds is the `checkpointer or MemorySaver()` default: `create_agent` presumably requires an explicit checkpointer (or defaults to none, which would break multi-turn memory), so `plug_and_play_agent` supplies a sane zero-config in-memory one so "multi-turn conversations work out of the box," per its own docstring. This is the exact same "no new engine, just composition" ethos as `cli.py`.

## Q2: How is a plain Python function's schema inferred here, and what happens if a tool function has no docstring or no type hints?

`plug_and_play_agent` passes `tools` straight through to `langchain.agents.create_agent`, which (per this module's docstring) inspects each function's type hints and docstring to build its tool schema automatically — no `ToolSpec`, no manual JSON schema, real structured tool-calling via `AIMessage.tool_calls`. `quickstart.py` itself contains no schema-inference code at all — that logic lives entirely inside LangChain/LangGraph. Consequently, if a tool function is missing type hints, the inferred JSON-schema argument types would fall back to whatever LangChain's default is for untyped parameters (typically treating them as accepting any value, i.e. a much weaker schema), and if it has no docstring, the tool's `description` field passed to the model would be empty or missing, which directly degrades the model's ability to decide when to call that tool. `quickstart.py`'s docstring explicitly warns about this in the `to_langchain_tool` bridge's context: "write real type hints on your tool functions and both paths get a correct schema for free" — the burden of producing a good schema shifts entirely onto the tool author's function signature quality, and there is no validation anywhere in this module that catches a poorly-annotated tool before runtime.

## Q3: Trace `to_langchain_tool(spec)` — why does it explicitly ignore `spec.parameters` and re-derive the schema from `spec.fn`'s type hints instead?

`to_langchain_tool` (quickstart.py:53) does `StructuredTool.from_function(func=spec.fn, name=spec.name, description=spec.description)` — notably, it never reads `spec.parameters` at all. The docstring explains why: `spec.parameters` on a `contracts.ToolSpec` is "a loose documentation dict, not JSON Schema" (i.e. it's whatever informal shape `scaffold.py`'s generated `tools.register(ToolSpec("lookup_lead", "TODO: describe lookup_lead", {}, lookup_lead))` puts there — see `scaffold.py`'s Q7, which shows this is literally `{}` in generated code). `StructuredTool.from_function` instead introspects `spec.fn`'s real Python type hints to build a genuine Pydantic-backed JSON schema. This means the governed path's `ToolSpec.parameters` field is effectively decorative today with respect to the LangChain bridge — it's never consulted, and a `ToolSpec` with a misleading or stale `parameters` dict (relative to its `fn`'s actual signature) would produce a correct LangChain tool schema anyway, because the bridge trusts the function signature, not the metadata dict.

## Q4: What happens if `to_langchain_tool` is called on a `ToolSpec` whose `fn` has no type hints or an unclear docstring — walk the failure mode through to the model's behavior.

Since `to_langchain_tool` delegates schema inference to `StructuredTool.from_function`, which in turn depends on `spec.fn`'s own annotations, a `ToolSpec` built the way `scaffold.py`'s generated stub does it — `def lookup_lead(TODO_arg: str) -> str: raise NotImplementedError(...)` — would actually produce a reasonably typed schema (the stub does have a `str` type hint), but its docstring is the placeholder `"TODO: describe {tool_name} does — this becomes its schema description."` per the `_TOOL_STUB_TEMPLATE`, so the schema `to_langchain_tool` builds would carry that literal TODO text as the tool's description exposed to the model. Practically: the model sees a tool whose description is unhelpful boilerplate, degrading its ability to decide when to invoke it, and this failure is entirely silent — `to_langchain_tool` raises no error, `StructuredTool.from_function` raises no error, and the agent runs, just with a badly-described tool. There's no validation step in `quickstart.py` (or anywhere else in this bridge) that flags a `TODO`-shaped description before it reaches a live model.

## Q5: `to_langchain_tools(registry)` iterates `registry.names()` and calls `registry.get(name)` for each. What are the failure modes if `registry` is not a real `ToolRegistry`, or a name in `names()` isn't actually retrievable via `get()`?

`to_langchain_tools` (quickstart.py:64) types `registry: Any` — there's no structural typing/Protocol check that `registry` actually implements `.names()` and `.get()`, unlike, say, `context.py`'s `VectorStore`/`KnowledgeStore` Protocols elsewhere in the codebase. If `registry` doesn't implement those methods, the failure is a plain `AttributeError` at call time with no context-specific error message. If `registry.names()` returns a name that `registry.get()` can't resolve (e.g. a race between registration and lookup, or a caller passing a stale name list), the failure is whatever `ToolRegistry.get()` itself raises (presumably a `KeyError` or similar) — `to_langchain_tools` adds no defensive handling, retry, or skip-and-warn behavior; a single bad name aborts building the entire tool list via a list comprehension (`[to_langchain_tool(registry.get(name)) for name in registry.names()]`), even if 9 of 10 tools would have converted fine.

## Q6: The module docstring calls this "the actual plug-and-play entry point, built on real LangChain and LangGraph abstractions... not a hand-rolled convention," implicitly contrasting it with `scaffold.py`'s generated agents. Why maintain both, and what's the philosophical tension?

`scaffold.py`'s generated agents use a hand-rolled, text-based `CALL <tool_name> {"arg": "value"}` protocol parsed out of the model's raw text response (see `scaffold.py`'s Q12) — a bespoke convention this framework invented and must maintain parsing/robustness for itself. `quickstart.py` instead defers entirely to LangGraph's own prebuilt executor and the LLM provider's native structured tool-calling (`AIMessage.tool_calls`), which is battle-tested, maintained by LangChain, and doesn't depend on a model reliably reproducing exact text syntax. The tension: `agent_foundry`'s governed path (`orchestration.py`/`scaffold.py`) exists specifically to add RBAC, guardrails, budget enforcement, and audit trails that a bare LangGraph prebuilt agent doesn't have out of the box — but achieving that governance meant building a custom think/act graph with its own tool-calling convention rather than layering governance on top of LangGraph's native tool-calling. `quickstart.py` is the escape hatch acknowledging that for teams who don't need that governance yet, the hand-rolled convention is unnecessary risk (a model that doesn't follow the `CALL` syntax exactly produces a silent no-op, not a hard `AIMessage.tool_calls` structure) — hence "the actual plug-and-play entry point."

## Q7: Why does `plug_and_play_agent` accept `model: "str | BaseChatModel"` rather than requiring a fully constructed `ChatAnthropic` (or similar) instance?

Accepting a bare string (presumably a model identifier LangChain's `create_agent` can resolve into a chat model itself, per LangChain v1.0+'s convention of accepting model ID strings directly) lowers the barrier for the "junior developer's whole agent is five lines" use case the docstring's own example demonstrates — though that example actually passes a constructed `ChatAnthropic(model="claude-sonnet-5")` instance, not a string, suggesting the string path is a LangChain convenience this wrapper merely passes through rather than something `quickstart.py` itself implements or tests. This is worth noting as a documentation/example inconsistency: the type hint advertises a string-based shortcut, but the module's own usage example doesn't demonstrate it, so a reader can't be fully sure from this file alone what string format (`"anthropic:claude-sonnet-5"`? bare model name?) `create_agent` expects.

## Q8: This module has zero exception handling anywhere — no try/except in `plug_and_play_agent`, `to_langchain_tool`, or `to_langchain_tools`. Is that a defect, and how would you defend or criticize it?

For a thin wrapper module, the absence of exception handling is arguably correct rather than a defect: `plug_and_play_agent` and the `to_langchain_tool*` bridge functions add no logic of their own beyond delegation (Q1, Q3), so swallowing or wrapping exceptions from `langchain.agents.create_agent` or `StructuredTool.from_function` would only obscure the real error's origin and stack trace without adding actionable information — a `try/except: raise SystemExit("something went wrong")` here would make debugging strictly worse. The counter-argument a reviewer might raise: an `ImportError` for `langchain`/`langgraph` (both imported lazily inside the function, consistent with `cli.py`'s deferred-import pattern) surfaces as a raw Python traceback rather than a friendly message pointing at `pip install agent-foundry[quickstart]` or similar — `cli.py`'s own `_EXTRAS` mechanism (see `cli.py`'s Q3) demonstrates the codebase knows how to give a better experience for missing optional dependencies elsewhere, but that pattern isn't applied here.

## Q9: What testing strategy would actually validate this module, given it has almost no logic of its own to unit test?

Because nearly all of `plug_and_play_agent`'s and `to_langchain_tool`'s behavior is delegated to LangChain/LangGraph internals, a meaningful test suite for `quickstart.py` needs to be an integration test, not a pure unit test: construct a real (or mocked) `BaseChatModel`, pass a couple of plain functions with good and bad type hints/docstrings, call `plug_and_play_agent`, and assert the returned graph actually invokes tools correctly end-to-end (verifying, e.g., that `agent.invoke(...)`'s result reflects a real tool call, and that omitting `checkpointer` still yields working multi-turn memory across two `.invoke()` calls with the same `thread_id`). For `to_langchain_tool`/`to_langchain_tools`, the highest-value test is exactly the scenario in Q3/Q4: build a `ToolSpec` with a deliberately wrong/stale `parameters` dict but a correctly-typed `fn`, convert it, and assert the resulting `StructuredTool`'s schema reflects `fn`'s real signature — proving (or catching a regression in) the "parameters dict is ignored" behavior this module's docstring claims.

## Q10: `to_langchain_tools` builds the entire list eagerly via a list comprehension over `registry.names()`. What happens under concurrent registration — could this module have a thread-safety issue?

`ToolRegistry` itself lives in `tools_gateway.py`, not this module, so `quickstart.py` has no locking of its own — it simply calls `.names()` then `.get(name)` for each. If some other thread is concurrently registering or removing tools on the same `ToolRegistry` instance while `to_langchain_tools` iterates, there's a classic TOCTOU (time-of-check-to-time-of-use) window: `.names()` could return a name that's been removed by the time the corresponding `.get(name)` executes a few list-comprehension iterations later, producing a `KeyError` (per Q5) purely from a race rather than a genuine caller bug. Whether this is a real risk depends on `ToolRegistry`'s own internal locking (not visible in this file), but `quickstart.py` itself does nothing to snapshot the registry state before iterating, so if `ToolRegistry` isn't internally synchronized, this bridge function inherits that risk silently.

## Q11: If you compare `plug_and_play_agent` to how a plain LangGraph user would write the same agent by hand, what exactly does this module save them, and is that savings worth a whole extra module?

A plain LangGraph user would write `from langchain.agents import create_agent; from langgraph.checkpoint.memory import MemorySaver; agent = create_agent(model, tools=tools, system_prompt=system_prompt, checkpointer=MemorySaver())` themselves — literally the same two lines `plug_and_play_agent` contains. The savings are: (1) not needing to know that `MemorySaver` is the correct default checkpointer to make multi-turn work (a real, if small, discoverability win for a newcomer), and (2) a documented, on-brand entry point inside `agent_foundry`'s own namespace that a user discovers via this framework's docs rather than LangChain's, plus the `to_langchain_tool` bridge which genuinely adds value the LangChain user wouldn't get to reimplement (a compatibility layer between the governed and ungoverned tool representations). Purely as line-count savings this module is marginal; its actual value is discoverability and being the on-ramp that the framework's docstrings elsewhere (`orchestration.py`'s referenced `AgentConfig` path) point newcomers toward before "growing into" governance — worth it as an onboarding artifact more than as a code-savings artifact.

## Q12: What's a limitation of `quickstart.py` you'd fix given more time?

The clearest one is the total absence of input validation or friendly errors anywhere in this module (Q8) — a missing `langchain`/`langgraph` install, a tool function with no type hints, or a `ToolRegistry` passed to `to_langchain_tools` that doesn't implement the expected duck-typed interface (Q5) all fail with raw, unhelpful tracebacks rather than actionable messages, which is a worse first-run experience than `cli.py`'s `_EXTRAS`-style guidance elsewhere in the same codebase. A second, more architectural gap: `to_langchain_tool`'s decision to always ignore `ToolSpec.parameters` (Q3) means a `ToolSpec` author who deliberately wants to override/narrow the auto-inferred schema (e.g. to add an enum constraint LangChain can't infer from a bare `str` type hint) has no way to do so through this bridge — the function offers no override path, silently discarding hand-authored schema metadata every time.
