# agent_foundry/eval.py — Q&A

The four-level eval harness (`atomic`/`component`/`flow`/`overall`, per PLAN.md section 2) that records scored observations during a live run — `EvalHarness` (in-memory) and `JSONLEvalSink` (durable, streams to a file) both satisfy the `Evaluator` protocol, and `trajectory_report()` reconstructs a single session's execution story purely by replaying the records the framework already wrote.

## Q1: Why four levels (`atomic`, `component`, `flow`, `overall`) instead of a single flat score per run?

A single scalar per run collapses "the model's individual reasoning step was fine but the tool it picked was wrong" and "every step was fine but the overall task still failed" into the same number, making regressions impossible to localize. `_LEVELS = ("atomic", "component", "flow", "overall")` (line 11) lets `EvalHarness.record(level, unit, metric, score, **detail)` attach a score to exactly the granularity that produced it: an `atomic` record for one guardrail check or one critique judgment (`orchestration.py`'s `make_critique_node` records these), a `component` record for one tool invocation's success/approval/permission outcome, a `flow` record for how one whole session ultimately resolved (`_finalize_turn`'s `record("flow", session_id, "completed", ...)`), and `overall` reserved for cross-session aggregate judgments. `EvalHarness.score_for(level)` and `.summary()` (lines 34-39) then let a caller ask "how are we doing at the tool-selection level" independently of "how are we doing at the whole-task level" — exactly the diagnostic granularity `trajectory_report()` needs to distinguish "guardrail blocked something" from "a tool failed and was never retried" from "the turn just didn't finish."

## Q2: Walk through exactly what `trajectory_report(harness, session_id)` does when called on a session with a tool that failed once and then succeeded.

First it filters `harness.records` to only those relevant to this session (line 75): a record matches if `detail.get("session_id") == session_id` (every atomic/component record carries this, per the framework's own instrumentation) OR the record is the flow-level one for this session (`r.level == "flow" and r.unit == session_id` — flow records have no `session_id` key in `detail` because `unit` already *is* the session_id). It then iterates the scoped records in order, tracking `last_ok: dict[str, bool]` (tool name → most-recently-seen pass/fail). For a `component`-level record whose `metric` is one of `_TOOL_METRICS = ("success", "approval", "permission", "action_guardrail")`, it appends the tool name to `report.tool_calls` (every attempt, in order, including denied ones), adds it to `report.tools_used`, and computes `ok = r.metric == "success" and r.score == 1.0`. The interesting bit: if `r.unit` is already a key in `last_ok` and the *previous* recorded outcome for that same tool was `False`, but this one is `True`, the tool name gets appended to `report.recovered_tool_failures` (line 87-88) — this is exactly the "failed once, succeeded on retry" case the question asks about. `last_ok[r.unit]` is then updated to the current outcome regardless. At the end, `report.tool_success_rate = tool_successes / tool_attempts` if any attempts happened at all (line 97-98), otherwise it stays at its dataclass default of `1.0` — a subtle default that means "no tool was ever called" reads identically to "every tool call succeeded" unless a caller separately checks `len(report.tool_calls)`.

## Q3: What happens if a component record's `unit` for a *different* tool has the same failed→succeeded transition interleaved with another tool's calls — does `recovered_tool_failures` get confused?

No, because `last_ok` is keyed per tool name, not by position in the record stream — `last_ok[r.unit]` only ever tracks the most recent outcome for that specific `unit` string, so interleaving tool A's fail/succeed sequence with tool B's own calls in between doesn't cross-contaminate the two. The one real edge case: if the *same* tool fails, succeeds, then fails again, it only gets added to `recovered_tool_failures` once (the fail→succeed transition), and a subsequent failure doesn't remove it from that list — so `recovered_tool_failures` answers "did this tool ever recover at least once," not "is this tool currently in a recovered state." A caller reading `recovered_tool_failures` as "these tools are now healthy" would be wrong if the third call in that same trajectory failed again; the report doesn't re-litigate a tool's final state, only whether a recovery event occurred anywhere in the trajectory.

## Q4: Why does `TrajectoryReport` deliberately exclude cost and latency, when those seem like obviously relevant eval dimensions?

The docstring (lines 46-55) is explicit: `AgentConfig.cost_ledger` (see `observability.CostLedger`) and `.sla_tracker` already own cost and latency data respectively, and duplicating those numbers into `EvalRecord`s would create "a second, driftable copy of the same numbers." This is a real architectural discipline choice — every additional place a number is stored is another place it can go stale relative to the source of truth, especially since cost/latency get updated by entirely different code paths (budget spending happens in `make_think_node`/`_invoke_tool_call`, independent of when/whether an eval record gets written). `TrajectoryReport` instead stays scoped to what genuinely only exists as `EvalRecord`s: tool choice/sequence, guardrail interventions, critique scores, and outcome — data that has no other canonical home. The tradeoff is that a caller wanting "cost per trajectory alongside the tool sequence" has to join two data sources themselves (by `session_id`/`thread_id`) rather than getting one denormalized report — more caller-side work, but no drift risk.

## Q5: `EvalHarness.record()` asserts `level in _LEVELS`. What happens in production if this assertion fires, and is that the right failure mode?

`assert level in _LEVELS, f"unknown eval level {level!r}"` (line 29) raises `AssertionError` immediately, at record time, inside whatever code path called `.record(...)` — which in `orchestration.py` is inline in `make_think_node`/`make_act_node`/`make_critique_node`/`_finalize_turn`, i.e. it would blow up the actual agent turn, not just the eval subsystem. That's a real risk: a typo'd level string (e.g. `"componant"`) in any instrumentation call becomes a production-breaking bug in the agent's core execution path, not a soft eval-logging failure that degrades gracefully. It's arguably the wrong failure mode for observability code specifically — most tracing/eval libraries choose to fail soft (log the error, drop the malformed record, keep the agent running) precisely because instrumentation should never be able to take down the thing it's instrumenting. It's also worth noting Python's `assert` statements are stripped entirely when running with `-O` (optimized mode) — so in that configuration, an invalid `level` would silently construct and store a malformed `EvalRecord` instead of raising, which is a second, opposite failure mode (silent corruption instead of a crash) depending on how the interpreter is invoked. `JSONLEvalSink.record()` (line 112-115) has the identical assertion and the identical exposure.

## Q6: `JSONLEvalSink` opens the file in `"a"` mode and does a full `open()`/`write()`/(implicit close) on every single `.record()` call. What's the performance and durability tradeoff here versus batching writes?

Opening and closing a file handle on every record call means every eval write pays full syscall overhead (open, write, fsync-on-close-depending-on-OS-buffering, close) rather than amortizing it across a batch — for a high-frequency agent loop recording atomic/component records on every think/act step, this is a meaningful throughput cost compared to holding one open handle and flushing periodically or in bulk. The upside, and it's a real one for an eval/audit sink specifically, is durability and crash-safety: each record is fully written and the handle closed before the function returns, so a process crash immediately after a `.record()` call can't lose that record to an unflushed OS-level buffer sitting in a long-lived file handle — every line that was successfully recorded is guaranteed on disk. This is the classic append-only-log tradeoff (durability per write vs. throughput), and for an eval trail specifically — where you want to reconstruct exactly what happened even after an unexpected crash mid-turn — favoring durability over raw write throughput is a defensible choice, though it would become a real bottleneck under high eval-record volume in production without batching.

## Q7: How does `Evaluator` as a `Protocol` (structural typing) change what it means to "swap the eval backend," compared to if `EvalHarness` were the only concrete class `orchestration.py` accepted?

Because `orchestration.py` type-hints `AgentConfig.eval_harness` against the `Evaluator` protocol rather than the concrete `EvalHarness` class, and the entire contract is one method — `.record(level, unit, metric, score, **detail) -> Any` — any object with a matching `.record()` signature works as a drop-in, with no inheritance, no registration, and no explicit "implements this interface" declaration required (Python's structural/duck typing for `Protocol` classes). `JSONLEvalSink` is the proof this actually works: it's a completely unrelated dataclass (no shared base class with `EvalHarness`) that happens to expose the same method shape, and it's usable anywhere `AgentConfig.eval_harness` is expected. The real consequence: any caller can write their own sink — one that pushes to Kafka, writes to Postgres, or forwards to an external eval platform — by implementing just `.record()`, without touching `orchestration.py` at all. The cost of this flexibility is that nothing statically enforces the four-level vocabulary (`_LEVELS`) or the `**detail` conventions (`session_id`, etc.) on a third-party implementation — a hand-rolled `Evaluator` that doesn't assert on `level` or doesn't preserve `detail["session_id"]` would silently break `trajectory_report()`'s ability to reconstruct trajectories, since that function's filtering logic (Q2) depends on those conventions being honored even though nothing in the `Protocol` itself requires it.

## Q8: What happens to `trajectory_report()` if a caller passes a `session_id` that has zero matching records — e.g. a typo'd ID or a session that never ran?

`scoped` (line 75) would be an empty list — the list comprehension just filters to nothing, no exception. The function then returns a `TrajectoryReport(session_id=session_id)` with every field left at its dataclass default: empty `tool_calls`/`tools_used`/`recovered_tool_failures`/`guardrail_blocks`/`critique_scores`, `tool_success_rate=1.0` (the default, never touched since `tool_attempts` stays `0` and the `if tool_attempts:` guard at line 97 never executes), and `outcome=None`. This is a genuinely ambiguous result: a session that had zero tool calls and completed perfectly, and a session that literally never happened (typo'd ID), produce structurally near-identical reports (`tool_success_rate=1.0`, empty lists) — the only field that distinguishes "session existed but did nothing" from "session doesn't exist" is `outcome` staying `None`, and only if you know to check it. There's no error, warning, or explicit `found: bool` field to disambiguate — a caller has to know this function fails silently-and-permissively rather than raising on an unknown session.

## Q9: How is this different from how LangSmith or Weights & Biases would score an eval run of the same agent?

LangSmith's eval model centers on datasets of input/output pairs run through a pipeline and scored by evaluators (LLM-as-judge or custom functions) against a single run-level score per example, with a hosted UI for comparing runs; its granularity is fundamentally "one example, one (or a few) scores," aggregated across a dataset. W&B's eval/experiment tracking is similarly run-centric — metrics logged per training/eval step, visualized as time series or tables, with sweep/comparison tooling built on top. `eval.py`'s four-level model is a different axis of granularity entirely: it's not "one score per example," it's "many scores at many structural levels *within a single agent turn*" — an `atomic` critique score, several `component` tool-success records, one `flow` outcome, all tagged to the same `session_id` so `trajectory_report()` can reconstruct the *shape* of what happened inside one turn (which tools, in what order, did any recover, were any guardrails tripped), not just whether the final answer passed a check. This is closer to a structured execution trace with embedded scoring than to a traditional ML eval dataset scorer — the two are complementary, not competing: `eval_dataset.py`'s `EvalCase`/`Scorecard` machinery (built on `core.evalgate`) is the module in this codebase that actually plays LangSmith's "dataset of cases, aggregate pass rate" role, while `eval.py`'s `EvalHarness` is closer to per-turn structured tracing with eval semantics baked in.

## Q10: What's the actual statistical rigor behind `EvalHarness.score_for()` and `.summary()` — is a plain arithmetic mean of scores at a level production-grade, or a reasonable approximation?

`score_for(level)` (line 34-36) is `sum(scoped) / len(scoped)` — an unweighted arithmetic mean over every record at that level, with no confidence interval, no variance/stddev reported, no minimum-sample-size guard, and (crucially) no weighting by how *many* underlying events contributed to each record. A `flow`-level mean that's `0.8` after 3 sessions and one that's `0.8` after 3,000 sessions are reported identically by `.summary()` — there's no way to know from this API alone whether that number is statistically meaningful or noise from a tiny sample. This is a reasonable approximation for a dev-loop signal ("did my last change move the needle in the right direction, roughly") but it is not production-grade statistical monitoring: there's no sequential testing, no significance testing against a baseline (that lives in `core.evalgate.Scorecard.compare_to()` and `eval_dataset.py`'s baseline persistence instead, which is a different, more rigorous mechanism), and a single catastrophic outlier score can swing a small-sample mean disproportionately with nothing here to flag it as an outlier. It's honestly scoped as a lightweight aggregator, not a statistics engine.

## Q11: If two threads call `EvalHarness.record()` concurrently on the same harness instance, what happens?

`EvalHarness.records` is a plain Python `list`, and `.record()` does `self.records.append(rec)` after constructing the `EvalRecord`. Exactly as with `observability.Tracer.spans`, `list.append` is atomic under CPython's GIL, so concurrent calls from multiple threads won't corrupt the list or lose an entry — this is safe in the same accidental-by-GIL way discussed for `Tracer`. What isn't safe, or even attempted, is any coordination *across* the append — if two threads are both computing `score_for(level)` while a third is appending, the reader might see a list snapshot from mid-append (Python's list operations don't require external locking for this specific case since `len()`/iteration over a list mid-append in CPython doesn't crash, though the *result* of a concurrent `score_for()` call could reflect a partially-updated view depending on exact timing — reading a list while another thread appends to it is safe from a memory-corruption standpoint but not a consistency guarantee). In practice, given `orchestration.py`'s node-per-thread execution model where each session's records interleave from the *same* thread sequentially (concurrent dispatch is at the tool-call level via `_dispatch_tool_calls`, and each of those calls its own `.record()` after its own work completes), true concurrent writes to the same harness are the tool-fan-out case specifically, and the risk is purely benign interleaving, not corruption.

## Q12: `TrajectoryReport.guardrail_blocks` only captures atomic records where `r.unit in ("input_guardrail", "output_guardrail") and r.score == 0.0`. What's the significance of the `score == 0.0` check, and what would a guardrail record with a nonzero, non-1.0 score mean here?

The `score == 0.0` filter (line 90) is what distinguishes "the guardrail actually blocked this turn" from "a guardrail check ran and passed" — a guardrail presumably records some score for every check it performs (not just failures), and only a `0.0` score represents an actual block/violation worth surfacing in the report. If a guardrail implementation ever recorded a graded score (say `0.5` for "partially concerning but allowed through"), this filter would silently exclude it from `guardrail_blocks` — the function has a binary pass/fail assumption baked into its filtering logic (`score == 0.0` means blocked, anything else is treated as "fine, don't report it") that wouldn't generalize if guardrails.py's actual scoring scheme were ever changed to something more graded than a strict 0/1. Given the codebase's actual guardrail check (`config.guardrails.check_output` returning an allowed/blocked boolean per `orchestration.py`'s usage), the binary assumption matches current reality, but it's a coupling worth knowing about if guardrail scoring is ever extended.

## Q13: What's a limitation of `eval.py` you'd fix given more time?

The clearest one is the fragile string-based joining logic in `trajectory_report()` (Q2/Q8): matching records to a session purely by `detail.get("session_id")` or the `flow`-unit-equals-session_id special case is an implicit contract between this function and every instrumentation call site in `orchestration.py`/`native_engine.py` — nothing enforces that a new node author who adds a `.record()` call remembers to pass `session_id` in `detail`, and if they forget, that record silently vanishes from every `trajectory_report()` for that session with no error anywhere. A stronger design would either make `session_id` a required, typed field on `EvalRecord` itself (rather than something buried in the free-form `detail` dict) or add a runtime check that fails loudly when the field is missing on a record level that requires it. A second, smaller fix: `EvalHarness.record()`'s `assert`-based validation (Q5) should be a proper exception with clear failure semantics (or a soft-fail/log-and-continue for genuinely non-critical eval calls), rather than something that can silently vanish under `-O` and otherwise take down the calling agent turn.

## Q14: `EvalRecord` (from `contracts.py`) carries a `detail: dict[str, Any]` free-form field alongside typed `level`/`unit`/`metric`/`score`. What's the tradeoff of that design versus giving each level its own strongly-typed record class?

A free-form `detail` dict means every call site — `make_think_node` recording `model`/`task`, `_invoke_tool_call`-adjacent code recording tool outcomes, `_finalize_turn` recording flow outcomes — can attach exactly the fields relevant to that call without a proliferation of level-specific record classes (`AtomicRecord`, `ComponentRecord`, `FlowRecord`, ...) that would need their own schemas, and without `EvalHarness`/`JSONLEvalSink` needing to know about all of them. The cost is exactly what Q12 and Q8 already surface: nothing statically checks that `detail` contains the keys downstream consumers like `trajectory_report()` actually depend on (`session_id`), so the connection between "what a node writes" and "what a reader expects" is a documentation-and-convention contract, not a type-checked one. This is a reasonable tradeoff for an evolving instrumentation surface (new detail fields get added constantly as the framework grows) traded against a real risk class (silent, unenforced key-name coupling) that only unit tests around `trajectory_report()`'s actual behavior would catch.

## Q15: What happens if `EvalHarness.summary()` is called mid-turn — after `make_think_node` has recorded its `"atomic"` record but before `_finalize_turn` has written the `"flow"` record for that session?

`summary()` (line 38-39) is just `{level: self.score_for(level) for level in _LEVELS}` — it has no concept of "in-progress" versus "finished" sessions, and no way to filter to only completed turns. It unconditionally averages whatever records happen to exist at call time for each level, so calling it mid-turn simply reflects a partial view: `score_for("flow")` would average only the flow records from *previously completed* sessions (since the current session's flow record hasn't been written yet), while `score_for("atomic")`/`score_for("component")` would already include whatever atomic/component records the in-progress session has produced so far. This is a real hazard for anything polling `summary()` for a live dashboard (`observability.render_dashboard` calls `eval_harness.summary()` directly): the numbers it displays are always a snapshot of whatever has been recorded up to that instant, with no distinction between "this reflects N fully-completed sessions" and "this reflects N-1 completed sessions plus a few loose atomic/component records from a session still in flight" — the two can look identical in the returned dict, and a caller has no way to tell from `summary()` alone which situation produced a given number.
