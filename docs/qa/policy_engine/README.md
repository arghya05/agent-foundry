# agent_foundry/policy_engine.py — Q&A

`PolicyDecisionPoint` is the single mandatory authorization call site every tool call passes through, composing a scope check, a data-classification role check, the deterministic action guardrail, an optional external `PolicyEngine` (`OPAPolicyEngine` over OPA's REST API, or `CedarPolicyEngine` over the embedded `cedarpy` engine), and an optional `EgressPolicy` host allowlist into one `decide()` call.

## Q1: `PolicyDecisionPoint.decide` (line 54) accepts an `args: dict[str, Any]` parameter, and every call site (`orchestration.py:602`, `native_engine.py:413`) passes the tool call's real arguments into it. Trace through `decide`'s body — where is `args` actually used?

Nowhere. Read `decide`'s body top to bottom: the scopes check (line 63) uses `scopes`/`identity.roles`; the classification check (line 67-70) uses `data_classification`/`identity.roles`; the guardrail call (line 71) uses `tool_name`/`cost_so_far`/`destructive`; the confirmation check (line 78) uses `requires_confirmation`; the external policy-engine call (line 80-86) builds its `input` dict from `identity.id`, `tool_name`, `policy.allowed_tools`, `cost_so_far`, `policy.max_cost_usd_per_thread`; the egress check (line 87-94) uses `hosts`. The `args` parameter is accepted into the function signature and then never read again — it's dead as far as `decide()`'s own logic is concerned. This is the single most important limitation to understand about this module: **no policy decision made here — not the built-in checks, not OPA, not Cedar — can ever be conditioned on the actual content of a tool call's arguments.** A policy like "block `transfer_funds` calls where `amount > 10000`" or "deny `send_email` if the recipient domain isn't in an allowlist derived from the message body" is structurally impossible to express through this call site as written, no matter how sophisticated the Rego/Cedar policy behind `OPAPolicyEngine`/`CedarPolicyEngine` is, because the argument values never leave `orchestration.py`/`native_engine.py` to reach the policy evaluation at all. Every check here operates on tool identity, actor identity, cost totals, and static per-tool metadata (`ToolSpec.scopes`/`egress_hosts`/`data_classification`) — never on the semantic content of a specific call.

## Q2: Given Q1, is `args` truly useless in `decide()`, or is there a legitimate reason to keep it in the signature even though the current implementation ignores it?

There's a legitimate forward-compatibility reason to keep it: the signature already carries everything a future content-aware check would need without requiring every call site to be rewritten. If someone later adds, say, an `if self.content_validator is not None: self.content_validator.check(tool_name, args)` step inside `decide()`, or extends the OPA/Cedar `input`/`entities` payload to include `args`, no caller in `orchestration.py` or `native_engine.py` needs to change — they already pass `args` positionally. So keeping the unused parameter is defensible API design (the extension point exists), but it's also a genuine trap for anyone reading the call sites and assuming — reasonably, since `args` is right there being passed in — that content-based policy is already possible today. It is not; today it's pure API surface with no wiring behind it.

## Q3: `OPAPolicyEngine.allow`'s `input` dict (line 81-84) sends `{"identity_id", "tool", "allowed_tools", "cost_so_far", "max_cost"}` to a running OPA server. Design the smallest Rego policy change that would be needed to make a content-based rule possible, and explain why that change has to happen in THIS file, not just in the `.rego` policy source.

Even a security engineer who fully controls the `.rego` policy file cannot write a content-aware rule today, because Rego can only evaluate the `input` document it's given, and `PolicyDecisionPoint.decide` (line 81-84) constructs that `input` dict without ever including `args`. No amount of Rego sophistication compensates for missing data — you cannot write `deny if input.args.amount > 10000` when `input.args` was never sent. The fix has to happen in `policy_engine.py`: `decide` would need to add `"args": args` (or a deliberately narrowed, sanitized subset of it — passing raw, unvalidated tool arguments to an external policy engine has its own data-classification implications, e.g. leaking `confidential`-tagged argument values to an OPA server's logs) into the dict built at line 81-84, and `OPAPolicyEngine.allow`'s `input` document would then carry it through to the `/v1/data/{path}` POST body untouched (it already forwards the whole `input` dict as-is, line 108). This is a clean illustration of why "policy as code" is only as expressive as the facts it's handed — the policy *engine* is real and general-purpose (a live OPA server evaluating arbitrary Rego), but the *integration* in this codebase currently starves it of the one input that would make per-argument rules possible.

## Q4: Walk through `PolicyDecisionPoint.decide`'s check ordering (scopes → data classification → guardrail → confirmation → external policy engine → egress). Why this order, and what would break (functionally or performance-wise) if the external policy-engine check ran first?

The order is deliberately cheapest-and-purely-local-first, most-expensive-and-networked-last: scope/role checks are in-memory set intersections, the classification check is a dict/set lookup, `guardrails.check_action` (via `GuardrailEngine`) is pure arithmetic/comparisons against `Policy` fields, and `requires_confirmation` is a plain boolean check — none of these do I/O. `OPAPolicyEngine.allow` and `CedarPolicyEngine.allow` are the first checks that cost real work: OPA is a synchronous HTTP round-trip (`urllib.request.urlopen`, with a `timeout_s` of 5 seconds by default) to a separate server process, and even Cedar's in-process `cedarpy.is_authorized` call, while not networked, does non-trivial policy evaluation. Running the cheap deterministic checks first means a tool call that's obviously going to be denied on a fast, local basis (wrong scope, missing role, over budget) never pays for the network round-trip at all — this matters both for latency (avoiding an unnecessary 5-second-worst-case OPA call on every denied call) and for resilience (a temporarily unreachable OPA server, per Q6, causes `decide()` to raise; ordering it last means that failure mode only affects calls that would have otherwise been allowed by every local check, not every single tool call regardless of outcome). If the external check ran first, every tool call — including ones a scope check alone would reject in microseconds — would incur the OPA/Cedar cost unconditionally, and an OPA outage would break authorization for calls that a local, deterministic policy would have denied anyway for unrelated reasons, muddying incident diagnosis (is this failing because of OPA being down, or because the caller genuinely lacks the scope?).

## Q5: `scopes` and `data_classification` (`_RESTRICTED_CLASSIFICATIONS = ("confidential", "restricted")`, line 29) both default to "unrestricted unless explicitly declared" — `scopes=frozenset()` skips the scope check entirely (line 63, `if scopes and ...`), and `data_classification="internal"` (the `ToolSpec` default) never matches `_RESTRICTED_CLASSIFICATIONS`. What's the practical consequence of this default for a newly registered tool that nobody explicitly configured?

A brand-new tool registered with the plain `ToolSpec(name=..., description=..., parameters=..., fn=...)` constructor and no explicit `scopes=`/`data_classification=` gets NO scope-based restriction (line 63's `if scopes and not (...)` is false when `scopes` is the empty-frozenset default, so the whole branch is skipped) and NO classification-based restriction (its `data_classification` defaults to `"internal"`, which isn't in `_RESTRICTED_CLASSIFICATIONS`, so line 67's `if data_classification in _RESTRICTED_CLASSIFICATIONS` is false). In other words, unless whoever registers a tool actively opts it into `scopes`/`data_classification="confidential"`, that tool is reachable by *any* identity with *any* roles, subject only to the remaining deterministic guardrail (autonomy/budget/approval-list) and whatever external policy engine or egress policy happens to be wired in (which, per `security.py`'s Q4/Q5, may also be unconfigured by default). This mirrors `EgressPolicy`'s own fail-open default (`security.py`), and it's the same tradeoff: convenient for a team just getting a tool working, but it means "no explicit configuration" and "deliberately unrestricted" are indistinguishable states — a team that forgets to classify a genuinely sensitive tool gets silent, unrestricted access rather than a loud failure prompting them to configure it.

## Q6: `OPAPolicyEngine.allow` (line 107) calls `urllib.request.urlopen(req, timeout=self.timeout_s)` with no try/except. What happens to a tool call, end-to-end, if the OPA server is unreachable when `decide()` calls into it?

`urlopen` raises (`urllib.error.URLError` on connection failure, or a timeout-derived exception once `self.timeout_s` — 5 seconds by default — elapses), and nothing in `OPAPolicyEngine.allow` or in `PolicyDecisionPoint.decide`'s call to `self.policy_engine.allow(...)` (line 81) catches it — the exception propagates straight up through `decide()`, through `orchestration.py`'s `make_act_node`/`native_engine.py`'s `_act`, uncaught by anything shown in this module. Practically, this means an OPA outage doesn't produce a controlled "deny" (`GuardrailResult(False, ...)`) — it produces an unhandled exception that will surface however the calling engine's own exception handling (or lack thereof) deals with it, which is a fundamentally different failure mode than every other check in `decide()`. Every built-in check in this file fails *closed with a reason* (a `GuardrailResult(False, "...")` the caller can log, surface to a user, or route to `escalation.py`); an OPA outage instead fails *loud and uncontrolled*. Whether that crashes the whole agent turn, gets caught by a broader exception handler somewhere upstream and treated as a generic tool failure, or does something else entirely depends on code outside `policy_engine.py` — but as written, this is the one check in the composed decision chain that doesn't degrade gracefully on infrastructure failure.

## Q7: Compare that to `json.loads(resp.read()).get("result", False)` at the end of `OPAPolicyEngine.allow` (line 116). What failure mode IS handled gracefully here, and why is the default `False` the right choice?

If OPA responds successfully (no network/HTTP error) but with a response body that doesn't contain a `"result"` key at all — e.g., the Rego package path in `self.path` doesn't exist, or the policy evaluates to `undefined` rather than an explicit `true`/`false` — `.get("result", False)` treats that as a denial rather than raising a `KeyError` or defaulting to permissive `True`. This is exactly the right default for an authorization check: an ambiguous or malformed "yes/no" answer from the policy engine should never be interpreted as "yes." It's a deliberate fail-closed choice, and it's worth contrasting directly with Q6 — a *malformed but successfully-received* OPA response degrades safely to deny, while a *connection failure to reach OPA at all* does not degrade safely, it crashes. That's an inconsistency in the failure-handling posture of the same class: one category of "OPA didn't give me a clean answer" is handled, a more catastrophic category isn't.

## Q8: `CedarPolicyEngine.allow`'s `input` dict processing (line 152) does `max_cost = float(input.get("max_cost", 1_000_000.0))`. If a caller's `input` dict omits `"max_cost"` — which the OPA-shaped convenience dict at `decide()` line 81-84 never actually omits, since it's built there directly — what does that default imply, and is it consistent with `contracts.Policy.max_cost_usd_per_thread`'s own default of `1.0`?

No — this is a meaningful inconsistency. `contracts.py`'s `Policy` dataclass defaults `max_cost_usd_per_thread` to `1.0` (a deliberately tight default budget ceiling, "fails closed" in spirit — a new `Policy()` with no configuration lets an agent spend at most $1 before `GuardrailEngine.check_action`'s budget check trips). `CedarPolicyEngine.allow`'s own internal default for a *missing* `max_cost` key, by contrast, is `1_000_000.0` — effectively "no budget ceiling" for any caller who constructs the Cedar input dict directly (bypassing `PolicyDecisionPoint.decide`, which always supplies `policy.max_cost_usd_per_thread` explicitly) and forgets to include `max_cost`. As long as every real call path goes through `decide()`, this gap is dormant — `decide()` never omits `max_cost` from the dict it builds. But it's a foot-gun for anyone using `CedarPolicyEngine` directly or writing a test/tool that constructs the `input` dict by hand: the class's own fallback silently assumes "unlimited spend is fine" rather than mirroring `Policy`'s own conservative default, and there's nothing in `CedarPolicyEngine` itself enforcing that a caller always supplies `max_cost`.

## Q9: `CedarPolicyEngine.allow` builds Cedar `entities` (line 170-177) with `"parents": []` for both the `Agent` and `Tool` entities. What does the absence of any entity hierarchy mean for what Cedar policies can express here, compared to how AWS actually uses Cedar for IAM-style policies in production?

Cedar's real power in AWS's own usage (e.g., Amazon Verified Permissions) comes substantially from hierarchical entities — a principal belonging to a group, a group belonging to an org, a resource belonging to a folder belonging to a bucket — letting policies grant/deny based on structural membership ("any principal in group X can act on any resource in folder Y") rather than only flat, per-entity attribute checks. `CedarPolicyEngine.allow` constructs exactly two entities per call — the calling `Agent` and the target `Tool` — both with empty `parents`, meaning there is no group/role hierarchy representable at all through this integration; the only relationship Cedar can reason about is the flat `attrs.allowed_tools` list attached directly to the `Agent` entity (`resource in principal.allowed_tools` in `DEFAULT_CEDAR_POLICY`, line 126). A more IAM-like design would model `identity.roles` (already present on the `Identity` dataclass in `contracts.py`) as parent entities or additional attributes so Cedar policies could express role-based rules ("any principal with role `finance-approver` may call any `Tool` tagged `financial`") instead of only per-identity allowlists. As shipped, `CedarPolicyEngine` demonstrates that the *engine* is real and correctly wired (verified against actual `cedarpy`, including a genuine Cedar `decimal` extension comparison for the cost ceiling per its own docstring), but the entity model feeding it is deliberately minimal — closer to a static allowlist expressed in Cedar syntax than to a full IAM-style hierarchical policy graph.

## Q10: Both `OPAPolicyEngine` and `CedarPolicyEngine` import their real dependencies (`cedarpy`) inside the method body (`import cedarpy` at line 153) rather than at module top, while `urllib.request`/`json` for `OPAPolicyEngine` are imported at module top (lines 9-10). Why the difference, and what does it buy?

`urllib.request` and `json` are Python stdlib — importing them at module top costs nothing and requires no optional dependency, so `OPAPolicyEngine` can be constructed and even have `.allow()` called (against a real OPA server) with zero extra `pip install`. `cedarpy` is a third-party package (the docstring says "Requires `pip install cedarpy`", line 139) that most Agent Foundry installations won't have and shouldn't be forced to install just to import `policy_engine.py` at all — if `import cedarpy` were hoisted to module top, simply doing `from agent_foundry.policy_engine import PolicyDecisionPoint` anywhere in the codebase (including `orchestration.py`'s import graph, since `PolicyDecisionPoint` is the type every `AgentConfig` builds by default) would raise `ImportError` on any environment without `cedarpy` installed, even for teams that never intend to use Cedar at all. Deferring the import into `CedarPolicyEngine.allow`'s method body means the dependency is only required at the moment someone actually constructs a `CedarPolicyEngine` and calls it — the same "optional dependency, pay only if you use it" pattern used elsewhere in the codebase for provider-specific integrations (e.g., `EncryptedJSONLAuditLog`'s `from cryptography.fernet import Fernet` inside `__post_init__`, in `security.py`).

## Q11: `PolicyDecisionPoint`'s docstring (line 45-48) states: "Wire it in via AgentConfig.pdp — make_act_node/native_engine._act ALWAYS call `.decide(...)`, never `config.guardrails.check_action(...)` directly... so this is a real invariant, not an opt-in a caller could forget." Is that invariant actually enforced by the type system or runtime, or is it a convention documented in a comment?

It's convention backed by code review discipline and a runtime `assert`, not something the type system can enforce. `orchestration.py`'s `AgentConfig.__post_init__` does guarantee `pdp` is never `None` (constructing a default `PolicyDecisionPoint(guardrails=self.guardrails)` if the caller didn't supply one), and the call site at `orchestration.py:600` has `assert config.pdp is not None` immediately before calling `config.pdp.decide(...)` — so within the two verified call sites (`orchestration.py:602`, `native_engine.py:413`), the invariant holds and both go through `decide()`, not `check_action` directly. But there is nothing in `GuardrailChecks`, `AgentConfig`, or `PolicyDecisionPoint` itself that would prevent a *third* execution path — a new custom engine, a test harness, or a future contributor's code — from calling `config.guardrails.check_action(...)` directly, bypassing scope checks, classification checks, the external policy engine, and egress entirely. Python has no access-control mechanism that would make `check_action` "only callable from `decide()`" — `GuardrailChecks.check_action` is a public Protocol method by construction (it has to be, since `PolicyDecisionPoint.decide` itself calls it at line 71). So the "real invariant, not an opt-in" claim is true of the two engines that exist in this codebase today, verified by grep, but it's an architectural convention the codebase's own structure makes easy to honor and easy to violate simultaneously — nothing would raise an error if a new engine implementation "forgot" to route through the PDP.

## Q12: How would `PolicyDecisionPoint` compare to how AWS IAM actually evaluates a request (explicit deny > explicit allow > implicit deny, evaluated across potentially many attached policies)? Is `decide()`'s composition model equivalent?

Structurally similar in spirit (multiple independent policy dimensions composed into one decision) but simpler and with a different default posture. IAM's evaluation logic is famously deny-overrides-allow across an arbitrary number of attached identity/resource/permission-boundary/SCP policies, with an implicit deny as the baseline unless something explicitly allows the action. `PolicyDecisionPoint.decide` is a fixed, hardcoded sequence of exactly five checks (scope, classification, guardrail, confirmation, external engine, egress — six if you count egress separately) evaluated in a fixed order, where **any single check failing produces an immediate deny** (each `if` block that finds a problem returns early with `GuardrailResult(False, ...)`) — this is closer to "all of N checks must pass" (a logical AND) than to IAM's "explicit deny anywhere wins, otherwise need at least one explicit allow." Concretely: `decide()` has no notion of an "explicit allow" overriding a stricter policy elsewhere — every check is a veto, there's no way for, say, `CedarPolicyEngine` to explicitly allow something that the deterministic guardrail already decided to block (correctly — those checks run in strict sequence, and the guardrail check happens BEFORE the external engine, so the external engine only ever gets a chance to independently *deny* something the built-in checks already passed, not to override them). This is arguably safer/simpler than IAM's full policy-combination algebra (no risk of a permissive policy statement anywhere in a large policy set silently overriding a restrictive one), at the cost of expressiveness — you cannot compose "generally deny, except explicitly allow this narrow case" the way a real IAM permission-boundary/SCP setup can.

## Q13: `PolicyEngine` (line 21) is a one-method `Protocol` (`allow(input: dict[str, Any]) -> bool`). What's the tradeoff of `input` being an untyped `dict[str, Any]` rather than a defined dataclass/TypedDict — especially since `OPAPolicyEngine.allow` and `CedarPolicyEngine.allow` each parse it slightly differently (`.get("result", False)` on the OPA response vs. `input.get(...)` calls with different defaults on the Cedar side)?

The untyped dict is what makes the Protocol genuinely provider-agnostic: OPA's Rego `input` document, Cedar's principal/action/resource/context shape, and any future engine's own expected shape are all free to interpret the same convenience dict differently without `PolicyEngine`'s Protocol definition needing to change — this is explicitly called out in `CedarPolicyEngine`'s docstring (line 141-146): "`allow()` takes the identical convenience input shape as `OPAPolicyEngine` — {...} — so a team can point Policy enforcement at OPA or Cedar interchangeably." The cost is exactly what Q8 already surfaces: since there's no shared schema, each implementation independently decides its own defaults for missing keys (`OPAPolicyEngine` doesn't apply any defaults — it forwards `input` to OPA verbatim and lets Rego decide what a missing field means; `CedarPolicyEngine` applies its own Python-side defaults, like `1_000_000.0` for a missing `max_cost`), so the two engines are NOT guaranteed to behave identically on the same *malformed or partial* input, only on the well-formed input `decide()` always constructs. A caller who only tests against `OPAPolicyEngine` and later swaps to `CedarPolicyEngine` (or vice versa) is trusting an informally-documented shape agreement, not a type-checked one — nothing would catch a future change to `decide()`'s dict-building code (line 81-84) that silently drops or renames a key, since `dict[str, Any]` accepts anything.

## Q14: `DEFAULT_CEDAR_POLICY` (line 119-129) only encodes two rules — tool membership (`resource in principal.allowed_tools`) and a cost ceiling (`context.cost_so_far.lessThan(context.max_cost)`). It says nothing about autonomy level, `requires_approval`, or destructive-action gating. If a team called `CedarPolicyEngine.allow(...)` directly instead of going through `PolicyDecisionPoint.decide`, what protection would they lose?

Every protection that lives in `GuardrailEngine.check_action` (autonomy-level gating via `AutonomyLevel.L1_RECOMMEND`/`L2_DRAFT` destructive blocking, the `requires_approval` human-in-the-loop set, and the `Policy.max_cost_usd_per_thread` budget check duplicated in Cedar-native form) plus everything in `decide()`'s own scope/classification/confirmation/egress checks would simply not run — `CedarPolicyEngine.allow` in isolation only ever answers "is this tool in the allowed list, and is spend under the ceiling," nothing more. This is fine and expected *as designed*, because `PolicyDecisionPoint.decide` is meant to be the sole integration point (per Q11) — `self.guardrails.check_action(...)` runs at line 71, strictly before the external engine is even consulted at line 80. But it's a sharp edge for anyone tempted to treat `CedarPolicyEngine`/`OPAPolicyEngine` as complete, standalone authorization systems rather than as one composable layer inside a larger decision: a team migrating "real policy-as-code" logic entirely into Cedar/Rego and calling `.allow()` directly (bypassing `decide()` to avoid double-checking things they've now "moved" into Cedar) would silently lose autonomy-level gating, per-tool human-approval requirements, and egress allowlisting unless they explicitly reimplemented all of that inside their own Rego/Cedar policy text — none of which `DEFAULT_CEDAR_POLICY` or the bundled OPA integration attempts to replicate.

## Q15: If you wanted to unit-test `PolicyDecisionPoint.decide`'s composition logic without standing up a real OPA server or installing `cedarpy`, how would this module's design make that easy or hard?

It's straightforward, and that's a direct consequence of `PolicyEngine`/`GuardrailChecks`/`EgressPolicy` all being either Protocols or simple dataclasses with no hidden global state. A test can construct `PolicyDecisionPoint(guardrails=<a stub GuardrailChecks with a canned check_action>, policy_engine=<a lambda-like stub implementing allow()>, egress=<a real or stubbed EgressPolicy>)` and exercise `decide()`'s branching entirely in-process, with no network calls, by supplying a fake `policy_engine.allow` that returns a fixed `True`/`False` to test that branch in isolation from OPA/Cedar's real wire protocols. This is the practical payoff of the Protocol-based design discussed in `guardrails.py`'s Q4: testing `decide()`'s own logic (ordering, short-circuiting, the scope/classification checks) doesn't require testing `OPAPolicyEngine`/`CedarPolicyEngine` at all — those two classes need their own separate, narrower tests (ideally against a real `opa run --server` instance and a real `cedarpy` install respectively, which the docstrings claim were actually done: "Verified against a live local `vault server -dev` instance" is `security.py`'s claim for Vault, and this file's `CedarPolicyEngine` docstring says "Verified against the real cedarpy package"). The design cleanly separates "does the composition logic work" from "does this specific external policy engine integration work," which is exactly the seam you want for fast, dependency-free unit tests plus a smaller set of slower integration tests against the real systems.
