# agent_foundry/a2a_bridge.py — Q&A

Makes an Agent Foundry agent discoverable and callable by other agents/organizations over Google's open Agent2Agent (A2A) protocol, via three functions built on the real protobuf-based `a2a-sdk`: `agent_card_for()` (advertise capabilities), `build_a2a_app()` (serve a compiled graph over A2A's task lifecycle as a FastAPI/ASGI app), and `send_a2a_message()` (call a remote A2A agent as a client).

## Q1: The module docstring is careful to distinguish A2A from MCP and from the framework's own supervisor/swarm. What's the actual boundary, and why does Agent Foundry need all three instead of picking one?

MCP (`mcp_tools.py`) is agent-to-*tool*: an LLM calls a function-shaped capability and gets structured data back, with no notion of the callee having its own goals or conversation state. The supervisor/swarm pattern in `orchestration.py` is agent-to-agent, but confined to one process and one trust domain — every sub-agent shares the same `Identity`, `Policy`, and event loop as the caller. A2A is agent-to-agent *across* process and organizational boundaries: the remote party is a black box you don't control, running on infrastructure you don't own, potentially built on a completely different stack. You can't get that from MCP (wrong semantics — MCP has no task lifecycle, no AgentCard-style capability discovery) or from the in-process supervisor (wrong trust/process boundary — it assumes shared memory and a shared `Identity`). Collapsing all three into one abstraction would either force every tool call to pay the overhead of a network task lifecycle, or force every cross-org call to fake being a local Python function, hiding real failure modes (network partition, a remote org's own RBAC rejecting you, a task that takes minutes rather than milliseconds) behind an interface that promises none of that.

## Q2: Walk through `agent_card_for()` line by line. What happens if the caller omits `rpc_url`?

`agent_card_for()` (line 37) takes an `AgentConfig`, a `name`, and a list of `skills` dicts, and builds a real `a2a.types.AgentCard`. Each skill dict becomes an `AgentSkill(id=..., name=..., description=..., tags=...)` — note `description` and `tags` use `.get()` with defaults, so a caller only has to supply `id` and `name` per skill. The card's own top-level `description` is hardcoded to `config.system_prompt[:200]` — the first 200 characters of the agent's system prompt stand in for a human-readable description, which is a lossy but zero-effort translation (a system prompt is written to steer the *model*, not to advertise capabilities to other agents, so this can read oddly or leak implementation details of the prompt to any org that fetches the card). If `rpc_url` is omitted, `interfaces` is an empty list (line 59), so the returned `AgentCard` has no `supported_interfaces` — other agents can still fetch and read the card (e.g. to decide whether to bother integrating) but have no advertised transport to actually connect through. This is a deliberate two-phase design: discoverability and connectivity are separable, matching A2A's own model where a card can exist before a server is actually up.

## Q3: `agent_card_for()` takes `skills` as a caller-supplied list, not derived automatically from `config.tools`. Why not auto-derive it, and what's the security implication of the manual approach?

The comment at line 44-45 says explicitly: "one entry per capability you want other agents to discover, typically one per tool in config.tools that you want exposed externally (a subset is fine...)". Auto-deriving from `config.tools` would silently expose every locally-registered tool's existence to any org that requests the card, even tools that are only meant to be reachable from inside the process (e.g. an internal `debug_dump_state` tool). Requiring the caller to explicitly list `skills` makes external advertisement an opt-in allowlist rather than an opt-out blocklist, which is the safer default when the audience is genuinely untrusted (other organizations, not just other in-process agents). The tradeoff is that `skills` and `config.tools` can drift — nothing keeps them in sync, so a builder could advertise a skill for a tool that was since removed from `config.tools`, or forget to update the card when a new externally-relevant tool is added. The comment also notes A2A discoverability and the framework's own RBAC (`Policy.allowed_tools`) are "independent gates" — advertising a skill via the card does not itself grant the remote caller permission to invoke anything; that's still enforced downstream by whatever policy the served graph applies.

## Q4: `build_a2a_app()`'s `_GraphExecutor.execute()` enqueues a `Task` event before doing anything else, and the comment calls out a subtle ordering requirement. What breaks if that Task enqueue were skipped or reordered?

Lines 82-86: the executor enqueues a `Task(id=..., context_id=..., status=TaskStatus(state=TASK_STATE_SUBMITTED))` onto the `EventQueue` *before* calling `TaskUpdater.start_work()`. The comment explains why: A2A's task-lifecycle protocol expects any status-update event to reference an already-known Task, but `TaskUpdater.submit()`/`start_work()` only emit *status update* events, not the initial `Task` object itself. If you skipped the explicit enqueue and went straight to `updater.start_work()`, a spec-compliant client would receive a status update referencing a `task_id` it has never seen a `Task` for — undefined/broken behavior depending on how strictly the client's state machine is implemented (some might silently drop it, others might raise on an unknown task). This is exactly the kind of protocol-fidelity detail that's easy to get wrong when treating A2A as "just an RPC call with extra steps" instead of respecting its actual state machine.

## Q5: The executor raises `RuntimeError` if `context.task_id` or `context.context_id` is `None` (line 87-88), but that check runs *after* the Task has already been enqueued using those same possibly-`None` values (line 84). Is that a real bug?

Yes — it's an ordering bug as written. `Task(id=context.task_id, context_id=context.context_id, ...)` at lines 83-86 already reads `context.task_id`/`context.context_id` before the guard at line 87 checks whether they're `None`. If the A2A SDK ever hands the executor a `RequestContext` with a `None` task_id or context_id, the malformed `Task` (with `id=None`) would already have been enqueued to the client before the `RuntimeError` is raised — the client sees a broken event, then the executor blows up. This isn't hypothetical defensive code exercised in the happy path; the SDK's `RequestContext` typing apparently allows `None` for these (hence the check existing at all), so in practice this is a real, if narrow, correctness gap in an otherwise carefully-commented file — the guard should run *before* line 83, not after.

## Q6: What is the known a2a-sdk upstream bug documented at the top of the file, and what does it mean for `build_a2a_app()` in production?

Per the docstring (lines 17-27): `build_a2a_app()` raises `AttributeError: ... has no attribute 'is_repeated'` while FastAPI/OpenAPI-doc-generation code inside `a2a-sdk`'s `_proto_schema.py` inspects a protobuf `FieldDescriptor` — it reads an `is_repeated` attribute that doesn't exist on either the C++/upb or pure-Python protobuf backend installed. The docstring's own hypothesis is that the library meant `field.label == FieldDescriptor.LABEL_REPEATED` instead. This is explicitly attributed to a2a-sdk 1.1.2 itself, not to this bridge's code, and `agent_card_for()`/`send_a2a_message()` are unaffected (they don't touch the OpenAPI-doc-generation path). Practically, this means `build_a2a_app()` — the *server* side of this bridge — can't be trusted in production against that a2a-sdk version until upstream fixes it; the project's own test suite (`tests/test_a2a_bridge.py`) documents this by skipping its live round-trip test with the same explanation rather than pretending it passes. This is an honest, verifiable limitation, not a guess — the module states it hit this against a real running server, matching the project's stated discipline of testing against live processes rather than mocked type shapes.

## Q7: `_GraphExecutor.cancel()` just raises `NotImplementedError`. Walk through what actually happens if a remote A2A client tries to cancel an in-flight task, and what the impact of that gap is.

Line 100-101: `cancel()` is defined but its entire body is `raise NotImplementedError("this reference executor doesn't support cancellation")`. If a remote client sends a cancel request through the A2A protocol against a task that's mid-execution, the `AgentExecutor` framework will invoke this method, which immediately raises. Depending on how `DefaultRequestHandler` surfaces executor exceptions (not shown in this file — it's `a2a-sdk` internal behavior), the remote client most likely receives an error response rather than a graceful "task cancelled" confirmation, and the underlying `graph.invoke()` call keeps running to completion on the server regardless — there's no mechanism here to interrupt it. This means a long-running or stuck task can't be aborted by a remote caller; the client's only recourse is to stop waiting for a response and treat the task as abandoned, while the server continues consuming resources (LLM calls, tool calls, budget) for a task nobody's listening for anymore. Since `graph.invoke()` is a synchronous blocking call, wiring in real cancellation would require either running it in a cancellable task/thread with a check for a cancellation flag, or relying on LangGraph's own interrupt/checkpoint machinery — neither of which this reference executor attempts.

## Q8: `send_a2a_message()` handles two different response payload shapes (`"message"` vs `"task"`). Why does a single logical reply require branching on two different SDK response types, and what happens if a response comes back with neither?

Lines 126-133: the client iterates `client.send_message(request)` as an async stream, and for each response checks `response.WhichOneof("payload")` — a protobuf oneof discriminator — branching on whether the payload is a standalone `message` or a `task`. The comment explains why both exist: `TaskUpdater.complete()` (used server-side in `build_a2a_app()`, and presumably by any other A2A-compliant server) attaches the final reply text to the task's *terminal status update* rather than emitting it as an independent `Message` event. So a caller must handle both representations to work against arbitrary A2A servers, not just ones built with this bridge's own `build_a2a_app()` — some servers may stream a `message` event, others fold the final content into `task.status.message.parts`. If a response arrives with neither payload type (e.g. some other oneof variant, or an intermediate task-update with no message attached), `reply_text` is never assigned in that iteration and simply keeps whatever value it had from a prior iteration (initialized to `""` at line 125) — the function doesn't distinguish "no reply yet" from "empty reply," so a remote agent that never sends a message/task-with-message payload silently returns an empty string rather than raising an error, which could mask a genuine protocol violation or a remote-side failure as a stylistically valid a but semantically wrong empty answer.

## Q9: What happens, concretely, if the remote agent at `url` in `send_a2a_message()` times out or the connection drops mid-stream?

Nothing in `send_a2a_message()` sets an explicit timeout, and no `except` clause wraps `client.send_message(request)` — the only structured control flow is the `try/finally` at lines 123-136, which guarantees `client.close()` runs but does not catch or translate exceptions. If the remote server hangs, whatever timeout behavior `a2a.client.ClientFactory`'s underlying HTTP/JSON-RPC transport applies (not visible in this file — it's `a2a-sdk`/`httpx` behavior) will eventually raise, and that raw exception propagates straight up to whatever called `send_a2a_message()` — there's no retry, no wrapping in a domain-specific exception, no fallback text. A caller integrating this into `orchestration.py` (e.g. via `agent_as_tool`-style wrapping, mirroring `autogen_bridge`/`crewai_bridge`) would need to add its own timeout/retry/exception-to-`ToolResult` translation, because this function assumes success and lets failure surface as whatever exception type the underlying SDK/transport happens to throw.

## Q10: How faithful is this bridge's translation of Agent Foundry's own conversational state to A2A's task/message model — what's lost?

The translation is deliberately thin. On the server side, `context.get_user_input()` (line 91) reduces the incoming A2A message down to plain text, discarding any richer A2A message structure (multiple `Part`s, non-text content types, attachments) — only text parts are read via `context.get_user_input()`, and the reply back is a single `Part(text=reply)` (line 98), so multi-modal or multi-part exchanges are not supported. Thread continuity across turns is mapped onto `thread_id = context.context_id or context.task_id` (line 92), which is then fed straight into the graph's `configurable.thread_id` — this assumes A2A's `context_id` is a stable, reusable identifier for a logical conversation the way LangGraph's `thread_id` is, which is a reasonable but unverified assumption about how A2A clients are expected to reuse `context_id` across turns. On the client side, `send_a2a_message()` similarly only extracts and concatenates `.text` from `Part`s (lines 129, 133), dropping any non-text parts a richer A2A response might include. So: identity/state continuity survives (via thread/context id), but content richness (multi-part messages, structured/typed content, streaming intermediate updates beyond the final reply) does not.

## Q11: Given more time, what's the single most valuable improvement to this module?

Fixing (or working around) the a2a-sdk `is_repeated` bug so `build_a2a_app()` is actually production-usable would unblock everything else, since right now the server half of the bridge is documented as broken against the latest released SDK. Close behind that: implementing real cancellation in `_GraphExecutor.cancel()` (today it's a guaranteed `NotImplementedError`), since a stuck or long-running `graph.invoke()` call currently cannot be aborted by a remote caller and will keep consuming resources indefinitely. A third candidate is fixing the ordering bug where `context.task_id`/`context.context_id` are read into the initial `Task` object before being checked for `None` (Q5) — small, but a genuine correctness gap in code that's otherwise unusually careful about protocol ordering.

## Q12: Why does `build_a2a_app()` accept `graph: Any` rather than a more specific type like a LangGraph `CompiledGraph`?

Per the docstring (lines 63-67), `build_a2a_app()` is meant to serve "any compiled graph (from any build_*_graph, or a quickstart agent)" — the only contract it actually relies on is that `graph.invoke(state_dict, config_dict)` returns something with `result["messages"][-1]["content"]`. Typing it as `Any` (and using duck-typed dict access rather than a `CompiledGraph`-specific import) keeps this bridge decoupled from LangGraph as a hard dependency and lets it serve any of the framework's other runtime backends (native engine, Temporal-backed graphs — per the project's "Runtime axis" architecture) as long as they expose the same `invoke()` shape. The cost is that there's no compile-time or import-time guarantee the passed object actually supports that shape — a wrong object just fails at the first `graph.invoke(...)` call inside `execute()`, surfaced as whatever exception LangGraph (or the alternate runtime) itself raises, with no earlier, clearer validation.

## Q13: The module states its three functions were "genuinely tested against a live local server," contrasted with `crewai_bridge.py`'s posture. Why does this distinction matter for someone evaluating the codebase?

The comment (lines 6-8) explicitly claims the same "real, not mocked" testing discipline as `mcp_tools.py` and `policy_engine.py` — the a2a-sdk's types were "verified via `DESCRIPTOR.fields`, never guessed," and a real local server was round-tripped against. This matters because it's an implicit admission (visible by contrast in `crewai_bridge.py`'s own docstring, which explicitly says CrewAI wasn't round-tripped in this environment) that not every bridge in this package carries the same evidentiary weight — some integrations are verified against running systems, others are written correctly-per-documentation but unverified. For an interview/architecture-review context, this is a good signal of engineering honesty: the developer is explicit about which claims are backed by an actual test run versus which are "should work, per the docs I read," rather than presenting uniform confidence across modules that don't deserve it equally.

## Q14: What's the security posture of exposing an Agent Foundry agent over A2A via `build_a2a_app()` — what could go wrong if this were put on the public internet unmodified?

Nothing in `build_a2a_app()` wires in authentication, authorization, or rate limiting for incoming A2A requests — the `FastAPI` app it returns has only the A2A protocol routes added via `add_a2a_routes_to_fastapi()`. Any client that can reach the ASGI app's `rpc_url` can submit a task, which is executed via `graph.invoke()` using whatever `Identity`/`Policy` is baked into the graph at build time (the executor has no way to derive per-caller identity from the A2A request — every remote caller is treated identically, under the graph's single configured policy). This is a materially different trust model from the framework's own RBAC layer (`Policy.allowed_tools`, `PolicyDecisionPoint`), which is designed around a caller-specific `Identity` — here, the "caller" is opaque to the graph. Combined with the fact that `agent_card_for()`'s advertised `description` is derived straight from `config.system_prompt[:200]` (Q2), an unauthenticated deployment leaks a slice of the system prompt to anyone who fetches the card, and lets anyone who can reach the RPC endpoint drive the underlying graph with the same privileges as any other caller. Production use would need an auth/authz layer in front of (or wrapped around) this FastAPI app — not something this bridge provides.

## Q15: `send_a2a_message()` discovers the target agent's card at `<url>/.well-known/agent-card.json` implicitly via `ClientFactory().create_from_url(url)`. What trust assumption does that bake in, and is it validated anywhere in this file?

The docstring (lines 115-116) states the card is discovered at that well-known path, but the actual discovery/parsing/validation is entirely delegated to `a2a.client.ClientFactory` — this file does zero validation of the card's contents (no check that the remote agent's advertised skills match what the caller expects, no pinning of the remote's identity, no verification that the URL wasn't redirected somewhere unexpected). The function trusts whatever `ClientFactory` resolves and connects to. This means `send_a2a_message()` is only as safe as the URL a caller supplies — if that URL comes from an untrusted source (e.g. a value discovered dynamically from another agent's output, rather than a hardcoded/configured endpoint), this function would happily connect to and exchange messages with an attacker-controlled A2A server, and whatever the response text is gets fed straight back into the calling context (e.g. as an LLM tool result) with no sanitization — a prompt-injection vector if the response text is later treated as trusted content upstream.
