# agent_foundry/escalation.py — Q&A

Defines the "third outcome besides auto-approve and deny": an `Escalator` Protocol and its zero-dependency reference implementation, `QueueEscalator`, which hands a case off to an async human/ticket queue (via `EscalationTicket`) instead of blocking the calling thread on an immediate synchronous decision.

## Q1: The module docstring says `Escalator` is "distinct from `Policy.requires_approval`, which pauses the *same* thread." Walk through exactly how the two mechanisms differ operationally.

`Policy.requires_approval` (enforced in `orchestration.py`'s `make_act_node`, via the PDP's decision and `"approval" in gr.reason`) triggers LangGraph's `interrupt()` — the *same* graph run pauses in place, its state is checkpointed, and the calling code path is blocked (or, for an async caller, suspended) until a `resume`-style call supplies `{"approved": bool}`. It's synchronous in the sense that the specific run that needed approval cannot proceed at all until that exact decision arrives. `Escalator.escalate()`, by contrast, doesn't pause anything — `QueueEscalator.escalate()` just constructs an `EscalationTicket`, stores it in `self._tickets`, and returns immediately; there's no blocking, no `interrupt()`, and nothing about the calling agent's own execution is suspended by this call. The module docstring's phrase "hands the case off entirely" is the key distinction: escalation is meant for routing a case to a human working an async queue (or "a different, more-trusted agent") on their own schedule, not for stopping one specific run dead until an answer comes back.

## Q2: Is `GuardrailResult.escalate` actually wired to `QueueEscalator` anywhere in this codebase today? Trace it and be precise.

No. `contracts.GuardrailResult` declares `escalate: bool = False` with the comment "True: hand off to a human/other agent (escalation.py) instead of a flat deny," but grepping the entire `agent_foundry` package for anywhere this flag is set to `True`, or anywhere it's *read* other than in its own declaration, turns up nothing outside `escalation.py`'s own docstring prose. `orchestration.py`'s `make_act_node` — the only place a `GuardrailResult`-shaped decision (`gr = config.pdp.decide(...)`) is actually consumed for a tool call — only ever inspects `gr.allowed` and does a substring check `"approval" in gr.reason`; it never reads `gr.escalate` at all. This means `escalation.py`'s `Escalator`/`QueueEscalator` machinery is, as of this codebase, a fully-implemented but *entirely unwired* integration point: the field exists on the contract, the reference implementation exists and is presumably tested standalone, but nothing in the think/act loop actually calls `.escalate()` when a guardrail sets `escalate=True` — because nothing ever sets it `True` to begin with. This is a genuine, honest gap worth calling out plainly rather than glossing over.

## Q3: Given the gap in Q2, what would concretely need to change in `orchestration.py` to actually wire escalation into the tool-call gate?

`make_act_node`'s branch that currently reads `if not gr.allowed and gr.reason and "approval" in gr.reason: ... interrupt(...)` would need a parallel branch checking `gr.escalate` (which the current `PolicyDecisionPoint.decide(...)` call would first need to actually be able to set — nothing in `guardrails.py`/`policy_engine.py`'s check functions was observed setting it either, based on the grep in Q2, so upstream checks would also need to start setting `escalate=True` for cases that warrant it). That branch would call something like `config.escalator.escalate(identity=identity, reason=gr.reason, context={"tool": tool_name, "args": args})` instead of (or in addition to) `interrupt()`, and `AgentConfig` would need a new optional `escalator: Escalator | None` field, following the same "optional, default `None`, unchanged behavior for everyone who doesn't configure it" pattern `AgentConfig.pdp`/`AgentConfig.critique` already establish. None of this exists today — it's a plausible, minimal-diff integration sketch, not a description of current behavior.

## Q4: Walk through exactly what happens if a caller calls `QueueEscalator.escalate()` but nobody ever calls `resolve()` on the resulting ticket.

`escalate()` creates an `EscalationTicket` with `resolved=False` (the dataclass default) and stores it keyed by `ticket.id` in `self._tickets`. `pending()` returns `[t for t in self._tickets.values() if not t.resolved]` — so an un-resolved ticket simply sits in that list forever, returned by every future call to `pending()`, with no expiry, no age-based escalation-of-the-escalation, and no notification mechanism to alert anyone that it's aging. There is no timeout field on `EscalationTicket` at all — only `created_at` (a plain `time.time()` timestamp), which records *when* it was created but nothing in `QueueEscalator` ever reads that field to detect staleness or trigger any follow-up action. A ticket from a month ago and a ticket from a second ago look identical to `pending()` — a caller would have to manually filter `pending()` by `created_at` themselves to build any kind of SLA or staleness alerting on top; the module provides no such logic itself.

## Q5: What happens if `resolve()` is called with a `ticket_id` that doesn't exist?

`resolve(self, ticket_id: str, resolution: str) -> None` does `self._tickets[ticket_id].resolved = True` directly — a plain dict subscript with no `.get()` or existence check. An unknown `ticket_id` raises an uncaught `KeyError`, propagating straight out of `resolve()` to whatever caller invoked it. There's no defensive check, no custom exception type analogous to `orchestration.py`'s `SupervisorRoutingError` that would give a caller a clear, escalation-specific error message — a typo'd or already-deleted ticket id just produces a generic `KeyError` with the raw dict-access line in the traceback. This is consistent with the module's overall minimalism (it's explicitly a "zero-dependency reference implementation" meant to be swapped for a real ticketing system), but it is a real rough edge for any caller building directly on `QueueEscalator` in production without wrapping it.

## Q6: Is `QueueEscalator` thread-safe? What happens if `escalate()` and `resolve()` are called concurrently from multiple threads?

`escalate()`'s dict assignment (`self._tickets[ticket.id] = ticket`) and `resolve()`'s attribute mutation (`self._tickets[ticket_id].resolved = True`) are each individually atomic under the GIL — no two threads can interleave mid-assignment on the same key, so the data structure itself won't corrupt. But there's no lock coordinating *sequences* of operations: nothing prevents two different callers from calling `resolve()` on the *same* ticket concurrently with two different `resolution` strings — both writes would succeed, one silently overwriting the other with no error, no warning, and no record of the conflicting attempt. There's also no "claim" step (e.g., an operator marking a ticket as "in review" before finally resolving it) that would let a system detect and prevent two operators from resolving the same ticket differently — `QueueEscalator` trusts that whatever calls `resolve()` is the sole authority on that ticket's outcome, which is a reasonable assumption for a single-operator queue but not for a team of reviewers pulling from the same `pending()` list concurrently.

## Q7: `QueueEscalator` is entirely in-memory. What happens to pending tickets if the process restarts, and how does that compare to the rest of the framework's durability story?

Every `EscalationTicket` lives only in `self._tickets`, a plain `dict` field on the dataclass with no persistence layer — a process restart discards every pending ticket with no trace, exactly the same non-durability gap `blackboard.py`'s `Blackboard` has for its shared reasoning state (see that module's own Q&A). What makes this particularly notable here is the contrast with `distributed.py`: every other stateful primitive in this framework's fleet-safety story — `RunBudget`, rate limiting, tool cache, SLA tracking, cost ledger, idempotency store, even a generic `StateStore` — has a corresponding `Redis*` class in `distributed.py` that satisfies the exact same Protocol for cross-replica, cross-restart durability. `escalation.py` has no such counterpart; there is no `RedisEscalator` in `distributed.py`, despite escalation tickets being exactly the kind of state (a human review queue) you'd most want to survive a restart or be visible across a fleet of replicas, not just the one process that happened to create the ticket. This is the single clearest gap between this module and the rest of the framework's design philosophy.

## Q8: Why is `Escalator` a `Protocol` declaring only `escalate()`, when `QueueEscalator` also implements `pending()` and `resolve()`? What does that asymmetry cost a caller?

Only `escalate(self, *, identity, reason, context=None) -> EscalationTicket` is part of the `Escalator` Protocol — `pending()` and `resolve()` are `QueueEscalator`-specific methods, not part of the structural interface. This mirrors `DecisionMaker`'s minimal-Protocol philosophy in `planning.py` (only `.choose()` is required there too, even though `BanditSelector` also has an `.observe()` method that isn't part of the Protocol) — the idea being that a caller who only needs to *create* escalations shouldn't be coupled to any particular queue-management API. The cost is real, though: any code written generically against the `Escalator` Protocol type (rather than against `QueueEscalator` concretely) can only call `.escalate()` — it cannot call `.pending()` or `.resolve()` polymorphically, because a different `Escalator` implementation (say, one that immediately files a Zendesk ticket via their REST API) has no obligation to expose those methods, or might expose entirely differently-shaped equivalents. This means any code that needs to *manage* escalations (list pending ones, resolve them) is necessarily written against `QueueEscalator` specifically, not against the abstract `Escalator` interface — a real, if intentional, limit on how far the Protocol-based swap point actually extends.

## Q9: The module docstring mentions handing a case off "to a different, more-trusted agent" as one of the two escalation destinations. Does anything in this file actually implement agent-to-agent handoff?

No — `Escalator.escalate()`'s signature (`identity`, `reason`, `context`) and `QueueEscalator`'s implementation are both shaped entirely around a human/ticket-queue model: an `EscalationTicket` records `identity_id`, `reason`, `context`, and eventually a human-authored `resolution` string. There's no field or code path here for routing to another *agent* rather than a human reviewer — no target-agent identifier, no mechanism to invoke a different `AgentConfig` or graph. The actual agent-to-agent handoff primitive in this codebase lives entirely in `orchestration.py`: `make_swarm_router`'s `HANDOFF <agent_name>` text convention (decentralized) or `build_supervisor_graph`'s `Command(goto=...)` routing (centralized) — both are LLM-driven, in-band routing decisions between peer agents, conceptually unrelated to `escalation.py`'s ticket-based, out-of-band human handoff. The module docstring's "or to a different, more-trusted agent" phrase describes a *conceptual* category of escalation destination this Protocol is generic enough to someday support, not something `QueueEscalator` — or any code in this file — currently implements.

## Q10: Why does `EscalationTicket.context` accept an arbitrary `dict[str, Any]` rather than a typed schema?

An escalation can originate from any guardrail check, any tool-call denial, any critique-gate low-confidence event, or any other future source — each of those has a completely different natural shape of "what a human needs to see to make a decision" (a denied tool call's `{tool, args, reason}` versus a critique escalation's `{kpi, score, threshold, draft_reply}`, per `orchestration.py`'s own `interrupt()` payloads for comparison). A typed schema would either need a large union of every possible escalation-context shape, or force every caller into a lossy common denominator. An untyped `dict[str, Any]` sacrifices any compile-time guarantee about what a ticket's context contains, in exchange for letting every kind of escalation source attach whatever context is actually relevant to it, at the cost of pushing that documentation burden onto each caller rather than the type system. This is consistent with the framework's broader tolerance for loosely-typed dicts at integration boundaries — the codebase's own `CLAUDE.md`-level architectural note (visible in the wider project) explicitly avoids Pydantic, favoring plain dataclasses and dicts throughout.

## Q11: Why does `EscalationTicket` use `uuid.uuid4().hex` for its `id` rather than a sequential integer or a timestamp-based id?

A random UUID guarantees uniqueness without requiring any shared counter state — no coordination needed even if multiple `QueueEscalator` instances (or, in a hypothetical distributed deployment, multiple processes each running their own escalator) were creating tickets concurrently, which a sequential integer counter could not guarantee without a central authority or a lock. This is the same rationale `orchestration.py`'s `agent_as_tool` uses for its per-call `thread_id` suffix (`uuid.uuid4().hex[:8]`) and `distributed.py`'s `RedisLease.acquire()` uses for its per-holder token — UUIDs are the standard, dependency-free way to get collision-resistant identifiers without a coordination point, which matters even more here given `QueueEscalator`'s complete lack of any distributed backing (per Q7) — if this were ever run across multiple processes without a shared Redis-backed store, at least the ticket ids themselves wouldn't collide, even though the underlying `_tickets` dicts would still be entirely disjoint per-process.

## Q12: Is there any priority, severity, or ordering concept on an `EscalationTicket`, and what does that mean for how `pending()` would be consumed by a real operator UI?

No — `EscalationTicket` has exactly five fields: `id`, `identity_id`, `reason`, `context`, `created_at`, plus `resolved`/`resolution` once closed. There's no `severity` or `priority` field, and `pending()` returns tickets in whatever order Python's dict preserves them (insertion order, in practice, since `dict` is ordered as of modern Python) — effectively FIFO by creation time, with no way to say "this escalation is more urgent than that one" short of an operator manually inspecting `context`/`reason` themselves. Every escalation — a critique gate's low-confidence flag and, hypothetically, a wire-transfer approval denial — would be treated identically for queue-ordering purposes if both were routed through the same `QueueEscalator`. A real operator-facing UI built on top of this would need to add its own prioritization logic entirely externally, since nothing in this module gives it anything to prioritize on beyond parsing `reason`/`context` heuristically.

## Q13: Compare the durability story of `interrupt()`-based approval versus `QueueEscalator`'s ticket queue. Which one can actually survive a process restart today, and why is that a little counterintuitive?

Somewhat counterintuitively, the "quick, synchronous, blocks-the-thread" `interrupt()` mechanism is the one with a genuine durability story, *provided* a durable `BaseCheckpointSaver` (like `SqliteSaver`/`PostgresSaver`, per `orchestration.py`'s module docstring on checkpointer durability) is configured instead of the default in-process `MemorySaver` — a paused, interrupted graph run's state is checkpointed and can be resumed even after a full process restart, because that's precisely what a LangGraph checkpointer exists to do. `QueueEscalator`, despite conceptually being the "hand it off, don't block anything" mechanism meant for asynchronous, potentially long-lived human review, has *zero* built-in persistence — a process restart loses every pending ticket outright, with no checkpointer-equivalent concept anywhere in `escalation.py`. So the mechanism explicitly designed for a short, synchronous pause turns out to be the durable one (when configured with a real checkpointer), while the mechanism explicitly designed for a longer-lived, asynchronous handoff is the one that's fragile to a restart — an inversion worth noticing precisely because it isn't the intuitive pairing of "quick things are fragile, long-lived things are durable."

## Q14: What's the single most consequential limitation you'd flag about this module in a design review, and why?

The unwired `GuardrailResult.escalate` flag from Q2 is the most consequential, because it means the entire "third outcome besides auto-approve and deny" the module's own docstring promises doesn't actually exist as an automatic, end-to-end behavior anywhere in this codebase today — a guardrail check *could* theoretically set `escalate=True`, but nothing currently does, and even if one did, `make_act_node` wouldn't act on it. `Escalator`/`QueueEscalator` are fully-built, presumably well-tested infrastructure sitting entirely unconnected to the actual tool-call gating path they were clearly designed to plug into. A close second is the total lack of persistence (Q7) — even once wired up, an in-memory-only ticket queue would lose every pending human-review case on a process restart, which is a serious operational gap for anything genuinely relying on human review as a safety backstop. Given more time, wiring the flag into `make_act_node` (per the Q3 sketch) and adding a `RedisEscalator` alongside `distributed.py`'s other Redis-backed Protocol implementations would be the two highest-leverage fixes, in that order.

## Q15: If a builder wanted "escalate to a Slack channel" today, how would they actually do it given what's in this file, and what would they have to build themselves?

They would implement a new class satisfying the `Escalator` Protocol's single method — `escalate(self, *, identity, reason, context=None) -> EscalationTicket` — whose body posts a formatted message to a Slack channel (reusing, notably, `channels.py`'s `_post_to_slack` helper or a similar API call) and still constructs and returns a real `EscalationTicket` object, since the Protocol's return type is fixed regardless of the delivery mechanism underneath. The module's own docstring explicitly anticipates this: "swap for a real ticketing system (Zendesk, Jira Service Desk, a Slack channel post) by implementing the same `escalate()` shape — the tickets it returns look the same either way." What the builder would *not* get for free: any way for a human's reply in that Slack channel to route back into `resolve()` automatically (there's no webhook-to-`resolve()` wiring anywhere in this codebase, and per Q8, `resolve()` isn't even part of the `Escalator` Protocol, so a Slack-backed implementation isn't obligated to expose an equivalent at all) — that round-trip would need to be built entirely from scratch, likely composing this module with `channels.py`'s Slack Events API handling to capture a reply and call back into whatever ticket store the builder chose.
