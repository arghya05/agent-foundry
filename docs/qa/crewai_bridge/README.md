# agent_foundry/crewai_bridge.py — Q&A

Wraps a CrewAI `Crew` (agents + tasks already wired together) as an ordinary Agent Foundry `ToolSpec` via `crewai_as_tool()`, so a whole crew becomes a single callable tool — subject to RBAC, guardrails, the circuit breaker, and the audit log — indistinguishable downstream from a local function, an MCP tool, or an AutoGen agent.

## Q1: `crewai_as_tool()` is 12 lines. What exactly does `call()` do, and what CrewAI-specific convention does `input_key` encode?

`call(query: str)` (lines 37-39) invokes `crew.kickoff(inputs={input_key: query})` — CrewAI's documented API for kicking off a crew's tasks with template variables — and returns `getattr(result, "raw", str(result))`, i.e. CrewAI's `CrewOutput.raw` attribute if present, else the stringified result object as a fallback. `input_key` (defaulting to `"query"`) exists because CrewAI tasks are typically authored with string templates like `"Research {topic} and summarize it"`, where `{topic}` is filled in from the `inputs` dict passed to `kickoff()` — the actual variable name is whatever the crew's task descriptions were written to expect, not a fixed convention CrewAI itself enforces. So `crewai_as_tool()` can't assume `"query"` is always right; a crew whose tasks were authored around `{topic}` instead would need `crewai_as_tool(..., input_key="topic")` for the interpolation to actually land in the right template variable. Get this wrong and the crew still runs — CrewAI won't error on an unused `inputs` key — but the crew executes with an empty/default value for whatever variable its tasks actually reference, silently producing a wrong or generic result rather than failing loudly.

## Q2: The docstring says this was "written against CrewAI's documented `Crew.kickoff()`/`CrewOutput` API," with "no CrewAI install round-tripped against this one in this environment." Why call that out explicitly, and what's the practical risk?

This is an explicit confidence downgrade relative to other bridges in the same package — contrast `a2a_bridge.py` and `mcp_tools.py`, which state they were verified against real running servers/processes, or `mcp_tools.py`'s "types verified via DESCRIPTOR.fields, never guessed." Here, `getattr(result, "raw", str(result))` is a bet that CrewAI's `CrewOutput` object exposes a `.raw` attribute for the final text — which is true per CrewAI's documented API, but has not been exercised against a live install in this environment. The practical risk: any drift in CrewAI's return-type API across versions (e.g. `.raw` renamed, deprecated, or changed to a different shape in some version) would silently degrade to the `str(result)` fallback rather than fail — meaning a working-per-docs assumption could quietly produce a garbled string (like a `repr()` of a `CrewOutput` object) instead of clean text, and nothing in this file would catch or flag that at runtime. The module is explicit and honest about this being unverified — a legitimate limitation, not a hidden one.

## Q3: The docstring compares this bridge's testing posture to `events.KafkaEventBus`. What does that comparison signal about how this codebase tracks confidence levels across "optional dependency" integrations?

It signals a deliberate, consistent practice in this codebase of documenting *which* integrations have been round-tripped against a real running instance of the third-party system versus which are correct-per-documentation-but-unverified. `KafkaEventBus` and `crewai_bridge.py` are grouped together as "same posture" — both wrap an optional third-party dependency (`pip install crewai`/a Kafka client) without a live instance available in the authoring environment, whereas MCP and OPA integrations elsewhere in the package explicitly were tested live. This is valuable for anyone doing due diligence on the codebase (or interviewing its author): it means the confidence level isn't uniform across all "supported integrations," and the honest thing to do — which this codebase does — is say so per-module rather than implying blanket verification. It also means these two modules are the first places to look for subtle drift bugs if the corresponding external system's API changes.

## Q4: The docstring warns to install `crewai` "in an isolated virtualenv for this project rather than a shared base Python environment," citing dependency pins on `langchain-core`/`openai`. What's the actual failure mode this is guarding against?

CrewAI's own dependency tree pins specific (and often narrow) version ranges of `langchain-core` and `openai` packages. If a developer `pip install`s `crewai` into a shared/base Python environment that other projects (or other parts of Agent Foundry, e.g. anything using `llm_gateway.py`'s own provider SDKs) also depend on, `pip`'s dependency resolver can silently downgrade or upgrade `langchain-core`/`openai` to satisfy CrewAI's pins — breaking whatever other code in that shared environment expected a different version. This isn't a code bug in `crewai_bridge.py` itself; it's operational advice born from experience with a real, known failure mode of installing CrewAI alongside other LLM tooling. It's a good example of the kind of practical packaging knowledge that only shows up when someone has actually tried to install these things together, reinforcing that this module's author engaged with CrewAI's real packaging behavior even without round-tripping the API calls themselves.

## Q5: Walk through exactly what happens if `crew.kickoff()` raises an exception mid-crew-execution — e.g. one of the crew's internal agents fails a tool call or hits a rate limit.

`call()` has no try/except of its own — any exception from `crew.kickoff()` (a CrewAI-internal agent error, an LLM provider error inside one of the crew's agents, a malformed task result) propagates straight out of `call()`. Since this function is registered as `ToolSpec.fn` and invoked via `ToolRegistry.invoke()`/`ainvoke()`, those methods catch `Exception` around the call (`tools_gateway.py`, the `try/except Exception` blocks in both `invoke()` and `ainvoke()`), retrying up to `spec.max_retries` (unset here, so `0` — the default) before returning `ToolResult(ok=False, error=str(e))`. So the calling agent's turn doesn't crash, but retries are effectively disabled unless the caller explicitly constructs the `ToolSpec` with `max_retries` set — and even one retry would re-run the *entire* crew from scratch (`kickoff()` has no notion of resuming a partially-completed multi-agent task), which could be expensive (re-running every agent/task in the crew) or even harmful if any of the crew's internal tasks have side effects that aren't idempotent.

## Q6: Why does the reverse direction — a CrewAI `Agent`'s `tools` parameter accepting an Agent Foundry tool — need "no adapter at all," per the docstring, and is that actually true without any caveats?

The docstring (lines 10-12) states CrewAI's `Agent.tools` accepts LangChain `BaseTool` instances, and that `quickstart.py`'s `to_langchain_tool()` already converts a governed `ToolSpec` into exactly that shape — so no *new* code is needed in this file for that direction, it's fully covered by existing conversion logic elsewhere in the codebase. This is true as far as it goes, but it means the "no adapter needed" claim is conditional on `to_langchain_tool()` (defined elsewhere, in `quickstart.py`) staying compatible with whatever `BaseTool` shape CrewAI's `Agent` actually expects at runtime — a coupling this file doesn't own or test. It also means, like the AutoGen reverse direction, that once a CrewAI agent is holding a converted `ToolSpec`-as-`BaseTool`, it invokes the underlying function directly rather than through `ToolRegistry.invoke()` — so the "RBAC, guardrails, circuit breaker, audit log all apply" framing in the top-of-file docstring is specifically about the forward direction (crew-as-tool inside an Agent Foundry `ToolRegistry`); calls flowing the other way, from inside a CrewAI agent, bypass that governance layer entirely.

## Q7: How faithfully does `crewai_as_tool()` translate CrewAI's task-based execution model into Agent Foundry's single-tool-call model? What's lost?

Almost everything about *how* the crew arrived at its answer is lost. A CrewAI `Crew` can involve multiple agents, each with their own role/goal/backstory, executing multiple `Task`s potentially in sequence or hierarchically, each task's output feeding into the next — CrewAI's own execution model is inherently multi-step and multi-agent. `call()` collapses all of that into: pass one `query` in via `inputs`, block until the entire crew finishes, extract one final string (`result.raw`). There is no way for the calling Agent Foundry graph to observe intermediate task outputs, no way to intervene between the crew's internal task hand-offs, and no way to know which of the crew's several agents actually produced the final answer versus contributed supporting work. This is the same lossy "black box in, string out" pattern as `autogen_bridge.py`'s `autogen_as_tool()` — a deliberate, repeated design choice across the interop layer that trades fidelity for a completely uniform tool-calling interface.

## Q8: What happens if a crew's tasks reference a template variable that doesn't match `input_key`, and how would a developer even notice?

Since CrewAI's `kickoff(inputs={...})` simply performs string-template interpolation for keys the task descriptions reference, passing `inputs={"query": query}` when the crew's tasks actually expect `{topic}` results in the `{topic}` placeholder being left either unfilled or filled with an empty/default value, depending on CrewAI's own template-interpolation behavior for missing keys — CrewAI does not raise an error here, because from CrewAI's point of view `inputs={"query": ...}` is a perfectly valid dict, it just happens not to match what the task template needs. The crew would still run to completion and `kickoff()` would still return a `CrewOutput`, so `call()` would return some plausible-looking string — a "silent semantic failure" rather than a crash. A developer would only notice by inspecting the actual output quality (the crew answering a generic/malformed version of the task rather than the intended query) — there's no validation anywhere in this bridge that `input_key` actually matches a variable the crew's tasks reference, because that information (the task templates) lives inside the opaque `crew` object this function is handed, not in anything `crewai_as_tool()` itself inspects.

## Q9: What's the concurrency/thread-safety posture of `crewai_as_tool()`, especially if the same `Crew` object is reused across multiple concurrent tool calls?

`call()` invokes `crew.kickoff()` directly with no locking, no cloning of the `crew` object, and no protection against concurrent invocation. Whether it's safe to call the *same* `Crew` instance concurrently from multiple threads (e.g. via `ToolRegistry`'s concurrent same-turn tool dispatch in `orchestration.make_act_node`/`native_engine._act`) depends entirely on CrewAI's own internal thread-safety guarantees for `kickoff()` — which this file makes no claim about and doesn't verify (consistent with the "not round-tripped" caveat in Q2). If CrewAI's `Crew`/`Agent` objects hold mutable internal state that isn't safe for concurrent `kickoff()` calls (a real possibility for any framework not explicitly designed for concurrent reentrant execution), registering one `Crew` instance as a tool and calling it from two concurrent agent turns could produce cross-talk or corrupted state between the two calls. The safe pattern, unstated here, would be one `Crew` instance per `crewai_as_tool()` registration used only serially, or constructing a fresh `Crew` per call — neither enforced by this code.

## Q10: What's a limitation of this module you'd fix given more time?

Actually installing `crewai` in an isolated environment and round-tripping `crewai_as_tool()` against a real `Crew.kickoff()` call would be the highest-value fix, since right now the module's core assumption (`CrewOutput.raw` being the right attribute) is unverified against a live install, unlike the MCP and A2A bridges elsewhere in the package. Close behind: adding at least a coarse validation that `input_key` is one of a set of expected template variables (if that's discoverable from the `crew` object at all — CrewAI may not expose task templates in an introspectable way), and adding an explicit exception boundary/timeout around `crew.kickoff()` so a hung or extremely long-running crew doesn't block a tool call indefinitely with no way to configure a per-call timeout (nothing here wires in `ToolSpec.timeout_s`'s enforcement — that has to happen at the caller/orchestration layer, if at all).

## Q11: Compare the failure-isolation properties of this bridge to `mcp_tools.py`'s. Why is an MCP tool call's failure mode meaningfully different from a CrewAI crew's failure mode?

An MCP tool call (`mcp_tools.MCPToolSource._make_spec`'s `call()`) invokes a single, typically fast, well-scoped remote operation over a persistent session — a failure there (an `is_error` result, a dropped connection) is relatively cheap to detect and retry, and the MCP protocol itself distinguishes tool-level errors (`result.is_error`) from transport-level ones. A CrewAI crew invoked via `crewai_as_tool()`, by contrast, is a potentially long, multi-agent, multi-LLM-call pipeline where a failure deep inside one task (agent 3 of 5 hits a rate limit) surfaces as one opaque exception from `kickoff()` with no partial-progress information — and, per Q5, a retry re-runs the *entire* pipeline rather than resuming from the failure point. This means the two bridges expose structurally similar interfaces (`ToolSpec` in, string out) but very different cost/risk profiles when things go wrong — something worth calling out explicitly if `max_retries` were ever set non-zero for a CrewAI-backed tool, since the retry semantics that make sense for a cheap MCP call could be expensive or unsafe for an entire crew re-run.

## Q12: Security-wise, what should a builder be careful of when wrapping a CrewAI crew as a tool this way?

As with the AutoGen bridge, everything the crew's *internal* agents do — their own tool calls, their own LLM interactions, any file/network access CrewAI's agents are configured with — happens entirely outside Agent Foundry's `Policy`/RBAC/audit-log boundary; only the boundary crossing (the `query` string in, the `raw` string out) is governed by wrapping the crew in a `ToolSpec`. If the crew's own agents have broad tool access (e.g. shell execution, unrestricted web browsing) configured through CrewAI directly, none of that is visible to or restrained by Agent Foundry's policy engine — a builder who registers a crew as a single governed tool might reasonably but incorrectly assume the crew's *internal* actions are equally governed, when in fact only the single call boundary is.
