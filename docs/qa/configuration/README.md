# Configuration — Q&A

There is **no dedicated `config.py` / `Settings` module** in Agent Foundry. Configuration is a cross-cutting concern handled by four separate, narrow mechanisms: raw `os.environ` reads at the four call sites that need them (`agent_foundry/llm_gateway.py:103`, `agent_foundry/security.py:119`, `agent_foundry/cli.py:180`, `agent_foundry/scaffold.py:62`), `CredentialVault` in `agent_foundry/security.py` for secrets, `FeatureFlagProvider`/`StaticFeatureFlagProvider` in `agent_foundry/feature_flags.py` for behavior toggles, and `argparse` defaults in `agent_foundry/cli.py` for process-level knobs like the serve port. This file exists because "why isn't there a config module" is exactly the kind of question a reviewer asks when they notice its absence — the answer below is the honest one, not a retrofit.

## Q1: Why is there no centralized `Config`/`Settings` class the way most frameworks (Django settings.py, FastAPI's `pydantic-settings`, 12-factor `env.py`) have one?
Because the project's own architecture stance is Python-native with no Pydantic dependency (see `docs/ARCHITECTURE.md` and the project's stated "no Pydantic" rule), and a general `Settings` object is exactly the kind of place teams reach for Pydantic first — a `BaseSettings` subclass that parses env vars into typed fields with validation. Building an equivalent by hand (a dataclass with manual env parsing, type coercion, and validation) is real, non-trivial work that nothing in the current codebase needed badly enough to justify. Instead, each of the four modules that actually needs an external value reads it at the point of use with a plain `os.environ.get(...)` and a local default. This is honest scrappiness, not a hidden design principle — the actual failure mode is that there is no single place to see "everything this system reads from the environment"; you have to grep for `os.environ` and `getenv` across the tree (which is exactly what this Q&A file is a stand-in for).

## Q2: Walk through every environment variable Agent Foundry actually reads, and where.
There are exactly four, and each is read in exactly one place: `ANTHROPIC_WORKSPACE_ID` in `llm_gateway.py:103` (optional workspace scoping for the Anthropic API — falls back to `None`/unscoped if unset), a credential-by-name lookup via `os.environ.get(name)` inside `CredentialVault.get()` in `security.py:119` (so *which* variable gets read is caller-determined, not a fixed name — e.g. a caller asking for `"OPENAI_API_KEY"` triggers a read of that exact variable), `PORT` in `cli.py:180` (used only as the argparse default for `agent-foundry serve --port`, coerced to `int`, defaulting to `8080` if unset or unparsable... actually unset falls back to the string `"8080"` which `int()` then parses — an unparsable non-numeric value would raise `ValueError` at CLI-parse time, not fail gracefully), and `ANTHROPIC_API_KEY` in `scaffold.py:62` (checked only for its presence, to warn a new user during `create_agent` scaffolding that they haven't set an API key yet — it doesn't read or validate the value itself).

## Q3: `CredentialVault.get()` does `self._overrides.get(name) or os.environ.get(name)` — what's the bug hiding in that line?
`or` short-circuits on any falsy value, not just `None`. If an override is explicitly set to an empty string `""` (a legitimate, if unusual, override — maybe a test deliberately clearing a credential), `or` treats it as absent and falls through to read the environment instead. The correct check would be `self._overrides[name] if name in self._overrides else os.environ.get(name)`. This is a real, narrow edge case: it only bites if something intentionally stores an empty-string override, which is rare, but it's the kind of one-line correctness bug worth being able to point to directly instead of claiming the module is bug-free.

## Q4: Why does `CredentialVault` exist at all instead of just calling `os.environ.get()` directly everywhere a secret is needed?
Two reasons visible in the code: it adds an in-memory `_overrides` layer so a credential can be rotated at runtime (`rotate()`) without touching the process environment or restarting anything, and it tracks `_rotated_at` timestamps so `age_s()` can answer "how stale is this credential" — a real operational question (e.g. "alert if a credential is older than 24h") that raw `os.environ.get()` has no way to answer. The docstring says explicitly this is a swappable reference implementation — `get()`/`rotate()` are the two methods a real backend (AWS Secrets Manager, Vault, GCP Secret Manager) would need to implement to be a drop-in replacement, following the same Protocol-based swap pattern used for `FeatureFlagProvider` and `VectorStore` elsewhere in the codebase.

## Q5: `CredentialVault` is a plain `dataclass` with instance dict fields (`_overrides`, `_rotated_at`) — is it thread-safe?
No, and nothing in the code claims it is. Two threads calling `rotate()` on the same vault instance concurrently can race on the two-step `self._overrides[name] = value; self._rotated_at[name] = time.time()` — a reader could observe the new override value with the old rotation timestamp, or vice versa, since Python dict writes aren't atomic across two separate statements even though each individual dict assignment is. In a single-process, single-worker CLI or short-lived script this never surfaces; it would surface the moment `CredentialVault` is shared across a multi-threaded server (e.g. `serve.py` handling concurrent requests) and rotation happens live. There's no lock here the way there is in `state_store.py`'s Postgres-backed store — this module was never hardened for that case.

## Q6: How would you actually build a real `Settings`/config layer for this project if asked to add one — what would you NOT reinvent?
Given the "no Pydantic" constraint, the right shape is a single frozen dataclass (or even a plain module-level namespace) constructed once at process startup by reading every `os.environ` value in one place, with explicit type coercion and a clear error message on a malformed value (unlike today's `PORT` parsing, which would raise a raw `ValueError` deep inside argparse). What you would NOT reinvent is validation-library machinery (custom validators, nested schema composition, `.env` file parsing with precedence rules) — that's exactly the surface area Pydantic-settings exists for, and hand-rolling a subset of it just to avoid the dependency has a real cost in edge-case correctness (see Q3) that a battle-tested library doesn't have. The honest tradeoff: the current scattered approach costs discoverability (Q2) and has zero abstraction overhead; a centralized dataclass costs a small amount of upfront ceremony and buys a single source of truth and testable defaults.

## Q7: `cli.py` defaults `--port` from `PORT` via `int(os.environ.get("PORT", 8080))` — what happens if `PORT` is set to a non-numeric string, e.g. `"abc"`?
`os.environ.get("PORT", 8080)` returns the string `"abc"` (the default `8080` is only used if the key is absent entirely — note it's an `int` literal there, only coerced to `int` again harmlessly), and `int("abc")` raises `ValueError` at argument-parser construction time, before `main()` even runs, with Python's raw traceback rather than a friendly CLI error message. This is a real, findable UX rough edge: a misconfigured `PORT` env var produces a stack trace instead of "PORT must be a valid integer, got 'abc'". Fixing it would mean wrapping the `int()` call in a try/except at CLI-build time.

## Q8: How does feature-flag configuration (`feature_flags.py`) relate to this "no config module" story — isn't that also configuration?
Yes, and it's the one piece of configuration infrastructure that *is* deliberately architected rather than ad hoc: `FeatureFlagProvider` is a `Protocol`, `StaticFeatureFlagProvider` is the zero-dependency in-memory reference implementation, and swapping in LaunchDarkly/Unleash later means implementing `is_enabled()` and nothing else changes. The distinction that matters: feature flags are *behavioral* configuration (should this code path run for this identity) that needs runtime mutability and per-identity targeting, so it earned a real abstraction; environment variables in this codebase are all *static, process-lifetime* configuration (an API key, a port, a workspace ID) that's read once and never changes, so they didn't get one. That's a defensible line to draw, but it does mean the project has an abstraction for the config concern that's least urgent (feature toggles are inherently already dynamic and rare to need at cold-start) and ad hoc code for the concern every deployment hits on day one (env vars).

## Q9: If two different modules both needed `ANTHROPIC_API_KEY` today, would they get the same value the same way?
No — and this is worth knowing cold. `scaffold.py:62` reads it directly via `os.environ.get("ANTHROPIC_API_KEY")` purely to check truthiness for a warning message. If `llm_gateway.py` also needs an Anthropic key (it takes `ANTHROPIC_WORKSPACE_ID` from the environment but the API key itself is passed to the underlying Anthropic SDK client, which does its own `ANTHROPIC_API_KEY` env lookup internally per the SDK's own conventions), and if something used `CredentialVault.get("ANTHROPIC_API_KEY")` as a third path, you'd have three independent code paths that could each see a *different* effective value if `CredentialVault._overrides` had a rotated override in memory that the other two paths never see (since they read the environment directly, not through the vault). That's the real cost of "no central config": there is no single source of truth guaranteeing every consumer of the same logical setting sees the same value.

## Q10: What's the testing story for configuration — how would you unit test `PORT` handling or `CredentialVault` overrides without mutating the real process environment?
For `CredentialVault`, it's already testable in isolation without touching `os.environ` at all: construct one directly with `_overrides={"KEY": "test-value"}` and call `.get("KEY")` — the override path never touches the real environment, which is a genuine design win of having the override dict as a first-class field rather than monkeypatching `os.environ` in tests. For the `PORT` case in `cli.py`, since the env var is read at argument-parser *construction* time (module import / function call, not at parse time per invocation), a test has to set `os.environ["PORT"]` (or use `monkeypatch.setenv`) *before* building the parser, which is a subtler ordering requirement than it looks — building the parser once and reusing it across tests with different `PORT` values won't work, because the default was already baked in at construction.

## Q11: Compare this to how a Temporal- or LangGraph-backed deployment typically handles configuration — is Agent Foundry missing anything those ecosystems assume you have?
Temporal workflows and workers typically lean on their own client configuration (namespace, task queue, TLS certs) resolved through the Temporal SDK's client options, and LangGraph deployments (e.g. LangGraph Platform) expect a `langgraph.json` plus environment-driven secrets for the underlying LLM provider — both ecosystems push you toward *some* declarative, file- or client-object-based configuration surface. Agent Foundry's Runtime axis (LangGraph/Native/Temporal) means that if you actually deploy on the Temporal or LangGraph runtime, you inherit *their* configuration surfaces for the orchestration plane, while Agent Foundry's own four env vars remain the configuration for the "framework-level" plane (credentials, feature flags, serve port). Nothing here is broken, but it does mean a real deployment has two configuration stories to reason about simultaneously — the runtime's and Agent Foundry's — and nothing in this codebase unifies them.

## Q12: What's a limitation of the current configuration approach you'd fix given more time, and how would you sequence the fix?
First, centralize the four `os.environ` reads into one `AppConfig` frozen dataclass built once at startup (closing Q2's discoverability gap and Q7's bad-error-message gap) without pulling in Pydantic — a ~30-line hand-rolled dataclass with a `from_env()` classmethod is enough. Second, fix the `or` vs. explicit-`in`-check bug in `CredentialVault.get()` (Q3) since it's a one-line, zero-risk fix. Third, only *after* those two, consider whether `CredentialVault` needs a lock (Q5) — that's lower priority because it only matters once the vault is actually shared across concurrent request handlers in `serve.py`, which may not be how it's deployed today. Sequencing this way fixes the cheap, unambiguous bugs before spending effort on a concurrency concern that might not be load-bearing yet.

## Q13: Is there any validation at all on configuration values, or is everything trusted as-is once read?
Effectively none beyond what `int()` gives you for free on `PORT` (which fails loudly, per Q7, rather than validating gracefully). `CredentialVault.get()` validates only presence (`KeyError` if missing), not shape — a credential could be an empty string, a value with leading/trailing whitespace, or the wrong secret entirely, and the vault has no opinion. `ANTHROPIC_WORKSPACE_ID` and `ANTHROPIC_API_KEY` are passed through as opaque strings with no format check. This is consistent with the project's general pattern of trusting internal/operator-supplied configuration rather than validating it defensively — configuration values aren't user input crossing a trust boundary the way an LLM's tool-call arguments are, so the absence of validation here is a reasonable, if implicit, boundary decision rather than an oversight on the same order as, say, missing input sanitization in `guardrails.py`.

## Q14: If someone wanted to add a fifth environment variable tomorrow — say `AGENT_FOUNDRY_LOG_LEVEL` — where would they put it, and what would that decision reveal about the codebase's current state?
They'd almost certainly put it wherever it's first needed (probably `observability.py`, reading `os.environ.get("AGENT_FOUNDRY_LOG_LEVEL", "INFO")` inline), following the exact pattern of the four existing reads — because that's the only pattern the codebase currently demonstrates. That's the tell: the absence of a config module isn't just a missing convenience, it's actively self-reinforcing, since every new contributor's fastest path is to copy the local-read pattern rather than introduce a new abstraction unprompted. This is a good concrete example of technical-debt inertia to be able to name explicitly in an interview: the fix gets more valuable (and slightly more annoying to retrofit) with every new env var added the old way.

## Q15: How does this module's honesty about not having "real" configuration infrastructure fit into the project's broader positioning as a portfolio/USP piece?
It's a stronger interview answer to say "we deliberately kept configuration as four narrow, obvious `os.environ` reads because nothing in this project's scope needed more, and here's exactly what I'd build first if it did (Q12)" than to either pretend a config module exists or over-engineer one prematurely to look complete. The project's own architecture already draws a similar line elsewhere — `FeatureFlagProvider` got a real Protocol-based abstraction because behavioral toggles are a recurring, load-bearing need, while static process config didn't, because until now it's genuinely been four values. Being able to articulate *why* something wasn't built, with the specific tradeoff and the specific next step, demonstrates more engineering judgment than a config module that was added just to check a box.
