# agent_foundry/contracts.py — Q&A

The zero-behavior "Phase 0" data-contract module — plain `@dataclass`/`Enum`/`Protocol`/`TypedDict` definitions (`Identity`, `AutonomyLevel`, `Policy`, `ToolSpec`, `ToolResult`, `Message`, `ToolCall`, `LLMResponse`, `Provider`/`Model`, `GuardrailResult`, `EvalRecord`) that every other governance module (`guardrails.py`, `security.py`, `policy_engine.py`, `sandbox.py`) imports and builds on — deliberately no Pydantic, no runtime validation, no business logic.

## Q1: `contracts.py` uses plain `@dataclass`/`TypedDict`, not Pydantic. What security/correctness properties does that choice explicitly give up, and where does the rest of the governance layer compensate (or fail to)?

Plain dataclasses give you attribute typing for IDE/static-analysis purposes and `__init__`/`__repr__`/`__eq__` boilerplate for free, but **zero runtime validation** — nothing stops `Identity(id=123, tenant_id=None, roles="admin")` from being constructed with an int `id`, a `None` `tenant_id`, and a bare string instead of a tuple for `roles` (which would then silently iterate character-by-character anywhere code does `"admin" in identity.roles` style checks, since `"a" in "admin"` is `True` — a real, exploitable type-confusion bug if `roles` is ever a raw string instead of a `tuple[str, ...]`). Pydantic would reject malformed construction at the boundary with a clear validation error; here, a malformed `Identity`/`Policy`/`ToolSpec` simply gets constructed successfully and the invalid state propagates downstream into `PolicyDecisionPoint.decide`'s `scopes & set(identity.roles)` (`policy_engine.py`) or `GuardrailEngine.check_action`'s `tool_name in self.policy.requires_approval` (`guardrails.py`) with no earlier failure point. The rest of the governance layer does NOT compensate for this — none of `guardrails.py`, `security.py`, or `policy_engine.py` re-validates the shape of an `Identity`/`Policy`/`ToolSpec` before using it; they all trust that whatever constructed these dataclasses got the types right. This is an explicit, stated architectural choice for this codebase (per the user's own memory of the project: "no Pydantic" is a deliberate constraint), not an oversight — but it does mean type correctness for these safety-critical contracts is enforced only at author-review-time and via static type checkers, never at runtime.

## Q2: `Identity` (line 16) is `@dataclass(frozen=True)` while `Policy` (line 45), `ToolSpec` (line 57), and `GuardrailResult` (line 154) are plain mutable `@dataclass`. Why the asymmetry, and what's the concrete risk of `Policy`/`ToolSpec` being mutable given they're safety-critical config?

`Identity` being frozen makes sense semantically: "who is making this call" should be immutable for the duration of a request — allowing `identity.roles = (...)` to be reassigned mid-flight would be a serious integrity problem if, say, a privilege-escalation bug let code mutate an `Identity` object's roles after an authorization decision was already made based on the pre-mutation value, and freezing forecloses that entire bug class by raising `FrozenInstanceError` on any attempted mutation. `Policy` and `ToolSpec` are NOT frozen, which means nothing stops code anywhere in the call chain from doing `policy.allowed_tools = frozenset()` or `spec.destructive = False` after the object was constructed and even after a `PolicyDecisionPoint.decide` call already inspected it — there's no dataclass-level protection against a `Policy` object being mutated between the moment `GuardrailEngine.check_action` reads `self.policy.max_cost_usd_per_thread` and any other code path that might also hold a reference to the same object. In a single-threaded, single-request-at-a-time flow this risk is mostly theoretical (nothing in the codebase's normal flow appears to mutate `Policy`/`ToolSpec` after construction), but it's a real gap if a `Policy` object is ever shared and concurrently accessed across multiple in-flight requests (e.g., one `Policy` instance reused across many `AgentConfig` invocations) — an accidental or malicious in-place mutation from one code path would be invisible to and silently affect every other holder of that same reference, with dataclasses offering no immutability guarantee to prevent it the way `Identity`'s `frozen=True` does.

## Q3: `AutonomyLevel` (line 23) is an `IntEnum` with six levels, L0 through L5, and its own docstring says "L5_FULL_AUTONOMY = 5 # same ceiling as L4 — the distinction is operational trust, not code" (line 31). What does that comment actually mean for someone auditing whether L5 grants any additional capability over L4, and is that a red flag or a reasonable design choice?

It means that from the code's perspective — every comparison against `AutonomyLevel` in `guardrails.py`'s `GuardrailEngine.check_action` (`autonomy <= AutonomyLevel.L1_RECOMMEND`, `autonomy == AutonomyLevel.L2_DRAFT`, `autonomy < AutonomyLevel.L4_POLICY_BOUND`) and in `policy_engine.py` — L4 and L5 are **completely indistinguishable**: nothing in the codebase branches on `autonomy == AutonomyLevel.L5_FULL_AUTONOMY` specifically, and `IntEnum` comparisons (`<`, `<=`, `==`) treat `4` and `5` as just two different integers that happen to both fail every "`< L4_POLICY_BOUND`" check identically. An auditor reading only the enum names might reasonably assume "full autonomy" implies some additional relaxation beyond "policy-bound" — the comment is honest that this is not the case in code; the distinction is purely an organizational/labeling convention an operator might use to mean "this identity/deployment has been reviewed and is operationally trusted to run at L4 semantics without a human watching," not a technical capability difference `check_action` enforces. This is a reasonable design choice as long as everyone consuming `AutonomyLevel` reads this comment and understands L5 is not "more permissive than L4" in any enforced sense — but it's a real audit trap: someone extending the codebase later could easily assume `L5_FULL_AUTONOMY` unlocks something L4 doesn't, write code accordingly, and introduce an actual capability gap where none was intended, precisely because the enum *looks* like it encodes six distinct capability tiers when it only encodes five.

## Q4: `ToolSpec.permissions` (line 87) is described as "Informational metadata for a caller's OWN RBAC check before registering this tool into `Policy.allowed_tools` — not enforced by `ToolRegistry.invoke()` itself." Contrast this with `ToolSpec.scopes` (line 67), which per `policy_engine.py`'s `PolicyDecisionPoint.decide` IS enforced at call time. Why do two conceptually similar "what can access this tool" fields exist with completely different enforcement guarantees, and what's the risk of confusing them?

`scopes` is actively checked on every single tool invocation — `PolicyDecisionPoint.decide` (`policy_engine.py`, line 63) computes `scopes & set(identity.roles)` and denies the call if the intersection is empty, so it's a real, load-bearing runtime authorization control. `permissions` is explicitly documented as NOT consulted by `ToolRegistry.invoke()` at all — it exists purely so that whatever code registers a tool (`core.tool_decorator.tool()`'s `permissions=` kwarg, or `agent_spec.build_agent()`'s structured tool entries, per the comment) has a place to record "this tool needs permission X" as metadata *before* deciding whether to add that tool's name into `Policy.allowed_tools` in the first place — a design-time/registration-time signal, not a runtime gate. The risk is exactly what a sharp reviewer should flag: a team could reasonably assume that setting `ToolSpec(permissions=frozenset({"admin"}))` on a tool actually restricts who can call it, the same way `scopes` does — and be wrong. If a tool with `permissions={"admin"}` but empty `scopes` ends up in `Policy.allowed_tools` for a non-admin identity (because whoever wired up the registration didn't separately honor the `permissions` metadata), `PolicyDecisionPoint.decide`'s scope check (line 63, `if scopes and not (...)`) is a no-op — empty `scopes` skips the check entirely — and the tool is fully callable regardless of the `permissions` field's contents. Two fields with the same intuitive purpose ("who's allowed to use this") but only one of them enforced is a genuine footgun for anyone who doesn't read both docstrings carefully.

## Q5: `ToolSpec.egress_hosts` (line 75-81) is documented as coming from "the tool's OWN declared destinations, known at registration time... not derived from `args`, which vary per call and have no generically reliable 'this is the host' field." What class of tool does this design fundamentally not protect, and why can't `contracts.py` fix that on its own?

Any tool whose actual network destination is determined dynamically by its own call arguments — a generic `http_tool` or `fetch_url` tool that takes a URL as one of its `parameters` — cannot have a meaningful, complete `egress_hosts` set at registration time, because the whole point of such a tool is that its destination varies per call, which is exactly the case `contracts.py`'s own comment says has "no generically reliable 'this is the host' field." `contracts.py` can't fix this by itself because it only defines the *data shape* (`egress_hosts: frozenset[str]`) — the actual decision of what to check it against happens in `policy_engine.py`'s `PolicyDecisionPoint.decide`, which (per this repo's `policy_engine.py` Q&A) only ever validates the tool's *declared* `egress_hosts` against `EgressPolicy`, never the tool's *actual runtime* destination for a given call. Fixing this properly would require either (a) the tool's own implementation independently re-validating its resolved destination against the same `EgressPolicy` before making the outbound call (duplicating enforcement logic outside the declarative `ToolSpec`/PDP layer), or (b) extending the whole call chain (`ToolSpec`, `decide()`, `EgressPolicy`) to accept a per-call, args-derived host rather than only a registration-time set — neither of which is something a passive dataclass field can express on its own; it needs cooperation from the code that actually calls the tool's `fn`.

## Q6: `Message` (line 101) is a `TypedDict` with the comment "a `TypedDict` is erased at runtime, so this changes no behavior... this type is never used for runtime validation anyway." What's the actual value this type provides if it enforces nothing at runtime, and is there a security cost to that?

The value is purely for static analysis and documentation — a type checker (mypy/pyright) can catch, at development time, code that constructs a `Message`-shaped dict with a typo'd key or wrong value type, and it gives a reader a single canonical reference for "what does a message dict actually look like across this codebase" without needing to grep every literal `{"role": ..., "content": ...}` construction site. There's no security cost specific to `Message` beyond what's already true of the rest of this module (Q1) — since `TypedDict` was never going to provide runtime validation even if the codebase wanted it to (that's a fundamental limitation of `TypedDict` in Python's type system, not a choice this file made), using it here doesn't create a false sense of runtime safety the way, say, a Pydantic model masquerading as "validated" without actually being validated at the right layer might. The comment is refreshingly honest that this is documentation-as-code, not a safety mechanism — which matters for a security reviewer: don't assume any message flowing through `AgentState.messages` has actually been shape-checked just because `Message` exists as a type; a malformed or attacker-influenced dict (e.g., one with an unexpected `content` type coming from a tool result) will flow through untouched by this type.

## Q7: `GuardrailResult.escalate` (line 158) defaults to `False` and is documented as "hand off to a human/other agent (escalation.py) instead of a flat deny." Per the actual `guardrails.py` code, is this field ever set to `True` by either shipped `GuardrailChecks` implementation, and what does that mean for `escalation.py`'s reachability from this layer?

No — neither `GuardrailEngine` nor `LLMGuardrails` in `guardrails.py` ever constructs a `GuardrailResult` with `escalate=True`; every guardrail failure from either implementation is an unconditional deny (`GuardrailResult(False, "...", "...")` with `escalate` left at its dataclass default of `False`). That means `escalation.py`'s "hand off to a human/other agent" pathway — whatever mechanism it implements — is entirely unreachable through the two reference guardrail implementations shipped in this codebase; the field exists as a documented extension point in the shared contract, but nothing currently populates it. This is worth being explicit about for anyone reading `escalation.py` expecting it to already be wired into the guardrail flow by default: it isn't, unless a custom `GuardrailChecks` implementation (or a modification to `LLMGuardrails`, e.g., treating an ambiguous LLM-judge response as `escalate=True` rather than collapsing it to an implicit allow) is written to actually set this flag. `contracts.py`'s job here was to define the *shape* of that extension point correctly (a boolean flag alongside `allowed`/`reason`/`stage`) — whether anything in the rest of the codebase actually uses it is a separate, currently-unmet, question.

## Q8: `Provider` (line 139) and `Model = Provider` (line 148) are the same `Protocol` under two names. Why maintain a literal alias rather than picking one canonical name, and what's the risk of two names for the same type long-term?

The comment explains the rationale directly: `Provider` is the name used throughout `llm_gateway.py`'s implementations (`AnthropicProvider`, `OpenAIProvider`, `MultiProvider`) and existing tests, so renaming everything to `Model` would be "pure churn" with no functional benefit — but `Model` is offered as "the public-facing alias... under the name a reader reaches for first," acknowledging that someone unfamiliar with this codebase's internal naming conventions is more likely to search for or expect "Model" as the name of an LLM-provider abstraction. The long-term risk of a `TypeAlias`-via-assignment like this is drift: if `Provider`'s definition changes (a new method added to the Protocol, a signature change to `complete`), `Model` picks up the change automatically since it's a literal reference to the same object, not a separate redefinition — so there's no risk of the two silently diverging in *shape*. The risk is more about developer experience and documentation debt: two names for the same concept means anyone writing new code, tests, or documentation has to make an arbitrary choice each time about which name to use, and a codebase that inconsistently uses both (some files importing `Provider`, others importing `Model`) is marginally harder to grep and reason about than one with a single canonical name — a cost the comment explicitly judges as worth paying to avoid a bigger churn cost.

## Q9: `Policy.max_cost_usd_per_thread` defaults to `1.0` and `Policy.max_steps_per_thread` defaults to `25` (line 48-49). What's the security reasoning behind these specific conservative defaults, and where in the governance layer are they actually enforced (versus merely declared here)?

`contracts.py` only *declares* these fields with conservative defaults — a tight, deliberately small default budget ($1, 25 steps) means a `Policy()` constructed with zero explicit configuration fails safe: a misconfigured or newly-registered agent can't accidentally rack up large costs or run away in an unbounded loop before hitting a ceiling, which is a sound "secure by default" posture for a field an integrator might easily forget to set explicitly. But `contracts.py` itself contains zero enforcement logic — `max_cost_usd_per_thread` is only actually checked in `guardrails.py`'s `GuardrailEngine.check_action` (`if cost_so_far >= self.policy.max_cost_usd_per_thread: return GuardrailResult(False, "thread cost budget exceeded", "action")`), and `max_steps_per_thread` is presumably enforced somewhere in `orchestration.py`'s step-counting logic (not part of this file). This is the expected and correct separation of concerns for a pure-data-contract module — but it does mean the "conservative default" security property this field provides is only as good as every caller that actually reads and enforces it; a hypothetical alternative `GuardrailChecks` implementation that ignores `Policy.max_cost_usd_per_thread` entirely would silently defeat the budget ceiling `contracts.py`'s default was designed to guarantee, and nothing in `contracts.py` (or anywhere else) forces a `GuardrailChecks` implementation to actually honor every field on `Policy`.

## Q10: `ToolSpec.cacheable` (line 69) says "only consulted by `ToolRegistry.invoke()` when NOT destructive — see tools_gateway.py." Why is it correct to only ever consider caching for non-destructive tools, and what's a subtle bug that would result from caching a `destructive=True` tool's result?

Caching means returning a previously-computed result instead of re-executing the tool's `fn` for what looks like an equivalent call — for an idempotent, side-effect-free tool (looking something up, reading a file, computing a value from pure inputs) this is a pure performance win with no behavioral difference the caller could observe. For a `destructive=True` tool (one that mutates external state — deletes a record, sends an email, charges a payment), caching would be actively wrong even if two calls have textually identical arguments: the caller's *intent* in issuing the call again is almost certainly "actually do this again" (or, if it's a retry after a failure, "confirm this took effect," which a cached hit would falsely report as success without the side effect having recurred) — returning a stale cached result instead of re-executing would silently violate the causal link between "the agent decided to take this destructive action" and "the destructive action actually happened," which is exactly the kind of gap that could let an agent believe an action succeeded (or occurred a second time) when it didn't. `contracts.py`'s role here again is just to declare the flag; the actual "don't consult cache for destructive tools" logic lives in `tools_gateway.py`'s `ToolRegistry.invoke()`, per the field's own docstring pointer — a correct design, but one where `ToolSpec.cacheable`'s safety property is entirely dependent on that other module continuing to honor the "only when NOT destructive" rule this comment documents but doesn't enforce from within `contracts.py` itself.

## Q11: `Policy.requires_approval` (line 50, a `frozenset[str]` of tool names) and `ToolSpec.requires_confirmation` (line 68, a per-tool `bool`) are two independent "this needs a human in the loop" mechanisms. Per `policy_engine.py`'s `PolicyDecisionPoint.decide`, do they compose safely, or can one accidentally mask the other?

They're checked at two different points in `decide()`'s sequence and via two different code paths, but they compose additively rather than redundantly, which is actually the safer of the two possible designs: `GuardrailEngine.check_action` (called at line 71 of `policy_engine.py`) checks `tool_name in self.policy.requires_approval` — a *policy-level, per-deployment* list of tool names that always need approval regardless of the tool's own opinion — while `decide()`'s own `if requires_confirmation:` check (line 78) reads `ToolSpec.requires_confirmation` directly, letting an individual tool *author* demand confirmation "on its own terms, not only via the policy" (per the comment at line 74-77). Since both checks are independent `if` blocks that each return an early deny, a tool needing approval via EITHER mechanism gets gated — neither can accidentally suppress the other, because there's no `elif` or short-circuit between them that would let one "win" over the other. The real risk isn't logical masking, it's operational confusion for whoever is configuring a deployment: two different people (the tool author setting `requires_confirmation=True` at registration time, and a policy administrator populating `Policy.requires_approval` at deployment-config time) can each reasonably believe they are the one true source of truth for "does this tool need a human," without either realizing the other mechanism exists — leading to duplicate approval prompts, or to a false sense that removing a tool from `Policy.requires_approval` fully un-gates it when `ToolSpec.requires_confirmation=True` on the tool itself still forces the same result.

## Q12: `ToolResult` (line 91) has independent `ok: bool`, `output: Any = None`, and `error: str | None = None` fields with no validation tying them together. What invalid states does this allow, and what's the risk if downstream code (e.g., an `AuditSink`, a KPI evaluator) assumes `ok`/`error`/`output` are always mutually consistent?

Nothing in the dataclass definition prevents constructing `ToolResult(tool="x", ok=True, output=None, error="boom")` (claims success but also carries an error message) or `ToolResult(tool="x", ok=False, output={"real": "data"}, error=None)` (claims failure but also carries what looks like valid output data) — these are self-contradictory states that a naive consumer might not defend against. `orchestration.py`'s `screen_tool_output(result.output) if result.ok else result.error` pattern (referenced in `guardrails.py`'s own docs) shows the expected convention — branch on `ok`, trust `output` when true and `error` when false — but that convention lives in the *calling* code, not enforced by `ToolResult` itself; a tool implementation or a buggy adapter that populates both `output` and `error` regardless of `ok`, or sets `ok=True` with a stale/leftover `error` string from a previous attempt, would have that inconsistency silently pass through unnoticed by `contracts.py`. For a security-adjacent consumer specifically — an `AuditSink.record(...)` call logging a tool result, or a KPI evaluator scoring "did this tool call succeed" — trusting `ok` alone without also checking that `error is None`/`output is not None` accordingly means an inconsistent `ToolResult` could produce a misleading audit trail entry (e.g., logging "succeeded" for a call that actually also carried a populated error message), which matters for exactly the kind of "who did what, and did it actually work" question `security.py`'s audit layer exists to answer.

## Q13: `EvalRecord.score` (line 167) is documented as "0..1" but is typed as a plain `float` with no range validation. What happens if a KPI implementation (e.g., in `kpi.py`) returns `score=5.0` or `score=-1.0`, and why does this matter for anything gating agent behavior on eval scores?

Nothing in `contracts.py` stops it — `score: float` accepts any float, so a buggy KPI function that forgets to normalize its output (e.g., returns a raw count instead of a 0-1 ratio, or computes a ratio that can exceed 1.0 due to a division-order bug) silently produces an out-of-contract `EvalRecord` with no error anywhere in this module. This matters wherever downstream code *thresholds* on score values expecting the documented 0-1 range — a comparison like `if score > 0.8: pass` still "works" numerically for a `score=5.0` (it's still `> 0.8`), potentially making a badly-out-of-range score look like an even *more* confident pass than a legitimate 0.95 would, rather than raising a visible error that would prompt someone to notice the KPI implementation is broken. Conversely a corrupted negative score could silently fail every threshold check for reasons unrelated to the actual quality being measured. Since `EvalRecord` explicitly documents the expected range in its own comment rather than encoding it as an enforced invariant (e.g., via a `__post_init__` assertion or a bounded type), this is the same category of gap as `data_classification`'s undocumented-value problem (Q11) — a self-documenting convention with zero enforcement, relying entirely on every KPI author getting the math right.

## Q14: `ToolCall` (line 120) carries `id: str`, `name: str`, `args: dict[str, Any]` with a comment emphasizing this represents "real, provider-native tool-calling... not a text convention parsed after the fact." Why does that distinction matter from a security standpoint, compared to an older pattern where a model's tool intent is parsed out of free-text output?

When a model's intent to call a tool is parsed out of free-text (e.g., regexing a response for something that looks like `CALL: search_web("query")`), the boundary between "content the model said" and "a structured, unambiguous instruction to invoke a specific function with specific arguments" is blurry and attacker-influenced text embedded anywhere in the model's own generated output (itself potentially shaped by an upstream prompt injection) could be crafted to look like a tool-call pattern and get misinterpreted as one, or a genuine tool call could be missed because the free-text format varied slightly. `ToolCall` representing real, provider-native structured tool-calling (Anthropic/OpenAI's actual `tool_use`/`function_call` response blocks) means the *provider's own model-serving infrastructure* is responsible for producing a well-formed `{id, name, args}` triple as a distinct, typed part of the response — not a substring of freeform text this codebase would need to parse and could parse incorrectly or be tricked into misparsing. This narrows (though doesn't eliminate) one class of injection risk: an attacker can still try to manipulate *what* tool gets called and with *what* arguments via prompt injection influencing the model's decision-making, but they have a much harder time forging a fake tool-call structure out of ordinary text content the model happens to emit, since `ToolCall` objects are constructed from the provider API's own structured response fields, not derived by this codebase re-interpreting freeform text.

## Q15: `ToolSpec.data_classification` (line 73) is a plain `str` field with a documented set of allowed values ("public | internal | confidential | restricted") but no `Literal` type or enum enforcing it. What happens if a caller sets `data_classification="Confidential"` (capitalized) or `"secret"` (a value not in the documented set)?

Nothing prevents either — `data_classification: str = "internal"` accepts any string, and `policy_engine.py`'s `_RESTRICTED_CLASSIFICATIONS = ("confidential", "restricted")` (lowercase, exact-match tuple) is the only place this value is actually interpreted. `"Confidential"` (capital C) would NOT match either string in `_RESTRICTED_CLASSIFICATIONS` via `if data_classification in _RESTRICTED_CLASSIFICATIONS` — meaning a tool intended to be locked down as confidential, but registered with a capitalization typo, silently falls through as if it were unrestricted ("internal"-equivalent) with no error, no warning, and no test that would catch a typo unless someone specifically wrote one. `"secret"` (a plausible but undocumented value someone might reach for) behaves identically — never matches, never restricts, silently permissive. This is the same class of problem as `AutonomyLevel`'s int-comparison foot-guns, but worse, because `AutonomyLevel` is at least a real `IntEnum` that a type checker and `Enum`'s own value-validation would catch a bad value for — `data_classification` being a bare `str` means a typo is not just possible but completely invisible until (or unless) someone notices in a security review that a tool they believed was locked down as "confidential" actually isn't, because policy_engine.py's exact-match check silently treated a typo'd classification as unrestricted. Using a real `Enum`/`Literal["public", "internal", "confidential", "restricted"]` here would have caught this class of mistake at construction/type-check time rather than leaving it as a silent runtime gap.
