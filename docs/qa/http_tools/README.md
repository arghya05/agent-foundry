# agent_foundry/http_tools.py — Q&A

The "3rd-party API adapters" chip under the Tools Gateway: `http_tool()` wraps any REST endpoint as a `ToolSpec` using only stdlib `urllib`, with `{placeholder}`-templated URLs, automatic query-param/JSON-body handling, and a registration-time `egress_hosts` derivation for the PDP's egress policy.

## Q1: Why does this module use bare `urllib` instead of `requests` or `httpx`, given the rest of the codebase uses richer HTTP clients elsewhere (e.g. `a2a_bridge.py`'s httpx dependency)?

The docstring states it directly (lines 1-4): this is meant to work for "literally any HTTP API" with "zero extra dependency." Every other bridge in this interop layer (`a2a_bridge.py`, `mcp_tools.py`, `crewai_bridge.py`, `autogen_bridge.py`) requires installing a specific third-party SDK because it's talking to a specific *protocol or framework* (A2A, MCP, CrewAI, AutoGen) that mandates a client library. Generic REST APIs don't have that constraint — any HTTP client can talk to them — so requiring `requests`/`httpx` here would add a mandatory dependency for a capability the Python standard library already fully covers (`urllib.request`, `urllib.parse`, `json`). This keeps `http_tool()` usable in the base install with no extra `pip install`, at the cost of `urllib`'s comparatively clunkier API (manual `Request` object construction, no built-in retry/session/connection-pooling ergonomics that `requests`/`httpx` provide out of the box).

## Q2: Walk through exactly what `call(**kwargs)` does for a `GET` request versus everything else. What determines whether a kwarg becomes part of the URL, a query param, or a JSON body?

Line 30: `resolved_url = url.format(**kwargs)` first substitutes every `{placeholder}` in the URL template using Python's `str.format()` — any kwarg whose name appears as `{name}` in the template is consumed here. Line 31: `remaining = {k: v for k, v in kwargs.items() if "{" + k + "}" not in url}` recomputes which kwargs are "leftover" by checking membership of the literal substring `"{k}"` in the *original* (unformatted) `url` template — not by tracking which keys `.format()` actually used. For `method.upper() == "GET"` (lines 34-36), if there are any `remaining` kwargs, they're appended as a URL-encoded query string via `urllib.parse.urlencode(remaining)`. For any other method (lines 37-39), `remaining` is JSON-serialized into the request body (`json.dumps(remaining).encode()`), and `Content-Type: application/json` is set via `req_headers.setdefault(...)` (only if not already present in `headers`, so a caller can override it). So the split is entirely determined by whether a given argument name textually appears as a `{placeholder}` in the URL template string — there's no separate declaration of "these kwargs are path params, these are query/body params" anywhere in `http_tool()`'s signature; it's inferred purely from string matching against the template.

## Q3: The `remaining` computation (line 31) re-derives "which kwargs were path params" by checking `"{" + k + "}" not in url` against the *original* template, rather than reusing whatever `.format()` actually consumed. Is that redundant, or does it matter?

It's not fully redundant — it's actually a second, independent check that happens to usually agree with what `.format()` did, but it's *not the same operation*, and this parallel-derivation approach is a mild code smell: two different pieces of logic (`str.format()`'s internal placeholder-matching and this method's own substring check) both have to agree for the function to behave correctly, and if `url.format(**kwargs)` ever raised (e.g. a placeholder in the template with no matching kwarg supplied), line 30 already failed before line 31's `remaining` computation is even reached — so in practice the two checks can't disagree in a way that produces wrong behavior on the *happy path*, but relying on textual substring matching rather than introspecting `string.Formatter().parse(url)` for the actual field names is fragile: if the URL template ever used more elaborate `str.format()` syntax (e.g. `{order_id!r}` or `{order_id:>10}` with conversion/format specs), the substring check `"{" + k + "}" not in url` would fail to match (since the template literally contains `{order_id:>10}`, not `{order_id}`), causing `order_id` to be incorrectly treated as a "remaining" kwarg and duplicated into the query string or body even though it was already consumed by `.format()`.

## Q4: Trace the SSRF-relevant reasoning behind `egress_hosts` (lines 48-54). Under what circumstance does the derived `egress_hosts` NOT actually match the host the request goes to?

The comment (lines 48-52) explains the design: `url`'s host is known "at REGISTRATION time" because it's a fixed template — only *path* placeholders vary per call, "never the host itself" — so `urllib.parse.urlparse(url).hostname` (line 52), computed once against the *unformatted* template, is trusted as the tool's declared `egress_hosts` for `policy_engine.PolicyDecisionPoint`'s egress check to enforce on every call. This reasoning holds **only if the placeholder actually never appears in the host/netloc portion of the URL**. If a builder wrote a template like `url="https://{tenant}.api.example.com/orders"` — a placeholder inside the hostname itself, which the docstring doesn't explicitly forbid — then `urlparse(url).hostname` at registration time would parse the *literal, unresolved* string `"{tenant}.api.example.com"` as the hostname (a syntactically odd but not necessarily rejected value depending on `urlparse`'s leniency), which would never match the *actual* resolved host once `{tenant}` is substituted with a real value per call (e.g. `"acme.api.example.com"`). This is a real gap: the PDP's egress allowlist would be checking a hostname that never actually appears in any real outgoing request, meaning the egress check for that tool is either always-failing (if it does exact string comparison, blocking every legitimate call) or effectively non-functional as an SSRF guard (if the PDP's check is more lenient) — either way, the "host known at registration time" assumption this whole design rests on is silently violated by a template shape the code doesn't prevent a caller from writing.

## Q5: Beyond the hostname-in-placeholder edge case, what other SSRF-adjacent risks exist in `http_tool()` that `egress_hosts` doesn't cover?

Several. First, `urllib.request.urlopen()` follows HTTP redirects by default with no configuration here to disable or restrict that — a well-behaved target host (matching `egress_hosts`) could respond with a `3xx` redirect to an entirely different host (including an internal/private address like `169.254.169.254` for cloud metadata endpoints, or `localhost`), and `urlopen()` would transparently follow it, making the *actual* final request go somewhere `egress_hosts` never authorized and the PDP never saw, since the PDP's check (wherever it runs, presumably before the call) only ever sees the tool's *declared* `egress_hosts`, not the redirect target. Second, path-placeholder values are inserted via `.format()` with zero encoding or validation (line 30) — an attacker-influenced `order_id` value containing `../` sequences, or characters that change how the resolved URL is parsed by the *target* server, could achieve path traversal or request smuggling against that server, none of which `egress_hosts` (a host-only allowlist) is designed to catch since the host itself doesn't change. Third, there's no timeout floor/ceiling enforcement or response-size limit — `resp.read()` (line 42) reads the entire response body into memory unconditionally, so a malicious or misbehaving endpoint returning an enormous body could exhaust memory; `timeout_s` bounds connection/read time but not payload size.

## Q6: What happens if the remote endpoint returns a malformed or unexpected response — e.g. a non-JSON body when JSON was expected, or a 4xx/5xx status code? Walk through the exact code path.

For a JSON-parse failure: line 43-46 wraps `json.loads(body)` in `try/except json.JSONDecodeError`, falling back to returning the raw decoded text (`body`) — so a non-JSON response never crashes `call()`; it just changes the *type* of the returned value (`dict`/`list` vs `str`) with no signal to the caller distinguishing "this endpoint genuinely returns plain text" from "this endpoint was supposed to return JSON but sent something broken instead" — both look identical from the tool's return value. For an HTTP error status: `urllib.request.urlopen()` itself raises `urllib.error.HTTPError` (a subclass of `OSError`) for any 4xx/5xx response — this isn't caught anywhere in `call()`, so it propagates straight out of the tool function. Since `http_tool()`'s returned `ToolSpec` is invoked the same way as any other tool, through `ToolRegistry.invoke()`/`ainvoke()`, that `HTTPError` is caught by the registry's own `try/except Exception` (`tools_gateway.py`), retried up to `spec.max_retries` (unset here, defaulting to `0`), and surfaced as `ToolResult(ok=False, error=str(e))`. Note `str(HTTPError)` typically includes the status code and reason phrase but not necessarily the response body — so error detail from the API (e.g. a JSON error payload explaining *why* the request failed) is likely lost entirely, since `HTTPError`'s body isn't read anywhere in this code path.

## Q7: What's a limitation of this module you'd fix given more time?

The redirect-following SSRF gap (Q5) is the most serious — disabling automatic redirect handling (or validating the redirect target's host against `egress_hosts` before following it) would close a real bypass of the PDP's egress allowlist that currently exists silently. Second: capturing and surfacing the response body on an `HTTPError` (many REST APIs put the actually-useful error detail in a JSON body on a 4xx, which is currently discarded) would make tool failures far more actionable for both the calling LLM and human debugging. Third: validating at `http_tool()` *registration* time that no `{placeholder}` appears inside the URL's netloc/host component (Q4) — a simple check against `urlparse(url).netloc` for `{`/`}` characters — would catch the "egress_hosts silently doesn't match the real host" class of bug before it ever reaches a live call.

## Q8: What happens if a caller supplies a kwarg whose name is NOT a placeholder in the URL and NOT expected by the target API — e.g. an extra, unvalidated key an LLM hallucinated as a tool argument?

`http_tool()` registers `ToolSpec(..., parameters={}, ...)` (line 53) — an *empty* parameters schema. This is a notable detail: `tools_gateway.tool_json_schema()` would convert an empty `{}` params dict into `{"type": "object", "properties": {}, "required": []}`, meaning the JSON Schema exposed to the calling LLM declares *no* expected parameters at all, and `tools_gateway._validate_args()`'s fallback validator (`_validate_basic`) would, for an object schema with empty `properties`/`required`, accept literally any dict of kwargs without complaint (nothing in `_validate_basic` rejects *extra* keys not in `properties` — it only checks required-key presence and known-key type matching). So any kwarg an LLM decides to pass — whether it matches a `{placeholder}` in the URL, is a legitimate query/body param the target API expects, or is a complete hallucination — sails through Agent Foundry's own argument validation untouched, and only gets "validated" implicitly by whether the *target API* itself rejects the resulting request (e.g. an unexpected query param is usually silently ignored by REST APIs, while a missing required one causes a 4xx from the target, not from this framework). This means `http_tool()` provides no schema-level guidance to the LLM about what arguments it actually expects — a real usability and safety gap: a builder who wants real argument validation for a specific HTTP tool would need to pass an explicit JSON Schema as `parameters` themselves, which `http_tool()`'s signature doesn't currently support (it always sets `parameters={}` — line 53 hardcodes this, ignoring any per-tool schema a caller might want to supply).

## Q9: Why does `req_headers.setdefault("Content-Type", "application/json")` use `setdefault` rather than always overwriting? What's the practical case this matters for?

`setdefault` (line 39) only sets `Content-Type` if the caller's `headers` dict didn't already specify one — this lets a caller override the content type for APIs that expect something other than JSON in the body (e.g. `application/x-www-form-urlencoded`, `application/xml`, or a vendor-specific media type) while still getting the JSON-serialization convenience for the common case. However, there's a real mismatch risk this doesn't protect against: even if a caller overrides `Content-Type` to something non-JSON, line 38 (`data = json.dumps(remaining).encode()`) *unconditionally* JSON-serializes the body regardless of what `Content-Type` was set to — so overriding the header to `application/x-www-form-urlencoded` would send a body that's still JSON-formatted bytes, just mislabeled with a different `Content-Type` header, which would almost certainly cause the target API to reject or misparse the request. The header override mechanism exists, but the actual body-encoding logic doesn't honor it — a real, if narrow, inconsistency between what the header claims and what bytes are actually sent.

## Q10: Compare `http_tool()`'s error-handling posture to `mcp_tools.py`'s `_make_spec().call()`. Which one gives a calling LLM more actionable information when a call fails, and why?

`mcp_tools.py`'s `call()` explicitly distinguishes success from failure using MCP's own `result.is_error` flag, and when it *is* an error, raises `RuntimeError(text or f"MCP tool {tool.name!r} failed")` — using whatever text content the server provided as the exception message, so the failure reason (as explained by the remote tool itself) is preserved and becomes `ToolResult.error`. `http_tool()`, by contrast, has no equivalent for HTTP error responses: an `HTTPError` from `urlopen()` carries only the status code/reason in its `str()` representation, with the response body (where the actually useful error explanation usually lives for a REST API) never read or surfaced (Q6). So an LLM receiving a failed `ToolResult.error` from an MCP tool is much more likely to get a substantive, actionable reason ("insufficient balance for refund") than an LLM receiving a failed `http_tool()` result, which is more likely to see something generic like `"HTTP Error 400: Bad Request"` with no further detail — a real fidelity gap between the two adapters' failure-reporting quality, and one of the more actionable candidates on the "fix given more time" list.

## Q11: How would you unit test `http_tool()` without making real network calls, given it's built on raw `urllib`?

Since `call()` uses `urllib.request.urlopen()` directly rather than an injectable client object, the cleanest test seam is monkeypatching `urllib.request.urlopen` (or `http_tools.urllib.request.urlopen`, depending on import style) to return a fake response object supporting the `with ... as resp:` context-manager protocol and a `.read()` method returning known bytes — this lets tests exercise the URL-templating logic (placeholder substitution, query-string construction for GET, JSON-body construction for POST/PUT), the JSON-vs-text response fallback (line 43-46), and the `egress_hosts` derivation (line 52) entirely without touching the network. A second, complementary layer would spin up a local `http.server`-based test server (stdlib-only, matching this module's own zero-extra-dependency philosophy) to catch integration-level issues the mock can't — e.g. verifying `Content-Type` is actually set correctly on the wire, or that redirect-following behavior (Q5) does what's assumed.

## Q12: Given `http_tool()` has no retry/backoff logic of its own (relying entirely on `ToolSpec.max_retries`, which defaults to `0`), what's the practical consequence for a flaky third-party API integrated this way?

Since `http_tool()` doesn't set `max_retries` on the `ToolSpec` it returns (it's left at the `contracts.ToolSpec` default of `0`), any transient failure — a momentary DNS blip, a connection reset, a `5xx` from an overloaded upstream API — results in an immediate `ToolResult(ok=False, ...)` with zero retries unless the *caller* of `http_tool()` explicitly constructs and overrides the returned `ToolSpec`'s `max_retries` field (the function's own signature doesn't expose a `max_retries` kwarg to set this at construction time). Combined with `tools_gateway.invoke()`'s lack of backoff between retries (documented in the `tools_gateway.py` Q&A), even if a builder did bump `max_retries` up, the retries would fire back-to-back with no delay — reasonable for a truly transient blip, but a poor fit for an upstream that's rate-limiting or genuinely overloaded, where immediate retries make the problem worse rather than better.
