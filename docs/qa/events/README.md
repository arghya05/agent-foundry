# agent_foundry/events.py — Q&A

An `EventBus` protocol for pub/sub between agents/services — `InMemoryEventBus` (synchronous, zero-dependency, fully tested) and `KafkaEventBus` (matches `kafka-python`'s real producer/consumer API, unverified against a live broker in this environment) — plus `wire_event_driven()`, which subscribes any compiled graph to a topic so it runs automatically whenever a matching event is published, turning the "Event Driven" orchestration pattern into a one-line wiring call.

## Q1: This module is the "events" one, but the git history has a commit titled "Real event streaming for native multi-agent topologies (Phase 4)" that touches `core/native_orchestration.py`, not `events.py`. What problem did that Phase 4 work actually solve, and how is it a completely different mechanism from what's in this file?

Before Phase 4 (per the commit message), every native topology's `.stream()` — supervisor, swarm, blackboard, debate, fanout, dag — just wrapped `.invoke()` in a single `yield`: a caller asking for a stream got one chunk, at the very end, after the entire multi-agent topology had already finished running. Phase 4 replaced that with one shared `_drive_stream` generator per topology class (confirmed in `core/native_orchestration.py`: `SupervisorGraph`, `SwarmGraph`, `BlackboardGraph`, `DebateGraph`, `FanoutGraph`, `DagGraph` all define `_drive_stream`, with both `.invoke()` and `.stream()` delegating to it) that yields real, discrete progress events as they actually happen — `router.selected`/`specialist.completed` for supervisor, `agent.completed`/`handoff` for swarm, `agent.posted`/`agent.post_failed` per participant per round for blackboard, `debater.answered`/`judge.decided` for debate, and for fanout/dag, `item.completed`/`step.completed` emitted via `as_completed()` as each concurrent unit *actually* finishes rather than after `pool.submit`-then-block-on-all. That's about giving live visibility into a multi-agent topology's internal progress while it runs. `events.py`'s `EventBus`, by contrast, has nothing to do with observing a topology's own internal execution — it's inter-agent/inter-service pub/sub: `InMemoryEventBus.publish(topic, event)` synchronously calls every `subscribe`d handler, and `wire_event_driven()` uses it to make a *whole graph invocation* the reaction to an external event landing on a topic. The two systems solve genuinely different problems (introspecting one topology's internal steps as they happen, vs. triggering entire graph runs from external events) and don't share code — Phase 4's `_drive_stream` generators don't publish onto an `EventBus`, and `EventBus` events aren't per-node progress events.

## Q2: Why does `agent_foundry` build a custom `EventBus` protocol with an in-memory reference implementation, instead of just requiring Kafka (or Redis, or NATS) from day one?

`InMemoryEventBus` (lines 24-41) is the reference implementation specifically because it's "zero-dependency, real and fully tested" per the module docstring — a developer can wire up and test the entire Event Driven pattern (`wire_event_driven`, subscribing a compiled graph to a topic) without standing up any external infrastructure, using pure in-process Python objects. This matters for the same reason `Tracer`/`OTelTracer` exist as a pair in `observability.py`: it lets the framework demonstrate and unit-test a real architectural pattern (event-driven triggering) with a trivially inspectable implementation (`InMemoryEventBus.history()` gives you the entire publish log for free, line 40-41) before anyone needs to touch a message broker. `KafkaEventBus` (lines 44-71) is the production-shaped alternative for when events genuinely need to cross process boundaries — but the `EventBus` `Protocol` (two methods: `publish`/`subscribe`) means the choice is deferred to deployment time, not baked into `wire_event_driven()` or any other caller; anything satisfying the two-method shape is a drop-in, the same "swappable interface" posture the codebase uses everywhere else (`TracerLike`, `CostLedgerLike`, `Evaluator`).

## Q3: The module docstring explicitly flags `KafkaEventBus` as unverified — "matches kafka-python's actual producer/consumer API... but there's no Kafka broker in this environment to round-trip against... unlike MCP and OPA elsewhere in this package, which were verified against real live processes." What exactly does "matches the API" mean here versus "verified," and why does that distinction matter for someone deciding whether to trust this code in production?

"Matches the API" means the code was checked against `kafka-python`'s actual documented/introspectable interface — `KafkaProducer(bootstrap_servers=..., value_serializer=...)`, `.send(topic, value=event)`, `.flush()`, `KafkaConsumer(topic, bootstrap_servers=..., value_deserializer=...)`, iterating the consumer for messages — so the method names, constructor kwargs, and call shapes are real and correctly spelled, not invented. It does not mean anyone has actually run this against a live Kafka broker and confirmed messages round-trip correctly end-to-end: things that only surface at runtime against a real broker — serialization edge cases, consumer group behavior, offset management (there's no explicit `group_id`, `auto_offset_reset`, or offset-commit configuration here, all of which matter enormously for whether a consumer replays old messages or waits for new ones, or whether multiple consumers on the same topic compete or duplicate), partition assignment, and connection/retry/backoff behavior on broker unavailability — are all unverified. Someone deciding whether to trust this in production needs to read "matches the API" as "the code compiles and calls the right functions," not as "this has been load-tested" — the honest thing to do before shipping it is to actually stand up a broker and exercise `KafkaEventBus.publish`/`.subscribe` against it, exactly as the docstring implies.

## Q4: Walk through exactly what happens if a subscriber's handler raises an exception inside `InMemoryEventBus.publish()`.

`publish()` (lines 32-35) does `self._log.append((topic, event))` first, then iterates `self._subscribers.get(topic, [])` and calls each `handler(event)` in registration order, synchronously, with no `try`/`except` around the handler call. If any handler raises, the exception propagates straight out of `publish()` to whatever code called it — and critically, any handlers registered *after* the one that raised never get called for this event, since the `for handler in ...` loop is interrupted by the unhandled exception. This has a real consequence for `wire_event_driven()` specifically: if `graph.invoke(...)` inside `on_event` (line 83-88) raises — a tool failure, a budget exceeded, any unhandled error inside the graph run — that exception propagates all the way back up through `publish()` to whoever published the original event, potentially crashing an unrelated caller's code path that had no reason to expect a graph invocation to fail synchronously inline. There's no dead-letter queue, no per-handler isolation, and no logging of the failure anywhere in this module — a single misbehaving subscriber can take down the entire publish call for every other subscriber on that topic, which is a meaningfully different (and generally worse) failure mode than most production event bus systems, which isolate consumers from each other by design (this is, after all, "synchronous, in-process pub/sub," per the class's own docstring — that's an explicit, named tradeoff, not an oversight, but it's one worth being very clear-eyed about before using it for anything where a single bad handler shouldn't be able to take everything else down).

## Q5: How does `InMemoryEventBus` differ from `KafkaEventBus` in terms of delivery ordering and timing guarantees, and what would break if code written against one were deployed against the other without changes?

`InMemoryEventBus.publish()` is fully synchronous: every subscriber runs to completion, in registration order, on the calling thread, before `publish()` returns — a caller doing `bus.publish(...)` immediately after knows every handler has already run. `KafkaEventBus.publish()` (`_producer.send(topic, value=event); _producer.flush()`) sends and flushes to the broker, which guarantees the message is durably written to Kafka, but says nothing about *consumers* — `KafkaEventBus.subscribe()` spins up a background daemon thread (`threading.Thread(target=run, daemon=True).start()`, line 71) running its own consumer loop, so handler execution is fully asynchronous relative to `publish()` returning; a caller cannot assume a handler has run, or even that a subscriber has been created and connected to the broker yet, by the time `publish()` returns. Code that assumes synchronous handler completion — e.g. `wire_event_driven()`-triggered logic that expects the graph invocation to have already happened and its side effects to be visible immediately after `bus.publish()` — would silently be wrong under `KafkaEventBus`: the graph invocation might not even start until well after `publish()` returns, since it depends on the background consumer thread's own poll loop picking up the message from the broker. There's also an ordering subtlety: `daemon=True` means that background consumer thread is killed abruptly if the main process exits, with no guarantee any in-flight message it's currently processing (mid-`graph.invoke()`) completes — a real risk for anything that needs graceful shutdown semantics.

## Q6: `wire_event_driven()`'s default `thread_id_fn` is `lambda event: f"event-{topic}"` — one shared thread per topic. What's the practical consequence of that default, and when would you need to override it?

Every event published to a given topic, by default, gets routed to the *same* `thread_id` (`f"event-{topic}"`), which means every triggered `graph.invoke()` call for that topic shares one continuous conversation/state thread in whatever `StateStore`/checkpointer the graph uses underneath — the graph accumulates history across every event ever published to that topic, treating them as one long-running conversation rather than N independent invocations. That's the right default for something like "a single monitoring agent that reacts to a stream of alerts and needs to remember what it's already seen," but it's the wrong default for something like "run an isolated one-shot workflow per incoming webhook event," where each event should get its own fresh thread with no shared history. A caller with the latter need must pass their own `thread_id_fn` — e.g. deriving a unique thread id from a field in the event payload itself (an order id, a request id) — since nothing in `wire_event_driven()` auto-detects which pattern is appropriate; the shared-thread default is a real design choice with real state-accumulation consequences that's easy to miss if you don't read the default closely.

## Q7: What happens, concretely, when a consumer (a subscriber) disconnects or its handler thread dies mid-stream under `KafkaEventBus`? Walk through the code path.

`KafkaEventBus.subscribe()`'s `run()` function (lines 62-69) constructs a `KafkaConsumer` and does `for message in consumer: handler(message.value)` inside a `daemon=True` background thread with no `try`/`except` anywhere in the loop. If `handler` raises for any message, the exception propagates up through the `for` loop, the `run()` function exits, and the *entire background thread dies* — silently, since nothing here logs the exception or restarts the thread (`daemon=True` threads don't print unhandled exceptions to a place callers of `subscribe()` would see, beyond Python's default `threading.excepthook`, which typically just prints a traceback to stderr and moves on). No message is retried, no dead-letter mechanism exists, and — critically — every message *after* the one that killed the thread is simply never consumed again: there's no restart logic, no supervisor thread watching for a dead consumer thread and recreating it. This is a real production gap: a Kafka consumer group in most real-world designs needs a supervising loop that catches per-message exceptions (log and skip, or retry with backoff, or route to a dead-letter topic) and/or a watchdog that detects a dead consumer thread and restarts it — none of which `KafkaEventBus` implements. Given the module's own honest admission that this class is unverified against a live broker, this specific failure mode (silent, unrecoverable consumer death on the first handler exception) is exactly the kind of thing that would only surface under real production load.

## Q8: `Experiment.assign()` (in `experiments.py`) uses deterministic hash bucketing keyed on an identity. Is there anything analogous to that determinism concern in `events.py`, or is delivery here inherently non-deterministic?

There's no equivalent determinism guarantee in `events.py` at all — `InMemoryEventBus.subscribe()` appends handlers to a plain list in registration order (`self._subscribers.setdefault(topic, []).append(handler)`, line 38), so *delivery order among multiple subscribers on the same topic* is deterministic and reproducible (registration order, every time), but there's no concept of routing a given event consistently to "the same" handler across separate runs the way `Experiment.assign()` guarantees a given identity always lands in the same variant. That's an apples-to-oranges comparison, though: `EventBus.publish()` broadcasts to *every* subscriber on a topic, not to a specific one selected via a bucketing function — there's no "pick one consumer for this event" concept anywhere in this module the way there is in `Experiment`, so determinism-of-routing isn't actually a relevant axis here. `KafkaEventBus` inherits whatever partition-assignment and consumer-group semantics Kafka itself provides once a `group_id` is configured (which this code doesn't currently set, per Q3/Q7) — that's the layer where "does the same key always route to the same consumer" would actually apply, and it's simply unconfigured in this implementation.

## Q9: Why does `wire_event_driven()` treat "event-driven" as "a trigger mechanism orthogonal to which topology handles the event" rather than its own topology?

The docstring is explicit about this (line 75-77): `wire_event_driven` accepts `graph: Any` — literally any compiled graph from any `build_*_graph` function, single-agent or any native/LangGraph multi-agent topology — and just subscribes it to a bus topic so it runs automatically when triggered, instead of being invoked directly by calling code. This reflects a real architectural insight: "event-driven" describes *how* a graph gets triggered (reactively, off a bus, versus a caller directly calling `.invoke()`), not *what shape* the graph's internal collaboration takes (supervisor, swarm, debate, single-agent, whatever). Making event-driven its own topology class would have meant either duplicating every existing topology's logic inside an "event-driven" wrapper, or artificially restricting event-driven triggering to only work with one specific topology shape — neither of which matches reality, since any topology can equally validly want to be triggered by an external event instead of a direct call. Keeping it as a standalone wiring function that composes with anything already compiled is the more composable design, at the cost of `wire_event_driven` itself knowing almost nothing about what it's actually triggering — it blindly constructs a `{"messages": [...], "thread_id": ...}` state dict and calls `.invoke()`, trusting that shape is universally accepted (which, per this codebase's own graph-building conventions, it is).

## Q10: What happens if the same event dict is published to a topic that has zero subscribers?

`InMemoryEventBus.publish()` does `self._log.append((topic, event))` unconditionally — the event is recorded in history regardless of whether anyone's listening — and then `for handler in self._subscribers.get(topic, [])` uses `.get(topic, [])`, which returns an empty list for an unknown topic rather than raising `KeyError`. So publishing to a topic with no subscribers is a complete no-op from the handler-execution side (the `for` loop simply doesn't iterate) but is *not* a no-op from the history side — `bus.history(topic)` would still show the event as published. This means `InMemoryEventBus` never gives any signal (an error, a warning, a return value indicating "zero subscribers received this") that a publish went nowhere — a caller relying on `wire_event_driven()`'s subscription actually being registered before the first event is published (a startup-ordering bug) would see their event silently swallowed with no indication anything was wrong, discoverable only by later inspecting `.history()` and noticing no corresponding graph invocation ever happened. `KafkaEventBus.publish()` has an analogous but differently-shaped gap: Kafka itself will happily accept and durably store a message on a topic with zero active consumer groups — it isn't lost, but it also isn't "delivered" to anything until a consumer eventually subscribes and polls it, which could be much later or never, depending on retention settings.

## Q11: How would you extend `InMemoryEventBus` to support asynchronous, non-blocking publish (so a slow subscriber doesn't block the publisher), and what existing pattern in the module would that resemble?

The natural analogue already exists in this very file: `KafkaEventBus.subscribe()`'s pattern of spinning up a background thread per subscriber and running its own consumer loop. You could give `InMemoryEventBus` a similar async mode — e.g. an `async_publish()` (or a constructor flag) that, instead of calling each handler inline on the publishing thread, submits each handler call to a thread pool (or a per-subscriber queue drained by a dedicated worker thread) and returns immediately. The tradeoff would be losing the current implementation's biggest practical virtue: `publish()`'s synchronous, in-order guarantee makes `InMemoryEventBus` trivially easy to reason about and test (call `publish()`, then immediately assert on side effects — no waiting, no polling, no flakiness) — exactly the property that makes it "real and fully tested" per the docstring, in contrast to `KafkaEventBus`'s inherent asynchrony making it much harder to test deterministically (there's no test file exercising `KafkaEventBus` against a live broker, consistent with the module's own honest admission). Any async extension should probably be an explicit opt-in variant, not a change to the existing synchronous default, precisely to preserve that testability.

## Q12: If two different callers both call `wire_event_driven()` on the *same* topic with two different graphs, what happens when an event is published?

Nothing prevents this, and nothing coordinates between the two subscriptions — `EventBus.subscribe(topic, handler)` just appends another handler to that topic's subscriber list, so both graphs' `on_event` closures get registered independently. When an event is published, `InMemoryEventBus.publish()` calls both handlers in registration order, meaning *both* graphs get invoked, each treating the same event dict as their own triggering user message, each potentially writing to their own `thread_id` (or, if both happened to use the default `thread_id_fn`, colliding on the exact same `f"event-{topic}"` thread id and interleaving state in whatever shared `StateStore` backs both graphs — a real correctness hazard if the two graphs weren't intended to share history). There's no topic-ownership or single-subscriber-per-topic enforcement anywhere in this module — `wire_event_driven` is a thin convenience wrapper, and avoiding this kind of accidental double-wiring is entirely the caller's responsibility.

## Q13: If a subscriber handler on topic `T` itself calls `bus.publish("T", ...)` inside its own execution, what happens under `InMemoryEventBus`?

`publish()` (lines 32-35) does `for handler in self._subscribers.get(topic, []): handler(event)` — a completely ordinary, non-reentrancy-guarded Python loop. If `handler` itself calls `bus.publish("T", another_event)` before returning, that's a plain recursive call into `publish()` on the same thread's call stack: the inner `publish()` call re-fetches `self._subscribers.get("T", [])` (the same list, since nothing removed or paused the subscription) and re-invokes every handler on topic `T` again, including the very handler currently executing further up the stack. If that handler unconditionally republishes on every invocation (rather than under some terminating condition), this is unbounded recursion — each nested `publish()` call adds stack frames with no iteration limit, no cycle detection, and no recursion-depth guard anywhere in this module, eventually raising `RecursionError` once Python's stack limit is hit. `wire_event_driven()`'s `on_event` closure (lines 83-88) is exactly the kind of handler that could trigger this by accident: if a graph invocation's own logic ever published back onto the same topic it was triggered from (e.g. an agent tool that re-publishes an event as part of its normal behavior), you'd get exactly this recursive-republish cascade with no framework-level protection against it — a caller building event-driven-triggered graphs needs to be personally careful never to have a triggered graph republish onto its own trigger topic.

## Q14: How does this module's event model compare to how Temporal (one of the three Runtime axis options this framework supports, per the project's architecture) handles signals and events for a running workflow?

Temporal's signal mechanism is fundamentally durable and asynchronous-by-design at the platform level: a signal sent to a running workflow is persisted by the Temporal service itself, delivered to the workflow's event history even if the worker processing it is temporarily down, and replayed deterministically if the workflow needs to recover from a crash — signals are a first-class part of workflow history, not a best-effort in-process callback. `InMemoryEventBus` has none of this: it's explicitly synchronous, in-process, and non-durable (a process restart loses every subscriber registration and the entire `_log` history, since `_subscribers`/`_log` are plain Python objects with no persistence). `KafkaEventBus` gets partway to Temporal's durability story by using a real broker (messages are durably stored, ordered per-partition, and survive a consumer restart if using the right offset-commit strategy — though as Q3/Q7 note, this implementation doesn't actually configure any of that yet), but even a correctly-configured `KafkaEventBus` still lacks Temporal's deeper guarantee of exactly-once, deterministic workflow replay tied to the event itself. The practical implication: `wire_event_driven()` is a good fit for "trigger a graph run when something happens, best-effort" use cases, but a workflow that genuinely needs guaranteed, ordered, replay-safe delivery of external signals into a long-running durable process is better served by running under this framework's actual Temporal runtime integration (a different axis of the framework entirely) rather than layering `EventBus` semantics on top of a non-durable runtime and hoping for the best.

## Q15: What's a limitation of `events.py` you'd fix given more time?

The most consequential one is the complete lack of error isolation in both `InMemoryEventBus.publish()` and `KafkaEventBus.subscribe()`'s consumer loop (Q4, Q7): a single handler exception can either abort delivery to every remaining subscriber on that topic (in-memory) or permanently kill the background consumer thread with no restart and no dead-letter path (Kafka). Given more time, I'd wrap each handler invocation in a `try`/`except` that logs the failure and continues to the next subscriber (in-memory) and add a supervising retry/restart loop with a configurable dead-letter topic for `KafkaEventBus`'s consumer thread — bringing both implementations in line with how most production event systems isolate consumers from each other's failures. A close second: `KafkaEventBus` has no `group_id`, offset-commit strategy, or reconnect/backoff logic configured anywhere in its constructor or `subscribe()` — all of which materially change delivery semantics (at-least-once vs. exactly-once, whether a restarted consumer replays history or picks up where it left off) and are exactly the kind of thing that can only be caught by testing against a real broker, which the module honestly admits hasn't happened yet.
