# agent_foundry/scaffold.py — Q&A

**2026-09-28 update:** the historical discussion below predates [governed exports](../../GOVERNED_TOOL_ADAPTERS.md). Raw conversions now require explicit opt-in; current enforcement and compatibility limits are documented there.

`scaffold.py` generates a runnable single-agent starting point — `prompts/<name>.md` and `agents/<name>.py` — by string-templating four constants (`_PROMPT_TEMPLATE`, `_TOOL_STUB_TEMPLATE`, `_AGENT_TEMPLATE`) and writing them to disk via the `create_agent()` function, so a new agent already has gateways, guardrails, eval, runtime budget, and tracing wired and only needs its prompt text and tool bodies filled in.

## Q1: Walk through exactly what happens when `create_agent("sales_agent", directory=".", tools=["lookup_lead", "send_email"])` is called (scaffold.py:97).

`create_agent` first defaults `tools = tools or []` and derives a human title via `name.replace("_", " ").replace("-", " ").title()` → `"Sales Agent"`. It builds `tool_lines` as a bullet list (`"- lookup_lead(...)\n- send_email(...)"`) for the prompt file, or the literal string `"(none yet — TODO: add some)"` if `tools` is empty. It creates `./prompts` (via `os.makedirs(prompts_dir, exist_ok=True)`) and writes `prompts/sales_agent.md` using `_PROMPT_TEMPLATE.format(title=title, tool_lines=tool_lines)` — a system prompt with a `TODO` placeholder and a `CALL <tool_name> {"arg": "value"}` protocol description. It then builds three more format-args: `tool_stubs` (Python function stub source per tool, from `_TOOL_STUB_TEMPLATE`, concatenated), `tool_registrations` (a `tools.register(ToolSpec(...))` line per tool, or a TODO comment if none), and `tool_names` (a comma-joined, quoted string for `frozenset({...})`). It creates `./agents` and writes `agents/sales_agent.py` by filling `_AGENT_TEMPLATE` with all of the above plus `name`. Finally it returns `{"prompt": prompt_path, "agent": agent_path}`. Nothing is imported, parsed, or validated as real Python during this call — it's pure string formatting and file I/O; the first time the generated code is actually checked for correctness is when someone runs `python agents/sales_agent.py`.

## Q2: Why does `create_agent` use raw string templates (`.format()`) instead of a templating engine like Jinja2, or a tool like `cookiecutter`/`copier`?

The module's own docstring frames the goal as moving "build time from days to hours" with zero extra ceremony — `cookiecutter`/`copier` are directory-tree-based scaffolders that need a separate template repository/directory structure, a `cookiecutter.json` (or `copier.yml`) config schema, and a runtime dependency, for what is here two small string templates and a handful of `str.format()` calls. Given `agent_foundry`'s consistent minimal-dependency posture (see `cli.py`'s lazy imports and `serve.py`'s "nothing imports a cloud-specific SDK" framing), pulling in a general templating engine for two files would be disproportionate. The real cost of the `.format()` approach is fragility: `_AGENT_TEMPLATE` embeds literal Python braces (e.g. `frozenset({{{tool_names}}})`, `identity = Identity(id="{name}-1", ...)`) that must be double-escaped (`{{`/`}}`) to survive `.format()`, which is exactly the kind of subtle bug class Jinja2's `{{ }}` / distinct-delimiter design avoids. A single unescaped brace anywhere in a future edit to `_AGENT_TEMPLATE` would raise a `KeyError`/`IndexError` at scaffold time with a confusing message, not a template-engine-level "undefined variable" error.

## Q3: What happens if a tool name passed to `--tools` isn't a valid Python identifier, e.g. `foundry init myagent --tools "look-up lead"`?

`create_agent` never validates tool names — it treats each string purely as text to interpolate into templates. `_TOOL_STUB_TEMPLATE.format(tool_name="look-up lead")` would happily produce `def look-up lead(TODO_arg: str) -> str:`, which is not valid Python syntax at all (illegal characters and a space in a function name). This would be written successfully to `agents/myagent.py` with no error at scaffold time — `create_agent` returns normally and prints "wrote ..." — and the failure only surfaces the moment someone runs `python agents/myagent.py`, as a `SyntaxError` pointing at the generated file. This is a real, unguarded gap: there's no `str.isidentifier()` check (or `keyword.iskeyword()` check against reserved words like `class` or `def`) anywhere in `create_agent`, `cmd_init`, or `_main()`. A tool named `class` or `import` would silently generate broken Python.

## Q4: The `_AGENT_TEMPLATE`'s generated `main()` does `sys.path.insert(0, os.path.dirname(os.path.dirname(os.path.abspath(__file__))))` before importing `agent_foundry`. Why, and what's fragile about it?

The generated `agents/<name>.py` file lives in a project's `agents/` subdirectory, and the template assumes `agent_foundry` itself is a sibling package one level up from that (i.e. the project root, `directory` in `create_agent`, either contains or is adjacent to an importable `agent_foundry`). Since the scaffolded script is meant to be runnable standalone (`python agents/sales_agent.py`) without the project root already being on `PYTHONPATH` or the project being `pip install -e`'d, it manually inserts the project root computed from its own file location (two `dirname()` calls: strip the filename, then strip the `agents/` directory) at the front of `sys.path`. This is fragile in exactly the way manual `sys.path` surgery always is: it assumes a fixed two-levels-up directory layout (`<root>/agents/<name>.py`), so if a user moves the generated file, symlinks it, or the "project root" isn't actually where `agent_foundry` is importable from (e.g. `agent_foundry` was `pip install`ed into a virtualenv rather than living as a sibling source directory), this line either does nothing useful or, worse, silently prepends a directory that happens to contain an unrelated module also named something imported later. A `pip install`-based or `pyproject.toml`-based project structure wouldn't need this hack at all; it exists purely to make the zero-setup, copy-a-script-and-run-it demo path work.

## Q5: The generated agent script raises `SystemExit("set ANTHROPIC_API_KEY to run this agent")` if the env var isn't set, but only checks for its presence — not its validity. What happens on invalid or expired keys?

That check (`if not os.environ.get("ANTHROPIC_API_KEY"): raise SystemExit(...)`) is deliberately shallow — it's a fast, local, zero-network-call fail-fast for the single most common first-run mistake (forgetting to export the key at all), not a full credential validator. An invalid, revoked, or expired key passes this check trivially and the failure instead surfaces later, deep inside `AnthropicProvider`/`LLMGateway` (constructed a few lines later at `LLMGateway(provider=AnthropicProvider())`) as whatever error the Anthropic SDK raises on the first actual API call inside `chat_loop`. This is a reasonable design tradeoff for a scaffolded starting point — validating a key would require an API round-trip at every script startup, adding latency and a network dependency to what should be an instant CLI check — but it does mean the error experience for "your key is wrong" is worse (a raw SDK exception, possibly deep in a traceback triggered mid-conversation) than for "you forgot to set it" (a clean, immediate `SystemExit` with an actionable message).

## Q6: `create_agent`'s `topology` parameter is accepted but the docstring says it's "currently informational (single-agent template)." What actually happens if you pass `topology="supervisor"`?

Nothing — `topology` is accepted as a keyword argument (`topology: str = "single"`, scaffold.py:97) but is never read anywhere in the function body; only `name`, `directory`, and `tools` actually influence the generated output. So `create_agent("x", topology="supervisor")` silently produces the exact same single-agent template as `topology="single"` would, with zero indication that the requested topology was ignored. `_main()`'s own `argparse` setup (line 134) at least constrains this at the CLI level with `choices=["single"]`, so `python -m agent_foundry.scaffold x --topology supervisor` is rejected by `argparse` before `create_agent` is ever called — but `create_agent` itself, called directly as a library function (as `cli.py`'s `cmd_init` does, and as any external caller could), has no such guard. This is an honest, acknowledged limitation per the function's own docstring, which explicitly tells the reader to "copy this file's `AGENT_TEMPLATE` as a starting point" for other topologies rather than pretending the parameter does something it doesn't.

## Q7: How does the generated agent's tool wiring in `_AGENT_TEMPLATE` connect a tool named in `--tools` to an actual `ToolRegistry` entry, and what's left for the developer to do?

Three of the four templated sections cooperate: `_TOOL_STUB_TEMPLATE` generates a bare function stub (`def lookup_lead(TODO_arg: str) -> str: raise NotImplementedError(...)`) appended after the imports; `tool_registrations` generates one line per tool inside `main()`: `tools.register(ToolSpec("lookup_lead", "TODO: describe lookup_lead", {}, lookup_lead))`; and `tool_names` feeds `Policy.allowed_tools=frozenset({"lookup_lead", "send_email"})`. So by the time `main()` runs, the tool is registered in the `ToolRegistry`, allow-listed in the `Policy`, and callable by name — but its actual implementation still raises `NotImplementedError` until the developer replaces the stub body, and its `ToolSpec` description is still the literal string `"TODO: describe lookup_lead"` (which would leak into the model's tool schema completely unhelpfully if left as-is), and its parameters dict is a hardcoded empty `{}` regardless of what the function stub's own signature declares — the JSON-schema-like `parameters` field on `ToolSpec` is never derived from the stub's type hints the way `quickstart.py`'s `create_agent`-based path does (see `quickstart.py`'s docstring contrasting the two).

## Q8: Contrast `scaffold.create_agent`'s tool-wiring model with `quickstart.plug_and_play_agent`'s. Why do both exist in the same codebase?

`scaffold.py` generates code for the "governed" path (`AgentConfig`/`build_agent_graph`, `ToolSpec` with manually-authored `parameters` dicts, `Policy.allowed_tools`, `GuardrailEngine`) — full RBAC/guardrails/eval/audit wiring, at the cost of the developer having to hand-author each `ToolSpec`'s schema. `quickstart.py`'s `plug_and_play_agent` wraps `langchain.agents.create_agent` directly, inferring tool schemas automatically from a plain function's type hints and docstring (no `ToolSpec`, no manual JSON schema). They coexist because they target different maturity stages of the same team: `quickstart.py`'s own docstring calls `to_langchain_tool()` "the bridge between them" so a team can start on the fast path and grow into the governed one without rewriting tools from scratch. `scaffold.py` produces a ready-made governed skeleton for teams that know from day one they need RBAC/guardrails; `quickstart.py` is for the "junior developer's whole agent is five lines" case. Interview-relevant subtlety: `create_agent` (scaffold.py) is a code-GENERATOR (writes files to disk you then edit), while `plug_and_play_agent` (quickstart.py) is a runtime FACTORY (returns a live LangGraph agent object) — they solve superficially similar "get started fast" problems via structurally opposite mechanisms.

## Q9: What happens if `create_agent` is called twice with the same `name` — does it overwrite, merge, or error?

`create_agent` opens both output files with plain `open(path, "w")` (scaffold.py:109, 121) — `"w"` mode truncates and overwrites unconditionally, with no existence check, no confirmation prompt, and no `--force` flag anywhere in `cli.py` or `_main()`. Re-running `foundry init sales_agent` after a developer has already filled in the TODOs and written real tool implementations would silently destroy all of that work and replace it with the pristine template again. This is a genuine, unguarded footgun — there's no `os.path.exists()` check before either write, and neither `cmd_init` nor `create_agent`'s docstring warns about it. A safer version would at minimum warn or refuse to overwrite a file that doesn't still contain the `TODO` markers (implying it was already edited).

## Q10: What's a limitation of `scaffold.py` you'd fix given more time?

The two most consequential are the silent overwrite behavior (Q9) and the complete lack of input validation on tool names (Q3) — both are "works fine in the happy path, corrupts state or produces invalid code in the unhappy path" gaps typical of a v1 scaffolder. A third, more architectural one: because `_AGENT_TEMPLATE` is a single hardcoded string constant supporting only the `"single"` topology, adding a second real topology (supervisor/swarm) means copy-pasting the entire ~90-line template and hand-maintaining two near-duplicate strings in sync forever — there's no shared sub-template for the parts that don't vary by topology (the imports, the `ANTHROPIC_API_KEY` check, the `PromptLibrary` load), so `scaffold.py`'s own docstring instruction to "copy this file's `AGENT_TEMPLATE` as a starting point" is explicitly setting up future code duplication rather than parameterizing the template to accept a topology-specific `build_*_graph` call.

## Q11: Why does the scaffolded agent script import `chat_loop` from `agent_foundry.ui.console` rather than making the CLI itself drive the conversation?

Because `create_agent` generates a standalone script meant to run independently of `foundry` entirely (`python agents/sales_agent.py`, no `foundry` invocation needed) — see the generated file's own module docstring instructing exactly that command. Baking `chat_loop` into the generated script (rather than, say, having `foundry run` supply the interactive loop) keeps the scaffolded agent fully self-sufficient and demonstrates that `ui.console.chat_loop` is a reusable, swappable UI layer (per `console.py`'s own docstring: "A production UI swaps this module for a web app talking to the same compiled graph") — the scaffolded script is simultaneously a working demo of the UI layer and the agent itself.

## Q12: The prompt template's tool-calling protocol is `CALL <tool_name> {"arg": "value"}` — text the model must emit verbatim, rather than a structured tool-calling API. Why, and what breaks if the model doesn't follow the format exactly?

This is the "governed" path's own text-based tool-invocation convention (distinct from `quickstart.py`'s real structured `AIMessage.tool_calls` — see that module's docstring drawing the same contrast) — `scaffold.py` only writes the prompt text asking the model to follow this convention; the actual parsing of `CALL <tool_name> {...}` lines out of a model's raw text response happens elsewhere in `orchestration.py`'s think/act nodes, not in `scaffold.py` itself. Because this is a plain-text protocol rather than the LLM API's native structured tool-calling, correctness depends entirely on the model reliably reproducing that exact syntax (right JSON, right spacing, right keyword) every time — a model that instead writes prose describing what it wants to do, or emits slightly malformed JSON, would not be recognized as a tool call by whatever regex/parser `orchestration.py` uses downstream. `scaffold.py`'s prompt template doesn't include any few-shot example of a full correct call/response exchange, which is a realistic factor in why a model might drift from the format over a long conversation — it only shows the abstract pattern once, with a "TODO: describe this agent's job" that a developer might fill in without preserving the tool-calling instructions' prominence.

## Q13: Trace what `_main()` does differently from `cli.py`'s `cmd_init`, and why maintaining two separate entry points to the same function is risky.

`scaffold.py`'s own `_main()` (line 130) is a standalone `argparse` CLI (`python -m agent_foundry.scaffold <name> --directory ... --topology ... --tools ...`) that exposes all three of `create_agent`'s parameters, including `--topology` with `choices=["single"]`. `cli.py`'s `cmd_init` is a second, independent `argparse` subparser (`foundry init <name> --directory ... --tools ...`) that omits `--topology` entirely (see the `cli.py` Q&A, Q2) — so `create_agent` is called with `topology`'s default (`"single"`) always, silently, when invoked via `foundry`. Two independent argument-parsing entry points into the same function is risky specifically because nothing keeps them in sync: a future contributor adding a new `create_agent` parameter (say, a `--license` flag) could easily update one entry point's `argparse` wiring and forget the other, and there's no shared parser-building helper or test asserting the two CLIs expose an equivalent surface — which is exactly the drift that already happened with `--topology`.

## Q14: How would a senior reviewer criticize the fact that `create_agent` returns `dict[str, str]` with hardcoded keys `"prompt"`/`"agent"` instead of a typed dataclass or named tuple?

The codebase elsewhere favors typed dataclasses for structured returns (e.g. `contracts.Identity`, `contracts.Policy`, `contracts.ToolSpec` are all `@dataclass`), so a bare `dict[str, str]` here is inconsistent with that convention and loses IDE/type-checker support for catching a typo like `paths["promt"]` — which would raise a runtime `KeyError` instead of a static-analysis error. It's a minor inconsistency rather than a functional bug (both call sites, `cli.py`'s `cmd_init` and `scaffold.py`'s own `_main()`, correctly use `paths['prompt']`/`paths['agent']`), but for a codebase whose stated goal is demonstrating disciplined, defensible engineering, a `@dataclass ScaffoldResult: prompt: str; agent: str` would be a small, free improvement in type safety.

## Q15: What testing strategy would you use to verify `scaffold.py`'s output is actually correct, beyond "it wrote two files"?

Because `create_agent` never validates its own template output as real Python (Q1, Q3), the strongest test isn't just asserting the two files exist and contain expected substrings — it's actually running `ast.parse()` (or `py_compile.compile()`) against the generated `agents/<name>.py` source to catch syntax errors from bad tool names or template escaping bugs before they ship, then separately `importlib`-loading the generated module in a sandboxed environment with `ANTHROPIC_API_KEY` unset to confirm the `SystemExit` fires correctly, and with it set (and the LLM call mocked) to confirm `main()` reaches `chat_loop` without raising. A property-based test feeding `create_agent` a range of tool-name strings (including edge cases like Python keywords, unicode, empty strings, and strings with `{`/`}`) against an `ast.parse()` assertion would directly target the gap identified in Q3.
