# agent_foundry/core/execution_context.py — Q&A

Defines `ExecutionContext`, the single per-request object (thread/session/user/tenant identity, budget/deadline/cancellation overrides, tool/model policy narrowing, memory scoping) that every layer of the framework receives instead of loose strings threaded ad hoc through each function, plus `CancellationToken`, a cooperative stop signal for a run's think/act loop.

## Q1: `resolved_thread_id()` falls back `thread_id or session_id or self.run_id`, where `run_id` defaults to a fresh `uuid.uuid4().hex`. Why fall all the way back to a random UUID instead of raising if the caller didn't set `thread_id`/`session_id`?

Because `run_id` is generated via `field(default_factory=lambda: uuid.uuid4().hex)` (line ~44), every `ExecutionContext()` — even one constructed with zero arguments — always has *some* unique identifier to fall back to, which means a caller who doesn't care about conversation continuity (a genuinely one-off, single-turn call) never needs to think about thread/session management at all: `agent.run("hello")` with no `context=` works out of the box, gets a fresh `run_id`-keyed thread, and that's fine because there's no continuation expected. Raising instead would force every caller — even ones who only ever want one-shot, stateless calls — to explicitly pass a `thread_id` just to avoid an exception, which contradicts the framework's broader design of "identity/threading fields are optional, only include what the caller actually set" (the same philosophy `to_request_state()` applies at line ~101, "Only includes fields the caller actually set"). The trade-off: a caller who *intends* to continue a conversation but forgets to pass a stable `thread_id`/`session_id` across calls won't get an error — they'll silently get two unrelated `run_id`-keyed threads, which can look like "the agent forgot everything" when it's actually just talking to two different threads.

## Q2: `to_request_state()`'s own docstring says it's "LangGraph-engine only for now" and that budget/deadline/cancellation_token/tool_policy/model_policy/memory_scope are "silently no-ops on the native runtime." Trace exactly which fields survive onto `runtime="native"`, and what's the concrete risk to a caller who sets `context.deadline` and runs on native expecting it enforced?

Looking at how each engine actually consumes `ExecutionContext`: `core/agent.py`'s `_request_identity_dict` (called by both `_CompiledWorkflow._initial_state` for every runtime, and forwarded into `NativeEngine.run(..., request_identity=...)`) is the *only* piece of `ExecutionContext` state the native path picks up — user_id/tenant_id/permissions, packaged as `request_identity`. Every other field `to_request_state()` would populate — `request_budget`, `request_deadline`, `request_cancellation_token`, `request_tool_policy`, `request_model_policy`, `request_memory_scope` — is only ever read back by `orchestration.py`'s `_resolve_budget`/`_check_deadline`/`_check_cancellation`/`_resolve_tool_policy`/`_resolve_model_names`/`_memory_key` functions, which are LangGraph-engine node closures; `native_engine.py`'s `_think`/`_act`/`_critique` never reference any of those keys. Concretely: a caller who does `agent.run(msg, context=ExecutionContext(deadline=time.time() + 5))` on `Agent(runtime="native")` gets **no** enforcement of that 5-second deadline at all — the run proceeds using only `AgentConfig.step_timeout_s`/`latency_budget` (if configured), with the per-request `deadline` override silently discarded. There's no warning or error raised anywhere in this call path — a caller relying on `ExecutionContext.deadline` as a safety net for native runtime would be flying blind, and the only way to discover this is reading this exact docstring or `native_engine.py`'s source.

## Q3: `ExecutionContext.cancellation_token`'s docstring states it's "checked at loop-safe points (top of think(), top of act(), before each individual tool call)" in "both engines," and that "`core.run.Run.cancel()` sets one of these automatically." Verify both claims against `native_engine.py` and `core/run.py`.

Neither claim holds up under inspection of the actual code in those two files. `native_engine.py`'s `_think`, `_act`, and `_critique` methods never reference `cancellation_token`, `request_cancellation_token`, or anything resembling a cancellation check anywhere — there is no "top of think()"/"top of act()"/"before each tool call" checkpoint implemented in the native engine at all; the claim of "both engines" checking it is only true for the LangGraph engine's `orchestration.py` node closures (via `_check_cancellation`, referenced in `to_request_state()`'s own docstring), which is itself consistent with `to_request_state()`'s honest admission that `request_cancellation_token` is "LangGraph-engine only for now." Separately, `core/run.py`'s `Run.cancel()` method (lines ~126–129) is: `if self._event_subscription is not None: self._event_subscription = None`, then `self.status = RunStatus.CANCELLED` — it never touches `self.context.cancellation_token` in any way, so the claim that "`Run.cancel()` sets one of these automatically" is not reflected in `core/run.py`'s actual implementation as read. This looks like genuine documentation/implementation drift (or an unfinished feature whose wiring was never completed) rather than a subtle behavior a reader is missing — a caller who trusts this docstring and expects `run.cancel()` to cooperatively stop an in-flight native-engine turn via the token mechanism it describes would be wrong on both counts.

## Q4: `deadline` (an absolute unix timestamp) is described as composing with, not replacing, `AgentConfig.step_timeout_s`/`latency_budget`. Given the Q2 finding that `deadline` is a no-op on native runtime, what actually enforces a deadline for a native-runtime run today?

Nothing does, for the per-request `ExecutionContext.deadline` override specifically. `AgentConfig.step_timeout_s` is enforced inside `native_engine.py`'s `_think` via `with_timeout(call, seconds=config.step_timeout_s)` (native_engine.py, line ~331) — a genuine per-LLM-call timeout — and `config.latency_budget.check(...)` is called at the top of `_think` (line ~280) if `config.latency_budget` is set on the `AgentConfig` itself. Both of these are **static, construction-time** limits baked into the `Agent`'s configuration, not per-request overrides — they apply identically to every call regardless of what any particular `ExecutionContext` carries. A caller who wants a *tighter* deadline for one specific request (e.g., "this particular HTTP request has a 3-second budget because the caller's own client will time out") has no native-runtime mechanism to express that per-call; they'd need to either construct a separate `Agent` with a tighter `step_timeout_s`/`latency_budget`, or use `runtime="langgraph"` where `_check_deadline` genuinely reads `request_deadline` back out of state.

## Q5: `tool_policy` and `model_policy` are documented as "narrows (never widens)" AgentConfig's own policy/model routes. Where is that narrowing invariant actually enforced — in this file, or elsewhere — and could a caller trivially violate it?

`execution_context.py` itself does nothing to enforce the narrowing claim — `tool_policy: Policy | None` and `model_policy: dict[str, Any] | None` (lines ~70, ~74) are plain, unconstrained fields; nothing in this dataclass validates that a caller-supplied `Policy` is actually a subset of `AgentConfig.policy`'s `allowed_tools`. The docstrings explicitly point the actual merge logic elsewhere — "See `orchestration._resolve_tool_policy`" and "See `orchestration._resolve_model_names`" — meaning the narrowing guarantee is entirely a *convention* enforced by those specific merge functions' implementation (presumably computing an intersection rather than a union), not something `ExecutionContext` itself guards against. A caller could trivially construct `ExecutionContext(tool_policy=Policy(allowed_tools=frozenset(EVERY_TOOL_NAME)))` and pass it to a request; whether that actually "widens" access beyond `AgentConfig.policy` depends entirely on `_resolve_tool_policy`'s merge implementation (not in this file) correctly intersecting rather than replacing — this dataclass provides no structural guarantee, only documentation of intent. Also worth noting: since `to_request_state()` confirms `request_tool_policy`/`request_model_policy` are LangGraph-only no-ops on native, this "narrows never widens" guarantee doesn't even apply on `runtime="native"` at all — there's no tool/model policy override mechanism reachable through `ExecutionContext` on native runtime in the first place.

## Q6: `memory_scope` overrides the key used for a run's semantic/RAG memory reads but explicitly *not* cost/audit tracking, which "stay thread-scoped." What's a concrete scenario where this could produce a cross-tenant information leak if used carelessly?

The intended use (per the docstring, line ~75–79) is "sharing retrieved context across two otherwise-separate threads" — e.g., two different conversation threads for the same underlying user that should still surface the same retrieved documents. The risk: if `memory_scope` is derived from caller-supplied or otherwise not-strictly-validated input (say, a request header or a loosely-scoped session identifier) rather than something tenant-namespaced, two *different* tenants' requests that happen to compute the same `memory_scope` string would have their semantic memory searches key against the same underlying store partition — `config.memory.semantic.search(session_id, ...)`-style calls (as seen in `native_engine.py`'s `_think`) would need `memory_scope` prefixed or otherwise isolated by tenant to prevent this, and nothing in `ExecutionContext` itself enforces that `memory_scope` values are tenant-namespaced — it's a bare `str | None` field with no validation. Since cost/audit intentionally stay thread-scoped regardless of `memory_scope` (an explicit, deliberate design choice per the docstring), a caller might reasonably but incorrectly assume the *same* isolation guarantee extends to `memory_scope`, when it's actually opt-in and caller-controlled.

## Q7: `ExecutionContext` is a plain `@dataclass`, not a Pydantic model — consistent with this project's "no Pydantic" architectural rule. What concrete runtime-validation guarantees does that give up, and where does the codebase compensate?

A plain dataclass performs zero runtime type coercion or validation on construction — nothing stops `ExecutionContext(permissions=["admin"])` (a `list`, not the declared `frozenset[str]`) from being constructed successfully; the type annotation is purely for static analysis (mypy/pyright), not enforced at runtime the way a Pydantic `BaseModel` would reject or coerce it automatically. Concretely, `_request_identity_dict` in `core/agent.py` does `tuple(context.permissions)` — this happens to work whether `permissions` is actually a `frozenset`, a `list`, or any other iterable, so the specific type-mismatch example above wouldn't even surface as a bug in that one call site, but a different consumer that specifically relied on `frozenset` semantics (e.g., calling `.issuperset(...)` or relying on hashability for deduplication) would fail with an `AttributeError` only at the point of actual misuse, not at construction. The codebase's general compensation strategy (consistent with what's visible in `AgentConfig.__post_init__`, referenced in `native_engine.py`'s comments) is validating important invariants in `__post_init__` hooks on dataclasses that need them — `ExecutionContext` itself has no `__post_init__` at all, meaning it's one of the more "trusting" dataclasses in the codebase, relying entirely on callers constructing it correctly and static type-checking to catch mistakes before runtime.

## Q8: Why is `permissions` specifically typed `frozenset[str]` rather than a plain `set[str]` or `list[str]`?

`frozenset` is immutable and hashable, which matters for two reasons visible from how this dataclass is used elsewhere in the codebase: `core/run.py`'s `Run.fork()` uses `dataclasses.replace(self.context, thread_id=new_thread_id, run_id=uuid.uuid4().hex)` (line ~152) to produce a new `ExecutionContext` sharing every other field's *value* with the original — if `permissions` were a mutable `set`, `replace()` would still share the same underlying set object by reference (dataclasses.replace does a shallow copy of unspecified fields), meaning a caller mutating `forked_context.permissions.add("new_role")` would silently mutate the *original* context's permissions too, since both point at the same set instance. `frozenset` makes any such accidental aliasing bug impossible, since it has no mutating methods at all — any "modification" must construct a brand-new frozenset, which is inherently safe to share by reference across multiple `ExecutionContext` instances produced via `replace()`.

## Q9: If a caller shares a single `ExecutionContext` object across two concurrent `agent.arun()` calls (e.g., reusing the same context object for two logically distinct requests to save an allocation), what actually happens?

Since `resolved_thread_id()` is a pure function of the context's own fields (`thread_id or session_id or self.run_id`) and returns the identical value every time it's called on the same object, both concurrent `arun()` calls resolve to the exact same `thread_id` — meaning both calls target the *same* conversation thread, not two independent ones. On `runtime="native"`, this means both calls contend for `NativeEngine._lock_for(thread_id)`'s per-thread lock (traced in the `core_native_engine` Q&A) — one call blocks until the other's entire turn finishes, and the two user messages get appended to the same `state["messages"]` list sequentially rather than being processed as independent conversations. This is very likely *not* what a caller intends if they were only trying to save an object allocation — sharing one `ExecutionContext` across logically distinct requests is a footgun with no protection against it in this dataclass; each logically distinct request should construct its own `ExecutionContext()` (which gets a fresh `run_id` by default) unless deliberate conversation-sharing is the actual intent.

## Q10: Compare `ExecutionContext` to how LangGraph itself represents per-invocation configuration (`RunnableConfig`, `{"configurable": {"thread_id": ...}}`), or to Temporal's `WorkflowInfo`. What's the design trade-off of the framework defining its own dataclass here instead of just using LangGraph's native config shape directly?

LangGraph's `RunnableConfig` is a loosely-typed `TypedDict`-like structure whose `"configurable"` sub-dict is essentially an untyped bag of whatever keys a particular graph's nodes choose to read — there's no compile-time or IDE-visible guarantee about what fields exist, and it's tightly coupled to LangGraph's own runtime, meaning code written against it directly wouldn't run at all on `runtime="native"`. `ExecutionContext` exists specifically because the framework supports two structurally different execution engines behind one API (`core/protocols.py`'s `WorkflowEngine` seam) — a single, framework-owned, statically-typed dataclass gives every caller (and every layer: model, tool, memory, policy, retrieval, audit, eval, events, per the module docstring) one common shape to code against regardless of which engine ultimately runs the request, with IDE autocomplete and type-checking support LangGraph's own loosely-typed config dict wouldn't provide. The cost, as this file's own docstrings repeatedly acknowledge (Q2's finding), is that this abstraction currently leaks: several fields only actually take effect on one of the two engines, so the unified type doesn't yet guarantee unified *behavior* — the type system promises more uniformity than the runtime currently delivers.

## Q11: `CancellationToken.is_cancelled()`/`.cancel()` are implemented via a plain `threading.Event`. Why `threading.Event` specifically, rather than a plain boolean flag with a lock, or an `asyncio.Event`?

`threading.Event` gives atomic, thread-safe set/check semantics (`.set()`/`.is_set()`) without the caller needing to manage a separate lock explicitly — a plain `bool` attribute guarded by a `threading.Lock` would require every reader and writer to explicitly acquire/release that lock around each access, which is exactly the boilerplate `threading.Event` already encapsulates internally (it uses a lock and a condition variable under the hood). `asyncio.Event` was not chosen because `CancellationToken` needs to be checked from **synchronous** code inside `native_engine.py`'s `_think`/`_act` (the docstring says "checked at loop-safe points"), and those methods run either directly on a calling thread (`Agent.run`) or inside a worker thread spawned via `asyncio.to_thread` (`Agent.arun`) — an `asyncio.Event` would require an event loop to be running in the checking context and would need `await`, which synchronous engine code can't do without its own `asyncio.run()` call, an unnecessary complication given `threading.Event` already works correctly across both sync and thread-pool-executed async contexts.

## Q12: The class docstring says cancellation "takes effect at the next checkpoint after" an in-flight LLM call or tool execution completes — "NOT preemptive." Given the Q3 finding that native_engine.py never actually checks `cancellation_token` anywhere, what does this mean in practice for a caller who constructs and passes their own `CancellationToken` on native runtime today?

In practice, given what's actually implemented (not just documented), a `CancellationToken` passed via `ExecutionContext(cancellation_token=my_token)` on `runtime="native"` has **no effect at all** — there's no checkpoint anywhere in `native_engine.py`'s `_think`/`_act`/`_critique`/`_drive_stream` that reads it, so calling `my_token.cancel()` while a native-runtime turn is mid-flight does nothing to stop it; the turn runs to completion (or to its next HITL pause point, which is unrelated to cancellation) regardless. This is a real, currently-unimplemented half of a documented feature: the class's own docstring describes intended behavior ("checked at loop-safe points... top of think(), top of act(), before each individual tool call") that matches what one would expect *if* `native_engine.py` had been wired up to check it, but as of this reading, that wiring doesn't exist in the native engine — only (per `to_request_state()`'s own admission) potentially on the LangGraph engine via `orchestration.py`'s `_check_cancellation`, which wasn't one of the files reviewed here to independently confirm.

## Q13: `ExecutionContext.metadata: dict[str, Any]` is a catch-all field with no documented consumer anywhere in this file. What's its actual purpose, and what's the risk of an unstructured escape hatch like this?

Unlike every other field on `ExecutionContext`, `metadata` has no dedicated comment explaining what reads it or what it's for — it's the one genuinely open-ended field, presumably intended for application-specific per-request data that doesn't warrant a first-class typed field of its own (e.g., a caller's own request-correlation ID, a feature flag, or arbitrary tracing tags an application wants threaded through without the framework needing to know about it). The risk of an unstructured `dict[str, Any]` escape hatch is exactly what you'd expect: nothing in this dataclass or `to_request_state()` forwards `metadata` into graph state or engine execution at all (it's conspicuously absent from `to_request_state()`'s field-by-field forwarding list, lines ~101–118) — so unlike every other override field here, `metadata` appears to be purely for the caller's own bookkeeping (e.g., reading it back off `context.metadata` after the fact for logging), not something any current engine layer actually consumes. A caller who assumes setting `context.metadata["priority"] = "high"` would somehow influence execution would be mistaken; it's inert by default unless some other, unreviewed part of the codebase specifically reads it.

## Q14: Trace how `to_request_state()`'s `request_identity` construction (`{"id": self.user_id or "unknown", "tenant_id": self.tenant_id or "", "roles": tuple(self.permissions)}`) differs from `core/agent.py`'s own `_request_identity_dict` helper — are they duplicated, and could they drift?

They are near-identical, separately-maintained implementations of the same idea: `core/agent.py`'s `_request_identity_dict(context)` (lines ~128–137) builds `{"id": context.user_id or "unknown", "tenant_id": context.tenant_id or "", "roles": tuple(context.permissions)}` guarded by the same "only if any identity field is actually set" check, while `ExecutionContext.to_request_state()` builds the identical dict shape inline as one branch of its larger multi-field method. This is real, unacknowledged duplication (unlike the `_ResumePayload` duplication elsewhere in the codebase, which at least has an explicit comment justifying it) — the two implementations happen to match today, but nothing enforces that they stay in sync if the identity dict's shape ever needs to change (e.g., adding a new field like `session_scope` to the identity payload would require updating both `_request_identity_dict` and `to_request_state()` identically, with no shared helper or test asserting equivalence between them).

## Q15: What is a concrete limitation of this module you'd fix given more time?

The clearest, highest-impact one is the native/LangGraph parity gap traced across Q2–Q4 and Q12: six of `ExecutionContext`'s override fields (`budget`, `deadline`, `cancellation_token`, `tool_policy`, `model_policy`, `memory_scope`) are silently inert on `runtime="native"`, with the only signal being a docstring comment rather than a runtime warning, type-level distinction, or test that would catch a caller relying on one of them under native. A more defensive design would have `Agent`/`_CompiledWorkflow` at least log a warning (or, more strictly, raise) when a caller passes a non-default value for one of these fields while running on `runtime="native"`, rather than silently dropping it — today, discovering this gap requires reading this exact file's docstrings, which is a real usability and correctness risk for anyone building on the native runtime without doing so.
