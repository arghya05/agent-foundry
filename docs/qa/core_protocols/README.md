# agent_foundry/core/protocols.py — Q&A

The framework's protocol seam: re-exports `Evaluator`/`EventBus`/`PolicyEngine` from their established homes, and defines `Tool`/`Memory`/`WorkflowEngine`/`StateStore` as `typing.Protocol` classes — structural contracts anything can satisfy without inheriting from a base class — with `WorkflowEngine` being the literal seam `Agent` dispatches through instead of hardcoding LangGraph.

## Q1: Why must `@runtime_checkable` be applied to every Protocol here? Walk through exactly what `isinstance(engine, WorkflowEngine)` does without it.

Python's `typing.Protocol` classes are, by default, purely static-analysis constructs — usable for type-checker validation (mypy/pyright checking that an object's shape matches) but not for runtime `isinstance()` checks, because a plain `Protocol` doesn't implement the `__instancecheck__` machinery needed to compare an arbitrary object's actual attributes against the protocol's declared members at runtime. The `WorkflowEngine` docstring states this precisely: "`@runtime_checkable` is required here — without it, `isinstance()` against a Protocol class raises `TypeError` instead of returning `False`, a real gotcha with Protocol classes." Concretely, without the decorator, `isinstance(some_engine, WorkflowEngine)` would raise `TypeError: Instance and class checks can only be used with @runtime_checkable protocols` at the call site — not silently return `False` the way a failed structural check might intuitively be expected to behave — which would break any code (tests, defensive assertions) that tries to verify an engine implementation's shape at runtime rather than only at type-check time. With `@runtime_checkable` applied, `isinstance()` instead checks for the *presence* of each declared method/attribute name on the object (see Q11 for what it does *not* check).

## Q2: `StateStore.load`'s declared parameter is named `run_id: str`, but every actual caller — `native_engine.py`'s `self._state_store.load(thread_id)` — passes what the rest of the codebase calls a `thread_id`, a distinct, longer-lived identifier from `ExecutionContext.run_id`. Is this a real naming bug, and when would it actually bite?

It's a genuine naming inconsistency, though a mostly harmless one at runtime today. `ExecutionContext.run_id` (in `core/execution_context.py`) is a fresh UUID generated per `ExecutionContext` construction — effectively per-request — while `thread_id` is the stable, potentially-reused identifier a conversation persists under across many separate calls/`run_id`s (via `resolved_thread_id()`'s `thread_id or session_id or run_id` fallback). `native_engine.py`'s `NativeEngine._state_for`/`_persist` calls `self._state_store.load(thread_id)`/`.save(thread_id, state)` positionally, so the parameter *name* declared in the `StateStore` Protocol (`run_id`) never actually matters for how the call succeeds — Python doesn't enforce keyword-argument name matching for a Protocol's structural check, and positional calls work regardless of what the callee's parameter is named. Where it *would* bite: any implementer of `StateStore` (a new `PostgresStateStore`/`RedisStateStore`, or a test double) who calls `.load(...)`/`.save(...)` using the Protocol's own declared keyword name — `store.load(run_id=some_value)` — would be passing a *thread_id* value under a parameter named as if it were a *run_id*, which is misleading to any reader or IDE tooltip trusting the Protocol's signature as documentation, even though it executes correctly. It's a genuine, if narrow, documentation-quality bug worth fixing (rename the parameter to `thread_id` to match its actual semantic meaning throughout the rest of the codebase).

## Q3: Why exactly 3 methods on `StateStore` (`load`/`save`/`delete`) rather than a 4th `checkpoint()` distinct from `save()`? Do you agree there's no scenario where "durable snapshot" needs to be distinct from "save now"?

The docstring's stated reasoning (lines ~80–83): "for a plain per-thread state dict there's no distinct 'durable snapshot' operation that isn't just 'save now,' so a fourth method would be a name with no different behavior behind it." This holds for the *current* usage pattern — `native_engine.py`'s `_raw()` calls `self._persist(state["thread_id"])` (which calls `state_store.save(...)`) at exactly the granularity a think/act/critique step completes, meaning every "save" already *is* a checkpoint in the sense that matters for resuming a paused or restarted conversation. Where this reasoning would need revisiting: if the framework ever wanted **versioned** or **point-in-time** state (e.g., "restore this thread to how it looked 3 turns ago" — the kind of capability `core/run.py`'s `replay()` explicitly disclaims as *not* provided today) rather than just "the current snapshot, overwritten on each save," a distinct `checkpoint()` that creates a new, addressable version rather than overwriting the single current one would be a genuinely different operation from `save()`. Given `replay()`'s own honest admission that per-step history isn't retained by any current checkpointer, the 3-method design is consistent with — not accidentally missing — the rest of the codebase's actual capabilities; adding a 4th method now would be speculative for a feature that doesn't exist elsewhere yet.

## Q4: Why is `StateStore` (and every Protocol in this module) declared with synchronous methods when the framework has an async surface (`Agent.arun`/`.astream`/`.aresume`)? What's the ceiling on this approach if a `StateStore` implementation is backed by slow network I/O?

The docstring is explicit (lines ~85–91): "this codebase's async surface... is a non-blocking layer wrapped around sync primitives (`asyncio.to_thread` for native, LangGraph's own off-thread scheduling for langgraph), not an async-native rewrite of the core loop; an async-only `StateStore` would be the one place that decision got silently reversed." Concretely, `Agent.arun()` (core/agent.py) either calls a real LangGraph graph's `.ainvoke()` directly, or — for native — wraps the entirely-synchronous `NativeEngine.run()` (which internally calls `state_store.load()`/`.save()` synchronously) inside `asyncio.to_thread(self.run, ...)`, moving the whole blocking call chain onto a thread-pool worker thread so the event loop itself isn't blocked. The ceiling: a `StateStore` backed by genuinely slow network I/O (a distant Postgres/Redis instance under load) blocks whichever thread is executing it — for native's `arun()` path, that's one of `asyncio.to_thread`'s limited default thread-pool workers, meaning enough concurrent slow-`StateStore` requests could exhaust the pool's available threads and cause unrelated concurrent `arun()` calls to queue up waiting for a free worker thread, a real (if generic to `asyncio.to_thread`-based designs) scalability ceiling that a native `async def load()`/`save()` interface wouldn't have.

## Q5: `WorkflowEngine.build(self, spec: Any, ...)` types `spec` as `Any`, even though every real implementation (`LangGraphWorkflowEngine`, `NativeWorkflowEngine` in `core/engines.py`) treats it as an `AgentConfig`. Why the loose typing, and what do you lose?

Typing `spec: Any` rather than `spec: AgentConfig` keeps the Protocol itself decoupled from any specific config shape — a hypothetical future `WorkflowEngine` implementation that wanted to accept something other than `AgentConfig` (say, a different spec type entirely for a fundamentally different execution model) wouldn't violate the Protocol's declared signature by doing so, since `Any` imposes no constraint. What's lost is static type-checking value: nothing about the `WorkflowEngine` Protocol itself would catch a new engine implementation whose `build()` actually expects, say, a `dict` instead of an `AgentConfig` — a mismatch that would only surface at runtime, the first time `Agent.__init__`'s `RUNTIMES[runtime].build(self.config, checkpointer=checkpointer)` call (core/agent.py, line ~438) actually passes a real `AgentConfig` object to that engine and it fails to interpret it correctly. Since both real implementations agree in practice (both treat `spec` as `AgentConfig`), this looseness is currently cosmetic rather than a live problem, but it does mean the Protocol's type signature alone can't be relied upon to guarantee input-shape compatibility across implementations — that guarantee exists only by convention and by `Agent`'s own single call site always passing an `AgentConfig`.

## Q6: `Tool` and `Memory` are described as "restating" `ToolSpec`'s and `MemoryStore`'s own established shapes as Protocols, added after those concrete classes already existed. What's the risk that the two drift out of sync over time — e.g., someone adds a method to `MemoryStore` and forgets to add it here?

Since `Memory` (lines ~36–45) declares exactly four methods — `get_profile`, `update_profile`, `append_turn`, `history` — copied from `MemoryStore`'s real public surface rather than `MemoryStore` being defined *to* implement this Protocol, there's no structural mechanism (no `class MemoryStore(Memory):` inheritance relationship, and Protocols don't require one) forcing the two to stay in sync. If `context.py`'s real `MemoryStore` later grows a fifth public method that `orchestration.py`'s node closures start relying on, nothing here would catch the omission automatically — `runtime_checkable`'s `isinstance()` check only verifies the methods *currently* declared on `Memory` are present, so a hand-written duck-typed memory implementation that satisfies today's four-method `Memory` Protocol but not a future fifth method would still pass `isinstance(candidate, Memory)` even after `MemoryStore` itself evolved past it — silently accepting an incomplete implementation. The only real defense against this drift is disciplined manual review whenever `MemoryStore`'s actual API changes, since nothing here is generated from or validated against `MemoryStore`'s real definition.

## Q7: Concretely, what does `core.agent._coerce_tools` gain from `Tool` being a `Protocol` rather than requiring a `ToolSpec` subclass? Walk through a caller handing in a plain hand-written class.

`core/agent.py`'s `_coerce_tools` (lines ~92–105) checks `elif isinstance(t, Tool): registry.register(ToolSpec(name=t.name, description=t.description, parameters=t.parameters, fn=t.fn))` — because `Tool` is `@runtime_checkable`, this `isinstance` check succeeds for **any** object exposing `.name`, `.description`, `.parameters`, `.fn` attributes with roughly the right shapes, regardless of whether that object has any inheritance relationship to `ToolSpec` at all. A caller could define `class MyCustomTool: name = "search"; description = "..."; parameters = {...}; fn = my_search_fn` — a plain class with zero imports from this framework — and pass an instance of it directly into `Agent(tools=[MyCustomTool()])`; `_coerce_tools` would accept it via the `Tool` Protocol check and repackage it into a real `ToolSpec` for internal use. Without `Tool` as a structural Protocol, the same caller would either need to explicitly subclass `ToolSpec` (a dataclass, awkward to subclass meaningfully) or construct a real `ToolSpec(...)` instance directly — the Protocol exists specifically to let third-party or hand-rolled tool objects integrate without requiring a hard dependency/import relationship on this framework's own `ToolSpec` class.

## Q8: Why does `core/protocols.py` re-export `Evaluator`, `EventBus`, `PolicyEngine` from their "established" modules rather than defining them directly here, or simply letting callers import them from `eval.py`/`events.py`/`policy_engine.py` directly?

The module docstring frames this file as "the framework's protocol seam" — a single, discoverable index of every structural contract in the system, regardless of which module each concrete implementation actually lives in. A caller (or a new contributor exploring the codebase) who wants to know "what are all the pluggable interfaces this framework exposes" can read `core/protocols.py`'s `__all__` list (`["Evaluator", "EventBus", "PolicyEngine", "Tool", "Memory", "WorkflowEngine", "StateStore"]`, line ~21) as a complete map, rather than needing to already know that `Evaluator` lives in `eval.py`, `EventBus` in `events.py`, and `PolicyEngine` in `policy_engine.py` specifically. The re-export costs nothing functionally (Python re-exports are just name bindings — `from ..eval import Evaluator` makes `core.protocols.Evaluator` and `eval.Evaluator` the exact same object), so this is purely an organizational/discoverability convenience, not a new abstraction layer — existing callers that already import directly from `eval.py`/`events.py`/`policy_engine.py` are entirely unaffected and don't need to change.

## Q9: `WorkflowEngine.resume()`'s signature includes `decision: dict[str, Any] | None = None` alongside `approved: bool`. Trace how `decision`'s extra keys actually get used — is this an intentional escape hatch, or a sign the resume payload shape is under-specified?

Per this Protocol's own docstring reference (and confirmed in `core/engines.py`'s `_invoke_resume`), `decision`'s extra keys are merged into the payload dict (`{"approved": approved, **(decision or {})}`) that ultimately reaches either a real LangGraph `Command(resume=payload)` or the native `_ResumePayload(resume=payload)` shim — but both `native_engine.py`'s `_resume_locked`/`_act` and (per the docstring's own characterization) `orchestration.py`'s `make_act_node`/`make_critique_node` only ever read the `"approved"` key off that payload for their own built-in approval/escalation logic; nothing in either engine's core control flow consumes any other key `decision` might carry. This is genuinely an intentional escape hatch, not an under-specification bug: it exists specifically so a caller's own tool implementation or downstream logic (invoked as part of the resumed turn) can read additional context — a clarification answer's actual text, a payment confirmation ID, an external event's full payload — off the same resume call without the framework needing to know or validate what those extra fields mean. The trade-off is that this makes the "resume payload" an intentionally open, unvalidated dict beyond the one field (`approved`) the framework itself understands — a caller relying on a specific extra key being present has no Protocol-level guarantee that it will be, since `WorkflowEngine.resume()`'s signature only requires `dict[str, Any] | None`, not any particular shape within it.

## Q10: If you were adding a Temporal-backed `WorkflowEngine`, which of the four Protocol methods (`build`/`run`/`stream`/`resume`) would be hardest to implement faithfully, and why?

`stream()` is the hardest to reconcile faithfully. `run()` and `resume()` both return a single, synchronous `RunResult` — a Temporal-backed implementation could, in principle, block on a Temporal workflow's execution and translate its final result into a `RunResult`, even if that means giving up some of Temporal's own async-native benefits for the duration of the call (an acceptable, if imperfect, trade-off, since the existing engines are already synchronous in this same sense). `stream()`, however, is expected to be a genuinely **incremental** Python generator/iterator yielding intermediate states as execution progresses (per `core_native_engine`'s Q&A on `stream_run`'s step-by-step yielding, matching LangGraph's `stream_mode="values"`) — bridging Temporal's actual progress-reporting mechanism (which typically involves polling workflow history or subscribing to signals from outside the workflow, not a natural Python generator yielding from inside a synchronous call) into that exact calling convention would require nontrivial bridging code, likely similar in spirit to `core/agent.py`'s own worker-thread-plus-queue bridge for `astream()`, but adapted to Temporal's polling-based progress model rather than a simple synchronous generator.

## Q11: `runtime_checkable` Protocols only verify the *presence* of matching method/attribute names, not their signatures or types. Could a class satisfy `isinstance(x, WorkflowEngine)` while having a completely incompatible `build()` — say, one that takes different arguments entirely? What's the practical consequence?

Yes — `runtime_checkable`'s `isinstance()` check inspects only whether the candidate object has callable/attribute members with the *matching names* (`build`, `run`, `stream`, `resume`), never their parameter lists, return types, or even whether they're actually callable with the arguments this Protocol declares. A class defining `def build(self) -> None: ...` (zero parameters, wrong return type) would still pass `isinstance(instance, WorkflowEngine)`, because Python's structural `runtime_checkable` check simply doesn't inspect signatures — that's a Protocol limitation independent of anything specific to this codebase. The practical consequence here: `Agent.__init__`'s implicit trust in `RUNTIMES[runtime]` (core/agent.py, line ~438, `RUNTIMES[runtime].build(self.config, checkpointer=checkpointer)`) has **no runtime protection** against a malformed third-party `WorkflowEngine` registered into `RUNTIMES` with an incompatible `build()` signature — the failure would only surface as a `TypeError: build() takes 1 positional argument but 2 were given` (or similar) at the actual call site, not at registration time or via any `isinstance` check anywhere in this codebase (notably, nothing in `core/agent.py` or `core/engines.py` actually calls `isinstance(engine, WorkflowEngine)` at all — the Protocol's `runtime_checkable` capability is available but not exercised as a guard anywhere in the reviewed files).

## Q12: `StateStore.delete()` has no caller anywhere across the seven core files reviewed. Is this dead API surface, or intentional forward-looking completeness?

Across `core/native_engine.py` (the only file among the seven that actually consumes a `StateStore`), `NativeEngine` calls `state_store.load(...)` (in `_state_for`) and `state_store.save(...)` (in `_persist`), but never `.delete(...)` anywhere in its own code. This strongly suggests `delete()` is forward-looking/completeness-oriented rather than dead: the docstring names three real implementations elsewhere in the codebase — `core/state_store.py`'s `MemoryStateStore`/`PostgresStateStore` and `distributed.py`'s `RedisStateStore` — and a natural real-world need for `.delete()` exists even if `NativeEngine` itself never calls it: an operator wanting to purge a completed or abandoned conversation's persisted state (for storage cost, compliance/data-retention requirements, or GDPR-style deletion requests) would need exactly this method, called from *outside* `NativeEngine`'s own control flow (e.g., an admin/ops tool operating directly against a `StateStore` instance). It's reasonable API completeness for external implementers and operators, not evidence of an unused abstraction — but it does mean this Protocol method's correctness (e.g., whether `PostgresStateStore.delete()` actually behaves as expected) isn't exercised by anything in the core execution path itself, only by whatever separate test suite covers the concrete `StateStore` implementations directly.

## Q13: Why `typing.Protocol` (structural typing) rather than `abc.ABC` (nominal typing, requiring explicit inheritance) for `WorkflowEngine`, given neither `NativeWorkflowEngine` nor `LangGraphWorkflowEngine` (in `core/engines.py`) actually inherits from it anywhere?

Confirmed by inspection: `class LangGraphWorkflowEngine:` and `class NativeWorkflowEngine:` (core/engines.py) both declare no base class at all — they satisfy `WorkflowEngine` purely structurally, by happening to implement matching method signatures, with zero import-time coupling to `core/protocols.py`. Had `WorkflowEngine` been an `abc.ABC` instead, both concrete classes would need to explicitly `class NativeWorkflowEngine(WorkflowEngine):` and implement every `@abstractmethod`, which would (a) force `core/engines.py` to import from `core/protocols.py` even though nothing about either engine's actual logic needs anything from that module, and (b) make it impossible for a completely external, third-party engine implementation (one that has never even heard of `core/protocols.py`) to be a valid `WorkflowEngine` without explicitly subclassing it first. `Protocol`'s structural typing means the Protocol exists purely as a **description** of a shape — useful for static type-checking call sites like `Agent.__init__` (`RUNTIMES[runtime].build(...)`) and for optional runtime verification via `isinstance()` (Q1) — without imposing any inheritance requirement on implementers, which fits this codebase's stated extensibility goal ("adding a third backend... means implementing `WorkflowEngine`," phrased as implementing a *shape*, not subclassing a *base class*).

## Q14: Do any of the seven core files reviewed actually call `Memory`'s `append_turn` or `history` methods, or only `get_profile`/`update_profile`? What does that suggest about how this Protocol was derived?

Across the seven files, `native_engine.py`'s `_think` method is the only place that touches `config.memory` directly, and it calls `config.memory.working.setdefault(...)`, `config.memory.semantic.search(...)`, and `config.memory.get_profile(resolved_user_id)` — never `append_turn` or `history`. This suggests the `Memory` Protocol here was derived by reading `context.MemoryStore`'s **full public surface** (all four methods it actually exposes) rather than being narrowly scoped to only what these seven core files happen to call — `append_turn`/`history` are presumably exercised by `orchestration.py`'s node closures or other parts of the codebase not reviewed here (the docstring itself says these four are "the four operations orchestration.py's node closures actually call on `AgentConfig.memory`," explicitly attributing the full set to `orchestration.py`, not to `native_engine.py`). This is a reasonable design: a Protocol scoped only to what one particular engine (native) happens to use would be an incomplete description of what "a valid `Memory` implementation" needs to support across the *whole* framework, including the LangGraph engine's own node logic.

## Q15: What is a concrete limitation of this module you'd fix given more time?

The `StateStore.load`'s misleading `run_id` parameter name (Q2) is the smallest but most concretely fixable issue — a one-line rename to `thread_id` (matching every actual caller's semantics) that would remove a genuine, if narrow, documentation-trust hazard for anyone implementing a new `StateStore` backend by reading this Protocol's signature as their guide. More structurally, the complete absence of any `isinstance(engine, WorkflowEngine)` check anywhere in `core/agent.py`'s actual `RUNTIMES[runtime].build(...)` call path (Q11) means the `runtime_checkable` capability this Protocol deliberately supports is unused as an actual runtime safety net — adding even a single `assert isinstance(engine, WorkflowEngine)` at the point a new engine is registered into `RUNTIMES` would catch a malformed implementation (missing a required method entirely) immediately at startup, rather than deep inside whatever code path first happens to call the missing method.
