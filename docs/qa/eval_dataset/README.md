# agent_foundry/eval_dataset.py — Q&A

A thin, purely additive layer on top of `core/evalgate.py`'s `EvalCase`/`Scorecard`/`run_eval`: `EvalDataset` gives a flat list of eval cases a name and version, and `BaselineScorecard` + `save_baseline`/`load_baseline` persist one run's `Scorecard` metrics to disk so the next run can regression-check against it via `Scorecard.compare_to()`.

## Q1: `BaselineScorecard` duplicates seven fields from `Scorecard` as a separate frozen dataclass instead of just pickling/reloading a real `Scorecard`. Why not reload the actual thing?

`Scorecard.cases` is a `list[CaseResult]`, and each `CaseResult` holds a full `RunResult` (per `core/evalgate.py`'s `run_eval`, which appends `run_result=result` for every case) — that's the agent's entire message history, tool calls, and possibly large intermediate state for every case in the dataset. The docstring for `BaselineScorecard` (lines 20-24) is explicit: this is "not cheaply serializable," so round-tripping a full `Scorecard` through JSON on disk would mean persisting and reloading potentially large, deeply nested run traces just to later read seven scalar properties off it. Instead, `BaselineScorecard` stores exactly the seven properties `Scorecard.compare_to()` actually reads via `getattr` — `task_success_rate`, `tool_accuracy_rate`, `trajectory_accuracy_rate`, `groundedness_avg`, `p95_latency_ms`, `avg_cost_usd`, `error_rate` — and nothing else. This works because `compare_to()` (in `core/evalgate.py`) is typed against `ScorecardLike`, a `Protocol` that only demands those seven properties exist; a real `Scorecard` satisfies it structurally, and so does `BaselineScorecard`, which is a duck-typed stand-in with no `.cases` at all. It's a clean case of "persist only what the consumer actually needs," not the full domain object.

## Q2: Walk through what happens, end to end, when `EvalDataset.save_baseline(scorecard, directory)` is called after a scorecard's `groundedness_avg` is `None` (no case in the run used a groundedness KPI), and then `load_baseline` is called later and its result is passed to `compare_to()`.

`save_baseline` (line 63) writes exactly seven keys into the JSON file including `"groundedness_avg": scorecard.groundedness_avg` — if that's `None`, `json.dumps` serializes it as JSON `null`, not omitted. `load_baseline` (line 78) later does `BaselineScorecard(**json.loads(path.read_text()))`, so `groundedness_avg` deserializes back to Python `None` — round-trips cleanly since `BaselineScorecard.groundedness_avg` is typed `float | None`. When that `BaselineScorecard` is handed to a *new* `Scorecard.compare_to(baseline)` call, `compare_to()`'s logic (in `core/evalgate.py`, `if self.groundedness_avg is not None and baseline.groundedness_avg is not None`) means the `groundedness_avg` delta is simply omitted from the returned deltas dict whenever either side is `None` — so a dataset that never used groundedness KPIs produces a clean comparison across the other six metrics with no crash and no misleading `None - None` or `float - None` arithmetic. The design is deliberately symmetric: `None` is a real, meaningful "not applicable" value here, not a missing-data placeholder that needs defaulting to `0.0` (which would falsely suggest "worse" or "better" depending on comparison direction).

## Q3: What happens if `EvalDataset.load(path)` is pointed at a file that's the *older* flat-list shape (`[{...}, {...}]`) instead of the versioned `{"name":..., "version":..., "cases":[...]}` shape?

`load()` (line 42-44) does `data = json.loads(...)` then unconditionally accesses `data["name"]`, `data["version"]`, `data["cases"]` — if `data` is actually a bare list (the old flat shape `cli.py`'s `cmd_eval` has always accepted), `data["name"]` raises `TypeError: list indices must be integers or slices, not str` immediately. `load()` itself does not use `looks_versioned()` to gracefully handle both shapes — that check is a separate static method (`EvalDataset.looks_versioned(data)`, lines 46-52) that a *caller* (presumably `cli.py`) is expected to invoke first to decide whether to call `EvalDataset.load()` at all or fall back to the older flat-list loading path directly. This is a real caller responsibility, not an automatic fallback: `EvalDataset.load()` assumes the versioned shape unconditionally and will raise a somewhat cryptic `TypeError` (not a clear "this looks like the old format" message) if handed the wrong one. Anyone integrating a new dataset-loading call site has to remember to call `looks_versioned()` themselves first — the module doesn't enforce this pairing.

## Q4: Why does `to_cases()` need to special-case `forbidden_tools`, converting it from whatever JSON gave it (a list) into a `frozenset`, instead of just doing `EvalCase(**raw)` directly?

`EvalCase.forbidden_tools` (in `core/evalgate.py`) is typed `frozenset[str]`, but JSON has no set/frozenset type — a JSON array of tool names round-trips as a Python `list`, not a `frozenset`. `to_cases()` (lines 54-61) checks `if "forbidden_tools" in raw and not isinstance(raw["forbidden_tools"], frozenset)` and converts it in place before constructing `EvalCase(**raw)`. Without this, `EvalCase(forbidden_tools=["send_email", "delete_user"])` would silently succeed (Python dataclasses don't enforce runtime type checks on field types by default) but store a `list` where a `frozenset` was expected — anywhere downstream that relies on `frozenset`-specific behavior (fast `in` membership checks, hashability, or set operations like `&`/`-` against another set of tool names) would break, either with a `TypeError` on set operations or, worse, silently work for membership checks (`in` works on lists too) while being subtly wrong for anything relying on hashability or set semantics. The `not isinstance(..., frozenset)` guard also means this is idempotent — calling `to_cases()` on already-frozenset data (e.g. if a case dict came from somewhere other than raw JSON) doesn't redundantly reconstruct it.

## Q5: `to_cases()` does `raw = dict(raw)` before mutating it. Why the defensive copy, and what would break without it?

`self.cases` is `list[dict[str, Any]]` — the same list of dicts is stored on the `EvalDataset` instance and could be iterated by `to_cases()` multiple times (nothing prevents calling `.to_cases()` twice on the same dataset, e.g. once for a dry-run preview and once for the real eval execution). If `to_cases()` mutated `raw` in place (the dict from `self.cases` directly) rather than a copy, the *first* call would permanently replace `raw["forbidden_tools"]` with a `frozenset` inside `self.cases` itself — which happens to be harmless for the specific `forbidden_tools` conversion since the `isinstance` guard makes it idempotent either way, but it's still mutating a data structure the caller might reasonably expect `to_cases()` to leave untouched (surprising if `self.cases` is later re-serialized via `json.dumps` expecting plain-JSON-compatible types — a `frozenset` isn't JSON-serializable, so a subsequent `json.dumps(dataset.cases)` would raise `TypeError: Object of type frozenset is not JSON serializable` after the first `to_cases()` call silently poisoned the stored data). The `dict(raw)` shallow copy avoids this entirely — `self.cases`' own dicts are never touched, only the copies handed to each `EvalCase(**raw)` constructor call.

## Q6: What's the actual regression-detection rigor here — is comparing a scorecard's seven scalar metrics against one saved baseline via subtraction (`compare_to()`) statistically sound for CI gating?

It's a simple delta, not a statistical test — `compare_to()` computes `self.<metric> - baseline.<metric>` for each of the seven metrics with no confidence interval, no variance estimate, no minimum-sample-size requirement, and no significance threshold baked into `eval_dataset.py`/`core/evalgate.py` itself (any "is this delta meaningful" judgment call is left entirely to whatever caller consumes the deltas dict, e.g. a CLI command deciding to fail CI if `task_success_rate` dropped by more than some hardcoded percentage). This means a baseline computed from a 5-case eval dataset and a fresh run also over 5 cases could show a swing from `task_success_rate=1.0` to `0.8` purely from one flaky case — statistically indistinguishable from noise — but `compare_to()` reports it as a flat `-0.2` delta with no framing of whether that's a real regression or sampling variance. This is a reasonable, honest starting point for regression detection in an eval harness that's meant to be a developer-loop signal (did things get obviously worse) but is not rigorous enough on its own to gate a release without human judgment or a much larger, statistically powered eval dataset with a real significance test layered on top — which this module doesn't attempt to provide.

## Q7: How does `EvalDataset`'s versioning (`name` + `version` + a baseline file per `{name}-{version}`) compare to how MLflow or W&B track eval/experiment history?

MLflow's tracking server and W&B's run history are both built around a persistent, queryable backend (a tracking server / database, or a hosted service) that stores every run's metrics, parameters, and artifacts indefinitely, with a UI for comparing arbitrary runs against each other, not just "the current run vs. one saved baseline." `EvalDataset`'s baseline mechanism (`save_baseline`/`load_baseline`, lines 63-83) is deliberately much narrower: exactly one baseline file per `(name, version)` pair, stored as a flat JSON file at `{directory}/{name}-{version}.baseline.json`, and calling `save_baseline` again for the same name/version simply overwrites the previous baseline (`path.write_text(...)` has no append/versioning-within-a-version semantics) — there is no history of *previous* baselines, no way to compare against "three baselines ago," and no built-in UI. This is the tradeoff of a file-based, git-friendly design (a baseline file can be committed alongside the dataset and diffed in a PR) versus a database-backed one (richer history, querying, visualization, but requiring infrastructure). For a small-to-medium eval suite checked into source control, the file-based approach is arguably a better fit for CI regression-gating (the baseline literally lives in the repo, versioned by git itself); it just doesn't attempt to be a general experiment-tracking platform the way MLflow/W&B are.

## Q8: What happens if `save_baseline` is called with a `directory` that doesn't exist yet, versus `load_baseline` called against a directory that was never created?

`save_baseline` explicitly handles the missing-directory case: `directory = Path(directory); directory.mkdir(parents=True, exist_ok=True)` (lines 64-65) creates the full directory tree if needed, with `exist_ok=True` making repeated calls safe (no `FileExistsError` on a second save). `load_baseline`, by contrast, does no directory creation — it builds `path = Path(directory) / f"{name}-{version}.baseline.json"` and immediately checks `if not path.exists(): return None` (lines 80-81). So the read path degrades gracefully (a nonexistent directory just means the path doesn't exist, and the function returns `None` — "no baseline yet" — rather than raising `FileNotFoundError`), which is the right behavior for a first-ever eval run where no baseline exists. The asymmetry (write creates, read doesn't need to and correctly doesn't try) is appropriate: there's never a legitimate reason to create a directory just to discover nothing's in it.

## Q9: `EvalDataset.cases` is typed `list[dict[str, Any]]` rather than `list[EvalCase]`. Why keep the raw dict representation as the dataclass's primary storage instead of eagerly converting to `EvalCase` objects at `load()` time?

Two reasons follow directly from the code. First, `EvalCase` objects aren't JSON-serializable in general (they can hold `kpi: KPI | None`, a `Callable`-bearing object, and `context: ExecutionContext | None`) — keeping `cases` as plain dicts is what makes `EvalDataset` itself trivially round-trippable through `json.loads`/`json.dumps` without needing a custom encoder. Second, the module docstring notes this dict shape is "the same shape `cli.py`'s `cmd_eval` already loads flat" — `EvalDataset` is explicitly designed as an additive wrapper (name + version + baseline persistence) around an existing flat-list convention `cli.py` depends on, not a replacement representation; converting eagerly to `EvalCase` at load time would break that compatibility and force every consumer of `dataset.cases` (if any exist beyond `to_cases()`) to deal with `EvalCase` objects instead of plain dicts. The conversion to real `EvalCase` objects only happens on demand via `to_cases()`, right before they're needed for actual execution (`run_eval` takes `list[EvalCase]`) — lazy, and only paid for by callers who actually need it.

## Q10: If a case dict in the JSON file has a key that isn't a valid `EvalCase` field (a typo, e.g. `"exepcted_tool"` instead of `"expected_tool"`), what happens when `to_cases()` runs?

`EvalCase(**raw)` is a direct dataclass constructor call with the dict unpacked as keyword arguments — Python dataclasses raise `TypeError: __init__() got an unexpected keyword argument 'exepcted_tool'` immediately for any key that doesn't match a declared field. There's no schema validation step in `eval_dataset.py` before this point that would catch the typo earlier or produce a more helpful error message (e.g. "did you mean `expected_tool`?", or a list of valid fields) — the failure surfaces as a fairly generic Python `TypeError` at whatever point `to_cases()` is called, which could be well after the dataset file was loaded and parsed successfully (`EvalDataset.load()` itself doesn't touch `EvalCase` at all, so a malformed case dict passes `load()` silently and only blows up later in `to_cases()`). This is a real rough edge for hand-authored eval dataset JSON files: errors surface late and with a Python-internals-flavored message rather than at parse time with a dataset-specific one.

## Q11: What happens if a case dict includes `"forbidden_tools"` as something that isn't a list at all — say, a single string `"send_email"` instead of `["send_email"]` — due to a hand-authoring mistake?

`to_cases()`'s check is `if "forbidden_tools" in raw and not isinstance(raw["forbidden_tools"], frozenset)` — a plain string is not a `frozenset`, so the guard passes and `raw["forbidden_tools"] = frozenset(raw["forbidden_tools"])` executes. `frozenset()` on a string doesn't raise; it iterates the string *character by character*, producing `frozenset({'s', 'e', 'n', 'd', '_', 'm', 'a', 'i', 'l'})` — a set of individual letters, not the intended single-tool-name set. This is a silent data-corruption bug: no exception, no warning, just a completely wrong `forbidden_tools` set that would make the eval case's trajectory-forbidden-tools check (in `core/evalgate.py`) effectively meaningless (checking whether individual character-strings like `"s"` appear in the actual tool-call sequence, which they never will, so the forbidden-tools check silently never fires). This is exactly the kind of malformed-example failure mode worth testing for explicitly — `to_cases()` has no type validation beyond the narrow `frozenset`-conversion guard, so any hand-authored JSON dataset with this class of mistake fails silently rather than loudly.

## Q12: Why does `BaselineScorecard` use `@dataclass(frozen=True)` specifically, rather than a plain mutable dataclass?

A loaded baseline is meant to be read-only reference data — it represents "what the metrics were at some past, already-completed run," and nothing in the eval-comparison flow (`compare_to()` only reads via `getattr`) has any legitimate reason to mutate it after loading. `frozen=True` makes accidental mutation (e.g. a caller doing `baseline.task_success_rate = 1.0` while debugging, or some future code path that tries to "correct" a baseline value in place) raise `FrozenInstanceError` immediately rather than silently succeeding and corrupting what's supposed to be an immutable historical snapshot for the duration of that comparison. It also signals intent to future maintainers: this class exists purely to be constructed once (via `load_baseline`) and read, never edited — the type itself documents that usage pattern.

## Q13: How would you extend `EvalDataset` to support comparing against the *previous N* baselines (a trend line) rather than just the single most recent one, given the current file-naming scheme?

The current scheme (`{name}-{version}.baseline.json`) hardcodes a single file per `(name, version)` pair, so every `save_baseline` call for the same name/version is a destructive overwrite — there is no built-in history. A minimal extension consistent with the existing design: change `save_baseline` to write a timestamped file (e.g. `{name}-{version}.{timestamp}.baseline.json`) alongside — or instead of — the canonical `{name}-{version}.baseline.json`, and add a method like `load_baseline_history(directory, name, version, limit=N)` that globs for and sorts the timestamped files. This preserves the simple single-baseline API (`load_baseline` keeps returning "the latest" for the common CI-gating case) while adding an opt-in trend view for anyone who wants it — without needing a database, staying consistent with the module's existing file-based, git-diffable philosophy rather than introducing new infrastructure.

## Q14: `looks_versioned()` is a `@staticmethod` that only checks `isinstance(data, dict) and "cases" in data`. What's a dataset file that would fool this check into a false positive or false negative?

False positive: any dict that happens to have a `"cases"` key for an unrelated reason — e.g. a malformed or hand-edited file like `{"cases": "not actually a list"}` — passes `looks_versioned()` (returns `True`) even though it isn't a well-formed versioned dataset at all; `EvalDataset.load()` would then proceed to `data["name"]`/`data["version"]` and raise `KeyError` if those are genuinely missing, or worse, construct an `EvalDataset` with a non-list `cases` field that only blows up later in `to_cases()`'s `for raw in self.cases` iteration (iterating over a string would treat each character as a "case," failing incomprehensibly at `dict(raw)` since a string isn't dict-convertible in the way intended — `dict("x")` actually raises `ValueError`, so this would surface as a `ValueError` far from the actual root cause). False negative: this check can't happen for the legitimate old flat-list shape (a bare `list` correctly returns `False`, by design), so there's no real false-negative case in normal usage — the check is narrowly correct for its one intended purpose (versioned-dict vs. flat-list) but offers zero structural validation beyond that single key's presence.

## Q15: What's a limitation of `eval_dataset.py` you'd fix given more time?

The clearest one is the complete absence of schema validation on load — `EvalDataset.load()` and `to_cases()` both trust the JSON file's shape entirely, and as Q10/Q11 show, both a missing/misspelled field and a wrong-type field (a string where a list was expected) fail either with a generic Python `TypeError` at an unhelpful point in the code, or — worse, in the `forbidden_tools`-as-string case — fail completely silently with corrupted data and no error at all. Given more time, I'd add an explicit validation pass in `to_cases()` (or a separate `validate()` method) that checks every case dict's keys against `EvalCase`'s actual dataclass fields and every known list-typed field's actual runtime type before construction, raising one clear, dataset-specific error (naming the case index and the bad field) instead of relying on whatever generic exception a raw `EvalCase(**raw)` or `frozenset(raw[...])` call happens to produce. A close second: baseline history (Q13) — a single overwritable baseline file is fine for "did this run regress vs. last time" but can't answer "is this metric trending down over the last 10 runs," which is a genuinely useful question a hand-authored eval suite would eventually want.
