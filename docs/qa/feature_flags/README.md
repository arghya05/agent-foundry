# agent_foundry/feature_flags.py — Q&A

A `FeatureFlagProvider` Protocol plus one zero-dependency reference implementation, `StaticFeatureFlagProvider`, giving on/off booleans and stable-hash-bucketed percentage rollouts (`is_enabled(flag, *, identity=None, default=False)`) for gating agent behavior — prompt versions, new tools, new topologies — without a code deploy.

## Q1: `StaticFeatureFlagProvider.is_enabled` (line 29) buckets a percentage rollout via `bucket_key = f"{flag}:{identity.id if identity else 'anonymous'}"` then `int(hashlib.sha256(bucket_key.encode()).hexdigest(), 16) % 100`. Why SHA-256 specifically, rather than Python's builtin `hash()`, and what would break if `hash()` were used instead?

Python's builtin `hash()` for strings is deliberately randomized per-process via `PYTHONHASHSEED` (a security mitigation against hash-flooding DoS attacks, enabled by default since Python 3.3) — calling `hash("user-42:my-flag")` in one process run and the same string in a different process run (a restart, a new worker in a multi-process deployment) produces *different* values. If `is_enabled` used `hash()` instead of `hashlib.sha256`, the same identity could land on different sides of a percentage rollout depending on which process/worker happened to handle the request, and would definitely flip after every restart — completely defeating the module's own stated goal, quoted directly in the docstring: "bucketed by a stable hash of (flag, identity), so the same identity always lands on the same side of the rollout instead of flapping between calls." `hashlib.sha256` is a fixed, deterministic, cryptographic hash with no process-dependent seed, so the same `bucket_key` string always produces the same digest and therefore the same bucket, both within a process and across restarts, and consistently across every replica in a multi-instance deployment — which is the actual requirement here, not resistance to hash-collision attacks (this isn't a security use of SHA-256 at all, just a convenient source of a uniformly-distributed, stable integer).

## Q2: The bucketing math is `int(hashlib.sha256(bucket_key.encode()).hexdigest(), 16) % 100`. Is the resulting distribution actually uniform across 0-99, and does `% 100` on a 256-bit hash introduce meaningful bias?

The distribution is close enough to uniform for this use case, though not perfectly uniform in a strict mathematical sense: SHA-256 produces a 256-bit integer (a number with roughly $2^{256}$ possible values), and $2^{256}$ is not an exact multiple of 100, so `% 100` technically maps slightly more of the input space to some remainders than others. However, the bias introduced is astronomically small — on the order of $100/2^{256}$, utterly negligible for any practical rollout-percentage purpose (nobody will notice bucket 37 being infinitesimally more likely than bucket 42 out of $2^{256}$ possible hash outputs). This is a case where a security-minded reviewer should recognize the difference between "technically not perfectly uniform" (true, and true of essentially every `hash % N` scheme where N doesn't evenly divide the hash space) and "materially exploitable or noticeably skewed" (false here) — flagging modulo bias as a real concern only matters when N is a large fraction of the hash space (e.g., hashing into a 128-value space and taking `% 100`), which isn't the case with a 256-bit digest and `% 100`.

## Q3: Can a user (or an agent identity) manipulate which side of a rollout they land on? Walk through what would need to be true for `identity.id` to be attacker-influenced, and what the consequence would be.

`bucket_key` is built purely from `flag` (a string chosen by whoever calls `is_enabled`, not the end user) and `identity.id` (from `contracts.py`'s `Identity` dataclass) — if an attacker could choose or influence their own `identity.id` value arbitrarily (e.g., a system that lets a caller self-report their own identity string without server-side verification, or that derives `identity.id` from some attacker-controlled request field), they could brute-force different `id` values offline, precompute which ones hash into the "enabled" bucket for a target `flag`, and then present that specific `id` to guarantee landing on the desired side of a rollout — completely defeating the purpose of a percentage rollout as a controlled, statistically-representative canary. This isn't a vulnerability in `feature_flags.py` itself, though — it's entirely dependent on how `Identity` objects are constructed and authenticated upstream (outside this file); `StaticFeatureFlagProvider` has no way to know or verify that `identity.id` is a trustworthy, non-attacker-chosen value, and its bucketing math offers no defense against a caller who can freely choose their own `id`. The broader lesson: percentage-rollout bucketing based on a hash of an identity value is only as tamper-resistant as the identity system issuing that value — if identities are self-declared and unauthenticated anywhere in the stack, gating a security-relevant feature flag (e.g., "is the new sandbox-escape-blocked code path enabled for this user") on an unauthenticated identity's percentage bucket would be a real exploitable weakness.

## Q4: `is_enabled` treats a missing `identity` as the literal string `"anonymous"` (`identity.id if identity else 'anonymous'`, line 35). What's the consequence of every anonymous caller sharing that exact literal string for percentage-rollout bucketing?

Every call to `is_enabled(flag, identity=None)` for the same `flag` produces the exact same `bucket_key` (`f"{flag}:anonymous"`), and therefore the exact same SHA-256 digest and the exact same bucket — meaning **all anonymous callers get identical treatment for any given flag**: either 100% of anonymous traffic is inside a 30%-rollout flag, or 0% of it is, with no actual distribution across the population of anonymous callers at all. This is a correctness gap worth flagging precisely because it's easy to miss: a percentage rollout implicitly promises "roughly N% of traffic sees this," but for any code path where `identity` is legitimately `None` (an unauthenticated request, a system-internal call with no identity context), the rollout percentage becomes meaningless — it degenerates to a single coin-flip made once (whichever bucket `"flagname:anonymous"` happens to hash into) that then applies uniformly to every anonymous caller forever, rather than each anonymous request getting independently and proportionally distributed. If a team relies on `StaticFeatureFlagProvider` for a canary rollout of security-relevant behavior gated to anonymous traffic specifically, they'd get an all-or-nothing outcome instead of the gradual, representative canary they likely intended.

## Q5: `FeatureFlagProvider` is a `Protocol` with one method, `is_enabled` (line 16). The module docstring says this "integrates with LaunchDarkly/Unleash/a config service the same way `VectorStore` integrates with Pinecone/Chroma — implement `is_enabled()`, nothing else in the framework changes." Is that composability claim actually true given how narrow the Protocol is (no `set()`, no flag-listing, no audit hook)?

For simple on/off or percentage-rollout consumption, yes — any caller in the codebase that only ever calls `provider.is_enabled(flag, identity=..., default=...)` genuinely doesn't care whether the answer comes from a static in-memory dict or a live call to LaunchDarkly's evaluation API, so swapping providers is a drop-in change at every *consuming* call site. But the Protocol is narrow by design in ways that matter for anything beyond read-only evaluation: `StaticFeatureFlagProvider.set(flag, value)` (line 39) — the only way to *change* a flag's state in this reference implementation — is explicitly NOT part of the `FeatureFlagProvider` Protocol, so code written generically against the Protocol type has no portable way to mutate flags; that's implementation-specific surface only `StaticFeatureFlagProvider` happens to expose. A LaunchDarkly-backed implementation wouldn't need a `set()` method at all (flags are managed via LaunchDarkly's own dashboard/API, not through this codebase), so the Protocol correctly excludes it — but that also means any test or admin tooling written against `StaticFeatureFlagProvider.set()` specifically is NOT portable to a different `FeatureFlagProvider` implementation, unlike code written purely against `is_enabled()`. The composability claim holds for the read path the framework actually depends on; it doesn't extend to flag administration, which was never part of the shared contract in the first place.

## Q6: If `flag` isn't present in `self.flags` at all, `is_enabled` returns `default` (line 30-31) rather than raising or treating an unknown flag as `False` unconditionally. Why does the caller-supplied `default` parameter matter here, and what's a security-relevant scenario where getting that default wrong has real consequences?

Making the fallback caller-controlled (rather than a hardcoded `False`) lets each call site decide the *safe* direction to fail for that specific flag — for a flag gating a new, unreviewed feature ("enable_experimental_tool"), the caller should pass `default=False` so an unconfigured or not-yet-rolled-out flag fails closed (the risky new behavior stays off unless explicitly turned on). But for a flag representing a *safety* control being incrementally adopted — e.g., "enforce_stricter_egress_policy" or "require_llm_guardrails" — a caller might reasonably want `default=True` so a flag that's simply not yet configured in `self.flags` doesn't silently disable a protection that was supposed to be on by default. Getting this backwards is a real, easy-to-make mistake with security consequences: if a security-hardening flag is checked with `is_enabled("stricter_checks", default=False)` and the flag is accidentally never populated into `self.flags` (a deployment/config bug, or simply forgetting to set it), the caller silently gets the *less safe* behavior with no error or warning — `is_enabled`'s contract makes this an entirely caller-side responsibility, and `StaticFeatureFlagProvider` itself has no way to distinguish "deliberately configured off" from "never configured at all" beyond whatever `default` value happens to be passed at each call site.

## Q7: `StaticFeatureFlagProvider.flags` is a plain mutable `dict[str, bool | int]` (line 27), and `set()` mutates it directly with no locking. Is `StaticFeatureFlagProvider` safe to share as a single instance read from many threads while another thread calls `set()` concurrently?

For CPython specifically, individual dict reads (`flag not in self.flags`, `self.flags[flag]`) and individual dict writes (`self.flags[flag] = value`) are each atomic at the bytecode level due to the GIL, so `is_enabled` won't crash or read a torn/partially-written value if `set()` runs concurrently on another thread — a reader will see either the old value or the fully-written new value for a given key, never a corrupted intermediate state. What's NOT guaranteed is any ordering or consistency guarantee across a burst of calls: if one thread calls `set("flag_a", True)` immediately followed by `set("flag_a", 50)` (rolling from fully-on to a 50% rollout) while other threads are concurrently calling `is_enabled("flag_a", ...)`, there's no synchronization ensuring readers see a consistent snapshot across multiple flags or that a specific write ordering is observed by all readers simultaneously — in practice, for a single-key read/write pattern like this, that's rarely a problem in practice (each individual flag's read is self-consistent), but it does mean there's no atomic "update these three related flags together" operation, and no mechanism here to prevent a reader from observing flag A's new value and flag B's old value mid-transition if a caller was relying on multiple flags changing together atomically.

## Q8: How would you extend `StaticFeatureFlagProvider` to log every flag evaluation for audit purposes (tying into `security.py`'s `AuditSink`), and would that logging itself introduce a new risk?

Since `FeatureFlagProvider` is a Protocol and `StaticFeatureFlagProvider` is a plain dataclass with no hidden internal hooks, the natural extension is a decorator/wrapper implementation — a new class also satisfying `FeatureFlagProvider` that wraps an inner provider and calls `self.audit.record(identity=identity, action="flag_evaluated", flag=flag, result=result)` (per `security.py`'s `AuditSink.record` signature) around each `is_enabled` call, then delegates to the wrapped provider for the actual evaluation. This composes cleanly with the existing architecture (the same "swap the interface, not the callers" pattern discussed for `guardrails.py`), and doesn't require modifying `StaticFeatureFlagProvider` itself. The risk to watch for: flag evaluation can happen *very* frequently (every request, every turn, potentially multiple times per turn if several flags gate different behaviors) — wiring every single evaluation into a synchronous audit sink like `JSONLAuditLog` (which opens and appends to a file on every `record()` call, per `security.py`) could turn a cheap in-memory dict lookup into a disk I/O operation on every flag check, a meaningful latency and I/O-volume cost that wasn't present before. A production version of this wrapper would likely want to sample or batch audit events for high-frequency flags rather than log every single evaluation unconditionally, especially for a flag checked on a hot path.

## Q9: `StaticFeatureFlagProvider` has no persistence — `self.flags` lives only in the instance's memory. What's the operational implication of this for a flag meant to represent a deliberate, audited security decision (e.g., "disable the vulnerable code path")?

Any flag set via `provider.set(flag, value)` exists only as long as that specific Python object stays alive — a process restart, redeploy, or a second, independently-constructed `StaticFeatureFlagProvider` instance (e.g., in a different worker process of a multi-process server) has no knowledge of flags set on a different instance, since there's no shared backing store (a database, a config file, a remote service) here at all. For a flag used purely for gradual feature rollout in a single-process demo or test, this is a non-issue and matches the class's own framing as "zero-dependency reference implementation." But for a flag representing something security-relevant — e.g., an incident-response decision to disable a compromised or vulnerable tool immediately — relying on `StaticFeatureFlagProvider.set()` in a multi-process or multi-replica deployment would NOT actually achieve "disabled everywhere": each replica's in-memory `flags` dict is independent, so an operator would need to individually reach every running process to actually flip the flag consistently, with no single source of truth and no audit trail of who changed what and when (contrast this with a real provider like LaunchDarkly/Unleash, which centralizes flag state and typically has built-in change-audit logging) — exactly the class of production-hardening gap the module's own docstring implies is expected to be filled by swapping in a real provider before this matters operationally.

## Q10: `flags: dict[str, bool | int]` is the declared type, but nothing in `is_enabled` or `set()` actually validates that a stored value is really a `bool` or an `int`. What happens if a caller calls `provider.set("my_flag", "on")` (a string) or `provider.set("my_flag", 50.5)` (a float)?

`isinstance(value, bool)` (line 33) is `False` for both a string and a float, so both fall through to the percentage-rollout branch: `bucket = int(hashlib.sha256(bucket_key.encode()).hexdigest(), 16) % 100` computes fine regardless of `value`'s type (it doesn't touch `value` at all), but the final `return bucket < value` then attempts `int < str` for the string case, which raises `TypeError: '<' not supported between instances of 'int' and 'str'` — an unhandled exception propagating straight out of `is_enabled` into whatever caller was just trying to check a feature flag, likely at a point in `orchestration.py` or elsewhere that wasn't expecting a flag check to ever throw. The float case (`50.5`) actually "works" without erroring (`int < float` comparison is valid Python), silently treating a float as a fractional percentage threshold that happens to function correctly by accident, not by design — nothing in the type hints or code comments suggests floats were ever an intended input. This is the same "no runtime validation" theme documented at length for `contracts.py`: the type hint `bool | int` is documentation, not enforcement, and a caller populating `self.flags` (directly, or via `set()`, which also does zero type-checking) with an unexpected type turns what should be a simple, side-effect-free flag lookup into a source of unhandled runtime exceptions.

## Q11: `isinstance(value, bool)` (line 33) is checked before treating `value` as a percentage. Given that Python's `bool` is a subclass of `int`, what's the practical difference between `provider.set("x", True)` and `provider.set("x", 1)` — and why is that difference a realistic bug magnet?

They behave completely differently, and it's easy to get this wrong by accident. `provider.set("x", True)` stores the actual Python singleton `True`; `isinstance(True, bool)` is `True`, so `is_enabled` takes the first branch and returns `True` unconditionally for every identity — a flat 100%-on flag. `provider.set("x", 1)` stores the plain integer `1`; `isinstance(1, bool)` is `False` (only the literal `True`/`False` objects are `bool` instances, even though `bool` subclasses `int`), so `is_enabled` falls through to the percentage-rollout branch and computes `bucket < 1`, which is `True` only for the roughly 1-in-100 identities whose hash bucket happens to be exactly `0` — effectively a 1% rollout, not "fully on." A developer reasoning loosely in a language where `0`/`1` and `False`/`True` are often used interchangeably (this is common muscle memory from other languages, or from casual Python where `if 1:` and `if True:` behave identically in a boolean *context*) could easily write `flags.set("new_tool_enabled", 1)` intending "turn this fully on" and instead silently ship a 1% canary — a meaningfully different, and for a security-relevant flag potentially dangerous, outcome (e.g., accidentally leaving a security fix disabled for 99% of traffic while believing it was fully deployed). Nothing in `StaticFeatureFlagProvider` warns about this; the `isinstance(value, bool)` check is doing exactly what it's supposed to do type-wise, but the human-usability gap between "the integer 1" and "the boolean True" as inputs to the same `bool | int` field is a genuine footgun.

## Q12: Is it a sound design choice to gate genuinely security-relevant behavior (e.g., "is the stricter egress policy active," "is the new guardrail rollout live") behind a `FeatureFlagProvider`/`StaticFeatureFlagProvider` at all, versus keeping such decisions purely in `Policy`/`contracts.py`?

There's a legitimate operational use case — rolling out a new, more restrictive security control gradually and being able to instantly roll it back without a code deploy if it causes unexpected breakage is a real and valuable capability, and it's exactly the kind of thing feature flags are good for in production security engineering (e.g., gradually enabling a new WAF rule). But it comes with a real tension against the "secure by default, fail closed" posture the rest of this governance layer tries to maintain (`Policy`'s conservative $1/25-step defaults in `contracts.py`, `EgressPolicy`'s documented-but-fail-open default in `security.py`): a feature flag is, by construction, an *additional* layer of indirection and potential misconfiguration between "the code that implements a security control" and "whether that control is actually active for a given request" — Q6, Q9, and Q11/Q12 collectively show several ways `StaticFeatureFlagProvider` specifically can silently resolve to the less-safe outcome (a missing flag falling back to a caller-chosen `default`, a `1` accidentally meaning 1% instead of 100%, per-process non-persistence in a multi-replica deployment). If a team uses feature flags to gate whether a critical guardrail is enforced, every one of those failure modes becomes a way for a critical safety control to be silently, unintentionally disabled — which argues for treating security-critical flags with much stricter defaults (`default=True`, fail-safe) and probably NOT rolling them out gradually via percentage bucketing in the first place, reserving percentage rollouts for genuinely lower-stakes behavioral changes (a new prompt version, a new non-security tool) and keeping hard security invariants enforced unconditionally in code (as `contracts.py`'s `Policy`/`AutonomyLevel` fields already are) rather than behind a flag that could be misconfigured off.

## Q13: The deterministic-hash bucketing (`hashlib.sha256`, not `random`) makes rollout membership reproducible for the same `(flag, identity)` pair every time. How does that specifically help — or not help — writing tests against code gated by `StaticFeatureFlagProvider`?

Because bucketing is a pure function of `(flag, identity.id)` with no randomness or hidden state beyond `self.flags`'s current contents, a test can deterministically predict which side of a rollout a given test identity lands on for a given percentage, without needing to mock `hashlib` or inject a fake random source — this is a meaningful testability win over an implementation that used `random.random() < value/100` per call, which would be non-deterministic across test runs and require seeding or mocking to test reliably. A test author can compute the expected bucket for a known `(flag, identity_id)` pair once (e.g., by running the exact same `int(hashlib.sha256(...).hexdigest(), 16) % 100` calculation) and then assert `is_enabled` returns the expected result for that exact pair. What it does NOT help with: testing the *aggregate* statistical property (does a 30% rollout actually land close to 30% of a large population?) still requires generating many distinct identities and checking the resulting distribution approximates the target percentage — a single deterministic test only confirms one identity's bucket, not that the bucketing function is well-distributed across the general population, which would need a broader statistical test (e.g., generating 10,000 synthetic identities and asserting the enabled fraction is within a tolerance of the configured percentage) that this module's test suite would need to write separately.

## Q14: Compare `StaticFeatureFlagProvider`'s rollout mechanism to how a production system like LaunchDarkly actually implements percentage rollouts and targeting rules. What capability gap is most likely to bite a team relying on this reference implementation for anything beyond a demo?

LaunchDarkly (and similar production flagging systems) support rich targeting rules layered on top of percentage rollouts — target specific user segments by attribute (role, region, plan tier), combine multiple conditions with AND/OR logic, exclude specific users regardless of their rollout bucket, and change rollout percentages live with immediate propagation to all connected clients via streaming updates, all with a full audit history of every change. `StaticFeatureFlagProvider` supports exactly two flag shapes — a plain bool, or a single int 0-100 bucketed by identity — with no attribute-based targeting at all (there's no way to say "enable this only for identities with role X" without writing custom logic entirely outside this class) and no live propagation mechanism (since it's just an in-memory dict per Q9, "pushing an update" means directly mutating that dict in whatever process happens to hold the reference, not a cross-fleet broadcast). The gap most likely to bite a team is exactly the targeting-rule absence: any real rollout strategy beyond "some flat percentage of all identities" — e.g., "enable for internal employees first, then 10% of external users, excluding any user who previously reported an issue" — simply isn't expressible through `is_enabled(flag, identity=None, default=False)`'s two-shape (`bool | int`) flag model, and would require either extending this class considerably or genuinely switching to a real provider, exactly as the module's own docstring anticipates.

## Q15: `StaticFeatureFlagProvider` has no way to combine flags (e.g., "enabled only if flag A is on AND flag B's rollout also includes this identity") or to express a dependency between flags. If a security review wanted to verify "the new stricter guardrail is either fully rolled out, or the old guardrail is still fully active — never both off simultaneously," could this module answer that question, and whose responsibility is it if not?

No — `StaticFeatureFlagProvider` has no concept of flag relationships at all; each flag is an independent entry in `self.flags`, evaluated independently by `is_enabled`, with no built-in mechanism to express or enforce an invariant spanning two flags (like "these two are never both false" or "flag B can only be true if flag A is also true"). Verifying such an invariant is entirely the calling code's responsibility — whatever code checks both `is_enabled("new_guardrail")` and `is_enabled("old_guardrail")` would need to explicitly assert the desired relationship itself (e.g., `assert new_enabled or old_enabled, "both guardrails disabled simultaneously"`), and nothing in `feature_flags.py` would catch a misconfiguration where an operator's `set()` calls left both flags off at the same time. This matters specifically because the two example flags in the question are exactly the kind of security-relevant pairing (an old control being phased out in favor of a new one) where a coverage gap during the transition — a moment where both are simultaneously disabled due to an ill-timed configuration change — is a realistic, high-consequence failure mode; a more sophisticated flagging system (or explicit application-level validation layered on top of this Protocol) would be needed to prevent it, since `StaticFeatureFlagProvider`'s flat, independent-flags model has no way to express or defend the invariant on its own.
