# agent_foundry/mcp_tools.py — Q&A

The MCP (Model Context Protocol) client bridge for the Tools Gateway: `MCPToolSource` connects to any MCP server over stdio or streamable HTTP, and registers each of its tools into a `ToolRegistry` as a normal `ToolSpec`, plus exposes MCP's other two primitives (resources, prompts) independently of tool registration.

## Q1: The docstring says MCP has "three primitives, not one." What are they, and why does this module expose all three rather than just tools (which is presumably the common case)?

The three are tools (`list_tools()`/`call_tool()`), resources (`list_resources()`/`read_resource()`), and prompts (`list_prompts()`/`get_prompt()`). Tools are function-shaped capabilities an LLM invokes; resources are readable content (files, data) a server exposes independent of any function call; prompts are reusable server-side prompt templates. `MCPToolSource` exposes all three (lines 95-124) because collapsing MCP down to "just tools" would silently drop capabilities a real MCP server may offer that have nothing to do with the Tools Gateway at all — the docstring gives concrete examples: pulling a resource straight into `context.py`'s semantic memory, or a prompt template into `prompts.py`, entirely independent of registering anything into a `ToolRegistry`. Only `register_all()` actually bridges into `ToolRegistry`; `list_resources()`/`read_resource()`/`list_prompts()`/`get_prompt()` are standalone methods a builder calls directly when they want MCP's other primitives for a different part of the framework.

## Q2: Walk through exactly why `MCPToolSource` needs its own background thread and event loop, rather than just using `asyncio.run()` per call the way `autogen_bridge.py` does.

The docstring (lines 14-18) states the reason directly: "The MCP SDK is async; the rest of the framework is sync... `orchestration.py` calls `tools.invoke()` directly, with no event loop running." A naive `asyncio.run()`-per-call approach (like `autogen_bridge.autogen_as_tool`) would work for a single one-shot async call, but MCP connections are stateful and long-lived — `ClientSession.initialize()` establishes a session that should persist across many subsequent tool calls, not be torn down and rebuilt every time. More fundamentally, per the comment at lines 58-62: "anyio's cancel scopes are bound to the asyncio Task that entered them, so the transport and session context managers must be entered *and* exited from the same task." If you tried to open the transport/session in one `asyncio.run()` call and make tool calls in separate later `asyncio.run()` calls, the `async with` context managers for the transport and session would be entered and exited across *different* tasks (each `asyncio.run()` creates a new loop and a new top-level task) — anyio's cancel-scope machinery explicitly forbids this and would raise. So `MCPToolSource.__init__()` (lines 31-34) spins up a dedicated background thread running one persistent event loop (`self._loop.run_forever()`), and `_start()`'s `lifetime()` coroutine (lines 65-80) stays alive as a single long-running task for the entire connection's lifetime, parked on `close_event.wait()` — every subsequent call is marshaled onto that same loop/task via `asyncio.run_coroutine_threadsafe` (`_run()`, lines 40-41).

## Q3: Explain the handshake in `_start()` between the connecting thread and the background loop's `lifetime()` coroutine — specifically, why is a `threading.Event` (`ready`) needed alongside the asyncio-level machinery?

`_start()` (lines 57-86) is called from whatever thread called `connect_stdio()`/`connect_http()` — typically the main thread, which has no event loop of its own running. It schedules `lifetime()` onto the background loop via `asyncio.run_coroutine_threadsafe(lifetime(), self._loop)` (line 82) and then blocks the *calling* thread on `ready.wait(timeout=30)` (line 83) — a plain `threading.Event`, not an asyncio primitive, because the calling thread isn't running an event loop and can't `await` anything. Inside `lifetime()` (running on the background loop), once `ClientSession(read, write)` is entered and `session.initialize()` completes, `self._session = session` is set and `ready.set()` is called (lines 73-75) — this is the signal that the connection is actually usable. If the transport/session setup raises instead, the `except BaseException` handler (lines 77-80) captures the exception into `self._connect_error`, *still* calls `ready.set()` (so the waiting thread doesn't hang forever), and re-raises (so the coroutine itself terminates with the failure visible to `asyncio.run_coroutine_threadsafe`'s future). Back on the calling thread, after `ready.wait()` returns, it checks `self._connect_error is not None` and re-raises it synchronously (lines 85-86) — this is what turns an async connection failure into a normal synchronous exception at the `connect_stdio()`/`connect_http()` call site. Without the `threading.Event`, the calling thread would have no cross-thread-safe way to block until the async setup either succeeds or fails, since `asyncio.Future`/`Event` objects aren't meant to be waited on synchronously from a different thread.

## Q4: What happens if `ready.wait(timeout=30)` in `_start()` times out — walk through the actual state left behind.

Line 83-84: `if not ready.wait(timeout=30): raise TimeoutError("timed out connecting to MCP server")`. This means the calling thread gives up and raises after 30 seconds, but the `lifetime()` coroutine scheduled onto the background loop is *not* cancelled — it keeps running (e.g. still blocked inside `stdio_client(params)`/`streamable_http_client(url)` trying to establish a connection, or a subprocess that hasn't started responding yet). The background thread itself was never stopped, so it keeps running `self._loop.run_forever()` indefinitely, and `self._lifetime_future` still references a task that may eventually complete (successfully connecting late, or eventually failing) with nothing left to observe the result — `self._session` could even get set well after the `TimeoutError` was already raised and handled elsewhere, silently "fixing" the connection state after the caller has already moved on and possibly abandoned or retried this `MCPToolSource` instance. This is a real resource-leak/zombie-task risk: there's no `self._lifetime_future.cancel()` on the timeout path, and no automatic cleanup — a caller who hits this timeout and just discards the `MCPToolSource` object leaks the background thread (it's a daemon thread, so it won't block process exit, but it lives for the process's lifetime otherwise) and whatever subprocess/connection `lifetime()` was in the middle of establishing.

## Q5: Describe exactly what `close()` does and why the ordering of its three lines matters.

Lines 88-93: first, if `self._close_event is not None` (i.e. a connection attempt actually got far enough to create one — set inside `lifetime()` at line 69), it calls `self._loop.call_soon_threadsafe(self._close_event.set)` to signal the `lifetime()` coroutine (parked on `close_event.wait()`) to wake up and unwind — this must go through `call_soon_threadsafe` because `close()` runs on the *calling* thread, not the loop's thread, and asyncio objects aren't safe to touch directly from another thread. It then blocks on `self._lifetime_future.result(timeout=10)` to wait for `lifetime()` to actually finish unwinding (exiting the `async with` blocks for the session and transport, i.e. actually closing the connection/subprocess cleanly) before proceeding — skipping this wait and stopping the loop immediately would risk cutting off `lifetime()` mid-cleanup, leaving the transport/subprocess in an undefined state. Only after that does it call `self._loop.call_soon_threadsafe(self._loop.stop)` to stop `run_forever()`, and finally `self._thread.join(timeout=5)` to wait for the background thread to actually exit. Reordering any of this — e.g. stopping the loop before `lifetime()` finishes unwinding — would abandon the `async with` context managers mid-exit, potentially leaking the underlying subprocess (for stdio) or connection (for HTTP) rather than closing it gracefully.

## Q6: What happens if `close()` is called on an `MCPToolSource` that never successfully connected (i.e. `connect_stdio()`/`connect_http()` was never called, or it raised)?

If `connect_stdio()`/`connect_http()` was never called at all, `self._close_event` is still `None` (its `__init__` default at line 36), so the `if self._close_event is not None:` guard at line 89 skips the wait-and-signal step entirely — `close()` falls straight through to stopping the loop and joining the thread, which is safe and correct since there's nothing to clean up. If `connect_stdio()`/`connect_http()` *was* called but raised (e.g. the connection failed inside `lifetime()`), `self._close_event` was still assigned at line 69 before the failure (it's set unconditionally as the first line inside `lifetime()`, before the `async with make_transport()` that can fail) — so `close()` would still try to signal it and wait on `self._lifetime_future.result(timeout=10)`, but that future would already be resolved (exceptionally, from the earlier re-raise at line 80) — calling `.result()` on an already-failed future re-raises that same exception, meaning `close()` itself could raise the original connection error a second time if called after a failed connect. This is a subtle rough edge: a caller who catches the exception from `connect_stdio()` and then calls `close()` for cleanup could be surprised by the same exception re-appearing from `close()`.

## Q7: `read_resource()`'s docstring says "binary/blob contents are skipped." What's the actual filtering logic, and what's lost?

Line 108: `return [c.text for c in result.contents if getattr(c, "text", None) is not None]` — this is a duck-typed filter, not an explicit check of the content's declared MIME type or an MCP-defined `type` discriminator. Any content item in the MCP resource response that doesn't have a truthy-checkable `.text` attribute (i.e. binary/blob resource contents, which MCP represents differently, typically with a `.blob` field instead) is silently dropped from the returned list — there's no error, no placeholder, no count of how many items were skipped. The docstring's own framing — "text is what's usable as agent context" — makes this an intentional simplification for the common case (feeding resource content into an LLM's context window), but it means `MCPToolSource` cannot be used to pull binary resources (images, PDFs, arbitrary blobs) out of an MCP server at all; a caller who needs binary resource access would have to bypass this method and talk to `self._session.read_resource()` directly.

## Q8: Walk through `_make_spec()`'s `call()` closure. What happens if the remote MCP tool call fails, and how does that map onto `ToolRegistry`'s error handling?

`_make_spec()` (lines 134-147) builds a `ToolSpec` per MCP tool, with `call(**kwargs)` (lines 135-140) as its `fn`. `call()` runs `self._run(self._session.call_tool(tool.name, kwargs))` — marshaling the async MCP call onto the background loop and blocking the calling thread for the result — then joins together every content block's `.text` where `getattr(b, "type", None) == "text"` (line 137), and checks `result.is_error` (line 138): if the MCP server itself reported the tool call as an error, it raises `RuntimeError(text or f"MCP tool {tool.name!r} failed")` — using the extracted text as the error message if there is any, otherwise a generic fallback. This `RuntimeError` then propagates out of `call()` exactly like any other tool exception, caught by `ToolRegistry.invoke()`/`ainvoke()`'s `try/except Exception` (`tools_gateway.py`), retried up to `spec.max_retries` (unset here, defaulting to `0`), and surfaced as `ToolResult(ok=False, error=str(e))`. So MCP's own error/success discriminator (`result.is_error`) is faithfully translated into Agent Foundry's exception-based error convention rather than being silently swallowed as a successful-but-wrong result — a correctness detail that matters, since without checking `is_error`, a failed MCP tool call could otherwise look identical to a successful one that happened to return an error message as its content.

## Q9: What happens if the connected MCP server *disconnects* mid-session — e.g. its subprocess crashes (stdio) or the HTTP connection drops — while a tool call is in flight, or between calls?

This isn't explicitly handled anywhere in this file. If the transport drops while a `self._session.call_tool(...)` coroutine is in flight (inside `_run()`'s blocking `.result()` wait on `asyncio.run_coroutine_threadsafe`), whatever exception the MCP SDK's transport layer raises for a broken connection propagates up through `_run()` to `call()`, and from there follows the same path as Q8 — caught by `ToolRegistry`, surfaced as a failed `ToolResult`. But there is a more serious latent issue: `lifetime()`'s `async with make_transport() as (read, write): async with ClientSession(read, write) as session: ... await close_event.wait()` — if the transport itself dies out from under `lifetime()` unexpectedly (not via `close_event` being set), the `async with` blocks would propagate that failure upward, likely terminating `lifetime()` and hence `self._lifetime_future` with an exception, but `self._session` still holds a reference to the now-dead session, and nothing here resets `self._session` to `None` or flags the source as disconnected. Any *subsequent* call to `list_tools()`/`call_tool()` etc. would still `assert self._session is not None` (true, since it was never cleared) and attempt to use a session that's transport is already gone — the resulting failure mode depends entirely on how the MCP SDK's `ClientSession` behaves when its underlying transport is dead, which this module doesn't guard against at all. There is no reconnection logic, no health check, and no explicit "is this source still alive" query exposed to callers.

## Q10: Why does `register_all()` register every tool the server exposes rather than requiring the caller to select which ones to expose, unlike `a2a_bridge.agent_card_for()`'s explicit opt-in `skills` list?

`register_all()` (lines 126-132) is the "connect to any MCP server" convenience path — it iterates `self.list_tools()` and registers all of them unconditionally, returning their names. This is the opposite security posture from `a2a_bridge.agent_card_for()`'s deliberate allowlist-by-omission design (Q3 in the a2a_bridge Q&A) — here, connecting to an MCP server means trusting it enough to expose *everything* it advertises into the local `ToolRegistry`. The rationale is presumably that MCP servers, unlike arbitrary external A2A organizations, are typically things a builder explicitly chose to connect to (a specific server binary or URL they configured), so there's an implicit trust decision already made at the `connect_stdio()`/`connect_http()` call site. But it does mean there's no per-tool filtering built into this bridge — if an MCP server exposes 50 tools and a builder only wants 3 registered, they'd need to call `list_tools()` themselves and selectively call `registry.register(self._make_spec(tool))` per tool (note `_make_spec` is "private" by naming convention but nothing prevents this), rather than using `register_all()` as-is. Downstream, `Policy.allowed_tools` still gates which of the registered tools any given `Identity` can actually invoke — registration into the `ToolRegistry` isn't the same as granting permission to call — but registration itself does mean the tool's existence, name, description, and schema are all now visible framework-wide.

## Q11: What are the security implications of exposing arbitrary MCP tools into a `ToolRegistry` this way — what's the actual attack surface?

Once registered via `register_all()`, an MCP tool is, per the module's own framing, "exactly like a local Python function" to everything downstream — RBAC, guardrails, circuit breaker, audit log all apply identically. But the tool's actual implementation is opaque: it's whatever code the remote MCP server chooses to run when `call_tool()` is invoked, which for a stdio-connected server is a subprocess this framework launched (`connect_stdio()`, line 43-49, runs `command`/`args`/`env` as a subprocess via `stdio_client`) with whatever permissions that subprocess has, and for an HTTP-connected server is a network call to a remote endpoint (`connect_http()`, lines 51-55) with no TLS/auth configuration surfaced in this module's API at all — `connect_http(url)` takes just a bare URL, with no header/auth-token parameter, so any authentication the remote MCP server requires has to be baked into the URL itself or handled by whatever the `mcp` SDK's `streamable_http_client` supports implicitly. The `tool.input_schema` (line 145) is trusted verbatim as the parameters schema shown to the calling LLM — a malicious or buggy MCP server could advertise a schema that doesn't match what it actually validates server-side, and there's no independent verification here that the server's behavior matches its advertised schema. Fundamentally, connecting to an MCP server is closer to "installing a plugin with function-call access" than "calling a well-audited internal function" — the framework's governance layer (RBAC, audit) constrains *who* can call the tool and logs that it was called, but does nothing to constrain or verify *what the tool itself actually does* once invoked.

## Q12: `connect_stdio()` launches a subprocess directly from `command`/`args`. What happens if that subprocess never starts, hangs on startup, or is a malicious/wrong binary?

If `stdio_client(params)` fails to launch the subprocess at all (e.g. `command` doesn't exist), that failure surfaces inside `lifetime()`'s `async with make_transport() as (read, write):` block, gets caught by the `except BaseException as e` handler (lines 77-80), stored in `self._connect_error`, and re-raised synchronously at the `connect_stdio()` call site via the `ready`/`_connect_error` handshake described in Q3 — a reasonably clean failure path. If the subprocess *does* launch but hangs during MCP's own initialization handshake (`session.initialize()`, line 73) without ever completing or erroring, `ready.set()` is never called, and the calling thread's `ready.wait(timeout=30)` eventually times out with `TimeoutError` (Q4) — but, as noted there, the hung subprocess and its `lifetime()` task are never actually cleaned up on that path, leaking both the subprocess and the background thread until `close()` is explicitly called (and even then, per Q6, `close()`'s cleanup assumes a resolved `self._lifetime_future`, which in a genuinely-hung-forever case it wouldn't be, so `close()` itself could then also hang on `self._lifetime_future.result(timeout=10)` until *that* timeout fires, after which the loop is stopped anyway but the underlying subprocess may still be left running since it was never explicitly killed). There's no explicit subprocess-kill call anywhere in this file — process lifecycle is entirely delegated to `stdio_client`'s own context-manager teardown, which only runs if `lifetime()` gets a chance to unwind cleanly.

## Q13: What's a limitation of this module you'd fix given more time?

The lack of reconnection/health-check logic (Q9) is the most consequential gap — once a session dies unexpectedly (not via an explicit `close()`), there's no detection, no automatic reconnect, and subsequent calls would fail in whatever ad-hoc way the dead session object happens to fail, rather than a clear "this MCP source is disconnected" error. Close behind: the timeout/cleanup gaps in `_start()`/`close()` (Q4, Q6) where a connection attempt that times out, or a `close()` called after a failed connect, can leak a background thread or subprocess, or re-raise a stale exception unexpectedly. A third, smaller one: `connect_http()` takes no auth/header parameter, so any MCP server requiring authentication has to be reachable via URL-embedded credentials or whatever the underlying `mcp` SDK supports implicitly — there's no explicit, documented way in this bridge's own API to pass bearer tokens or custom headers.

## Q14: How would you test `MCPToolSource` without a real external MCP server dependency, and does anything in the file suggest how it actually was tested?

The docstring's authorial framing elsewhere in the package (referenced in `a2a_bridge.py`'s own docstring: "same discipline as mcp_tools.py and policy_engine.py, not just a type shape") states MCP was "genuinely tested against a live local server" — implying the real test strategy here is to spin up an actual local MCP server (stdio subprocess or local HTTP server implementing the protocol) and round-trip `connect_stdio()`/`connect_http()`, `list_tools()`, `register_all()`, and a real tool call through it, rather than mocking the `mcp` SDK's internals. That's a meaningfully stronger testing posture than the "unverified, per-docs" stance disclosed in `crewai_bridge.py`. A reasonable *additional* test layer without needing a live server for every test: a fake in-process object matching `ClientSession`'s interface (`list_tools`, `call_tool`, `list_resources`, etc.) to unit-test `_make_spec()`'s error-translation logic (the `is_error` branch, the text-joining logic) in isolation from the real threading/event-loop machinery, which is exactly the kind of narrow-but-real logic (Q8) that's easy to get subtly wrong.
