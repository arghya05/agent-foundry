# agent_foundry/core/engines.py — Q&A

Defines the two concrete `WorkflowEngine` implementations (`LangGraphWorkflowEngine`, `NativeWorkflowEngine`) and the `RUNTIMES` registry that `core/agent.py`'s `Agent` dispatches through, so adding a new backend means implementing one protocol and adding one dict entry rather than editing `Agent` itself.

## Q1: `LangGraphWorkflowEngine.run`/`.stream`/`.resume` and `NativeWorkflowEngine.run`/`.stream`/`.resume` are, respectively, nearly line-for-line identical (both `run`/`resume` call the exact same module-level `_invoke`/`_invoke_resume` functions). Why weren't these hoisted into a shared base class instead of duplicated across two classes?

They aren't duplicated in the way that matters — `run` and `resume` on both classes call the exact same free functions, `_invoke` and `_invoke_resume` (lines ~38–60), so there's no logic duplication, only two thin one-line method bodies per class that forward to shared functions. The module docstring explains *why* this works at all: "both `.build()` outputs... speak the same `.invoke(state_or_command, run_config)`/`.stream(...)` calling convention" — a compiled LangGraph graph and a `native_engine._NativeGraph` are structurally interchangeable at the call site, so the shared functions don't need to know or care which one they're driving. A shared base class would add an inheritance relationship for methods that are already de-duplicated via composition (shared functions), and `stream()` genuinely differs in one respect between the two classes (each calls `compiled.stream(...)` directly rather than through a shared helper, because there's no resume-vs-fresh-run branching needed for streaming) — so a base class would either need an abstract `build()` only, which is exactly what the `WorkflowEngine` Protocol in `core/protocols.py` already expresses without inheritance machinery.

## Q2: Trace what `LangGraphWorkflowEngine.build()` actually forwards to `build_agent_graph()`. What happens if `AgentConfig` gains a new field that this method's explicit keyword list doesn't forward, versus if the same field is added and consumed by `NativeEngine`?

`LangGraphWorkflowEngine.build` (lines ~66–74) enumerates roughly twenty `spec.<field>` keyword arguments by name — `system_prompt`, `llm`, `tools`, `guardrails`, `eval_harness`, `identity`, `policy`, `budget`, `tracer`, `task`, `audit`, `breaker`, `cost_ledger`, `memory`, `context_engine`, `step_timeout_s`, `latency_budget`, `sla_tracker`, `critique`, `user_id`, `pdp`, `role`, plus `checkpointer`. If `AgentConfig` grows a 23rd field, this call site must be manually updated to forward it, or `build_agent_graph` simply never receives it — a silent drop, not an error, since `spec` is a dataclass and nothing here iterates its fields generically. Compare this to `NativeWorkflowEngine.build` (line ~99), which just does `_NativeGraph(spec)` — passing the **entire** `AgentConfig` object by reference. `native_engine.py`'s `NativeEngine`/`_NativeGraph` then reads whatever fields it needs directly off `config.<field>` at runtime (e.g., `config.memory`, `config.context_engine`, `config.critique` are all read live inside `_think`/`_act`/`_critique`). This is a real asymmetric footgun: a new `AgentConfig` field that only the native engine is written to consume will "just work" on `runtime="native"` the moment `NativeEngine`'s code reads it, but will be silently inert on `runtime="langgraph"` until someone remembers to add it to this method's explicit forwarding list — and there's no test or type check here that would catch the omission, since `build_agent_graph`'s own keyword-only signature would simply use its own default for whatever wasn't passed.

## Q3: Why is `from langgraph.types import Command` a local import inside `_invoke_resume` rather than a top-level module import?

If `Command` were imported at module load time, simply `import`ing `core/engines.py` would require `langgraph` to be installed, even for a caller who only ever uses `runtime="native"` and never touches `LangGraphWorkflowEngine`. The whole point of `NativeWorkflowEngine`/`native_engine.py` (per that module's own docstring) is to prove the framework can run with **zero** LangGraph dependency; a top-level import here would break that guarantee for anyone using `Agent(runtime="native")` in an environment without `agent-foundry[langgraph]` installed, since `core/agent.py` imports from `core/engines.py` unconditionally. Deferring the import to inside `_invoke_resume`, gated behind `if hasattr(compiled, "ainvoke")` (line ~54) — which is only ever true for a real compiled LangGraph graph — means the `langgraph` package is only actually imported at the moment it's genuinely needed, and never for a pure-native session.

## Q4: `_invoke_resume`'s `hasattr(compiled, "ainvoke")` is the sole discriminator between "build a real `Command`" and "build a `_ResumePayload`". Is this robust? What would break it?

It's duck-typing on a single attribute name, not a type check against any real LangGraph class, and the module's own reasoning (mirrored in `core/agent.py`'s `_resume_command`) is that this attribute happens to be a reliable proxy: a real compiled LangGraph graph always exposes `.ainvoke` (its native async invoke method), while `native_engine._NativeGraph` never does. It would break if something monkey-patched or wrapped a `_NativeGraph` instance with an `ainvoke` attribute for unrelated reasons (e.g., a test harness adding async compatibility shims uniformly to every compiled-graph-like object) — the code would then try to construct a real `langgraph.types.Command`, which itself requires `langgraph` to be importable, defeating the whole point of the native path. It would also break in the other direction if a *real* LangGraph compiled graph somehow lacked `.ainvoke` (unlikely given LangGraph's public API, but not something this code verifies) — `_invoke_resume` would then hand it a `_ResumePayload` dataclass instead of a real `Command`, and `compiled.invoke(command, ...)` would fail or misbehave since a real LangGraph graph's `.invoke()` expects a genuine `Command` for a resume, not just anything with a `.resume` attribute (unlike `_NativeGraph.invoke`, which duck-types on `getattr(x, "resume", None)` deliberately).

## Q5: `NativeWorkflowEngine.build()` raises `ValueError` if `checkpointer is not None`, but `Agent.__init__` already raises for exactly this combination before ever calling `RUNTIMES[runtime].build(...)`. Is the check here dead code, or genuine defense-in-depth?

It's genuine defense-in-depth, not dead code, because `Agent.__init__`'s validation only covers the *construction-time* path. `Agent._runner_for` (in `core/agent.py`, line ~447) explicitly guards against passing a stale checkpointer to native by computing `checkpointer = self._checkpointer if name != "native" else None` before calling `RUNTIMES[name].build(...)` — so through that specific call site, native never receives a non-`None` checkpointer either. But `RUNTIMES` and `NativeWorkflowEngine`/`LangGraphWorkflowEngine` are public, importable objects — any code (a test, a future caller, a different part of the codebase) that calls `NativeWorkflowEngine().build(some_config, checkpointer=some_checkpointer)` directly, bypassing `Agent` entirely, would hit this exact guard. The check here is the engine's own invariant, independent of whichever caller reaches it — exactly the kind of validation that belongs at the lowest layer that actually knows the constraint ("native keeps its own in-memory state and doesn't accept a checkpointer") rather than solely at a higher-level caller that happens to also know it.

## Q6: `RUNTIMES` is described as "the actual extension point" for adding a third backend like Temporal. Walk through precisely what a `TemporalWorkflowEngine` would need to implement, and where the friction would actually be.

It would need to satisfy `core/protocols.py`'s `WorkflowEngine` Protocol: a `build(spec: AgentConfig, *, checkpointer=None) -> Any` returning some object representing a runnable Temporal workflow handle, plus `run`/`stream`/`resume` methods matching the same signatures as the two existing engines, each ultimately returning a `RunResult` (via `result_from_graph_output` or an equivalent normalization). The friction is that `_invoke`/`_invoke_resume` here assume the compiled object exposes a synchronous `.invoke(state, run_config)` call that returns a plain dict shaped like `{"messages": [...], "thread_id": ..., "__interrupt__": [...]}` — Temporal's actual execution model is asynchronous and durable by nature (a workflow can span hours or days, survive process restarts, and its result is retrieved via a separate polling/signal mechanism, not a single blocking call). A faithful `TemporalWorkflowEngine.run()` would need to either block synchronously waiting for the workflow to reach a decision point (defeating much of Temporal's async value) or this framework's `run`/`resume` contract itself would need to grow an async-native or polling-based variant — meaning the *real* extension cost isn't "add one RUNTIMES entry," it's reconciling Temporal's semantics with a protocol designed around two engines that are both effectively synchronous, in-process, and non-durable-by-default.

## Q7: `RUNTIMES` maps to two already-instantiated singleton objects (`NativeWorkflowEngine()`, `LangGraphWorkflowEngine()`), not classes. What does that imply about state these engine instances could hold, and is there a hidden shared-state risk?

Because `RUNTIMES["native"]` and `RUNTIMES["langgraph"]` are single, module-level instances shared across every `Agent` in the process (every `Agent(runtime="native")` anywhere in the same Python process calls methods on the *same* `NativeWorkflowEngine()` object), these classes must be stateless — and inspecting them, they are: `NativeWorkflowEngine.build()` and `LangGraphWorkflowEngine.build()` both construct and return a fresh, independent object (`_NativeGraph(spec)` or a freshly compiled LangGraph graph) per call, with no instance attributes stored on `self` at all. All actual per-agent, per-thread state lives inside the objects `build()` returns (`_NativeGraph`'s own `NativeEngine` with its `self._threads` dict, or LangGraph's own compiled graph plus checkpointer), never inside `NativeWorkflowEngine`/`LangGraphWorkflowEngine` themselves. If a future engine implementation added instance state to `self` inside one of these classes, it would silently become shared and racy across every `Agent` using that runtime process-wide — this file's current design avoids that trap by construction (statelessness), but nothing in the `WorkflowEngine` Protocol enforces it; a careless third implementation could reintroduce exactly this bug.

## Q8: What does `result_from_graph_output` need to reconcile between LangGraph's `.invoke()` output and `NativeEngine`'s `.invoke()` output for `_invoke`/`_invoke_resume` here to treat them identically?

Neither `_invoke` nor `_invoke_resume` branch on which engine produced `raw` — both simply call `compiled.invoke(...)` and pass the result straight to `result_from_graph_output(raw, thread_id=thread_id)`. This only works because `native_engine.py`'s `NativeEngine`/`_NativeGraph` was deliberately built (per that module's docstring) to return "a plain dict shaped exactly like a LangGraph compiled graph's own `.invoke()` result" — the same three keys (`messages`, `thread_id`, and optionally `__interrupt__`), with `__interrupt__` holding a list of objects exposing a `.value` attribute (native's own `_Interrupt` dataclass mimics this shape exactly, rather than being a real LangGraph interrupt object). `result_from_graph_output` therefore never needs engine-specific branches; its entire contract is "given this exact dict shape, produce a `RunResult`," and the burden of matching that shape falls on each engine's `.invoke()`/`.stream()` implementation, not on the normalization function — which is precisely why adding a third engine requires it to conform to this same output shape, an implicit contract of `WorkflowEngine.build()`'s return value that isn't enforced by the type system (the Protocol declares `build(...) -> Any`).

## Q9: If you wanted to add uniform retry-on-transient-failure behavior for every engine's `.run()` call, where would you put it, and why not directly inside `LangGraphWorkflowEngine.run`/`NativeWorkflowEngine.run`?

The natural place is wrapping the shared `_invoke`/`_invoke_resume` functions (or adding a decorator/wrapper around them) rather than duplicating retry logic inside each of the four thin per-class methods that call them, since both classes' `run`/`resume` already funnel through these two functions — a single change point covers both engines automatically. Putting retry logic instead inside each class's own `run`/`resume` method individually would reintroduce exactly the duplication the shared-function design was meant to avoid, and would risk the two copies drifting (different retry counts, different exception types treated as transient) the same way the duplicated `_ResumePayload` dataclasses already risk drifting between this module and `core/agent.py`.

## Q10: Compare `LangGraphWorkflowEngine.build()`'s and `NativeWorkflowEngine.build()`'s error-handling posture for a bad `AgentConfig`. If `spec.llm` is `None` (an invalid config), does either `build()` catch that here, or does the failure surface elsewhere?

Neither `build()` method here validates `spec` at all — `LangGraphWorkflowEngine.build` just forwards every field straight into `build_agent_graph(...)`, and `NativeWorkflowEngine.build` just wraps `spec` in `_NativeGraph(spec)` without inspecting it. A malformed `AgentConfig` (e.g., `llm=None`) would fail downstream — inside `build_agent_graph`'s own node construction for LangGraph, or inside `NativeEngine._think`'s `config.llm.complete(...)` call (which would raise `AttributeError: NoneType has no attribute 'complete'`) the first time a turn actually runs, for native. This module deliberately has no validation layer of its own; `AgentConfig.__post_init__` (referenced elsewhere, e.g. the `core/native_engine.py` comment "AgentConfig.__post_init__ guarantees config.pdp is never None") is where such invariants are actually enforced, upstream of both engines — `core/engines.py` trusts that any `AgentConfig` it receives already satisfies those invariants, rather than re-checking them.

## Q11: `_invoke_resume`'s `payload = {"approved": approved, **(decision or {})}` merges an optional `decision` dict on top of the fixed `approved` key. What happens if a caller's `decision` dict itself contains an `"approved"` key with a conflicting value — say `decision={"approved": False}` while the caller also passed `approved=True`?

Because `decision`'s keys are spread with `**` *after* the initial `{"approved": approved}` literal in the same dict literal, a colliding key in `decision` silently overwrites the explicit `approved` argument — `decision={"approved": False}` combined with `_invoke_resume(..., approved=True, decision={"approved": False})` produces `payload = {"approved": False}`, the opposite of what the `approved=True` argument said. Nothing in this function or its docstring warns about or guards against this collision; the comment only explains that "extra keys are always safe to add" for keys that *aren't* `approved`. This is a real, unguarded footgun for any caller building `decision` dicts programmatically from untrusted or loosely-controlled data (e.g., forwarding a webhook payload's fields directly as `decision=`) — a stray `"approved"` key in that payload silently flips the actual resume decision.

## Q12: Why does `LangGraphWorkflowEngine.stream()` and `NativeWorkflowEngine.stream()` build the initial state dict inline (duplicating the literal `{"messages": [...], "thread_id": thread_id}` construction) instead of reusing `_invoke`'s state-construction logic?

`_invoke` (line ~38) builds the state as a temporary local purely to hand to `compiled.invoke(...)` and discard; `stream()` on both engines needs the identical dict shape but passed to `compiled.stream(...)` with an additional `stream_mode="values"` keyword the `invoke` call doesn't take. Rather than parameterizing `_invoke` to conditionally call either `.invoke` or `.stream` (which would need a branch or a callback parameter, adding indirection for two call sites), the code just repeats the three-line dict literal in each `stream()` method. This is a small, deliberate duplication trade-off — four lines repeated across two methods versus a more abstract helper — that keeps each engine's `stream()` self-contained and easy to read in isolation, at the minor cost of needing to update both if the initial-state shape ever changes (a change that would also need to hit `_invoke`/`_invoke_resume` and both `core/agent.py`'s `_CompiledWorkflow._initial_state` and `native_engine.py`'s own state-construction — so this specific duplication is not meaningfully worse than the coupling that already exists elsewhere).

## Q13: What is a concrete limitation of this module you'd fix given more time?

The `AgentConfig` field-forwarding asymmetry from Q2 is the sharpest one: `LangGraphWorkflowEngine.build()`'s explicit ~20-argument forwarding list is a maintenance trap that will silently drop any new `AgentConfig` field an engineer forgets to add here, with no test failure to catch it unless a test specifically exercises that field on the LangGraph runtime. A more robust design would have `LangGraphWorkflowEngine.build()` either accept `**asdict(spec)` and let `build_agent_graph` pick out what it needs via `**kwargs`, or have a single source-of-truth mapping (a class-level tuple of field names) shared between this method and a test that asserts it stays in sync with `AgentConfig`'s actual `dataclasses.fields()` — today, nothing enforces that the twenty names hardcoded here track `AgentConfig`'s real field list.

## Q14: How is this module tested without needing a real LLM or a running LangGraph installation, in principle?

Since both engines' `build()` methods take a plain `AgentConfig` and their `run`/`stream`/`resume` methods only need an object satisfying the `.invoke`/`.stream` calling convention, a test can construct an `AgentConfig` with a fake `LLMGateway` (one whose `.complete()` returns a scripted `LLMResponse` rather than calling out to Anthropic/OpenAI) and drive `NativeWorkflowEngine().build(fake_config).run(...)` end-to-end with zero network access — `NativeWorkflowEngine` has no LangGraph dependency at all. Testing `LangGraphWorkflowEngine` specifically does require `langgraph` installed (since `build_agent_graph` constructs a real `StateGraph`), but even then, the fake `LLMGateway` avoids needing a real model — the engine-selection and dispatch logic in this file is fully testable independent of any real inference call.

## Q15: `NativeWorkflowEngine.run`/`.stream`/`.resume` are identical in *code* to `LangGraphWorkflowEngine`'s, yet the module docstring frames `NativeEngine`'s existence as "proving `WorkflowEngine` is a real seam, not a LangGraph-only abstraction." How does code that's this similar actually prove that?

The proof isn't in `core/engines.py` itself — it's in what's *underneath* `NativeWorkflowEngine.build()`'s single line, `_NativeGraph(spec)`. The fact that `run`/`stream`/`resume` here can be byte-for-byte identical dispatch code across both engines is itself the evidence that `WorkflowEngine` is a genuine structural abstraction: if the native engine required different calling conventions (different argument shapes, different return types, a different way of signaling a paused HITL state), this file's `_invoke`/`_invoke_resume`/`stream()` methods would need engine-specific branches, and they don't. The real engineering work proving the seam is real lives in `native_engine.py` — reimplementing the entire think/act/critique control flow, tool-call dispatch, guardrails, budget tracking, and HITL pause/resume as raw Python matching LangGraph's `StateGraph` semantics closely enough that this file's generic dispatch code needs no awareness of which one it's talking to.
