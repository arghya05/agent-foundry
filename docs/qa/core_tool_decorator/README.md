# agent_foundry/core/tool_decorator.py — Q&A

This module provides `@tool(...)`, the ergonomic decorator that turns a plain Python function into a governed `contracts.ToolSpec` — with real enforced behavior, not just sugar: `timeout` enforces via `runtime.with_timeout`/`asyncio.wait_for`, and `cache_ttl` implements a real exact-args-match cache — while leaving `ToolRegistry.invoke()`'s own name-based `allowed_tools` enforcement in `tools_gateway.py` completely unchanged.

## Q1: Why must the async branch's `wrapped` be declared `async def` rather than a plain sync function that calls and returns the coroutine from `fn`?

The code comment (lines 35-43) spells out the exact bug this avoids: if `wrapped` were a plain `def` that did `return fn(**kwargs)` where `fn` is itself a coroutine function, calling `fn(**kwargs)` doesn't run anything — it just constructs and returns an unawaited coroutine *object*, which would silently become the tool's "output" instead of raising an obvious error. Worse, `inspect.iscoroutinefunction(wrapped)` would then read `False` (since `wrapped` itself is a plain sync function), even though *calling* it returns a coroutine — and `ToolRegistry.invoke()` (`tools_gateway.py`) has its own check for exactly this async-vs-sync distinction to decide whether to `await` a tool's result. A sync `wrapped` wrapping an async `fn` would hide the async-ness from that check, "the exact bug class that check exists to catch, reintroduced one layer up." Declaring `wrapped` itself as `async def` (lines 44-54) fixes both problems at once: `inspect.iscoroutinefunction(wrapped)` correctly reports `True`, and the `await fn(**kwargs)` (or `await asyncio.wait_for(fn(**kwargs), timeout=timeout)`) inside it actually runs the coroutine to completion before returning a real value.

## Q2: The cache key is `tuple(sorted(kwargs.items()))`. What happens if a tool is called with an unhashable argument value (e.g., a `list` or `dict`)?

`sorted(kwargs.items())` itself only needs the *keys* to be comparable (dict keys — strings — are always unique, so Python's tuple comparison never has to fall through to comparing values when keys already differ), so sorting alone doesn't fail on unhashable values. The failure happens one step later: the resulting tuple is used as a **dict key** — `cache.get(key)` / `cache[key] = (...)` (lines 47-53, 59-65) — and Python dict keys must be hashable. If any kwarg's *value* is a `list`, `dict`, or other unhashable type, `hash(key)` (implicitly invoked by the dict lookup) raises `TypeError: unhashable type: 'list'` at the very first cache-enabled call with that argument — a hard crash inside the tool wrapper, not a graceful cache-bypass. This is a real, undocumented limitation: `cache_ttl` silently assumes every tool it's applied to only ever receives hashable argument values, and there's no fallback (e.g., "skip caching for this call") if that assumption is violated.

## Q3: The wrapped function's signature is `def wrapped(**kwargs)` / `async def wrapped(**kwargs)` — no positional parameters at all. What does this mean for how a decorated tool can actually be called?

Every call to a `@tool`-decorated function must pass arguments as keywords — `wrapped(**kwargs)` has no positional parameter slots, so `get_weather("NYC")` (positional) would raise `TypeError: wrapped() takes 0 positional arguments but 1 was given`, while `get_weather(city="NYC")` works. In practice this restriction costs nothing in the intended use case: a tool invoked by an LLM's function-calling mechanism always arrives as a JSON object of named arguments (`ToolRegistry.invoke()` calls tools with `**args` from a parsed JSON-schema-shaped dict), so keyword-only calling is exactly the natural shape already. The cost only shows up if some *other* Python code tries to call a `@tool`-decorated function directly and positionally, the way you'd normally call any Python function — that code would break, and the fix (switching to keyword arguments) is not obviously signposted by the decorator itself.

## Q4: Does the cache ever proactively evict expired entries, or only check expiry lazily on read?

Only lazily, on read: `hit = cache.get(key); if hit is not None and time.time() - hit[0] <= cache_ttl: return hit[1]` (lines 48-50, 60-62) — if the cached entry is *stale* (older than `cache_ttl`), the check simply falls through to re-executing `fn` and overwriting that same key's cache entry with a fresh one; a stale-but-unused entry that's never looked up again is **never removed** from the `cache` dict. Combined with the fact that `cache` is keyed by the *exact* combination of argument values seen, a long-lived process whose tool is called with many distinct argument combinations over its lifetime (e.g., a search tool called with thousands of distinct queries over days) will accumulate one permanent dict entry per distinct call it has ever served, with no LRU eviction, no maximum size, and no periodic sweep — a real, unbounded memory-growth limitation for any tool with a large or unbounded argument space and a long process lifetime.

## Q5: Is the cache shared across multiple `Agent`/`ToolRegistry` instances that happen to use the same underlying decorated function?

Yes, and this is worth calling out because it's non-obvious. `cache: dict[...] = {}` is created *once*, inside `decorator(fn)` (line 32), the moment `@tool(...)` is applied to a given function definition — not once per `ToolSpec` construction, not once per `Agent`. Since `@tool(...)` decorates a *module-level function definition* exactly once (Python evaluates a decorator once, when the `def` statement executes), the resulting `ToolSpec.fn` (which is `wrapped`) closes over that single `cache` dict for the lifetime of the process. If that same decorated `ToolSpec` object (or, more subtly, if the same underlying module-level function is imported and registered into two separate `ToolRegistry` instances belonging to two different `Agent`s), both agents' tool calls read and write the *same* cache — a cache hit recorded from Agent-A's call is directly visible to Agent-B's identical call, potentially serving stale or cross-tenant data if the two agents' calls with identical arguments were not actually supposed to be treated as interchangeable. Whether that's desirable (a deliberately shared, process-wide memoization) or a surprising leak depends entirely on what the tool does and whether its output is meant to be call-context-independent — the decorator itself makes no distinction and offers no per-agent cache isolation.

## Q6: Why does the sync branch use `runtime.with_timeout` (thread-pool-based) while the async branch uses `asyncio.wait_for`, instead of one shared timeout mechanism?

These two are not interchangeable, and the choice in each branch is forced by what kind of callable is being timed. `with_timeout` (`runtime.py`) works by submitting a blocking, synchronous callable to a background thread and waiting on the result with a timeout — appropriate for a plain sync function that has no cooperative cancellation points of its own. `asyncio.wait_for`, by contrast, works by wrapping an *awaitable* (a coroutine) and cancelling it if it doesn't complete in time — this only works because the thing being timed is a coroutine object with actual suspend points the event loop can interrupt at. Using `with_timeout` on an async function would be wrong twice over: `with_timeout`'s target `fn` is expected to be a plain callable that *runs to completion and returns a value* when called on its worker thread, but calling an async function just returns a coroutine object immediately (never actually executing the coroutine's body) — `with_timeout` would "time out" instantly having done no real work, or (if adapted naively) block that worker thread trying to run an event loop inside another event loop, a well-known asyncio anti-pattern. Conversely, `asyncio.wait_for` cannot time out a genuinely blocking synchronous call at all — since a blocking call never yields control back to the event loop, `wait_for`'s cancellation mechanism (raising `CancelledError` at an `await` point) has no opportunity to interject.

## Q7: Does `with_timeout` (the sync path) actually stop a hung tool function when it exceeds `timeout`?

No, not in the sense of actually terminating it — this is a real, honest limitation inherited directly from `runtime.with_timeout`'s own implementation (`concurrent.futures.ThreadPoolExecutor(max_workers=1).submit(fn).result(timeout=seconds)`). Python cannot forcibly kill a running thread. If the decorated sync tool genuinely hangs (an infinite loop, a blocking network call with no timeout of its own) past the configured `timeout`, the *caller* of the `@tool`-wrapped function correctly receives a `concurrent.futures.TimeoutError` and can move on — but the submitted worker thread keeps running in the background indefinitely, holding onto whatever resources (file handles, sockets, memory) it acquired, for as long as it takes to actually finish (or forever). Repeated timeouts on a tool prone to hanging would leak one live background thread per timeout, unbounded — a resource leak the timeout mechanism itself provides no protection against.

## Q8: Does the async path have the same leak problem?

No — this is a genuine advantage of the async branch over the sync one. `asyncio.wait_for(fn(**kwargs), timeout=timeout)` (line 51), on timing out, actually issues a `.cancel()` against the underlying task/coroutine and raises `asyncio.TimeoutError`; because coroutines cooperate with cancellation at their `await` points (raising `CancelledError` into the coroutine at its next suspension point), a well-behaved async tool genuinely stops running shortly after the timeout fires, rather than continuing to execute in the background the way the thread-based sync path does. The caveat is "well-behaved": a coroutine that has long stretches of code between `await` points (e.g., a tight CPU-bound loop with no `await` inside it) won't actually be interrupted until it reaches its next await, so cancellation is prompt only to the extent the coroutine itself yields control reasonably often — but this is still structurally better than the sync path's guaranteed leak.

## Q9: `spec.permissions = frozenset(permissions)` is set as a plain attribute assignment on the constructed `ToolSpec`, not passed to `_toolspec_from_callable` as a constructor argument. Is `permissions` even a real field on `ToolSpec`, and what does it actually gate?

Yes — `contracts.ToolSpec.permissions: frozenset[str] = field(default_factory=frozenset)` is a real dataclass field (`contracts.py`, line 87), whose own comment states plainly: "Informational metadata for a caller's OWN RBAC check before registering this tool into `Policy.allowed_tools` — **not enforced by `ToolRegistry.invoke()` itself** (that's still the existing name-based `allowed_tools` allowlist)." `@tool`'s `permissions=` kwarg (lines 27, 69) is set via a post-construction attribute assignment simply because `_toolspec_from_callable` (reused from `core/agent.py`, and used for the plain function-to-`ToolSpec` conversion path too) has no `permissions` parameter in its own signature — so the decorator constructs the base spec through the shared helper, then layers `permissions` on afterward. The critical, honest limitation here: setting `permissions=["admin"]` on a `@tool`-decorated function does **nothing** to actually restrict who can call it. It's purely inspectable metadata (`spec.permissions`) that some *other* piece of code — a caller's own RBAC layer, before it decides whether to add this tool's name into a given `Policy.allowed_tools` set — is expected to check. If a developer sets `permissions=["admin"]` and never writes that separate RBAC check anywhere, the tool remains fully callable by anyone whose `Policy.allowed_tools` includes its name, with zero enforcement of the declared permission tag at all.

## Q10: Does `@tool`'s own `timeout=` kwarg populate `ToolSpec.timeout_s` (the field `contracts.py` describes as "per-tool override of `AgentConfig.step_timeout_s`")?

No — and this is a subtle, easy-to-miss inconsistency worth flagging explicitly. `@tool`'s `timeout` parameter is consumed *entirely inside* `decorator(fn)`'s closure — it's baked into `wrapped`'s own body (`with_timeout(lambda: fn(**kwargs), seconds=timeout)` for sync, `asyncio.wait_for(fn(**kwargs), timeout=timeout)` for async) and never written onto the resulting `ToolSpec` object at all: `spec = _toolspec_from_callable(wrapped, ...)` followed only by `spec.permissions = frozenset(permissions)` — `spec.timeout_s` is left at its dataclass default (`None`). This means a `@tool(timeout=5.0)`-decorated function has its timeout enforced *inside the function call itself*, completely independent of and invisible to `ToolSpec.timeout_s`, which per its own comment is meant to be "consulted... to override `AgentConfig.step_timeout_s`" by whatever code reads that field elsewhere (presumably `orchestration.py`'s step-execution logic). Any code that inspects `tool_spec.timeout_s` expecting it to reflect a `@tool(timeout=...)`-configured value would see `None` and wrongly conclude the tool has no per-tool timeout override, even though it functionally does — just enforced through a completely different mechanism than the field that's supposed to represent it.

## Q11: How does `functools.wraps(fn)` on `wrapped` interact with `_toolspec_from_callable`'s schema inference, given `wrapped`'s own signature is just `(**kwargs)`?

This is a genuinely elegant detail worth understanding precisely. `_toolspec_from_callable` (`core/agent.py`, lines 79-89) derives a tool's JSON-schema-like `parameters` dict via `inspect.signature(fn).parameters` — and `inspect.signature()` has a documented behavior of automatically *following* a callable's `__wrapped__` attribute when present, unwrapping through decorators to find the original function's real signature, specifically so tools decorated with `functools.wraps` don't lose their introspectable signature. `functools.wraps(fn)` (applied to `wrapped` at lines 44 and 56) sets `wrapped.__wrapped__ = fn` (along with copying `__name__`, `__doc__`, etc.) — so even though `wrapped` is literally defined as `def wrapped(**kwargs)`, `inspect.signature(wrapped)` returns `fn`'s *original* signature (e.g., `(city: str) -> str`), not `wrapped`'s own degenerate `(**kwargs)` signature. This is precisely why `_toolspec_from_callable(wrapped, ...)` correctly infers the real parameter types and names from the original undecorated function, despite being handed the wrapper rather than the original — without `functools.wraps`, the schema would incorrectly show a single generic `**kwargs`-shaped (or empty) parameter list instead of the tool's real typed arguments.

## Q12: If `name=`/`description=` aren't passed to `@tool(...)`, where do the resulting `ToolSpec`'s name/description actually come from?

`_toolspec_from_callable` falls back to `fn.__name__`/the first line of `fn.__doc__` when `name`/`description` aren't given explicitly (lines 88-89 of `core/agent.py`). Since it's called as `_toolspec_from_callable(wrapped, name=name, description=description)` (line 68), and `functools.wraps(fn)` already copied `fn.__name__` and `fn.__doc__` onto `wrapped` (Q11), the fallback naturally resolves to the *original* function's name and docstring, not some generic `"wrapped"` placeholder — the tool a downstream LLM sees is named and described exactly as if `_toolspec_from_callable` had been called on the undecorated function directly, purely as a byproduct of `functools.wraps` correctly propagating identity metadata through the closure.

## Q13: `_toolspec_from_callable`'s type inference only maps `str`, `int`, `float`, `bool` to JSON-schema types, defaulting everything else to `"string"`. How does this limit what `@tool`-decorated functions can meaningfully declare?

Since `@tool` relies entirely on `_toolspec_from_callable` for parameter-schema generation, it inherits this same limitation: a parameter annotated `list[str]`, `Optional[int]`, an `Enum`, or a Pydantic/dataclass model type all fall through to the generic `"string"` JSON-schema type in `type_names.get(p.annotation, "string")` (`core/agent.py`, line 87) — the LLM calling this tool would be told (incorrectly) that such a parameter is a plain string, with no structural hint about the real expected shape. Compare this to LangChain's `@tool` decorator, which can derive a full nested Pydantic-based JSON schema (including lists, unions, and nested objects) directly from type annotations — Agent Foundry's simpler four-type mapping is a deliberate consequence of the "no Pydantic" architectural constraint, trading richer automatic schema inference for a dependency-free, easily-auditable implementation; a tool needing a genuinely structured parameter today has to either accept the degraded `"string"` schema and parse it manually inside the function body, or bypass `@tool`/`_toolspec_from_callable` entirely and construct a `ToolSpec` with a hand-written `parameters` JSON schema.

## Q14: Walk through exactly what happens when `@tool(timeout=2.0, cache_ttl=60)` decorates `def get_weather(city: str) -> str: ...`, and an agent calls it twice with `city="NYC"` within 60 seconds.

At decoration time, `tool(timeout=2.0, cache_ttl=60)` returns `decorator`, which is immediately applied to `get_weather`: a fresh, empty `cache = {}` dict is created in the closure; since `get_weather` is not a coroutine function, the sync branch builds `wrapped` (line 56-66); `spec = _toolspec_from_callable(wrapped, name=None, description=None)` infers `name="get_weather"`, `description` from its docstring (or falls back to the name), and `parameters={"city": "string"}` (via `inspect.signature(wrapped)` correctly resolving to `get_weather`'s real signature per Q11); `spec.permissions = frozenset()` (no permissions given); the module-level name `get_weather` is rebound to this `ToolSpec` object. First call: an agent (via `ToolRegistry.invoke()`) calls `get_weather(city="NYC")` → `wrapped(city="NYC")` → `key = (("city", "NYC"),)` → `cache.get(key)` is `None` (empty cache) → falls to `result = with_timeout(lambda: fn(city="NYC"), seconds=2.0)`, which runs the real `get_weather` body on a worker thread bounded to 2 seconds → on success, `cache[key] = (time.time(), result)` is recorded, and `result` is returned. Second call, moments later, same arguments: `key` is identical → `cache.get(key)` returns the stored `(timestamp, result)` tuple → `time.time() - timestamp <= 60` is `True` → the cached `result` is returned **immediately, with no call to the real `get_weather` function and no timeout enforcement invoked at all** — the underlying function body never re-executes.

## Q15: Is the `cache` dict itself thread-safe under concurrent calls to the same decorated tool?

No lock protects it — same pattern as `runtime.py`'s `RunBudget`/`RateLimiter`. If two threads call the same `@tool`-decorated function with identical arguments at nearly the same moment, both can independently compute the same `key`, both find `cache.get(key)` returns `None` (or a stale entry) at the same time, and both proceed to actually execute `fn(**kwargs)` — a "thundering herd" of duplicate work for what should have been a single cached result. This duplicate execution is wasteful (and, for a non-idempotent tool, could be genuinely harmful — e.g., duplicate side effects) but not *corrupting*: the final `cache[key] = (...)` write from whichever thread finishes last simply overwrites the other's write, a clean (if wasteful) last-writer-wins outcome under CPython's GIL-protected single dict `__setitem__`, not a torn or corrupted cache entry.

## Q16: How would you test this decorator's cache-TTL and timeout behavior without making tests slow or flaky?

For cache-TTL expiry: rather than actually sleeping past `cache_ttl` in a test, monkeypatch `time.time` (the module's own `time.time()` calls, both for the cache-write timestamp and the expiry check) to return controlled, incrementing values across a test — call the decorated function once at simulated `t=0`, assert the cache entry exists, advance the patched clock past `cache_ttl`, call again, and assert the underlying function was actually re-invoked (e.g., via a call counter on a wrapped mock) rather than served from cache. For timeout behavior, rather than waiting out a real multi-second timeout, use a very small `timeout` value (e.g., `0.01`) against a deliberately slow test function (a short `time.sleep`/`asyncio.sleep` comfortably longer than the timeout) and assert the correct exception type is raised (`concurrent.futures.TimeoutError` for sync, `asyncio.TimeoutError` for async) — verifying the sync/async branch dispatch itself is best done by asserting `inspect.iscoroutinefunction(decorated_tool.fn)` matches the underlying function's own async-ness, directly testing the Q1 correctness property.

## Q17: Given more time, what's the single most valuable fix to this module?

Unbounded cache growth (Q4) is the most concrete, currently-real production risk: a long-lived process with a `@tool(cache_ttl=...)`-decorated function that's called with many distinct argument combinations over its lifetime will accumulate cache entries indefinitely, since nothing ever removes an entry once it's written, whether or not it's still within its TTL. The fix is straightforward in principle — bound the cache with a max-size eviction policy (an LRU cache via `functools.lru_cache`-style bookkeeping, or a periodic sweep removing entries older than `cache_ttl` regardless of whether they're re-read) — but nontrivial to retrofit cleanly given the cache is a bare dict closed over inside `decorator()`, with no external handle exposed for a caller to inspect or manually clear it (there's no `wrapped.cache_clear()` the way `functools.lru_cache`-wrapped functions expose, for instance) — that lack of an eviction/introspection API is itself worth adding alongside a size bound.
