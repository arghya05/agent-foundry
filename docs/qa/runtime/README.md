# agent_foundry/runtime.py — Q&A

This module is the Layer-03 "harness" — per-thread cost/step/latency budgets (`RunBudget`, `LatencyBudget`), retry/timeout helpers (`with_retry`, `with_timeout`), and fleet-primitives (`CircuitBreaker`, `RateLimiter`, `SLATracker`) — deliberately *not* the LangGraph/Native/Temporal engine-selection logic, which lives in `core/engines.py`'s `RUNTIMES` dict.

## Q1: The task calls this "the Runtime axis abstraction (LangGraph/Native/Temporal selection)," but that's not what's in this file. What's actually here, and where does engine selection really live?

`agent_foundry/runtime.py`'s own docstring is explicit: "Layer 03 — Harness/Runtime: per-thread budgets, retries, timeouts, circuit breaking… Thread/session lifecycle itself is delegated to LangGraph's checkpointer." There is no `RUNTIMES` dict, no `WorkflowEngine` protocol, and no Temporal implementation in this file at all. The actual axis selection — `Agent.__init__`/`Agent._runner_for` dispatching between `LangGraphWorkflowEngine` and `NativeWorkflowEngine` — lives in `core/engines.py`, in the `RUNTIMES: dict[str, Any] = {"native": ..., "langgraph": ...}` registry (lines 119-122). Critically, **Temporal does not exist as a real backend anywhere in the codebase** — `engines.py`'s own docstring uses "adding a third backend (Temporal, say)" purely as the *illustrative example* of how easy the seam makes extension, not as a claim that it's implemented. So "Runtime axis = LangGraph/Native/Temporal" describes the intended axis and its two real members plus one aspirational one, not the contents of `runtime.py`. This file is the *harness* that every engine's compiled graph calls into (budgets, timeouts, breakers), one layer below the axis, not the axis itself.

## Q2: Why does `RunBudget` track `_spent`/`_steps` as `dict[str, float]`/`dict[str, int]` keyed by `thread_id` instead of a single running total?

Because one compiled graph commonly serves many concurrent sessions — `orchestration.py`/`serve.py` build one shared graph and give each HTTP request its own `thread_id`. If `RunBudget` used one shared accumulator, session A spending toward its cap would count against session B's cap too: a genuine cross-session denial-of-service (the docstring notes this was "found while wiring exactly this deployment shape," not hypothetical). `spend()` and `step()` (lines 65-75) look up `self._spent.get(thread_id, 0.0)` / `self._steps.get(thread_id, 0)`, add, write back, and raise `BudgetExceeded` only if *that thread's* total crosses `policy.max_cost_usd_per_thread`/`max_steps_per_thread`. Callers that never pass `thread_id` all collapse onto `_DEFAULT_THREAD`, so single-session tests/examples behave exactly as they did before this became thread-aware — `cost_usd`/`steps` properties (lines 83-95) sum across every bucket, preserving the old single-number semantics for that case while `cost_usd_for(thread_id)`/`steps_for(thread_id)` give the real per-session figure a multi-tenant deployment needs.

## Q3: Is `RunBudget.spend()` thread-safe? Walk through what happens if two threads call it concurrently for the *same* `thread_id`.

No — there is no `threading.Lock` anywhere in `RunBudget`, `LatencyBudget`, `CircuitBreaker`, `RateLimiter`, or `SLATracker` in this file (contrast with `core/state_store.py`'s `MemoryStateStore`, which does take a lock around every operation). `spend()` does a read-modify-write: `total = self._spent.get(thread_id, 0.0) + amount; self._spent[thread_id] = total`. Under CPython's GIL, the individual dict `__getitem__`/`__setitem__` calls are atomic, but the *sequence* (read, add, write) is not — two threads racing on the same `thread_id` can both read the same starting total, both add their own `amount`, and the second write clobbers the first, silently under-counting spend and defeating the fail-closed guarantee the docstring promises ("Enforced fail-closed: exceeding cost or step limits raises, it does not silently cap"). In practice this is masked today because the real caller — `NativeEngine` — already serializes access to a given `thread_id` via its own per-thread lock (`_lock_for`, see `core/native_engine.py`), so two `RunBudget.spend()` calls for the same `thread_id` shouldn't happen concurrently *in the shipped call path*. But `RunBudget` itself provides no such guarantee if used directly (e.g., a custom orchestration that calls `budget.spend()` from multiple threads without its own lock) — this is a real, honest gap: the class's own docstring markets fail-closed enforcement, but the enforcement is only correct under an external synchronization discipline the class doesn't itself provide or document as a precondition.

## Q4: Why are `RunBudgetLike`, `LatencyBudgetLike`, `CircuitBreakerLike`, `RateLimiterLike`, and `SLATrackerLike` separate `Protocol`s instead of one shared base class, or nothing at all (just duck-typing)?

Each one formalizes "the real contract `AgentConfig.<field>` needs" — Python's structural typing already let any matching object stand in for e.g. `RunBudget` before these Protocols existed (that's literally what duck typing gives you for free), so the Protocols don't change runtime behavior at all; they exist for static typing and documentation. The shared rationale, repeated verbatim across all five docstrings, is "the same swappable-interface posture VectorStore/AuditSink/Evaluator/Provider already have" — a distributed deployment (many replicas) needs each of these backed by something *shared* (Redis, a real counter/SLO service) instead of an in-process dict, and the Protocol spells out exactly the method shape a drop-in replacement must satisfy, with zero other code changes required. They're kept as five separate Protocols rather than one generic `Budget`-like interface because the five concepts genuinely have different method shapes (`spend`/`step` vs `check`/`elapsed_s` vs `record`/`is_open` vs `allow` vs `record`/`success_rate`/`p95_latency_ms`/`error_budget_remaining`/`breaches`) — collapsing them into one interface would force irrelevant methods onto implementations that don't need them, violating interface segregation for a marginal gain in DRY-ness.

## Q5: Walk through `with_timeout`. Why a `ThreadPoolExecutor` instead of `signal.alarm` or wrapping the call in `asyncio`?

`with_timeout(fn, *, seconds)` (lines 147-157) submits `fn` to a single-worker `ThreadPoolExecutor` and calls `.result(timeout=seconds)`, which raises `concurrent.futures.TimeoutError` if `fn` hasn't finished in time. `signal.alarm` was never a real option here: it only works on the main thread and only on Unix, and this needs to work uniformly for arbitrary sync tool calls from arbitrary calling contexts. Wrapping in `asyncio` isn't a substitute either — `with_timeout` exists specifically for *synchronous*, blocking callables (the sync branch of `core/tool_decorator.py`'s `@tool` uses it exactly this way), and there's no way to asyncio-cancel a plain blocking function that never yields control. The real cost of the thread-pool approach: Python cannot forcibly kill a running thread. If `fn` actually hangs past `seconds`, `with_timeout` returns/raises on time, but the submitted thread keeps running in the background indefinitely, consuming a thread and any resources `fn` holds — a slow leak under repeated timeouts, not called out anywhere in the docstring. This is the same shape of unaddressed limitation the async path (`asyncio.wait_for`) doesn't have, since asyncio cancellation actually propagates a `CancelledError` into the awaited coroutine.

## Q6: Why does `with_timeout` deliberately raise `concurrent.futures.TimeoutError` rather than relying on the builtin `TimeoutError`?

The docstring spells this out precisely: from Python 3.11 onward, `concurrent.futures.TimeoutError` and the builtin `TimeoutError` are literally the *same object* (an alias), but on Python 3.10 — this package's stated minimum per `pyproject.toml`'s `requires-python` — they are distinct, unrelated exception classes. `ex.submit(fn).result(timeout=seconds)` already raises the `concurrent.futures` one natively; there's no cross-version aliasing to worry about because the function never converts it. A caller catching `concurrent.futures.TimeoutError` specifically gets the exact same behavior on 3.10 and 3.11+; a caller catching bare `TimeoutError` only gets consistent behavior from 3.11 on. Choosing the `concurrent.futures` exception explicitly (rather than, say, catching-and-reraising as the builtin) means the function's contract doesn't silently change shape depending on which Python version it happens to run under.

## Q7: `with_retry` uses exponential backoff (`backoff_s * 2**i`) and catches bare `Exception`. What are the real gaps here?

`with_retry(fn, *, attempts=3, backoff_s=0.5)` (lines 135-144) retries up to `attempts` times, sleeping `backoff_s * 2**i` between attempts (0.5s, 1s, 2s for the defaults), and re-raises the last exception if every attempt fails. Three concrete gaps: (1) it catches `except Exception` unconditionally — there's no way to say "retry on `ConnectionError` but fail fast on `ValueError`" (a programming bug), so a caller wanting selective retry has to wrap `fn` itself to re-raise non-retryable errors as something `with_retry` would still catch, which is awkward. (2) There's no jitter — every caller hitting the same downstream failure at the same time (e.g., a provider outage) backs off in lockstep (0.5s, 1s, 2s), which is the textbook thundering-herd pattern that jittered backoff exists to avoid. (3) There's no overall deadline — `attempts=3` bounds the *count* of tries but the wall-clock time is unbounded if `fn` itself is slow (each attempt could itself hang); `with_retry` and `with_timeout` are not composed together anywhere in this module, so a caller wanting both has to nest them manually (`with_retry(lambda: with_timeout(fn, seconds=5))`).

## Q8: `CircuitBreaker` opens after `failure_threshold` consecutive failures and closes on the next success. What's missing compared to a production circuit breaker (e.g., Envoy's or resilience4j's)?

`CircuitBreaker.record(tool, ok)` (lines 178-186) increments a per-tool consecutive-failure counter on failure and adds `tool` to `self._open` once it crosses `failure_threshold`; on success it resets the counter to 0 and discards `tool` from `_open`. Two real gaps: first, there's no **half-open** state — a real breaker, once open, should let through occasional trial requests to detect recovery; this one stays fully open until *something* calls `record(tool, ok=True)` again, but nothing in this class ever calls itself, so the caller must keep attempting calls to the (still reported open) tool and manually feed the result back in — the breaker doesn't gate calls, it only tracks state. Second, there's no time-based auto-reset: an open breaker never closes on its own after some cooldown, only on an explicit subsequent success — if nothing ever calls that tool again to "prove" success, it stays open forever. Third, `is_open()` (lines 187-188) is purely advisory — nothing in `runtime.py` itself consults it to actually block a call; the actual gating (if any) has to happen in the caller (e.g., `orchestration.py` or `tools_gateway.py` checking `breaker.is_open(tool_name)` before invoking).

## Q9: Explain `RateLimiter`'s token-bucket math precisely, including its edge cases.

`RateLimiter.allow(key)` (lines 212-220) computes `tokens = min(self.burst, self._tokens.get(key, self.burst) + (now - self._last.get(key, now)) * self.rate_per_s)` — i.e., start from the last known token count (or a full bucket, `burst`, on first use), add continuously-accrued tokens since `_last[key]` at `rate_per_s` tokens/second, and cap at `burst` so a long-idle key doesn't accumulate unbounded credit. It then updates `_last[key] = now` unconditionally (so elapsed time is always measured from the last check, not the last *allowed* call), and if `tokens < 1` it persists the fractional `tokens` and returns `False` (rate-limited); otherwise it deducts one token and returns `True`. Using floats rather than integers for the bucket lets sub-second `rate_per_s` values (e.g., 0.5/s) accrue fractional credit smoothly instead of rounding to zero every check — an integer bucket would need an accumulator anyway to avoid starving low rates. One thing worth noting: like every other primitive in this file, `_tokens`/`_last` are plain dicts with no lock — concurrent `allow()` calls for the same `key` race the same way `RunBudget.spend()` does.

## Q10: Contrast `RunBudget`/`LatencyBudget` with `SLATracker` — why does one raise and the other only report?

`RunBudget.spend()`/`.step()` and `LatencyBudget.check()` are **enforcement** primitives: they raise `BudgetExceeded` synchronously, mid-task, the moment a ceiling is crossed — the caller cannot proceed past that point without handling the exception. `SLATracker`, by contrast, is purely **observational**: `record(ok=, latency_ms=)` (lines 256-259) appends to a rolling window (bounded to `window` entries via `list.pop(0)`) of *already-completed* tasks, and `success_rate()`/`p95_latency_ms()`/`error_budget_remaining()`/`breaches()` compute statistics over that window on demand — nothing about calling `record()` can itself raise or block anything. The docstring frames this precisely: "RunBudget/LatencyBudget *enforce* a ceiling mid-task and raise; this *reports* on tasks already finished," closing the gap between "did this one request go over budget" (a per-request question) and "are we meeting our uptime and latency commitments across every completed task this window" (a fleet-health question). This is also why `SLATracker` explicitly documents itself as a stand-in for "a real SLO platform (Datadog SLOs, Prometheus recording rules) once volume warrants it" — it's a rolling in-memory window, not a time-series database, and would need to be swapped out (behind `SLATrackerLike`) the moment volume or cross-process aggregation matters.

## Q11: What's the actual failure mode of `LatencyBudget` if a caller never supplies `thread_id`, versus the intended multi-session use?

`LatencyBudget.check(*, thread_id=_DEFAULT_THREAD)` (lines 124-128) lazily starts the clock the first time a given `thread_id` is seen (`self._start.setdefault(thread_id, time.time())`), then raises `BudgetExceeded` once `time.time() - start > self.max_seconds`. Because the start time is per-`thread_id`, the docstring's stated goal holds: "a shared graph running for hours across many sessions must not fail every NEW session's very first turn just because the deployment itself has been up longer than `max_seconds`" — a brand-new `thread_id` always gets a fresh clock. If a caller *never* passes `thread_id` (every pre-existing single-session test/example), every call collapses onto `_DEFAULT_THREAD`, and the clock starts on the very first `check()` call ever made for that bucket and never resets — which is exactly the old single-session behavior, unchanged. The risk is purely at the integration boundary: if a long-lived multi-session deployment forgets to thread `thread_id` through every `check()` call (e.g., one code path passes it and another doesn't), sessions silently share the default bucket's clock and could see spurious `BudgetExceeded` failures attributable to unrelated traffic — the same cross-session bleed `RunBudget`'s docstring calls out explicitly, but `LatencyBudget`'s own docstring doesn't repeat the warning as loudly.

## Q12: Where is `RunCancelled` actually raised, and how does that differ from `BudgetExceeded`'s enforcement model?

`RunCancelled` (lines 22-25) is declared here but never raised anywhere *in this file* — its docstring says it's "raised at the next loop-safe checkpoint (top of think/act, or before an individual tool call) once `ExecutionContext.cancellation_token` has been cancelled," pointing to `core.execution_context.CancellationToken` as the actual owner of that state. This is **cooperative** cancellation, not preemptive: nothing in this codebase can forcibly interrupt a Python call stack mid-instruction (short of OS-level thread termination, which Python doesn't support safely). Instead, code that owns natural "checkpoint" boundaries — the top of a think/act loop, or just before dispatching a tool call — is expected to poll the cancellation token and raise `RunCancelled` itself if it's been set. This is fundamentally different from `BudgetExceeded`, which is raised *inline* by the exact call that crosses the ceiling (`spend()`/`step()`/`check()` themselves do the raising); `RunCancelled`'s trigger (someone else calling `.cancel()` on the token) and its raise site (the next checkpoint) are decoupled in time, so a cancellation requested while a tool call is mid-flight won't actually stop anything until that tool call returns and the next checkpoint is reached.

## Q13: The task calls out `p95_latency_ms` — is `SLATracker`'s percentile calculation "correct," and how does it compare to `core/evalgate.py`'s own percentile function for the same conceptual metric?

`SLATracker.p95_latency_ms()` (lines 266-271) does `idx = min(len(vals) - 1, int(len(vals) * 0.95)); return vals[idx]` — a nearest-rank-style percentile with truncation (via `int()`), no interpolation between the two bracketing values. `core/evalgate.py`'s `_percentile(values, pct)` (lines 65-73), used for `Scorecard.p95_latency_ms`, instead does `k = (len(s)-1) * pct; lo, hi = floor(k), ceil(k); return s[lo] + (s[hi]-s[lo]) * (k-lo)` — genuine linear interpolation between adjacent order statistics. These are two different algorithms for the same named metric living in the same codebase, and they can disagree: for `[10, 20, 30, 40]` at the 95th percentile, `SLATracker` gives `idx = min(3, int(3.8)) = 3` → `40`, while `evalgate._percentile` gives `k = 3*0.95 = 2.85` → `30 + (40-30)*0.85 = 38.5`. Neither is "wrong" as a definition of p95, but having two silently-different implementations of the same concept — one truncating to the nearest sample, one interpolating — means a p95 number quoted from `SLATracker` (fleet SLA reporting) is not directly comparable to a p95 number quoted from `Scorecard` (eval-gate reporting) even over identical underlying latency data. This is a real, unflagged inconsistency worth fixing by extracting one shared `_percentile` helper.

## Q14: What's a concrete example of `error_budget_remaining()`'s formula, and what does a negative value mean?

`error_budget_remaining()` (lines 273-280) computes `allowed = 1 - target_success_rate` (e.g., `1 - 0.999 = 0.001`), `actual = 1 - success_rate()` (the observed failure fraction), and returns `1 - (actual / allowed)`. If the target is 99.9% success and the observed rate over the rolling window is exactly 99.9%, `actual == allowed` and the result is `1 - 1 = 0.0` — budget exactly exhausted. If observed success is 100% (`actual = 0`), the result is `1 - 0 = 1.0` — budget fully intact. If observed success drops to 99.5% (`actual = 0.005`), `1 - (0.005/0.001) = 1 - 5 = -4.0` — a large *negative* number, meaning the failure budget has been blown by 4x its allowance; `breaches()` (lines 282-288) would independently flag this via the plain `success_rate() < target_success_rate` check. The `allowed == 0` special case (a target of exactly 100% success) short-circuits to `1.0 if actual == 0 else 0.0` specifically to avoid a divide-by-zero.

## Q15: What would break if a caller mixed `thread_id`-aware and `thread_id`-blind calls for the same logical session?

Say a caller calls `budget.step(thread_id="session-42")` for most of a run but one code path calls `budget.step()` with no `thread_id` (falling back to `_DEFAULT_THREAD`). That single call's count lands in the *default* bucket, not `"session-42"`'s bucket — it neither counts against session 42's own step ceiling (so a policy meant to cap session 42 undercounts it) nor stays isolated (it now silently shares the default bucket with every *other* caller in the process that also forgot to pass `thread_id`, from `RunBudget`'s own cross-session-bleed docstring reasoning). This is a purely intra-process integration bug class: nothing in `RunBudget`/`LatencyBudget` validates that `thread_id` is passed consistently, and there's no way for the class itself to detect "you forgot the keyword argument on this one call site" — it would show up only as budget numbers that don't add up during debugging or an audit.

## Q16: How would you back `RunBudget` with Redis for a multi-replica deployment, and how much of this file would you have to change?

None of *this file* — that's the entire point of the `*Like` Protocols. A Redis-backed implementation would implement `RunBudgetLike`'s four methods (`spend`, `step`, `cost_usd_for`, `steps_for`) using, e.g., `INCRBYFLOAT`/`INCR` against Redis keys namespaced by `thread_id`, and raise `BudgetExceeded` on the same conditions after the increment. Anywhere `AgentConfig.budget: RunBudgetLike` is currently populated with a real `RunBudget()`, you'd substitute the Redis-backed one instead — a drop-in swap, "no other code changes," exactly as each docstring promises. The same pattern applies verbatim to `LatencyBudgetLike`, `CircuitBreakerLike`, `RateLimiterLike`, and `SLATrackerLike` — this module deliberately keeps every fleet-shared primitive behind a narrow Protocol specifically so that in-process correctness (what's implemented here) and fleet-wide correctness (what a real deployment eventually needs) are two independent concerns joined only at the Protocol boundary.

## Q17: If you had more time, what's the single most valuable fix to this module?

Two candidates worth naming honestly. First, none of `RunBudget`, `LatencyBudget`, `CircuitBreaker`, `RateLimiter`, or `SLATracker` actually synchronizes its own internal dict mutations with a lock (Q3), unlike `core/state_store.py`'s `MemoryStateStore`; today this is safe only because real callers (`NativeEngine`) happen to already serialize per-`thread_id` access externally, which is an implicit, undocumented precondition rather than a guarantee the class itself enforces — a future caller that doesn't hold that discipline would silently under-enforce budgets. Second, the `p95_latency_ms` inconsistency between this module and `core/evalgate.py` (Q13) means the same-sounding metric name means two different computations depending on which subsystem reports it — worth consolidating into one shared percentile helper so eval-gate scorecards and fleet SLA dashboards are numerically comparable.
