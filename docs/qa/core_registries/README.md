# agent_foundry/core/registries.py — Q&A

This module provides three named, control-plane lookup registries — `PromptRegistry` (versioned prompts backed by a `VersionStore`), `PolicyRegistry` (named `contracts.Policy` objects), and `EvalRegistry` (named `Evaluator` objects) — plus `InMemoryVersionStore`, the zero-dependency default `VersionStore` backing `PromptRegistry`.

## Q1: Why three separate classes (`PromptRegistry`, `PolicyRegistry`, `EvalRegistry`) instead of one generic `Registry[T]`?

Because each one hands back a value with a *different shape and different retrieval semantics* that plugs directly into a different `Agent`/`AgentConfig` parameter with zero adaptation: `PromptRegistry.get(name)` returns a plain `str` usable as `Agent(instructions=registry.get("fashion_advisor"))`; `PolicyRegistry.get(name)` returns a real `contracts.Policy` usable as `Agent(policy=registry.get("retail_policy"))`; `EvalRegistry.get(name)` returns a real `Evaluator` usable as `eval_harness=`. A single generic `Registry[T]` with `register`/`get`/`names` would technically cover `PolicyRegistry` and `EvalRegistry` (both are genuinely just `dict[str, T]` wrappers, lines 73-105), but `PromptRegistry` is not a flat map at all — it's versioned, with `register`/`get`/`rollback`/`history` all delegating through a `VersionStore` (lines 53-70), a fundamentally richer contract than "look up a name." Collapsing all three into one generic class would either strip `PromptRegistry` of versioning or force `PolicyRegistry`/`EvalRegistry` to carry unused versioning methods — the module docstring's framing ("Each registry hands back a plain value already accepted by Agent's constructor... no changes to Agent itself were needed to wire these in") makes clear the actual design goal is API-surface-per-value-type, not DRY-ness across registries.

## Q2: `InMemoryVersionStore.publish()` mints a version as `str(time.time_ns())`. What can go wrong with this scheme?

Two real edge cases. First, resolution: `time.time_ns()` is nanosecond-precision, but *actual* clock resolution on most systems is coarser (microsecond or worse), so two `publish()` calls for the *same* `name` in rapid succession — plausible in a tight test loop or a fast automated pipeline — can produce the identical version string; `_versions[name]` (a `list[tuple[str, str, str]]`, line 25) would then contain two entries with the same version key, and `get(name, version=...)` (lines 34-41) does a linear `for v, content, _label in ...: if v == target: return content` — it returns the *first* match, silently discarding the second publish's distinguishability even though both were recorded. Second, clock monotonicity: `time.time_ns()` is wall-clock time, not a monotonic clock — if the system clock is adjusted backward (NTP correction, manual change) between two `publish()` calls, the second publish can produce a version string that sorts *before* the first, even though it happened later; nothing in `history()` (lines 48-50) or `rollback()` (lines 43-46) assumes or enforces ordering by version string, but any external code treating these version strings as chronologically sortable would be misled.

## Q3: `PromptRegistry.store: VersionStore = field(default_factory=InMemoryVersionStore)`. Why `default_factory` rather than `store: VersionStore = InMemoryVersionStore()`?

Because Python dataclasses forbid mutable default values shared across instances — `store: VersionStore = InMemoryVersionStore()` would raise `ValueError: mutable default <class 'InMemoryVersionStore'> for field store is not allowed` at class-definition time, since `InMemoryVersionStore` is itself a (mutable) dataclass. `default_factory=InMemoryVersionStore` instead stores the *constructor*, and each `PromptRegistry()` instantiation calls it fresh, giving every registry instance its own independent, empty `InMemoryVersionStore` rather than every instance secretly sharing one module-level store object (which would mean two unrelated `PromptRegistry()` instances leaking published prompts into each other). This is the same `field(default_factory=...)` pattern used throughout `core/*.py` for exactly this reason (see `PolicyRegistry._policies`, `EvalRegistry._evaluators`, `InMemoryVersionStore._versions`/`_current` all doing the same thing). Swapping in `FileVersionStore` for on-disk persistence — the docstring's stated escape hatch (line 23) — is just `PromptRegistry(store=FileVersionStore(directory=...))`, no other code change, because `PromptRegistry` only ever calls the four `VersionStore` Protocol methods on `self.store`.

## Q4: Walk through `PromptRegistry.rollback(name, version=v)` followed by `PromptRegistry.get(name)` (no version argument) — what actually happens to `_current`?

`rollback()` (`InMemoryVersionStore`, lines 43-46) first validates `v` exists among `self._versions.get(name, [])` (raising `ValueError` if not), then does `self._current[name] = version` — an unconditional pointer move, no new version is created, no new tuple appended to `_versions[name]`. A subsequent `get(name)` with no `version` kwarg (lines 34-41) resolves `target = version or self._current.get(name)`, so it now resolves to the rolled-back version and returns that entry's `content`. `history(name)` (lines 48-50) reflects this too: it computes `current = self._current.get(name)` fresh on each call and marks whichever version tuple matches as `"current": str(v == current)` — so after a rollback, the history listing correctly shows the *older* version as current and the newer one(s) as not, purely by re-deriving the comparison at read time rather than storing a stale "is_current" flag on the tuples themselves.

## Q5: If a fresh `register()` call happens *after* a `rollback()`, does the rollback's effect persist or get silently undone?

Silently undone — and this is worth flagging as a real, surprising interaction rather than a documented one. `register(name, content)` (`PromptRegistry`, line 60-61) calls straight through to `store.publish(name, content, label=label)`, and `publish()` (`InMemoryVersionStore`, lines 28-32) unconditionally does `self._current[name] = version` for the *newly minted* version — moving the "current" pointer forward regardless of what it was pointing at a moment ago. So: publish v1, publish v2 (current=v2), roll back to v1 (current=v1), then publish v3 (current=v3) — v3 becomes current immediately, with no signal anywhere that a rollback had ever been in effect moments earlier. A caller who rolled back specifically to *pin* a known-good prompt while investigating a regression, and who (or whose CI) then runs an unrelated `register()` call for that same name, would have that pin silently overridden with no warning, no version-conflict check, and no way to tell from `history()` alone that this happened without comparing timestamps manually.

## Q6: `PolicyRegistry.get()` and `EvalRegistry.get()` raise a raw `KeyError` on a missing name; `PromptRegistry.get()` (via `InMemoryVersionStore`) raises `FileNotFoundError` (no versions published) or `ValueError` (bad version). Is this exception-type inconsistency a real problem?

Yes, and it's not a deliberate design choice — it falls straight out of each registry's underlying storage: `PolicyRegistry._policies`/`EvalRegistry._evaluators` (lines 78, 96) are plain dicts, so `self._policies[name]` (line 83) and `self._evaluators[name]` (line 101) raise whatever `dict.__getitem__` raises on a missing key — `KeyError`, unmodified, un-wrapped. `PromptRegistry.get()` (line 63-64) instead delegates to `InMemoryVersionStore.get()`, whose own error handling was written independently and chose `FileNotFoundError`/`ValueError` (arguably borrowed from filesystem semantics, since `FileVersionStore` — the on-disk alternative implementation — genuinely deals with files). A caller writing generic error-handling code around "look up something from a registry, handle the not-found case" cannot write one `except` clause that covers all three registries — they'd need `except KeyError` for two of them and `except (FileNotFoundError, ValueError)` for the third, an avoidable inconsistency that a shared base exception (e.g., a `RegistryNotFoundError` all three raise) would have closed.

## Q7: Are these registries thread-safe? Is `register()` safe to call concurrently with `get()`?

None of the three registries (nor `InMemoryVersionStore`) take a lock anywhere — no `threading.Lock`, unlike `core/state_store.py`'s `MemoryStateStore`. For `PolicyRegistry.register()`/`EvalRegistry.register()`, the underlying operation is a single dict assignment (`self._policies[name] = policy`), which is atomic enough under CPython's GIL that a concurrent `get()` will observe either the old or the new value cleanly, never a torn write — so these two are "accidentally" safe for concurrent register/get pairs, though not for anything requiring a consistent multi-key view. `InMemoryVersionStore.publish()` is a different story: it does `self._versions.setdefault(name, []).append((version, content, label))` followed by `self._current[name] = version` — **two separate, non-atomic mutations**. A concurrent reader calling `get(name)` between those two statements could observe a `_versions[name]` list that already contains the new tuple while `_current[name]` still points at the *old* version — momentarily inconsistent, though not corrupting (both dicts individually stay valid). A genuine race window exists if two threads `publish()` to the *same* `name` concurrently: both could read the same `_versions.setdefault(name, [])` list reference, both append, and both then race to set `_current[name]` — the loser's publish is still recorded in the version list but its "current" pointer update is silently clobbered by the winner's, without either caller being told this happened.

## Q8: The module docstring says wiring these registries into `Agent` required "no changes to Agent itself." How is that actually achieved?

By designing each registry's `get()` to return *exactly* the type `AgentConfig`'s corresponding field already expected before these registries existed: `PromptRegistry.get()` → `str` (matches `instructions: str`), `PolicyRegistry.get()` → `contracts.Policy` (matches `policy: Policy`), `EvalRegistry.get()` → `Evaluator` (matches `eval_harness: Evaluator`). None of these are new types `Agent.__init__` has to learn to unwrap — a caller just does `Agent(instructions=prompt_registry.get("x"), policy=policy_registry.get("y"), eval_harness=eval_registry.get("z"))` and every argument arrives already in the shape `Agent` has always accepted. This is the adapter pattern applied at the *call-site* boundary rather than inside the consumer: the registries do the work of resolving "named + versioned" down to "the plain value you actually need right now," so the complexity of naming/versioning never has to leak into `Agent`'s own constructor logic.

## Q9: `history()` returns `"current": str(v == current)` — a *string* `"True"`/`"False"`, not a Python `bool`. Why might that be a real bug for a caller?

This is a genuine, concrete correctness trap: `str(v == current)` produces the literal string `"True"` or the literal string `"False"` — and **both are truthy** in Python, since any non-empty string is truthy. A caller writing the natural, idiomatic check `if entry["current"]:` to find the current version in a history listing would find that *every* entry satisfies that condition, because `"False"` is just as truthy as `"True"` — the check would silently never filter anything, always "matching" the last entry iterated (or every entry, if collecting a list). The only correct way to consume this field is the awkward `if entry["current"] == "True":` — a comparison a caller has to know to write, since nothing in the type (`dict[str, str]`, per `history()`'s declared return type `list[dict[str, str]]`) hints that this particular key needs string-equality rather than truthiness. This looks like an accidental type choice (perhaps to keep the whole dict uniformly `dict[str, str]` for easy JSON-serialization) rather than an intentional API design, and it's exactly the kind of thing a unit test asserting `history(...)[i]["current"] is True` (or explicitly `== "True"`) would have caught immediately.

## Q10: How does this compare to something like MLflow's Model Registry or LangSmith's prompt hub for named, versioned artifact management? What's missing here for production use?

The core idea — named entities with publish/rollback/history — is the same shape as MLflow's model stages or LangSmith's prompt versioning, but this module is deliberately minimal: `InMemoryVersionStore` has no persistence by default (it's explicitly the zero-dependency reference implementation, same posture as `context.InMemoryVectorStore`), no access control or audit trail on who published or rolled back a version (compare MLflow's stage-transition approvals), no diffing between two versions' content, and no metadata beyond a single free-text `label` string per version. `FileVersionStore` closes the persistence gap (writing to disk instead of an in-process dict) but doesn't add any of the governance features — for genuine production use with multiple authors touching shared prompts, you'd want at minimum an audit log of who changed what and when, and probably some form of approval gate before a rollback/publish becomes "current" for live traffic.

## Q11: The module docstring says this gives prompts/policies/evaluators "the layer `ToolRegistry` already had," but `ToolRegistry` itself lives in `tools_gateway.py`, not here. What does that say about registry-pattern consistency across the codebase?

It's an honest tell that the "named registry" pattern was independently reinvented at least twice — once for tools (`tools_gateway.ToolRegistry`, presumably `register`/`get`/`names` by string key, per this module's own description of it) and once here for prompts/policies/evaluators — rather than factored into one shared base class or mixin that both modules build on. This isn't necessarily wrong (each registry's `get()` needs to return a different concrete type, per Q1/Q8's reasoning, so a shared *generic* base wouldn't obviously simplify either implementation), but it does mean a change to "how registries behave" (say, adding a common `RegistryNotFoundError`, addressing Q6) would have to be applied by hand in at least two separate places rather than in one shared location, and there's no compile-time or interface-level guarantee that `ToolRegistry` and `PromptRegistry`/`PolicyRegistry`/`EvalRegistry` stay behaviorally consistent (e.g., in what exception a missing name raises) as either evolves.

## Q12: Does anything actually verify that an object passed as `store=` to `PromptRegistry` satisfies the `VersionStore` Protocol?

No — `VersionStore` is a `Protocol` (`versioning.py`, lines 16-21), and Python does not check Protocol conformance at construction time; `PromptRegistry(store=some_object)` will happily accept *any* object regardless of whether it actually implements `publish`/`get`/`rollback`/`history`. Static type checkers (mypy, pyright) would flag a mismatch if they can see the concrete type, but at runtime, the first sign of trouble is whichever method `PromptRegistry` calls first raising `AttributeError: 'SomeObject' object has no attribute 'publish'` deep inside `register()`, not a clean validation error at `PromptRegistry(store=...)` construction time. This is the standard tradeoff of structural typing via Protocols (no `isinstance` enforcement, no inheritance requirement) versus an ABC with `abstractmethod`s (which *would* raise `TypeError` at instantiation if incomplete) — the codebase consistently favors Protocols elsewhere too (see `runtime.py`'s `*Like` protocols), so this is a deliberate, repeated tradeoff, not an oversight specific to this module.

## Q13: `PromptRegistry.register()`/`.get()`/`.rollback()`/`.history()` are all one-line pass-throughs to `self.store`'s identically-named methods. Is this wrapper class even necessary — could `Agent(instructions=...)` just call a `VersionStore` directly?

Not directly usable, because `instructions=` needs a plain `str`, and `VersionStore.get(name, version=None)` already returns a `str` too — so at first glance `PromptRegistry` looks redundant. But `PromptRegistry` is the layer that gives the *registry* its own identity independent of which storage backend sits underneath it: code holding a `PromptRegistry` doesn't need to know or care whether it's backed by `InMemoryVersionStore` or `FileVersionStore` — it just calls `.get(name)`. A `VersionStore` alone has no concept of "the registry a caller is handed" as a first-class object to pass around (e.g., into a dependency-injection container, or as a typed constructor argument elsewhere) distinct from "the storage mechanism" — `PromptRegistry` is that stable façade, letting the storage implementation be swapped (`store=FileVersionStore(...)`) without changing the type any calling code depends on.

## Q14: Given the `"current": str(bool)` bug in Q9, what's a minimal unit test that would have caught it?

```python
def test_history_current_flag_is_a_real_bool():
    reg = PromptRegistry()
    reg.register("p", "v1")
    reg.register("p", "v2")
    entries = reg.history("p")
    current_entries = [e for e in entries if e["current"]]
    assert len(current_entries) == 1  # fails today: both "True" and "False" are truthy, so this passes trivially either way —
    assert current_entries[0]["current"] == "True"  # this is the assertion that actually pins the real (string) contract
```
The first assertion alone is a trap — it would pass even with the bug, since both string values are truthy and there just happens to be one entry per version regardless. The test that actually catches the issue has to assert the *value*, not just truthiness (`entries[i]["current"] == "True"` for the current one and `== "False"` for the rest), which is exactly the awkward, non-obvious comparison a consumer would have to know to write — a strong signal the API itself should just return a `bool`.

## Q15: How would you extend `PromptRegistry` to support a draft/published distinction, given the current four-method contract?

The current `VersionStore` Protocol has no notion of state beyond "all published versions plus one current pointer" — every `publish()` immediately becomes the new current (Q5). Adding drafts cleanly would mean either extending the Protocol itself with a `publish(..., *, promote: bool = True)` flag (so `publish(..., promote=False)` records the content and returns a version identifier without moving `_current`, and a separate `promote(name, version)` call does what `rollback()` already does structurally — move the pointer to an existing version), or layering a *new* method on top of the existing four rather than changing their signatures (to avoid breaking `FileVersionStore`, which would also need updating). The cleaner path is probably realizing that `rollback(name, version=v)` is already exactly "move current to an existing version" — a `promote()` method could be implemented as a thin alias for `rollback()` under a name that reads correctly for the draft→published direction, with `publish(..., promote=False)` as the one genuinely new capability needed.
