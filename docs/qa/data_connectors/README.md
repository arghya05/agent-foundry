# agent_foundry/data_connectors.py — Q&A

The Data Layer connector for structured data sources: `DataSource` is a minimal `Protocol` (`query(sql, params) -> list[dict]`), `SQLiteDataSource` is the zero-dependency reference implementation, and `data_query_tool()` wraps any `DataSource` as a read-only, SELECT-only `ToolSpec` with an optional table allowlist.

## Q1: The module docstring distinguishes this from `context.py`'s "unstructured RAG/vector search." Why does structured-data access need its own abstraction rather than just being another kind of tool a builder writes by hand?

The docstring (lines 1-9) frames `DataSource` as the generic "any data source" input side — the point of the `Protocol` (line 20-21) is that `SQLiteDataSource` is explicitly called out as just "the zero-dependency reference implementation," and "any DB-API 2.0-shaped connection (psycopg2 for Postgres, mysql-connector, a Snowflake/BigQuery client wrapped to match) implements the same `DataSource.query()` shape and plugs in identically — nothing else in the framework changes." This is the value of the abstraction: `data_query_tool()`'s SELECT-only enforcement, table-allowlist checking, and `ToolSpec` wrapping (with all the RBAC/caching/audit machinery that comes with being a `ToolRegistry` tool) are written once, against the `Protocol`, and apply uniformly regardless of which real database sits behind it. Without this layer, every builder connecting a new database would have to reimplement the SELECT-only guard and table-allowlist logic themselves, with no guarantee of consistency (or even remembering to add the guard at all) across different database integrations.

## Q2: `SQLiteDataSource`'s own docstring documents a real bug that was "found only once this was actually served over real HTTP." Walk through exactly what the bug was and why a "ScriptedProvider/direct-call test" wouldn't have caught it.

Lines 25-37: a plain `sqlite3.connect()` object is only usable from the thread that created it — SQLite's C-level thread-affinity check raises `sqlite3.ProgrammingError: SQLite objects created in a thread can only be used in that same thread` if a different thread touches the connection. The bug manifested because `serve.py`'s FastAPI route handler (`def chat(...)`, a *sync* function) runs in FastAPI's thread-pool executor — meaning the actual tool call executes on a worker thread that is *not* the thread that opened the `SQLiteDataSource` connection at agent-build time (agent construction presumably happens once, e.g. at app startup, on the main thread). A "ScriptedProvider/direct-call test" — the kind of test that constructs an agent and calls its methods synchronously in a single test process/thread, with no thread-pool executor in the loop — would never exercise this cross-thread path, because both the connection's creation and its use would happen on the *same* thread throughout the test. The bug only surfaces once a real ASGI server with a thread-pool-executing request handler is actually serving requests — exactly the kind of environment-dependent bug that's invisible to unit tests that don't replicate the real deployment's threading model. The docstring adds a second, equally important detail: the resulting `sqlite3.ProgrammingError` was "silently swallowed into a generic `ToolResult(ok=False)` with no exception text surfaced anywhere" — meaning the failure was not just hard to reproduce in tests, it was also hard to *diagnose* in production because the actual exception message got lost somewhere in the failure path (consistent with `tools_gateway.invoke()`'s `except Exception as e: ... error=str(e)` — `str(e)` on a `sqlite3.ProgrammingError` should actually preserve the message, so "no exception text surfaced anywhere" likely points to a logging gap further upstream, e.g. nothing logging `ToolResult.error` before it's turned into a generic user-facing failure).

## Q3: The fix was `check_same_thread=False` plus a `threading.Lock`. Why isn't `check_same_thread=False` alone sufficient — what would break without the lock?

`check_same_thread=False` (line 40) only *disables SQLite's own guard* against cross-thread use of a connection object — it does not make the underlying connection safe for genuinely *concurrent* access from multiple threads at once. SQLite's C library itself is not guaranteed thread-safe for simultaneous operations on one connection object depending on how it was compiled/configured — the docstring states this precisely: "permitting cross-thread use doesn't by itself make concurrent access from multiple threads at once safe" (lines 36-37). The `threading.Lock` (line 42) wrapped around `self._conn.execute(...)`/`cursor.fetchall()` in `query()` (lines 44-47) serializes actual access — only one thread's query runs against the connection at a time, turning "usable from any thread, but not concurrently" into "usable from any thread, one at a time." Without the lock, two FastAPI worker threads handling two simultaneous chat requests that both trigger `query_data` calls could interleave raw SQLite C-level operations on the same connection object — a genuine data race that could manifest as corrupted results, a crash, or (depending on SQLite's internal locking) a silent hang, none of which `check_same_thread=False` alone prevents.

## Q4: Is the lock in `SQLiteDataSource` sufficient for genuine multi-request throughput, or does it introduce its own bottleneck? What would you do differently for a production high-concurrency scenario?

The lock fully serializes every `query()` call across every thread — under real concurrent load (many simultaneous chat requests each triggering a `query_data` tool call), only one query executes at a time system-wide, turning what could be independent, parallelizable database reads into a single-file queue. For a lightweight reference/demo data source (which is explicitly what `SQLiteDataSource` claims to be — "the zero-dependency reference implementation"), this is an acceptable, honest tradeoff: correctness over throughput. For genuine production high-concurrency use, the better answer is exactly what the module's own docstring points to: swap in a real DB-API 2.0 connection to an actual production database (Postgres via `psycopg2`, etc.) that supports genuine concurrent connections/connection pooling — SQLite's single-writer, single-connection-at-a-time model isn't designed for high-concurrency multi-threaded serving in the first place, so the "fix" for a production scenario isn't a smarter lock around `SQLiteDataSource`, it's not using file-based SQLite as the backing store under real concurrent load at all, which the `DataSource` `Protocol`'s design explicitly anticipates and accommodates.

## Q5: `data_query_tool()`'s SELECT-only check is `stripped.startswith("select")` on the lowercased, stripped SQL string. How would you bypass this check to run a non-SELECT statement, if at all?

Practically, you likely can't get a *destructive* statement to execute through this single check alone, because `sqlite3.Cursor.execute()` itself only accepts one SQL statement per call — passing something like `"SELECT 1; DROP TABLE users;"` would either raise a `sqlite3.Warning`/error from the SQLite driver for containing multiple statements, or (depending on the exact Python/sqlite3 version behavior) only execute the first statement and never reach the `DROP TABLE`. So the "stacked query" classic bypass is largely neutralized by `sqlite3.execute()`'s own single-statement restriction, not by anything `data_query_tool()` itself does. However, the check is genuinely naive in a different, more subtle way: it only inspects the *prefix* of the string, so a query like `"SELECT * FROM users UNION SELECT sql, name, type, tbl_name, rootpage FROM sqlite_master--"` still starts with `select` and passes the guard cleanly, while potentially exfiltrating schema/data from tables the caller was never meant to query at all — the check has no ability to detect or block a `SELECT` that reads from unintended tables via `UNION`, subqueries, or joins.

## Q6: The `allowed_tables` restriction (line 74) is `any(t.lower() in stripped for t in allowed_tables)` — a substring match against the whole query text. What's wrong with this as a security boundary, concretely?

This is a "contains the table name as a substring somewhere in the query text" check, not a real SQL-aware check of which tables the query actually touches. It has both false-negative and false-positive failure modes that matter for security: **false positive (over-permissive)** — a query that merely mentions the allowed table name in an unrelated context (e.g. a string literal `WHERE description = 'formulary review'` incidentally containing the substring `formulary` from an `allowed_tables={"formulary"}` set) would pass the check even if the query's actual `FROM` clause targets a completely different, disallowed table — the check doesn't parse the query's real table references, it just greps for the name anywhere in the text. **False negative (over-restrictive)** is less of a security issue but still a real usability bug — a legitimately intended query against the allowed table using a table alias or fully-qualified name that doesn't literally contain the raw allowlisted string would be incorrectly rejected. The fundamentally correct approach would require actually parsing the SQL (e.g. with `sqlparse` or a real SQL AST) to extract the referenced table names and compare those against `allowed_tables`, rather than a naive substring search over the raw query string — this is a textbook case of "looks like a check, isn't actually a robust one" that a security reviewer should flag immediately.

## Q7: Given points 5 and 6, is `data_query_tool()` actually safe against SQL injection, or does it just prevent the *category* of "obviously destructive statement"?

It's the latter, and the module is honest about the scope of what it does: the two checks together (`SELECT`-prefix, optional table-substring allowlist) prevent the *obvious*, blunt attacks — a model or malicious input trying to run `DROP TABLE`, `DELETE FROM`, `UPDATE`, `INSERT`, etc. — but they do essentially nothing against a sophisticated SELECT-based attack that stays entirely within the `SELECT ...` grammar: reading unintended tables via `UNION`/subqueries/joins (Q5), reading SQLite's own `sqlite_master` table to enumerate schema, or exfiltrating data through error-based or timing-based side channels if the query engine surfaces those. There's also no protection here against `sql` itself being attacker-influenced in a way that constructs a malicious *SELECT* — the `sql` argument to `data_query_tool()`'s `run(sql: str)` (line 70) is the *entire raw query string* passed by the calling model, not a parameterized query with separately-bound values (contrast `DataSource.query(sql, params=())`, which *does* support parameterized/bound values at the interface level — but `data_query_tool()`'s wrapper never uses the `params` argument at all; `source.query(sql)` at line 76 always passes an empty tuple implicitly). So this tool is best understood as "coarse guardrails against a model's model-generated SQL doing something obviously destructive," not "SQL-injection-hardened," and a security reviewer should treat any table whose contents are sensitive as requiring either a much narrower dedicated tool (parameterized, hand-written query with only a few well-typed filter arguments) or real SQL parsing/allowlisting, not this generic pass-through.

## Q8: Why does `data_query_tool()` bother mentioning that RBAC "on top of this is the usual `Policy.allowed_tools`, same as any tool" (lines 57-58)? What does that layering actually buy, given the weaknesses in Q5-Q7?

This clarifies that `data_query_tool()`'s SELECT-only/table-allowlist checks are *not* Agent Foundry's access-control mechanism — they're a narrow, SQL-specific guardrail *in addition to* the framework's standard `Policy.allowed_tools` gate, which controls *whether a given identity can call this tool at all*, independent of what SQL it tries to run once it's allowed to call it. This layering matters because it means the two mechanisms answer different questions: `Policy.allowed_tools` answers "is this caller permitted to use `query_data` at all," while the SELECT/table checks inside `run()` answer "given that the caller is permitted to query, is this *specific query* within the narrow SQL shape we consider acceptable." Given the substring-matching weaknesses in Q6, the practical security posture actually relies more heavily on `allowed_tables` being a soft nudge/documentation aid than a hard boundary — the *real* hard boundary for a genuinely sensitive table would need to be either a database-level permission grant (the DB connection itself only having SELECT rights on specific tables, enforced by the database, not by string matching in Python) or a properly parsed query validator, neither of which this module implements.

## Q9: The `description` parameter's docstring (lines 60-68) claims it was "verified for real against the live Anthropic API," generating a specific wrong query. What exactly went wrong in that verification, and what does it prove about tool descriptions in general?

The documented finding: with the generic default description ("Run a read-only SQL SELECT against the connected data source"), a real model call against the live Anthropic API generated `SELECT * FROM formulary WHERE drug_name ILIKE '%metformin%'` — guessing a table name (`formulary`) that didn't match the actual table (`drug_formulary`), *and* using `ILIKE`, a PostgreSQL-specific case-insensitive-match operator that SQLite doesn't support at all (SQLite would raise a syntax error on `ILIKE`). This is a two-part failure: the model hallucinated both the schema (table/column names) and the SQL dialect, because the tool's `description` gave it literally nothing to work with beyond "this is a SQL SELECT tool" — with no schema information, an LLM has no choice but to guess plausible-sounding names and syntax from its training data, which may not match the actual connected database at all. This is a broader, important point about tool design generally that this file makes concrete with a real, reproduced failure rather than a hypothetical: a tool's natural-language `description` is not just documentation for a human, it's the *only* schema information a model has to work with when constructing arguments — the recommendation to "pass a description naming the real table and columns (and the SQL dialect, if it's not obvious)" (line 68) is the practical, evidence-backed fix.

## Q10: Walk through exactly what happens if `run(sql)` is called with a query that references a table not in `allowed_tables` — what's the actual error the calling LLM sees, and is that error informative enough to let the model self-correct?

Lines 74-75: `if allowed_tables is not None and not any(t.lower() in stripped for t in allowed_tables): raise ValueError(f"query must reference one of: {sorted(allowed_tables)}")`. This `ValueError` propagates out of `run()` exactly like any other tool exception, and since `data_query_tool()`'s returned `ToolSpec` is invoked through `ToolRegistry.invoke()`/`ainvoke()`, it's caught there and surfaced as `ToolResult(ok=False, error="query must reference one of: ['drug_formulary', ...]")`. This is actually a reasonably informative error for a model to self-correct from — it explicitly lists the allowed table names, giving the model concrete, actionable information to retry with (assuming the calling orchestration loop feeds tool errors back to the model for retry, which is the standard ReAct-style pattern this framework's `orchestration.py` presumably implements). This is notably *more* actionable than, say, `http_tools.py`'s swallowed HTTP error bodies (per that module's Q&A) — a good contrast for evaluating which of these interop-layer error messages actually help a model recover versus which leave it guessing.

## Q11: What happens if `source.query(sql)` itself raises — e.g. a genuine SQL syntax error, or (per Q2) the cross-thread SQLite error before the fix was applied? Does `run()` add any handling of its own?

No — `run()` has no try/except around `source.query(sql)` (line 76); any exception the underlying `DataSource` implementation raises (a `sqlite3.OperationalError` for bad SQL syntax, a `sqlite3.ProgrammingError` for the cross-thread bug documented in `SQLiteDataSource`'s own docstring before its fix, or whatever exception a Postgres/Snowflake-backed `DataSource` implementation raises for its own failure modes) propagates unchanged straight out of `run()`, caught only by `ToolRegistry.invoke()`/`ainvoke()`'s generic exception handler, same as Q10's `ValueError` path. This means the *quality* of the error message a model sees for a genuine database-level failure is entirely at the mercy of whatever `DataSource` implementation is plugged in — `sqlite3`'s own error messages are reasonably descriptive (e.g. "no such table: X," "near \"FROM\": syntax error"), which happens to work in this tool's favor for the SQLite reference implementation, but there's no guarantee every DB-API-2.0-shaped connection produces equally model-legible error text.

## Q12: What's a limitation of this module you'd fix given more time?

The substring-based `allowed_tables` check (Q6) is the most consequential real weakness — it's a security-adjacent control that looks stricter than it actually is, and a genuine SQL parser (even a lightweight one, just enough to extract `FROM`/`JOIN` table references) would close both the false-positive and false-negative gaps. Close behind: the fact that `run(sql)` never uses `DataSource.query()`'s own `params` argument for parameter binding — every query is a single raw SQL string with no separation between "trusted query shape" and "untrusted values," which is the opposite of standard SQL-injection-prevention practice (parameterized queries); a redesigned version might expose a small set of typed, named filter arguments instead of a raw `sql: str` parameter for any table where the query patterns are predictable, falling back to raw SQL (with its current limitations, clearly documented) only for genuinely ad-hoc exploratory querying. A third, smaller item: the SELECT-prefix check's blindness to `UNION`/subquery-based schema exfiltration (Q5) — even without full parsing, blocking mentions of `sqlite_master`/`information_schema`/`pg_catalog` etc. in `allowed_tables`-restricted mode would close an easy, cheap-to-fix information-disclosure vector.
