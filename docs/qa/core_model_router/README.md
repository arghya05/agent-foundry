# agent_foundry/core/model_router.py — Q&A

This module decides *which model list* `LLMGateway.routes[task]` should point at, from a `ModelRequest`'s capability/cost/latency requirements matched against a `ModelCapabilities` catalog, via a single `apply_route()` call — it leaves `llm_gateway.py`'s own mechanical routing/failover loop completely unchanged.

## Q1: Why does `apply_route()` mutate `llm.routes[task]` once, ahead of time, instead of `ModelRouter` being consulted on every `LLMGateway.complete()` call?

Because `LLMGateway.complete()` (`llm_gateway.py`, unchanged by this module) is deliberately a dumb, fast mechanism: it "walks `routes[task]` in order with failover" (this module's own docstring, line 2-3) — no capability reasoning at call time, just try model 1, on exception try model 2, etc. `ModelRouter.select()` is a *policy decision* — "which models are even eligible" — that only needs to be recomputed when the request's requirements or the catalog change, not on every single completion call. `apply_route(llm, task=, request=, router=, fallback=)` (lines 69-75) calls `router.select(request)` once and writes `llm.routes[task] = [selected, *(fallback or [])]`; from that point on, every `llm.complete(task=task)` call reuses the resolved list with zero added latency or routing logic, and gets `llm_gateway.py`'s existing retry/failover for free. The tradeoff is staleness: if the catalog's cost/latency data changes after `apply_route()` ran, `routes[task]` won't reflect it until `apply_route()` is called again — this is a "resolve once, mutate a route table" design, not a per-request dynamic router (contrast with something like LiteLLM's Router or Martian, which re-score on every call); Agent Foundry trades per-call adaptivity for a route table that's cheap to reuse, cacheable, and trivially observable (you can just print `llm.routes` to see what's live).

## Q2: Explain `request.capabilities <= m.capabilities` precisely — what does the `<=` operator mean here and what happens with an empty request?

Both `ModelRequest.capabilities` and `ModelCapabilities.capabilities` are typed `frozenset[str]`. Python's `frozenset.__le__` implements *subset* testing, so `request.capabilities <= m.capabilities` reads as "every capability the request declares is present in the model's capability set" — not equality, not intersection-nonempty, a strict subset-or-equal check. This means a `ModelRequest(capabilities=frozenset())` (the default) is a subset of *every* model's capability set, including a model whose own `capabilities` is also empty — so `candidates()` (lines 51-58) returns every catalog entry when the request declares no capability requirements at all. Conversely, a catalog entry with `capabilities=frozenset()` (a model nobody has annotated with any tags) can only ever satisfy requests that themselves require nothing — it will never match a request asking for `{"vision"}`, even if the model actually supports vision, simply because nobody encoded that fact into the catalog. This makes the whole matching scheme only as good as the catalog's own capability tagging discipline.

## Q3: Why are `ModelCapabilities` and `ModelRequest` frozen dataclasses?

`@dataclass(frozen=True)` (lines 20, 34) makes both immutable and hashable (given all their fields are themselves hashable — `frozenset`, `str`, `float`, `str | None` all qualify). Immutability matters because a `ModelCapabilities` entry is a *catalog fact* — "this is what model X can do and costs" — that should never be mutated in place once published into `ModelRouter.catalog`; if it were mutable, some code path could quietly change a model's advertised cost or capabilities out from under every `ModelRouter` instance sharing that catalog dict. Hashability is a side benefit of `frozen=True` here (dataclasses only auto-generate `__hash__` when frozen) — nothing in this module actually puts these objects into a set or uses them as dict keys today, but keeping them frozen costs nothing and keeps the door open for that later (e.g., de-duplicating requests, memoizing `select()` by request) without a breaking change.

## Q4: What happens when no model in the catalog satisfies a `ModelRequest` — walk through the exact failure path.

`candidates(request)` (lines 51-58) filters `self.catalog.values()` by three conditions ANDed together: the capability subset check (Q2), `request.max_cost_per_1m_input_usd is None or m.cost_per_1m_input_usd <= request.max_cost_per_1m_input_usd`, and `request.latency is None or m.latency_class == request.latency`. If nothing survives all three, `candidates()` returns `[]`. `select(request)` (lines 60-66) then checks `if not names: raise ValueError(f"no model in the catalog satisfies {request!r}")` — a hard, fail-closed error, not a silent fallback to some default model or an empty route. This mirrors the same fail-closed posture `RunBudget` in `runtime.py` takes toward budget/step ceilings: the module would rather surface "your requirements are unsatisfiable by the current catalog" loudly at `apply_route()` call time than let `llm.routes[task]` end up pointing at a model that violates the caller's stated cost/latency/capability constraints. The tradeoff is that a caller must handle `ValueError` at setup/config time (e.g., app startup wiring routes) rather than discovering the problem only when a request happens to hit that route later.

## Q5: How does `select()` break ties among multiple capability-satisfying candidates, and is that tie-break itself well-defined?

Two paths: if `self.registry` (a `ModelRegistry` from `llm_gateway.py`) is set, `select()` returns `self.registry.ranked(names)[0]` — the best-measured-eval-score model among the candidates. If no registry is given, it falls back to `min(names, key=lambda n: self.catalog[n].cost_per_1m_input_usd)` — cheapest candidate wins. Neither path considers *both* signals simultaneously: with a registry, cost is completely ignored among tied or near-tied scores (a marginally-better-scoring but 10x-more-expensive model wins outright); without a registry, quality is completely ignored (the absolute cheapest candidate wins even if a slightly pricier one is dramatically better). `ModelRegistry.ranked()` (`llm_gateway.py`, lines 338-340) does `sorted(models, key=self.avg_score, reverse=True)` — Python's `sorted` is stable, so genuine score ties resolve by the *input order* of `models`, which is `candidates()`'s catalog-dict iteration order (insertion order in Python 3.7+) — meaning tie-breaking among equally-scored models is really "whichever was registered into the catalog first," an implicit and easy-to-miss determinism source.

## Q6: What's the cold-start problem with `ModelRegistry`-driven ranking?

`ModelRegistry.avg_score(model)` (`llm_gateway.py`, lines 334-336) returns `0.0` for any model with no recorded scores (`self._scores.get(model, [])` defaults to `[]`, and `sum([])/len([])` would divide by zero — but the code returns `0.0` explicitly, not `1.0` or `None`, via the `if scores else 0.0` guard). This means a brand-new, never-evaluated model and a model that has been evaluated and measured to be *genuinely bad* (also converging toward low scores) both sort near the bottom of `ranked()` — the router can't distinguish "unproven" from "proven-bad." A model catalog with new entries added faster than they're evaluated will consistently deprioritize its newest, least-tested models in favor of established ones, even if the new model is actually better — a real cold-start bias baked into `ranked()`'s naive average.

## Q7: `apply_route()` overwrites `llm.routes[task]` wholesale. What happens to a `fallback` list from a *previous* `apply_route()` call for the same task?

It's discarded entirely. `llm.routes[task] = [selected, *(fallback or [])]` (line 74) is a full replacement, not a merge — calling `apply_route(llm, task="chat", request=..., router=..., fallback=["model-B"])` and later `apply_route(llm, task="chat", request=..., router=...)` (no fallback this time) leaves `routes["chat"]` as a single-element list, silently dropping the earlier fallback chain. There's also no synchronization: `LLMGateway.routes` is a plain `dict[str, list[str]]` (from `llm_gateway.py`'s `LLMGateway` dataclass, line 348) with no lock, so if `apply_route()` is called concurrently from multiple threads for the *same* `task` (e.g., a background re-routing job racing a request handler), the two writes can interleave unpredictably — whichever `apply_route()` call's dict assignment lands last wins, with no detection or warning that a concurrent update occurred.

## Q8: Compare this design to LiteLLM's Router or "Martian"-style LLM routers, which route dynamically per request. Why did Agent Foundry choose "resolve once into a static route table" instead?

Dynamic per-request routers re-evaluate cost/quality/latency tradeoffs on every single call, which lets them react instantly to live signals (current provider latency, live pricing, real-time load) but adds routing overhead and non-determinism to every request — two identical calls can get routed to different models depending on transient state, which complicates caching (`llm_gateway.py`'s own `PromptCache` is keyed by `(model, messages)` — a stable route makes cache hits predictable) and debugging (you can't just ask "what model does task X use" without also asking "as of what moment"). Agent Foundry's `apply_route()` instead treats routing as a **configuration decision**, resolved explicitly and inspectable afterward (`llm.routes[task]` is just a plain list you can print or assert on in a test) — cheap to reuse, trivially cacheable, and fully deterministic between resolutions, at the cost of not adapting to conditions that change between one `apply_route()` call and the next. This fits a system whose other Layer-03 primitives (`CircuitBreaker`, `RateLimiter` in `runtime.py`) already handle *live* failure/load conditions at the failover level inside `LLMGateway.complete()` itself — `ModelRouter` only needs to answer the slower-moving question of "which models are eligible at all," not "which is fastest right now."

## Q9: `capabilities` and `latency_class` are arbitrary caller-defined string tags, not a fixed vocabulary. What can go wrong?

The docstring for `ModelCapabilities` is explicit about this being deliberate: "`capabilities`/`latency_class` are caller-defined tags (e.g. `{"vision", "tool_calling"}`, `"fast"`/`"standard"`), not a fixed vocabulary this module hardcodes claims about real models into" (lines 24-26). The flexibility is real — this module never has to be updated when a new provider ships a new capability — but there's zero validation anywhere: a typo like `request.capabilities = frozenset({"tool-calling"})` (hyphen) against a catalog tagged `{"tool_calling"}` (underscore) silently produces zero candidates, and `select()` raises the generic `ValueError(f"no model in the catalog satisfies {request!r}")` with no hint that the real cause was a string mismatch, not a genuine capability gap. There's no enum, no `Literal[...]` type, no autocomplete-friendly constant set — the entire scheme relies on every catalog author and every request author independently agreeing on the same exact strings by convention.

## Q10: Walk through calling `apply_route(llm, task="support_chat", request=ModelRequest(capabilities={"tool_calling"}, max_cost_per_1m_input_usd=5.0), router=router, fallback=["claude-haiku"])` end to end, then a later `llm.complete(task="support_chat")`.

`apply_route` calls `router.select(request)`. `select()` calls `self.candidates(request)`, which iterates `router.catalog.values()`, keeping any `ModelCapabilities` `m` where `{"tool_calling"} <= m.capabilities` AND `m.cost_per_1m_input_usd <= 5.0` (the `latency` check is skipped since `request.latency is None`). Say `["claude-sonnet-5", "gpt-4o-mini"]` both qualify. If `router.registry` is set and has recorded eval scores for both, `select()` returns `registry.ranked(["claude-sonnet-5", "gpt-4o-mini"])[0]` — say `"claude-sonnet-5"` scores higher. Back in `apply_route`, `llm.routes["support_chat"] = ["claude-sonnet-5", "claude-haiku"]`, and the function returns `"claude-sonnet-5"`. Later, `llm.complete(messages, task="support_chat")` (`llm_gateway.py`, `complete()`, lines 357-375) does `for model in models or self.routes.get(task, self.routes["default"])`: it iterates `["claude-sonnet-5", "claude-haiku"]`, tries `self.provider.complete(..., model="claude-sonnet-5")` first, and only falls through to `"claude-haiku"` if that call raises (a provider outage) or the rate limiter denies it — `ModelRouter` played no further role in that call; it already did its job when `apply_route` ran.

## Q11: Why is `catalog` typed `dict[str, ModelCapabilities]` (keyed by name) rather than a plain `list[ModelCapabilities]`?

Keying by name gives O(1) lookup by model name elsewhere in the codebase (e.g., `self.catalog[n].cost_per_1m_input_usd` inside `select()`'s `min(names, key=...)`, line 66) without a linear scan, and it enforces uniqueness — you can't accidentally register the same model name twice with two different capability sets, since the second registration would just overwrite the first under that key. The cost is that `candidates()` (line 51-58) has to explicitly re-extract `.name` back out (`m.name for m in self.catalog.values() if ...`) since dict *values* don't carry their own key — a small redundancy (the catalog stores `name` both as the dict key and as a field on `ModelCapabilities` itself) that exists because `ModelCapabilities` needs to be a self-describing value usable independent of its position in the dict.

## Q12: Is `ModelRouter` itself safe to share across threads calling `select()` concurrently?

`candidates()` and `select()` are read-only over `self.catalog` and `self.registry` — no mutation happens inside `ModelRouter` itself, so concurrent `select()` calls sharing a router instance are safe *as long as nothing else concurrently mutates the underlying `catalog` dict or the `registry`'s scores*. That caveat is real: `ModelRegistry.record_score()` (`llm_gateway.py`, lines 331-332) does `self._scores.setdefault(model, []).append(score)` — a compound dict-of-lists mutation with no lock, exactly the same unsynchronized-mutation pattern flagged in `runtime.py`'s `RunBudget` (see that module's Q&A, Q3). If eval results are being recorded into the same `ModelRegistry` concurrently with `select()` calls reading from it (e.g., an eval pipeline and live traffic sharing one registry), there's a theoretical race on the underlying list mutation, though in practice CPython's GIL makes the individual `append()` atomic enough that this rarely manifests as corruption — it can still manifest as a `ranked()` call briefly seeing a partially-updated score list mid-append in principle.

## Q13: The `LLMGateway` import is guarded by `TYPE_CHECKING` while `ModelRegistry` is imported directly at module load. Why the difference?

At the top of the file: `from ..llm_gateway import ModelRegistry` (a real, unconditional import, line 14) versus `if TYPE_CHECKING: from ..llm_gateway import LLMGateway` (lines 16-17). `ModelRegistry` is used as a real runtime value — `ModelRouter.registry: ModelRegistry | None` is a dataclass field whose type annotation is evaluated at class-definition time in some contexts (and more importantly, `ModelRegistry` is genuinely *instantiated and used* — `self.registry.ranked(names)` calls a real method on a real object), so it must be a real import. `LLMGateway`, by contrast, is only ever referenced as a **type annotation string** in `apply_route`'s signature (`llm: "LLMGateway"`, quoted so it doesn't need to resolve at runtime at all) — the function only ever *mutates an attribute* (`llm.routes[task] = ...`) and never constructs or calls a method requiring the real class, so it doesn't need the import to exist at runtime. Given `from __future__ import annotations` is active (line 9), all annotations are lazily-evaluated strings anyway, but the `TYPE_CHECKING` guard also protects against a circular import: if `llm_gateway.py` ever imports from `core/model_router.py` (directly or transitively), an unconditional `from ..llm_gateway import LLMGateway` at module scope here would fail at import time; gating it under `TYPE_CHECKING` means type checkers see the real class while the actual Python interpreter never executes that import line.

## Q14: What does `ModelRequest()` (every field at its default) actually select, and is that a useful default?

With `capabilities=frozenset()`, `max_cost_per_1m_input_usd=None`, and `latency=None`, every single condition in `candidates()` is vacuously satisfied by every catalog entry (Q2's subset-of-everything property, plus both `is None` cost/latency skips) — so `candidates()` returns the entire catalog. `select()` then either asks the registry to rank the *whole catalog* by eval score, or (with no registry) picks the single globally cheapest model in the catalog. So `ModelRequest()` effectively means "give me either the best-measured or the cheapest model overall, with no filtering at all" — a legitimate, if blunt, default for a caller that genuinely has no capability/cost/latency requirements, but easy to reach for by accident (e.g., constructing a `ModelRequest` and forgetting to set `capabilities`) and getting silently permissive matching instead of an error.

## Q15: How would you unit test `ModelRouter.select()`'s tie-breaking to make it deterministic and verifiable?

Given `ranked()`'s stability-dependent tie-break (Q5), a good test would construct a catalog as a plain `dict` literal (whose iteration order is guaranteed insertion order in Python 3.7+), register identical scores for two or more models via `ModelRegistry.record_score()`, call `select()`, and assert the result equals the *first-inserted* of the tied models — pinning the currently-implicit "ties go to whichever was registered first" behavior as an explicit, tested contract rather than an accidental side effect of dict ordering + `sorted`'s stability. A second useful test: construct a request whose `max_cost_per_1m_input_usd` excludes the top-ranked-by-score model, and assert `select()` correctly falls back to the next-best *candidate* (not just the next-best in the whole catalog) — verifying `candidates()`'s filtering and `select()`'s ranking compose correctly rather than testing them only in isolation.

## Q16: Why is this routing logic a separate module from `llm_gateway.py` rather than folded into `LLMGateway` directly?

Single-responsibility: `LLMGateway.complete()` is a mechanical dispatcher (walk a list, try each, fail over) that doesn't need to know *why* a route list looks the way it does — it's unchanged by this module specifically so that its failover/caching/rate-limiting logic (already tested, already relied upon) never has to be touched to add a new way of *deciding* routes. `model_router.py` owns the separate concern of "what qualifies," which can evolve independently (new capability schemes, new tie-break strategies, a smarter cost model) without risking regressions in the actual request-dispatch path. This mirrors the same reuse-over-reimplementation posture seen elsewhere in the codebase (e.g., `core/evalgate.py` reusing `orchestration._get_all_tool_calls` rather than re-deriving tool-call detection) — compose a new capability on top of an existing, stable primitive instead of modifying the primitive itself.

## Q17: Given more time, what's the most valuable improvement to this module?

Joining routing to *live* runtime signals rather than only static catalog facts: today `ModelCapabilities.latency_class` is a hand-authored tag ("fast"/"standard") that never reflects a provider's actual measured latency, and `select()` has no visibility into `runtime.py`'s `CircuitBreaker`/`RateLimiter` state — a router could pick a model whose breaker is currently open, only for `LLMGateway.complete()`'s failover to immediately skip past it anyway. Feeding real-time circuit-breaker/rate-limiter state and measured (not declared) latency into `candidates()`/`select()` would make routing decisions track reality more closely, at the cost of reintroducing some of the per-call dynamism this module currently avoids by design (Q1, Q8) — a genuine tradeoff, not a free win.
