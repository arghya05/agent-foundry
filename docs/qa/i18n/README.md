# agent_foundry/i18n.py — Q&A

`i18n.py` is a small, dependency-free, purely-functional localization module — a `LocaleSpec` registry (currency symbol, decimal/thousands separators, date format, digit-grouping style) plus three pure formatting functions (`format_number`, `format_currency`, `format_date`) that never touch Python's stdlib `locale` module or any process-global state.

## Q1: The module docstring says it's "deliberately dependency-free and not built on Python's stdlib `locale` module" because that module "mutates process-global state via `locale.setlocale()`." Explain exactly what would break, concretely, if this module used `locale.setlocale()` instead.

`locale.setlocale()` changes the CURRENT PROCESS's locale setting globally — every thread in that process sees the new locale immediately, because it's a single mutable C-level global, not a per-call or per-thread value. In a FastAPI deployment (which `serve.py` builds and runs via `uvicorn`, using a thread pool for sync route handlers), imagine two requests arrive nearly simultaneously: a US-locale user's request calls `locale.setlocale(locale.LC_ALL, "en_US")` to format a number, then before that request finishes, an India-locale user's request calls `locale.setlocale(locale.LC_ALL, "en_IN")` on a different thread in the SAME process. Now the first request's still-in-flight formatting call could use `en_IN` formatting instead of `en_US` — its user gets the wrong currency symbol or decimal grouping, non-deterministically, depending on request timing. This is precisely the failure mode the docstring calls "exactly the shared-graph, many-sessions deployment shape this framework already assumes," explicitly drawing the same parallel as `runtime.py`'s per-`thread_id` `RunBudget` (state that MUST be request/session-scoped, never global) and the "SQLite-thread-safety fix in `data_connectors.py`" (another place the codebase had to fix a shared-mutable-state bug under concurrent request handling).

## Q2: What design property makes every function in `i18n.py` "safe under FastAPI's thread-pool execution," and how would you prove that property by reading the code rather than taking the docstring's word for it?

The docstring's claim is: "Every function here is a pure function of `(locale_code, value)`, not process state." Verifying this by inspection: `resolve_locale(code)` (i18n.py:50-51) reads only from the module-level `_LOCALES` dict and its argument, returning a value with no side effect; `format_number`, `format_currency`, `format_date` (i18n.py:76-92) each take a `locale: str` keyword argument, call `resolve_locale(locale)` to get an immutable `LocaleSpec` (it's a `@dataclass(frozen=True)`, i18n.py:24), and compute a return value purely from that spec plus the function's own value argument — none of them read or write any variable outside their own local scope except the read-only `_LOCALES` dict lookup. Since two threads simultaneously calling `format_currency(100, locale="en-US")` and `format_currency(100, locale="en-IN")` each pass their OWN locale code as an argument rather than mutating any shared "current locale" variable, there's no cross-thread interference possible — this is the textbook definition of thread-safety via purity/immutability rather than via locking. The one shared mutable structure, `_LOCALES` itself, is only ever mutated by `register_locale()` (i18n.py:44-47), which is expected to be called at startup/configuration time, not per-request — though nothing in the code enforces that usage pattern (see Q7).

## Q3: Walk through `_group_indian` step by step for the input `"1234567"`, explaining exactly why Indian-style grouping needs a different algorithm from `_group_western`.

`_group_indian("1234567")` (i18n.py:63-73): `len(digits) > 3` is true, so `last3 = "567"`, `rest = "1234"`. Loop: `len(rest) > 2` is true (`4 > 2`), so `parts.append(rest[-2:])` → `parts = ["34"]`, `rest = "12"`. Loop again: `len(rest) > 2` is now false (`2 > 2` is false), loop exits. `parts.append(rest)` → `parts = ["34", "12"]`. Return `",".join(reversed(parts)) + "," + last3` → `reversed(["34", "12"])` is `["12", "34"]`, joined as `"12,34"`, plus `",567"` → final result `"12,34,567"`. This is the correct Indian numbering convention (lakh/crore grouping: 3 digits, then groups of 2), contrasted with `_group_western`'s uniform groups-of-3 (`"1,234,567"`). The two need genuinely different algorithms — not just a different separator — because the GROUP SIZE itself differs after the first group (western: 3,3,3,...; Indian: 3,2,2,...), which is exactly why `LocaleSpec.grouping` is a discrete `"western"`/`"indian"` string dispatched via `(_group_indian if spec.grouping == "indian" else _group_western)(whole)` (i18n.py:80) rather than a single parameterized grouping-width function.

## Q4: `format_number` calls `f"{abs(value):.{decimals}f}".partition(".")` to split whole and fractional parts. What happens if `decimals=0`, and is there a bug lurking in the `whole`/`frac` unpacking?

With `decimals=0`, `f"{abs(value):.0f}"` produces a string with NO decimal point at all (e.g. `"1235"` for `1234.5`, note Python's `.0f` formatting rounds). `str.partition(".")` on a string containing no `"."` returns `(the_whole_string, "", "")` — so `whole = "1235"`, `frac = ""`. This is handled correctly downstream: `format_number` (i18n.py:76-82) ends with `return f"{sign}{grouped}{spec.decimal_sep}{frac}" if decimals else f"{sign}{grouped}"` — the `if decimals else` branch specifically avoids appending a trailing decimal separator with an empty fractional part when `decimals == 0`, which is the correct behavior (you don't want `"1,235."` with a dangling dot). This is a case where the code correctly anticipated its own edge case rather than a bug — the `if decimals` check exists precisely because the author noticed `frac` would be empty in that case and handled it explicitly rather than leaving a stray separator.

## Q5: What happens if `format_currency` or `format_number` is called with a locale code that isn't in `_LOCALES` and was never registered via `register_locale` — e.g. `format_currency(100, locale="fr-FR")`?

`resolve_locale(code)` (i18n.py:50-51) does `_LOCALES.get(code or DEFAULT_LOCALE, _LOCALES[DEFAULT_LOCALE])` — an unknown code like `"fr-FR"` isn't in `_LOCALES`, so `.get()` returns the fallback, `_LOCALES[DEFAULT_LOCALE]` (i.e. `en-US`'s spec). This means `format_currency(100, locale="fr-FR")` silently returns US-dollar-formatted output (`"$100.00"`) with NO error, warning, or any signal that the requested locale doesn't exist — a caller could ship a typo'd locale code (`"en-us"` lowercase, or `"EN-US"`, since the lookup is a case-sensitive dict key match with no normalization) and would see silently wrong currency symbols in production with zero indication of the mistake. This is a real, unguarded design choice: graceful degradation to a sensible default is defensible for a best-effort localization layer, but the complete silence (no logging, no exception even in a "strict mode") means a locale-code typo could go undetected for a long time.

## Q6: `register_locale`'s docstring says the built-in registry "covers this framework's verified use cases (US/UK/India)." What does "verified" mean here concretely, and what's the honest gap this implies?

Concretely, `_LOCALES` (i18n.py:36-41) ships exactly four entries: `en-US`, `en-GB`, `en-IN`, `hi-IN` — the last two sharing IDENTICAL specs (both `₹`, `.`/`,` separators, `%d/%m/%Y`, `grouping="indian"`) except for the locale code itself, which suggests `hi-IN` (Hindi-India) was added specifically to handle a user-facing locale PREFERENCE STRING that differs from `en-IN` even though the actual number/date formatting conventions are the same for both. The honest gap: this is a hardcoded, tiny table covering exactly the markets this specific framework's author verified (per the docstring's own wording, not a general claim of broad locale coverage) — there's no ISO 4217/CLDR-derived comprehensive locale database here the way `babel` or ICU would provide. Any of the world's other ~190 currencies/locales (EUR, JPY, or non-Gregorian date conventions) require a caller to manually construct and register their own `LocaleSpec` via `register_locale()` before use — this module is explicitly a minimal, hand-curated starting point, not a general i18n library, and says so.

## Q7: `register_locale` mutates the module-level `_LOCALES` dict with no locking. Is this actually a thread-safety concern given the module's stated design goal, and when would it matter?

`register_locale(spec)` (i18n.py:44-47) does `_LOCALES[spec.code] = spec` — a plain dict item assignment with no lock. Under CPython's GIL, a single dict `__setitem__` is atomic at the bytecode level, so a concurrent READER (`resolve_locale` doing `_LOCALES.get(...)`) won't see a torn/partially-constructed dict from a concurrent writer — that specific low-level hazard doesn't apply here. However, this is still architecturally in tension with the module's own core design principle (Q1/Q2): `register_locale` IS a form of shared mutable global state, unlike every other function in the file. If it were called repeatedly at REQUEST time rather than at startup (e.g. a caller mistakenly calling `register_locale` per-request to "customize" a locale on the fly), it would reintroduce exactly the kind of shared-global-state race the module otherwise avoids by design — two concurrent requests registering DIFFERENT specs under the SAME locale code could have one silently overwrite the other, and a THIRD request reading that code mid-write would get whichever version won the race. The module doesn't document or enforce "call this only at startup," so the safety property depends entirely on how a caller actually uses it, not on anything the code itself guarantees.

## Q8: The module docstring says a user's locale preference should be "stored on `MemoryStore.profiles`... not new framework state." Trace the intended integration: how would a caller actually retrieve and apply a user's locale using `i18n.py` and `context.py` together, and what could go wrong at the seam between them?

Per the docstring (i18n.py:13-16): `memory.update_profile(user_id, locale="en-IN")` (a `context.py` `MemoryStore` method) stores the preference, and a caller reads it back with `memory.get_profile(user_id).get("locale")`, then passes that value into `format_currency(amount, locale=that_value)`. The seam risk: `get_profile(user_id)` returns a plain `dict[str, Any]` (context.py's `MemoryStore.profiles`) with NO schema validation — nothing stops a caller (or a tool like `profile_write_tool` in `context.py`, which lets the AGENT ITSELF write arbitrary `field`/`value` pairs into a profile) from storing a malformed or nonsensical locale string, e.g. `field="locale", value="not-a-real-locale"`. Since `i18n.py`'s `resolve_locale` silently falls back to `DEFAULT_LOCALE` for any unrecognized code (Q5), this composition is forgiving rather than fragile — a garbage locale value from a profile write degrades to US-formatting rather than crashing — but the FAILURE is invisible: an agent that let a user's typo'd locale preference silently degrade to `en-US` currency formatting would have no way to know that happened from either module's code alone.

## Q9: Compare this module's approach to Python's stdlib `locale`/Babel's `babel.numbers`/`babel.dates`. What's the real engineering tradeoff being made, beyond "fewer dependencies"?

Stdlib `locale` requires the target locale to be INSTALLED on the operating system (`locale -a` on Linux/macOS must list it, or `setlocale` raises), which is a real deployment/portability headache for a container that needs to support many locales — you'd need to bake locale data into every container image. Babel ships a comprehensive, CLDR-derived locale database as a real dependency but handles vastly more cases correctly (pluralization rules, non-Gregorian calendars, RTL text direction, currency rounding conventions that vary by currency) than this module's four hand-curated `LocaleSpec` entries ever could. `i18n.py`'s tradeoff is explicit: zero install-time OS/package dependency, complete thread-safety by construction (no global state to synchronize, unlike stdlib `locale`), and full auditability (four `LocaleSpec` entries anyone can read start-to-finish in thirty seconds) — at the cost of only supporting exactly what's been hand-registered, with silent fallback rather than either raising or supporting the full range of real-world locale complexity (e.g. this module has no concept of pluralized strings at all — "1 item" vs "2 items" — since it only formats numbers/currency/dates, not translated text with plural forms).

## Q10: `format_date` takes `date | datetime` and calls `.strftime(...)`. What happens if a caller passes a naive vs. timezone-aware `datetime`, and does `LocaleSpec.date_format` account for time-of-day at all?

Every `LocaleSpec` in `_LOCALES` (i18n.py:37-41) uses a date-ONLY `strftime` pattern (`"%m/%d/%Y"`, `"%d/%m/%Y"`) — there is no time-of-day component (`%H:%M`) anywhere in the registry, and `format_date`'s signature/implementation (i18n.py:90-92) never inspects or uses timezone information even when given a timezone-aware `datetime` — `.strftime()` on an aware datetime simply formats the WALL-CLOCK fields already stored on that object, it does NOT convert to a different timezone as part of formatting. So passing a UTC-aware `datetime` versus an aware `datetime` already converted to `Asia/Kolkata` would produce DIFFERENT date strings depending on which side of midnight each falls on in ITS OWN stored timezone — `format_date` performs no timezone normalization or awareness-checking at all, which means correct date formatting for a specific locale's LOCAL calendar day is entirely the caller's responsibility (they must convert to the correct timezone themselves before calling this function). This is a reasonable scope boundary for a module this small, but it's an unstated one — a caller expecting `format_date(locale="en-IN")` to render "today, in India's timezone" would be surprised that no such conversion happens.

## Q11: What's a limitation of `i18n.py` you'd fix given more time?

The most impactful one is the completely silent fallback-to-default behavior for unknown locale codes (Q5) — for a governed, enterprise-facing framework, silently mis-formatting currency for an unrecognized locale (with zero logging, warning, or optional strict mode) is the kind of bug that could ship to production undetected, especially given how it composes with `context.py`'s unchecked, agent-writable `profiles` dict (Q8) — an LLM-driven tool call writing a slightly wrong locale string into a user's profile would silently and permanently degrade that user's currency formatting with no error trail to debug from. A second, smaller gap: `resolve_locale`'s dict lookup is case-sensitive with no normalization (`"en-us"` and `"EN-US"` both miss `_LOCALES`'s `"en-US"` key) — a simple `.strip()`/case-normalization pass in `resolve_locale` before the dict lookup would close a likely-common real-world typo class for free.
