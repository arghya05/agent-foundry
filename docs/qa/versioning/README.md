# agent_foundry/versioning.py — Q&A

A `VersionStore` Protocol plus `FileVersionStore`, a zero-dependency, append-only publish/rollback mechanism for prompts, policy documents, or any text artifact — every `publish()` writes a brand-new immutable version file and moves a `current` pointer, so `rollback()` is just moving that pointer back, and nothing is ever overwritten or deleted.

## Q1: `FileVersionStore.publish` (line 36) generates the version identifier as `str(time.time_ns())`. What's the concrete failure mode if two `publish()` calls for the SAME `name` happen within the same nanosecond (or the underlying OS clock's actual resolution is coarser than a nanosecond)?

`time.time_ns()` returns an integer count of nanoseconds since the epoch, but the *resolution* of the underlying system clock is platform-dependent and frequently coarser than one nanosecond — many systems only guarantee microsecond or even millisecond resolution in practice, meaning two calls to `time.time_ns()` in rapid succession (e.g., two concurrent threads calling `publish()` for the same `name` back-to-back) can legitimately return the identical integer. If that happens, both calls compute the same `version` string, and the second `publish()`'s writes — `(d / f"{version}.txt").write_text(content)`, `(d / f"{version}.label").write_text(label)`, `(d / "current").write_text(version)` — silently overwrite the first call's files at the exact same paths. This directly contradicts the module's own core promise, stated in the top-of-file docstring: "Nothing is ever overwritten, so full history is always recoverable." A version collision under concurrent publishing is precisely the scenario where that promise breaks — the first published version's content is silently lost, with no error, no warning, and no way for `history()` (which only lists filenames it finds on disk) to even reveal that a collision happened, since the collided version simply looks like one normal, singular version was published.

## Q2: `FileVersionStore` has no locking anywhere in its methods (`publish`, `get`, `rollback`, `history` all do plain, unsynchronized filesystem I/O). Walk through a concrete race between two threads calling `publish("prompt_v2", ...)` concurrently, focusing on more than just the version-collision from Q1 — what about the write-ordering of the three separate files per version?

Beyond the version-string-collision case, there's a second, independent race even when two publishes get *different* version strings: `publish` performs three separate, non-atomic file writes in sequence — the content file, the label file, then the `current` pointer file. If Thread A's `publish()` and Thread B's `publish()` interleave at the OS scheduler's discretion, it's possible for Thread A to write its content file, then Thread B fully completes all three of its writes (content, label, `current` now points to B's version), and only then does Thread A write ITS `current` pointer, overwriting Thread B's pointer to point back to A's earlier version — even though B's publish call returned successfully and its caller believes B's version is now "current." Neither publish call's data is corrupted individually (each version's `.txt`/`.label` files are written completely and correctly), but the `current` pointer ends up reflecting whichever thread happened to write it last, not necessarily the causally-latest publish — a classic lost-update race with no atomicity across the three writes or across concurrent callers. `get(name)` (no `version` argument) and `rollback`'s callers relying on "current means the most recently published version" get a wrong answer with no indication anything went wrong.

## Q3: `FileVersionStore.get` (line 44) does `version = current_file.read_text().strip()` then reads `(d / f"{version}.txt").read_text()`. What happens if `rollback()` runs on a DIFFERENT thread between those two lines?

This is a genuine time-of-check-to-time-of-use (TOCTOU) race, not merely a theoretical one: `get()` first reads the `current` pointer file to learn which version string to fetch (line 47-50), then performs a second, separate filesystem read for that specific version's content file (line 51). If another thread calls `rollback(name, version=<some_older_version>)` between those two operations, it rewrites the `current` file — but that doesn't actually affect the read already in flight, since `get()` already captured `version` as a local variable before `rollback` ran; `get()` will still successfully return the *previously*-current version's content (not the just-rolled-back-to one), which is at least not a crash, but is a stale read relative to what `current` says by the time `get()`'s caller receives the result. The more concerning race is the reverse: if a `rollback()` call swaps `current` to point to a version whose `.txt` file gets deleted by some external cleanup process (nothing in this module deletes version files itself, but nothing prevents an external retention/GC process built on top of this store from doing so) between `get()`'s two reads, `get()` would raise `FileNotFoundError` on the second read for a version that was valid when the pointer was read but isn't by the time the content read happens. Neither race causes data corruption (this store never overwrites version content, per Q1's caveat), but both illustrate that `FileVersionStore` provides no read-consistency guarantee across its two-step "read pointer, then read content" pattern.

## Q4: `rollback(name, *, version)` (line 53) validates that `(d / f"{version}.txt").exists()` before moving the pointer, raising `ValueError` if not. Is this validation actually race-free, or does it have the same class of gap as a classic TOCTOU bug?

It's the textbook check-then-act pattern: `if not (d / f"{version}.txt").exists(): raise ValueError(...)` followed, if the check passes, by `(d / "current").write_text(version)` as a separate operation — nothing atomically guarantees the file still exists at the moment of the actual pointer write. In this specific module, since nothing in `FileVersionStore` itself ever deletes a version file (there's no `delete()` method anywhere in the class), the file that just passed the existence check genuinely cannot disappear due to any operation *this module* performs — so in isolation, the TOCTOU window is not exploitable through this code alone. It becomes a real gap only if an external process (a retention policy, a manual cleanup script, an operator manually deleting old version files to save disk space) can delete version files concurrently with a `rollback()` call in flight — a scenario this module doesn't anticipate or guard against, since its own written-once/never-deleted design implicitly assumes it's the sole writer to its `directory` tree. The class's docstring promise ("nothing is ever overwritten, so full history is always recoverable") is honest about *this module's* behavior, but offers no defense if something outside this module violates that assumption on the same directory.

## Q5: `history(name)` (line 59) does `versions = sorted(p.stem for p in d.glob("*.txt"))`. Since `version` strings are `str(time.time_ns())` (a decimal integer as a string), does lexicographic string sorting actually produce chronological order?

Yes, but only because of a specific numeric property that holds today and could silently stop holding in the future: lexicographic (string) sorting of decimal-integer strings produces correct numeric ordering *if and only if all the strings have the same number of digits* — `"9" < "10"` numerically, but `"9" > "10"` lexicographically (`"9"` sorts after `"1"` since `'9' > '1'` as the first character comparison). `time.time_ns()` as of any date in the current epoch (nanoseconds since 1970) produces a consistently large number of digits (19 digits for dates in the 2020s-2100s range), so within that range, every version string generated has the same digit count, and lexicographic sort happens to coincide with numeric/chronological sort. This is a fragile, undocumented invariant rather than a deliberately engineered guarantee — `history()`'s correctness depends on `time.time_ns()` never producing a value with a different digit count than any other value it's being compared against, which holds for the foreseeable future (digit count only changes at specific nanosecond-since-epoch magnitude boundaries, centuries apart) but is exactly the kind of implicit assumption that a comment or a `key=int` in the `sorted()` call would make explicit and future-proof rather than leaving as an accident of how large `time.time_ns()`'s current output happens to be.

## Q6: `FileVersionStore.__post_init__` (line 27) does `self.directory = Path(self.directory); self.directory.mkdir(parents=True, exist_ok=True)`. What does `exist_ok=True` mean for the security posture of this store if `directory` is attacker-influenced or shared across tenants without additional scoping?

`exist_ok=True` simply means "don't raise if the directory already exists" — a purely functional convenience so repeated instantiation against the same path doesn't error — but it also means `FileVersionStore` will happily create and write into whatever `directory` (and, via `_artifact_dir`, whatever `name`-derived subdirectory) it's given without any validation that the path is safe or expected. Neither `__post_init__` nor `_artifact_dir` (line 31-34, `d = self.directory / name; d.mkdir(...)`) sanitizes `name` in any way — if `name` is ever influenced by untrusted input (e.g., an agent-chosen artifact name derived from a user's request, or a multi-tenant deployment where `name` might be tenant-supplied), a value like `"../../etc/some_path"` would resolve via `Path`'s `/` operator to a directory outside the intended `directory` tree entirely, a classic path-traversal pattern. `FileVersionStore` performs zero validation against this — it's implicitly designed for the case where `name` values come from trusted, internal callers (e.g., a fixed set of known prompt/policy artifact names hardcoded by the team, not end-user input), and using it with untrusted `name` values without an additional allowlist or sanitization layer in front of it would reintroduce a real path-traversal vulnerability that this module does nothing to prevent.

## Q7: Compare `FileVersionStore`'s "never overwrite, just move a pointer" design to how a real version-control system (Git) or a database's MVCC (multi-version concurrency control) achieves similar guarantees. What's structurally missing here that those systems have?

Git and MVCC-based databases both share the core idea this module borrows — never mutate existing data in place, always create new immutable versions and shift what "current" means — but both add integrity and concurrency-control layers `FileVersionStore` lacks entirely. Git's object store is content-addressed (objects are named by the SHA-1/SHA-256 hash of their content), so two different pieces of content can never collide under the same identifier, and any corruption or tampering is immediately detectable because the hash wouldn't match; `FileVersionStore`'s time-based version identifiers (Q1) have neither property — a version's name says nothing about its content, and there's no way to verify a version file hasn't been tampered with or corrupted after the fact. A real MVCC database uses transaction IDs and proper locking/compare-and-swap semantics to guarantee that concurrent writers never silently clobber each other's "current" pointer the way Q2 shows is possible here — typically via an atomic compare-and-swap on the pointer update, or full ACID transaction isolation. `FileVersionStore` gets the *append-only, keep-everything* half of the pattern right (a genuinely valuable property — "rollback is just moving the pointer back" is simple and correct in the *single-writer* case), but it's missing the concurrency-safety and tamper-evidence layers that make Git/MVCC systems safe under concurrent, potentially adversarial use — this reference implementation is correctly scoped for a single-writer-at-a-time operational model, not a concurrent or security-sensitive one.

## Q8: If `VersionStore` is used to version *prompts* specifically (per the module's stated use case), and an attacker somehow gained write access to the `directory` `FileVersionStore` operates on, what's the actual blast radius compared to, say, corrupting an `EgressPolicy` config?

If an attacker can write into `FileVersionStore`'s backing directory, they can create a brand-new "version" file with arbitrary content and then simply write that version's identifier into the `current` pointer file — `rollback()`'s own validation (Q4) only checks that A version file exists at that path, not that it's a version this module itself legitimately created via `publish()`, so an attacker with raw filesystem write access can inject a fully attacker-controlled prompt that `get(name)` will then serve as if it were a legitimately published version, with the injected content indistinguishable from a real, historically-published one once `current` points to it. For a prompt-versioning use case specifically, this is a severe, direct attack: whatever consumes `FileVersionStore.get("system_prompt")`'s return value presumably feeds it straight into the LLM's system prompt for every subsequent request, so a compromised `directory` becomes a direct system-prompt-injection vector with no cryptographic integrity check (no signature, no hash-chaining, nothing like Git's content-addressing from Q7) to detect the tampering — `history()` would even show the injected version sitting right alongside genuine ones with no way to distinguish them. Compare this to corrupting `EgressPolicy`'s config (`security.py`), which affects what hosts a given tool can reach — serious, but scoped to network egress; a compromised prompt version store can directly rewrite the agent's own instructions, which is a strictly more powerful attack primitive. This underscores that `FileVersionStore`'s `directory` deserves the same filesystem-permission rigor as any other security-sensitive configuration store, something the module's docstring doesn't call out explicitly.

## Q9: `history(name)` reads every `.label` file's content (line 66, one `read_text()` call per version) to build the returned list. For an artifact with thousands of published versions (e.g., a prompt iterated on daily for years), what's the performance characteristic of calling `history()`, and does anything in this module mitigate it?

`history()` does one `glob("*.txt")` filesystem scan (O(number of files in the directory)) and then, for every version found, up to two more filesystem operations (`.exists()` and `.read_text()` on the corresponding `.label` file) inside the list comprehension at line 63-69 — so the total cost scales linearly with the total number of versions ever published for that `name`, with no pagination, no limit parameter, and no caching anywhere in `FileVersionStore`. For an artifact published many times a day over years, `history()` becomes an increasingly expensive call every time it's invoked, since there's no way to ask for "just the last 20 versions" — the entire history must be enumerated and every label file read even if the caller only wants a small recent slice. This mirrors the same class of "reads the entire dataset just to return a small useful subset" performance gap flagged for `JSONLAuditLog.tail()` in `security.py` — a totally reasonable tradeoff for a reference implementation meant to demonstrate the pattern correctly, but a real production version of this store (backed by a database or object store with proper indexing/pagination) would need `history()` reworked to avoid the linear-scan-of-everything cost as version counts grow unbounded.

## Q10: `get`, `rollback`, and `history` all call `self._artifact_dir(name)` as their very first step, and `_artifact_dir` (line 31-34) unconditionally calls `d.mkdir(parents=True, exist_ok=True)` before returning. What's the concrete, verifiable side effect of calling `store.history("some_name_never_published")` — a purely read-looking operation — on a `name` that was never published at all?

It silently creates a brand-new, empty directory on disk at `self.directory / "some_name_never_published"`, purely as a side effect of `_artifact_dir` being called — `history()` never checks whether the artifact has ever been published before calling `_artifact_dir`, so even a read-only-looking call for a nonexistent artifact mutates the filesystem. The call then proceeds harmlessly (`d.glob("*.txt")` on the freshly-created empty directory yields nothing, so `history()` correctly returns `[]`), but the empty directory persists afterward regardless of whether anything was ever published there. This is a genuinely surprising implementation detail: a caller probing "does this artifact exist yet?" via `history(name)` or a failed `get(name)` (which also calls `_artifact_dir` before checking `current_file.exists()`) leaves filesystem clutter behind for every name it ever checked, published or not — and, combined with Q6's path-traversal concern, means even a *read* call with an attacker-influenced `name` (not just a `publish`/`rollback` write) can create directories outside the intended tree, expanding the path-traversal risk surface to every method in this class, not just the ones that write actual version content.

## Q11: `rollback(name, version=<old_version>)` moves the `current` pointer backward, but doesn't delete, hide, or otherwise mark as invalid any of the versions that were published *after* the version being rolled back to — they remain fully visible in `history()` and fully retrievable via `get(name, version=<newer_id>)`. If a caller then publishes a brand-new version right after a rollback, what does `history()`'s flat, timestamp-sorted list fail to capture about the artifact's actual lineage?

`history()`'s `sorted(p.stem for p in d.glob("*.txt"))` (line 62) produces a flat, purely chronological list with no notion of parent/child relationships between versions — unlike Git, where every commit explicitly records its parent commit hash, forming a real DAG, `FileVersionStore` has no equivalent of a "this version was published as a rollback-then-edit of version X" relationship anywhere in its data model. Concretely: if version 3 is published, then someone `rollback()`s to version 1, then publishes a new version 4 (based conceptually on version 1's content, not version 3's), `history()`'s flat, timestamp-ordered list shows `[1, 2, 3, 4]` in that order with no indication that version 4 is a logical descendant of version 1 rather than of version 3 — the fact that version 3 was "abandoned" via the rollback is completely invisible from `history()`'s output alone; you'd only infer it by separately knowing that a rollback to version 1 happened between versions 3 and 4 being published. This is a real limitation for anyone trying to reconstruct "what actually happened to this artifact over time" purely from `history()` — the underlying data (nothing is ever deleted, per the module's core promise) is sufficient to recover full content history, but the *causal/branching* structure of that history is lost, unlike a true version-control system's explicit lineage tracking.

## Q12: `get(name, version=<a version string that doesn't exist>)` raises a plain `FileNotFoundError` (via `(d / f"{version}.txt").read_text()` failing natively, line 51), while `rollback(name, version=<a version string that doesn't exist>)` raises an explicit `ValueError` (line 55-56, from a deliberate `if not ... exists(): raise ValueError(...)` check). Is this inconsistency in exception types for the "same" underlying problem (a version that doesn't exist) a real API design gap?

Yes — this is a legitimate rough edge in an otherwise small, clean API surface: a caller who wants to handle "the requested version doesn't exist" as a distinct, expected error case (as opposed to letting it propagate as an unhandled crash) has to catch two different exception types depending on which method they called, `FileNotFoundError` for `get()` versus `ValueError` for `rollback()`, even though both represent conceptually identical failures ("this version identifier isn't one that was ever published for this name"). `get()`'s `FileNotFoundError` is also somewhat accidental/implicit — it's simply whatever `pathlib.Path.read_text()` happens to raise when the target file doesn't exist, not a deliberately chosen, documented exception for this specific "unknown version" case — whereas `rollback()`'s `ValueError` is deliberate, with a clear, human-readable message (`f"no such version {version!r} for {name!r}"`). A more consistent design would either have both methods raise the same custom exception type (e.g., a `VersionNotFoundError` defined once in this module) or, at minimum, document clearly that callers need to catch different exception types for functionally equivalent failures across the two methods — as shipped, a generic `try: ... except FileNotFoundError` wrapped around a `get()` call would silently NOT catch the equivalent failure from a `rollback()` call on the same kind of bad input, a subtle trap for anyone writing shared error-handling logic across both methods.

## Q13: `VersionStore` is a `Protocol` (line 16) with `FileVersionStore` as its only implementation in this file. What would a production-grade, database- or object-store-backed `VersionStore` implementation need to additionally guarantee, beyond just implementing the same four method signatures, to actually fix the concurrency gaps from Q1-Q4 while remaining a drop-in replacement?

Implementing the same four signatures (`publish`, `get`, `rollback`, `history`) is necessary but not sufficient for a safe drop-in replacement — a caller relying on `VersionStore` as an abstraction is implicitly relying on certain *behavioral* guarantees the Protocol's type signature alone doesn't capture: that `publish()` is atomic (either a version is fully recorded with a unique, monotonically-assigned identifier and possibly becomes `current`, or nothing changes at all — no risk of the Q1/Q2 partial-write or collision races), that `rollback()`'s existence-check-then-pointer-update is a single atomic operation (no Q3/Q4-style TOCTOU window), and that `get()`/`history()` see a consistent snapshot rather than potentially torn state from a concurrent write. A database-backed implementation could deliver all of this cleanly using a proper transaction (an auto-incrementing or UUID version ID assigned inside the same transaction that inserts the content row, and a `current_version` column updated via the same transaction or a `SELECT ... FOR UPDATE`), and an object-store-backed one (S3 with versioning enabled, for instance) could lean on the store's own native object-versioning and conditional-write (`If-Match`/ETag) features to get atomicity without inventing it from scratch. The key point for someone evaluating whether to trust a new `VersionStore` implementation: the Protocol's type signature says nothing about these atomicity/consistency guarantees at all — verifying a new implementation is actually safe for concurrent use requires reading its actual concurrency-control approach, not just confirming it type-checks against `VersionStore`.

## Q14: `VersionStore.publish` doesn't return a `label`-derived identifier or any indication of *whether* this specific `content` differs from the currently-published version — every `publish()` call, even one that republishes byte-identical content, creates a brand-new version file and timestamp. Is that a bug, or a deliberate simplicity tradeoff, and what's the cost either way?

It's a deliberate simplicity tradeoff rather than a bug: `publish()` has no dedup logic (no comparison of `content` against the current version's content before deciding whether to actually write a new file), so calling `publish(name, same_content_as_before)` unconditionally creates a new, distinct version with its own fresh `time.time_ns()` identifier, even though nothing about the artifact's actual content changed. This keeps the implementation simple and avoids an extra content-comparison read on every publish, but it means `history(name)`'s version count doesn't correspond to "number of distinct content revisions" — it's "number of times `publish()` was called," which could be meaningfully larger if a caller republishes unchanged content repeatedly (e.g., a CI/CD pipeline that re-publishes a prompt on every deploy regardless of whether it changed). For an artifact where the audit-trail question "how many times did the actual prompt content change, and when" matters (a compliance-relevant question for a security-sensitive prompt), this reference implementation conflates "publish event" with "content change event," and a caller who cares about that distinction would need to implement their own dedup check (comparing new `content` against `store.get(name)`'s current value before deciding to call `publish()` at all) rather than relying on `FileVersionStore` to do it for them.

## Q15: Given everything in Q1-Q4 (version-collision races, non-atomic multi-file writes, TOCTOU windows), how would you actually design a test suite that gives confidence in `FileVersionStore`'s correctness without requiring a full rewrite of the class to be atomic first?

Two distinct tiers of testing are needed, and conflating them would give false confidence. The first tier is straightforward single-threaded correctness testing — publish a few versions, assert `get()` without a `version` argument returns the latest, assert `get(name, version=<specific>)` returns exactly that version's content, assert `rollback()` moves `current` correctly and `get()` reflects it afterward, assert `history()` returns entries in the right order with correct `current` flags — all of which this module's straightforward, side-effect-per-call design makes easy and fast to test with no mocking required (real temp directories via `tempfile.TemporaryDirectory`, no fakes needed). The second tier — actually exercising the Q1-Q4 races — requires deliberately concurrent tests (e.g., spawning multiple threads calling `publish()` for the same `name` simultaneously and checking whether any content is silently lost, or interleaving `rollback()` and `get()` calls across threads) and, honestly, such tests would very likely *fail* against the current implementation, which is exactly the point: writing them and marking them as expected-failures (or skipped with a clear comment referencing the known race) is more honest than not writing them at all, since their absence today means nobody has verified — and the concurrent behavior remains an open, undemonstrated gap — whether `FileVersionStore` behaves safely under any concurrent load, despite being the kind of store a multi-request-serving production system would naturally end up calling concurrently.
