# agent_foundry/core/native_orchestration.py — Q&A

The LangGraph-free counterparts of `orchestration.py`'s seven multi-agent topology builders (supervisor/swarm/blackboard/debate/fanout/dag), each duck-typing the same `.invoke(state, run_config)`/`.stream(...)` calling convention a compiled LangGraph graph exposes, so `Workflow.*`'s `runtime="native"` option works with zero changes to `core/agent.py`'s wrapper classes.

## Q1: Why does this module need `_PausableTurns` at all — what's actually wrong with each topology just calling `NativeEngine().run(specialist_config, messages)` directly per specialist turn?

A bare, ephemeral `NativeEngine()` constructed fresh for each specialist call, driven, and then discarded would work fine for a specialist turn that completes cleanly — but it would silently lose all state the instant that turn pauses for a tool-approval or critique-escalation interrupt, since `NativeEngine`'s pending state lives entirely inside `self._threads`/`self._thread_locks` on that one instance. A later `.resume()` call has no way to reconnect to "the exact `NativeEngine` instance whose `_act()` call was mid-loop" if that instance was already thrown away. `_PausableTurns` (lines ~74–130) solves this by keeping a dict of `{key: NativeEngine}` alive specifically for turns that paused (`_remember_or_forget` only evicts an engine once `result.get("__interrupt__")` is falsy — i.e., the turn actually finished), keyed by `f"{outer_thread_id}-{specialist_name}"`. This is the mechanism that makes topology-level human-in-the-loop possible at all — without it, a supervisor/swarm/blackboard/debate topology could pause a specialist's tool call but would have no way to resume that *same* specialist's *same* paused state on the next `.resume()` call.

## Q2: Walk through exactly what happens if a supervisor-routed specialist's tool call needs approval mid-turn — from `_NativeSupervisorGraph._drive_stream` all the way to a subsequent `.resume()`.

A fresh call to `_NativeSupervisorGraph.invoke(state, run_config)` with no `resume` attribute goes to `_drive_stream`'s `else` branch (line ~205): the user message is appended to `history`, `_resolve_supervisor_route(...)` picks a specialist `name`, and `self._turns.run(self._agents[name], list(history), key=f"{thread_id}-{name}")` is called. Inside `_PausableTurns.run` (line ~97), a **fresh** `NativeEngine()` is constructed, seeded directly by reaching into its private `_threads` dict (`engine._threads[key] = state`), and driven via `engine._drive(config, state, key)` while holding `engine._lock_for(key)`. If that specialist's turn hits an approval-needing tool call, `_drive` returns a dict with `__interrupt__` set (exactly as traced in the `core_native_engine` Q&A). `_remember_or_forget` sees `result.get("__interrupt__")` is truthy and stores `self._engines[key] = engine` — keeping that exact engine (and its mutated `state`) alive. Back in `_NativeSupervisorGraph._drive_stream`, `result.get("__interrupt__")` is truthy, so `self._paused[thread_id] = name` is recorded and the method yields `{"messages": ..., "thread_id": ..., "__interrupt__": ...}` and returns. A later `.invoke(Command(resume=...), run_config)` (or the native `_ResumePayload` equivalent) hits the `if resume_payload is not None:` branch: it looks up `name = self._paused.get(thread_id)`, then calls `self._turns.resume(self._agents[name], key=f"{thread_id}-{name}", approved=decision)` — `_PausableTurns.resume` retrieves the *same* kept-alive `engine` from `self._engines[key]` and calls `engine.resume(config, approved=approved, thread_id=key)`, continuing exactly where that specialist's `_act` left off.

## Q3: `_PausableTurns.run()` directly manipulates `NativeEngine`'s private attributes (`engine._threads_lock`, `engine._threads[key] = state`, `engine._lock_for(key)`) rather than calling any public method on `NativeEngine`. What does this say about the boundary between "public API" and "same-package collaborator" in this codebase?

`NativeEngine`'s actual public surface — `run`, `stream_run`, `resume` — always expects to *own* the decision of whether a given `thread_id` is new (creating fresh state) or continuing (loading existing state) via its own `_state_for`. `_PausableTurns` needs something neither of those methods offers: seed a specific engine instance with an **already-constructed** message history as if a turn were mid-flight, without going through `run()`'s "append this one new user message" semantics (the specialist's full turn history is passed in wholesale by the caller, not built up incrementally). Rather than adding a new public `NativeEngine` method just for this one internal caller, the code reaches directly into `_threads`/`_lock_for` — an explicit acknowledgment (via the comment on lines ~103–108) that this is a deliberate, same-package trade-off: `native_orchestration.py` and `native_engine.py` are treated as tightly-coupled collaborators within `core/`, not as strictly-separated public-API consumers, in exchange for not growing `NativeEngine`'s public surface with a method that has exactly one caller.

## Q4: `_NativeSwarmGraph` imposes `max_handoffs=25` to prevent an infinite loop between two specialists handing off to each other forever — but the LangGraph swarm graph has no such bound. Is this an improvement, a runtime-switching footgun, or both?

It's genuinely both. The class docstring (lines ~227–234) is explicit that this is "a genuinely possible (not hypothetical) infinite loop" and that "a native in-process loop with no bound at all would just hang the calling thread" — LangGraph's own graph-based execution model has its own (separate, LangGraph-level) recursion-limit protections that a raw Python `while True:` loop here simply doesn't get for free, so `max_handoffs` is a necessary safety net specific to *this* implementation's control-flow shape, not an arbitrary addition. But it is also a genuine behavioral divergence: a swarm configuration that happens to legitimately need more than 25 handoffs to converge (rare, but not impossible for a complex multi-specialist workflow) would silently succeed on `runtime="langgraph"` and silently truncate (falling through the `while True:` loop's `break` once `hops_done >= self._max_handoffs`, per line ~288) on `runtime="native"` — a caller switching runtimes for performance or dependency reasons could hit a behavior change they don't expect, with no error raised, just an early exit from the handoff chain.

## Q5: `_NativeFanoutGraph.__init__` raises `ValueError` if `config.critique is not None`, citing "the same race-condition reasoning as the LangGraph version." This file never actually explains what that race is. Is that a real gap, or is the reasoning self-evident from the code here?

It's a genuine cross-module documentation gap as written in *this* file: `_NativeFanoutGraph`'s docstring (lines ~480–487) and `__init__`'s error message both explicitly defer the explanation to `build_fanout_graph`'s own docstring in `orchestration.py`, which isn't one of the files reviewed here. Reading `_native_run_worker_messages` and `_NativeFanoutGraph._drive_stream` in isolation doesn't make the race obvious: each fanout worker gets its own fresh `NativeEngine()` and its own independent `state` dict (line ~146–150), so at first glance concurrent workers don't appear to share mutable per-turn state the way `_PausableTurns`' shared `_engines` dict does for supervisor/swarm/blackboard/debate. Without reading `orchestration.py`, the honest answer is: this file asserts the restriction and points elsewhere for the "why," but doesn't restate enough for a reader of *this* module alone to verify the claim — a legitimate, self-admitted (via the cross-reference) explanatory gap rather than something this file gets wrong, but still a real discoverability cost for anyone auditing `native_orchestration.py` on its own.

## Q6: `_NativeBlackboardGraph` deliberately never puts agent contributions into the returned `messages` list — they only ever land on the shared `Blackboard` object. Why replicate that "surprising" behavior rather than fix it in the native version?

The class docstring (lines ~303–309) calls this out as intentional parity: "Matches the LangGraph version's own (slightly surprising but deliberate) behavior exactly." `collaborate()` in the LangGraph version only ever returns `{"round": ...}`, never a `"messages"` key, so any caller of `Workflow.blackboard(...)` already has to read the shared `Blackboard` object to see what agents actually said, regardless of runtime. If the native version "fixed" this by also appending each specialist's raw reply into `history`/`messages`, then a caller switching between `runtime="langgraph"` and `runtime="native"` for the exact same blackboard workflow would get **different** result shapes back from `.invoke()` — breaking the entire cross-engine interchangeability promise this module exists to uphold. Keeping the "surprising" behavior consistent across both engines is more valuable than making either one individually more intuitive in isolation.

## Q7: Compare `_NativeDagGraph`'s wave-based `ThreadPoolExecutor` scheduling to how `build_dag_graph` achieves parallelism through LangGraph's own superstep model. Are the two guaranteed to execute steps in the same grouping for the same DAG?

`_NativeDagGraph._drive_stream` (lines ~551–565) computes `ready = [step for step in remaining.values() if all(dep in results for dep in step.depends_on)]` on every iteration of its `while remaining:` loop, then submits every currently-ready step to a `ThreadPoolExecutor` and waits (via `as_completed`) for the whole wave to finish before recomputing readiness for the next wave. This produces a specific, deterministic **wave** grouping: all steps whose dependencies are satisfied at time T run concurrently in the same `ThreadPoolExecutor` batch. LangGraph's own superstep model similarly runs every node whose incoming edges are all satisfied within one synchronous "step" concurrently, then advances — so the two *should* produce equivalent wave groupings for the same DAG shape, since both are computing readiness the same way (dependency-satisfaction, not any timing/completion-order heuristic). The comment on line ~535 ("No LLM involved — DAGStep is already framework-agnostic, reused unchanged") reinforces that `DAGStep` objects themselves carry the exact dependency graph both engines schedule against — the actual difference is implementation mechanism (raw `ThreadPoolExecutor` waves vs. LangGraph's own graph scheduler), not the logical grouping of which steps can run together.

## Q8: `_NativeDagGraph` raises `RuntimeError("DAG has unsatisfiable dependencies...")` when `ready` is empty but `remaining` is non-empty. What two distinct failure modes does that single check conflate, and could a caller tell them apart from the error alone?

The comment (line ~557) itself acknowledges this: "a cycle, or a step depending on an unknown step." Both produce the exact same symptom — some steps remain in `remaining` whose `depends_on` never all resolve into `results` — because a step depending on a name that's never a key in `self._steps` can *never* become satisfied (exactly like a cycle, where two steps depend on each other and neither's dependencies ever clear). The single `RuntimeError` message doesn't distinguish which case occurred, and a caller debugging this would have to manually inspect `self._steps`' `depends_on` lists to determine whether it's a genuine cycle or a simple typo/missing-step reference — a more diagnostic implementation could cross-reference `remaining`'s dependency names against the full set of known step names up front and raise a more specific error (e.g., naming the unknown dependency directly) before ever attempting to run anything.

## Q9: Why does `ThreadPoolExecutor(max_workers=min(len(items), self._max_concurrency) or 1)` include the `or 1` guard, and what happens if `items` is an empty list?

`ThreadPoolExecutor` raises `ValueError: max_workers must be greater than 0` if given `max_workers=0`; `min(len(items), self._max_concurrency)` would evaluate to `0` exactly when `items` is empty (since `min(0, anything) == 0`), so `or 1` prevents constructing an invalid, zero-worker pool in that edge case. Because `_NativeFanoutGraph._drive_stream`'s dict comprehension `{pool.submit(...): item for item in items}` (line ~522) simply produces an empty dict when `items` is empty, the pool would never actually be asked to run anything regardless of `max_workers` — the `or 1` guard exists purely to avoid `ThreadPoolExecutor`'s own constructor validation from raising on a scenario (zero items) that's otherwise handled gracefully (the loop over `as_completed(future_to_item)` — also empty — simply does nothing, and the final `yield {"messages": [], "thread_id": thread_id, "items": []}` fires immediately).

## Q10: Trace `_NativeSupervisorGraph._drive_stream`'s asymmetry: a fresh call appends `state["messages"][-1]` to `history` before routing, but a resumed call does **not** re-append anything. Why is that asymmetry correct?

On a fresh call (the `else` branch, line ~206), `state["messages"][-1]` is the caller's brand-new user message for this turn — it hasn't been recorded in `history` yet, so it must be appended before `_resolve_supervisor_route` is called (the router needs to see the full conversation including this new message to decide who should handle it). On a resumed call (the `if resume_payload is not None:` branch, line ~198), there is no new user message at all — a resume payload only carries `{"approved": ..., **decision}`, not a new turn of conversation; the `history` list already has everything it should, exactly as it was left when the turn paused. Appending anything to `history` on a resume would incorrectly inject a phantom message into the conversation that the user never actually sent. This mirrors `NativeEngine.resume()`'s own equivalent behavior (native_engine.py) of never appending a new user message on resume, only continuing from `state["_pending"]`.

## Q11: Each topology class (`_NativeSupervisorGraph`, `_NativeSwarmGraph`, `_NativeBlackboardGraph`, `_NativeDebateGraph`) constructs its own `_PausableTurns()` instance in `__init__`. Could two different topology instances' `_PausableTurns` keys (`f"{thread_id}-{specialist_name}"`) ever collide with each other?

No — because `_PausableTurns._engines` is an instance attribute (`self._engines: dict[str, NativeEngine] = {}`, line ~95) and each topology class constructs its own private `_PausableTurns()` (e.g., `self._turns = _PausableTurns()` inside `_NativeSupervisorGraph.__init__`), the key namespace is scoped per topology-graph instance, not shared globally across the whole process. Even if a `_NativeSupervisorGraph` and a `_NativeSwarmGraph` happened to use the exact same `thread_id` and specialist name (producing an identical key string), they'd be looking it up in two entirely separate `dict`s, so there's no cross-topology collision risk — the key convention only needs to be unique *within* one topology graph instance's own lifetime, which it is, since `thread_id` scopes conversations and `specialist_name` scopes which agent within that conversation.

## Q12: `_ThreadLocks.lock_for(thread_id)` is held for an entire multi-step turn (route + specialist run + history append) in every topology class here. What happens to a second concurrent request for the *same* `thread_id` while this lock is held, and what's the worst-case wait?

`_ThreadLocks.lock_for` (lines ~55–71) returns a real `threading.Lock()` per `thread_id`, and every topology's `_drive_stream` wraps its *entire* body in `with self._locks.lock_for(thread_id):` — meaning a second concurrent call for the same `thread_id` blocks on `Lock.acquire()` until the first call fully finishes: routing, running the specialist's complete turn (potentially several LLM calls and tool executions inside `_PausableTurns.run`/`.resume`), and appending to history. The worst case is the duration of an entire specialist turn — for a supervisor topology, that could be several sequential LLM round-trips plus tool executions, easily seconds, during which any other request touching that same conversation (including, notably, an unrelated caller trying to poll status or cancel) is fully blocked at the Python level. This is the same "hold the lock for the whole turn" discipline `NativeEngine` itself uses (its own class docstring makes the identical argument: the conversational history is mutated across several steps, not atomically), so it's a consistent design choice across the codebase, but it does mean per-thread concurrency is effectively zero within a single topology instance — only *different* `thread_id`s ever run concurrently.

## Q13: Neither `self._paused` (per topology class) nor `_PausableTurns._engines` ever gets cleaned up for a thread that's simply abandoned — a `Run` that pauses for approval and is never resumed. Is this a real memory-leak-shaped limitation?

Yes, and it's unaddressed anywhere in this file. `_NativeSupervisorGraph._paused[thread_id] = name` (and its `_NativeSwarmGraph`/`_NativeBlackboardGraph`/`_NativeDebateGraph` equivalents) is only ever removed via `self._paused.pop(thread_id, None)` on a *successful* resume-to-completion path — there's no TTL, no explicit `.cancel()`/`.forget()` API, and no background sweep. Likewise, `_PausableTurns._remember_or_forget` (line ~125) only evicts an engine from `self._engines` when a turn's result has no `__interrupt__` — an engine kept alive for a paused turn that's never resumed stays in that dict, holding its full `NativeEngine` (including its entire `_threads` state dict, i.e., the whole conversation history up to the pause point) for the lifetime of the topology graph instance. For a long-running server process fielding many independent conversations where some fraction predictably abandon pending approvals (a very real production pattern — a human reviewer who never gets to the approval queue item), both `_paused` and `_engines` grow unboundedly, and nothing in this module ever shrinks them. This is a genuine gap you'd want to fix with an explicit TTL-based eviction policy or a `Workflow`-level `.forget(thread_id)` API before running this in a long-lived process handling real HITL volume.

## Q14: How does this native-topology design compare to CrewAI's `Process.hierarchical` or AutoGen's `GroupChatManager` for implementing a manager/supervisor pattern without a graph execution engine?

CrewAI's hierarchical process and AutoGen's `GroupChatManager` both typically run entirely in-process and synchronously, with the "manager" logic and the participating agents' state living inside the same object graph for the duration of one call — neither has a first-class notion of "pause this multi-agent conversation for external human approval and resume it later, potentially from a different process" baked into the framework itself; that's usually left to the application layer to bolt on. `_NativeSupervisorGraph`/`_NativeSwarmGraph`/etc. bake exactly that concern in as a structural feature via `_PausableTurns`, specifically because this framework's `WorkflowEngine` contract (both LangGraph and native) already treats "the graph can pause mid-turn awaiting a human decision" as a first-class, expected code path for the single-agent case, and this module's whole purpose is extending that same guarantee to multi-agent topologies. The trade-off is the added complexity traced in Q1–Q3 (keeping engines alive across call boundaries, reaching into private attributes) — a cost CrewAI/AutoGen's simpler run-to-completion model doesn't pay, because it doesn't offer the same pause/resume guarantee.

## Q15: What's a concrete capability LangGraph's graph engine gives the `Workflow.*` topologies "for free" that this native module has to either forgo or re-implement by hand?

Cross-process durability and distributed execution are the clearest gaps: a real LangGraph checkpointer (Postgres-backed, for instance) can persist a paused multi-agent conversation's full graph state such that a *different* process — potentially on a different machine — can pick up and resume it later, and LangGraph's own scheduler can, in principle, distribute node execution. Every native topology class here keeps its state (`self._threads`, `self._paused`, `_PausableTurns._engines`) in plain in-process Python dicts with no persistence layer at all (unlike single-agent `NativeEngine`, which at least has an optional `state_store` plumbed through for cross-restart durability) — a process restart while any native topology has a paused thread loses that thread's pending state entirely, with no recovery path. Building equivalent durability into `native_orchestration.py` would mean giving every topology class the same kind of pluggable `StateStore` `NativeEngine` already has, persisting `history`/`_paused`/which-specialist-is-mid-turn at each step boundary — a nontrivial extension this module doesn't currently attempt.
